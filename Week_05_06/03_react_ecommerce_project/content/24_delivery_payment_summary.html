บทเรียน 24 · ชำระเงิน (Checkout)

ตัวเลือกจัดส่ง ชำระเงิน และสรุปคำสั่งซื้อ

Delivery, Payment & Order Summary

บทนี้เป็นบทสายผลิต: เราจะสร้างคอมโพเนนต์ที่เหลือทั้งหมดของหน้า Checkout รวดเดียว 6 ตัว แต่ก่อนลงมือ มาดูพิมพ์เขียวกันก่อน เพราะทั้ง 6 ตัวถูกออกแบบเป็นชั้น ๆ ตามหน้าที่ และการเห็นภาพนี้สำคัญกว่าโค้ดของตัวใดตัวหนึ่ง:

  • ชั้นล่างสุด — option components: DeliveryOption, PaymentOption เป็นคอมโพเนนต์ "โง่" (dumb/presentational) สุด ๆ — รับ props มา render เป็น radio หนึ่งแถว ไม่มี state ไม่รู้ด้วยซ้ำว่ามีตัวเลือกอื่นกี่ตัว
  • ชั้นกลาง — box components: CheckoutDeliveryBox, CheckoutPaymentBox วนลูปรายการจาก consts.ts มาสร้าง option หลาย ๆ แถว และรับ "id ที่ถูกเลือก" กับ callback มาเป็น props — ตัวมันก็ยังไม่ own state การเลือก แค่ส่งต่อ
  • ฝั่งขวาของหน้า: SummaryOrder + SummaryOrderItem แสดงรายการสินค้าจากตะกร้า และ BillingSummary แสดงยอดรวมพร้อมปุ่ม Place Order
  • เจ้าของ state ตัวจริง: hook useCheckout ในบทที่ 25 — มันจะถือทั้งที่อยู่ ทั้ง id จัดส่ง/ชำระเงินที่เลือก แล้วแจกลงมาให้ทุกกล่องผ่านหน้าเพจ

ท่านี้คือท่าเดียวกับ CheckoutAddressBox เมื่อบทที่แล้ว: คอมโพเนนต์เล็กโง่ที่สุดเท่าที่จะโง่ได้ state ลอยขึ้นไปรวมที่จุดเดียวข้างบน ผลตอบแทนคือทุกตัวในบทนี้ทดสอบง่าย ใช้ซ้ำได้ และอ่านจบใน 30 วินาที

DeliveryOption — radio หนึ่งแถวของวิธีจัดส่ง

สร้าง src/features/checkout/components/DeliveryOption/DeliveryOption.tsx:

import React from "react";
import RadioInput from "@/shared/components/RadioInput/RadioInput";

interface DeliveryOptionProps {
  id: number;
  name: string;
  description: string;
  selected: boolean;
  onSelect: (id: number) => void;
}

const DeliveryOption: React.FC<DeliveryOptionProps> = ({
  id,
  name,
  description,
  selected,
  onSelect,
}) => {
  return (
    <RadioInput
      id={`delivery-option-${id}`}
      name="deliveryOption"
      checked={selected}
      onChange={() => onSelect(id)}
      label={
        <>
          <span className="mr-5">{name}</span>|
          <span className="ml-5">{description}</span>
        </>
      }
    />
  );
};

export default DeliveryOption;

นี่คือผลตอบแทนของแรงที่ลงไปในบทที่ 09 — RadioInput ที่เราสร้างไว้จัดการเรื่อง input + label + การจับคู่ htmlFor ให้หมดแล้ว คอมโพเนนต์นี้เลยเหลือแค่งานแปลงร่าง: รับข้อมูล delivery หนึ่งตัว มาประกอบเป็น props ให้ RadioInput

  • id={`delivery-option-${id}`} — DOM id ต้องไม่ซ้ำกันทั้งหน้า เราเลยผูกกับ id ของตัวเลือก จะได้ delivery-option-1, delivery-option-2 คลิกที่ label แล้ว radio ติดเพราะ id นี้แหละ
  • name="deliveryOption" — radio ที่ name เดียวกันเป็นกลุ่มเดียวกันในสายตาเบราว์เซอร์ เลือกได้ทีละตัว
  • checked={selected} กับ onChange={() => onSelect(id)} — ตัวมันไม่ตัดสินใจอะไรเอง ข้างบนบอกว่าถูกเลือกก็แสดงว่าถูกเลือก ผู้ใช้คลิกก็แค่ตะโกน id ของตัวเองขึ้นไป
  • label รับ JSX ได้ — จำได้ไหมว่าเราประกาศ prop นี้เป็น React.ReactNode ไว้ ทำให้ยัด markup อย่าง ชื่อ + เส้นคั่น + คำอธิบาย ลงไปได้เลย ไม่ใช่แค่ string

โครงเหมือน DeliveryOption ทั้งดุ้น ต่างกันแค่ name ของกลุ่ม radio กับหน้าตาของ label — ฝั่ง payment ใช้สองบรรทัด: ชื่อวิธีจ่ายตัวหนา คำอธิบายสีจางข้างใต้ คุณอาจสงสัยว่าทำไมไม่ยุบสองตัวนี้เป็นคอมโพเนนต์เดียวแล้วส่ง label เข้ามา — ทำได้ แต่สองตัวนี้เป็นคนละ concept ทางธุรกิจที่บังเอิญหน้าตาคล้ายกันวันนี้ วันที่ payment ต้องโชว์ไอคอนบัตรเครดิตหรือ delivery ต้องโชว์ราคา การแยกไว้แต่แรกทำให้ต่างคนต่างโตได้โดยไม่พันกัน

CheckoutDeliveryBox — กล่องรวมตัวเลือกจัดส่ง

ขยับขึ้นชั้นกลาง สร้าง src/features/checkout/components/CheckoutDeliveryBox/CheckoutDeliveryBox.tsx:

import styles from "./CheckoutDeliveryBox.module.scss";
import { DeliveryOption as TDeliveryOption } from "@/features/checkout/types";
import DeliveryOption from "@/features/checkout/components/DeliveryOption/DeliveryOption";

interface CheckoutDeliveryBox {
  title: string;
  selectedDeliveryId: number;
  deliveryOptions: TDeliveryOption[];
  onSelectOption: (id: number) => void;
}

const CheckoutDeliveryBox: React.FC<CheckoutDeliveryBox> = ({
  title,
  deliveryOptions,
  selectedDeliveryId,
  onSelectOption,
}) => {
  return (
    <div className={`${styles.container} p-20`}>
      <h3 className="fs-20 pb-10">{title}</h3>
      <hr className="mb-20" />

      {deliveryOptions.map(({ id, name, description }) => (
        <div key={id} className="mb-10">
          <DeliveryOption
            id={id}
            name={name}
            description={description}
            selected={id === selectedDeliveryId}
            onSelect={onSelectOption}
          />
        </div>
      ))}
    </div>
  );
};

export default CheckoutDeliveryBox;

คู่กับ style ของมัน CheckoutDeliveryBox.module.scss:

@use "../../../../styles/variables";

.container {
  background-color: variables.$grey05;
}

สามจุดที่น่าหยุดดู:

  • import { DeliveryOption as TDeliveryOption } — ไฟล์นี้อยากใช้ชื่อ DeliveryOption สองความหมาย: เป็น type จาก types.ts และเป็น component จากบนหัวบทนี้ ชื่อชนกันตรง ๆ เราเลย rename ฝั่ง type ตอน import เป็น TDeliveryOption (T นำหน้า = type) — ท่ามาตรฐานเวลา type กับ component ชื่อพ้องกัน
  • บรรทัดสำคัญที่สุดคือ selected={id === selectedDeliveryId} — กล่องแปลง "id ที่ถูกเลือก" (ข้อมูลชิ้นเดียว) ให้กลายเป็น boolean รายตัว: ตัวที่ id ตรงได้ true ที่เหลือได้ false การเลือกทีละตัวเลยเกิดขึ้นเองโดยไม่ต้องมี logic ยกเลิกตัวเก่า
  • onSelect={onSelectOption} — callback ถูกส่งผ่านลงไปเฉย ๆ พอผู้ใช้คลิก Express Delivery ข้อความ "เลือก id 2 แล้วนะ" จะวิ่งจาก RadioInput → DeliveryOption → กล่องนี้ → หน้าเพจ → useCheckout แล้วค่าที่อัปเดตก็ไหลย้อนกลับลงมาเป็น selectedDeliveryId ตัวใหม่ — วงจร one-way data flow ครบรอบ

เกร็ด TypeScript: ไฟล์นี้ประกาศ interface CheckoutDeliveryBox ชื่อเดียวกับตัว component เป๊ะ ๆ ซึ่ง TypeScript ยอมให้ทำได้ เพราะ type กับค่า (value) อยู่คนละ namespace กัน — อ่านแล้วอย่าเพิ่งงงว่าทำไม compile ผ่าน

SummaryOrderItem — สินค้าหนึ่งแถวในใบสรุป

ข้ามมาฝั่งขวาของหน้า: ใบสรุปคำสั่งซื้อ เริ่มจากหน่วยเล็กสุดก่อน สร้าง src/features/checkout/components/SummaryOrderItem/SummaryOrderItem.tsx:

import React from "react";
import styles from "./SummaryOrderItem.module.scss";
import { CartItem } from "@/features/cart/store/CartContext";

interface SummaryOrderItemProps {
  item: CartItem;
}

const SummaryOrderItem: React.FC<SummaryOrderItemProps> = ({ item }) => {
  const { title, price, quantity, id, image } = item;

  return (
    <div key={id} className={`flex align-item-center`}>
      <img className={`${styles.image} mr-10`} src={image} alt={title} />
      <div className="flex-grow">
        <p className="fs-16 fw-medium mb-5">{title}</p>
        <p className="fs-14 text-muted">
          ${price.toFixed(2)} X {quantity}
        </p>
      </div>
      <div className="fs-16 fw-bold text-primary">
        ${(price * quantity).toFixed(2)}
      </div>
    </div>
  );
};

export default SummaryOrderItem;

กับ SummaryOrderItem.module.scss ที่สั้นที่สุดในคอร์ส:

.image {
  width: 60px;
}

จุดที่น่าสนใจที่สุดของไฟล์นี้คือบรรทัด import: import { CartItem } from "@/features/cart/store/CartContext"; — คอมโพเนนต์ของ feature checkout ไป import type จาก feature cart นี่ไม่ใช่การละเมิดสถาปัตยกรรม แต่เป็นการยอมรับความจริงของ domain: ใบสรุปคำสั่งซื้อแสดง "ของในตะกร้า" โดยนิยาม ข้อมูลนั้นเป็นของ cart และ cart เป็นคนนิยามรูปร่างมัน การประกาศ type ใหม่ฝั่ง checkout ให้หน้าตาเหมือนกันจะสร้าง drift แบบเดียวกับที่เราหนีมาตั้งแต่บทที่ 22 — feature หนึ่งพึ่ง type สาธารณะ ของอีก feature ได้ ตราบใดที่พึ่งในทิศทางที่ make sense ตาม flow ของธุรกิจ (checkout เกิดหลัง cart เสมอ)

ที่เหลือคืองานแสดงผลตรง ๆ: รูปเล็ก 60px, ชื่อสินค้า, ${price.toFixed(2)} X {quantity} บรรทัดจาง ๆ และราคารวมต่อรายการ (price * quantity) ตัวหนาสีแบรนด์ชิดขวาด้วย flex-grow ตรงกลางที่ดันมันออกไป

SummaryOrder — ใบสรุปที่อ่านตะกร้าเอง

สร้าง src/features/checkout/components/SummaryOrder/SummaryOrder.tsx:

import React from "react";
import styles from "./SummaryOrder.module.scss";
import { useCart } from "@/features/cart/useCart";
import SummaryOrderItem from "@/features/checkout/components/SummaryOrderItem/SummaryOrderItem";

const SummaryOrder: React.FC = () => {
  const { cart } = useCart();

  return (
    <div className={`${styles.container} p-20`}>

        <div className="mb-15" key={item.id}>
          <SummaryOrderItem item={item} />
        </div>
      ))}
    </div>

และ SummaryOrder.module.scss:

@use "../../../../styles/variables";

.container {
  background-color: variables.$grey05;
}

ตัวนี้แหวกแนวจากเพื่อนร่วมบทนิดหนึ่ง: มันไม่รับ props เลย แต่เรียก useCart() ดึงข้อมูลตะกร้าจาก context ตรง ๆ (hook จากบทที่ 19) ทำไมไม่ส่ง cart.items ลงมาเป็น prop เหมือนตัวอื่น? เพราะข้อมูลตะกร้ามีเจ้าของอยู่แล้วใน CartProvider ระดับแอป การให้หน้าเพจอ่านจาก context แล้วส่งต่อลงมาอีกทอดเป็นแค่การเพิ่ม prop-drilling โดยไม่ได้อะไรเพิ่ม ต่างจาก "id ที่เลือก" ของ delivery/payment ซึ่งเป็น state ที่เกิดในหน้า Checkout เองจึงต้องไหลผ่าน props — เกณฑ์การตัดสินใจคือ state เป็นของใคร ไม่ใช่ความเคยชิน

BillingSummary — ยอดเงินและปุ่มชี้ชะตา

ชิ้นสุดท้ายของบท สร้าง src/features/checkout/components/BillingSummary/BillingSummary.tsx:

import React from "react";
import styles from "./BillingSummary.module.scss";
import Button from "@/shared/components/Button/Button";

interface BillingSummaryProps {
  subTotal: number;
  shipping: number;
  total: number;
  isLoading: boolean;
  isDisabled: boolean;
  onPlaceOrder: () => void;
}

const BillingSummary: React.FC<BillingSummaryProps> = ({
  subTotal,
  shipping,
  total,
  isLoading = false,
  isDisabled = false,
  onPlaceOrder,
}) => {
  return (
    <div className={`${styles.container} p-20`}>
      <h3 className="fs-20 fw-bold mb-20">Billing Summary</h3>
      <hr className="mb-20" />
      <div className="flex justify-between mb-10">
        <span className="fs-18 text-muted">Sub Total</span>
        <span className="fs-18 text-primary">${subTotal.toFixed(2)}</span>
      </div>
      <div className="flex justify-between mb-10">
        <span className="fs-18 text-muted">Shipping</span>
        <span className="fs-18 fw-medium text-primary">
          ${shipping.toFixed(2)}
        </span>
      </div>
      <hr className="mb-20" />
      <div className="flex justify-between mb-20">
        <span className="fs-24 fw-bold">Total</span>
        <span className="fs-24 fw-bold text-primary">${total.toFixed(2)}</span>
      </div>

      <Button
        className="width-full"
        onClick={onPlaceOrder}
        isLoading={isLoading}
        disabled={isDisabled}
      >
        Place Order
      </Button>
    </div>
  );
};

export default BillingSummary;

ปิดท้ายด้วย BillingSummary.module.scss:

@use "../../../../styles/variables";

.container {
  background-color: variables.$grey05;
}

BillingSummary เป็น presentational แท้ ๆ อีกตัว: รับตัวเลขสามตัว (subTotal, shipping, total) มาแสดง ไม่คำนวณอะไรเองเลยสักบาท — การคำนวณทั้งหมดจะอยู่ใน useCheckout ซึ่งเป็นที่เดียวที่รู้ทั้งของในตะกร้าและค่าส่งของ delivery ที่ถูกเลือก การแยกแบบนี้ทำให้บทที่ 27–29 เราเทสต์ "คำนวณถูกไหม" กับ "แสดงผลถูกไหม" แยกจากกันได้อย่างสะอาด

ส่วนปุ่ม Place Order ใช้ของเก่าจากบทที่ 09 คุ้มมาก:

  • isLoading — ตอนบทหน้าเรายิงคำสั่งซื้อขึ้น API ปุ่มจะเปลี่ยนเป็น ClipLoader หมุน ๆ อัตโนมัติ เพราะ Button ของเรารองรับ prop นี้อยู่แล้ว
  • disabled={isDisabled} — บทหน้าเราจะส่งเงื่อนไข "ยังไม่ได้กรอกที่อยู่" เข้ามาทางนี้ กันผู้ใช้กดสั่งซื้อทั้งที่ข้อมูลไม่ครบ
