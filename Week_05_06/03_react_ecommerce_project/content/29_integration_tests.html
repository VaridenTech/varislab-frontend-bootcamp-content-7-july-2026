Integration Tests: ทดสอบทั้งหน้าเหมือนผู้ใช้จริง

Integration Tests

ถึงยอดพีระมิดแล้ว: integration test ระดับทั้งหน้า คราวนี้เราไม่เรียกฟังก์ชันหรือ hook ตรง ๆ อีกต่อไป — เราจะเปิดแอปทั้งแอปขึ้นมาด้วย renderRoute ที่สร้างไว้ในบทที่ 26 (router จริง provider จริง component จริง มีแค่ network ที่เป็น MSW) แล้วทำแบบที่ผู้ใช้ทำ: อ่านข้อความบนจอ คลิกปุ่ม พิมพ์ฟอร์ม จากนั้น assert สิ่งที่ผู้ใช้ควรเห็น เทสต์ชั้นนี้แต่ละตัวจึงพิสูจน์การประกอบร่างของทุกอย่างที่เราสร้างมา 25 บท — routing, queries, context, ฟอร์ม, component — ว่าต่อติดกันจริง

ก่อนลงมือ มีเครื่องมือสองเรื่องที่ต้องเข้าใจให้เคลียร์ เพราะเทสต์ทุกตัวในบทนี้ใช้:

findBy กับ getBy — ต่างกันที่การรอ

query ของ Testing Library มีสามตระกูล เลือกใช้ตามสถานการณ์:

  • getBy... — หาเดี๋ยวนี้ ไม่เจอโยน error ทันที เหมาะกับ element ที่ต้องอยู่บนจอแล้วแน่ ๆ
  • await findBy... — หาแบบรอได้ (retry จนเจอหรือครบ timeout ~1 วินาที) เหมาะกับ element ที่จะโผล่หลังงาน async — ซึ่งในแอปเราคือ "แทบทุกอย่าง" เพราะเปิดหน้ามาจะเจอ spinner ก่อนเสมอ ระหว่างที่ TanStack Query ยิง request ไป MSW ข้อมูลถึงจะมา
  • queryBy... — หาแล้วคืน null ถ้าไม่เจอ (ไม่โยน error) มีไว้สำหรับ assert ว่าอะไรไม่อยู่บนจอ

กฎหัวแม่มือของบทนี้: หลัง render หรือหลัง action ที่ทำให้เกิดการยิง API — ใช้ findBy ตัวแรกเป็น "ประตูรอ" ให้หน้าโหลดเสร็จ หลังจากนั้นของที่อยู่บนจอแล้วใช้ getBy ได้เลย

user-event ไม่ใช่ fireEvent

Testing Library มี fireEvent ที่ยิง DOM event ดิบ ๆ ทีละลูก แต่เราจะใช้ user-event ทั้งบท เพราะมันจำลองพฤติกรรมผู้ใช้ทั้งลำดับ: การคลิกหนึ่งครั้งของ user-event คือ pointer move → pointer down → focus → pointer up → click และการพิมพ์คือ keydown/keypress/keyup ทีละตัวอักษร ผลคือมันเจอ bug ที่ fireEvent มองข้าม เช่น ปุ่มที่ถูก disabled หรือ input ที่อ่านค่าจาก keyboard event — user-event จะคลิกปุ่ม disabled ไม่ได้เหมือนผู้ใช้จริงนั่นแหละ ท่าใช้มาตรฐานคือ const user = userEvent.setup() ต้นเทสต์ แล้ว await ทุกการกระทำ (ทุก method ของมันเป็น async)

หน้า Home — เทสต์ควันไฟ

เริ่มจากเทสต์ที่เรียบที่สุดแต่คุ้มที่สุด สร้าง src/pages/Home/Home.test.tsx:

import { screen } from "@testing-library/react";
import { renderRoute } from "@/test/renderRoute";

describe("Home page", () => {
  it("renders deal products and category products from the API", async () => {
    renderRoute("/");

    expect(await screen.findByText("Product 1")).toBeInTheDocument();
    expect(await screen.findByText("beauty product 1")).toBeInTheDocument();
  });
});

สามบรรทัดในตัวเทสต์ แต่ดูสิ่งที่มันพิสูจน์: renderRoute("/") เปิดแอปที่หน้าแรก — route table จริงต้อง match, MainLayout กับ Header/Footer ต้อง render, หน้า Home ยิงสาม query (best products, categories, สินค้าตาม category) ผ่าน axios + interceptor ไปเจอ MSW แล้วสองบรรทัด findByText รอจนข้อมูลจากคนละ endpoint ขึ้นจอ: Product 1 มาจากแถว DEALS OF THE DAY ที่ใช้ productQueries.list({ limit: 5 }) (fixture ตั้งชื่อว่า Product N) ส่วน beauty product 1 มาจาก section ล่างที่ query ตาม category แรกคือ beauty — ถ้าจุดไหนในสายนั้นหลุดสักจุดเดียว เทสต์นี้แดง มันคือ "smoke test" ที่บอกใน 1 เทสต์ว่าแกนกลางของแอปยังหายใจอยู่

หน้า Category — คลิกเปลี่ยนหมวด คลิกเปลี่ยนหน้า

คราวนี้เพิ่ม interaction เข้ามา สร้าง src/pages/Category/Category.test.tsx:

import { screen } from "@testing-library/react";
import userEvent from "@testing-library/user-event";
import { renderRoute } from "@/test/renderRoute";

describe("Category page", () => {
  it("switches category and pages through results", async () => {
    const user = userEvent.setup();
    renderRoute("/categories");

    expect(await screen.findByText("beauty product 1")).toBeInTheDocument();

    // The Footer also lists "Fragrances" as a static (non-interactive) <li>;
    // scope to the clickable CategoryMenu <span> to avoid ambiguity.
    await user.click(screen.getByText("Fragrances", { selector: "span" }));
    expect(await screen.findByText("fragrances product 1")).toBeInTheDocument();

    await user.click(screen.getByText("2"));
    expect(
      await screen.findByText("fragrances product 21"),
    ).toBeInTheDocument();
  });
});

เทสต์เดียวเดินสามจังหวะ และแต่ละจังหวะมีบทเรียน:

  • จังหวะแรก — เปิด /categories รอ beauty product 1 (หมวดแรกจาก fixture คือค่าเริ่มต้น)
  • จังหวะสอง: ปัญหา element ซ้ำ — จะคลิกคำว่า "Fragrances" ใน CategoryMenu แต่เพราะเรา render ทั้งแอปผ่าน MainLayout — Footer ก็มีคำว่า Fragrances อยู่ด้วย (เป็น <li> ประดับเฉย ๆ) ถ้าใช้ getByText("Fragrances") ตรง ๆ Testing Library จะโยน error "found multiple elements" ทางแก้ในไฟล์นี้คือ option selector: "span" — จำกัดผลลัพธ์เฉพาะ <span> ซึ่งคือตัวที่คลิกได้ใน CategoryMenu นี่คือตัวอย่างจริงของราคาที่จ่ายให้ integration test: จอมีของเยอะ ต้องระบุเป้าให้แม่น
  • จังหวะสาม: pagination — คลิกปุ่ม "2" ของ react-paginate แล้วรอ fragrances product 21 — เลข 21 ไม่ใช่เลขสุ่ม: หน้า 2 × หน้าละ 20 → skip 20 → handler ตั้งชื่อสินค้าตัวแรกเป็นลำดับ 21 เท่ากับพิสูจน์ทั้ง derived pagination state ของหน้า Category, การส่ง skip ใน request และ UX ของ keepPreviousData (รายการเก่ายังคาอยู่ระหว่างโหลด — เหตุผลที่ต้องใช้ findBy รอรายการใหม่)

หน้า Cart — ปรับจำนวน ลบสินค้า

หน้า Cart ไม่ยิง API เลย — state ทั้งหมดมาจาก CartProvider + localStorage สร้าง src/pages/Cart/Cart.test.tsx:

import { screen } from "@testing-library/react";
import userEvent from "@testing-library/user-event";
import { CART_STORAGE_KEY } from "@/features/cart/store/cartStorage";
import { renderRoute } from "@/test/renderRoute";

function seedCart() {
  localStorage.setItem(
    CART_STORAGE_KEY,
    JSON.stringify({
      items: [
        { id: 1, title: "Widget", price: 10, quantity: 1, image: "/w.png" },
      ],
    }),
  );
}

describe("Cart page", () => {
  it("shows the empty state when there are no items", async () => {
    renderRoute("/cart");
    expect(await screen.findByText("Your Cart is Empty")).toBeInTheDocument();
  });

  it("updates quantity and total", async () => {
    const user = userEvent.setup();
    seedCart();
    renderRoute("/cart");

    expect(await screen.findByText("Widget")).toBeInTheDocument();
    expect(screen.getByText("Total Price: $10.00")).toBeInTheDocument();

    await user.click(screen.getByRole("button", { name: ">" }));
    expect(screen.getByText("Total Price: $20.00")).toBeInTheDocument();
  });

  it("removes an item", async () => {
    const user = userEvent.setup();
    seedCart();
    renderRoute("/cart");

    await user.click(await screen.findByRole("button", { name: "×" }));
    expect(await screen.findByText("Your Cart is Empty")).toBeInTheDocument();
  });
});

เทคนิคเด่นของไฟล์นี้:

  • seedCart() — ท่าเดิมจากบทที่แล้ว: เขียน localStorage ก่อน render ให้ CartProvider lazy init ไปเจอของ ประกาศเป็นฟังก์ชันเพราะใช้สองเทสต์ (เทสต์ empty state ไม่ seed — และมั่นใจได้ว่าตะกร้าว่างจริงเพราะ afterEach ล้าง storage ให้ทุกเทสต์)
  • หา element ด้วย role — getByRole("button", { name: ">" }) คือปุ่มเพิ่มจำนวนใน CartTable (name ของปุ่มคือข้อความในปุ่ม) การหาแบบ role ตรงกับที่ screen reader มองเห็น จึงเป็น query ที่ Testing Library แนะนำสุด — ได้เทสต์ accessibility แถมโดยไม่ต้องพยายาม
  • สังเกตจุดที่ใช้ getBy ได้ — หลังผ่านประตู findByText("Widget") แล้ว การคลิกเพิ่มจำนวนเป็น state update ล้วน (ไม่มี network) React ประมวลผลเสร็จก่อน await user.click คืนค่า — ยอดเงิน Total Price: $20.00 จึง assert ด้วย getByText ได้ทันที ตัวเลขนี้ยังพิสูจน์ useMemo ที่คำนวณยอดรวมและ toFixed(2) ในหน้า Cart ด้วย
  • เทสต์ลบ — คลิกปุ่ม × แล้วหน้าต้องเด้งกลับไป empty state ครบวงจร: มีของ → ลบ → ว่าง

หน้า Checkout — happy path จากฟอร์มถึง Order Success

เทสต์สุดท้ายคือเทสต์ที่ "จริง" ที่สุดในชุด: เดิน flow สั่งซื้อทั้งเส้นเหมือนลูกค้าคนหนึ่ง สร้าง src/pages/Checkout/Checkout.test.tsx:

import { screen, waitFor } from "@testing-library/react";
import userEvent from "@testing-library/user-event";
import { CART_STORAGE_KEY } from "@/features/cart/store/cartStorage";
import { renderRoute } from "@/test/renderRoute";

describe("Checkout page", () => {
  it("places an order and navigates to the success page", async () => {
    const user = userEvent.setup();
    localStorage.setItem(
      CART_STORAGE_KEY,
      JSON.stringify({
        items: [
          { id: 1, title: "Widget", price: 10, quantity: 2, image: "/w.png" },
        ],
      }),
    );

    const { router } = renderRoute("/checkout");

    await user.type(screen.getByPlaceholderText("Enter Address"), "1 Main St");
    await user.type(
      screen.getByPlaceholderText("Enter Email"),
      "jane@example.com",
    );
    await user.type(
      screen.getByPlaceholderText("Enter Phone Number"),
      "0812345678",
    );
    await user.click(screen.getByRole("button", { name: "Submit" }));

    await user.click(screen.getByRole("button", { name: /place order/i }));

    await waitFor(() =>
      expect(router.state.location.pathname).toBe("/order/success"),
    );
    expect(screen.getByText("Order Placed Successfully!")).toBeInTheDocument();
  });
});

ไล่ตาม flow แล้วนับดูว่าเทสต์เดียวนี้แตะกี่ระบบ:

  • พิมพ์สามช่องด้วย user.type — หา input จาก placeholder (ข้อความเดียวกับที่ผู้ใช้ใช้หาช่องกรอกนั่นแหละ) แล้วกด Submit — จังหวะนี้ react-hook-form + zodResolver ทำงานจริง: ถ้าข้อมูลไม่ผ่าน schema ฟอร์มจะไม่ submit และ storeCheckoutAddress ไม่ถูกเรียก (อยากเห็นกับตา ลองแก้อีเมลเป็น "nope" แล้วดูเทสต์พังตรง Place Order)
  • ปุ่ม Place Order หาแบบ regex — { name: /place order/i } คือ case-insensitive match กันเหนียวเรื่องตัวพิมพ์/การจัดรูปข้อความในปุ่ม
  • assert การ navigate ด้วย router ที่ renderRoute คืนมา — นี่คือเหตุผลที่บทที่ 26 ให้ helper คืน router ออกมาด้วย: หลัง mutation สำเร็จ (MSW ตอบ 201 ที่ POST /carts/add) → onSuccess ล้างตะกร้าแล้ว goToOrderSuccess() — เราใช้ waitFor รอจน router.state.location.pathname เป็น /order/success แล้วปิดท้ายด้วยการเช็คว่าหน้า Order Success render ข้อความจริงบนจอ ไม่ใช่แค่ URL เปลี่ยน

เทสต์ตัวเดียวนี้ครอบคลุม: routing, seed ตะกร้าจาก localStorage, ฟอร์ม + validation, cart context, mutation, axios + interceptor, MSW และการ navigate — ถ้ามันเขียว แปลว่า flow ที่สำคัญที่สุดของธุรกิจ (การจ่ายเงิน!) ต่อกันครบทั้งเส้น

มองย้อนพีระมิดทั้งลูก

สามบทที่ผ่านมาเราสร้างเทสต์สามชั้น แต่ละชั้นจับ bug คนละแบบ — และนั่นคือเหตุผลที่ต้องมีครบทุกชั้น ไม่ใช่เลือกชั้นเดียว:

  • Unit (22 tests) — จับ bug ใน logic: สูตรคำนวณผิด, edge case ที่ลืมคิด, reducer ที่ merge จำนวนพลาด รันเร็วระดับมิลลิวินาที และพังทีไรชี้บรรทัดได้เลย
  • Hook (6 tests) — จับ bug ในการเชื่อมชั้นข้อมูล: query key ที่ประกอบผิด, parameter ที่หล่นหายระหว่างทาง, mutation ที่ลืมล้างตะกร้า — สิ่งที่ unit test มองไม่เห็นเพราะมันอยู่ระหว่างหน่วย
  • Integration (6 tests) — จับ bug ในการประกอบร่างที่ผู้ใช้เจอจริง: route ที่หลุด, provider ที่ลืมห่อ, ปุ่มที่กดแล้วเงียบ แลกกับความช้ากว่าและเวลาพังต้องไล่หาต้นเหตุไกลกว่า

รูปทรง "ฐานกว้าง ยอดแหลม" จึงไม่ใช่ความบังเอิญ: เทสต์ถูกและเร็วมีเยอะ ๆ ได้ เทสต์แพงมีพอประมาณให้ครอบ flow สำคัญ และเวลา integration test แดงขึ้นมา — ชั้น unit ข้างล่างนี่แหละที่จะบอกว่าต้นเหตุอยู่ฟังก์ชันไหน
