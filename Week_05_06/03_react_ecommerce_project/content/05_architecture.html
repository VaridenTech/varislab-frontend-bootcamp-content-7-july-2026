สถาปัตยกรรม Feature-based

Feature-based Architecture

บทนี้แทบไม่มีโค้ดให้พิมพ์ — และนั่นแหละคือประเด็น ก่อนจะสร้างไฟล์อีกหลายสิบไฟล์ในบทถัด ๆ ไป เราต้องตอบคำถามที่โปรเจกต์จริงทุกโปรเจกต์ต้องตอบ: ไฟล์แต่ละไฟล์ควรอยู่ตรงไหน และเพราะอะไร ถ้าคุณเข้าใจแผนที่ในบทนี้ บทที่เหลือทั้งคอร์สจะรู้สึกเหมือนแค่เติมของลงช่องที่เตรียมไว้แล้ว ไม่ใช่การงมว่าไฟล์ใหม่ควรไปกองไว้ที่ไหน

ทำไมไม่แบ่งตามชนิดไฟล์

สัญชาตญาณแรกของหลายคน (และ tutorial จำนวนมาก) คือแบ่งโฟลเดอร์ตามชนิดของไฟล์:

src/
├── components/     # component ทั้ง 40 ตัวของทั้งแอป
├── hooks/          # hook ทุกตัว
├── types/          # type ทุกตัว
├── api/            # ฟังก์ชันเรียก API ทุกตัว
└── utils/

โครงแบบนี้ดูเป็นระเบียบดี — ตอนที่มีไฟล์อยู่สิบไฟล์ แต่พอแอปโตขึ้น มันสร้างปัญหาซ้ำ ๆ สามข้อ:

  • งานหนึ่งชิ้น กระจายทั่วโปรเจกต์ — แก้ฟีเจอร์ตะกร้าสินค้าทีเดียว ต้องเปิด components/CartTable.tsx, hooks/useCart.ts, types/cart.ts, api/cart.ts กระโดดไปมาสี่โฟลเดอร์ ทั้งที่ไฟล์พวกนี้เปลี่ยนพร้อมกันเสมอ
  • โฟลเดอร์กลายเป็นกองรวม — components/ ที่มี component 40 ตัวปนกันหมด ไม่บอกอะไรเลยว่าตัวไหนเป็นของฟีเจอร์ไหน ตัวไหนใช้ที่เดียว ตัวไหนใช้ทุกที่
  • ลบฟีเจอร์ = ผ่าตัดใหญ่ — อยากถอดระบบ checkout ออก? ขอให้โชคดีกับการไล่เก็บเศษไฟล์ที่กระจายอยู่ทุกโฟลเดอร์ให้ครบโดยไม่ลบของคนอื่นติดมือไปด้วย

ทางแก้คือกลับหลักคิด: โค้ดที่เปลี่ยนด้วยกัน ควรอยู่ด้วยกัน — แบ่งตามฟีเจอร์ก่อน แล้วค่อยแบ่งตามชนิดไฟล์ข้างในถ้าจำเป็น นี่คือที่มาของชื่อ feature-based architecture

สี่ชั้นของแอปเรา

src/ ของเราแบ่งเป็นสี่ชั้นหลัก (บวกสองโฟลเดอร์เสริม) แต่ละชั้นมีหน้าที่ตอบคำถามคนละข้อ:

  • app/ — แอปประกอบร่างอย่างไร จุดศูนย์รวมระดับบนสุด: router, providers, query client และ layout เป็นชั้นเดียวที่ได้รับอนุญาตให้รู้จักทุกอย่างในแอป
  • pages/ — แต่ละ URL แสดงอะไร หนึ่งโฟลเดอร์ต่อหนึ่ง route ทำหน้าที่เป็น "ผู้กำกับฉาก": หยิบข้อมูลจาก query และ component ของ feature มาเรียงเป็นหน้า แต่ต้องบาง — ไม่มี business logic ของตัวเอง
  • features/ — ความสามารถของแอปมีอะไรบ้าง หัวใจของสถาปัตยกรรม: products, cart, checkout แต่ละตัวคือ vertical slice ที่เป็นเจ้าของทุกอย่างของโดเมนตัวเอง — types, การเรียก api, queries, components ไปจนถึง store
  • shared/ — ของกลางที่ไม่ผูกกับใคร component และเครื่องมือที่ generic จริง ๆ: Button, Modal, axios client, ฟังก์ชันคำนวณ ฯลฯ กติกาเหล็กคือห้ามมีความรู้เรื่องโดเมนของแอปปนอยู่ในนี้
  • styles/ — SCSS ชั้น global จากบทที่แล้ว
  • test/ — โครงพื้นฐานของชุดทดสอบ (มาถึงในบทที่ 26)

กติกาการเป็นเจ้าของ

โฟลเดอร์เป็นแค่ครึ่งเดียวของสถาปัตยกรรม อีกครึ่งคือกติกาว่าอะไรอยู่ที่ไหนและใครเรียกใครได้:

  • pages ต้องบาง — หน้าที่ของมันคือประกอบร่าง ไม่ใช่คิดเอง ถ้าคุณเริ่มเขียนตรรกะคำนวณหรือการเรียก API ในไฟล์ page แปลว่าโค้ดนั้นกำลังหลงทาง — มันควรไปอยู่ใน feature
  • feature เป็นเจ้าของโดเมนตัวเอง — ทุกอย่างเกี่ยวกับสินค้า (type, api, query, component แสดงสินค้า) อยู่ใน features/products ที่เดียว อยากรู้ว่าแอปนี้จัดการสินค้าอย่างไร เปิดโฟลเดอร์เดียวเห็นครบ และวันไหนอยากลบฟีเจอร์ทิ้ง ก็ลบโฟลเดอร์เดียวจบ
  • shared รับเฉพาะของ generic — เกณฑ์ตัดสินง่าย ๆ: "component นี้ยกไปใช้ในแอปอื่นที่ไม่ใช่ E-commerce ได้เลยไหม?" Button กับ Modal ได้ — อยู่ shared ส่วน ProductCard ไม่ได้ (มันรู้จัก type Product) — อยู่ features แม้ Header ของเราจะดูเฉพาะทาง แต่มันเป็นโครงของเปลือกแอปที่ไม่ผูกกับ feature ไหนเป็นพิเศษ จึงอยู่ shared ได้
  • import ไหลทางเดียว — app → pages → features → shared ชั้นบนเรียกชั้นล่างได้เสมอ แต่ห้ามย้อนกลับ: shared ห้าม import จาก features (ไม่งั้นมันไม่ generic แล้ว), features ห้าม import จาก pages และไม่มีใครนอกจาก main.tsx ควรแตะ app เมื่อไหร่ที่คุณพบว่าต้องฝืนกติกานี้ นั่นคือสัญญาณว่าไฟล์สักตัววางผิดชั้น — ย้ายไฟล์ ไม่ใช่ฝืน import
💡 กติกาข้อสุดท้ายคือเหตุผลที่สถาปัตยกรรมนี้ "อ่านง่าย": เห็นชื่อไฟล์ก็เดาได้ทันทีว่ามันรู้จักใครได้บ้าง component ใน shared การันตีว่าอ่านจบในตัวเอง ไม่มีสายใยลับไปแตะ state ของ feature ไหน

สร้างโครงโฟลเดอร์

ลงมือสร้างโครงกระดูกกันเลย จาก root ของโปรเจกต์:

mkdir -p src/app/layouts
mkdir -p src/pages
mkdir -p src/features/products src/features/cart src/features/checkout
mkdir -p src/shared/api src/shared/components src/shared/hooks src/shared/utils

(src/shared/types กับ src/styles มีอยู่แล้วจากบทที่แล้ว) ข้อสังเกตเล็ก ๆ สำหรับคนใช้ git: git ไม่บันทึกโฟลเดอร์เปล่า ดังนั้นถ้ารัน git status ตอนนี้จะยังไม่เห็นโฟลเดอร์ใหม่พวกนี้ — ไม่ใช่บั๊ก พวกมันจะเริ่มปรากฏเมื่อมีไฟล์แรกเข้าไปอยู่ในบทถัด ๆ ไป

ไฟล์แรกของ shared/types

ปิดบทด้วยไฟล์จริงหนึ่งไฟล์ที่เข้ากติกา "generic เท่านั้น" แบบเต็มตัว สร้างไฟล์ src/shared/types/generic.type.ts:

export interface Pagination {
  total: number;
  skip: number;
  limit: number;
}

สามฟิลด์นี้คือภาษากลางของการแบ่งหน้าข้อมูลที่ dummyjson (และ API แบบ REST จำนวนมาก) ใช้: ทุกครั้งที่ขอรายการอะไรก็ตาม เซิร์ฟเวอร์จะแนบมาด้วยว่าของทั้งหมดมีกี่ชิ้น (total) ข้ามมากี่ชิ้น (skip) และหน้านี้ขอมากี่ชิ้น (limit) interface นี้จะได้ทำงานจริงในบทที่ 13 เมื่อ FetchProductsResponse ของ feature products มา extends มัน, ในฟังก์ชันคำนวณของ pagination.utils.ts และในหน้า Category (บทที่ 17) ที่แปลงสามตัวเลขนี้เป็นแถบเลขหน้าให้ผู้ใช้กด

สังเกตว่าทำไมมันอยู่ shared/types ไม่ใช่ features/products: ในนั้นไม่มีคำว่า product สักคำ — มันคือรูปร่างของ "การแบ่งหน้า" ล้วน ๆ ที่ list ไหน ๆ ก็ใช้ได้ ผ่านเกณฑ์ "ยกไปแอปอื่นได้ไหม" สบาย ๆ ในทางกลับกัน ถ้าวันหน้าเราเผลอเพิ่มฟิลด์ products เข้าไปใน interface นี้ นั่นคือวินาทีที่มันต้องย้ายบ้านออกจาก shared ทันที

💡 Checkpoint: บทนี้ไม่มีอะไรเปลี่ยนบนหน้าจอ — ตัวชี้วัดคือโครงสร้าง รัน find src -type d | sort แล้วผลลัพธ์ต้องมีครบ: src/app/layouts, src/pages, src/features/products, src/features/cart, src/features/checkout, src/shared/api, src/shared/components, src/shared/hooks, src/shared/types, src/shared/utils, src/styles จากนั้น npm run typecheck กับ npm run lint ต้องผ่านเหมือนเดิม ได้แผนที่ครบแล้ว — บทหน้าเราจะเริ่มเทของลงช่องแรก: react-router 8
