เจ็ดคอมโพเนนต์ในบทเดียว: จัดส่ง ชำระเงิน และสรุปรายการ

Delivery, Payment & Order Summary

บทนี้เป็นบทสายผลิต: เราจะสร้างคอมโพเนนต์ที่เหลือทั้งหมดของหน้า Checkout รวดเดียว เจ็ดตัว พร้อมไฟล์ .module.scss อีกห้าไฟล์ รวมสิบสองไฟล์ในบทเดียว มากกว่าบทเรียน 21 ที่เคยหนักที่สุดในคอร์สด้วยเก้าไฟล์ — และเป็นบทที่การแบ่งงานให้ Agent ให้ผลตอบแทนสูงที่สุดเท่าที่คอร์สนี้จะแสดงให้ดูได้

เหตุผลที่มันคุ้มไม่ใช่เพราะ "โค้ดเยอะ" เฉย ๆ แต่เพราะโค้ดเจ็ดชิ้นนี้ซ้ำแบบกันเอง: PaymentOption คือ DeliveryOption ที่เปลี่ยน label, CheckoutPaymentBox คือ CheckoutDeliveryBox ที่เปลี่ยนชื่อ prop งานประเภท "ทำตามแบบนี้อีกครั้ง แต่เปลี่ยนสามจุด" คือสิ่งที่โมเดลทำได้เร็วและแม่นกว่ามนุษย์ที่ต้องพิมพ์ซ้ำจนตาลาย

แต่ความซ้ำแบบเดียวกันนี้เองที่ทำให้บทนี้เป็นบทที่ความผิดพลาดซ่อนตัวได้ดีที่สุด — เวลาคุณอ่าน diff ของไฟล์ที่หน้าตาเหมือนไฟล์ก่อนหน้า 90% สายตาจะข้ามส่วนที่เหมือนโดยอัตโนมัติ แล้วส่วนที่ควรต่างแต่ดันเหมือน (เช่น name="deliveryOption" ที่ถูก copy มาไว้ในกล่อง payment) จะไหลผ่านไปเงียบ ๆ อาการของบั๊กแบบนั้นคือ radio สองกลุ่มบนหน้าจอกลายเป็นกลุ่มเดียวกัน — เลือก Bank Transfer แล้ว Express Delivery หลุดติ๊ก ซึ่งเป็นอาการที่คุณจะเจอตอนบทเรียน 28 ประกอบหน้าเสร็จ ห่างจากบรรทัดที่ผิดไปหนึ่งบท

สรุปเป็นประโยคเดียวที่ควรติดไว้ในหัวตลอดบทนี้: บทที่ Agent ทำงานคุ้มที่สุด กับบทที่คุณต้องอ่าน diff ละเอียดที่สุด เป็นบทเดียวกัน

พิมพ์เขียวของทั้งเจ็ดตัว

ก่อนลงมือ มาดูพิมพ์เขียวกันก่อน เพราะทั้งเจ็ดตัวถูกออกแบบเป็นชั้น ๆ ตามหน้าที่ และการเห็นภาพนี้สำคัญกว่าโค้ดของตัวใดตัวหนึ่ง:

  • ชั้นล่างสุด — option components: DeliveryOption, PaymentOption เป็นคอมโพเนนต์ "โง่" (dumb/presentational) สุด ๆ — รับ props มา render เป็น radio หนึ่งแถว ไม่มี state ไม่รู้ด้วยซ้ำว่ามีตัวเลือกอื่นกี่ตัว
  • ชั้นกลาง — box components: CheckoutDeliveryBox, CheckoutPaymentBox วนลูปรายการจาก consts.ts มาสร้าง option หลาย ๆ แถว และรับ "id ที่ถูกเลือก" กับ callback มาเป็น props — ตัวมันก็ยังไม่ own state การเลือก แค่ส่งต่อ
  • ฝั่งขวาของหน้า: SummaryOrder + SummaryOrderItem แสดงรายการสินค้าจากตะกร้า และ BillingSummary แสดงยอดรวมพร้อมปุ่ม Place Order
  • เจ้าของ state ตัวจริง: hook useCheckout ในบทเรียน 28 — มันจะถือทั้งที่อยู่ ทั้ง id จัดส่ง/ชำระเงินที่เลือก ทั้งยอดเงินที่คำนวณแล้ว แล้วแจกลงมาให้ทุกกล่องผ่านหน้าเพจ

ท่านี้คือท่าเดียวกับ CheckoutAddressBox เมื่อบทที่แล้ว: คอมโพเนนต์เล็กโง่ที่สุดเท่าที่จะโง่ได้ state ลอยขึ้นไปรวมที่จุดเดียวข้างบน ผลตอบแทนคือทุกตัวในบทนี้ทดสอบง่าย ใช้ซ้ำได้ และอ่านจบใน 30 วินาที — ซึ่งข้อสุดท้ายจะสำคัญมากตอนคุณต้องอ่าน diff เจ็ดก้อนติดกัน

ทำไมบทนี้ต้องแบ่งเป็นสองรอบ

เกณฑ์จากบทเรียน 19 บอกให้แบ่ง prompt เมื่อของที่ต้องตรวจเกินหนึ่งหน้าจอ และของนั้นแยกเป็นก้อนที่ทดสอบแยกกันได้ — ต้องเข้าทั้งสองข้อถึงจะแบ่ง บทนี้เข้าครบทั้งคู่ นับเป็นครั้งที่สองต่อจากบทเรียน 19 เองที่เป็นคนตั้งเกณฑ์ (ส่วนบทเรียน 21 เข้าแค่ข้อแรก จึงแบ่งด้วยเหตุผลคนละแบบ):

  • สิบสองไฟล์ในรอบเดียวคือ diff ที่ยาวกว่าหน้าจอหลายเท่า ไม่มีใครอ่านจบด้วยความตั้งใจเท่ากันตั้งแต่ไฟล์แรกถึงไฟล์สุดท้าย
  • และมันแยกเป็นสองก้อนที่ไม่รู้จักกันเลยจริง ๆ: ก้อน "ตัวเลือก" (option + box สี่ไฟล์) ไม่ import อะไรจากก้อน "ใบสรุป" (summary + billing สามไฟล์) เลยแม้แต่บรรทัดเดียว ตรวจก้อนแรกจบแล้ว commit ได้โดยที่ก้อนที่สองยังไม่มีตัวตน

เราจึงแบ่งตามรอยที่มันแยกกันอยู่แล้ว:

  1. รอบที่ 1 — ฝั่งซ้ายของหน้า: DeliveryOption, PaymentOption, CheckoutDeliveryBox, CheckoutPaymentBox (+ scss สองไฟล์) ทั้งสี่ตัวพึ่งของเก่าอย่างเดียว: RadioInput จากบทเรียน 12 และ types.ts จากบทเรียน 25
  2. รอบที่ 2 — ฝั่งขวาของหน้า: SummaryOrderItem, SummaryOrder, BillingSummary (+ scss สามไฟล์) ก้อนนี้แตะของจากฟีเจอร์ cart คือ CartItem และ useCart

ข้อดีที่ไม่ได้ตั้งใจแต่ได้มาฟรีคือ: การแบ่งแบบนี้ทำให้ คู่แฝดอยู่ในรอบเดียวกัน — คุณจะได้ DeliveryOption กับ PaymentOption มาพร้อมกันในหน้าจอเดียว เปิดเทียบกันได้ทันทีโดยไม่ต้องเลื่อนหา ซึ่งเป็นวิธีเดียวที่จะจับ copy-paste ที่ผิดได้จริง

  • DeliveryOption / PaymentOption — ต้องแปลงข้อมูลตัวเลือกหนึ่งตัวให้กลายเป็น RadioInput หนึ่งแถว ต้องไม่มี state ต้องไม่รู้ว่าตัวเองถูกเลือกหรือไม่ (รับมาเป็น prop) และต้องไม่ import consts.ts
  • CheckoutDeliveryBox / CheckoutPaymentBox — ต้องรับรายการตัวเลือกเป็น prop แล้ววนลูป ต้องแปลง "id ที่เลือก" เป็น boolean รายตัว ต้องไม่ import consts.ts เอง และต้องไม่มี state
  • SummaryOrderItem — ต้องรับ CartItem หนึ่งชิ้นมาแสดง ต้องคำนวณยอดของแถวตัวเองได้ แต่ต้องไม่รู้จักตะกร้าทั้งใบ

  • BillingSummary — ต้องรับตัวเลขสามตัวมาแสดงอย่างเดียว ต้องไม่เรียก useCart ไม่คำนวณยอดเอง และต้องไม่รู้ว่า "สั่งซื้อ" แปลว่าอะไร

นี่คือผลตอบแทนของแรงที่ลงไปในบทเรียน 12 — RadioInput ที่เราสร้างไว้จัดการเรื่อง input + label + การจับคู่ htmlFor ให้หมดแล้ว คอมโพเนนต์นี้เลยเหลือแค่งานแปลงร่าง: รับข้อมูล delivery หนึ่งตัว มาประกอบเป็น props ให้ RadioInput

  • id={`delivery-option-${id}`} — DOM id ต้องไม่ซ้ำกันทั้งหน้า เราเลยผูกกับ id ของตัวเลือก จะได้ delivery-option-1, delivery-option-2 คลิกที่ label แล้ว radio ติดเพราะ id นี้แหละ
  • name="deliveryOption" — radio ที่ name เดียวกันเป็นกลุ่มเดียวกันในสายตาเบราว์เซอร์ เลือกได้ทีละตัว ค่านี้คือจุดที่ copy-paste ผิดแล้วเงียบที่สุดของบท ตามที่ checklist เตือนไว้
  • checked={selected} กับ onChange={() => onSelect(id)} — ตัวมันไม่ตัดสินใจอะไรเอง ข้างบนบอกว่าถูกเลือกก็แสดงว่าถูกเลือก ผู้ใช้คลิกก็แค่ตะโกน id ของตัวเองขึ้นไป สังเกตว่า onChange ของ RadioInput ไม่รับพารามิเตอร์ (เราออกแบบไว้แบบนั้นตั้งแต่บทเรียน 12) การห่อด้วย arrow function ตรงนี้จึงไม่ใช่ wrapper เปล่า ๆ แต่เป็นการเติม id เข้าไป ซึ่งเป็นคนละเรื่องกับ wrapper ที่ checklist ปฏิเสธ
  • label รับ JSX ได้ — จำได้ไหมว่าเราประกาศ prop นี้เป็น React.ReactNode ไว้ ทำให้ยัด markup อย่าง ชื่อ + เส้นคั่น + คำอธิบาย ลงไปได้เลย ไม่ใช่แค่ string
💡 ของที่ควรถูกทักในรีวิว: ตัวเลือกจัดส่งมี price อยู่ในข้อมูล (Standard $5.99 / Express $15.99 จาก consts.ts) แต่แถวของมันไม่แสดงราคาเลย — DeliveryOptionProps ไม่มี field price ด้วยซ้ำ ผู้ใช้จึงเห็นแค่ "Express Delivery | Approx 1 - 2 Days" แล้วต้องกดเลือกดูเองว่ายอดฝั่งขวาขยับขึ้นเท่าไร นี่คือช่องว่างของ UX ที่มองไม่เห็นวันนี้ (เพราะยังไม่มีหน้าให้ดู) และจะเห็นชัดมากในบทเรียน 28 ตอนที่คุณกด Express แล้วต้องกวาดตาไปหาคำตอบอีกฝั่งของจอ ในรีวิวจริงข้อนี้คือ comment ที่ควรทักคู่กับ estimatedTime ที่ไม่มีใครใช้จากบทเรียน 25: เรามีข้อมูลสองก้อนที่ควรแสดงตรงนี้พอดี ก้อนหนึ่งถูกทิ้ง อีกก้อนถูกเก็บไว้เฉย ๆ การเพิ่ม prop price แล้วต่อท้าย label เป็นงานสามบรรทัดที่กระทบไฟล์เดียว (CheckoutDeliveryBox มี price อยู่ในมืออยู่แล้วเพราะมันรับ TDeliveryOption[] เต็ม ๆ) เราคงตามต้นฉบับเพื่อให้ diff ตรง แต่จดไว้เป็นข้อแรกของบันทึกรีวิวได้เลย

สามจุดที่น่าหยุดดู:

  • import { DeliveryOption as TDeliveryOption } — ไฟล์นี้อยากใช้ชื่อ DeliveryOption สองความหมาย: เป็น type จาก types.ts และเป็น component จากบนหัวบทนี้ ชื่อชนกันตรง ๆ เราเลย rename ฝั่ง type ตอน import เป็น TDeliveryOption (T นำหน้า = type) — ท่ามาตรฐานเวลา type กับ component ชื่อพ้องกัน และเป็นหนี้ก้อนที่บทเรียน 25 เตือนไว้ว่าจะมาเก็บเงินในบทนี้พอดี
  • บรรทัดสำคัญที่สุดคือ selected={id === selectedDeliveryId} — กล่องแปลง "id ที่ถูกเลือก" (ข้อมูลชิ้นเดียว) ให้กลายเป็น boolean รายตัว: ตัวที่ id ตรงได้ true ที่เหลือได้ false การเลือกทีละตัวเลยเกิดขึ้นเองโดยไม่ต้องมี logic ยกเลิกตัวเก่า
  • onSelect={onSelectOption} — callback ถูกส่งผ่านลงไปเฉย ๆ พอผู้ใช้คลิก Express Delivery ข้อความ "เลือก id 2 แล้วนะ" จะวิ่งจาก RadioInput → DeliveryOption → กล่องนี้ → หน้าเพจ → useCheckout แล้วค่าที่อัปเดตก็ไหลย้อนกลับลงมาเป็น selectedDeliveryId ตัวใหม่ — วงจร one-way data flow ครบรอบ

💡 ของที่ควรถูกทักในรีวิว — สองข้อในหกบรรทัดแรกของ JSX: ข้อแรกคือ key={id} บน <div> ตัวนอกสุด ซึ่งไม่มีผลอะไรเลย — key เป็นของที่ React ใช้ตอนจับคู่สมาชิกในรายการ เท่านั้น และรายการที่แท้จริงอยู่ที่ SummaryOrder ซึ่งใส่ key={item.id} ให้ <div className="mb-15"> ที่ครอบคอมโพเนนต์นี้ไว้เรียบร้อยแล้ว (ถูกต้องแล้วด้วย) ส่วน key ที่นี่คือ prop ที่ React รับไปแล้วทิ้ง ไม่ error ไม่เตือน ไม่ทำอะไรทั้งนั้น อาการนี้เกิดจากการย้ายโค้ดออกมาเป็นคอมโพเนนต์ใหม่แล้วยก key ติดมาด้วย ซึ่งเป็นร่องรอยที่พบบ่อยมากในโค้ดจริง ข้อสองอยู่บรรทัดเดียวกัน: className={`flex align-item-center`} เป็น template literal ที่ไม่มีตัวแปรอยู่ข้างในเลยสักตัว — className="flex align-item-center" เป็น string ธรรมดาให้ผลเหมือนกันทุกประการและอ่านง่ายกว่า ร่องรอยเดียวกันอีกแบบ: เคยมี ${styles.something} อยู่ข้างในแล้วถูกลบออกภายหลัง ทั้งสองข้อไม่มีผลต่อผู้ใช้แม้แต่นิดเดียว แต่ทั้งสองข้อคือ comment หนึ่งบรรทัดในรีวิวจริง และเป็นตัวอย่างที่ดีของสิ่งที่ lint จับไม่ได้แต่คนอ่านจับได้ทันที
