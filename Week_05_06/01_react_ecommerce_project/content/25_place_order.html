บทเรียน 25 · ชำระเงิน (Checkout)

สั่งซื้อและ Order Success

Place Order

ถึงบทประกอบร่างแล้ว! สามบทที่ผ่านมาเราเตรียมชิ้นส่วนไว้ครบมือ: schema กับข้อมูลตัวเลือก (บทที่ 22), กล่องที่อยู่ (บทที่ 23), กล่องจัดส่ง/ชำระเงิน/ใบสรุป/ยอดเงิน (บทที่ 24) — แต่ยังไม่มีใคร render และยังไม่มี "สมอง" ที่ถือ state กับ logic การสั่งซื้อ บทนี้เราจะเติมสองอย่างสุดท้าย: ชั้น API + hook useCheckout แล้วแทนที่ stub ของหน้า Checkout และ OrderSuccess ที่ค้างมาตั้งแต่บทที่ 06 ให้กลายเป็นหน้าจริง จบบทนี้ผู้ใช้จะช้อปครบ loop ตั้งแต่หยิบของใส่ตะกร้าจนเห็นหน้ายืนยันคำสั่งซื้อ

สร้าง api.ts — ยิงคำสั่งซื้อขึ้นเซิร์ฟเวอร์

เริ่มจากชั้นล่างสุดเช่นเคย สร้าง src/features/checkout/api.ts:

import { apiClient } from "@/shared/api/client";
import { CheckoutAddressFormData } from "@/features/checkout/schema";

export interface PlaceOrderPayload {
  userId: number;
  products: { id: number; quantity: number }[];
  address: CheckoutAddressFormData;
}

export interface PlaceOrderResponse {
  id: number;
}

export async function placeOrder(
  payload: PlaceOrderPayload,
): Promise<PlaceOrderResponse> {
  const { data } = await apiClient.post<PlaceOrderResponse>(
    "/carts/add",
    payload,
  );
  return data;
}

โครงเหมือน features/products/api.ts จากบทที่ 13 เป๊ะ — ฟังก์ชัน async บาง ๆ ที่เรียก apiClient (axios instance จากบทที่ 12) แล้วคืน data ที่ type แล้ว จุดที่ต่างคือคราวนี้เป็น .post() ครั้งแรกของคอร์ส: เราส่งข้อมูลขึ้นไป ไม่ใช่ดึงลงมา

เรื่องที่ต้องพูดตรง ๆ กันก่อน: POST /carts/add ของ dummyjson เป็น mock endpoint — มันรับ payload, ตอบกลับมาเป็น cart จำลองพร้อม id ที่ปั้นขึ้นมา แต่ไม่ได้บันทึกอะไรลงฐานข้อมูลจริง (echo back) dummyjson ไม่มีระบบ order จริง ๆ ให้เราใช้ ซึ่งสำหรับการเรียนแบบนี้คือข้อดี: เรากดสั่งซื้อกี่รอบก็ได้โดยไม่ทิ้งขยะไว้ที่ไหน สังเกตด้วยว่า field address ใน payload เป็นของที่ dummyjson ไม่รู้จักด้วยซ้ำ (มันรับแล้วเมิน) แต่เราใส่ไว้เพราะโค้ดฝั่งเราควรเขียนเหมือน API จริง — วันที่ย้ายไป backend จริง สิ่งที่เปลี่ยนคือ URL ไม่ใช่โครงโค้ด

  • PlaceOrderPayload — รวมสามส่วน: userId (hardcode เป็น 1 เพราะเราไม่มีระบบ login), รายการสินค้าแบบย่อ (เอาแค่ id + quantity พอ เซิร์ฟเวอร์รู้ราคาเองอยู่แล้ว — อย่าเชื่อราคาที่ client ส่งมา!) และ address ที่ reuse type CheckoutAddressFormData จาก schema ตรง ๆ — schema เดียว ไหลตั้งแต่ฟอร์มยัน payload
  • PlaceOrderResponse — dummyjson ตอบกลับ cart ก้อนใหญ่ แต่เราประกาศ type เฉพาะ field ที่ใช้จริงคือ id การ type ให้แคบที่สุดเท่าที่ใช้เป็นนิสัยที่ดี: response เปลี่ยนโครงเมื่อไร โค้ดเราพังเฉพาะจุดที่พึ่งมันจริง ๆ
  • error ไม่ต้องจัดการที่นี่ — interceptor ใน client.ts แปลงทุกความล้มเหลวเป็น ApiError ให้แล้วตั้งแต่บทที่ 12 ชั้นนี้แค่ปล่อยให้ reject ไหลขึ้นไป

สร้าง useCheckout — สมองของทั้งหน้า

ต่อไปคือไฟล์ที่สำคัญที่สุดของ chapter สร้าง src/features/checkout/useCheckout.ts:

import { useMemo, useState } from "react";
import { useMutation } from "@tanstack/react-query";
import { CheckoutAddressFormData } from "@/features/checkout/schema";
import { deliveryOptions, paymentOptions } from "@/features/checkout/consts";
import { useCart } from "@/features/cart/useCart";
import useProductRoute from "@/shared/hooks/useProductRoute";
import { placeOrder } from "@/features/checkout/api";

const useCheckout = () => {
  const [checkoutAddress, setCheckoutAddress] =
    useState<CheckoutAddressFormData | null>(null);
  const [selectedDeliveryOptionId, setSelectedDeliveryOptionId] =
    useState<number>(deliveryOptions[0].id);
  const [selectedPaymentOptionId, setSelectedPaymentOptionId] =
    useState<number>(paymentOptions[0].id);
  const { goToOrderSuccess } = useProductRoute();
  const { cart, clearCart } = useCart();

  // Helper to get selected delivery option
  const selectedDeliveryOption = useMemo(
    () =>
      deliveryOptions.find((option) => option.id === selectedDeliveryOptionId),
    [selectedDeliveryOptionId],
  );

  // Compute billing summary data
  const billingSummary = useMemo(() => {
    const subtotal = cart.items.reduce(
      (sum, item) => sum + item.price * item.quantity,
      0,
    );

    const shipping = selectedDeliveryOption?.price || 0; // Get price of the selected delivery option
    const total = subtotal + shipping;

    return { subtotal, shipping, total };
  }, [cart, selectedDeliveryOption]);

  const storeCheckoutAddress = (addressData: CheckoutAddressFormData) => {
    setCheckoutAddress(addressData);
  };

  const onSelectDeliveryOption = (optionId: number) => {
    setSelectedDeliveryOptionId(optionId);
  };

  const onSelectPaymentOption = (optionId: number) => {
    setSelectedPaymentOptionId(optionId);
  };

  const { mutate: placeOrderMutate, isPending: isPlaceOrderLoading } =
    useMutation({
      mutationFn: () => {
        if (!checkoutAddress) {
          throw new Error("Delivery Address is Missing");
        }

        return placeOrder({
          userId: 1,
          products: cart.items.map((item) => ({
            id: item.id,
            quantity: item.quantity,
          })),
          address: checkoutAddress,
        });
      },
      onSuccess: () => {
        clearCart();
        goToOrderSuccess();
      },
    });

  const onPlaceOrder = () => {
    placeOrderMutate();
  };

  return {
    checkoutAddress,
    deliveryOptions,
    paymentOptions,
    selectedDeliveryOptionId,
    selectedPaymentOptionId,
    billingSummary,
    isPlaceOrderLoading,
    storeCheckoutAddress,
    onSelectDeliveryOption,
    onSelectPaymentOption,
    onPlaceOrder,
  };
};

export default useCheckout;

ไฟล์ยาวหน่อยแต่แบ่งเป็นห้าท่อนชัด ๆ ค่อย ๆ ไล่กัน:

ท่อนที่ 1: state สามก้อนของหน้า Checkout

นี่คือ state ที่สามบทก่อนหน้า "ลอยขึ้นมารอ" — ในที่สุดก็ได้บ้านอยู่:

  • checkoutAddress — เริ่มเป็น null (ยังไม่ได้กรอก) พอฟอร์มบทที่ 23 submit ผ่าน validation ค่าจะมาลงที่นี่ผ่าน storeCheckoutAddress
  • selectedDeliveryOptionId — ค่าเริ่มต้นคือ deliveryOptions[0].id แปลว่าหน้าเปิดมาพร้อม Standard Delivery ติ๊กอยู่แล้ว ไม่มีจังหวะไหนที่ radio ทั้งกลุ่มว่างเปล่า — UX ที่ดีของ radio คือ "มีตัวเลือกเสมอ" และการอ้าง [0].id จาก consts แปลว่าถ้าวันหน้าเราสลับลำดับ array ค่า default ก็ขยับตามเองโดยไม่ต้องแก้โค้ดตรงนี้
  • selectedPaymentOptionId — ตรรกะเดียวกัน default เป็น Cash on Delivery

ถัดมา hook หยิบเครื่องมือเก่าสองชิ้น: goToOrderSuccess จาก useProductRoute (บทที่ 07) ไว้พาไปหน้าสำเร็จ และ cart + clearCart จาก useCart (บทที่ 19) — checkout อ่านตะกร้าเพื่อสร้าง order และล้างตะกร้าเมื่อสำเร็จ

ท่อนที่ 2–3: ค่าที่คำนวณจาก state ด้วย useMemo

selectedDeliveryOption แปลง id ที่เลือกกลับเป็น object เต็ม ๆ (เพราะเราต้องใช้ price ของมัน) ส่วน billingSummary คือเลขสามตัวที่ BillingSummary บทที่แล้วนั่งรออยู่:

  • subtotal — reduce รวม price × quantity ของทุกชิ้นในตะกร้า สูตรเดียวกับหน้า Cart บทที่ 21
  • shipping — ราคาของ delivery ที่เลือก (?.price || 0 กันกรณี find ไม่เจอ ซึ่งตามโครงข้อมูลจริงไม่ควรเกิด แต่ TypeScript บังคับให้เราคิดถึงมัน — ดีแล้ว)
  • total — บวกกันตรง ๆ

ทั้งสองก้อนเป็น derived state: คำนวณได้จาก state อื่นเสมอ จึงห้ามเก็บเป็น useState แยก (เดี๋ยวลืม sync) ใช้ useMemo ให้คำนวณใหม่เฉพาะเมื่อ dependencies เปลี่ยน — เลือก Express ปุ๊บ selectedDeliveryOption เปลี่ยน → billingSummary คำนวณใหม่ → ค่าส่งกับยอดรวมบนจอเด้งตามทันทีโดยไม่มีใครสั่ง

ท่อนที่ 4: useMutation — ทำไมไม่ใช่ query?

ตั้งแต่บทที่ 14 เราใช้ useQuery (ผ่าน query factories) มาตลอด แต่ query คือเครื่องมือของ "การอ่าน": TanStack Query จะ cache ผลลัพธ์, ยิงซ้ำให้ตอน mount, refetch ตอนกลับมาโฟกัสหน้าต่าง — พฤติกรรมพวกนี้เหมาะกับ GET ทั้งนั้น แต่ลองนึกภาพมันเกิดกับ "การสั่งซื้อ" สิ: เปิดหน้าแล้วสั่งซื้อเองอัตโนมัติ? สลับแท็บกลับมาแล้วสั่งซ้ำอีกรอบ? หายนะชัด ๆ

การเขียน (สร้าง/แก้/ลบข้อมูลฝั่งเซิร์ฟเวอร์) ต้องใช้ useMutation ซึ่งนิสัยตรงข้ามทุกข้อ: ไม่ cache, ไม่ยิงเอง, ทำงานเฉพาะเมื่อเราสั่งผ่าน mutate() เท่านั้น สิ่งที่มันให้เราคือ state รอบการยิงนั้น — ที่เราใช้คือ isPending (rename เป็น isPlaceOrderLoading) ซึ่งจะไหลไปเป็น prop isLoading ของปุ่ม Place Order ให้กลายเป็น spinner ระหว่างรอเซิร์ฟเวอร์ตอบ

ใน mutationFn มีด่านกันพลาดอยู่บรรทัดแรก: ถ้า checkoutAddress ยังเป็น null ให้ throw ทันที ตามจริงปุ่มถูก disable ไว้อยู่แล้วถ้ายังไม่กรอกที่อยู่ (เดี๋ยวเห็นในหน้าเพจ) แต่การเช็คซ้ำในชั้น logic เป็น defensive programming ที่ถูกต้อง — UI เปลี่ยนได้เสมอ และการเช็คนี้ยังทำให้ TypeScript รู้ว่าหลังบรรทัดนั้น checkoutAddress ไม่ใช่ null แน่ ๆ (type narrowing) เราจึงส่งมันเข้า payload ได้โดยไม่ต้อง ! จากนั้นก็ map ของในตะกร้าให้เหลือ { id, quantity } ตามรูปแบบที่ PlaceOrderPayload กำหนด

แล้วก็ถึง callback ที่เป็นหัวใจของ flow ทั้งบท:

onSuccess: () => {
  clearCart();
  goToOrderSuccess();
},

onSuccess ทำงานเฉพาะเมื่อเซิร์ฟเวอร์ตอบสำเร็จ: ล้างตะกร้า (dispatch CLEAR_CART → reducer คืน items: [] → write-through ของ CartProvider เขียนทับ localStorage ให้ด้วย — กลไกจากบทที่ 19 ทำงานให้ฟรี ๆ) แล้วพาผู้ใช้ไป /order/success ลำดับนี้สำคัญนะ: ถ้าเราล้างตะกร้าก่อนยิง API แล้ว API พัง ของในตะกร้าผู้ใช้หายเกลี้ยงทั้งที่ยังไม่ได้ซื้อ — side effect ต้องเกิดหลังความสำเร็จได้รับการยืนยันเท่านั้น

ข้อสังเกตเรื่อง error: ถ้า API ล้มเหลว onSuccess ไม่ทำงาน ตะกร้ายังอยู่ครบ ปุ่มหยุดหมุนแล้วกลับมากดใหม่ได้ — ปลอดภัย แต่เวอร์ชันนี้ยังไม่ได้แสดงข้อความ error ให้ผู้ใช้เห็น (useMutation มี error ให้หยิบอยู่แล้ว แค่ hook เรายังไม่ return ออกไป) ถือเป็นแบบฝึกหัดต่อยอดที่ดีมาก: ลอง return error ออกไปแล้วแสดง ErrorMessage เหนือปุ่มดูเมื่อจบคอร์ส

ท่อนที่ 5: return — สัญญาของ hook

ก้อน return คือ "API ของหน้า Checkout" ทั้งหมดในที่เดียว: ข้อมูล (ที่อยู่, รายการตัวเลือก, id ที่เลือก, ยอดเงิน, สถานะ loading) กับ handlers (เก็บที่อยู่, เลือกจัดส่ง/จ่ายเงิน, สั่งซื้อ) สังเกตว่า hook ส่งต่อ deliveryOptions / paymentOptions จาก consts ออกไปด้วย — หน้าเพจเลยไม่ต้อง import consts เอง ทุกอย่างเกี่ยวกับ checkout ไหลผ่านประตูบานเดียว ซึ่งจะทำให้ mock ง่ายมากตอนเขียนเทสต์บทที่ 28

ได้เวลาฆ่า stub ที่อยู่มาตั้งแต่บทที่ 06 เปิด src/pages/Checkout/Checkout.tsx แล้วแทนที่ทั้งไฟล์:

.addressBox {

}

หน้านี้แทบไม่มี logic เลย — และนั่นแหละคือความสำเร็จ มันคือ "wiring diagram" ล้วน ๆ:

  • CategoryBanner name="Checkout" — reuse แบนเนอร์หัวหน้าเพจจากบทที่ 17 เปลี่ยนแค่ข้อความ ได้หน้าตาสอดคล้องกับหน้า Category ฟรี ๆ
  • layout สองคอลัมน์ — flex gap-20 แบ่งซ้าย 60% (addressBox: กล่องที่อยู่ → จัดส่ง → ชำระเงิน เรียงลงมา) ขวา 40% (summaryBox: ใบสรุป + ยอดเงิน) ตาม SCSS module สองบรรทัดข้างบน
  • ทุก prop มาจาก useCheckout ก้อนเดียว — destructure ทีเดียวแล้วแจกจ่าย รวมถึงท่า destructure ซ้อน billingSummary: { subtotal, shipping, total } ที่แกะเลขสามตัวออกมาในบรรทัดเดียว
  • isDisabled={!checkoutAddress} — ด่านกันพลาดฝั่ง UI ที่สัญญาไว้: ตราบใดที่ยังไม่ submit ที่อยู่ ปุ่ม Place Order จะกดไม่ได้ พอที่อยู่มาปุ๊บปุ่มติดเอง เพราะ prop คำนวณใหม่ทุก render
  • SummaryOrder ไม่รับ prop อะไรเลย — ตามที่ออกแบบไว้บทที่แล้ว มันอ่านตะกร้าจาก context เอง

สังเกตว่าหน้านี้ไม่มี guard กรณีตะกร้าว่าง — เข้าตรง ๆ ที่ /checkout ทั้งที่ตะกร้าโล่งก็จะเห็นใบสรุปว่าง ๆ กับยอด $5.99 (ค่าส่งอย่างเดียว) ซึ่งใช้งานได้แต่ไม่สวยนัก โปรเจกต์ต้นฉบับเลือกเก็บหน้าให้เรียบง่ายไว้ก่อน ถ้าอยากฝึกเพิ่ม ลอง redirect ไปหน้า Cart เมื่อ cart.items.length === 0 เป็นการบ้านหลังจบคอร์สได้

หน้า Order Success ฉบับสมบูรณ์

ชิ้นสุดท้าย! route /order/success มีอยู่แล้วตั้งแต่บทที่ 06 เหลือแค่ทำหน้าให้สมศักดิ์ศรี เปิด src/pages/Order/OrderSuccess.tsx แล้วแทนที่ stub ทั้งไฟล์:

import { FontAwesomeIcon } from "@fortawesome/react-fontawesome";
import { faCircleCheck } from "@fortawesome/free-solid-svg-icons";

const OrderSuccess: React.FC = () => {
  return (
    <div>
      <div className="bg-grey01 pt-45 pb-45 text-center">
        <FontAwesomeIcon
          icon={faCircleCheck}
          className="fs-72 text-primary mb-20"
        />
        <h2 className="fs-28 mb-15 text-uppercase fw-bold">
          Order Placed Successfully!
        </h2>
        <p className="fs-18 text-muted">

หน้าเรียบ ๆ ตั้งใจ: ไอคอน faCircleCheck ตัวโต (Font Awesome ติดตั้งไว้ตั้งแต่บทที่ 07) + หัวข้อ + ข้อความยืนยัน บนพื้นเทาอ่อน จัดทุกอย่างด้วย utility classes ล้วน ๆ ไม่ต้องมี SCSS module สังเกตว่าหน้านี้ไม่ต้องล้างตะกร้าเอง — งานนั้น onSuccess ของ mutation ทำจบไปแล้วก่อนจะ navigate มาถึง แบ่งหน้าที่ชัด: hook จัดการผลลัพธ์ หน้าเพจแค่แสดงความยินดี

ทดสอบ happy path ทั้งเส้น

นี่คือช่วงเวลาที่รอมาตั้งแต่บทที่ 01 — flow ช้อปปิ้งครบ loop ครั้งแรกของแอป รัน npm run dev แล้วไล่ตามนี้ทีละข้อ:

  1. เปิดหน้า Product ของสินค้าสักชิ้น กด Add to Cart (จะเพิ่มหลายชิ้นก็ยิ่งดี)
  2. เข้าหน้า Cart ตรวจของ แล้วกดไปหน้า Checkout
  3. เห็นหน้าใหม่เอี่ยม: แบนเนอร์ Checkout, กล่องซ้ายสามใบ, ใบสรุปขวาที่มีสินค้าของเราครบ และปุ่ม Place Order ที่ยังกดไม่ได้
  4. ลองกด Submit ฟอร์มทั้งที่ว่าง → ข้อความแดง "Address is required" ฯลฯ โผล่ครบสามช่อง — zod ทำงานแล้ว ลองพิมพ์ email มั่ว ๆ ดูด้วยว่าได้ "Enter a valid email address"
  5. กรอกให้ครบแล้ว Submit → ที่อยู่ขึ้นไปแสดงในกล่อง และปุ่ม Place Order ติดสว่างพร้อมกด
  6. สลับ delivery เป็น Express → Shipping ฝั่งขวาเด้งเป็น $15.99 และ Total ขยับตามทันที เลือก payment ตามใจ
  7. กด Place Order → ปุ่มกลายเป็น spinner แวบหนึ่ง → เด้งไปหน้า Order Success ไอคอนติ๊กถูกเขียว
  8. ดู Header: ตัวเลขบนไอคอนตะกร้าเป็น 0 แล้ว — CLEAR_CART ทำงาน
💡 Checkpoint สุดท้าย: เปิด DevTools → แท็บ Application → Local Storage → key ecommerce-cart:v1 ต้องกลายเป็น {"items":[]} — หลักฐานว่า write-through จากบทที่ 19 เขียนทับตะกร้าที่ล้างแล้วลง localStorage เรียบร้อย ลอง refresh หน้าไหนก็ได้ ตะกร้าต้องยังว่างอยู่ และเปิดแท็บ Network ระหว่างกด Place Order จะเห็น POST https://dummyjson.com/carts/add พร้อม response จำลองที่มี id กลับมา ถ้าทุกข้อผ่าน — ยินดีด้วย แอป E-commerce ของคุณขายของได้แล้วครบ loop ตั้งแต่เลือกของยันยืนยันคำสั่งซื้อ chapter ถัดไปเราจะทำให้มันพิสูจน์ได้ว่าทำงานถูกต้อง ด้วยชุดเทสต์เต็มรูปแบบ
