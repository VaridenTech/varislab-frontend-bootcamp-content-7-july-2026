Maintainability Review

รูปแบบที่ทำให้โค้ดดูแลยาก

สองบทก่อนตรวจว่าโค้ดทำงานถูกต้องหรือไม่ บทนี้จะดูว่าอีกหกเดือนเรายังแก้และต่อยอดโค้ดได้สะดวกหรือไม่ สาเหตุที่พบบ่อยคือ Agent ทำงานตามบริบทของแต่ละ prompt และอาจไม่เชื่อมโยงกับของเดิมทั้งหมด ถ้าเราไม่ review ภาพรวมจึงมักพบรูปแบบต่อไปนี้

ปัญหาที่ 1 — copy-paste หลายชุด: ย้อนดูแถว stat cards จากบทเรียน 10

วันที่ดีไซเนอร์ขอเปลี่ยน padding การ์ด เราต้องแก้ 4 ที่ให้เหมือนกันเป๊ะ — พลาดหนึ่งที่คือ UI เพี้ยนแบบตาเปล่าจับยาก

ปัญหาที่ 2 — ternary ซ้อนใน className: badge จากบทเรียน 11 ยังมีเงื่อนไขเดียวจึงพออ่านได้ แต่เมื่อเพิ่มสถานะที่สามอย่าง Working / Canceled / Done ในตาราง Projects เงื่อนไขจะเริ่มซ้อนและตามได้ยาก

ปัญหาที่ 3 — เลข arbitrary ที่ไม่มีที่มา: w-[260px] ของ sidebar มีเหตุผลจากดีไซน์ ส่วน mt-[13px] ไม่บอกว่ามาจากข้อกำหนดใด ค่าที่ไม่มีคำอธิบายทำให้คนที่มาแก้ต่อไม่แน่ใจว่าสามารถเปลี่ยนได้หรือไม่

ปัญหาที่ 4 — ชื่อ generic: ชื่ออย่าง Card2, NewSection และ Wrapper บอกรูปร่างหรือชนิดของ element แต่ไม่บอกหน้าที่ในระบบ

กติกาหลักของเลนส์นี้

เห็น class string ชุดเดียวกัน ≥ 2 ที่ = แยกเป็น component — ไม่ใช่แยกเป็นไฟล์ CSS และไม่ใช่ @apply (บทเรียน 05 อธิบายไว้แล้วว่าทำไม) โลก React + Tailwind ทำ DRY ที่ระดับ JSX: ปุ่มที่ใช้ซ้ำคือ <Button>, การ์ดสถิติที่ใช้ซ้ำคือ <StatCard> — component ห่อทั้ง markup, class และพฤติกรรม (focus, disabled, aria) ไว้ในที่เดียว ซึ่ง class ห่อไม่ได้

อีกข้อดีคือ สิ่งที่เราแก้ในบทเรียน 12–13 เช่น focus ring, aria และ overflow จะถูกใช้ร่วมกันทุกจุดเมื่อรวมไว้ใน component เดียว การแก้ component หนึ่งครั้งจึงช่วยให้ทุกตำแหน่งที่เรียกใช้ได้พฤติกรรมเดียวกัน

Checklist ตรวจ Maintainability

เลนส์ที่สาม — "checklist บทเรียน 14"

  • Class string ซ้ำ ≥ 2 ที่ → แยก component (prettier-plugin-tailwindcss ที่เรียง class ให้เป็นมาตรฐานเดียวกัน ทำให้ "ซ้ำ" มองเห็นด้วยตา)
  • เลข arbitrary [...] ที่ไม่ได้ตั้งใจ → เปลี่ยนเป็น token หรือ scale ปกติ; ที่ตั้งใจ (ความกว้าง sidebar) → คงไว้พร้อมรู้ที่มา
  • Ternary ซ้อนใน className → เปลี่ยนเป็น variant map (เดี๋ยวเห็นในบทเรียน 15)
  • Component เกิน ~150 บรรทัด → แตกไฟล์ (DashboardPage ตอนนี้เกินไปมาก)
  • ชื่อ generic → ตั้งชื่อตาม domain: StatCard ไม่ใช่ Card2
  • Mock data ฝังใน component → แยกไป src/data/ (Agent ทำถูกแล้วเพราะ prompt สั่ง — เช็คว่าไม่มีหลงเหลือ)
  • ไอคอน SVG ก้อนเดียวกัน copy หลายที่ → แยกเป็นไฟล์ icon component

ไล่ checklist กับโค้ดของเรา

เมื่อตรวจครบทั้งสามหน้า เราจะได้รายการสำหรับ refactor ในบทเรียน 15

  • Stat card — ซ้ำ 4 ที่ในหน้า Dashboard → แยกเป็น StatCard
  • ปุ่ม — DOCUMENTATION (sidebar), SIGN UP (ฟอร์ม), VIEW ALL (จะเจอในหน้า Profile) — สามหน้าตา แต่จริง ๆ คือปุ่มเดียวกัน 3 variant → แยกเป็น Button
  • Badge สถานะ — ternary ในหน้า Tables + สถานะ Working/Done/Canceled ที่เป็นข้อความเฉย ๆ → แยกเป็น StatusBadge
  • Progress bar — ซ้ำข้ามสองหน้า (ตาราง Projects ใน Dashboard และใน Tables) → แยกเป็น ProgressBar
  • เมนู sidebar — markup ของ NavLink ก้อนใหญ่วนใน map สองรอบ (เมนูหลัก + ACCOUNT PAGES) → แยกเป็น NavItem
  • Toggle — ตอนนี้มีที่เดียว (Remember me) แต่หน้า Profile ที่กำลังจะมามี Platform Settings ที่ใช้อีก 6 ตัว → แยกเป็น component ตั้งแต่ตอนนี้คุ้มแน่นอน

รายการนี้ตรงกับ pattern ที่เราสังเกตไว้ตั้งแต่บทเรียน 06 ก่อนเริ่มเขียนโค้ด แสดงว่าการอ่านส่วนที่ซ้ำใน UI ช่วยให้เราคาดการณ์โครงสร้าง component ได้ล่วงหน้า

บทถัดไปจะลงมือ refactor ตามรายการนี้ หลังจากนี้ทุกครั้งที่รับงานจาก Agent ให้ตรวจตามลำดับ responsive (12) → accessibility (13) → maintainability (14) เพื่อเริ่มจากปัญหาที่สังเกตเห็นได้ง่ายไปหาปัญหาที่ต้องอ่านโค้ดละเอียดขึ้น
