Maintainability Review

กลิ่นของโค้ด AI

สองเลนส์แรกตรวจว่าโค้ด "ทำงานถูกไหม" — เลนส์นี้ตรวจว่า "อยู่กับมันไหวไหมในอีกหกเดือน" ต้นตอของกลิ่นทั้งหมดคือเรื่องเดียว: Agent ทำงานเป็นครั้ง ๆ ไม่จำของเดิม — แต่ละ prompt คือช่างคนใหม่ที่เดินเข้าไซต์งาน สร้างของตัวเองเสร็จแล้วกลับบ้าน ไม่มีใครมองภาพรวม ผลคือ pattern คลาสสิกชุดนี้

กลิ่นที่ 1 — copy-paste ยาวเหยียด: ย้อนดูแถว stat cards จากบทเรียน 10

<div className="flex items-center justify-between rounded-2xl bg-white p-4 shadow-sm">
  <div>
    <p className="text-sm font-medium text-muted">Today's Money</p>
    <p className="text-xl font-bold text-ink">
      $53,000 <span className="text-sm font-bold text-success">+55%</span>
    </p>
  </div>
  <div className="flex size-12 items-center justify-center rounded-xl bg-primary">
    <WalletIcon className="size-6 text-white" />
  </div>
</div>
<div className="flex items-center justify-between rounded-2xl bg-white p-4 shadow-sm">
  <div>
    <p className="text-sm font-medium text-muted">Today's Users</p>
    {/* ...โครงเดิมเป๊ะ อีก 3 รอบ... */}

วันที่ดีไซเนอร์ขอเปลี่ยน padding การ์ด เราต้องแก้ 4 ที่ให้เหมือนกันเป๊ะ — พลาดหนึ่งที่คือ UI เพี้ยนแบบตาเปล่าจับยาก

กลิ่นที่ 2 — ternary ซ้อนใน className: badge จากบทเรียน 11 — เงื่อนไขเดียวยังพออ่านได้ แต่รอวันที่มีสถานะที่สาม (ตาราง Projects มี Working / Canceled / Done แล้วนะ) ternary จะเริ่มซ้อนจนอ่านไม่ออก

กลิ่นที่ 3 — เลข arbitrary ปริศนา: w-[260px] (sidebar — ตั้งใจ มาจากดีไซน์ ✓) vs mt-[13px] (มาจากไหน? ใครจะกล้าแก้?) — ค่าที่ไม่มีที่มาคือกับระเบิดของคนถัดไป

กลิ่นที่ 4 — ชื่อ generic: Card2, NewSection, Wrapper — Agent ชอบตั้งชื่อตามรูปร่าง ไม่ใช่ตามความหมาย

กติกาหลักของเลนส์นี้

เห็น class string ชุดเดียวกัน ≥ 2 ที่ = แยกเป็น component — ไม่ใช่แยกเป็นไฟล์ CSS และไม่ใช่ @apply (บทเรียน 05 อธิบายไว้แล้วว่าทำไม) โลก React + Tailwind ทำ DRY ที่ระดับ JSX: ปุ่มที่ใช้ซ้ำคือ <Button>, การ์ดสถิติที่ใช้ซ้ำคือ <StatCard> — component ห่อทั้ง markup, class และพฤติกรรม (focus, disabled, aria) ไว้ในที่เดียว ซึ่ง class ห่อไม่ได้

ประโยชน์ทบต้นที่มักมองข้าม: ทุกอย่างที่เราเพิ่งแก้ในบทเรียน 12–13 (focus ring, aria, overflow) ถ้าอยู่ใน component เดียว มันจะถูกทุกที่โดยอัตโนมัติตลอดไป — การ refactor คือการทำให้ความถูกต้องแพร่พันธุ์

Checklist ตรวจ Maintainability

เลนส์ที่สาม — "checklist บทเรียน 14"

  • Class string ซ้ำ ≥ 2 ที่ → แยก component (prettier-plugin-tailwindcss ที่เรียง class ให้เป็นมาตรฐานเดียวกัน ทำให้ "ซ้ำ" มองเห็นด้วยตา)
  • เลข arbitrary [...] ที่ไม่ได้ตั้งใจ → เปลี่ยนเป็น token หรือ scale ปกติ; ที่ตั้งใจ (ความกว้าง sidebar) → คงไว้พร้อมรู้ที่มา
  • Ternary ซ้อนใน className → เปลี่ยนเป็น variant map (เดี๋ยวเห็นในบทเรียน 15)
  • Component เกิน ~150 บรรทัด → แตกไฟล์ (DashboardPage ตอนนี้เกินไปมาก)
  • ชื่อ generic → ตั้งชื่อตาม domain: StatCard ไม่ใช่ Card2
  • Mock data ฝังใน component → แยกไป src/data/ (Agent ทำถูกแล้วเพราะ prompt สั่ง — เช็คว่าไม่มีหลงเหลือ)
  • ไอคอน SVG ก้อนเดียวกัน copy หลายที่ → แยกเป็นไฟล์ icon component

ไล่ checklist กับโค้ดของเรา

ผลการไล่ทั้งสามหน้า — นี่คือ "ใบสั่งงาน" ที่จะส่งเข้าบทเรียน 15

  • Stat card — ซ้ำ 4 ที่ในหน้า Dashboard → แยกเป็น StatCard
  • ปุ่ม — DOCUMENTATION (sidebar), SIGN UP (ฟอร์ม), VIEW ALL (จะเจอในหน้า Profile) — สามหน้าตา แต่จริง ๆ คือปุ่มเดียวกัน 3 variant → แยกเป็น Button
  • Badge สถานะ — ternary ในหน้า Tables + สถานะ Working/Done/Canceled ที่เป็นข้อความเฉย ๆ → แยกเป็น StatusBadge
  • Progress bar — ซ้ำข้ามสองหน้า (ตาราง Projects ใน Dashboard และใน Tables) → แยกเป็น ProgressBar
  • เมนู sidebar — markup ของ NavLink ก้อนใหญ่วนใน map สองรอบ (เมนูหลัก + ACCOUNT PAGES) → แยกเป็น NavItem
  • Toggle — ตอนนี้มีที่เดียว (Remember me) แต่หน้า Profile ที่กำลังจะมามี Platform Settings ที่ใช้อีก 6 ตัว → แยกเป็น component ตั้งแต่ตอนนี้คุ้มแน่นอน

สังเกตว่ารายชื่อนี้ตรงกับ pattern ที่เราอ่านออกตั้งแต่บทเรียน 06 ตอนยังไม่มีโค้ดสักบรรทัด — การอ่าน UI ที่ดีทำนายโครงสร้าง component ได้ล่วงหน้า วนกลับมาบรรจบพอดี

บทถัดไปลงมือเคลียร์ใบสั่งงานนี้ทั้งใบ — เลนส์ครบสามแล้ว ต่อไปทุกครั้งที่รับงานจาก Agent ให้ไล่สามเลนส์นี้เป็นกิจวัตร: responsive (12) → accessibility (13) → maintainability (14) ตามลำดับ จากมองเห็นง่ายไปมองเห็นยาก
