Accessibility Review

จุดที่ AI พังแบบเงียบที่สุด

ปัญหา responsive มองเห็นด้วยตา — ย่อจอปุ๊บของล้นปั๊บ แต่ปัญหา accessibility มองไม่เห็นและไม่มี error: หน้าตาถูกทุก pixel, console สะอาด, demo ให้ลูกค้าดูผ่านฉลุย — แต่คนที่ใช้คีย์บอร์ดล้วน ๆ เข้าเมนูไม่ได้ และ screen reader อ่านหน้าจอแล้วได้ยินแต่ "button, button, button" AI สร้างปัญหาแบบนี้เก่งเป็นพิเศษเพราะมัน optimize จากภาพ ส่วน semantics อยู่ใต้ภาพ ต้องทดสอบเป็นถึงจะเจอ — บทนี้สอนทั้งวิธีทดสอบและวิธีแก้

ล่า TODO ข้อ 3 — เมนู sidebar เป็น div

ทดสอบ: กดปุ่ม Tab ไล่จากบนสุดของหน้า — โฟกัสกระโดดจากโลโก้ข้ามเมนูทั้งแผงไปลง search box เพราะเมนูเป็น <div onClick> ซึ่งไม่อยู่ใน tab order ของเบราว์เซอร์ (แถมคลิกแล้วก็แค่ console.log — ยังไม่ได้นำทางจริงด้วยซ้ำ)

หลักการที่จำง่ายที่สุดของ a11y: ของที่กดได้ต้องเป็น <a> (พาไปที่อื่น) หรือ <button> (ทำอะไรบางอย่าง) เท่านั้น — สอง element นี้ได้ tab order, การกด Enter/Space และการประกาศบทบาทต่อ screen reader มาฟรีทั้งหมด เมนู sidebar คือการนำทาง จึงต้องเป็นลิงก์ — และเพราะเราใช้ react-router ให้ใช้ NavLink ซึ่งแถมสถานะ active ให้ด้วย

// src/components/Sidebar.tsx — เพิ่ม to ลง data ก่อน
const menu = [
  { label: "Dashboard", to: "/", icon: HomeIcon },
  { label: "Tables", to: "/tables", icon: TableIcon },
  { label: "Billing", to: "/billing", icon: CardIcon },
  { label: "RTL", to: "/rtl", icon: RtlIcon },
];

import { NavLink } from "react-router";

{menu.map((item) => (
  <NavLink
    key={item.to}
    to={item.to}
    onClick={onClose}
    className={({ isActive }) =>
      `flex items-center gap-3 rounded-2xl px-4 py-3 text-sm font-bold ` +
      (isActive ? "bg-white text-ink shadow-sm" : "text-muted hover:bg-white")
    }
  >
    <span className="flex size-8 items-center justify-center rounded-xl bg-white text-primary">
      <item.icon />
    </span>
    {item.label}
  </NavLink>
))}

ของแถมสามต่อ: คีย์บอร์ดใช้ได้จริง, การนำทางทำงานจริง (แทน console.log), และสถานะ active ที่เคย hardcode ไว้ที่ Dashboard ตอนนี้คำนวณจาก route จริงผ่าน isActive — แก้ปัญหา a11y แล้วโค้ดกลับถูกขึ้นทั้งระบบ ไม่ใช่เรื่องบังเอิญ: semantics ที่ถูกมักลากโครงสร้างที่ถูกมาด้วย

ล่า TODO ข้อ 4 — มองไม่เห็นโฟกัส

Tab เข้าเมนูได้แล้ว แต่มองไม่เห็นว่าอยู่ช่องไหน — เพิ่ม focus ring ให้ทุก interactive element ตามท่าบทเรียน 04

focus-visible:ring-2 focus-visible:ring-primary/50 focus-visible:outline-none

ติดที่ NavLink, ปุ่มทุกปุ่ม, ลิงก์ทุกลิงก์ (ช่อง input ใช้ focus:border-primary อย่างที่ Agent ทำไว้ — ถูกแล้ว ไม่ต้องแตะ) ถ้าขี้เกียจไล่ติดทีละตัว ใจเย็น ๆ: บทเรียน 15 จะแยกปุ่มเป็น component เดียวแล้ว focus style จะติดมาฟรีทุกที่ — ตอนนี้แก้เฉพาะ NavLink กับปุ่มใน shell ก่อนก็พอ

Checklist ตรวจ Accessibility

เลนส์ที่สอง — "checklist บทเรียน 13"

  • Heading ไล่ระดับ — h1 เดียวต่อหน้า ไม่กระโดดจาก h1 ไป h4
  • Landmark ครบ — aside / nav / header / main (Agent ทำถูกแล้วเพราะ rules สั่ง — เช็คซ้ำเฉย ๆ)
  • alt ทุกรูป — avatar ใช้ชื่อคน (alt={author.name} ✓) รูปตกแต่งล้วนใช้ alt="" ให้ screen reader ข้าม — คำตอบของ TODO ข้อ 7 (กอง avatar ในตาราง Projects): รูปใช้ alt="" ได้ แต่ควรมีข้อความจริงบอกจำนวน เช่น title บนกอง หรือยอมรับว่าข้อมูลนี้เป็น decorative เสริม — ตัดสินใจแล้วจดเหตุผล ดีกว่าปล่อยผ่านโดยไม่รู้ตัว
  • ปุ่มไอคอนล้วนมี aria-label — เก็บหนี้ TODO ข้อ 10: ปุ่ม social หน้า Sign Up (aria-label="สมัครด้วย Facebook" ฯลฯ), ไอคอน settings/กระดิ่งใน Navbar, ปุ่ม kebab ในตาราง Projects
  • ตาราง — หัวคอลัมน์เป็น <th scope="col"> ไม่ใช่ <td> ตัวหนา และเพิ่ม <caption className="sr-only">รายชื่อผู้เขียน</caption> ให้ screen reader รู้ว่าตารางนี้คืออะไร (sr-only = มีอยู่จริงแต่ไม่แสดงผล)
  • ฟอร์ม — ทุก input มี <label htmlFor> จริง (Agent ทำถูกแล้วในหน้า Sign Up เพราะ prompt สั่ง)
  • Interactive = <button>/<a> เท่านั้น — หลักการใหญ่ของบทนี้
  • Contrast ผ่านเกณฑ์ — ดูหัวข้อถัดไป
  • Tab ให้ครบทุกหน้า — การทดสอบที่ถูกที่สุดและจับปัญหาได้มากที่สุด ทำให้เป็นนิสัย

ล่า TODO ข้อ 9 — toggle ที่เป็น div

สวิตช์ Remember me ของ Agent สวยแต่กลวง: div กดด้วยคีย์บอร์ดไม่ได้ และ screen reader ไม่รู้ว่าเปิดหรือปิดอยู่ ท่าที่ถูกคือ checkbox จริงที่ซ่อนสายตาแต่ไม่ซ่อนจากเครื่องมือ แล้ววาดสวิตช์ด้วย CSS ทับ — ใช้ peer ของ Tailwind (พี่น้องของ group: อ้างสถานะของพี่น้องแทนแม่)

<label className="flex cursor-pointer items-center gap-3">
  <input type="checkbox" defaultChecked className="peer sr-only" />
  <span
    className="relative h-6 w-11 rounded-full bg-gray-300 transition-colors
      peer-checked:bg-primary peer-focus-visible:ring-2 peer-focus-visible:ring-primary/50
      after:absolute after:top-0.5 after:left-0.5 after:size-5 after:rounded-full
      after:bg-white after:transition-transform peer-checked:after:translate-x-5"
  />
  <span className="text-sm font-bold text-ink">Remember me</span>
</label>

แกะทีละชิ้น: sr-only ซ่อน checkbox จริงไว้ (แต่ยังโฟกัส/กด/อ่านได้), แทร็กเปลี่ยนสีด้วย peer-checked:bg-primary, ปุ่มกลมคือ after: ที่เลื่อนด้วย peer-checked:after:translate-x-5, และทั้งหมดอยู่ใน <label> เดียว — คลิกที่ไหนของแถวก็ toggle ได้ กด Space ได้ Tab เข้าได้ ครบ

Contrast — กับดักของดีไซน์นี้เอง

เช็คสีด้วย WebAIM Contrast Checker: ตัวหนังสือขาวบนเขียวมิ้นต์ #4fd1c5 ได้ contrast ประมาณ 2:1 — เกณฑ์ WCAG AA ต้องการ 4.5:1 สำหรับข้อความปกติ แปลว่าไม่ผ่าน และดีไซน์ต้นฉบับก็เป็นแบบนี้จริง ๆ — ดีไซน์สวย ๆ จากมืออาชีพก็พลาดเรื่องนี้ได้

ทางเลือกของเราเรียงตามความเข้มงวด: (1) ใช้ text-ink บนพื้น primary สำหรับข้อความที่ต้องอ่าน (เข้มบนอ่อน ผ่านสบาย), (2) ใช้ primary เวอร์ชันเข้มขึ้นเป็นพื้นปุ่ม, หรือ (3) ยอมรับความเสี่ยงเฉพาะจุดตกแต่งที่มีข้อความซ้ำอ่านได้ที่อื่น — ข้อสำคัญไม่ใช่ว่าเลือกข้อไหน แต่คือรู้ว่ากำลังเลือก ไม่ใช่ปล่อยผ่านเพราะไม่เคยวัด

เครื่องมือ + ให้ AI ช่วยตรวจ

  • Lighthouse (แท็บใน DevTools) — เลือก Accessibility แล้วรันกับหน้า Dashboard: มันจะจับ image-alt, contrast, ชื่อปุ่มที่หายไป พร้อมลิงก์อธิบาย
