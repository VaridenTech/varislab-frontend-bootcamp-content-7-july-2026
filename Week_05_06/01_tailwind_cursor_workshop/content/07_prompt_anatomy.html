บทเรียน 07 · จาก Screenshot สู่ Prompt (Screenshot to Prompt)

เขียน UI Prompt ที่ชัดเจน

Prompt Anatomy

Prompt คลุมเครือทำให้ผลลัพธ์ไม่ตรง

ลองดู prompt แบบที่คนส่วนใหญ่พิมพ์ครั้งแรก

ทำหน้า admin dashboard สวย ๆ ให้หน่อย

ลองนับสิ่งที่ Agent ต้องเดา: ใช้สีอะไร layout แบบไหน มี sidebar หรือไม่ มีกี่การ์ดและใช้ข้อมูลอะไร กราฟเป็นแบบไหน ใช้ Tailwind, CSS หรือ styled-components และต้องแยกไฟล์อย่างไร เมื่อข้อมูลเหล่านี้ไม่ครบ Agent อาจสร้าง dashboard ที่ดูดีแต่ไม่ตรงกับงาน ทำให้เราต้องย้อนมาแก้หลายจุด

AI ทำงานได้ดีขึ้นเมื่อได้รับข้อกำหนดที่ชัดเจน หน้าที่ของเราคือเปลี่ยนสิ่งที่เห็นใน screenshot และสิ่งที่ตกลงกันไว้ให้เป็นสเปกที่อธิบายได้ครบ

กายวิภาคสี่ส่วน

Prompt สำหรับ UI แบ่งได้เป็นสี่ส่วน แต่ละส่วนช่วยลดข้อมูลที่ Agent ต้องคาดเดา

  • 1. บริบท — บอกว่าเป็นแอปอะไร ใช้ stack ใด และมีอะไรอยู่แล้ว เช่น token, component และโครงโฟลเดอร์
  • 2. โครงสร้าง — ไล่ region ของหน้าจอจากบนลงล่าง พร้อมเนื้อหาจริงจาก screenshot เพื่อบอกว่าต้องสร้างอะไร
  • 3. ข้อกำหนดทางเทคนิค — ระบุวิธีทำ เช่น ใช้ Tailwind เท่านั้น ออกแบบแบบ mobile-first ใช้ semantic HTML และแยกไฟล์อะไรบ้าง
  • 4. ขอบเขต — ระบุสิ่งที่ยังไม่ต้องทำ เพื่อไม่ให้ Agent สร้างหน้าอื่น ติดตั้ง library หรือเพิ่ม animation เกินจากงานที่สั่ง

และแนบ screenshot ไปด้วยเสมอ — รูปกับข้อความทำงานคนละหน้าที่: รูปสื่อ pixel (สัดส่วน สี บรรยากาศ) ข้อความสื่อโครงสร้างและกติกา ใช้คู่กันได้ผลดีกว่าอย่างใดอย่างหนึ่งเดี่ยว ๆ มาก

Worked example — prompt ของ app shell

มาเขียนของจริง: prompt สำหรับ "โครง" ของแอป (sidebar + navbar) ซึ่งเราจะใช้สั่ง Agent จริงในบทเรียน 09 อ่านภาพประกอบก่อน แล้วดูว่าแต่ละบรรทัดของ prompt มาจากส่วนไหนของภาพ

สร้าง app shell ของเว็บ admin dashboard "Purity Dashboard" ตาม screenshot ที่แนบมา
(สนใจเฉพาะ sidebar ด้านซ้ายกับแถบบนของพื้นที่เนื้อหา)

บริบท: โปรเจกต์ React + TypeScript + Vite ติดตั้ง Tailwind CSS v4 และ react-router แล้ว
มี design tokens: primary (เขียวมิ้นต์), primary-dark, ink, muted, surface, success, danger

โครงสร้าง:
- Sidebar ซ้าย กว้างราว 260px พื้นหลังสีเดียวกับพื้นหลังหน้า (surface):
  - โลโก้ข้อความ "PURITY UI DASHBOARD" ด้านบน คั่นด้วยเส้นบาง ๆ
  - เมนูหลัก: Dashboard, Tables, Billing, RTL — แต่ละรายการมีไอคอนในกล่องสี่เหลี่ยมมุมโค้ง
  - หัวข้อตัวพิมพ์เล็ก "ACCOUNT PAGES" ตามด้วย Profile, Sign In, Sign Up
  - รายการที่ active: การ์ดพื้นขาว เงาอ่อน ไอคอนพื้นเขียวมิ้นต์ตัวอักษรขาว
  - รายการปกติ: ตัวอักษร muted ไอคอนพื้นขาวตัวอักษรเขียวมิ้นต์
  - ล่างสุด: การ์ดพื้นเขียวมิ้นต์ "Need help? Please check our docs" พร้อมปุ่มขาว DOCUMENTATION
- Navbar บนของพื้นที่เนื้อหา: breadcrumb "Pages / Dashboard" กับชื่อหน้าตัวหนา ด้านซ้าย,
  ช่องค้นหา placeholder "Type here...", ลิงก์ Sign In, ไอคอน settings และกระดิ่ง ด้านขวา
- พื้นที่เนื้อหา: ว่างไว้ก่อน ใส่  ของ react-router

ข้อกำหนดทางเทคนิค:
- ใช้ Tailwind utilities เท่านั้น ห้ามสร้างไฟล์ .css เพิ่ม
- Mobile-first: จอเล็กซ่อน sidebar ไว้ก่อนได้ (จะทำ drawer ภายหลัง)
- ใช้ semantic HTML: aside สำหรับ sidebar, nav, header, main; ไอคอนเป็น SVG inline
- แยกไฟล์: src/app/layouts/DashboardLayout.tsx, src/components/Sidebar.tsx, src/components/Navbar.tsx
- src/app/router.tsx: createBrowserRouter ให้ DashboardLayout เป็น layout route
  และมีหน้า Dashboard ว่าง ๆ ที่ path "/" ; ครอบ RouterProvider ใน main.tsx

ขอบเขต: ยังไม่ต้องสร้างเนื้อหาหน้า Dashboard จริง ยังไม่ต้องมี state ใด ๆ
และยังไม่ต้องทำหน้าอื่น

ไล่ดูที่มาของแต่ละส่วน

  • บรรทัดแรกวางกรอบ + บอกว่าให้ดูภาพเฉพาะส่วนไหน (ภาพเดียวมีทั้งหน้า — ต้องชี้)
  • "บริบท" มาจากบทเรียน 02 (stack) และ 05 (token) — บอกชื่อ token ให้ Agent ใช้ bg-primary ไม่ใช่ bg-teal-400
  • "โครงสร้าง" คือ bullet list จากการ decompose ในบทเรียน 06 แทบจะคำต่อคำ — สังเกตว่ามีเนื้อหาจริง ("PURITY UI DASHBOARD", "Type here...") ไม่ใช่ "ใส่โลโก้กับเมนู"
  • "ข้อกำหนดทางเทคนิค" ล็อกวิธีทำ รวมถึงชื่อไฟล์ — เรากำหนดโครงโปรเจกต์เอง จำได้ไหม
  • "ขอบเขต" ช่วยจำกัดงาน ถ้าไม่มีบรรทัดนี้ Agent อาจสร้างหน้า Dashboard ส่วนอื่นเพิ่มมาด้วย ทำให้ diff ใหญ่เกินความจำเป็น

Wireframe และ requirement ข้อความล้วน

กายวิภาคเดียวกันใช้ได้กับ input ทุกแบบ ไม่ใช่แค่ screenshot สวย ๆ

  • Wireframe หยาบ ๆ — สเก็ตช์บนกระดาษ/ไวท์บอร์ด ถ่ายรูปแนบได้เลย โครงสร้างชัดอยู่แล้วในเส้น เราแค่เติมส่วนบริบท (สี token, spacing) ที่ wireframe ไม่ได้บอก
  • Requirement ข้อความล้วน — เช่น "อยากได้หน้า list ผู้ใช้ กรองตามสถานะได้" กรณีนี้ไม่มีรูปให้แนบ เราจึงต้องเขียนส่วนโครงสร้างเองจากข้อสรุปที่คุยกับทีมไว้ และตรวจให้ครบก่อนส่งคำสั่ง

Checklist ก่อนกดส่ง

  • มีครบสี่ส่วนไหม (บริบท / โครงสร้าง / ข้อกำหนด / ขอบเขต)
  • โครงสร้างไล่บนลงล่าง พร้อมเนื้อหาจริง ไม่ใช่คำว่า "ฯลฯ" ไหม
  • บอกชื่อไฟล์ที่อยากได้ไหม
  • บอกสิ่งที่ยังไม่ต้องทำไหม
  • แนบรูปแล้วหรือยัง
