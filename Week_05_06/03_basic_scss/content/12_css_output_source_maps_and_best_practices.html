CSS Output, Source Maps และ Best Practices

ตอนนี้เราเรียนตั้งแต่ตัวแปรไปจนถึง control flow แล้ว บทสุดท้ายจึงพากลับมาดูภาพรวมว่า “เวลาใช้งานจริง เราควรคอมไพล์ Sass แบบไหน และควรดูแลไฟล์ผลลัพธ์อย่างไร” เพราะต่อให้เขียน SCSS ได้ดี ถ้า workflow ตอน build ไม่ชัด ทีมก็ยังสับสนได้ว่าไฟล์ไหนควรแก้ ไฟล์ไหนควรถูก generate และไฟล์ไหนเหมาะกับ production

คำสั่งที่ใช้บ่อยที่สุดมีอยู่ 3 แบบ

สำหรับคอร์สเริ่มต้น ชุดคำสั่งต่อไปนี้ครอบคลุมงานที่เจอบ่อยที่สุด:

npx sass --watch scss/main.scss:css/main.css
npx sass scss/main.scss css/main.css --style=expanded
npx sass scss/main.scss css/main.min.css --style=compressed --no-source-map
คำสั่ง เหมาะเมื่อไร ผลลัพธ์หลัก
--watch กำลังพัฒนาและบันทึกไฟล์บ่อย ๆ คอมไพล์ใหม่อัตโนมัติทุกครั้งที่ SCSS เปลี่ยน
--style=expanded อยากได้ CSS ที่อ่านง่ายสำหรับเปิดตรวจ จัดบรรทัดและย่อหน้าให้อ่านสะดวก
--style=compressed --no-source-map เตรียมไฟล์ขนาดเล็กสำหรับ deploy ได้ CSS แบบบีบอัดและไม่สร้างไฟล์แผนที่ต้นฉบับ

งานพัฒนาต่อเนื่องใช้ watch mode

npx sass --watch scss/main.scss:css/main.css

คำสั่งนี้เหมาะที่สุดตอนกำลังทำหน้าเว็บอยู่จริง เพราะทุกครั้งที่คุณกดบันทึก Sass จะคอมไพล์ scss/main.scss ไปเป็น css/main.css ให้อัตโนมัติ จึงลดการสลับไปพิมพ์คำสั่งเดิมซ้ำ ๆ ใน terminal

ถ้าเปิด DevTools ในเบราว์เซอร์ระหว่างพัฒนา watch mode จะยิ่งมีประโยชน์ เพราะคุณจะเห็นผลที่อัปเดตไว และถ้า source maps ยังเปิดอยู่ เครื่องมือ developer จะชี้กลับไปที่ไฟล์ SCSS ต้นทางได้ง่ายขึ้นด้วย

งานตรวจโค้ดหรือส่งต่อให้ทีมใช้ expanded CSS

npx sass scss/main.scss css/main.css --style=expanded

--style=expanded ทำให้ CSS ที่ได้ยังอ่านง่าย มีการขึ้นบรรทัดและเว้นวรรคชัดเจน เหมาะเมื่อคุณอยากเปิดไฟล์ผลลัพธ์เพื่อตรวจว่า selector, property หรือค่าที่คอมไพล์ออกมาตรงกับที่คิดไว้หรือไม่ 

.button {
  padding: 1rem 1.25rem;
  background-color: #6f3cc3;
  color: #ffffff;
}

รูปแบบนี้เหมาะสำหรับการ debug ในระดับไฟล์ผลลัพธ์ เช่นเช็กว่า mixin ถูก expand ครบไหม หรือ loop สร้างคลาสเกินจำเป็นหรือเปล่า

งาน production เน้นไฟล์เล็กและชัดว่าเป็น output

npx sass scss/main.scss css/main.min.css --style=compressed --no-source-map

คำสั่งนี้สร้างไฟล์ css/main.min.css แบบบีบอัด ทำให้ขนาดไฟล์เล็กลง เหมาะกับการนำไป deploy และ --no-source-map จะปิดการสร้าง source map จึงได้ output ที่เหลือแค่ไฟล์ CSS ตามต้องการ 

.button{padding:1rem 1.25rem;background-color:#6f3cc3;color:#fff}

การตั้งชื่อไฟล์เป็น .min.css ไม่ใช่ข้อบังคับของ Sass แต่เป็น convention ที่ช่วยให้ทั้งทีมเห็นทันทีว่าไฟล์นี้คือเวอร์ชันสำหรับใช้งานจริง ไม่ใช่ไฟล์ที่ตั้งใจเปิดมาแก้ด้วยมือ

Source maps คือสะพานจาก CSS กลับไปหา SCSS

source map คือไฟล์ metadata ที่บอกว่า CSS แต่ละบรรทัดมาจาก SCSS ต้นฉบับส่วนไหน เวลา inspect element ในเบราว์เซอร์ เราจึงย้อนกลับไปหาไฟล์ _buttons.scss หรือ main.scss ได้เร็ว แทนที่จะต้องไล่จาก CSS ที่คอมไพล์แล้วอย่างเดียว

  • ระหว่างพัฒนา source maps ช่วย debug ได้เร็วขึ้นมาก
  • ระหว่างเรียนช่วยให้เห็นความเชื่อมโยงระหว่าง SCSS กับ CSS ชัดขึ้น
  • ตอน build production บางทีมปิด source maps เพื่อให้ artifact ที่ deploy มีแต่ไฟล์ที่จำเป็นจริง

ไม่มีคำตอบเดียวว่าควรเปิด source maps ใน production หรือไม่ เพราะขึ้นกับ pipeline, ความต้องการด้าน debug หลัง deploy และนโยบายของทีม แต่สำหรับคำสั่ง production พื้นฐานในบทนี้ เราเลือกตัวอย่างที่ปิดไว้ก่อนเพื่อให้เห็นผลของ --no-source-map แบบชัดเจน

อย่าแก้ CSS ที่ generate แล้วด้วยมือ

หลักจำที่สำคัญที่สุดของบทนี้คือ แก้ที่ SCSS ต้นฉบับเสมอ ถ้าคุณไปแก้ css/main.css หรือ css/main.min.css โดยตรง การคอมไพล์รอบถัดไปจะเขียนทับทันที ทำให้ทีมงงว่าทำไม style ที่เพิ่งแก้หายไป

ถ้าเห็นไฟล์ CSS เปลี่ยนไปหลังรัน Sass ให้คิดว่า “นี่คือผลลัพธ์” ไม่ใช่ “นี่คือที่ที่ฉันควรเริ่มแก้ปัญหา”

ควร commit ไฟล์ CSS ลง git หรือไม่

เรื่องนี้ขึ้นกับวิธี deploy ของโปรเจกต์ ถ้า server หรือ CI คอมไพล์ Sass ให้ทุกครั้งอยู่แล้ว หลายทีมจะ commit เฉพาะ SCSS แล้วให้ระบบสร้าง CSS ตอน build

แต่ถ้าโปรเจกต์เป็น static site ง่าย ๆ, ส่งไฟล์ให้คนอื่นเปิดตรง ๆ หรือมีสภาพแวดล้อมที่ไม่ได้ติดตั้ง Sass ไว้ การ commit CSS ที่คอมไพล์แล้วก็อาจเหมาะกว่า เพื่อให้ทุกคนเปิดใช้งานได้ทันทีโดยไม่ต้อง build เพิ่ม

สถานการณ์ แนวทางที่มักเหมาะกว่า
มี build pipeline ชัดเจนใน CI/CD มัก commit เฉพาะ SCSS แล้ว build CSS ตอน deploy
ต้องส่งไฟล์เว็บสำเร็จรูปให้เปิดใช้งานได้ทันที มัก commit CSS ที่คอมไพล์แล้วไปด้วย
ทีมยังใหม่กับ tooling และต้องการเห็น output ชัด ๆ อาจเก็บทั้ง SCSS และ CSS ช่วงแรกเพื่อให้เรียนรู้ workflow

สิ่งสำคัญไม่ใช่ว่าต้องเลือกทางไหนเหมือนทุกทีม แต่คือทีมต้องตกลงให้ตรงกันว่าไฟล์ CSS ปลายทางถูกสร้างที่ไหน ใครเป็นคนสร้าง และ git ควรเก็บอะไรไว้เป็น source of truth

เลือกเครื่องมือ SCSS ให้เหมาะกับปัญหา

เครื่องมือ ใช้เมื่อไร อย่าใช้แทนอะไร
Variables ค่าถูกใช้ซ้ำและต้องเปลี่ยนพร้อมกัน เช่น สี ระยะ spacing อย่าใช้แทนข้อมูลหลายชุดที่ควรจัดเป็น map
Nesting ต้องการแสดงความสัมพันธ์ใกล้ชิดของ selector แบบไม่ลึกเกินไป อย่าซ้อนหลายชั้นจน selector ยาวและ debug ยาก
Modules และ @use ต้องแยก token หรือ helper ออกเป็นไฟล์ที่เรียกใช้ซ้ำ ไม่ควรใช้ @import กับโค้ดใหม่
Mixins ต้อง reuse กลุ่ม declaration หรือ pattern ที่มีพารามิเตอร์ อย่าใช้แทน class จริงเมื่อ pattern นั้นควรเป็น component ปกติ
Loops และ control flow ต้อง generate ชุดกฎที่มีรูปแบบแน่นอนและจำนวนจำกัด อย่าใช้สร้าง CSS ปริมาณใหญ่เกินการใช้งานจริง

Checklist สั้น ๆ ก่อนจบบทเรียน

  • พัฒนาต่อเนื่อง ใช้ --watch
  • อยากอ่าน output ง่าย ใช้ --style=expanded
  • อยากได้ไฟล์ production ที่เล็ก ใช้ --style=compressed
  • ถ้าไม่ต้องการ source maps ให้เติม --no-source-map
  • แก้ที่ SCSS ต้นฉบับ ไม่แก้ไฟล์ CSS ที่ generate แล้ว
  • ตกลงกับทีมให้ชัดว่าจะ commit CSS หรือ build ตอน deploy

แบบฝึกหัด

สมมติว่าคุณมีไฟล์ scss/main.scss อยู่แล้ว และวันนี้มีสองงาน: งานแรกคือพัฒนา UI ต่อเนื่องระหว่างเปิดเบราว์เซอร์ไว้ดูผล งานที่สองคือเตรียมไฟล์ CSS ขนาดเล็กสำหรับ production ให้เลือกคำสั่งที่เหมาะกับแต่ละงานจากทั้งสามคำสั่งในบทนี้ แล้วอธิบายด้วยว่าแต่ละ flag สำคัญอย่างไร

ดูเฉลย

งานพัฒนาต่อเนื่องควรใช้:

npx sass --watch scss/main.scss:css/main.css
  • --watch ทำให้ Sass เฝ้าดูไฟล์และคอมไพล์ใหม่อัตโนมัติ
  • รูปแบบ input:output บอกว่าต้องอ่านจาก scss/main.scss แล้วเขียนไปที่ css/main.css

งาน production ควรใช้:

npx sass scss/main.scss css/main.min.css --style=compressed --no-source-map
  • --style=compressed บีบ CSS ให้สั้นลงเพื่อลดขนาดไฟล์
  • --no-source-map ปิดการสร้าง source map
  • การเขียนออกเป็น main.min.css ช่วยสื่อว่านี่คือไฟล์ output ที่เหมาะกับการนำไปใช้งานจริง
