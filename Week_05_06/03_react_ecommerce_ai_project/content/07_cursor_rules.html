บทเรียน 07 · ตั้งวงกับ Cursor (Setting Up Cursor)

เขียน .cursor/rules ของโปรเจกต์

Project Rules

บทที่แล้วเราติดตั้งเครื่องมือเสร็จ บทนี้เราจะบอกมันว่าโปรเจกต์นี้ทำงานอย่างไร ทั้งบทมีไฟล์ให้สร้างไฟล์เดียว แต่ไฟล์นั้นจะมีผลกับทุก prompt ที่คุณส่งตลอด 27 บทที่เหลือ

ปัญหา: prompt เดียวกัน ผลลัพธ์คนละทิศ

สมมติคุณส่งคำสั่งสั้น ๆ ให้ Agent ที่ยังไม่รู้จักโปรเจกต์เราเลย: "สร้าง component ชื่อ ProductCard ที่แสดงรูป ชื่อ และราคาสินค้า" สิ่งที่มักจะได้กลับมาคือโค้ดที่ทำงานได้ แต่ไม่ตรงกับข้อตกลงของเราเลยสักข้อ:

  • ไฟล์ไปโผล่ที่ src/components/ProductCard.tsx — โฟลเดอร์ที่ไม่มีในผังของเรา และเป็นการแบ่งตามชนิดไฟล์แบบที่บทเรียน 05 อธิบายไปแล้วว่าเราไม่เอา
  • style เป็น style={{ padding: 16, border: "1px solid #ddd" }} เขียนติดไว้ใน JSX ทั้งที่เราวางระบบ SCSS Modules ไว้ตั้งแต่บทเรียน 04
  • import เขียนว่า import { Product } from "../../features/products/types" ทั้งที่เราตั้ง alias @/ ไว้ในบทเรียน 03 เพื่อไม่ให้มีบรรทัดหน้าตาแบบนี้
  • บางรอบมันแถม npm install clsx มาให้ด้วย เพราะมัน "คิดว่าน่าจะสะดวก"

ไม่มีข้อไหนเป็นความผิดของ AI มันไม่เคยเห็นข้อตกลงของเรา มันจึงเลือกสิ่งที่พบบ่อยที่สุดในโค้ด React ทั่วโลก ซึ่งไม่ใช่สิ่งที่โปรเจกต์นี้ตกลงกันไว้ ทางแก้แบบตรงไปตรงมาคือพิมพ์ข้อตกลงพวกนี้ลงไปในทุก prompt — และนั่นคือสิบกว่าบรรทัดเดิมซ้ำอีกยี่สิบกว่ารอบ ซึ่งนอกจากจะน่าเบื่อแล้ว วันที่คุณลืมพิมพ์สักข้อ คุณจะได้โค้ดที่หลุดกติกากลับมาโดยไม่รู้ตัว

rules คืออะไร

Cursor ให้เราเก็บข้อตกลงพวกนี้ไว้ในไฟล์ในโฟลเดอร์ .cursor/rules/ ของโปรเจกต์ ไฟล์นามสกุล .mdc คือ markdown ที่มี frontmatter ข้างบนบอกว่ากติกาชุดนี้ใช้เมื่อไหร่ — ถ้าเขียน alwaysApply: true แปลว่าใช้กับทุกคำขอในโปรเจกต์นี้ Agent จะอ่านไฟล์นี้เองก่อนลงมือทุกครั้ง โดยที่เราไม่ต้อง @ แนบมันไปด้วย

พูดอีกอย่างคือ rules ทำให้ prompt ของเราสั้นลง ไม่ใช่ยาวขึ้น สิ่งที่เป็นจริงเสมอสำหรับโปรเจกต์นี้ (stack, ผังโฟลเดอร์, ข้อห้าม) ย้ายไปอยู่ในไฟล์ ส่วน prompt เหลือแค่สิ่งที่ต่างกันในแต่ละงาน — จะสร้างอะไร ชื่ออะไร ทำอะไรได้บ้าง คุณจะเห็นผลของเรื่องนี้ชัดมากในบทหน้า ตอนที่ prompt ของงานสร้าง router ทั้งชุดยาวไม่ถึงหนึ่งหน้าจอ

อีกเรื่องที่ควรรู้ตั้งแต่ตอนนี้: .cursor/rules/project.mdc เป็นไฟล์ในโปรเจกต์ มันถูก commit เข้า git เหมือนไฟล์อื่น ๆ ไม่ใช่การตั้งค่าส่วนตัวในเครื่องคุณ ในทีมจริงข้อนี้คือประเด็นทั้งหมดของมัน — กติกาของโปรเจกต์อยู่ใน repo และเปลี่ยนผ่าน pull request ไม่ใช่คนละชุดในเครื่องแต่ละคน

สร้างไฟล์กติกา

สร้างโฟลเดอร์และไฟล์จาก root ของโปรเจกต์:

mkdir -p .cursor/rules

แล้วสร้าง .cursor/rules/project.mdc ด้วยเนื้อหานี้ทั้งหมด — นี่คือกติกาชุดที่ทุก prompt ในคอร์สนี้เขียนขึ้นโดยถือว่ามีอยู่แล้ว ถ้าคุณตัดข้อไหนออก prompt ในบทหลัง ๆ จะขาดข้อมูลไปหนึ่งชิ้นเสมอ:

---
description: กติกาของโปรเจกต์ e-commerce นี้
alwaysApply: true
---

# Stack
- React 19 + TypeScript (strict) + Vite 8
- react-router 8 (data mode), TanStack Query 5, axios
- SCSS Modules เท่านั้น ห้ามใช้ inline style และห้ามใช้ CSS-in-JS
- ฟอร์มใช้ react-hook-form + zod

# โครงสร้างไฟล์
- src/app/      — router, providers, layouts
- src/pages/    — หนึ่งโฟลเดอร์ต่อหนึ่งหน้า พร้อม components/ ของหน้านั้น
- src/features/ — โค้ดที่ผูกกับฟีเจอร์ (products, cart, checkout): api, queries, types, store
- src/shared/   — ของที่ใช้ข้ามฟีเจอร์: components, hooks, utils, api, types
- ห้ามสร้างโฟลเดอร์ระดับบนใหม่นอกเหนือจากนี้
- component หนึ่งตัว = หนึ่งโฟลเดอร์: Name.tsx + Name.module.scss

# กติกาการเขียนโค้ด
- import ข้ามโฟลเดอร์ใช้ alias @/ เสมอ ห้ามใช้ ../../
- ห้ามใช้ any และห้ามใช้ as เพื่อกลบ type error
- ห้าม fetch ใน useEffect — server state ทุกตัวผ่าน TanStack Query
- reducer ต้องเป็น pure function: ห้าม mutate state เดิม
- ตั้งชื่อ: component = PascalCase, hook = useCamelCase, ไฟล์ util = camelCase.utils.ts

# ขอบเขต
- ห้ามติดตั้ง dependency ใหม่ถ้าไม่ได้สั่ง
- ห้ามแก้ไฟล์ที่ไม่ได้ระบุในคำสั่ง
- ห้ามเขียน comment อธิบายสิ่งที่โค้ดบอกอยู่แล้ว

สังเกตว่าไม่มีอะไรในไฟล์นี้ที่คุณเพิ่งเจอครั้งแรก ทั้งหมดคือข้อสรุปของบทเรียน 02–05 ที่ถูกเขียนใหม่ให้อยู่ในรูปที่เครื่องอ่านรู้เรื่อง:

  • Stack — รายการเครื่องมือจากบทนำ บวกข้อห้ามเรื่อง style ที่มาจากบทเรียน 04 บรรทัด "SCSS Modules เท่านั้น" ตัดปัญหา inline style และ CSS-in-JS ทิ้งตั้งแต่ต้นทาง ส่วน react-router, TanStack Query, axios, react-hook-form และ zod ยังไม่ได้ติดตั้งในตอนนี้ — เขียนไว้เพราะมันคือทิศทางของโปรเจกต์ Agent จะได้ไม่เสนอ Redux หรือ SWR เข้ามาแทน แต่ละบทจะติดตั้งของที่ต้องใช้ด้วยมือก่อนส่ง prompt เสมอ (ดูตัวอย่างในบทหน้า)
  • โครงสร้างไฟล์ — สี่ชั้นจากบทเรียน 05 ตรงตัว พร้อมสองบรรทัดที่ทำหน้าที่เป็นรั้ว: ห้ามสร้างโฟลเดอร์ระดับบนใหม่ (กัน src/components/ ที่ยกตัวอย่างไปข้างบน) และ component หนึ่งตัวหนึ่งโฟลเดอร์คู่กับ .module.scss ของมัน
  • กติกาการเขียนโค้ด — ข้อแรกคือ alias จากบทเรียน 03 ที่เหลือคือกติกาที่บทเรียน 01 บอกว่าคือความหมายของคำว่า "ถูกวิธี" ในคอร์สนี้ ข้อ any และ as สำคัญกว่าที่เห็น เพราะเวลา AI เจอ type error มันมีทางออกที่ง่ายที่สุดอยู่สองทางนี้เสมอ ซึ่งทำให้ error หายจากจอโดยที่ปัญหายังอยู่ครบ
  • ขอบเขต — สามข้อนี้คุมขนาดของ diff ข้อ "ห้ามแก้ไฟล์ที่ไม่ได้ระบุ" คือข้อที่ทำให้ git diff ในขั้นตอนตรวจงานอ่านไหว ส่วนข้อสุดท้ายกัน comment ประเภท // set the loading state ที่ทับอยู่บน setLoading(true) ซึ่ง AI ผลิตออกมาเยอะมากถ้าไม่ห้าม

commit ไฟล์นี้ทันที — ก่อนส่ง prompt แรก ตามกติกาของบทที่แล้ว:

git add .cursor/rules/project.mdc
git commit -m "chore: add cursor project rules"

ทดลองให้เห็นผลด้วยตัวเอง

อ่านมาถึงตรงนี้คุณอาจเชื่อไปแล้วว่ามันช่วย แต่ให้ลองเองหนึ่งรอบ ใช้เวลาห้านาที และเป็นครั้งเดียวในคอร์สที่เราจะจงใจสั่งงานแบบไม่มีกติกาเพื่อดูว่าผลออกมาหน้าตาอย่างไร โจทย์ที่ใช้คือ component เล็ก ๆ ที่ไม่เกี่ยวกับแอปจริง (เราจะลบทิ้งทั้งสองรอบ):

สร้าง component ชื่อ Badge ที่รับ prop label แล้วแสดงเป็นป้ายสีเทา

สังเกตว่า prompt นี้จงใจสั้นและกำกวม ไม่ได้บอกว่าจะให้ไฟล์ไปอยู่ไหนหรือ style ด้วยอะไร — นั่นคือประเด็นของการทดลอง: เราอยากรู้ว่าเมื่อเราไม่บอก มันเติมช่องว่างด้วยอะไร

รอบที่ 1 — ปิดกติกา

  1. git status ต้องสะอาด
  2. ปิดกติกาชั่วคราวด้วยวิธีที่แน่นอนที่สุดคือเปลี่ยนชื่อไฟล์: mv .cursor/rules/project.mdc .cursor/rules/project.mdc.off (ใน Cursor มีหน้า Settings สำหรับเปิด/ปิด rules อยู่ด้วย แต่ตำแหน่งเมนูเปลี่ยนไปตามเวอร์ชัน การเปลี่ยนชื่อไฟล์ได้ผลเหมือนกันและไม่มีทางเข้าใจผิด)
  3. เปิดแชท เลือกโหมด Agent ส่ง prompt ข้างบน
  4. ดู git status และ git diff แล้วจดสามอย่างไว้: ไฟล์ไปอยู่ที่ไหน, style ด้วยวิธีอะไร, import เขียนแบบไหน
  5. ล้างทิ้ง: git restore . แล้วลบไฟล์ใหม่ที่ยังไม่ถูก track ออกให้หมด (git status จะบอกว่ามีไฟล์อะไรบ้าง)

รอบที่ 2 — เปิดกติกา

  1. เปลี่ยนชื่อไฟล์กลับ: mv .cursor/rules/project.mdc.off .cursor/rules/project.mdc
  2. git status ต้องสะอาดอีกครั้ง
  3. เปิดแชทใหม่ (อย่าส่งต่อในแชทเดิม — ข้อความรอบแรกยังค้างอยู่และจะปนผลการทดลอง) ส่ง prompt เดิมคำต่อคำ
  4. จดสามอย่างเดิมอีกครั้ง แล้วเทียบกัน

ผลที่คาดว่าจะเห็นคือรอบสองไฟล์ไปอยู่ในโฟลเดอร์ที่ผังของเรามีจริง มาพร้อม .module.scss คู่กัน และ import ใช้ @/ ส่วนรายละเอียดอื่นอาจต่างไปจากนี้ — โมเดลแต่ละตัวและแต่ละรอบไม่เหมือนกันเป๊ะ ๆ สิ่งที่ต้องดูให้ออกคือทิศทาง ไม่ใช่ผลลัพธ์ที่ตรงกันทุกตัวอักษร

ถ้ารอบสองยังไม่ต่างจากรอบแรกเลย ให้เช็กสามอย่างก่อนสรุปว่ากติกาไม่ทำงาน: ไฟล์ชื่อ .cursor/rules/project.mdc ถูกต้องไหม (จุดข้างหน้าครบ นามสกุล .mdc ไม่ใช่ .md), frontmatter สามบรรทัดบนสุดอยู่ครบและมี alwaysApply: true ไหม, และคุณเปิดโฟลเดอร์รากของโปรเจกต์ใน Cursor อยู่จริงไหม

ปิดท้ายด้วยการล้างของทดลองให้หมด: git restore . และลบไฟล์ Badge ทั้งหมดทิ้ง จบบทนี้ในโปรเจกต์ควรมีไฟล์ใหม่แค่ .cursor/rules/project.mdc ไฟล์เดียว

rules ไม่ใช่คาถา

สิ่งที่ต้องเข้าใจให้ตรงกันก่อนจบบท: กติกาชุดนี้ลดโอกาสพลาด ไม่ได้กำจัดมัน Agent อ่านไฟล์นี้ทุกครั้งจริง แต่มันไม่ใช่ตัวตรวจ (linter) ที่บังคับผลลัพธ์ได้ มันคือข้อความอีกชุดที่ถูกเอามาชั่งน้ำหนักรวมกับคำสั่งของคุณ ยิ่งงานซับซ้อนหรือ prompt ยาว โอกาสที่บางข้อจะหลุดก็ยิ่งมี

ที่เห็นบ่อยคือมันทำถูกเก้าข้อแล้วหลุดข้อเดียว — โครงสร้างถูก ชื่อไฟล์ถูก SCSS module มาครบ แต่มี as unknown as Product โผล่มาหนึ่งบรรทัดตรงจุดที่ type ไม่ลงตัว ซึ่งเป็นบรรทัดที่ผ่าน npm run lint ได้สบาย ๆ

นี่คือเหตุผลที่ทุกบทตั้งแต่บทเรียน 09 เป็นต้นไปยังมีช่อง ✅ ให้ตรวจอยู่ดี แม้กติกาจะอยู่ในไฟล์แล้ว rules ทำให้ของที่กลับมาใกล้เคียงสิ่งที่ต้องการมากขึ้นมาก จนคุณเหลืองานแค่ไล่ตรวจ ไม่ใช่ไล่แก้ทั้งไฟล์ — แต่มันไม่ได้ทำให้ขั้นตอนตรวจหายไป

เครื่องมือพร้อม กติกาพร้อม เหลืออย่างเดียวคือวิธีสั่งงานและวิธีตรวจของที่ได้กลับมา ซึ่งเป็นเนื้อหาทั้งหมดของบทหน้า และเป็นบทสุดท้ายก่อนที่เราจะเริ่มสร้างแอปจริง

💡 Checkpoint: ไฟล์ .cursor/rules/project.mdc มีอยู่จริงและ commit เข้า git แล้ว (เช็กด้วย git log --oneline -1 และ ls -a .cursor/rules), คุณทดลอง Badge ครบทั้งสองรอบและบอกได้ว่าสามอย่าง — ตำแหน่งไฟล์, วิธี style, รูปแบบ import — ต่างกันอย่างไร, และ git status ตอนนี้สะอาด ไม่มีไฟล์ Badge หลงเหลืออยู่ ถ้ายังมีไฟล์ทดลองค้างอยู่ ลบให้หมดก่อนไปบทหน้า เพราะบทถัดไปเราจะเริ่มนับ diff กันจริงจังแล้ว
