บทเรียน 08 · ตั้งวงกับ Cursor (Setting Up Cursor)

Prompt สำหรับ Codebase และวงจรตรวจงาน

Prompting & Review Loop

บทนี้คือบทสุดท้ายก่อนลงสนามจริง และเป็นบทที่คุณจะย้อนกลับมาเปิดบ่อยที่สุดในคอร์ส เพราะสองสิ่งที่อยู่ในนี้ — โครงของ prompt และวงจรตรวจงาน — จะวนซ้ำในทุกบทตั้งแต่บทเรียน 09 เป็นต้นไป กล่อง 🤖 ทุกกล่องเขียนตามโครงในบทนี้ และกล่อง ✅ ทุกกล่องคือขั้นที่สองของวงจรในบทนี้

ข้อแตกต่างสำคัญที่ต้องตั้งหลักให้ถูกก่อน: คุณไม่ได้กำลังสั่งให้ AI สร้างของจากศูนย์ คุณกำลังสั่งให้มันเติมของลงในโปรเจกต์ที่มีรูปทรงอยู่แล้ว งานของ prompt จึงไม่ใช่การบรรยายว่าอยากได้อะไรสวย ๆ แต่คือการบอกให้ครบว่าของใหม่ต้องเข้ากับของเดิมอย่างไร

กายวิภาคสี่ส่วน

ทุก prompt ในคอร์สนี้มีสี่ส่วน เรียงตามนี้เสมอ และใช้คำเดิมทุกครั้งเพื่อให้คุณกวาดตาหาส่วนที่ต้องการเจอทันที:

  • บริบท: — ไฟล์ไหนในโปรเจกต์ที่เกี่ยวข้องกับงานนี้ ส่วนนี้คือ @-mention เป็นหลัก บวกข้อเท็จจริงสั้น ๆ ที่ Agent มองไม่เห็นจากไฟล์ (เช่น "โฟลเดอร์นี้ยังว่างเพราะเราตั้งใจให้ว่าง") สังเกตว่ามันไม่ใช่การเล่าว่า "แอปนี้คือเว็บขายของ" — Agent ไม่ได้ต้องการเรื่องเล่า มันต้องการรู้ว่าจะไปอ่านของจริงได้ที่ไฟล์ไหน
  • โครงสร้าง: — จะสร้างไฟล์อะไร ชื่ออะไร อยู่ที่ไหน ระบุเป็นรายการ path เต็ม ๆ ตรงนี้คือจุดที่ผังจากบทเรียน 05 ถูกใช้งานจริง คุณไม่ได้ปล่อยให้ AI เลือกที่อยู่ของไฟล์ คุณเป็นคนบอก
  • ข้อกำหนดทางเทคนิค: — ต้องทำอะไรได้บ้าง และทำด้วยวิธีไหน ชื่อ export, ชื่อ hook ที่ต้องใช้, พฤติกรรมของแต่ละกรณี ส่วนนี้ยาวที่สุดเสมอ และเป็นส่วนที่ตัดสินว่าคุณจะได้ของถูกตั้งแต่รอบแรกหรือต้องสั่งซ้ำสามรอบ
  • ขอบเขต: — ห้ามทำอะไร สิ่งที่ยังไม่ถึงเวลา ไฟล์ที่ห้ามแตะ dependency ที่ห้ามติดตั้ง ส่วนนี้สั้นที่สุดแต่ตัดงานตรวจออกไปได้มากที่สุด เพราะมันคือสิ่งที่ทำให้ git diff เล็กพอที่จะอ่านจบ

คำถามที่ควรถามตัวเองก่อนกดส่ง: "มีอะไรในหัวผมที่ Agent ต้องเดา" ทุกอย่างที่มันต้องเดา คือสิ่งที่คุณจะต้องไปไล่แก้ทีหลัง

Worked example: prompt ของเราเตอร์

มาเขียนของจริงกัน นี่คือ prompt ที่คุณจะได้ใช้จริงในบทเรียน 09 เพื่อสร้าง router.tsx พร้อมหน้าเปล่าทั้งหกหน้า — ยังไม่ต้องส่งตอนนี้ บทนี้เราอ่านมันเพื่อดูว่าทำไมแต่ละบรรทัดต้องอยู่ในนั้น

ก่อนอื่นสิ่งที่ต้องทำก่อนเปิดแชท: ติดตั้ง router ด้วยมือตัวเอง

npm install react-router
git add -A && git commit -m "chore: install react-router"

ที่ไม่ปล่อยให้ Agent ติดตั้งเอง เพราะการเลือก dependency และเวอร์ชันเป็นการตัดสินใจ ไม่ใช่การพิมพ์ — และกติกาในไฟล์ rules ก็เขียนไว้แล้วว่าห้ามติดตั้งอะไรถ้าไม่ได้สั่ง ตอนนี้ working tree สะอาด พร้อมส่ง prompt:

สร้างเราเตอร์และหน้าเปล่าทั้งหกหน้าของแอป

บริบท: @src/app @src/pages @src/main.tsx
ติดตั้ง react-router 8 ไว้แล้ว
src/app/ กับ src/pages/ ยังเป็นโฟลเดอร์ว่าง ส่วน src/main.tsx render placeholder App จาก ./App และ import ./styles/main.scss อยู่
alias @/ ชี้ไปที่ src/ ตั้งค่าไว้แล้วทั้งใน vite.config.ts และ tsconfig.app.json

โครงสร้าง: สร้างไฟล์ตามนี้ ไม่มากไม่น้อยกว่านี้
- src/app/router.tsx
- src/app/RouteErrorFallback.tsx
- src/app/layouts/MainLayout/MainLayout.tsx
- src/app/App.tsx
- src/pages/Home/Home.tsx
- src/pages/Category/Category.tsx
- src/pages/Product/Product.tsx
- src/pages/Cart/Cart.tsx
- src/pages/Checkout/Checkout.tsx
- src/pages/Order/OrderSuccess.tsx
และแก้ src/main.tsx ให้ render App ตัวใหม่ จากนั้นลบ src/App.tsx เดิมทิ้ง (ย้ายมาเป็น src/app/App.tsx แล้ว)

ข้อกำหนดทางเทคนิค:
- router.tsx: export const routes: RouteObject[] และ export const router = createBrowserRouter(routes)
  โดย import createBrowserRouter กับ RouteObject จาก "react-router"
- routes มี route แม่หนึ่งตัว element เป็น MainLayout และ errorElement เป็น RouteErrorFallback
  ไม่ต้องใส่ path ให้ route แม่
- children ของ route แม่ เรียงตามลำดับนี้:
  "/"               -> Home
  "/categories"     -> Category
  "/products/:id"   -> Product
  "/cart"           -> Cart
  "/checkout"       -> Checkout
  "/order/success"  -> OrderSuccess
- MainLayout: default export ที่ render Outlet ของ react-router ไว้ในแท็ก main
- RouteErrorFallback: default export ที่ใช้ useRouteError() กับ isRouteErrorResponse()
  ถ้าเป็น route error response ให้แสดงข้อความ `${error.status} ${error.statusText}`
  ถ้าไม่ใช่ ให้แสดง "Something went wrong. Please reload the page."
- หน้าทั้งหกเป็น stub: default export ที่ return แท็ก h1 ชื่อหน้าเท่านั้น ยังไม่ต้องมี state หรือข้อมูล
- App.tsx: default export ที่ return RouterProvider พร้อม prop router={router}
  โดย import RouterProvider จาก "react-router/dom"
- src/main.tsx: render App จาก "./app/App" และคงบรรทัด import "./styles/main.scss" ไว้
- import ไฟล์ที่อยู่คนละโฟลเดอร์ใช้ alias @/ ไฟล์ที่อยู่โฟลเดอร์เดียวกันใช้ ./ ได้

ขอบเขต:
- ห้ามติดตั้ง dependency ใหม่
- ยังไม่ต้องสร้าง Header, Footer, QueryClientProvider หรือไฟล์ .module.scss ใด ๆ
- ห้ามแก้ไฟล์อื่นนอกจากที่ระบุไว้ข้างบน

ที่มาของแต่ละบรรทัด

ไม่มีบรรทัดไหนในนั้นที่คิดขึ้นสด ๆ ทุกบรรทัดมีที่มาจากสิ่งที่เราตกลงกันไว้แล้วในบทก่อน ๆ:

  • บรรทัดแรก — สรุปงานทั้งชิ้นเป็นประโยคเดียว มีไว้ให้ Agent (และตัวคุณเองตอนย้อนอ่าน history) รู้ว่าคำสั่งนี้จบที่ตรงไหน
  • @src/app @src/pages @src/main.tsx — เทคนิคจากบทเรียน 06 สามตัวนี้คือทุกที่ที่ diff จะไปตกลง ไม่แนบมากกว่านี้เพราะการแนบไฟล์ที่ไม่เกี่ยวไม่ได้ทำให้แม่นขึ้น
  • "ยังเป็นโฟลเดอร์ว่าง" — Agent เห็นว่าโฟลเดอร์ว่าง แต่ไม่รู้ว่าว่างเพราะเราตั้งใจ หรือว่างเพราะมันเปิดผิดที่ ประโยคเดียวนี้กันไม่ให้มันไป "ค้นหา" router ที่อื่นในโปรเจกต์ก่อนเริ่มทำงาน
  • ประโยคที่บอกว่า main.tsx มีอะไรอยู่ — เขียนให้ตรงกับไฟล์จริง (placeholder App จากบทเรียน 02 และ import "./styles/main.scss" จากบทเรียน 04) เพราะ prompt นี้สั่งให้แก้ main.tsx ด้วย และไฟล์ที่สั่งให้แก้ ถ้าอธิบายผิด Agent มีสิทธิ์เขียนใหม่ทั้งไฟล์ ผลที่ตามมาคือบรรทัด main.scss หายไปเงียบ ๆ — style ทั้งแอปหายทั้งชุด โดยที่ lint ผ่าน typecheck ผ่าน และหน้าเว็บก็ยังขึ้น นี่คือเหตุผลที่ ข้อกำหนดทางเทคนิค: ย้ำอีกครั้งว่าให้คงบรรทัดนั้นไว้ ข้อเท็จจริงในส่วนบริบทต้องตรงกับของจริงเสมอ ไม่ใช่ตรงกับที่คุณจำได้
  • บรรทัด alias — มาจากบทเรียน 03 ตรง ๆ ในไฟล์ rules เขียนไว้แล้วว่าให้ใช้ @/ แต่ตรงนี้เราย้ำว่ามันถูกตั้งค่าไว้จริงทั้งสองที่ ต่างกันตรงที่ข้อแรกคือกติกา ข้อนี้คือข้อเท็จจริงของโปรเจกต์ — Agent ที่ไม่แน่ใจว่า alias ใช้ได้จริง มักเล่นปลอดภัยด้วยการเขียน ../../ ให้
  • รายการไฟล์ทั้งสิบ — ยกมาจากผังปลายทางในบทเรียน 05: สี่บรรทัดใน app/ ที่กำกับว่า "(บท 09)" และหกโฟลเดอร์ใน pages/ ที่บทนี้จะสร้างเป็นหน้าเปล่าไว้ก่อน ส่วนเนื้อในของแต่ละหน้าค่อยมาตามบทที่กำกับไว้ในผัง (19, 20, 21, 24, 28) สิ่งที่คุณกำลังทำคือแปลผังที่ตัดสินใจไว้แล้วให้เป็นคำสั่ง ไม่ใช่ให้ AI ออกแบบผังให้ ส่วนคำว่า "ไม่มากไม่น้อยกว่านี้" มีไว้เพราะพฤติกรรมปกติของ Agent คือแถมไฟล์ที่มัน "คิดว่าน่าจะต้องมี" มาให้ด้วย เช่น index.ts ที่ re-export ทุกอย่าง
  • ชื่อ export ที่ระบุเป๊ะ (routes, router, default export) — เพราะบทเรียน 11 จะมาแก้ App.tsx เพื่อครอบ providers และบทเรียน 33 จะ import routes ไปใช้ในเทสต์ ถ้าปล่อยให้ AI ตั้งชื่อเอง คุณจะได้ appRouter บ้าง AppRoutes บ้าง แล้วต้องมาไล่แก้ทีหลัง ด้วยเหตุผลเดียวกันนี้เอง App.tsx ตัวใหม่ต้องอยู่ที่ src/app/ ไม่ใช่ src/ — บทเรียน 02 บอกไว้แล้วว่าไฟล์ placeholder ที่คุณพิมพ์ไว้จะย้ายเข้า src/app/ ในบทนี้ prompt จึงต้องสั่งลบ src/App.tsx เดิมด้วย ไม่ใช่แค่สร้างตัวใหม่ ถ้าลืมบรรทัดนั้น คุณจะจบบทเรียน 09 ด้วย App.tsx สองไฟล์ที่ไม่มีเครื่องมือตัวไหนบ่นให้ฟัง — noUnusedLocals มองไม่เห็นไฟล์ที่ไม่มีใคร import
  • ตาราง path หกบรรทัด — คือหน้าทั้งหกที่บทเรียน 01 สัญญาไว้ เขียนเป็น path จริง ๆ ไม่ใช่ "หน้าสินค้า หน้าตะกร้า ฯลฯ" สังเกต "/products/:id" ที่ระบุชื่อ param เป็น id — บทเรียน 21 จะอ่านค่านี้ด้วย useParams ถ้าตรงนี้กลายเป็น :productId ทุกอย่างหลังจากนั้นเลื่อนตามหมด
  • พฤติกรรมของ RouteErrorFallback — ระบุทั้งสองกรณีและระบุข้อความจริง เพราะ "แสดง error ให้สวย ๆ" คือคำสั่งที่ตรวจไม่ได้ ส่วน "ถ้าไม่ใช่ route error response ให้แสดงข้อความนี้" คือคำสั่งที่คุณเปิดไฟล์แล้วชี้ได้ทันทีว่าทำหรือไม่ทำ
  • บรรทัด import ท้ายส่วนเทคนิค — ขยายกติกาในไฟล์ rules ที่เขียนกว้าง ๆ ว่า "import ข้ามโฟลเดอร์ใช้ alias @/ เสมอ" ให้ชัดขึ้นสำหรับงานนี้ ผลคือ router.tsx จะ import RouteErrorFallback ที่อยู่โฟลเดอร์เดียวกันด้วย ./RouteErrorFallback และ import MainLayout กับหน้าทั้งหกด้วย @/
  • ขอบเขต: สามบรรทัด — บรรทัด "ยังไม่ต้องสร้าง Header, Footer, QueryClientProvider" กันไม่ให้มันทำงานของบทเรียน 10 กับ 11 มาให้ล่วงหน้า (ซึ่งฟังดูเหมือนได้กำไร แต่แปลว่าคุณต้องตรวจโค้ดของสามบทพร้อมกันในรอบเดียว) ส่วนบรรทัด .module.scss น่าสนใจกว่านั้น: ไฟล์ rules บอกว่า component หนึ่งตัวต้องมี .module.scss คู่กัน แต่งานนี้เราไม่ต้องการ — prompt ยกเว้นกติกาเฉพาะงานได้ แต่ต้องเขียนบอกให้ชัด ถ้าเงียบไว้ Agent จะทำตามกติกาในไฟล์ ซึ่งก็ถูกของมัน

สังเกตสิ่งที่ไม่มีใน prompt นี้ด้วย: ไม่มีคำว่า SCSS Modules ไม่มีคำว่าห้ามใช้ any ไม่มีคำอธิบายว่าโปรเจกต์แบ่งเป็นสี่ชั้นอะไรบ้าง ทั้งหมดนั้นอยู่ใน .cursor/rules/project.mdc แล้วจากบทที่แล้ว นี่คือผลตอบแทนของการเขียนไฟล์กติกา — prompt เหลือเฉพาะสิ่งที่เป็นของงานนี้งานเดียว

วงจรตรวจงาน 5 ขั้น

Agent ทำงานเสร็จแล้ว จอเต็มไปด้วยไฟล์ใหม่ และมีปุ่ม Accept รออยู่ ตรงนี้คือจุดที่กดผ่านได้ง่ายที่สุด ส่วนเราจะเดินห้าขั้นนี้ทุกครั้ง เรียกว่าวงจรตรวจงาน และทุกบทหลังจากนี้จะอ้างถึงมันด้วยชื่อนี้:

  1. อ่าน diff ทั้งหมดก่อน — git diff (และ git status เพื่อดูไฟล์ใหม่ที่ยังไม่ถูก track) ไม่ใช่แค่ดูว่าหน้าเว็บขึ้นไหม เปิดหน้าเว็บแล้วเห็นของถูกต้อง แปลว่า "รันผ่าน" ไม่ได้แปลว่า "โค้ดใช้ได้" สิ่งที่ต้องมองหาคือไฟล์ที่คุณไม่ได้สั่งให้แตะ บรรทัดที่ทำเกินจากที่สั่ง และ import ที่หน้าตาแปลก ๆ นี่คือขั้นที่ต้องมี working tree สะอาดก่อนส่ง prompt ถึงจะทำได้จริง
  2. ไล่ checklist ของบทนั้น — กล่อง ✅ ของแต่ละบทเป็นรายการข้อเท็จจริงที่ชี้ในโค้ดได้ ไล่ทีละข้อ อย่ากวาดตาแล้วเหมารวม และทุกกล่อง ✅ จะมีบรรทัดที่ขึ้นต้นว่า AI มักพลาดตรงนี้: ซึ่งบอกจุดพลาดจริงของโค้ดชุดนั้น — อ่านบรรทัดนั้นก่อนเสมอ แล้วไปดูจุดนั้นเป็นจุดแรก มันคือทางลัดที่คุ้มที่สุดในการตรวจงาน
  3. รันเครื่องมือ — npm run lint และ npm run typecheck (สคริปต์ที่ตั้งไว้ตั้งแต่บทเรียน 03 เบื้องหลังคือ tsc -b) สองคำสั่งนี้จับสิ่งที่ตาคนมองข้ามได้เร็วกว่ามาก แต่จำไว้ว่ามันจับได้แค่ปัญหาเชิงกล ไม่ได้จับว่าโค้ดทำถูกเรื่องหรือเปล่า — as unknown as Product ผ่านทั้งสองตัวสบาย ๆ
  4. รันจริงแล้วทำตาม checkpoint — npm run dev แล้วทำตามที่ checkpoint ท้ายบทบอกทีละข้อ กดปุ่มจริง เปลี่ยน URL จริง ไม่ใช่แค่ดูว่าหน้าไม่ขาว
  5. ถามตัวเองว่า "ถ้ามีคนถามว่าบรรทัดนี้ทำอะไร ตอบได้ไหม" — ไล่ดูโค้ดที่เพิ่งได้มาแล้วตอบคำถามนี้กับตัวเองอย่างซื่อสัตย์ ตอบไม่ได้แม้แต่บรรทัดเดียว ให้เปิดโหมด Ask @ ไฟล์นั้นแล้วถามจนเข้าใจก่อนไปบทถัดไป นี่คือกติกาข้อเดียวของคอร์สนี้ในรูปของขั้นตอนที่ทำได้จริง

ห้าขั้นนี้ฟังดูเยอะ แต่พอทำจนคล่องแล้วใช้เวลาไม่ถึงสิบนาทีต่อบท และมันแลกมากับการไม่ต้องมานั่งหาสาเหตุตอนบทเรียน 24 ว่าทำไมตะกร้าคำนวณราคาผิด ทั้งที่ต้นเหตุคือบรรทัดที่คุณกด Accept ผ่านไปตั้งแต่บทเรียน 22

เมื่อครบห้าขั้นและทุกอย่างผ่านแล้ว ค่อย commit — และการ commit นั้นก็คือขั้นเตรียมของ prompt ถัดไปพอดี วงจรจึงต่อกันเป็นวงกลมจริง ๆ

เจอของไม่ตรง แล้วทำอย่างไรต่อ

สมมติขั้นที่หนึ่งหรือสองเจอปัญหา คุณมีทางเลือกสามทาง และการเลือกผิดทางคือเหตุผลหนึ่งที่ทำให้คนใช้เวลากับ AI นานกว่าเขียนเอง:

  • แก้ต่อ — ใช้เมื่อรูปทรงถูกแล้ว รายละเอียดผิด ไฟล์อยู่ถูกที่ โครงถูก แต่ลืม errorElement ไปหนึ่งจุด สั่งต่อในแชทเดิมสั้น ๆ ว่าให้แก้อะไรตรงไหน
  • ถอยแล้วสั่งใหม่ — ใช้เมื่อรูปทรงเองผิด เช่นมันสร้าง route ไว้คนละที่กับที่สั่ง หรือแตกไฟล์ผิดชั้นไปทั้งชุด กรณีนี้ git restore . ลบไฟล์ใหม่ทิ้ง แล้วกลับไปแก้ที่ prompt ไม่ใช่แก้ที่โค้ด เพราะของที่ออกมาผิดรูป แปลว่าคำสั่งขาดข้อมูลไปหนึ่งชิ้น — ไล่หาว่าชิ้นไหน แล้วเติมลงไป
  • เขียนเอง — บางทีของที่เหลือคือโค้ดสิบบรรทัดที่คุณรู้อยู่แล้วว่าต้องเป็นอะไร การพิมพ์เองเร็วกว่าและแม่นกว่าการอธิบายให้เครื่องเข้าใจ ทางเลือกนี้ไม่ใช่การยอมแพ้

กับดักที่เจอบ่อยที่สุดคือใช้ "แก้ต่อ" กับปัญหาที่ควรใช้ "ถอยแล้วสั่งใหม่" — ไล่แก้รูปทรงที่ผิดด้วยคำสั่งต่อ ๆ กันไปทีละจุด นี่คือวิธีที่ไฟล์ 20 บรรทัดกลายเป็น 200 บรรทัดที่ไม่มีใครอธิบายได้ว่าทำไมต้องมีบรรทัดไหนบ้าง สัญญาณเตือนง่าย ๆ: ถ้าสั่งแก้ไปสองรอบแล้วยังไม่เข้าที่ ให้ถอย

เรื่องนี้ยังมีรายละเอียดอีกมาก โดยเฉพาะกรณีที่ยากที่สุดคือโค้ดที่รันผ่านแต่ผิด ซึ่งอ่านผ่าน ๆ แล้วดูดีทุกบรรทัด บทเรียน 29 ทั้งบทมีไว้เพื่อการนี้ — เราจะเอาโค้ดจริงที่ AI เขียนผิดมาแกะกันทีละกรณี ตอนนี้จำสามทางเลือกไว้ก่อนพอ

บทที่ห้าม AI

อีกเรื่องที่จะเจอตั้งแต่บทหน้าเป็นต้นไป: บางบทจะมีกล่อง ✍️ ที่บอกว่าโค้ดชุดนั้นห้ามให้ AI เขียน ให้คุณพิมพ์เองทั้งหมด มีสิบจุดตลอดคอร์ส และไม่ได้เลือกมามั่ว ๆ ทุกจุดคือโค้ดที่ "อ่านแล้วเข้าใจ" ไม่พอ ต้องผ่านมือถึงจะใช้เป็น เช่น cartReducer, query key factory ของสินค้า, zod schema ของ checkout และเทสต์ตัวแรกของแต่ละชนิด

ทุกกล่อง ✍️ จะบอกเหตุผลไว้หนึ่งบรรทัดว่าทำไมจุดนั้นถึงต้องเป็นคุณ — อ่านบรรทัดนั้นก่อนเริ่มพิมพ์ มันไม่ใช่การลงโทษ และไม่ใช่ความเชื่อว่าพิมพ์เองแล้วโค้ดดีกว่า มันคือจุดที่ถ้าคุณข้ามไป คุณจะตรวจงานของ AI ในบทถัด ๆ ไปไม่เป็น เพราะไม่มีมาตรฐานในหัวไว้เทียบ

จบสามบทของช่วงนี้แล้ว: เครื่องมือติดตั้งแล้ว กติกาโปรเจกต์อยู่ในไฟล์แล้ว และคุณมีทั้งโครง prompt กับวงจรตรวจงานอยู่ในมือ บทหน้าคือของจริงบทแรก — เราจะส่ง prompt ที่คุณเพิ่งอ่านทั้งอันนั้นให้ Agent แล้วเดินวงจรตรวจงานครบทั้งห้าขั้นด้วยกันรอบหนึ่ง

💡 Checkpoint: บทนี้ไม่มีโค้ดให้รัน ตัวชี้วัดคือคุณต้องท่องได้โดยไม่ต้องเปิดหน้านี้: prompt มีสี่ส่วนอะไรบ้างและเรียงอย่างไร (บริบท: / โครงสร้าง: / ข้อกำหนดทางเทคนิค: / ขอบเขต:), วงจรตรวจงานมีห้าขั้นอะไรบ้าง และขั้นไหนที่ต้อง commit ก่อนถึงจะทำได้ ถ้ายังไม่แน่ ให้อ่านซ้ำหัวข้อที่ตอบไม่ได้ก่อนเปิดบทเรียน 09 — สองอย่างนี้จะวนซ้ำอีก 27 บท การกลับมาเปิดดูทุกครั้งจะช้ากว่าการจำให้ได้ตั้งแต่ตอนนี้มาก
