การทดสอบ Hooks และ Queries

Hook Tests

ชั้นถัดไปของพีระมิด: hook ปัญหาแรกที่เจอทันทีคือกฎเหล็กของ React — hook เรียกได้เฉพาะข้างใน component เท่านั้น เราจะเรียก useQuery(...) ตรง ๆ ในไฟล์เทสต์ไม่ได้ ทางออกคือ renderHook จาก React Testing Library: มันสร้าง component จิ๋ว ๆ ที่มองไม่เห็นขึ้นมาหนึ่งตัว เรียก hook ของเราข้างในนั้น แล้วส่งผลลัพธ์ล่าสุดออกมาให้เราทาง result.current — อ่านค่าได้ทุกเมื่อ และมันอัปเดตเองทุกครั้งที่ hook re-render

ปัญหาที่สอง: hook ของเราไม่ได้ลอยอยู่เดี่ยว ๆ — useQuery ต้องการ QueryClientProvider, useCart ต้องการ CartProvider, useNavigate ต้องการ router ดังนั้นหัวใจของบทนี้คือการประกอบ wrapper ที่จัด provider ให้ครบเท่าที่ hook แต่ละตัวต้องใช้ — ไม่มากกว่านั้น ไม่น้อยกว่านั้น

และของใหม่ที่มากับชั้นนี้คือ เวลา unit test ในบทที่แล้วรับ input แล้วได้ output ทันทีในบรรทัดเดียว ส่วนบทนี้ทุกอย่างเป็น async: เรียก hook แล้วยังไม่มีข้อมูล ต้องรอ พอมีเวลาเข้ามาในสมการ คำถามที่บทที่แล้วถามว่า "assertion นี้แดงได้ไหม" จะมีรูปใหม่ที่ยากขึ้นหนึ่งชั้น — assertion นี้ทำงานตอนไหน เพราะเทสต์ async ที่ assert เร็วเกินไปคือเทสต์ที่ผ่านโดยไม่ได้ดูของจริงเลยสักครั้ง นั่นคือจุดที่กล่อง ✅ ของบทนี้จะเน้นทั้งกล่อง

✅ ตรวจโค้ดที่ AI สร้าง

✅ ตรวจโค้ดที่ AI สร้าง — git status และ git diff ก่อน แล้วไล่ทีละข้อ ข้อแรกเป็นข้อที่ต้องดูก่อนข้ออื่นทั้งหมด และเป็นข้อที่ต่อยอดจากกติกาของบทที่แล้วโดยตรง:

  • AI มักพลาดตรงนี้: assert สถานะ loading แล้วจบ โดยไม่เคยรอข้อมูลจริง — ก้อนที่ต้องระวังหน้าตาแบบนี้: const { result } = renderHook(...); expect(result.current.isLoading).toBe(true); จบเทสต์ตรงนั้น มันผ่านทันทีทุกครั้ง เร็วมาก ไม่เคยแดง — แต่สิ่งที่มันพิสูจน์คือ "TanStack Query คืน isLoading: true ตอน render แรก" ซึ่งเป็นพฤติกรรมของไลบรารี ไม่ใช่ของโค้ดเรา ต่อให้ queryFn ชี้ไป URL ที่ไม่มีอยู่จริง ต่อให้ queryKey สะกดผิด ต่อให้ MSW ไม่ได้สตาร์ท เทสต์นี้ก็ยังเขียว มีอีกรูปหนึ่งที่แนบเนียนกว่าและต้องดูให้ออก: await waitFor(() => expect(result.current.isLoading).toBe(false)) — คราวนี้มีการรอจริง แต่รอผิดสัญญาณ เพราะ isLoading กลายเป็น false ทั้งตอนสำเร็จและตอนล้มเหลว เท่ากับประตูนี้เปิดให้ query ที่พังผ่านเข้ามาได้ด้วย สิ่งที่ต้องรอคือ isSuccess === true ซึ่งเป็น true ทางเดียวเท่านั้น ญาติสุดท้ายของตระกูลนี้คือการลืม await หน้า waitFor ซึ่งโชคดีที่ดัง (assertion บรรทัดถัดไปจะเจอ undefined) แต่จะทิ้ง unhandled rejection ไว้ในรายงานให้งงเล่น วิธีตรวจสองคำสั่ง: grep -n "isLoading\|isPending\|isFetching" src/features/products/queries.test.tsx ต้องว่างเปล่า และ grep -c "await waitFor" src/features/products/queries.test.tsx ต้องได้ 4 คือหนึ่งบรรทัดต่อหนึ่ง it พอดี
  • ทำให้มันแดงด้วยมือ — กติกาเดิมจากบทที่ 31 ใช้ต่อได้ทั้งดุ้น สามคู่ที่ต้องทำในบทนี้ แก้ไฟล์ต้นทาง รันเทสต์ ดูให้เห็นแดง แล้ว git restore:
    • src/features/products/api.ts — ในฟังก์ชันที่ดึงสินค้าตามหมวด ลบการส่ง skip ออกจาก params → "byCategory fetches products for a category and page" ต้องแดงที่บรรทัด expect(result.current.data?.skip).toBe(20) ด้วยข้อความ expected +0 to be 20 — และเพราะ it หยุดที่ assertion แรกที่พัง คุณจะยังไม่เห็นบรรทัด beauty product 21 แดง ถ้าอยากเห็นมันแดงด้วย ให้คอมเมนต์บรรทัด skip ออกแล้วรันซ้ำ จะเห็นบรรทัดที่สองแดงแทน — ข้อนี้เป็นนิสัยของ test runner ที่ต้องรู้ไว้ตั้งแต่ตอนนี้ เพราะมันแปลว่าจำนวนบรรทัดที่แดง ไม่ได้บอกจำนวนสิ่งที่พัง
    • src/features/checkout/useCheckout.ts — ย้าย clearCart() ออกจาก onSuccess ไปไว้ในตัว onPlaceOrder ก่อนเรียก placeOrderMutate() → เทสต์ "errors and keeps the cart when no address is set" ต้องแดง นี่คือบั๊กเดียวกับที่บทเรียน 28 และตระกูล 3 ของบทเรียน 29 อธิบายไว้ว่ามองไม่เห็นในเครื่องตัวเองเพราะ dummyjson ตอบ 200 เสมอ — วันนี้มันมีเครื่องมือตะโกนบอกแล้ว และนั่นคือทั้งหมดที่บทเรียน 29 สัญญาว่าสี่บทนี้จะทำให้

src/features/products/queries.test.tsx

productQueries จากบทเรียน 17 คือประตูสู่ข้อมูลสินค้าทั้งหมดของแอป เทสต์ชุดนี้จะพิสูจน์ว่าทั้งสี่ query ประกอบ queryKey/queryFn ถูก, เรียก API ถูกเส้นทาง และส่ง parameter ครบทั้งสาย (สังเกตนามสกุล .tsx — ไฟล์เทสต์ฝั่ง React ของโปรเจกต์นี้ใช้ .tsx ทั้งหมด):

import { renderHook, waitFor } from "@testing-library/react";
import { useQuery } from "@tanstack/react-query";
import { productQueries } from "./queries";
import { createQueryWrapper } from "@/test/utils";

describe("productQueries", () => {
  it("list fetches products with the given limit", async () => {
    const { result } = renderHook(
      () => useQuery(productQueries.list({ limit: 5 })),
      { wrapper: createQueryWrapper() },
    );

    await waitFor(() => expect(result.current.isSuccess).toBe(true));
    expect(result.current.data?.products).toHaveLength(5);
  });

  it("byCategory fetches products for a category and page", async () => {
    const { result } = renderHook(
      () =>
        useQuery(
          productQueries.byCategory({ category: "beauty", page: 2, limit: 20 }),
        ),
      { wrapper: createQueryWrapper() },
    );

    await waitFor(() => expect(result.current.isSuccess).toBe(true));
    expect(result.current.data?.skip).toBe(20);
    expect(result.current.data?.products[0]?.title).toBe("beauty product 21");
  });

  it("categories fetches the category list", async () => {
    const { result } = renderHook(() => useQuery(productQueries.categories()), {
      wrapper: createQueryWrapper(),
    });

    await waitFor(() => expect(result.current.isSuccess).toBe(true));
    expect(result.current.data?.map((c) => c.slug)).toEqual([
      "beauty",
      "fragrances",
      "furniture",
    ]);
  });

  it("detail fetches a single product", async () => {
    const { result } = renderHook(() => useQuery(productQueries.detail(7)), {
      wrapper: createQueryWrapper(),
    });

    await waitFor(() => expect(result.current.isSuccess).toBe(true));
    expect(result.current.data?.id).toBe(7);
  });
});

โครงของทุกเทสต์เหมือนกันเป๊ะ — เรียก renderHook พร้อม wrapper, รอให้ query สำเร็จ, แล้ว assert ข้อมูล มาแกะทีละชิ้น:

  • renderHook(() => useQuery(...), { wrapper }) — argument แรกคือฟังก์ชันที่เรียก hook (จะถูกรันข้างใน component จิ๋วที่ว่า) ส่วน wrapper คือ component ที่จะห่อรอบมัน — เราส่ง createQueryWrapper() ที่สร้างไว้ในบทเรียน 30 ซึ่งก็คือ QueryClientProvider ดี ๆ นี่เอง
  • ทำไมต้อง QueryClient ใหม่ทุกเทสต์? — สังเกตว่าเราเรียก createQueryWrapper() ใหม่ในทุก it ไม่ได้สร้างครั้งเดียวแชร์กัน เหตุผล: QueryClient คือที่อยู่ของ cache ถ้าแชร์กัน เทสต์ detail(7) ที่รันทีหลังอาจได้ข้อมูลจาก cache ของเทสต์ก่อนหน้าแบบทันทีโดยไม่ยิง request เลย — เทสต์จะ "ผ่าน" หรือ "พัง" ด้วยเหตุผลผิด ๆ ตามลำดับการรัน ซึ่งเป็นเทสต์ประเภทอันตรายที่สุด: flaky test ที่ผลเปลี่ยนไปมา cache สดใหม่ทุกเทสต์ = ทุกเทสต์เป็นอิสระต่อกัน 100% (แถม retry: false ที่ตั้งไว้ใน createTestQueryClient ยังทำให้กรณี fail ไม่ต้องรอ retry ให้เสียเวลา)
  • waitFor — query เป็นงาน async: ตอน renderHook จบใหม่ ๆ result.current.isLoading ยังเป็น true อยู่ waitFor จะรัน callback ซ้ำ ๆ จนกว่า assertion ข้างในจะไม่โยน error (หรือครบ timeout ~1 วินาทีแล้วยอมแพ้) — อย่าลืม await เด็ดขาด ไม่งั้นเทสต์จะวิ่งเลยไป assert ข้อมูลทั้งที่ยังโหลดไม่เสร็จ
  • ทำไมต้องรอ isSuccess ไม่ใช่ !isLoading — สองอย่างนี้ต่างกันตรงกรณีที่ query พัง: เมื่อ request ล้มเหลว isLoading จะกลายเป็น false เหมือนกับตอนสำเร็จทุกประการ ส่วน isSuccess เป็น true ทางเดียวเท่านั้น การเลือกสัญญาณจึงเป็นการเลือกว่าเทสต์นี้รับประกัน "query หยุดทำงานแล้ว" หรือ "query สำเร็จแล้ว" — คนละเรื่องกันคนละขั้ว และเป็นเส้นแบ่งที่ตาคุณต้องหยุดทุกครั้งที่เห็น waitFor ในโค้ดที่ AI เขียน
  • assertion แต่ละตัวพิสูจน์คนละเรื่อง — list({ limit: 5 }) ได้ 5 ชิ้นพอดี แปลว่า limit เดินทางจาก parameter → api.ts → query string → MSW ครบสาย ส่วน byCategory({ page: 2, limit: 20 }) เด็ดกว่านั้น: skip ต้องเป็น 20 และสินค้าตัวแรกต้องชื่อ beauty product 21 — ชื่อนี้ handler ประกอบขึ้นจาก slug + ลำดับที่คำนวณจาก skip (บทเรียน 30) ดังนั้นถ้าเห็นชื่อนี้ แปลว่าทั้งชื่อ category และการคำนวณหน้า 2 → skip 20 ของ calculateOffset ทำงานถูกต้องจริงในบริบทจริง ไม่ใช่แค่ใน unit test

src/features/checkout/useCheckout.test.tsx

useCheckout จากบทเรียน 28 คือ hook ที่ยุ่งที่สุดของแอป: มันใช้ useCart (ต้องการ CartProvider), useMutation (ต้องการ QueryClientProvider) และ useProductRoute ซึ่งข้างในคือ useNavigate (ต้องการ router) เทสต์มันจึงต้องประกอบ provider ครบสามชั้น:

import { ReactNode } from "react";
import { act, renderHook, waitFor } from "@testing-library/react";
import { QueryClientProvider } from "@tanstack/react-query";
import { MemoryRouter } from "react-router";
import useCheckout from "./useCheckout";
import { CartProvider } from "@/features/cart/store/CartProvider";
import { CART_STORAGE_KEY } from "@/features/cart/store/cartStorage";
import { useCart } from "@/features/cart/useCart";
import { createTestQueryClient } from "@/test/utils";

function wrapper({ children }: { children: ReactNode }) {
  return (
    <MemoryRouter initialEntries={["/checkout"]}>
      <QueryClientProvider client={createTestQueryClient()}>
        <CartProvider>{children}</CartProvider>
      </QueryClientProvider>
    </MemoryRouter>
  );
}

describe("useCheckout", () => {
  it("clears the cart after a successful order", async () => {
    localStorage.setItem(
      CART_STORAGE_KEY,
      JSON.stringify({
        items: [
          { id: 1, title: "Widget", price: 10, quantity: 2, image: "/w.png" },
        ],
      }),
    );

    const { result } = renderHook(
      () => ({ checkout: useCheckout(), cart: useCart() }),
      { wrapper },
    );

    expect(result.current.cart.cart.items).toHaveLength(1);
    expect(result.current.checkout.billingSummary.subtotal).toBe(20);

    act(() => {
      result.current.checkout.storeCheckoutAddress({
        address: "1 Main St",
        email: "jane@example.com",
        phone: "0812345678",
      });
    });

    act(() => {
      result.current.checkout.onPlaceOrder();
    });

    await waitFor(() => expect(result.current.cart.cart.items).toHaveLength(0));
  });

  it("errors and keeps the cart when no address is set", async () => {
    localStorage.setItem(
      CART_STORAGE_KEY,
      JSON.stringify({
        items: [
          { id: 1, title: "Widget", price: 10, quantity: 2, image: "/w.png" },
        ],
      }),
    );

    const { result } = renderHook(
      () => ({ checkout: useCheckout(), cart: useCart() }),
      { wrapper },
    );

    act(() => {
      result.current.checkout.onPlaceOrder();
    });

    await waitFor(() =>
      expect(result.current.checkout.isPlaceOrderLoading).toBe(false),
    );
    expect(result.current.cart.cart.items).toHaveLength(1);
  });
});

ไฟล์นี้มีเทคนิคใหม่หลายตัว ไล่ตามลำดับที่เจอ:

  • wrapper เขียนเองเต็ม ๆ — คราวนี้ createQueryWrapper() ไม่พอ เราประกาศ component wrapper ที่ซ้อนสามชั้น: MemoryRouter คือ router ที่เก็บ history ในหน่วยความจำ (แบบเบาของ createMemoryRouter — พอสำหรับกรณีที่ hook แค่เรียก navigate โดยไม่ต้อง render route ปลายทาง) ตามด้วย QueryClientProvider และ CartProvider ตัวจริงจากแอป — เราไม่ mock cart เลย เพราะพฤติกรรมที่อยากพิสูจน์คือ "checkout สั่ง cart ให้ล้างจริงไหม" ซึ่งต้องใช้ของจริงถึงจะพิสูจน์ได้
  • สังเกตว่า navigation ก็ไม่ได้ mock — goToOrderSuccess() จะ navigate จริง ๆ ใน MemoryRouter แค่ไม่มีหน้าไหน render ออกมาให้ดู เทสต์นี้เลือก assert ผ่านตะกร้าแทน (การ assert ตัว URL ปลายทางเป็นหน้าที่ของ integration test บทหน้า)
  • เตรียมตะกร้าผ่าน localStorage — เราเขียนตะกร้า (Widget ราคา 10 จำนวน 2) ลง CART_STORAGE_KEY ก่อน renderHook พอ CartProvider mount มันจะ lazy init จาก loadCartState() แล้วเจอของที่เราวางไว้ — ได้เทสต์ที่เดินผ่านโค้ด persistence จริงอีกรอบ ฟรี ๆ (และไม่ต้องเก็บกวาด เพราะ afterEach ใน setup ล้าง localStorage ให้แล้ว) นี่คือกลไกเดียวกับที่ useReducer แบบสามอาร์กิวเมนต์ในบทเรียน 22 ทำให้เป็นไปได้ — ถ้าตอนนั้นเขียนเป็นสองอาร์กิวเมนต์ กลไกนี้ก็ยังทำงาน แต่จะทำงานซ้ำทุก render
  • เรียกสอง hook ในครั้งเดียว — callback ของ renderHook คืน object { checkout: useCheckout(), cart: useCart() } สอง hook นี้จึงรันใน component เดียวกัน ใต้ CartProvider ตัวเดียวกัน — cart กลายเป็น "หน้าต่าง" ให้เราแอบดู state ของตะกร้าจากข้างนอก ระหว่างที่ checkout คือตัวที่เราสั่งงาน (นั่นคือที่มาของ result.current.cart.cart.items ที่อ่านแล้วสะดุดตา — cart ตัวแรกคือ key ที่เราตั้งเอง ตัวที่สองคือ field ที่ useCart คืนมา)
  • act(...) — ทุกครั้งที่เราเรียกฟังก์ชันที่ทำให้ state เปลี่ยน (เช่น storeCheckoutAddress ที่ setState ข้างใน) ต้องห่อด้วย act เพื่อบอก React ว่า "ประมวลผล update ให้จบก่อน แล้วค่อยให้เทสต์ไปต่อ" — ไม่งั้นจะเจอ warning และ result.current อาจยังเป็นค่าเก่า และเหตุผลที่ต้องเป็น act สองก้อนคือ onPlaceOrder ต้องอ่าน checkoutAddress ที่ก้อนแรกเพิ่งเซ็ตไป ถ้ารวมเป็นก้อนเดียว state ยังไม่ทันถูก commit
  • เส้นทางของเทสต์แรก (happy path) — assert ค่าตั้งต้นก่อน (ตะกร้ามี 1 รายการ, billingSummary.subtotal = 10 × 2 = 20 — ได้เทสต์ logic ใน useMemo แถมมาด้วย) จากนั้นบันทึกที่อยู่ → กดสั่งซื้อ → placeOrder ยิง POST /carts/add ซึ่ง MSW ตอบ 201 → onSuccess ของ mutation รัน clearCart() — เราพิสูจน์ทั้งหมดนั้นด้วย waitFor บรรทัดเดียว: รอจนตะกร้าว่าง
  • เส้นทางของเทสต์ที่สอง (error path) — กดสั่งซื้อโดยไม่บันทึกที่อยู่ mutationFn จะ throw new Error("Delivery Address is Missing") ทันที mutation กลายเป็นสถานะ error, onSuccess ไม่รัน เรารอให้ isPlaceOrderLoading กลับเป็น false แล้ว assert ว่าตะกร้ายังอยู่ครบ — เทสต์ error path แบบนี้สำคัญไม่แพ้ happy path: ผู้ใช้ต้องไม่เสียตะกร้าเพราะการสั่งซื้อที่ล้มเหลว
💡 ของที่ควรถูกทักในรีวิว — สองข้อ และข้อแรกอยู่ในบรรทัดที่กล่อง ✅ ข้างบนเพิ่งสั่งห้ามไปหมาด ๆ: เทสต์ที่สองของ useCheckout.test.tsx รอด้วย await waitFor(() => expect(result.current.checkout.isPlaceOrderLoading).toBe(false)) ซึ่งเป็นสัญญาณที่เป็น false อยู่แล้วตั้งแต่ก่อนเริ่ม — isPlaceOrderLoading คือ isPending ของ mutation ที่เริ่มต้นเป็น false ขึ้นเป็น true ชั่วขณะ แล้วกลับมาเป็น false ดังนั้น waitFor ก้อนนี้อาจผ่านตั้งแต่รอบ poll แรกโดยที่ mutation ยังไม่ได้ล้มเหลวด้วยซ้ำ พูดให้ตรงคือ เทสต์นี้ไม่ได้ยืนยันเลยว่า mutation พังจริง มันยืนยันแค่ว่า "ตอนนี้ไม่ได้กำลังโหลด" แล้วเช็คว่าตะกร้ายังมีของ ซึ่งเป็นเงื่อนไขที่จะผ่านเหมือนกันเป๊ะถ้า onPlaceOrder ไม่ทำอะไรเลยสักอย่าง สาเหตุที่มันเขียนแบบนี้ก็เพราะไม่มีสัญญาณที่ถูกต้องให้รอ: useCheckout return isPlaceOrderLoading ออกมาตัวเดียว ไม่ได้ return isPlaceOrderError หรือ error เลย — เทสต์จึงถูกจำกัดด้วยรูปร่างของ public API ที่บทเรียน 28 ออกแบบไว้ ในรีวิวจริงข้อนี้ควรถูกทักที่ hook ไม่ใช่ที่เทสต์: เพิ่ม isPlaceOrderError เข้าไปใน return แล้วให้เทสต์รอ toBe(true) ซึ่งเป็นสัญญาณทางเดียว วิธีพิสูจน์ว่าปัญหานี้มีจริงใช้เวลาสามสิบวินาที: แก้ onPlaceOrder ใน useCheckout.ts ให้เป็นฟังก์ชันว่าง (ลบบรรทัด placeOrderMutate(); ทิ้ง) แล้วรันไฟล์นี้ไฟล์เดียว — เทสต์ตัวที่สองจะยังเขียว ทั้งที่โค้ดไม่ได้ทำอะไรเลย (ส่วนตัวแรกจะแดง ซึ่งเป็นคนละเรื่อง — มันแดงเพราะตะกร้าไม่ถูกล้าง ไม่ใช่เพราะมันตรวจจับ error ได้) ข้อสอง อยู่ใน queries.test.tsx: ไม่มีเทสต์ตัวไหน assert queryKey เลยแม้แต่ตัวเดียว ทั้งสี่เทสต์ดูแต่ ข้อมูลที่ได้กลับมา ซึ่งไม่เปลี่ยนเลยไม่ว่า key จะสะกดอย่างไร แปลว่า productKeys — ไฟล์ที่บทเรียน 17 บังคับให้พิมพ์เองด้วยเหตุผลว่า "key ผิดคือบั๊กที่ไม่มีเครื่องมือไหนจับได้" — ยังคงไม่มีเครื่องมือไหนจับได้อยู่ดีหลังจบบทนี้ ในตระกูลเดียวกัน placeholderData: keepPreviousData ในจาน byCategory ก็ไม่มีเทสต์ตัวไหนแตะ ทั้งที่บทเรียน 29 ยกมันเป็นตัวอย่างเปิดของบั๊กเงียบทั้งบท ทางแก้คือเทสต์เพิ่มหนึ่งตัวที่ assert productKeys.byCategory({...}) ตรง ๆ ว่าได้ array หน้าตาแบบไหน ซึ่งเป็น unit test ธรรมดาที่ไม่ต้อง render อะไรเลยด้วยซ้ำ — เราไม่เพิ่มเพราะยึดตามต้นฉบับ แต่ต้องรู้ว่าตอนนี้ตาข่ายมีรูตรงไหน

อ่าน error ของเทสต์ async ให้เป็น

เทสต์ async พังแล้วอ่านยากกว่า unit test เยอะ เพราะสิ่งที่รายงานมักเป็นปลายเหตุ สี่อาการที่จะเจอบ่อยและวิธีไล่:

  • waitFor timeout — ข้อความจะเป็น assertion ล่าสุดที่ยังไม่ผ่าน เช่น expected true, received false ของ isSuccess อย่าเพิ่งงมที่ assertion — ถามก่อนว่า "ทำไม query ไม่สำเร็จ?" ลอง log result.current.error ดู มักเจอคำตอบทันที (URL ผิด, handler ไม่ match, provider ไม่ครบ)
  • MSW ฟ้อง unhandled request — เพราะเราตั้ง onUnhandledRequest: "error" ไว้ ถ้า request หลุดไปโดยไม่มี handler จะเห็นข้อความบอก method + URL เต็ม ๆ เอา URL นั้นไปเทียบกับ handlers.ts ทีละตัวอักษร — เกือบทุกครั้งคือ path สะกดผิด, ลืมสร้าง handler หรือ VITE_API_BASE_URL ไม่ตรง
  • warning "not wrapped in act(...)" — แปลว่ามี state update เกิดขึ้นนอก act/waitFor มักเพราะเรียกฟังก์ชันของ hook ตรง ๆ โดยไม่ห่อ act หรือเทสต์จบก่อนที่งาน async จะเสร็จ
  • เทสต์ผ่านบ้างพังบ้าง (flaky) — เกือบทั้งหมดมาจากการลืม await หน้า waitFor (เทสต์วิ่งจบก่อนงานเสร็จ) หรือ state ที่รั่วข้ามเทสต์ เช่น แชร์ QueryClient หรือลืมว่ามีอะไรค้างใน localStorage — ถ้าเจอ ให้รันเทสต์ไฟล์นั้นเดี่ยว ๆ เทียบกับรันทั้งชุด ผลต่างกันเมื่อไหร่ แปลว่ามี state รั่วแน่นอน

สังเกตว่าสามในสี่ข้อนี้เป็นอาการที่ดัง ตามนิยามของบทเรียน 29 — เทสต์แดง มีข้อความ มีเลขบรรทัด ข้อที่ต้องระวังจริง ๆ คือสิ่งที่ไม่อยู่ในรายการนี้เลย: เทสต์ async ที่เขียวเพราะมันไม่เคยรออะไร ซึ่งไม่มีอาการ ไม่มีข้อความ และไม่มีวันปรากฏในรายงาน — จับได้ทางเดียวคือการอ่านว่าแต่ละ waitFor รอสัญญาณอะไร
