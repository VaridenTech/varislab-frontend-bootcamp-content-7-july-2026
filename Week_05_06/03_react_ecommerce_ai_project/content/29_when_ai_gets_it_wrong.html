เมื่อ AI เขียนผิด

When the AI Gets It Wrong

ยี่สิบบทที่ผ่านมา ทุกกล่อง ตรวจโค้ดที่ AI สร้าง จบด้วยบรรทัดเดียวกันเสมอ: AI มักพลาดตรงนี้: ตอนอ่านทีละบท มันเป็นแค่คำเตือนประจำบท — เปิดไฟล์นั้น ดูจุดนั้น ผ่านแล้วไปต่อ บทนี้เราเอาทั้งยี่สิบบรรทัดมากองรวมกันแล้วถามคำถามที่ตอบได้เฉพาะตอนมองพร้อมกันทั้งกอง: มันซ้ำกันตรงไหน

คำตอบคือมันไม่ได้กระจัดกระจายอย่างที่เห็นตอนเจอทีละตัว จุดพลาดทั้งหมดในโปรเจกต์นี้ลงเอยที่หกตระกูล และแต่ละตระกูลมีวิธีจับกับวิธีรับมือของตัวเองที่ใช้ซ้ำได้กับทุกตัวในตระกูลนั้น ที่สำคัญกว่านั้นคือมันแบ่งได้อีกแกนหนึ่งซึ่งเป็นแกนที่ตัดสินว่าคุณจะเสียเวลากับมันมากแค่ไหน: บั๊กที่เครื่องมือจับได้ กับ บั๊กที่มีแต่คนจับได้

บทนี้ไม่มี prompt ให้ส่งและไม่มีไฟล์ให้สร้าง ของที่จะได้กลับไปคือสามอย่าง: ตารางอาการที่เปิดกลับมาดูได้เวลาเจอของแปลก ๆ, เกณฑ์ตัดสินว่าจะแก้ต่อ ถอย หรือพิมพ์เอง และสัญญาณสามข้อที่บอกว่าคุณกำลังจะกด Accept ของที่ไม่ควรกด

เส้นแบ่งที่ต้องขีดก่อนอย่างอื่น: ดัง กับ เงียบ

บั๊กดัง คือบั๊กที่มีเครื่องมือตะโกนบอกคุณ — npm run typecheck ตก, npm run lint แดง, หรือหน้าเว็บขาวทั้งหน้า บั๊กประเภทนี้ไม่น่ากลัวเลยแม้จะดูน่าตกใจ เพราะมันบอกชื่อไฟล์ บอกเลขบรรทัด และบอกว่าต้องแก้อะไรมาให้พร้อม เวลาที่เสียไปกับมันคือหน่วยนาที

บั๊กเงียบ คือบั๊กที่ lint ผ่าน typecheck ผ่าน หน้าเว็บขึ้นสวยงาม และคุณกด Accept ไปด้วยความสบายใจ มันจะไปโผล่ในอีกห้าบทข้างหน้า หรือไม่ก็ไปโผล่กับผู้ใช้ที่เน็ตหลุดกลางคัน เวลาที่เสียไปกับมันคือหน่วยชั่วโมง เพราะตอนที่อาการปรากฏ คุณจะไม่มีทางเดาได้เลยว่าต้นเหตุอยู่ที่บรรทัดที่คุณอนุมัติผ่านไปเมื่อสัปดาห์ที่แล้ว

ตัวอย่างที่ชัดที่สุดของเส้นแบ่งนี้อยู่ในไฟล์เดียวกัน บรรทัดเดียวกัน ที่คุณเขียนเองไปแล้วในบทเรียน 17 — จาน byCategory ของ query factory เริ่มจากแบบที่ผิดแล้วดังก่อน:

// ผิดแบบดัง — เขียน option ของ TanStack Query v4 ที่ v5 ถอดออกไปแล้ว
byCategory: (params: CategoryProductsParams) =>
  queryOptions({
    queryKey: productKeys.byCategory(params),
    queryFn: () => getProductsByCategory(params),
    keepPreviousData: true,
  }),

คุณไม่มีวันพลาดตัวนี้ เพราะ npm run typecheck จะพ่นข้อความนี้ใส่หน้าทันที:

error TS2769: No overload matches this call.
  Object literal may only specify known properties, and 'keepPreviousData'
  does not exist in type 'UndefinedInitialDataOptions<...>'.

เหตุผลที่มันดังคือ queryOptions รับ object literal ตรง ๆ TypeScript จึงตรวจ excess property ให้ครบทุก overload ทีนี้ดูตัวที่เงียบ — จุดพลาดในเรื่องเดียวกันเป๊ะ ต่างกันแค่มันไม่ได้เขียนอะไรผิด มันแค่ไม่เขียน:

// ผิดแบบเงียบ — ไม่มี property แปลกปลอมให้ compiler ตรวจ เพราะไม่มีบรรทัดนั้นเลย
byCategory: (params: CategoryProductsParams) =>
  queryOptions({
    queryKey: productKeys.byCategory(params),
    queryFn: () => getProductsByCategory(params),
  }),

ก้อนนี้ lint ผ่าน typecheck ผ่าน และในวันที่คุณเขียนมันเสร็จก็ยังไม่มีหน้าไหนเรียกใช้ให้เห็นผลด้วยซ้ำ อาการของมันไปโผล่ตอนบทเรียน 20 ในรูปของกริดสินค้าทั้งกริดที่หายวับกลายเป็น spinner ทุกครั้งที่ผู้ใช้กดเปลี่ยนหน้า ของที่ถูกคือบรรทัดนี้:

import { keepPreviousData, queryOptions } from "@tanstack/react-query";

// ...

byCategory: (params: CategoryProductsParams) =>
  queryOptions({
    queryKey: productKeys.byCategory(params),
    queryFn: () => getProductsByCategory(params),
    placeholderData: keepPreviousData,
  }),

สองอาการนี้มาจากความเข้าใจผิดเรื่องเดียวกัน อยู่ในไฟล์เดียวกัน และตัวหนึ่งกินเวลาคุณสามสิบวินาที ส่วนอีกตัวรอดไปได้สามบทเรียน นั่นคือเหตุผลที่แกนดัง/เงียบสำคัญกว่าการจำรายชื่ออาการ: เครื่องมือดูแลฝั่งดังให้คุณหมดแล้ว งานที่เหลือของคุณคือฝั่งเงียบทั้งหมด และตารางหกตระกูลข้างล่างนี้ ส่วนใหญ่ของมันอยู่ฝั่งเงียบ

หกตระกูลของความผิด

ทุกแถวในตารางต่อจากนี้มาจากบรรทัด AI มักพลาดตรงนี้: ของบทใดบทหนึ่งใน 09–28 ไม่มีข้อไหนที่คิดขึ้นมาใหม่ ตัวเลขในวงเล็บคือเลขบทที่เจอมันครั้งแรก เปิดกลับไปอ่านบรรทัดเต็มของบทนั้นได้เสมอ

ตระกูล 1 — เดาความจริงที่มันมองไม่เห็น

Agent อ่านโค้ดในโปรเจกต์ได้ แต่มันไม่เคยเห็น JSON ที่ API ส่งกลับมาจริง ไม่เคยเห็นหน้าเว็บที่ render ออกมา และไม่ได้เปิดไฟล์ SCSS ทุกไฟล์มาไล่ดูว่ามี class ชื่ออะไรบ้าง ทุกอย่างที่มันมองไม่เห็น มันจะเดา และมันเดาด้วยชื่อที่ "ฟังดูสมเหตุสมผล" ซึ่งเป็นการเดาที่แนบเนียนที่สุด เพราะโค้ดที่ได้อ่านแล้วดูถูกทุกบรรทัด

สมมติฐานเรื่องสเกลข้อมูล — StarReview และ RatingBreakdown หารคะแนนด้วยสองเพราะเชื่อว่าเป็นสเกล 0–10 (14, 21) comment // Score between 0 and 10 ในบทเรียน 14 คือสมมติฐานที่ไม่เคยมีใครไปตรวจกับข้อมูลจริง แล้วมันเดินทางข้ามสี่คอมโพเนนต์ เงียบ — dummyjson ให้มาเป็นสเกล 0–5 (ต่ำสุด 2.51 สูงสุด 4.99) ผลคือไม่มีสินค้าชิ้นไหนในร้านที่ดาวทึบเกินสองดวง และแถบ 5★ กับ 4★ เป็นศูนย์เสมอ ตรวจสมมติฐานเรื่องหน่วยและช่วงค่ากับ payload จริงตั้งแต่วันที่เขียน type ไม่ใช่วันที่ render
ชื่อ class ที่ไม่มีนิยาม (image-container, banner-container) หรือเกือบถูก (font-bold แทน fw-bold) (18, 19, 21) ชื่อที่คุ้นจากเฟรมเวิร์กอื่น โดยเฉพาะ Tailwind ซึ่งชื่อ class หน้าตาคล้ายกับ utility ของบทเรียน 04 มาก เงียบ — ไม่มี TypeScript ไม่มี lint ตัวไหนตรวจว่า string ใน className มีอยู่จริงในไฟล์ CSS ต้อง grep -rn "ชื่อ-class" src/styles/ ทีละตัว ระบุชื่อ class ที่ต้องใช้ลงใน prompt ตรง ๆ แล้วไล่ grep ทุกชื่อที่โผล่ใน diff — สองนาทีที่ไม่มีเครื่องมือทำแทนได้

ตระกูล 2 — เขียนด้วยเวอร์ชันที่โลกมีโค้ดเยอะกว่า

โมเดลเห็นโค้ด react-router v6 และ TanStack Query v4 มามากกว่าของใหม่หลายเท่า เวลาไม่มีอะไรบังคับ มันจะเขียนแบบที่มันเห็นบ่อยกว่า ตระกูลนี้น่าสนใจตรงที่มันมีทั้งฝั่งดังและฝั่งเงียบอยู่ในตระกูลเดียวกัน และเส้นแบ่งไม่ได้อยู่ที่ว่าอันไหนผิดหนักกว่า แต่อยู่ที่ว่ามันเขียนของแปลกปลอมเพิ่มเข้ามา (compiler เห็น) หรือมันแค่เลือกโครงคนละแบบ (compiler ไม่มีอะไรให้เทียบ)

อาการทำไมเกิดวิธีจับวิธีแก้
router.tsx ออกมาเป็น <BrowserRouter> ครอบ <Routes> ครอบ <Route> แทน createBrowserRouter + RouterProvider (09) โค้ด v6 ในโลกยังมีมากกว่า data mode มาก เงียบ — ทั้งสองแบบทำให้หน้าเว็บขึ้นเหมือนกันเป๊ะ lint และ typecheck ผ่านทั้งคู่ เปิดไฟล์แล้วค้นคำว่า <Route ถ้าเจอแม้แต่ตัวเดียวคือรูปทรงผิด ถอยแล้วสั่งใหม่ — เติมบรรทัดที่ระบุ data mode ลงใน prompt ไม่ใช่ไล่แก้ทีละแท็ก
ทิ้ง queryOptions แล้วเขียนเป็น custom hook ที่เรียก useQuery(key, fn) แบบสองอาร์กิวเมนต์ (17) ไวยากรณ์ v4 ที่ v5 เปลี่ยนไปรับ options object ก้อนเดียว ดัง — npm run typecheck ฟ้อง TS2769 ว่า Property 'queryKey' is missing in type 'string[]' ถอยแล้วสั่งใหม่ — ถึงจะดัง แต่สิ่งที่ผิดคือรูปทรงทั้งก้อน ไม่ใช่บรรทัดเดียว
keepPreviousData: true แทน placeholderData: keepPreviousData (17) option ของ v4 ที่ถูกถอดออกไปแล้ว ดัง — TS2769 พร้อมชื่อ property ที่ผิดในข้อความ error แก้ต่อ — เปลี่ยนชื่อ option ให้ถูก จบในบรรทัดเดียว
ลืมบรรทัด placeholderData ไปทั้งบรรทัด (17) เป็นการไม่ทำ ไม่ใช่การทำผิด จึงไม่มีอะไรให้ compiler จับ เงียบ — ไปโผล่ตอนบทเรียน 20 เป็นกริดที่กะพริบเป็น spinner ทุกครั้งที่เปลี่ยนหน้า นับบรรทัดในจาน byCategory ด้วยตา แก้ต่อ — และเพิ่มข้อกำหนดข้อนี้ลง prompt รอบหน้าให้ชัด
เขียนปุ่มเลขหน้าเองด้วย map แทนที่จะห่อ react-paginate (13) pagination เขียนมือเป็นแบบฝึกหัดยอดนิยม โค้ดตัวอย่างมีเยอะกว่าการห่อ library เงียบ — เปิด Pagination.tsx แล้วค้นคำว่า map เป็นอย่างแรก ถอยแล้วสั่งใหม่ — ของที่ได้จะไม่มีอะไรตรงกับ contract สามบรรทัดที่ออกแบบไว้เลย
ผูก input เป็น controlled ด้วย useState แล้วเรียก safeParse เอง แทนที่จะใช้ register ของ react-hook-form (26) ฟอร์มแบบ controlled คือท่ามาตรฐานของ React ที่มีโค้ดในโลกมากที่สุด เงียบสนิท — กรอกได้ error ขึ้นครบ submit ได้ แยกไม่ออกจากภาพหน้าจอ ต้อง grep -n "useState" ในไฟล์ฟอร์ม ซึ่งต้องว่างเปล่า ถอยแล้วสั่งใหม่ — ระบุชื่อ API ที่ต้องใช้ (register, handleSubmit, zodResolver) ลงใน prompt

ตระกูล 3 — วางของถูกไว้ผิดที่

ตระกูลนี้อันตรายที่สุดในหกตระกูล เพราะโค้ดทุกบรรทัดถูก ฟังก์ชันที่เรียกก็ถูกตัว ค่าที่ส่งก็ถูกค่า สิ่งเดียวที่ผิดคือมันอยู่ผิดไฟล์หรือผิดจังหวะเวลา — ซึ่งเป็นสิ่งที่ไม่มีเครื่องมือไหนมีความเห็น

ก้อนนี้เงียบสนิททั้ง lint และ typecheck และในแง่ของ cache มันก็ไม่ได้พังด้วย — useState เรียก initializer ครั้งเดียวตอน mount สิ่งที่ผิดคือคนละเรื่อง: โปรเจกต์เราตกลงกันตั้งแต่บทเรียน 11 ว่า client มีตัวเดียวและอยู่ใน src/app/queryClient.ts เพราะไฟล์นั้นเป็นที่ตั้งค่า staleTime กับ retry ของทั้งแอป และเพราะเทสต์ในบทเรียน 30 ต้องสร้าง client ของตัวเองต่างหากโดยไม่ไปยุ่งกับตัวนี้ ของที่ถูกจึงเป็นสองไฟล์:

// src/app/queryClient.ts — ระดับบนสุดของไฟล์ ไม่มี indent ข้างหน้า
import { QueryClient } from "@tanstack/react-query";

export const queryClient = new QueryClient({
  defaultOptions: {
    queries: {
      staleTime: 60 * 1000,
      retry: 1,
    },
  },
});
// src/app/providers.tsx — import เข้ามาใช้ ไม่สร้างเอง
import { queryClient } from "./queryClient";

export function AppProviders({ children }: { children: ReactNode }) {
  return (
    <QueryClientProvider client={queryClient}>
      <CartProvider>{children}</CartProvider>
      {import.meta.env.DEV && <ReactQueryDevtools initialIsOpen={false} />}
    </QueryClientProvider>
  );
}

บทเรียนของก้อนนี้ไม่ใช่ท่าเขียน QueryClient แต่คือ: การที่ lint เขียวหลังการแก้ ไม่ได้แปลว่าแก้ถูก มันแปลว่ากฎที่เขียนไว้ไม่มีอะไรจะพูดกับโค้ดชุดนี้แล้วเท่านั้น กติกาของโปรเจกต์มีมากกว่าที่กฎจะเขียนได้เสมอ

2. useReducer สองอาร์กิวเมนต์ — ต่างกันแค่วงเล็บคู่เดียว

// ผิด — เรียกฟังก์ชันแล้วส่ง "ผลลัพธ์" เข้าไป
const [cart, dispatch] = useReducer(cartReducer, loadCartState());

// ถูก — ส่ง "ตัวฟังก์ชัน" ให้ React เก็บไว้เรียกเองครั้งเดียวตอน mount
const [cart, dispatch] = useReducer(cartReducer, undefined, loadCartState);

ต่างกันแค่วงเล็บคู่เดียวกับคำว่า undefined แต่แบบบนแปลว่าทุกครั้งที่ CartProvider re-render — คือทุกครั้งที่มีของเข้าออกตะกร้า และทุกครั้งที่ parent re-render — JavaScript จะเปิด localStorage, ดึง string ออกมา, JSON.parse ใหม่ทั้งก้อน แล้วโยนผลลัพธ์ทิ้ง เพราะ React ใช้ค่านั้นเฉพาะตอน mount แรกเท่านั้น

วิธีจับคือมองว่าหลังชื่อ loadCartState มีวงเล็บ () ต่อท้ายไหม มีคือผิด ไม่มีเครื่องมือตัวไหนในโปรเจกต์นี้จับได้เลย: lint ผ่าน typecheck ผ่าน หน้าเว็บทำงานถูกต้องทุกประการ ตะกร้าจำของได้ ปิดเบราว์เซอร์แล้วเปิดใหม่ก็ยังอยู่ครบ พิสูจน์ได้ทางเดียวคือวาง console.log ไว้ใน loadCartState แล้วนับจำนวนบรรทัดใน console

3. clearCart ที่อยู่ก่อนเวลา

ก้อนนี้คือของที่คุณจะไม่มีวันเห็นอาการในเครื่องตัวเอง เพราะ dummyjson ตอบ 200 ทุกครั้ง:

// src/pages/Checkout/Checkout.tsx — ผิด
const { clearCart } = useCart();
const { onPlaceOrder, /* ... */ } = useCheckout();

// ...

<BillingSummary
  onPlaceOrder={() => {
    onPlaceOrder();
    clearCart();
  }}
/>

onPlaceOrder เรียก mutate() ซึ่งเป็น fire-and-forget — มันคืนค่ากลับมาทันที ก่อน request ออกจากเครื่องด้วยซ้ำ ดังนั้น clearCart() บรรทัดถัดมาจะทำงานก่อนเซิร์ฟเวอร์ตอบเสมอ ผลคือกดปุ่มปุ๊บตะกร้าว่างปั๊บ ไม่ว่าคำสั่งซื้อจะสำเร็จหรือไม่ อาการจะไปโผล่กับลูกค้าที่เน็ตหลุดกลางคัน แล้วเสียของทั้งตะกร้าโดยไม่ได้ออร์เดอร์ ที่ถูกคือมันต้องอยู่ในที่ที่ React Query รับประกันว่าจะถูกเรียกก็ต่อเมื่อ request สำเร็จ:

// src/features/checkout/useCheckout.ts — ถูก
const { mutate: placeOrderMutate, isPending: isPlaceOrderLoading } = useMutation({
  mutationFn: () => {
    if (!checkoutAddress) {
      throw new Error("Delivery Address is Missing");
    }

    return placeOrder({
      userId: 1,
      products: cart.items.map((item) => ({
        id: item.id,
        quantity: item.quantity,
      })),
      address: checkoutAddress,
    });
  },
  onSuccess: () => {
    clearCart();
    goToOrderSuccess();
  },
});

วิธีตรวจสองคำสั่ง: grep -n "useCart\|clearCart" src/pages/Checkout/Checkout.tsx ต้องว่างเปล่า และ grep -n "clearCart" src/features/checkout/useCheckout.ts ต้องเจอบรรทัดเดียว คือบรรทัดที่อยู่ใน onSuccess ญาติสนิทของอาการนี้คือ navigate("/order/success") ที่ถูกวางไว้จุดเดียวกันด้วยเหตุผลเดียวกัน ผลเหมือนกันเป๊ะ คือเด้งไปหน้าขอบคุณตั้งแต่ยังไม่รู้ผล

4. สาขาที่หายไปสองสาขา

ก้อนนี้คือตัวอย่างที่ตรงที่สุดของ "โค้ดที่สั้นกว่าและถูกในสายตา TypeScript ทุกประการ":

// src/pages/Home/Home.tsx — ผิด
<div className="flex gap-25">
  <ProductsList
    products={bestProductsData?.products}
    onProductClick={onProductClick}
  />
</div>

ProductsList รับ undefined ได้อยู่แล้ว เพราะเราออกแบบไว้แบบนั้นเองในบทเรียน 18 โค้ดก้อนนี้จึงไม่มีอะไรผิดเลยสำหรับ compiler และสั้นกว่าตัวจริงถึงสิบบรรทัดต่อหนึ่ง section ตัวจริงเป็นแบบนี้:

// src/pages/Home/Home.tsx — ถูก
<div className="flex gap-25">
  {isBestProductsError ? (
    <ErrorMessage />
  ) : isBestProductsLoading ? (
    <div className="text-center">
      <ClipLoader size={40} aria-label="Loading Spinner" data-testid="loader" />
    </div>
  ) : (
    <ProductsList
      products={bestProductsData?.products}
      onProductClick={onProductClick}
    />
  )}
</div>

บนเครื่องคุณที่เน็ตดีและ API ตอบใน 200ms สองก้อนนี้ให้หน้าตาเดียวกันทุกพิกเซล วันที่ dummyjson ล่มหรือผู้ใช้อยู่บนมือถือสัญญาณอ่อน ก้อนแรกให้ช่องว่างเปล่าตรงที่ควรมีสินค้า ไม่มี spinner ไม่มีข้อความ ไม่มีอะไรบอกว่าเกิดอะไรขึ้น

สังเกตว่าทั้งสี่ก้อนมีอะไรเหมือนกัน: ไม่มีก้อนไหนเลยที่จับได้ด้วยการเปิดหน้าเว็บดู ทุกก้อนต้องจับด้วยการอ่านโค้ด หรือด้วยการจงใจสร้างสถานการณ์ที่ไม่มีใครอยากให้เกิด (ตั้ง throttling เป็น Offline, กดปุ่มลดจนถึงศูนย์, เข้าออกหน้าเดิมยี่สิบรอบ) นั่นคือรูปร่างของงานตรวจโค้ดที่ AI เขียน

ตัดสินใจสามทาง

บทเรียน 08 แนะนำสามทางเลือกนี้ไว้แล้ว: แก้ต่อ / ถอยแล้วสั่งใหม่ / เขียนเอง ตอนนั้นเรายังไม่มีตัวอย่างพอจะบอกว่าจะรู้ได้อย่างไรว่าตอนนี้อยู่ในสถานการณ์ไหน ตอนนี้มีแล้ว

คำถามที่ต้องตอบไม่ใช่ "ผิดมากหรือผิดน้อย" แต่คือ "รูปทรงถูกไหม" — และคำว่ารูปทรงในโปรเจกต์นี้มีความหมายที่ชี้ได้ ไล่สามคำถามนี้ตามลำดับ หยุดที่ข้อแรกที่ตอบว่า "ไม่":

  1. ไฟล์ที่ได้มา อยู่ path ที่คุณสั่ง และมีเท่าที่สั่งไหม — git status กับ git diff --stat ตอบข้อนี้ได้ในสิบวินาที ไฟล์เกิน ไฟล์ขาด หรือไฟล์อยู่ผิดโฟลเดอร์ = รูปทรงผิด
  2. ชื่อ export, signature ของ props และทิศทางการไหลของข้อมูล ตรงกับที่สั่งไหม — RatingBreakdown ที่เปลี่ยนมารับ rating: number เอง, BillingSummary ที่เรียก useCart() แทนรับ props, custom hook ที่โผล่มาแทน queryOptions ทั้งสามอันนี้คือรูปทรงผิด ไม่ใช่รายละเอียดผิด
  3. สิ่งที่ผิด คุณชี้เป็นบรรทัดได้ไหม — ถ้าชี้ได้ว่า "บรรทัด 14 ขาด setPage(1)" นั่นคือรายละเอียด ถ้าตอบได้แค่ "มันไม่ค่อยถูก" นั่นคือคุณยังอ่านไม่ครบ หรือมันผิดรูปทรง

แก้ต่อ — เมื่อรูปทรงถูก รายละเอียดผิด

เงื่อนไขคือผ่านทั้งสามข้อข้างบน แล้วสิ่งที่ผิดชี้เป็นบรรทัดได้ วิธีสั่งมีรูปแบบเดียว: ชี้ไฟล์ ชี้ฟังก์ชัน บอกสิ่งที่ต้องการ ปิดขอบเขต

ใน src/pages/Category/Category.tsx ฟังก์ชัน onCategoryClick เรียกแค่
setSelectedCategory ให้เพิ่ม setPage(1) ต่อท้ายในฟังก์ชันเดียวกัน
ห้ามแก้ไฟล์อื่น และห้ามย้าย logic นี้ไปไว้ใน useEffect

คำสั่งที่ใช้ไม่ได้คือ "ยังไม่ถูก แก้ให้หน่อย" หรือ "ทำให้มันทำงานถูกที" — ไม่ใช่เพราะมันสุภาพเกินไป แต่เพราะมันไม่มีข้อมูลใหม่อยู่ในนั้นเลย Agent ที่ได้คำสั่งแบบนี้จะเดาว่าอะไรผิด และการเดารอบที่สองมักออกมาไกลกว่ารอบแรก บรรทัดสุดท้ายที่ปิดขอบเขตก็สำคัญไม่แพ้กัน เพราะ "แก้ตรงนี้" กับ "จัดระเบียบไฟล์นี้ใหม่ทั้งไฟล์" เป็นสองงานที่ Agent แยกให้เองไม่ได้ถ้าคุณไม่บอก

กติกาที่ต้องมีคู่กันเสมอ: สั่งแก้ได้สองรอบ ถ้ารอบที่สองยังไม่เข้าที่ ให้ถอย ไม่ต้องลองรอบที่สาม

ถอยแล้วสั่งใหม่ — เมื่อรูปทรงผิดตั้งแต่ต้น

นี่คือทางที่คนใช้น้อยเกินไปที่สุดในสามทาง เพราะมันรู้สึกเหมือนทิ้งงานที่ทำมาแล้ว ทั้งที่งานที่ทิ้งคืองานที่ Agent ทำ ไม่ใช่งานที่คุณทำ ตัวอย่างที่ชัดที่สุดคือ router ในบทเรียน 09 ของที่ได้มาหน้าตาแบบนี้:

// src/app/router.tsx — รูปทรงผิดทั้งไฟล์
export default function AppRouter() {
  return (
    <BrowserRouter>
      <Routes>
        <Route element={<MainLayout />}>
          <Route path="/" element={<Home />} />
          <Route path="/categories" element={<Category />} />
          <Route path="/products/:id" element={<Product />} />
        </Route>
      </Routes>
    </BrowserRouter>
  );
}

ก้อนนี้ทำให้หน้าเว็บขึ้นได้ทุกหน้า lint ผ่าน typecheck ผ่าน และถ้าคุณเลือก "แก้ต่อ" คุณจะได้เดินเข้าไปในกับดักที่ยาวที่สุดของคอร์สนี้ — สั่งให้เปลี่ยนเป็น createBrowserRouter แล้วมันจะเก็บ <Routes> ไว้ข้างใน สั่งให้ลบอีกทีมันจะเปลี่ยน export ตัวเดียว สั่งอีกทีมันจะสร้างไฟล์ที่สอง สามรอบผ่านไปคุณจะได้ไฟล์ที่ไม่มีใครอธิบายได้ว่าทำไมต้องมีบรรทัดไหนบ้าง ของที่ถูกคือของที่ต่างจากข้างบนตั้งแต่บรรทัดแรกยันบรรทัดสุดท้าย:

// src/app/router.tsx — ถูก
export const routes: RouteObject[] = [
  {
    element: <MainLayout />,
    errorElement: <RouteErrorFallback />,
    children: [
      { path: "/", element: <Home /> },
      { path: "/categories", element: <Category /> },
      { path: "/products/:id", element: <Product /> },
      // ...
    ],
  },
];

export const router = createBrowserRouter(routes);

ขั้นตอนของการถอยมีสามข้อ และข้อที่สองคือข้อที่คนลืม:

  1. git restore . — คืนไฟล์ที่ถูกแก้กลับไปเป็นของ commit ล่าสุด
  2. ลบไฟล์ใหม่ทิ้งด้วย — git restore ไม่แตะไฟล์ที่ยังไม่ถูก track ดู git status ว่ามีอะไรค้างอยู่บ้าง แล้วลบให้หมด (git clean -fd ทำให้ในคำสั่งเดียว แต่รู้ตัวไว้ว่ามันลบไฟล์ที่ไม่ได้ track ทุกตัว ไม่ใช่เฉพาะของที่ Agent สร้าง)
  3. กลับไปแก้ที่ prompt ไม่ใช่ที่โค้ด — ของที่ออกมาผิดรูป แปลว่าคำสั่งขาดข้อมูลไปหนึ่งชิ้น หาให้เจอว่าชิ้นไหน สำหรับ router ชิ้นนั้นคือบรรทัดนี้ใน ข้อกำหนดทางเทคนิค: — ใช้ createBrowserRouter + RouterProvider ของ data mode ห้ามใช้ <BrowserRouter>, <Routes> หรือ <Route> ใน JSX

ถ้าพลาดข้อเดิมสองครั้งกับ prompt คนละอัน แปลว่ามันไม่ใช่ปัญหาของ prompt แต่เป็นปัญหาของกติกา — ที่ที่ควรไปแก้คือ .cursor/rules/project.mdc จากบทเรียน 07 เพราะกติกาในไฟล์นั้นถูกอ่านทุกครั้งโดยที่คุณไม่ต้องพิมพ์ซ้ำ

เขียนเอง — เมื่อการอธิบายแพงกว่าการพิมพ์

สองเกณฑ์ ใช้อันไหนก่อนถึงก็ได้:

  • อธิบายไปสามครั้งแล้วยังไม่ได้ — สองครั้งแรกคือโควตาของ "แก้ต่อ" ครั้งที่สามคือหลังถอยแล้วสั่งใหม่หนึ่งรอบ ถ้าถึงตรงนี้แล้วยังไม่เข้าที่ แปลว่าสิ่งที่คุณต้องการมีรายละเอียดที่อธิบายเป็นภาษาคนได้ยากกว่าเขียนเป็นโค้ด
  • โค้ดสั้นกว่าคำอธิบาย — วัดตรง ๆ ได้เลย ถ้าย่อหน้าที่คุณกำลังจะพิมพ์ใส่แชทยาวกว่าโค้ดที่คุณต้องการ ให้พิมพ์โค้ด cartReducer เป็นตัวอย่างที่ชัดที่สุด: อธิบายกติกาทั้งสี่ action ให้ครบพอที่จะไม่มีอะไรถูกเดา ใช้ที่ว่างมากกว่าตัว reducer เอง

สิบจุดที่คอร์สนี้บังคับให้พิมพ์เองตลอดทั้งคอร์สถูกเลือกด้วยเกณฑ์เดียวกันนี้บวกอีกข้อหนึ่ง: ถ้าคุณไม่เคยพิมพ์ cartReducer เอง คุณจะไม่มีมาตรฐานในหัวไว้เทียบตอนตรวจ reducer ที่ AI เขียนให้ในโปรเจกต์หน้า

ที่ต้องพูดให้ชัดคือ "เขียนเอง" ไม่ใช่การยอมแพ้ และไม่ใช่การถอยไปเป็นค่าเริ่มต้น มันคือการอ่านตัวเลขให้ออกว่าตอนนี้ทางไหนถูกกว่า คนที่ไม่เคยเลือกทางนี้เลย กับคนที่เลือกทางนี้ตลอด เสียเวลาไปพอ ๆ กันด้วยเหตุผลคนละข้อ

สามข้อนี้ต่างจากตารางข้างบน ตรงที่มันไม่ใช่อาการของโค้ด แต่เป็นอาการของคนตรวจ และมันมาก่อนบั๊กเสมอ

1. diff ยาวเกินกว่าจะอ่านไหว

เกณฑ์ไม่ใช่จำนวนบรรทัด แต่คือคำถามนี้: อ่านจบแล้วชี้ได้ทุกไฟล์ไหมว่าทำไมมันถึงอยู่ใน diff นี้ ถ้ามีแม้แต่ไฟล์เดียวที่ตอบไม่ได้ diff นั้นยาวเกินไปแล้ว ไม่ว่ามันจะมีกี่บรรทัด

ทำอะไรแทน: อย่าเริ่มด้วย git diff ให้เริ่มด้วย git diff --stat ซึ่งเป็นรายชื่อไฟล์ล้วน ๆ เทียบกับรายการใน โครงสร้าง: ของ prompt ก่อน ถ้ารายชื่อไม่ตรง ถอยเลยโดยยังไม่ต้องอ่านเนื้อในสักบรรทัด ส่วนวิธีป้องกันคือสองอย่างที่ต้องทำก่อนส่ง prompt: commit ให้ working tree สะอาด และเขียนส่วน ขอบเขต: ให้ครบ — diff ที่อ่านไหวเป็นผลของ prompt ที่ดี ไม่ใช่ของความอดทนในการอ่าน

2. เทสต์ผ่านแต่คุณอธิบายไม่ได้ว่าทำไม

ข้อนี้จะมีความหมายเต็มที่ตอนบทเรียน 30–33 แต่ต้องรู้ไว้ตั้งแต่ตอนนี้ เพราะมันเป็นกับดักที่ทำให้คนเชื่อโค้ดผิดชุด เทสต์ที่ AI เขียนมีแนวโน้มจะ assert สิ่งที่โค้ดทำอยู่ ไม่ใช่ สิ่งที่โค้ดควรทำ — ซึ่งแปลว่าถ้าโค้ดผิด เทสต์จะยืนยันความผิดนั้นให้เป็นสีเขียว

ทำอะไรแทน: ทำให้มันแดงด้วยมือ เปิดโค้ดจริง (ไม่ใช่เทสต์) แล้วแก้ให้ผิดหนึ่งบรรทัด — ลบ setPage(1) ทิ้ง, เปลี่ยน <= 1 เป็น <= 0, ย้าย clearCart() ออกจาก onSuccess — แล้วรันเทสต์ใหม่ ถ้ามันยังเขียว เทสต์นั้นไม่ได้ทดสอบสิ่งที่คุณคิดว่ามันทดสอบ จากนั้น git restore คืนของเดิม การทดลองนี้ใช้เวลาสามสิบวินาทีและตอบคำถามที่การอ่านเทสต์เฉย ๆ ตอบไม่ได้

3. ยอมรับโค้ดเพราะ "มันก็รันได้"

อ่านตารางทั้งหกตระกูลข้างบนอีกรอบแล้วนับดู: อาการเกือบทั้งหมดในนั้นรันได้ หน้าเว็บขึ้น ปุ่มกดได้ ข้อมูลมาครบ "มันก็รันได้" จึงไม่ใช่หลักฐานว่าโค้ดถูก มันเป็นแค่หลักฐานว่าโค้ดไม่ crash ซึ่งเป็นเกณฑ์ที่ต่ำกว่าที่คุณต้องการมาก

ทำอะไรแทน: ใช้ขั้นที่ห้าของวงจรตรวจงานจากบทเรียน 08 ตรง ๆ — ไล่ดูโค้ดที่เพิ่งได้มาแล้วถามตัวเองอย่างซื่อสัตย์ว่า "ถ้ามีคนถามว่าบรรทัดนี้ทำอะไร ตอบได้ไหม" ตอบไม่ได้แม้แต่บรรทัดเดียว ให้เปิดโหมด Ask @ ไฟล์นั้นแล้วถามจนเข้าใจก่อนไปต่อ นี่คือกติกาข้อเดียวของคอร์สนี้ในรูปของขั้นตอนที่ทำได้จริง และเป็นด่านสุดท้ายที่เหลืออยู่หลังจากเครื่องมือทุกตัวบอกว่าผ่านแล้ว

ก่อนไปต่อ

สิ่งที่บทนี้ทำคือรวบยี่สิบบรรทัดกระจัดกระจายให้เป็นของที่ใช้ซ้ำได้: หกตระกูล หนึ่งเส้นแบ่ง (ดัง/เงียบ) สามทางเลือก และสามสัญญาณ ถ้าจะจำอะไรกลับไปข้อเดียว ให้จำเส้นแบ่งดังกับเงียบ เพราะมันเปลี่ยนวิธีจัดสรรเวลาตรวจงานของคุณทั้งหมด — เครื่องมือดูแลฝั่งดังให้ครบแล้ว เวลาของคุณควรไปอยู่ฝั่งเงียบทั้งก้อน

สี่บทถัดไปคือการเอาฝั่งเงียบส่วนหนึ่งไปทำให้ดัง: บทเรียน 30–33 เราจะติดตั้งชุดทดสอบแล้วเขียนเทสต์ครบทุกชั้น เพื่อให้อาการอย่าง "ลืม setPage(1)" หรือ "clearCart อยู่ผิดที่" มีเครื่องมือมาตะโกนบอกแทนที่จะรอให้คนสังเกต ส่วนบทเรียน 34 จะกลับมาที่เรื่องเดียวกันนี้จากอีกด้าน คือการใช้ AI ตรวจงานของ AI แล้วดูว่ามันทำอะไรได้และทำอะไรไม่ได้

🚨 ทักษะที่แยกคนใช้ AI เป็นกับไม่เป็น ไม่ใช่การเขียน prompt ที่เก่งกว่า แต่คือการรู้ว่าเมื่อไหร่ควรเลิกใช้มันแล้วลงมือเอง prompt ที่ดีขึ้นช่วยได้จนถึงจุดหนึ่ง หลังจุดนั้นสิ่งที่ประหยัดเวลาคือการปิดแชทแล้วพิมพ์โค้ดสิบบรรทัดที่คุณรู้อยู่แล้วว่าต้องเป็นอะไร
