บทเรียน 34 · ส่งท้าย (Wrap Up)

ใช้ AI ตรวจงานตัวเอง

AI Code Review

ยี่สิบสี่บทที่ผ่านมา Cursor ทำงานอย่างเดียวคือเขียน — เราส่ง prompt มันคืน diff เราอ่านแล้วกด Accept หรือถอย บทนี้เราสลับทิศ: ชี้มันไปที่โค้ดที่เสร็จและ commit ไปหมดแล้ว แล้วสั่งให้มันอ่าน ของที่ได้กลับมาไม่ใช่ไฟล์ที่เปลี่ยน แต่เป็นรายการข้อสังเกต หลังส่ง prompt ทั้งสี่อันในบทนี้ git status ต้องยังสะอาดเท่าเดิมทุกครั้ง

ความต่างนี้เปลี่ยนราคาของความผิดพลาดไปทั้งหมด เวลามันคิดผิดตอนเขียน สิ่งที่ได้คือโค้ดผิดที่อาจถูก Accept เข้าไปในโปรเจกต์ แล้วอีกห้าบทค่อยไปโผล่เป็นอาการที่ไม่มีใครโยงกลับมาถึงบรรทัดนั้นได้ เวลามันคิดผิดตอนอ่าน สิ่งที่ได้คือหนึ่งบรรทัดในรายการที่คุณเปิดไฟล์แล้วพบว่าไม่จริง เสียเวลาไปสองนาที นั่นคือเหตุผลที่งานอ่านเป็นงานที่มอบให้มันได้ด้วยความระวังน้อยกว่างานเขียนมาก — แต่ความปลอดภัยนั้นมีเงื่อนไขข้อเดียว: มันจะปลอดภัยก็ต่อเมื่อคุณไม่เอารายการที่ได้กลับไปสั่งแก้รวดเดียว หัวข้อ "วิธีอ่านผลลัพธ์" ทั้งหัวข้อพูดเรื่องนี้เรื่องเดียว

อย่าสับสนบทนี้กับบทเรียน 29 สองบทนี้ทำงานคนละทิศกัน บทเรียน 29 คือคุณเป็นคนอ่าน — คุณมีตารางหกตระกูลอยู่ในมือ แล้วเปิด diff ที่เพิ่งได้มาสด ๆ เพื่อไล่หาอาการที่รู้จักชื่อมันอยู่แล้ว บทนี้คือมันเป็นคนอ่าน — โค้ดถูก commit ไปหมดแล้ว ไม่มี diff ให้เปิด และสิ่งที่คุณอยากรู้คือของที่คุณไม่รู้ด้วยซ้ำว่ามีอยู่ กระจายอยู่ในไฟล์ร้อยกว่าไฟล์ที่ไม่มีใครนั่งอ่านพร้อมกันทั้งหมดได้ในบ่ายเดียว นี่เป็นงานเดียวในคอร์สนี้ที่ปริมาณคือตัวปัญหา ไม่ใช่ความยาก และงานรูปนี้เครื่องทำได้เร็วกว่าคนจริง ๆ

ท่าที่ใช้ก็เป็นท่าเดิมจากแบบฝึกท้ายบทเรียน 06 ที่คุณเปิดโหมด Ask แล้วถามเรื่อง alias @/ จาก vite.config.ts ต่างกันข้อเดียวแต่เป็นข้อใหญ่: คราวนั้นคุณรู้คำตอบอยู่ก่อนแล้ว คุณจึงตรวจคำตอบของมันได้ทันทีที่อ่านจบ คราวนี้คุณไม่รู้ ซึ่งแปลว่าวิธีตรวจต้องเปลี่ยนไปทั้งหมด และนั่นคือครึ่งหลังของบทนี้

กติกาสามข้อก่อนส่ง prompt แรก

สามข้อนี้ต้องครบก่อนพิมพ์ตัวอักษรแรก ไม่ใช่ข้อแนะนำ:

  1. สลับ dropdown เป็นโหมด Ask — ดูให้เห็นกับตาว่าไม่ใช่ Agent ตามที่บทเรียน 06 ย้ำไว้ prompt สี่อันข้างล่างนี้ถ้าส่งไปตอนอยู่โหมด Agent มันจะเริ่มแก้ไฟล์ให้ทันที ซึ่งทำลายจุดประสงค์ทั้งบท: สิ่งที่เราต้องการคือรายการที่จะเอาไปตัดสินใจ ไม่ใช่ diff ที่ต้องมานั่งกู้คืน
  2. git status ต้องสะอาด — เหตุผลเดียวกับที่ทำมาตลอดตั้งแต่บทเรียน 06 แต่คราวนี้มันทำหน้าที่เพิ่มอีกอย่าง: มันเป็นสัญญาณเตือน ถ้าคุณเผลออยู่โหมด Agent แล้วมันแก้ไฟล์ให้ git status จะบอกทันทีว่ามีอะไรเปลี่ยน ในบทนี้ไฟล์ที่เปลี่ยนแม้แต่ไฟล์เดียวคือความผิดพลาด ไม่ใช่ผลงาน
  3. ทุก prompt ต้องจบด้วยบรรทัดที่สั่งให้ตอบเป็นรายการที่มี path:บรรทัด และห้ามแก้ไฟล์ — บรรทัดนี้ไม่ได้มีไว้กันมันแก้อย่างเดียว path กับเลขบรรทัดคือสิ่งเดียวที่ทำให้คุณตรวจข้อนั้นได้ในสิบวินาที ข้อที่ตอบมาลอย ๆ ว่า "การจัดการ error ในหลายจุดยังไม่สม่ำเสมอ" คือข้อที่ยืนยันไม่ได้ และข้อที่ยืนยันไม่ได้ต้องทิ้ง ไม่ใช่เก็บไว้กังวล

สี่ prompt สำหรับตรวจโปรเจกต์ตัวเอง

สี่อันนี้เลือกมาเพราะทั้งสี่เป็นคำถามที่ตอบได้จากตัวโค้ดล้วน ๆ — ไม่ต้องรู้ว่าลูกค้าอยากได้อะไร ไม่ต้องรู้ว่าทีมตกลงอะไรกันไว้ ทุกข้อที่มันตอบกลับมา คุณเปิดไฟล์ยืนยันเองได้ นั่นคือเกณฑ์ที่ใช้เลือก ไม่ใช่ว่าเรื่องไหนสำคัญที่สุด (คำถามที่ไม่ผ่านเกณฑ์นี้อยู่ในหัวข้อสุดท้ายของบท)

ส่งทีละอัน อ่านให้จบ แล้วค่อยส่งอันถัดไป อย่าส่งรวดเดียวสี่อัน — สิ่งที่คุณต้องการจากบทนี้คือรายการสั้นสี่รายการที่อ่านไหว ไม่ใช่รายงานยาวสิบหน้าที่ปิดทิ้งแล้วไม่กลับมาอ่านอีกเลย

1. logic ที่เขียนซ้ำกันข้ามไฟล์

@src/pages @src/features @src/shared
อ่านไฟล์ .ts และ .tsx ทั้งหมดในสามโฟลเดอร์นี้ แล้วหา logic ที่เขียนซ้ำกัน
ตั้งแต่สองไฟล์ขึ้นไป — ทั้งแบบที่โค้ดเหมือนกันคำต่อคำ และแบบที่คนละสำนวน
แต่คำนวณสิ่งเดียวกัน

สำหรับแต่ละชุดที่ซ้ำ ตอบสี่บรรทัด:
- path:บรรทัด ของทุกจุดที่ซ้ำ
- หนึ่งประโยคว่ามันคำนวณอะไร
- ควรย้ายไปอยู่ที่ไหน เลือกจากสามที่นี้เท่านั้น: src/shared/utils/,
  src/shared/hooks/ หรือในโฟลเดอร์ของฟีเจอร์เจ้าของ (src/features/<ชื่อ>/)
- หนึ่งประโยคว่าทำไมถึงเป็นที่นั้น ไม่ใช่อีกสองที่

กติกาของโปรเจกต์นี้ที่ต้องใช้ตัดสิน: ของที่อยู่ใน src/shared/ ต้องไม่ผูกกับ
ฟีเจอร์ใดฟีเจอร์หนึ่ง ถ้าโค้ดชุดนั้นอ่านค่าจากตะกร้าหรือจากฟอร์ม checkout
มันไม่ใช่ของ shared/

ห้ามแก้ไฟล์ใด ๆ ตอบเป็นรายการอย่างเดียว

สังเกตย่อหน้ารองสุดท้าย: เราเขียนกติกาของบทเรียน 05 ลงไปใน prompt ตรง ๆ ถ้าไม่เขียน คำตอบที่มีโอกาสได้มากที่สุดคือ "ยกทุกอย่างไป shared/utils/" เพราะเป็นคำตอบที่อ่านแล้วดูสะอาดและไม่ต้องรู้อะไรเกี่ยวกับโปรเจกต์นี้เลย — กติกาที่ไม่ได้เขียนลง prompt คือกติกาที่ไม่มีอยู่ในสายตา Agent ซึ่งเป็นรากเดียวกับตระกูล 4 ของบทเรียน 29

ของที่มีอยู่จริงในโปรเจกต์นี้ให้มันหาเจอ — สองชุด และทั้งคู่ยืนยันด้วย grep ได้ในสิบวินาที ชุดแรกคือสูตรหายอดรวมตะกร้าที่เขียนไว้สองที่ด้วยมือทั้งคู่:

// src/pages/Cart/Cart.tsx
cart.items.reduce((total, item) => total + item.price * item.quantity, 0);

// src/features/checkout/useCheckout.ts
cart.items.reduce((sum, item) => sum + item.price * item.quantity, 0);

สูตรเดียวกันเป๊ะ ต่างกันแค่ชื่อตัวแปรตัวสะสม ชุดที่สองคือการจัดรูปเงิน — เครื่องหมาย $ ต่อด้วย .toFixed(2) — ซึ่งเขียนกระจายอยู่สิบสี่จุดในหกไฟล์ (ProductDetailInfo สองจุด, ProductCard สองจุด, SummaryOrderItem สองจุด, BillingSummary สามจุด, CartTable สี่จุด และ Cart.tsx อีกหนึ่ง) ทั้งที่ src/shared/utils/price.utils.ts มีอยู่แล้วตั้งแต่บทเรียน 18 และข้างในมีฟังก์ชันเดียวคือ calculateOriginalPrice

ทีนี้มาถึงส่วนที่น่าสนใจกว่าตัวรายการ: สองชุดนี้คำตอบไม่เหมือนกัน การจัดรูปเงินเป็น formatPrice(value: number): string ที่ไม่รู้จักตะกร้าและไม่รู้จักสินค้า — เข้า src/shared/utils/price.utils.ts ได้เต็มตัว ส่วนสูตรยอดรวมอ่าน cart.items ซึ่งเป็นโครงสร้างที่ฟีเจอร์ cart เป็นเจ้าของ มันจึงต้องไปอยู่ที่ src/features/cart/ ไม่ใช่ shared/ ต่อให้ทั้งหน้า Cart และ useCheckout ต่างก็เรียกใช้มัน — คนใช้อยู่สองฟีเจอร์ไม่ได้แปลว่ามันเป็นของกลาง มันแปลว่าฟีเจอร์ checkout อ่านของของฟีเจอร์ cart ซึ่งเป็นคนละเรื่องกัน นี่คือข้อที่คุณต้องตัดสินเอง ไม่ว่ามันจะตอบมาว่าอะไร

2. ทุกจุดที่เรียก API

@src/pages @src/features
ไล่หาทุกจุดในสองโฟลเดอร์นี้ที่เรียก useQuery หรือ useMutation ของ
@tanstack/react-query ข้ามไฟล์ที่ลงท้ายด้วย .test.ts และ .test.tsx ไป

ทำเป็นตาราง หนึ่งแถวต่อหนึ่งจุด คอลัมน์:
- path:บรรทัด
- จุดนั้นดึงหรือส่งข้อมูลอะไร
- โค้ดตรงนั้นอ่าน isLoading หรือ isPending ไปใช้จริงไหม (ใช่/ไม่)
- โค้ดตรงนั้นอ่าน isError ไปใช้จริงไหม (ใช่/ไม่)
- ถ้าตอบ "ไม่" ข้อใดข้อหนึ่ง บอกด้วยว่าผู้ใช้จะเห็นอะไรบนหน้าจอ
  ระหว่างที่ request ยังไม่เสร็จ และตอนที่มันล้มเหลว

การ destructure ตัวแปรออกมาเฉย ๆ ไม่นับว่า "ใช้" ต้องมีบรรทัดใน JSX
ที่อ่านค่านั้นไปตัดสินว่าจะ render อะไร ถึงจะนับ

ห้ามแก้ไฟล์ใด ๆ ตอบเป็นตารางอย่างเดียว

บรรทัด "การ destructure เฉย ๆ ไม่นับ" คือบรรทัดที่ทำให้ prompt นี้มีประโยชน์ ถ้าไม่มีมัน คำตอบจะกลายเป็นการนับว่ามีคำว่า isLoading โผล่กี่ครั้ง ซึ่งตอบคำถามคนละข้อกับที่เราถาม

ของจริงในโปรเจกต์นี้: มีเจ็ดจุด — useQuery หกจุด (Home.tsx สามจุด, Category.tsx สองจุด, Product.tsx หนึ่งจุด) และ useMutation อีกหนึ่งจุดใน useCheckout.ts ห้าจุดจัดการครบทั้ง loading และ error ตามที่บทเรียน 19–21 ไล่ตรวจไปทีละหน้าแล้ว เหลือสองจุดที่ไม่ได้อ่านอะไรเลยทั้ง isLoading และ isError และทั้งสองจุดเป็น query ตัวเดียวกัน:

// src/pages/Home/Home.tsx บรรทัด 36
const { data: categories } = useQuery(productQueries.categories());

// src/pages/Category/Category.tsx บรรทัด 23
const { data: categories } = useQuery(productQueries.categories());

แล้วปลายทางของทั้งสองไฟล์เขียนเหมือนกันอีก: categories={categories || []} แปลว่าวันที่ /products/categories ล้ม ผู้ใช้จะได้แถบหมวดหมู่ว่างเปล่าโดยไม่มี spinner ไม่มีข้อความ และไม่มีอะไรบอกว่าเกิดอะไรขึ้น — ตรงกับตระกูล 5 ของบทเรียน 29 ทุกตัวอักษร ต่างกันตรงที่คราวนี้ไม่ใช่ AI ที่ตัดสาขาทิ้ง มันเป็นแบบนี้มาตั้งแต่โค้ดอ้างอิงต้นฉบับ

นี่เป็นตัวอย่างแรกของบทนี้ที่แสดงว่า prompt แบบนี้หาอะไรเจอที่การอ่านทีละบทหาไม่เจอ: ตอนบทเรียน 19 คุณตรวจ Home.tsx ทั้งไฟล์แล้ว ตอนบทเรียน 20 คุณตรวจ Category.tsx ทั้งไฟล์แล้ว ทั้งสองรอบผ่าน เพราะในแต่ละไฟล์มี ErrorMessage กับ ClipLoader อยู่จริง — สิ่งที่มองไม่เห็นตอนอ่านทีละไฟล์คือช่องว่างในตารางที่โผล่ก็ต่อเมื่อวางทุกจุดเรียงกันในหน้าเดียว

3. accessibility สามข้อ

แม้โค้ดที่มันควรจะทดสอบจะถูกเขียนผิด

มองหาสามรูปแบบนี้เป็นอย่างน้อย:
- assertion ที่ฝั่งขวาคำนวณค่าที่คาดหวังด้วยสูตรเดียวกับโค้ดที่กำลังทดสอบ
  หรือเรียกฟังก์ชันตัวเดียวกันนั้น แทนที่จะเป็นค่าตายตัว
- เทสต์ที่เขียนค่าลงไปแล้วอ่านกลับมาด้วยฟังก์ชันจากไฟล์เดียวกัน โดยไม่มี
  ค่าตายตัวอยู่ในเทสต์เลยแม้แต่ตัวเดียว
- assertion ที่เทียบแค่ว่า "เนื้อหาเท่ากัน" ทั้งที่สัญญาของโค้ดชุดนั้น
  คือการคืน object ตัวใหม่ ไม่ใช่แก้ของเดิม

แต่ละข้อตอบสามบรรทัด:
- path:บรรทัด
- แก้โค้ดต้นทางให้ผิดอย่างไร เทสต์ตัวนี้ถึงจะยังเขียวอยู่
- ควรเพิ่ม assertion บรรทัดไหนเข้าไป เทสต์ถึงจะแดง

ห้ามแก้ไฟล์ใด ๆ และห้ามเขียนเทสต์เพิ่ม ตอบเป็นรายการอย่างเดียว

บรรทัด "แก้โค้ดต้นทางให้ผิดอย่างไร เทสต์ถึงจะยังเขียว" คือหัวใจของ prompt นี้ เพราะมันบังคับให้คำตอบอยู่ในรูปที่คุณเอาไปทดลองได้จริงในสามสิบวินาที — แก้ตามที่มันบอก รันเทสต์ ดูว่าเขียวจริงไหม แล้ว git restore เป็นวิธีเดียวกับที่บทเรียน 31 ให้ทำหกครั้งในกล่อง ✅ ต่างกันแค่คราวนี้เป็น AI ที่เสนอว่าจะแก้บรรทัดไหน แทนที่จะเป็นบทเรียนที่บอกไว้ล่วงหน้า

ของจริงในโปรเจกต์นี้มีสองข้อ และทั้งคู่ทดลองมาแล้วจริง ตัวเลขที่แสดงข้างล่างคือผลที่ได้จริง:

ข้อแรก — src/features/cart/store/cartReducer.test.ts เทสต์ห้าตัวในไฟล์นี้ครอบ action ครบทั้งสี่ประเภท แต่ไม่มีตัวไหนพิสูจน์ immutability ซึ่งเป็นสัญญาข้อเดียวที่ทำให้ cartReducer.ts ถูกจัดเป็นไฟล์พิมพ์เองตั้งแต่บทเรียน 22 บทเรียน 31 บอกเรื่องนี้ไว้แล้วในกล่อง 💡 ท้ายบท คราวนี้เอามาลองจริง — เขียน ADD_TO_CART ใหม่ให้ mutate ของเดิมทั้งสองสาขา:

สามท่ายืนยัน เรียงตามราคา

ก่อนแก้ทุกข้อ ต้องผ่านหนึ่งในสามท่านี้ ใช้ท่าที่ถูกที่สุดที่ตอบได้:

  1. grep — สิบวินาที ใช้ได้กับข้อที่เป็นเรื่องของ "มีอยู่กี่ที่" เช่นข้อที่บอกว่าสูตรยอดรวมซ้ำสองที่: grep -rn "item.price \* item.quantity" src/ ต้องเจอสองบรรทัดตามที่มันว่า เจอสามคือมันตอบไม่ครบ เจอหนึ่งคือมันเดา
  2. เปิดไฟล์อ่านบรรทัดนั้น — หนึ่งนาที ใช้กับข้อที่ต้องดูบริบทรอบ ๆ ถึงจะตัดสินได้ เช่นข้อที่บอกว่า Home.tsx ไม่ได้จัดการ error ของ categories — grep บอกได้แค่ว่าไม่มีคำว่า isError ใกล้ ๆ บรรทัดนั้น แต่ตอบไม่ได้ว่าปลายทางเขียน || [] ไว้ ซึ่งเป็นข้อมูลที่เปลี่ยนวิธีแก้
  3. เขียนการทดลองที่ต้องแดง — สามสิบวินาทีถึงห้านาที ใช้กับข้อที่พูดถึงพฤติกรรม ไม่ใช่รูปร่างของโค้ด นี่คือท่าที่แพงที่สุดและตอบได้แน่นอนที่สุด

แก้ทีละข้อ commit แยก

สิ่งที่ห้ามทำเด็ดขาดหลังได้รายการมาคือพิมพ์ว่า "แก้ทุกข้อในรายการให้ที" แล้วสลับเป็นโหมด Agent เหตุผลมีสามข้อและไม่ได้เกี่ยวกับความปลอดภัยเลยสักข้อ:

  • รายการนั้นมีข้อที่ผิดปนอยู่แน่นอน — และคุณจะไม่รู้ว่าข้อไหน เพราะทุกข้อถูกแก้ไปพร้อมกันหมดใน diff ก้อนเดียว
  • diff ที่ได้จะยาวเกินกว่าจะอ่านไหว — ซึ่งเป็นสัญญาณอันตรายข้อที่หนึ่งของบทเรียน 29 ในรูปที่คุณสร้างขึ้นมาใส่ตัวเอง เกณฑ์ยังเป็นเกณฑ์เดิม: อ่านจบแล้วชี้ได้ทุกไฟล์ไหมว่าทำไมมันถึงอยู่ในนี้
  • บางข้อในรายการไม่ใช่การแก้บั๊ก แต่เป็นการเปลี่ยนการตัดสินใจ — เช่นข้อที่เสนอให้ย้ายสูตรยอดรวมไป shared/ ข้อแบบนี้ต้องมีคนตอบว่าเอาหรือไม่เอา และเหตุผลของคำตอบนั้นควรอยู่ใน commit message ไม่ใช่จมอยู่ในกองสิบสองไฟล์ที่แก้พร้อมกัน

จังหวะที่ใช้ได้จริงคือวนสี่ก้าวนี้ทีละข้อ: ยืนยันด้วยหนึ่งในสามท่าข้างบน → แก้ (จะพิมพ์เองหรือสั่ง Agent แบบชี้ไฟล์ชี้ฟังก์ชันตามรูปแบบของบทเรียน 29 ก็ได้) → npm run lint, npm run typecheck และ npm run test ให้ผ่านครบ → commit หนึ่งข้อหนึ่ง commit ข้อความสั้น ๆ ที่บอกว่าแก้อะไรและทำไม ช้ากว่าแบบรวดเดียวแน่นอน แต่ทุกข้อที่ผ่านไปแล้วจะไม่ต้องกลับมาสงสัยอีก และถ้าข้อไหนพัง git revert ตัวเดียวจบโดยไม่แตะข้ออื่น

ผลลัพธ์ประเภทที่สี่: ของที่คุณไม่ได้ถาม

นอกจากข้อที่ถูก ข้อที่ผิด และข้อที่เป็นการตัดสินใจ ยังมีประเภทที่สี่ที่โผล่มาแน่ ๆ คือของที่มันเห็นระหว่างทางแล้วแถมมาให้ ในโปรเจกต์นี้ prompt ข้อ accessibility จะแถมเรื่องนี้มาเกือบแน่นอน: CategoryMenu.tsx ใช้ <span onClick> เป็นรายการหมวดหมู่, ProductCard.tsx ใช้ <div onClick> เป็นการ์ดสินค้าทั้งใบ, CartSummary.tsx ใช้ <div onClick> เป็นไอคอนตะกร้า และ thumbnail ใน ProductImageGallery.tsx ก็เป็น <div onClick> อีกเหมือนกัน ทั้งสี่จุดกดด้วยคีย์บอร์ดไม่ได้ ซึ่งเป็นอาการเดียวกับที่ตระกูล 6 ของบทเรียน 29 บันทึกไว้ตอนพูดถึง <div onClick={() => navigate("/cart")}>

ของแบบนี้ไม่ต้องทิ้ง แต่ก็ไม่ต้องแก้ในรอบนี้ จดลงไฟล์ไว้แล้วเดินตามรายการเดิมให้จบก่อน เหตุผลตรงไปตรงมา: การเผลอเดินตามของแถมทีละข้อคือวิธีที่งานรีวิวหนึ่งบ่ายกลายเป็นการรื้อโปรเจกต์สามวันโดยไม่มีใครตั้งใจ ตัวรายการที่คุณตั้งใจถามคือขอบเขตของงาน ของที่โผล่มาเองคืองานรอบหน้า

สิ่งที่มันบอกไม่ได้

ทุกอย่างในบทนี้ตั้งอยู่บนความสามารถอย่างเดียวของมัน: มันอ่านโค้ดได้ทั้งโปรเจกต์แล้วบอกว่าโค้ดสอดคล้องกันเองหรือเปล่า ไฟล์นี้ทำอย่างนี้แต่ไฟล์ข้าง ๆ ทำอีกอย่าง, ตรงนี้มีสาขา error ตรงนั้นไม่มี, สูตรนี้เขียนซ้ำสองที่ ทั้งหมดนี้เป็นข้อเท็จจริงที่อยู่ในไฟล์ ต่อให้ไม่มีใครอธิบายอะไรให้ฟัง มันก็หาเจอ

สิ่งที่มันบอกไม่ได้คือสิ่งที่สร้างขึ้นมานั้นถูกต้องหรือเปล่า และคำว่าถูกต้องที่นี่หมายถึงถูกตามความจริงข้างนอกที่ไม่ได้เขียนอยู่ในโค้ดสักตัวอักษร สามคำถามต่อไปนี้เป็นคำถามจริงของโปรเจกต์นี้ และไม่มีคำถามไหนที่ AI ตอบได้จากการอ่านโค้ด ไม่ว่าจะให้อ่านกี่รอบ:

  • ยอดรวมควรคิด VAT ไหม — useCheckout.ts คำนวณ total = subtotal + shipping แล้ว BillingSummary แสดงสามบรรทัด Sub Total / Shipping / Total ไม่มีคำว่า tax หรือ VAT อยู่ในโปรเจกต์นี้เลยสักไฟล์ AI อ่านแล้วจะไม่พบความไม่สอดคล้องแม้แต่นิดเดียว เพราะทุกอย่างตรงกันหมด: ตัวคำนวณคำนวณสองก้อน ตัวแสดงผลแสดงสองก้อน เทสต์ใน useCheckout.test.tsx ก็ยืนยันสองก้อน ถ้าร้านนี้ต้องเก็บ VAT 7% ทุกบรรทัดที่ว่ามาผิดหมด ทั้งที่เขียวหมด
  • ค่าส่งควรฟรีเมื่อไหร่ — src/features/checkout/consts.ts ตั้งไว้สองตัวเลือกราคาตายตัว 5.99 กับ 15.99 แล้ว shipping ก็คือราคาของตัวที่เลือก จบ ไม่มีเงื่อนไขไหนในโปรเจกต์ที่ทำให้มันเป็นศูนย์ได้ AI จะไม่ทักเรื่องนี้เพราะไม่มีอะไรให้ทัก — โค้ดทำสิ่งที่มันเขียนไว้ว่าจะทำครบถ้วน กติกา "ซื้อครบห้าสิบดอลลาร์ส่งฟรี" ถ้ามีอยู่จริง มันอยู่ในหัวเจ้าของร้าน ไม่ได้อยู่ในไฟล์
  • ฟีเจอร์นี้ควรมีอยู่ไหมตั้งแต่แรก — คำถามนี้ไม่มีบรรทัดให้ชี้เลยด้วยซ้ำ มันเป็นคำถามว่าทำไมต้องมี CountdownTimer บนหน้า Home ที่นับถอยหลังไปยังพรุ่งนี้ทุกวัน หรือทำไมตัวเลือกการชำระเงินสองตัวถึงไม่มีผลกับอะไรเลยหลังกด Place Order คำถามพวกนี้ตอบจากไฟล์ไม่ได้ เพราะคำตอบอยู่ที่ว่าเว็บนี้มีไว้ทำอะไรและใครจะใช้

สามคำถามข้างบนกับดาวสองดวงนี้มีอะไรเหมือนกันอยู่ข้อเดียว: ทุกข้อคือคำตอบที่มีคนเคยตัดสินใจไว้ แล้วโค้ดเป็นแค่บันทึกของการตัดสินใจนั้น AI อ่านบันทึกได้แม่นยำมาก แต่มันอ่านการตัดสินใจไม่ได้ เพราะการตัดสินใจไม่เคยถูกเขียนลงไป และนี่คือประโยคเดียวกับที่บทเรียน 01 เปิดคอร์สไว้ในย่อหน้าเรื่อง "ส่วนที่มันไม่น่าไว้ใจคือการตัดสินใจ" — ห่างกันสามสิบสามบท ผ่านโค้ดจริงมาทั้งแอป แล้วมันยังเป็นข้อเดิม

ก่อนไปต่อ

สิ่งที่บทนี้เพิ่มเข้ามาไม่ใช่ prompt สี่อัน แต่คือลำดับการทำงานที่ใช้ซ้ำได้กับโปรเจกต์อื่น: ถามคำถามที่ตอบได้จากโค้ดล้วน ๆ → บังคับให้คำตอบมี path:บรรทัด → ยืนยันทีละข้อด้วยท่าที่ถูกที่สุดที่ตอบได้ → แก้ทีละข้อ commit แยก → จดของแถมไว้ทำรอบหน้า สี่ prompt ในบทนี้เป็นแค่ตัวอย่างที่พอดีกับแอปนี้ ถ้าคุณเปลี่ยนโปรเจกต์ prompt จะเปลี่ยน แต่ห้าก้าวนี้ไม่เปลี่ยน

และของที่ควรเก็บกลับไปข้อเดียวคือเส้นแบ่งท้ายบท: สอดคล้องกันเอง กับ ถูกต้อง เป็นคนละเรื่องกัน เครื่องมือทุกตัวที่เราติดตั้งมาตลอดคอร์ส — TypeScript, ESLint, Prettier, Vitest และตอนนี้คือ AI ที่อ่านโค้ดได้ทั้งโปรเจกต์ในนาทีเดียว — ทั้งหมดทำงานอยู่ฝั่งซ้ายของเส้นนั้น ฝั่งขวายังว่างอยู่เหมือนเดิม และคนที่ยืนอยู่ฝั่งนั้นคือคุณคนเดียว บทหน้าเรา build โปรเจกต์นี้ให้เสร็จ ดูวิธี deploy แล้วสรุปว่าตลอดสามสิบห้าบทนี้คุณได้อะไรกลับไปบ้าง
