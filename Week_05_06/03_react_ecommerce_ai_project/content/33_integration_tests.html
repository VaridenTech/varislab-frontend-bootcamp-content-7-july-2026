Integration Tests

ถึงยอดพีระมิดแล้ว: integration test ระดับทั้งหน้า คราวนี้เราไม่เรียกฟังก์ชันหรือ hook ตรง ๆ อีกต่อไป — เราจะเปิดแอปทั้งแอปขึ้นมาด้วย renderRoute ที่สร้างไว้ในบทเรียน 30 (router จริง provider จริง component จริง มีแค่ network ที่เป็น MSW) แล้วทำแบบที่ผู้ใช้ทำ: อ่านข้อความบนจอ คลิกปุ่ม พิมพ์ฟอร์ม จากนั้น assert สิ่งที่ผู้ใช้ควรเห็น เทสต์ชั้นนี้แต่ละตัวจึงพิสูจน์การประกอบร่างของทุกอย่างที่เราสร้างมาตั้งแต่บทเรียน 09 — routing, queries, context, ฟอร์ม, component — ว่าต่อติดกันจริง

ก่อนลงมือ มีเครื่องมือสองเรื่องที่ต้องเข้าใจให้เคลียร์ เพราะเทสต์ทุกตัวในบทนี้ใช้:

findBy กับ getBy — ต่างกันที่การรอ

query ของ Testing Library มีสามตระกูล เลือกใช้ตามสถานการณ์:

  • getBy... — หาเดี๋ยวนี้ ไม่เจอโยน error ทันที เหมาะกับ element ที่ต้องอยู่บนจอแล้วแน่ ๆ
  • await findBy... — หาแบบรอได้ (retry จนเจอหรือครบ timeout ~1 วินาที) เหมาะกับ element ที่จะโผล่หลังงาน async — ซึ่งในแอปเราคือ "แทบทุกอย่าง" เพราะเปิดหน้ามาจะเจอ spinner ก่อนเสมอ ระหว่างที่ TanStack Query ยิง request ไป MSW ข้อมูลถึงจะมา
  • queryBy... — หาแล้วคืน null ถ้าไม่เจอ (ไม่โยน error) มีไว้สำหรับ assert ว่าอะไรไม่อยู่บนจอ

กฎหัวแม่มือของบทนี้: หลัง render หรือหลัง action ที่ทำให้เกิดการยิง API — ใช้ findBy ตัวแรกเป็น "ประตูรอ" ให้หน้าโหลดเสร็จ หลังจากนั้นของที่อยู่บนจอแล้วใช้ getBy ได้เลย

สังเกตว่านี่คือปัญหาเดียวกับ waitFor ในบทที่แล้ว แค่เปลี่ยนรูป: findBy คือ waitFor ที่ผูกกับการค้นหา element และคำถามเดิมยังใช้ได้ทั้งดุ้น — เรารออะไรอยู่ การรอ "ข้อความของสินค้าชิ้นแรก" กับการรอ "spinner หายไป" เป็นการรับประกันคนละอย่างกัน และอย่างหลังผ่านได้แม้ข้อมูลจะไม่มาเลย

user-event ไม่ใช่ fireEvent

Testing Library มี fireEvent ที่ยิง DOM event ดิบ ๆ ทีละลูก แต่เราจะใช้ user-event ทั้งบท เพราะมันจำลองพฤติกรรมผู้ใช้ทั้งลำดับ: การคลิกหนึ่งครั้งของ user-event คือ pointer move → pointer down → focus → pointer up → click และการพิมพ์คือ keydown/keypress/keyup ทีละตัวอักษร ผลคือมันเจอ bug ที่ fireEvent มองข้าม เช่น ปุ่มที่ถูก disabled หรือ input ที่อ่านค่าจาก keyboard event — user-event จะคลิกปุ่ม disabled ไม่ได้เหมือนผู้ใช้จริงนั่นแหละ ท่าใช้มาตรฐานคือ const user = userEvent.setup() ต้นเทสต์ แล้ว await ทุกการกระทำ (ทุก method ของมันเป็น async)

ข้อที่ว่า "คลิกปุ่ม disabled ไม่ได้" มีน้ำหนักเป็นพิเศษในโปรเจกต์นี้ เพราะบทเรียน 24 ให้ปุ่มลดจำนวนมี disabled={item.quantity <= 1} ติดอยู่ — ถ้าเราใช้ fireEvent.click เทสต์จะกดปุ่มนั้นได้ทั้งที่ผู้ใช้จริงกดไม่ได้ แล้วเราจะได้เทสต์ที่พิสูจน์พฤติกรรมที่ไม่มีทางเกิดขึ้นจริง

✍️ ส่วนนี้พิมพ์เอง

บทเรียน 31 บอกไว้แล้วว่าไฟล์เทสต์อยู่ปลายสายเสมอ ไม่มีอะไร import มัน — ข้อนั้นยังจริงในบทนี้ แต่คราวนี้มีสายการพึ่งพาในไฟล์เดียวกันโผล่มาแทน และมันชี้ไปทางเดียวกับกฎเดิมเป๊ะ: เคสที่ Agent จะเขียนต่อ ไม่ได้อยู่เดี่ยว ๆ มันเรียก seedCart() และใช้ renderRoute กับ screen ที่ import ไว้ด้านบนของไฟล์

ไล่ดูว่าใครพึ่งใครใน Cart.test.tsx ฉบับสมบูรณ์:

  • บรรทัด import สี่บรรทัด และฟังก์ชัน seedCart — ไม่พึ่งอะไรในไฟล์เลย

  • เคส "updates quantity and total" — พึ่ง seedCart, renderRoute, screen และ userEvent ครบทุกตัว

ทางเดียวที่จะให้เคสของ Agent มีของครบตอนที่มันเขียน คือเราต้องพิมพ์หัวไฟล์กับ seedCart ให้เสร็จก่อน ถ้าเราให้มันสร้างทั้งไฟล์แล้วสั่งว่า "ห้ามเขียนเคสปรับจำนวน" สิ่งที่พังไม่ใช่เคสที่เราตัดออก (มันไม่มีอยู่ ก็ไม่มีอะไรให้พัง) แต่คือเคส "removes an item" ที่เรียก seedCart() ซึ่งไม่มีใครประกาศ — typecheck ตายที่บรรทัดนั้น นี่คือกฎเดิมจากบทเรียน 12 และ 22 ในรูปย่อส่วน: สิ่งที่พังคือตัวที่พึ่งพา ไม่ใช่ตัวที่ถูกตัด

และเคสที่เลือกให้พิมพ์เองก็ไม่ได้เลือกเพราะมันอยู่ตรงกลาง แต่เพราะมันเป็นเคสเดียวในสามเคสที่พิสูจน์ตัวเลขที่ถูกคำนวณใหม่ — กด > หนึ่งครั้งแล้วยอดต้องขยับจาก $10.00 เป็น $20.00 ซึ่งต้องผ่าน reducer, context, useMemo และ toFixed(2) ครบทั้งสาย อีกสองเคสพิสูจน์แค่ว่าข้อความหนึ่งก้อนโผล่หรือหายไป ซึ่งเขียนให้ผ่านโดยไม่ได้พิสูจน์อะไรได้ง่ายกว่ามาก

src/pages/Cart/Cart.test.tsx (ยังไม่ครบไฟล์ — Agent จะเติมอีกสองเคส):

import { screen } from "@testing-library/react";
import userEvent from "@testing-library/user-event";
import { CART_STORAGE_KEY } from "@/features/cart/store/cartStorage";
import { renderRoute } from "@/test/renderRoute";

function seedCart() {
  localStorage.setItem(
    CART_STORAGE_KEY,
    JSON.stringify({
      items: [
        { id: 1, title: "Widget", price: 10, quantity: 1, image: "/w.png" },
      ],
    }),
  );
}

describe("Cart page", () => {
  it("updates quantity and total", async () => {
    const user = userEvent.setup();
    seedCart();
    renderRoute("/cart");

    expect(await screen.findByText("Widget")).toBeInTheDocument();
    expect(screen.getByText("Total Price: $10.00")).toBeInTheDocument();

    await user.click(screen.getByRole("button", { name: ">" }));
    expect(screen.getByText("Total Price: $20.00")).toBeInTheDocument();
  });
});

เหตุผล: integration test คือที่ที่ AI เขียน "ผ่านแต่ไม่ได้พิสูจน์อะไร" ได้ง่ายที่สุด เพราะหน้าจอมีของเยอะ และอะไรก็ตามที่โผล่บนจอใช้เป็น assertion ได้หมด เทสต์ที่เขียนว่า expect(await screen.findByText("Cart")).toBeInTheDocument() จะผ่านตลอดกาลเพราะคำว่า Cart อยู่ใน CategoryBanner ที่ render ทั้งสองกิ่งของหน้า — ทั้งตอนตะกร้ามีของและตอนตะกร้าว่าง เคสที่คุณเพิ่งพิมพ์ต่างออกไปตรงที่มันบังคับให้ค่าบนจอเปลี่ยนเพราะการกระทำของผู้ใช้ ซึ่งเป็นเงื่อนไขที่โกงไม่ได้ ห้าบรรทัดในตัวเคสมีการตัดสินใจของคนอยู่สี่จุดที่ Agent ไม่มีทางเดาถูกครบ: การเลือกใช้ findByText เป็นประตูรอแล้วสลับเป็น getByText หลังจากนั้น, การเลือกหาปุ่มด้วย getByRole แทน CSS selector, การเขียนยอดเงินเต็ม ๆ ทั้ง $10.00 และ $20.00 แทนที่จะเช็คแค่ว่ามีเลข 20 อยู่ที่ไหนสักที่บนจอ และการรู้ว่า await user.click คืนค่ามาแล้ว React ประมวลผลเสร็จแล้ว จึงไม่ต้อง await ซ้ำในบรรทัดถัดไป ถ้าคุณไม่เคยลากเส้นสี่เส้นนี้เอง คุณจะไม่มีอะไรในหัวไว้เทียบตอนอ่านเคสที่ Agent เขียนให้ในอีกไม่กี่นาที

ไล่ตาม flow แล้วนับดูว่าเทสต์เดียวนี้แตะกี่ระบบ:

  • พิมพ์สามช่องด้วย user.type — หา input จาก placeholder (ข้อความเดียวกับที่ผู้ใช้ใช้หาช่องกรอกนั่นแหละ) แล้วกด Submit — จังหวะนี้ react-hook-form + zodResolver ทำงานจริง: ถ้าข้อมูลไม่ผ่าน schema ฟอร์มจะไม่ submit และ storeCheckoutAddress ไม่ถูกเรียก (อยากเห็นกับตา ลองแก้อีเมลเป็น "nope" แล้วดูเทสต์พังตรง Place Order) และสังเกตว่าการพิมพ์ทีละตัวอักษรแบบนี้คือสิ่งที่จับบั๊ก value={...} ที่แถมมากับ register ในบทเรียน 26 ได้ — ช่องที่เป็น controlled แบบค่าไม่มีวันเปลี่ยนจะรับตัวอักษรไม่ได้เลย
  • ปุ่ม Place Order หาแบบ regex — { name: /place order/i } คือ case-insensitive match กันเหนียวเรื่องตัวพิมพ์/การจัดรูปข้อความในปุ่ม
  • assert การ navigate ด้วย router ที่ renderRoute คืนมา — นี่คือเหตุผลที่บทเรียน 30 ให้ helper คืน router ออกมาด้วย: หลัง mutation สำเร็จ (MSW ตอบ 201 ที่ POST /carts/add) → onSuccess ล้างตะกร้าแล้ว goToOrderSuccess() — เราใช้ waitFor รอจน router.state.location.pathname เป็น /order/success แล้วปิดท้ายด้วยการเช็คว่าหน้า Order Success render ข้อความจริงบนจอ ไม่ใช่แค่ URL เปลี่ยน

เทสต์ตัวเดียวนี้ครอบคลุม: routing, seed ตะกร้าจาก localStorage, ฟอร์ม + validation, cart context, mutation, axios + interceptor, MSW และการ navigate — ถ้ามันเขียว แปลว่า flow ที่สำคัญที่สุดของธุรกิจ (การจ่ายเงิน!) ต่อกันครบทั้งเส้น

  • Integration (6 tests) — จับ bug ในการประกอบร่างที่ผู้ใช้เจอจริง: route ที่หลุด, provider ที่ลืมห่อ, ปุ่มที่กดแล้วเงียบ, ข้อความที่ถูกเปลี่ยนถ้อยคำ แลกกับความช้ากว่าและเวลาพังต้องไล่หาต้นเหตุไกลกว่า
