บทเรียน 25 · ชำระเงิน (Checkout)

Zod Schema และโครงข้อมูล Checkout

Checkout Schema

ตะกร้าสินค้าของเราสมบูรณ์แล้วจากบทเรียน 24 — เพิ่มของได้ ลบได้ ปรับจำนวนได้ และจำของไว้ใน localStorage ได้ ตอนนี้เหลือด่านสุดท้ายของขาช้อป: Checkout ซึ่งเราจะใช้เวลา 4 บท (บทนี้ถึงบทเรียน 28) สร้างตั้งแต่ฐานข้อมูลของฟีเจอร์ ฟอร์มที่อยู่ ตัวเลือกจัดส่ง/ชำระเงิน สรุปยอด ไปจนถึงการยิงคำสั่งซื้อจริงและหน้า Order Success

แผนของทั้ง chapter เป็นแบบนี้:

  1. บทนี้ — วางรากฐานข้อมูล: zod schema สำหรับ validate ที่อยู่, types และรายการตัวเลือกจัดส่ง/ชำระเงิน
  2. บทเรียน 26 — ฟอร์มที่อยู่ด้วย react-hook-form
  3. บทเรียน 27 — คอมโพเนนต์ตัวเลือกจัดส่ง ชำระเงิน และสรุปคำสั่งซื้อ เจ็ดตัวรวด
  4. บทเรียน 28 — hook useCheckout, ประกอบหน้า Checkout ทั้งหน้า และสั่งซื้อจริง

และบทนี้เป็นบทที่กลับมาพิมพ์เองอีกครั้ง ห่างจากครั้งก่อน (cartReducer.ts ในบทเรียน 22) มาสามบท ไฟล์ที่จะพิมพ์คือ schema.ts — สั้นกว่า reducer มาก แต่มีที่ทางในลำดับงานที่ต่างจากทุกครั้งที่ผ่านมา เดี๋ยวเราจะไล่เหตุผลกันหลังจากคุยเรื่องแนวคิดจบ

คิดจาก "ข้อมูล" ก่อน "หน้าตา"

สังเกตว่าเราไม่ได้เริ่ม chapter นี้ด้วยการเขียน JSX ของฟอร์ม แต่เริ่มด้วยคำถามว่าข้อมูลของการ checkout หน้าตาเป็นอย่างไร — ที่อยู่จัดส่งต้องมี field อะไรบ้าง แต่ละ field มีเงื่อนไขอะไร ตัวเลือกจัดส่งมีกี่แบบ ราคาเท่าไร วิธีนี้เรียกกันว่า schema-first: นิยามรูปร่างและกติกาของข้อมูลให้ชัดก่อน แล้วค่อยให้ UI มาเกาะกับมันทีหลัง

เครื่องมือหลักของเราคือ zod — library สำหรับประกาศ schema ของข้อมูลใน TypeScript จุดที่ทำให้ zod เป็นที่นิยมมากคือ schema เดียวให้ของสองอย่างพร้อมกัน:

  • Runtime validation — ตอนผู้ใช้กด submit เราเอาข้อมูลจริงมาตรวจกับ schema ได้ พร้อมข้อความ error ของแต่ละ field
  • TypeScript type — ใช้ z.infer สกัด type ออกมาจาก schema ได้เลย ไม่ต้องประกาศ interface ซ้ำอีกรอบ

ลองนึกภาพทางเลือกอีกทาง: เขียน interface CheckoutAddressFormData ด้วยมือหนึ่งชุด แล้วเขียนฟังก์ชัน validate ด้วยมืออีกชุด — วันหนึ่งมีคนเพิ่ม field ใหม่ใน interface แต่ลืมแก้ตัว validate (หรือกลับกัน) สองที่นี้ก็จะเหลื่อมกัน (drift) โดยไม่มีใครเตือน กับ zod ปัญหานี้หายไปทั้งก้อน เพราะทั้ง type และ validation งอกจากแหล่งเดียวกัน แก้ schema ที่เดียว ทุกอย่างขยับตามอัตโนมัติ

จำย่อหน้าข้างบนไว้ให้แม่น เพราะมันคือสิ่งที่ Agent พลาดบ่อยที่สุดในบทนี้ และเป็นเหตุผลที่กล่อง ✅ ท้ายบทมีข้อ grep รออยู่

ติดตั้งแพ็กเกจด้วยมือ

ตามกติกาเดิมตั้งแต่บทเรียน 08: dependency เราติดตั้งเอง แล้ว commit ให้ working tree สะอาดก่อนเปิดแชท คราวนี้มีสามตัวและลงพร้อมกันได้เลย:

npm install zod react-hook-form @hookform/resolvers
git add -A && git commit -m "chore: install zod and react-hook-form"
  • zod — ตัวประกาศ schema และ validate ที่เพิ่งเล่าไป (เราใช้ zod 4)
  • react-hook-form — library จัดการฟอร์มที่เราจะใช้เต็ม ๆ ในบทหน้า
  • @hookform/resolvers — สะพานเชื่อมระหว่างสองตัวแรก ทำให้ react-hook-form เรียก zod schema มา validate ให้อัตโนมัติ

ทั้งสามตัวถูกออกแบบมาทำงานด้วยกันจนแทบเป็นชุดมาตรฐานของฟอร์มในโปรเจกต์ React ปัจจุบัน — เจอ combo นี้ที่ไหนให้รู้ว่าคือ "ฟอร์มที่ validate จริงจัง"

เปิด package.json ดูสักครู่ก่อนไปต่อ แล้วยืนยันว่าเลขเวอร์ชันของ zod ขึ้นต้นด้วย 4 — ทั้งบทนี้และเอกสารที่เราจะอ้างถึงใช้ API ของ zod 4 ถ้าวันที่คุณเรียน npm ให้ zod 5 มา ให้อ่าน changelog ก่อนแล้วเทียบกับโค้ดในบทนี้ อย่าเพิ่งพิมพ์ตาม

ทำไมบทนี้ ✍️ ถึงมาก่อน 🤖

กฎที่เราได้จากบทเรียน 12 คือ: สิ่งที่พังเมื่อคุณตัดไฟล์ X ออกจาก prompt คือไฟล์ที่ import X ไม่ใช่ตัว X เอง เอากฎนี้มาจับกับสามไฟล์ของบทนี้ แล้วไล่สายการพึ่งพาดู:

  • schema.ts — import แค่ zod ไม่ import ไฟล์ไหนในโปรเจกต์เลย
  • types.ts — ไม่มีบรรทัด import เลยสักบรรทัด
  • consts.ts — import สอง interface จาก ./types

ผลที่ได้ต่างจากทุกบทที่ผ่านมา: ไม่มีไฟล์ไหนในบทนี้ import ไฟล์ที่เราจะพิมพ์เอง schema.ts เป็นเกาะกลางบท ตัดออกจาก prompt กี่รอบก็ไม่มีอะไรพัง และพิมพ์ก่อนหรือหลังก็ typecheck ผ่านทั้งคู่ (ขอแค่ zod ถูกติดตั้งแล้ว ซึ่งเราเพิ่งทำไปเมื่อครู่) เทียบกับสามครั้งก่อน: บทเรียน 12 ลูกศรบังคับให้พิมพ์ก่อน, บทเรียน 15 ลูกศรชี้กลับด้านจึงต้อง 🤖 ก่อน, บทเรียน 22 ไฟล์อยู่กลางสายจนต้องผ่า prompt เป็นสองรอบแล้วเสียบมือเข้าตรงรอยตัด คราวนี้ลูกศรไม่ได้บอกอะไรเราเลย

เมื่อการคอมไพล์ไม่ตัดสินให้ ก็ต้องหาเกณฑ์อื่น และเกณฑ์นั้นคือ Agent จะได้เห็นอะไรตอนมันทำงาน:

  • ถ้าพิมพ์ทีหลัง — ตอน Agent สร้าง types.ts ไฟล์ schema.ts ยังไม่มีตัวตน สิ่งที่มันเห็นคือโฟลเดอร์ features/checkout/ ที่ว่างเปล่ากับคำสั่งว่า "ประกาศ type ของฟีเจอร์ checkout" — โมเดลที่เจอโจทย์แบบนี้จะเติม type ของที่อยู่ให้ด้วยความหวังดี เพราะฟีเจอร์ checkout ก็ต้องมีที่อยู่สิ ผลคือได้ interface ที่ซ้ำกับ schema แบบเป๊ะ ๆ หนึ่งชุด
  • ถ้าพิมพ์ก่อน — schema.ts มีอยู่จริงและ commit แล้ว บรรทัด บริบท: จึง @-mention มันได้ Agent เห็นกับตาว่า CheckoutAddressFormData มีอยู่แล้วและมาจาก z.infer และเราสั่งห้ามประกาศซ้ำได้อย่างมีน้ำหนัก

สรุปคือลำดับของบทนี้ถูกตัดสินด้วยบริบทที่ Agent มองเห็น ไม่ใช่ด้วยลำดับการคอมไพล์ — เป็นเกณฑ์ที่สี่ที่คอร์สนี้ใช้ ต่อจากลูกศรที่ชี้ไปข้างหน้า (บทเรียน 12 และ 17), ลูกศรที่ชี้กลับด้าน (บทเรียน 15) และไฟล์ที่อยู่กลางสาย (บทเรียน 22) และเป็นเกณฑ์ที่คุณจะต้องหยิบมาใช้เองบ่อย เพราะไฟล์จำนวนมากในโปรเจกต์จริงไม่ได้ผูกกันแน่นพอที่การคอมไพล์จะตัดสินลำดับให้

เป้าหมายของบทนี้

สามไฟล์ทั้งหมดลงในโฟลเดอร์ src/features/checkout/ ที่เรา mkdir ทิ้งไว้ตั้งแต่บทเรียน 05 แล้วปล่อยให้ว่างเปล่ามายี่สิบบท — วันนี้เป็นวันที่มันได้ผู้อาศัยรายแรก:

src/
└── features/
    └── checkout/
        ├── schema.ts    # ✍️ พิมพ์เอง — ก่อนเปิดแชท
        ├── types.ts     # 🤖
        └── consts.ts    # 🤖

สัญญาที่แต่ละไฟล์ต้องทำให้ได้ — และสิ่งที่มันต้องไม่ทำ:

  • schema.ts — ต้องเป็นแหล่งเดียวของกติกาที่อยู่จัดส่ง ทั้งข้อความ error และ type ต้องออกมาจากไฟล์นี้ ต้องไม่ import อะไรนอกจาก zod และต้องไม่มีการประกาศ interface ด้วยมือ
  • types.ts — ต้องประกาศรูปร่างของตัวเลือกจัดส่งและตัวเลือกชำระเงินเท่านั้น ต้องไม่รู้จักที่อยู่ ไม่รู้จัก zod และต้องไม่มีบรรทัด import เลย
  • consts.ts — ต้องเป็นที่เดียวที่รายการตัวเลือกจริงถูกเขียนไว้ ต้องผูก type จาก types.ts และต้องไม่มีตัวเลือกไหนถูก hardcode ซ้ำในคอมโพเนนต์ภายหลัง

✍️ ส่วนนี้พิมพ์เอง

✍️ ส่วนนี้พิมพ์เอง — ทำตามลำดับนี้ ห้ามก๊อปวาง ห้ามให้ Agent ช่วยเติม (autocomplete ของ Cursor ที่เด้งขึ้นมาแล้วคุณกด Tab รับ ก็คือการก๊อป):

  1. ยืนยันว่า commit ของการติดตั้งแพ็กเกจผ่านไปแล้ว — git status ต้องสะอาด
  2. พิมพ์ src/features/checkout/schema.ts ทั้งไฟล์ ระหว่างพิมพ์ให้หยุดถามตัวเองทุกครั้งที่เจอข้อความใน "" ว่า ผู้ใช้จะเห็นข้อความนี้ตอนไหน
  3. npm run lint และ npm run typecheck ให้ผ่านทั้งคู่ แล้ว git commit — ไฟล์ต้องมีอยู่จริงและถูก commit ก่อน ถึงจะ @-mention มันใน prompt ได้

src/features/checkout/schema.ts:

import { z } from "zod";

export const checkoutAddressSchema = z.object({
  address: z.string().min(1, "Address is required"),
  email: z
    .string()
    .min(1, "Email is required")
    .pipe(z.email("Enter a valid email address")),
  phone: z.string().min(1, "Phone number is required"),
});

export type CheckoutAddressFormData = z.infer<typeof checkoutAddressSchema>;

เหตุผล: schema คือกติกาทางธุรกิจ ไม่ใช่ boilerplate — สิบสามบรรทัดนี้ตอบคำถามที่ไม่มีใครตอบแทนคุณได้: ที่อยู่ต้องกรอกอะไรบ้าง, เบอร์โทรต้องตรวจรูปแบบไหม, ผู้ใช้ที่ปล่อยช่อง email ว่างควรเห็นข้อความว่าอะไร ทุกข้อคือการตัดสินใจของ product ที่มีคนได้-เสียจริง Agent ตอบข้อพวกนี้ให้คุณได้เสมอและตอบได้อย่างมั่นใจมากด้วย — แต่มันจะตอบจากค่าเฉลี่ยของฟอร์มทั้งอินเทอร์เน็ต ไม่ใช่จากแอปของคุณ และข้อความสามข้อในไฟล์นี้จะถูก assert ตรง ๆ ในเทสต์บทเรียน 31 อีกด้วย

ไล่ดูทีละ field:

  • address — z.string().min(1, "Address is required") คือ "ต้องเป็น string และยาวอย่างน้อย 1 ตัวอักษร" พูดง่าย ๆ คือห้ามเว้นว่าง argument ตัวที่สองคือข้อความ error ที่จะโผล่ใต้ input ถ้าไม่ผ่าน
  • email — ตัวนี้มีสองด่านต่อกัน เดี๋ยวขยายความด้านล่าง
  • phone — เช็คแค่ห้ามว่างเหมือน address เราตั้งใจไม่เช็ครูปแบบเบอร์โทร เพราะรูปแบบเบอร์แต่ละประเทศต่างกันมาก และนี่คือ checkout จำลอง — กติกาแค่ไหนถึงพอดี เป็นการตัดสินใจของ product ไม่ใช่ของ library

สองด่านของ email: .min(1) แล้ว .pipe(z.email())

.pipe() คือการต่อท่อ schema สองตัวเข้าด้วยกัน: ข้อมูลต้องผ่านด่านแรกก่อน แล้วผลลัพธ์ถึงจะไหลเข้าด่านถัดไป เหตุผลที่เราไม่เขียน z.email() เดี่ยว ๆ คือคุณภาพของข้อความ error — ถ้าผู้ใช้ปล่อย email ว่างไว้ การบอกว่า "Enter a valid email address" มันแปลก ๆ (เขายังไม่ได้กรอกอะไรเลย!) เราอยากได้ "Email is required" ต่างหาก การต่อท่อทำให้แต่ละกรณีได้ข้อความที่ตรง:

  • ปล่อยว่าง → ตกด่าน .min(1) → "Email is required"
  • กรอกแต่ไม่ใช่รูปแบบ email เช่น hi → ผ่านด่านแรก ตกด่าน z.email() → "Enter a valid email address"
⚠️ สังเกตว่าเราเขียน z.email() เป็นฟังก์ชันระดับบนสุด — นี่คือ API ของ zod 4 ถ้าคุณไปเจอบทความหรือโค้ดเก่าที่เขียน z.string().email() นั่นคือท่าของ zod 3 ซึ่งใน zod 4 ถูก deprecated แล้ว อ่านเอกสารหรือตัวอย่างจากที่ไหนก็ตาม เช็คเวอร์ชันก่อนเสมอ — และข้อนี้ใช้กับคำตอบของ Agent ด้วย: ข้อมูลที่โมเดลเห็นตอนเทรนมี zod 3 มากกว่า zod 4 หลายเท่า ถ้าคุณเผลอให้มันเขียนไฟล์นี้ ท่า z.string().email() คือสิ่งที่คุณมีโอกาสได้กลับมาสูงที่สุด

z.infer — type ที่งอกจาก schema

บรรทัดสุดท้ายคือหัวใจของ schema-first:

export type CheckoutAddressFormData = z.infer<typeof checkoutAddressSchema>;

z.infer อ่าน schema แล้วสกัด TypeScript type ออกมาให้ ผลลัพธ์ของบรรทัดนี้เทียบเท่ากับการเขียน { address: string; email: string; phone: string } ด้วยมือ แต่ต่างกันตรงที่มันคำนวณมาจาก schema — พรุ่งนี้ถ้าเราเพิ่ม field postcode เข้าไปใน z.object({...}) type นี้จะมี postcode ทันที และ TypeScript จะไล่ฟ้องทุกไฟล์ที่ใช้ type นี้แล้วยังไม่รองรับ field ใหม่ให้เราเอง type นี้จะถูกใช้ทั่วทั้ง chapter: เป็น type ของฟอร์มในบทหน้า, เป็น state ใน useCheckout, และเป็นส่วนหนึ่งของ payload ตอนสั่งซื้อในบทเรียน 28

อยากเห็น validation ทำงานตอนนี้เลย ลองนึกภาพ (หรือทดลองใน scratch file ก็ได้ ไม่ต้องเก็บไว้ในโปรเจกต์):

// ตัวอย่างประกอบ — ไม่ต้องสร้างเป็นไฟล์ในโปรเจกต์
const result = checkoutAddressSchema.safeParse({
  address: "",
  email: "hi",
  phone: "",
});
// result.success === false และใน result.error จะพบว่า
// address → "Address is required"
// email   → "Enter a valid email address"
// phone   → "Phone number is required"

safeParse คืนผลเป็น object ที่มี success บอกผ่าน/ไม่ผ่าน โดยไม่ throw — ในบทหน้าเราไม่ต้องเรียกมันเองด้วยซ้ำ เพราะ zodResolver จะจัดการรอบ validate ทั้งหมดให้ แล้วส่งข้อความ error ไปโผล่ใต้ input ที่ถูกต้องเอง ส่วนตัว safeParse เองจะกลับมาอีกครั้งในบทเรียน 31 ตอนที่เราเขียน unit test ให้ schema ตัวนี้โดยตรง — เทสต์ที่ไม่ต้อง render อะไรเลย เพราะไฟล์นี้ไม่รู้จัก React

✅ ตรวจโค้ดที่ AI สร้าง

✅ ตรวจโค้ดที่ AI สร้าง — git status และ git diff ก่อน แล้วไล่ทีละข้อ ข้อแรกคือข้อที่ทั้งบทนี้ถูกจัดลำดับมาเพื่อกันมันโดยเฉพาะ:

  • AI มักพลาดตรงนี้: ประกาศ interface ของที่อยู่ซ้ำใน types.ts — โจทย์ว่า "ประกาศ type ของฟีเจอร์ checkout" กับไฟล์ชื่อ types.ts เป็นคู่ที่ชวนให้ Agent เติมของให้ครบชุด สิ่งที่ได้กลับมาคือ export interface CheckoutAddressFormData { address: string; email: string; phone: string; } (หรือชื่อใกล้ ๆ อย่าง CheckoutAddress) นั่งอยู่ใต้สอง interface ที่เราสั่ง — ถูกทุกตัวอักษรและอันตรายที่สุดในบทนี้ เพราะวันที่เราเพิ่ม postcode ลง schema type ที่ z.infer ให้จะขยับเอง ส่วนสำเนาที่เขียนมือจะค้างอยู่ที่เดิม แล้วโค้ดครึ่งแอปที่ import ผิดตัวจะเชื่อว่าที่อยู่ไม่มี postcode ต่อไปโดย lint และ typecheck ไม่ปริปากสักคำ วิธีตรวจ: grep -n "address\|email\|phone" src/features/checkout/types.ts ต้องว่างเปล่า และ grep -rn "CheckoutAddressFormData" src/features/checkout/ ต้องเจอบรรทัดเดียว คือบรรทัด z.infer ใน schema.ts ที่คุณพิมพ์เอง อาการญาติที่เจอรองลงมาคือ Agent เขียน export type { CheckoutAddressFormData } from "./schema"; ใน types.ts เพื่อ "รวม type ไว้ที่เดียว" — ไม่ drift ก็จริง แต่สร้างทางเข้าที่สองให้ของชิ้นเดียว แล้วบทถัดไปจะมีสองไฟล์ให้เลือก import ซึ่งคนละครึ่งทีมจะเลือกคนละทาง
  • ไฟล์ใหม่ 2 ไฟล์พอดี และ git status ต้องไม่มีไฟล์เดิมไฟล์ไหนขึ้นสถานะ modified — โดยเฉพาะ schema.ts ที่คุณเพิ่งพิมพ์ และ package.json (ถ้า package.json หรือ package-lock.json เปลี่ยน แปลว่า Agent ลงแพ็กเกจอะไรบางอย่างโดยไม่ได้บอก — อ่านให้ออกว่าอะไรก่อนกด accept)
  • grep -c "import" src/features/checkout/types.ts ต้องได้ 0 — ไฟล์นี้ต้องเป็นเกาะที่ไม่พึ่งใครเลย ถ้ามันไป import Product จาก features/products/types.ts มาใช้ต่อ (Agent ที่เห็นไฟล์นั้นในบริบทชอบทำ) ให้เอาออก — ตัวเลือกจัดส่งไม่ใช่สินค้า
  • ไม่มี ? ในทั้งสอง interface — ทุก field บังคับกรอก เพราะเราเขียนค่าเองในไฟล์ถัดไปอยู่แล้ว ไม่มีเหตุผลที่ field ไหนจะหายได้
  • บรรทัด import ใน consts.ts เป็น from "./types" ไม่ใช่ from "@/features/checkout/types" — สองแบบทำงานเหมือนกันเป๊ะ เราเลือกแบบสัมพัทธ์ตามที่ไฟล์ในโฟลเดอร์เดียวกันทำกันมาตั้งแต่ features/cart/store/ บทเรียน 22 ข้อนี้ไม่มีอะไรพังถ้าผิด แต่ diff ของคุณจะไม่ตรงกับโค้ดอ้างอิง
  • ค่า id เป็น 1, 2, 3, 4 ตามลำดับจริง ไม่ใช่ 1, 2 แล้วขึ้น 1, 2 ใหม่ฝั่ง payment — Agent เกือบทุกตัวจะ "แก้ให้" ตรงนี้เพราะมันดูเหมือนความผิดพลาด (เหตุผลที่ต้นฉบับเป็นแบบนี้อยู่ในกล่อง 💡 ใต้ consts.ts) ถ้ามันเริ่มใหม่ที่ 1 วันนี้ไม่มีอะไรพัง แต่ค่า default ใน useCheckout บทเรียน 28 จะชี้ไปคนละตัวกับที่บทนั้นอธิบายไว้
  • ราคาเป็น 5.99 และ 15.99 แบบ number เปล่า ๆ ไม่ใช่ "$5.99" และไม่ใช่ 599 (สตางค์) — ทั้งแอปคิดเงินเป็นหน่วยดอลลาร์ทศนิยมสองตำแหน่งมาตั้งแต่ CartItem.price บทเรียน 22 ปนหน่วยเมื่อไหร่ยอดรวมใน BillingSummary จะเพี้ยนแบบไม่มีใครสังเกต
  • ข้อความทั้งหกก้อนตรงตัวอักษร โดยเฉพาะ "Approx 1 - 2 Days" ที่มีเว้นวรรคคร่อมขีด ต่างจาก "Approx 5 to 7 Days" ที่ใช้คำว่า to — ไม่สม่ำเสมอตั้งแต่ต้นฉบับ และ Agent จะจัดให้เข้าชุดกันโดยอัตโนมัติถ้าเราไม่ห้าม ไม่มีเทสต์ตัวไหนแตะข้อความพวกนี้ เหตุผลเดียวที่ต้องตรงคือให้ diff ของคุณเทียบกับโค้ดอ้างอิงได้
  • ไม่มี as const ไม่มี enum และไม่มี comment สักบรรทัดในทั้งสองไฟล์ — grep -n "//" src/features/checkout/consts.ts ต้องว่างเปล่า
  • npm run lint และ npm run typecheck ผ่านทั้งคู่ บทนี้มีบรรทัด import แค่บรรทัดเดียวในทั้งสองไฟล์ import-x/order จึงไม่มีอะไรให้จัดเรียง ถ้า lint ตกในบทนี้ ให้อ่าน error จริง ๆ อย่าเพิ่งรีบ --fix
  • เปิดหน้าเว็บดูก็ได้ แต่ต้องไม่มีอะไรเปลี่ยน — บทนี้ไม่มีใคร import สามไฟล์นี้เลยสักคน grep -rn "features/checkout" src/pages src/shared src/app ต้องว่างเปล่า

โค้ดอ้างอิง

src/features/checkout/types.ts — รูปร่างของตัวเลือกจัดส่งและการชำระเงิน:

export interface DeliveryOption {
  id: number;
  name: string;
  description: string;
  price: number;
  estimatedTime: string;
}

export interface PaymentOption {
  id: number;
  name: string;
  description: string;
}

คำถามที่ควรถาม: ทำไมสองตัวนี้เป็น interface ธรรมดา ไม่เป็น zod schema เหมือนที่อยู่? เพราะ zod มีไว้ validate ข้อมูลที่ไหลเข้ามาจากภายนอกซึ่งเราการันตีอะไรไม่ได้ — ข้อมูลที่ผู้ใช้พิมพ์, ข้อมูลจาก API แต่รายการตัวเลือกจัดส่ง/ชำระเงินคือค่าคงที่ที่เราเขียนเองกับมือในไฟล์ถัดไป TypeScript ตรวจมันตอน compile ได้ครบถ้วนอยู่แล้ว การเอา zod มาตรวจค่าที่เราพิมพ์เองอีกรอบตอน runtime ไม่ได้เพิ่มความปลอดภัยอะไร ใช้เครื่องมือให้ตรงงาน: zod สำหรับข้อมูลเชื่อถือไม่ได้ interface สำหรับข้อมูลที่เราควบคุมเอง

💡 ของที่ควรถูกทักในรีวิว — สองข้อในไฟล์สิบสามบรรทัด: ข้อแรกคือ estimatedTime ซึ่งเป็น field บังคับที่ไม่มีใครอ่านเลยสักคนตลอดทั้งแอป ลอง grep -rn "estimatedTime" src/ หลังจบบทเรียน 28 ดู — จะเจอสองที่คือบรรทัดที่ประกาศมันใน types.ts กับค่าที่กรอกไว้ใน consts.ts ไม่มีคอมโพเนนต์ไหนแตะ (CheckoutDeliveryBox ในบทเรียน 27 destructure แค่ { id, name, description } ส่วน useCheckout ในบทเรียน 28 อ่านแค่ price) ซ้ำร้ายค่าของมันยังซ้ำกับ description อยู่แล้ว — "5-7 Days" กับ "Approx 5 to 7 Days" คือข้อมูลเดียวกันสองสำนวน วันที่ธุรกิจเปลี่ยนเวลาจัดส่ง คนแก้จะแก้ที่เดียวแล้วอีกที่ค้างไว้ตลอดกาลโดยไม่มีใครรู้เพราะไม่มีใครแสดงมัน field ที่ไม่มีใครใช้คือของที่ควรถูกลบในรีวิว ไม่ใช่ของที่ควรลอกตาม เราสั่งให้ Agent สร้างตามต้นฉบับเพื่อให้ diff ตรง แต่ในรีวิวจริงนี่คือ comment บรรทัดเดียว ข้อสองมองไม่เห็นวันนี้แต่จะมาเจ็บในบทเรียน 27: ชื่อ DeliveryOption กับ PaymentOption ที่เราตั้งให้ type จะไปชนกับชื่อคอมโพเนนต์ที่ต้องสร้างในบทนั้นพอดี ผลคือ CheckoutDeliveryBox ต้องเขียน import { DeliveryOption as TDeliveryOption } เพื่อเลี่ยงชื่อชนกันเอง ถ้าเราตั้งชื่อ type ว่า DeliveryOptionData ตั้งแต่วันนี้ ปัญหานั้นจะไม่เกิดเลย — การตั้งชื่อในไฟล์ที่ยังไม่มีใครใช้ คือหนี้ที่ออกใบแจ้งหนี้ในอีกสองบทข้างหน้าเสมอ

💡 ของที่ควรถูกทักในรีวิว: paymentOptions เริ่มนับ id ที่ 3 ไล่ต่อจาก deliveryOptions ที่จบไว้ที่ 2 — สอง array นี้ไม่มีความเกี่ยวข้องกันเลย ไม่เคยถูกรวมร่าง ไม่เคยถูกเทียบ id ข้ามฝั่ง แต่ละอันมี useState ของตัวเองใน useCheckout บทเรียน 28 การใช้เลขต่อกันแบบนี้จึงสื่อความเป็นเจ้าของที่ไม่มีอยู่จริง (หน้าตาเหมือนเคยเป็น array เดียวกันแล้วถูกผ่าออกภายหลัง) และมันมีราคาจริงตอนแก้: วันที่ธุรกิจขอเพิ่ม "Same Day Delivery" คนเขียนจะต้องจำได้ว่าห้ามใช้ 3 ทั้งที่ไม่มีอะไรในโค้ดบอกเขาเลย — ไม่มี type ไหนกัน ไม่มีเทสต์ไหนฟ้อง เจอตอนกด radio แล้วติดผิดกล่องเท่านั้น ทางแก้ในรีวิวจริงคือให้แต่ละ array เริ่มที่ 1 ของตัวเอง (id มันแยก namespace กันอยู่แล้วโดยธรรมชาติ) หรือถ้าอยากได้ความชัดจริง ๆ ก็เปลี่ยน id เป็น string อย่าง "standard" / "cod" ซึ่งอ่านออกทันทีตอน debug เราคงเลขตามต้นฉบับเพื่อให้ diff ตรงกับโค้ดอ้างอิงและกับบทเรียน 28

ทำไมตัวเลือกอยู่ใน consts ไม่ฝังในคอมโพเนนต์

มือใหม่จำนวนมากจะเขียนรายการพวกนี้ hardcode ไว้ใน JSX ของคอมโพเนนต์ที่แสดงมันเลย ซึ่งดูเร็วดี แต่ใน chapter นี้ข้อมูลชุดเดียวกันถูกใช้จากหลายที่มาก:

  • CheckoutDeliveryBox และ CheckoutPaymentBox (บทเรียน 27) — วนลูปแสดงเป็น radio ให้เลือก
  • useCheckout (บทเรียน 28) — ใช้ deliveryOptions[0].id เป็นค่าที่เลือกเริ่มต้น และค้นหา price ของตัวที่เลือกมาคำนวณค่าส่งใน billing summary
  • เทสต์ (บทเรียน 32–33) — import รายการเดียวกันมา assert ว่ายอดรวมและ UI ตรงกับตัวเลือกที่เลือก

ถ้าข้อมูลฝังอยู่ใน JSX ของคอมโพเนนต์ใดคอมโพเนนต์หนึ่ง ที่อื่นจะเข้าถึงไม่ได้เลย (หรือต้อง copy ไปแปะ ซึ่งคือการเปิดประตูให้ข้อมูล drift อีกแล้ว) การแยก data ออกจาก presentation แบบนี้ทำให้วันที่ธุรกิจอยากเพิ่ม "Same Day Delivery" เราแก้ array เดียวใน consts.ts แล้วทั้ง UI ตัวเลือก ทั้งการคำนวณราคา ทั้งเทสต์ ขยับตามพร้อมกันหมด และในอนาคตถ้าตัวเลือกพวกนี้ย้ายไปอยู่บน API จริง จุดที่ต้องแก้ก็มีจุดเดียวเช่นกัน — วันนั้น types.ts จะกลายเป็น type ของ response และ consts.ts จะกลายเป็น api.ts ซึ่งเป็นการเปลี่ยนที่กระทบคอมโพเนนต์ศูนย์ตัว

🤔 อธิบายให้ได้

  1. เพิ่ม field postcode: z.string().min(1, "Postcode is required") เข้าไปใน checkoutAddressSchema แล้วรัน npm run typecheck — ตอบว่าทำไมวันนี้ไม่มีไฟล์ไหนฟ้องเลยสักไฟล์ จากนั้นเปิดบทเรียน 26 กับ 28 อ่านผ่าน ๆ แล้วระบุล่วงหน้าให้ได้ว่าหลังสองบทนั้นจบ การเพิ่มบรรทัดเดียวนี้จะทำให้ TypeScript ฟ้องที่ไฟล์ไหนบ้าง และไฟล์ไหนที่ไม่ฟ้องแม้จะเกี่ยวข้องกับที่อยู่ (เสร็จแล้วเอา field ออก)
  2. เปลี่ยน email ใน schema ให้เหลือ z.email("Enter a valid email address") เฉย ๆ (ตัด .min(1).pipe(...) ทิ้ง) แล้วเรียก safeParse ด้วย email: "" ในไฟล์ scratch — ตอบว่าผู้ใช้จะเห็นข้อความอะไร และอธิบายว่าทำไมลำดับของสองด่านถึงสลับกันไม่ได้ (ลอง .pipe() สลับข้างดูแล้วตอบว่าเกิดอะไรขึ้น) เสร็จแล้วเติมกลับ
  3. สมมติว่ามีคนย้าย deliveryOptions ไปประกาศไว้ในตัว CheckoutDeliveryBox ตรง ๆ ตอนบทเรียน 27 — ไล่ให้ครบว่ามีใครอีกบ้างในบทเรียน 28 และ 32 ที่ต้องการ array ตัวนี้ และแต่ละคนจะทำอย่างไรแทน ตอบด้วยว่าอาการที่ผู้ใช้เห็นจะเป็นอย่างไรถ้าคนที่สองเลือกวิธี copy array ไปแปะแล้วแก้ราคาผิดไปหนึ่งตัว
