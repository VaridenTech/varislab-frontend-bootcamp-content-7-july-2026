บทเรียน 21 · การทดสอบ (Testing)

การทดสอบด้วย Vitest

Vitest

ถึงตรงนี้แอปของเราทำงานได้ครบแล้ว — เลือกพิซซ่า ใส่ตะกร้า สั่งซื้อ ดูออร์เดอร์ย้อนหลัง ส่งฟอร์มติดต่อ ทุกครั้งที่แก้โค้ดสักจุด เราก็เปิดเบราว์เซอร์แล้วคลิกไล่ดูว่ายังใช้ได้อยู่ไหม บทนี้เราจะเปลี่ยนการคลิกซ้ำ ๆ นั้นให้เป็นโค้ดที่รันแทนเราได้

ทำไมต้องเขียนเทสต์

คำถามที่คนเรียนถามบ่อยที่สุดคือ “ในเมื่อกดดูเองก็ได้ ทำไมต้องเสียเวลาเขียนเทสต์” คำตอบไม่ใช่เรื่องความถูกต้องวันนี้ แต่เป็นเรื่องของวันข้างหน้า

  • มันไม่ scale — แอปเรามี 5 หน้าจอ กดตรวจครบยังพอไหว พอมี 50 หน้าจอ คุณจะกดตรวจไม่ครบ และคุณจะเลิกกดตรวจ
  • มันจับของที่คุณ “ไม่ได้แตะ” — บั๊กที่เจ็บที่สุดคือแก้ตะกร้าแล้วหน้าออร์เดอร์ย้อนหลังพัง เพราะคุณไม่ได้เปิดหน้านั้นดูเลย
  • มันทำให้กล้า refactor — เมื่อมีเทสต์คุ้มหลังอยู่ การรื้อโค้ดให้ดีขึ้นจะกลายเป็นเรื่องปกติ ไม่ใช่เรื่องน่ากลัว
  • มันคือเอกสารที่ไม่มีวันล้าสมัย — คนที่เข้ามาอ่านโค้ดทีหลังดูเทสต์แล้วรู้ทันทีว่า component นี้ควรทำอะไร และคำอธิบายนั้นโกหกไม่ได้ เพราะถ้ามันไม่จริง เทสต์จะไม่ผ่าน

💡 อย่าเพิ่งตั้งเป้าว่าต้องเทสต์ครบ 100% เป้าหมายที่ดีกว่ามากสำหรับผู้เริ่มต้นคือ “เทสต์สิ่งที่พังแล้วเจ็บที่สุด” เช่น การคำนวณราคารวมในตะกร้า ซึ่งถ้าผิดคือเก็บเงินลูกค้าผิด ส่วนเรื่องอย่างสีของปุ่มนั้นปล่อยไปได้

Vitest คืออะไร

Vitest คือ test runner ที่สร้างโดยทีมเดียวกับที่ทำ Vite แนวคิดของมันตรงไปตรงมามาก: ในเมื่อเรามี build pipeline ที่ใช้สร้างแอปอยู่แล้ว ทำไมตอนรันเทสต์ถึงต้องไปตั้งค่า pipeline อีกชุดหนึ่งแยกต่างหาก? สภาพแวดล้อมตอนเทสต์ควรเหมือนสภาพแวดล้อมจริงของแอปให้มากที่สุด

ผลคือเราแทบไม่ต้องตั้งค่าอะไรเลย เพราะ Vitest ใช้ vite.config.ts ตัวเดิมที่เรามีอยู่แล้ว รู้จัก JSX และ TypeScript อยู่แล้ว และเข้าใจ import แบบเดียวกับที่แอปเราใช้ — เขียนเทสต์เป็น TypeScript ได้ทันทีโดยไม่ต้องตั้งค่าเพิ่มแม้แต่บรรทัดเดียว ซึ่งต่างจากสมัย Jest ที่ต้องไปตั้ง ts-jest หรือ Babel preset กันอีกยกหนึ่ง

Vitest ออกแบบมาให้ API เหมือน Jest ซึ่งเป็น test runner ที่ครองวงการ JavaScript มานาน แทบจะสลับกันใช้ได้เลย ข้อดีคือทุกอย่างที่คุณเรียนในบทนี้เอาไปใช้กับ Jest ได้หมด และทั้งคู่ก็ยืมรูปแบบคำสั่งอย่าง describe, it, expect มาจาก Jasmine อีกที ดังนั้นเรียนครั้งเดียวใช้ได้กับเครื่องมือแทบทุกตัวในวงการ

ติดตั้ง

npm install -D vitest@^4.1.0 @testing-library/react@^16.3.0 happy-dom@^20.11.0

เราติดตั้งสามตัวด้วยกัน แต่ละตัวทำคนละหน้าที่

แพ็กเกจ หน้าที่
vitest ตัวรันเทสต์ คอยหาไฟล์เทสต์ รันมัน แล้วรายงานผลว่าผ่านหรือไม่ผ่าน
@testing-library/react ชุดเครื่องมือสำหรับ render component ออกมาแล้วค้นหา/โต้ตอบกับสิ่งที่แสดงผล
happy-dom DOM จำลองที่ทำงานใน Node.js เพราะเทสต์ของเราไม่ได้รันในเบราว์เซอร์จริง

ขยายความอีกนิดสำหรับสองตัวหลัง

  • @testing-library/react เป็นวิธีที่แนะนำสำหรับเทสต์ React ในปัจจุบัน จุดขายของมันคือปรัชญา “เทสต์เหมือนที่ผู้ใช้ใช้งานจริง” คือให้ค้นหา element จากสิ่งที่ผู้ใช้เห็น เช่น ข้อความบนปุ่มหรือ label ของช่องกรอก แทนที่จะไปยึดกับชื่อ class หรือโครงสร้างภายในของ component ผลคือเทสต์จะไม่พังเวลาคุณแก้ดีไซน์ แต่จะพังเมื่อพฤติกรรมของแอปเปลี่ยนจริง ๆ ซึ่งเป็นสิ่งที่เราต้องการ
  • happy-dom จำเป็นเพราะโค้ด React ของเราเรียกใช้สิ่งที่มีเฉพาะในเบราว์เซอร์ เช่น document และ window แต่ Node.js ไม่มีสิ่งเหล่านี้ happy-dom จึงสร้าง DOM จำลองขึ้นมาให้ในหน่วยความจำ มันคล้าย jsdom ที่ใช้กันมานาน แต่เล็กกว่าและเร็วกว่ามาก แลกกับการที่มันไม่ได้ทำครบทุกอย่างเหมือนเบราว์เซอร์จริง (เดี๋ยวในบทท้าย ๆ เราจะได้รันเทสต์ในเบราว์เซอร์จริงกันด้วย)

ตั้งค่า

เพิ่ม config เล็ก ๆ นี้ใน object ของ vite.config.ts เพื่อบอก Vitest ว่าให้ใช้ DOM จำลอง

// เปลี่ยน import บรรทัดบนสุด จาก "vite" เป็น "vitest/config"
import { defineConfig } from "vitest/config";

// เพิ่มเข้าไปใน object ที่ส่งให้ defineConfig
test: {
  environment: "happy-dom",
},

💡 สังเกตว่าเราเปลี่ยนที่มาของ defineConfig จาก "vite" เป็น "vitest/config" ด้วย ถ้าไม่เปลี่ยน TypeScript จะฟ้องว่า Object literal may only specify known properties, and 'test' does not exist in type 'UserConfig' — เพราะ defineConfig ของ Vite ไม่รู้จัก key test ส่วนตัวที่มาจาก vitest/config เป็นตัวเดียวกันทุกอย่าง แค่รู้จัก option ของ Vitest เพิ่มเข้ามา นี่คือ error ที่คนเจอกันบ่อยมากตอนเพิ่ม Vitest เข้าโปรเจกต์ TypeScript ครั้งแรก

จากนั้นเพิ่ม npm script ใน package.json

"test": "vitest"

💡 ชื่อ test เป็นชื่อพิเศษที่ npm รู้จัก คุณจึงสั่งได้สั้น ๆ ว่า npm test หรือสั้นกว่านั้นคือ npm t โดยไม่ต้องมีคำว่า run

สุดท้าย เข้าไปใน src แล้วสร้างโฟลเดอร์ชื่อ __tests__ — สังเกตว่ามี underscore สองตัวขนาบทั้งสองข้าง Vitest จะถือว่าไฟล์ทุกไฟล์ในโฟลเดอร์นี้คือเทสต์ ธรรมเนียม underscore คู่นี้ยืมมาจาก Python ที่ใช้สื่อว่า “ชื่อนี้มีความหมายพิเศษ มีบางอย่างกำลังมองหาชื่อนี้อยู่” ซึ่งในที่นี้คือตัว Vitest เอง

ตอนนี้โครงสร้างโปรเจกต์ควรเป็นแบบนี้

pizza-app/
├── src/
│   ├── __tests__/        ← เทสต์อยู่ตรงนี้
│   ├── api/
│   ├── routes/
│   ├── App.tsx
│   ├── Pizza.tsx
│   └── types.ts          ← type ที่ใช้ร่วมกัน รวมถึงในเทสต์ด้วย
├── tsconfig.json
├── vite.config.ts
└── package.json

ไฟล์เทสต์ก็ใช้กฎเดียวกับโค้ดแอป: เทสต์ที่มี JSX (คือเทสต์ที่ render component) ใช้ .test.tsx ส่วนเทสต์ที่เป็น logic ล้วน ๆ ใช้ .test.ts

ลองรันดู

สั่ง npm t ได้เลย ตอนนี้ยังไม่มีไฟล์เทสต์สักไฟล์ Vitest จึงจะบ่นว่าหาเทสต์ไม่เจอ ซึ่งถูกต้องแล้ว ขอให้สังเกตว่ามันไม่ได้จบการทำงาน แต่ค้างรอไว้

นั่นเพราะโดยค่าเริ่มต้น Vitest ทำงานในโหมด watch คือมันจะเฝ้าดูไฟล์ของคุณ แล้วรันเฉพาะเทสต์ที่เกี่ยวข้องกับไฟล์ที่คุณเพิ่งบันทึกใหม่โดยอัตโนมัติ คุณจึงเขียนโค้ดไปแล้วเห็นผลทันทีในอีกหน้าต่างหนึ่งโดยไม่ต้องสลับไปกดอะไรเลย นี่เป็นฟีเจอร์ที่ทำให้การเขียนเทสต์รู้สึกลื่นขึ้นมาก กด q เพื่อออกจากโหมดนี้

🔍 ถ้าจะรันบนระบบ CI/CD ที่ต้องการให้จบแล้วคืนค่าสถานะ ให้ใช้ npx vitest run ซึ่งจะรันครั้งเดียวแล้วจบ ไม่ค้างรอ

ลองทำเอง

ก่อนไปบทถัดไปที่เราจะเขียนเทสต์จริงจัง ลองสร้างไฟล์ src/__tests__/sanity.test.ts เพื่อยืนยันว่าเครื่องมือตั้งค่าถูกแล้ว

import { expect, test } from "vitest";

test("ตั้งค่า Vitest เรียบร้อยแล้ว", () => {
  expect(1 + 1).toBe(2);
});
  1. รัน npm t แล้วดูว่าเทสต์ผ่านเป็นสีเขียว
  2. แก้ toBe(2) เป็น toBe(3) แล้วบันทึกไฟล์ โดยไม่ต้องไปสั่งอะไรใหม่ สังเกตว่า Vitest รันใหม่ให้เองทันที และอ่านข้อความ error ดูว่ามันบอกอะไรเราบ้าง
  3. แก้กลับให้ผ่าน แล้วลองเปลี่ยนชื่อไฟล์เป็น sanity.ts เฉย ๆ (เอา .test ออก) สังเกตว่า Vitest มองไม่เห็นมันแล้ว เพราะมันมองหาเฉพาะไฟล์ที่มี .test. หรือ .spec. ในชื่อ
  4. เปลี่ยนชื่อกลับ แล้วลองเขียนเทสต์เพิ่มอีกหนึ่งข้อในไฟล์เดียวกัน ดูว่าผลลัพธ์แสดงทั้งสองข้ออย่างไร
  5. ลองเขียน expect("2").toBe(2) ดู สังเกตว่านอกจากเทสต์จะไม่ผ่านแล้ว TypeScript ยังขีดเส้นแดงให้ตั้งแต่ก่อนรันด้วย เพราะ expect() ของ Vitest เป็น generic — มันจำ type ของสิ่งที่คุณส่งเข้าไป แล้วบังคับให้ .toBe() รับ type เดียวกัน การเทียบข้ามชนิดที่เคยเป็นบั๊กเงียบ ๆ ในเทสต์ JavaScript จึงจับได้ตั้งแต่ตอนพิมพ์

เมื่อทุกอย่างพร้อมแล้ว ลบไฟล์นี้ทิ้งได้ บทถัดไปเราจะเริ่มเทสต์ component จริงของแอปเรา

สรุป

  • เทสต์ไม่ได้มีไว้พิสูจน์ว่าโค้ดวันนี้ถูก แต่มีไว้กันไม่ให้โค้ดวันหน้าพังโดยที่เราไม่รู้ตัว
  • Vitest ใช้ config เดียวกับ Vite เราจึงแทบไม่ต้องตั้งค่าอะไรเพิ่ม (ยกเว้นเปลี่ยนที่มาของ defineConfig เป็น vitest/config) และสิ่งที่เรียนใช้กับ Jest ได้เกือบทั้งหมด
  • ต้องมีสามชิ้นประกอบกัน: ตัวรันเทสต์ (Vitest), เครื่องมือ render component (Testing Library) และ DOM จำลอง (happy-dom)
  • ไฟล์เทสต์อยู่ใน src/__tests__ และต้องมี .test. อยู่ในชื่อไฟล์ ใช้ .test.tsx เมื่อมี JSX และ .test.ts เมื่อไม่มี
  • โหมด watch คือค่าเริ่มต้น ส่วน vitest run ไว้ใช้บน CI
