การทดสอบ React ขั้นพื้นฐาน

Basic React Tests

มาเขียน test แรกสำหรับ Pizza.tsx กัน โดยทั่วไป นี่คือแนวทางที่คอร์สนี้แนะนำสำหรับการเขียนเทสต์ React:

  • พยายาม test functionality ไม่ใช่ implementation ให้ tests โต้ตอบกับ components อย่างที่ผู้ใช้ทำ ไม่ใช่อย่างที่ developer ทำ ซึ่งหมายถึงคุณพยายามคิดเรื่องอย่าง “ผู้ใช้จะเห็นอะไร” หรือ “ถ้าผู้ใช้คลิกปุ่ม modal จะขึ้น” มากกว่า “ทำให้แน่ใจว่า state นี้ถูกต้อง” หรือ “ให้แน่ใจว่า library นี้ถูกเรียก” นี่ไม่ใช่กฎ; บางครั้งคุณต้อง test สิ่งเหล่านั้นด้วยเพื่อยืนยันว่า app ทำงานถูกต้อง ใช้วิจารณญาณที่ดีที่สุดของคุณ
  • UI มักเปลี่ยนบ่อยมากตลอดอายุของโปรเจกต์ พยายามอย่าเสียแรงโดยไม่จำเป็นกับสิ่งที่ไม่สำคัญและมีแนวโน้มจะเปลี่ยน
  • เมื่อเจอ bug ที่สำคัญพอจะกลับไปแก้ ให้เขียน test ที่จับ bug นั้นได้ ลำดับที่ดีคือเขียน test ให้ fail ก่อน แล้วค่อยแก้โค้ด แบบนี้เมื่อ test กลับมาผ่าน คุณจะมั่นใจได้ว่าปัญหาเดิมจะไม่ย้อนกลับมาอีก
  • ถามตัวเองว่าอะไรสำคัญใน app ของคุณ แล้วใช้เวลา test สิ่งนั้น ถามตัวเองแบบ “ถ้าผู้ใช้ทำ X ไม่ได้ app นี้ก็ไร้ค่า” แล้ว test สิ่งนั้นให้ละเอียดกว่า ถ้าผู้ใช้เปลี่ยน theme ไม่ได้คงไม่ถึงกับโลกแตก (a11y สำคัญนะ) คุณจึงใช้เวลาทดสอบมันน้อยกว่าได้ แต่ถ้าผู้ใช้ log in ไม่ได้ app ก็ไร้ค่า Test นั่น
  • ลบ tests เป็นประจำ Tests มีอายุการใช้งาน
  • แก้หรือลบ flaky tests Tests แย่แย่กว่าไม่มี tests

โอเค สร้าง file ใหม่ชื่อ Pizza.test.tsx (เป็น .tsx เพราะเทสต์นี้มี JSX อยู่ข้างใน) naming convention นี้เป็นแค่นิสัย Pizza.spec.tsx ก็พบได้ทั่วไปเช่นกัน แต่ตราบใดที่อยู่ใน __tests__ directory จะเรียกมันว่าอะไรก็ไม่สำคัญนัก

import { render } from "@testing-library/react";
import { expect, test } from "vitest";
import Pizza from "../Pizza";

test("alt text renders on image", async () => {
  const name = "My Favorite Pizza";
  const src = "https://picsum.photos/200";
  const screen = render(
    <Pizza name={name} description="super cool pizza" image={src} />
  );

  const img = screen.getByRole("img") as HTMLImageElement;
  expect(img.src).toBe(src);
  expect(img.alt).toBe(name);
});

มีจุดเดียวที่ต่างจากเวอร์ชัน JavaScript คือ as HTMLImageElement เหตุผลคือ getByRole() คืน HTMLElement กลาง ๆ ซึ่งไม่มี property src หรือ alt — สอง property นั้นมีเฉพาะใน HTMLImageElement เราจึงต้องบอก TypeScript ว่าสิ่งที่ได้มาคือ <img> จริง ๆ

นี่เป็นการใช้ as ที่ยอมรับได้ เพราะเราเพิ่งขอ element ที่มี role เป็น img มาเองกับมือ แต่ถ้าอยากเลี่ยง as ให้หมดจริง ๆ ก็มีทางเลือกที่ปลอดภัยกว่าและ Testing Library แนะนำมากกว่าด้วย คือใช้ matcher ที่ไม่ต้องแตะ property ของ DOM เลย

const img = screen.getByRole("img");
expect(img).toHaveAttribute("src", src);
expect(img).toHaveAttribute("alt", name);

(วิธีนี้ต้องติดตั้ง @testing-library/jest-dom เพิ่ม ซึ่งคอร์สนี้ไม่ได้ใช้ แต่รู้ไว้ว่ามีทางเลือกนี้อยู่ และในบทที่ 30 เราจะได้เห็นรูปแบบที่คล้ายกันมากตอนเทสต์ในเบราว์เซอร์จริง)

นี่คือ test ที่พื้นฐานที่สุดของคุณ มัน render React component แล้วเริ่มทำ assertions กับมัน ที่นี่เรากำลัง assert ว่าภาพพิซซ่าของเราลงเอยด้วย alt text ที่ถูกต้อง ไม่ใช่ test ที่มีประโยชน์ที่สุด แต่เป็นจุดเริ่มต้นที่ดีให้เราเห็นวิธี assert บางอย่าง มันจะมีประโยชน์ขึ้นมาทันทีถ้าโปรเจกต์เคยมี bug ที่ alt text หายไปในบางกรณี

เราใช้ getByRole ที่นี่เพื่อหยิบ image บน page โดยทั่วไป React Testing Library อยากให้คุณใช้แนวคิดแบบผู้ใช้เป็นศูนย์กลางในการ assert สิ่งต่าง ๆ บน page กรณีนี้เรากำลังพยายามหา image ซึ่งเป็นสิ่งที่ผู้ใช้จะเห็น เปรียบกับการใช้ CSS selector เลือก image (ทำได้นะ แค่ไม่ค่อยเป็นที่นิยม) ซึ่งเน้น implementation มาก (ผู้ใช้ไม่รู้และไม่สนใจ CSS classes)

มาเพิ่มอีก test เพื่อให้แน่ใจว่าเรามี default image หาก pizza ไม่ได้รับ image

🚨 อันนี้ยังไม่ทำงาน นั่นตั้งใจไว้

test("to have default image if none is provided", async () => {
  const screen = render(
    <Pizza name={"Cool Pizza"} description="super cool pizza" />
  );

  const img = screen.getByRole("img") as HTMLImageElement;
  expect(img.src).not.toBe("");
});

คราวนี้ TypeScript บ่นก่อนที่เทสต์จะได้รันด้วยซ้ำ

ในเวอร์ชัน JavaScript ของบทนี้ คุณต้องรันเทสต์ก่อนถึงจะรู้ว่ามีปัญหา แต่พอเป็น TypeScript คุณจะเห็นเส้นแดงตั้งแต่ตอนพิมพ์เลย

Property 'image' is missing in type '{ name: string; description: string; }'
but required in type 'PizzaProps'.

หยุดคิดสักครู่ตรงนี้ เพราะมันน่าสนใจกว่าที่เห็น TypeScript ไม่ได้บอกว่าเทสต์เราผิด แต่กำลังบอกว่า เทสต์ของเราขัดแย้งกับสิ่งที่ component ประกาศไว้ เรากำลังจะเทสต์ว่า "ถ้าไม่ส่ง image จะเป็นยังไง" ทั้งที่ PizzaProps บอกว่า image เป็น prop ที่ต้องส่งเสมอ อย่างใดอย่างหนึ่งต้องผิด

และคำตอบก็ชัด: เราต้องการให้ image ส่งหรือไม่ส่งก็ได้จริง ๆ ดังนั้น type ต่างหากที่ต้องแก้ ไปที่ Pizza.tsx แล้วทำให้มันเป็น optional

type PizzaProps = {
  name: string;
  description: string;
  image?: string; // เพิ่ม ? เข้าไป
};

ตอนนี้เทสต์ compile ผ่านแล้ว แต่ยังไม่จบ ถัดมาสิ่งที่มันจะบ่นคือเราไม่ได้ clean up หลังตัวเองหลังแต่ละ test React Testing Library ต้องการให้เราทำ

// at top
import { render, cleanup } from "@testing-library/react"; // add cleanup
import { afterEach, expect, test } from "vitest"; // add afterEach
afterEach(cleanup);

test ก็ยังไม่ผ่าน? อ้อ เพราะมันจับ bug ได้! ถ้าคุณไม่ส่ง image ให้ มันก็พัง นั่นไม่ใช่ user experience ที่ดี ไปแก้มันใน Pizza.tsx กัน

// replace src
src={props.image ? props.image : "https://picsum.photos/200"}

ตอนนี้มันทำงานแล้ว!

ลองย้อนดูสิ่งที่เพิ่งเกิดขึ้นทั้งกระบวนการ เราแก้สองอย่างซึ่งเป็นคนละเรื่องกัน

  • แก้ type (image?: string) — เปลี่ยน "สัญญา" ว่า component นี้รับอะไรได้บ้าง TypeScript จับให้ตั้งแต่ตอนพิมพ์
  • แก้ logic (ใส่ default image) — เปลี่ยนพฤติกรรมจริงตอนรัน มีแต่เทสต์เท่านั้นที่จับได้

นี่คือเหตุผลที่ type ไม่ได้มาแทนที่เทสต์ และเทสต์ก็ไม่ได้มาแทนที่ type — สองอย่างนี้จับบั๊กคนละชนิดกัน type ตอบคำถามว่า "ข้อมูลรูปร่างถูกไหม" ส่วนเทสต์ตอบว่า "แล้วมันทำงานถูกหรือเปล่า" คำถามที่ได้ยินบ่อยว่า "ใช้ TypeScript แล้วยังต้องเขียนเทสต์อีกไหม" จึงมีคำตอบตรงนี้เอง
