Browser Tests

🚨 สิ่งนี้เป็น experimental และมีแนวโน้มสูงที่จะเปลี่ยนในอนาคต ให้ถือว่านี่เป็น sneak peak ของสิ่งที่จะมา ไม่ใช่สิ่งที่ควรทำในวันนี้

Vitest กำลังเริ่มรองรับ browser-based testing ที่ลึกขึ้น สำหรับพวกเราที่อยู่มานานพอจะจำ Selenium ได้ สิ่งนี้อาจทำให้หวาดกลัวถึงใจ แต่ไม่ต้องกลัว! Browser-based testing tools พัฒนาไปไกลมากตั้งแต่นั้น จนทั้งเร็วและเชื่อถือได้ โดยเฉพาะเพราะ Microsoft project Playwright

อย่างไรก็ตามนี่ก็ยังเป็นช่วงแรก ๆ เราจะดูวิธีตั้งค่ากัน แต่ระวังว่ามันอาจเปลี่ยนได้ เพราะพวกเขายังทำงานกับมันอย่างแข็งขัน!

ดังนั้นก่อนอื่นมาติดตั้ง libraries ที่ต้องใช้

npm i -D @vitest/browser@^4.1.0 @vitest/browser-playwright@^4.1.0 playwright@^1.62.0 vitest-browser-react@^2.2.0

โอเค ตอนนี้เราอยากเขียน browser based tests แต่เราก็มี Node.js-based tests อยู่เดิมจำนวนมาก บาง Node.js based tests ที่มีอยู่แล้วจะใช้ใน browser ไม่ได้ แต่ไม่ต้องห่วง Vitest มี tool สำหรับสิ่งนี้พอดี คือ projects จริง ๆ มันสร้างมาเพื่อจัดการ monorepos แต่ใช้ที่นี่ได้ดีพอกัน

เปิด vite.config.ts แล้วแทนที่ test object เดิมด้วยแบบนี้

import { defineConfig } from "vitest/config";
import react from "@vitejs/plugin-react";
import { tanstackRouter } from "@tanstack/router-plugin/vite";
import { playwright } from "@vitest/browser-playwright";

export default defineConfig({
  server: {
    /* proxy config เดิมของคุณ */
  },
  plugins: [tanstackRouter({ target: "react", autoCodeSplitting: true }), react()],
  test: {
    projects: [
      {
        extends: true,
        test: {
          name: "happy-dom",
          include: ["**/*.node.test.{ts,tsx}"],
          environment: "happy-dom",
        },
      },
      {
        extends: true,
        test: {
          name: "browser",
          include: ["**/*.browser.test.{ts,tsx}"],
          setupFiles: ["vitest-browser-react"],
          browser: {
            enabled: true,
            provider: playwright(),
            instances: [
              { browser: "firefox" }, // you can use chromium or webkit here too
            ],
          },
        },
      },
    ],
  },
});

🚨 ถ้าคุณเคยเห็นตัวอย่างที่ใช้ vitest.workspace.js — รูปแบบนั้นถูกยกเลิกไปแล้วตั้งแต่ Vitest 3 และถูกลบออกจริงใน Vitest 4 ทั้ง defineWorkspace และไฟล์ vitest.workspace.* ไม่มีอยู่แล้ว ของใหม่คือ test.projects ที่อยู่ใน config เดียวกันนี้เลย ซึ่งอ่านง่ายกว่ามาก เพราะทุกอย่างอยู่ที่เดียว บทความและวิดีโอเก่า ๆ บนอินเทอร์เน็ตจำนวนมากยังสอนแบบเดิมอยู่ ให้ระวังไว้

  • extends: true บอกให้แต่ละ project สืบทอด plugins และ server จาก config ตัวนอก ถ้าไม่ใส่ Vitest จะไม่รู้จัก React plugin แล้วเทสต์ที่มี JSX จะพังทันที
  • เพราะเราใช้ defineConfig จาก "vitest/config" อยู่แล้วตั้งแต่บทที่ 23 ทุก option ในนี้จึงมี auto-complete ครบ ลองพิมพ์ browser: แล้วกด Ctrl+Space ดู
  • provider: playwright() — สังเกตว่าใน Vitest 4 provider เป็นฟังก์ชันที่ import มาจาก package แยก ไม่ใช่ string "playwright" แบบเดิมแล้ว ข้อดีคือ option ของ Playwright ทั้งหมดมี type ตรวจให้ด้วย
  • instances เป็น array เพราะ Vitest 4 รันเทสต์ชุดเดียวกันในหลายเบราว์เซอร์พร้อมกันได้ แค่เพิ่ม { browser: "chromium" } เข้าไปอีกตัว

ตอนนี้หาก test ลงท้ายด้วย .node.test.tsx มันจะ run ผ่าน happy-dom based environment และถ้าลงท้ายด้วย .browser.test.tsx มันจะ run ใน browser-based environment ใหม่ของเราพร้อม Playwright ไป rename tests ของเราให้สะท้อนสิ่งนี้กัน

  • Cart.browser.test.tsx
  • contact.lazy.node.test.tsx
  • Pizza.node.test.tsx
  • usePizzaOfTheDay.node.test.tsx

Snapshotting ทำงานใน browser ดังนั้นอันนั้นใช้ได้ Anything ที่ใช้ vitest-fetch-mock เป็น Node.js only ดังนั้นสำหรับสิ่งเหล่านั้นเราต้องกำกับว่า node เราจะสร้าง Pizza file ใหม่ จึงปล่อยอันนั้นไว้ และ custom hook test ของเรา mock fetch ดังนั้นเป็น Node only

โอเค ตอนนี้สร้าง Pizza.browser.test.tsx

import { render } from "vitest-browser-react";
import { expect, test } from "vitest";
import Pizza from "../Pizza";

test("alt text renders on image", async () => {
  const name = "My Favorite Pizza";
  const src = "https://picsum.photos/200";
  const screen = await render(
    <Pizza name={name} description="super cool pizza" image={src} />
  );

  const img = screen.getByRole("img");

  await expect.element(img).toBeInTheDocument();
  await expect.element(img).toHaveAttribute("src", src);
  await expect.element(img).toHaveAttribute("alt", name);
});
⚠️ สังเกตว่าเราเขียน await render(...) ต่างจาก render() ของ @testing-library/react ที่ใช้มาตลอด — ใน vitest-browser-react ฟังก์ชัน render คืน Promise เพราะมันต้องรอเบราว์เซอร์จริง render ให้เสร็จก่อน ถ้าลืม await TypeScript จะฟ้องทันทีว่า Property 'getByRole' does not exist on type 'Promise<RenderResult>' ซึ่งเป็นตัวอย่างที่ดีมากของบั๊ก async ที่ TypeScript จับให้ก่อนที่คุณจะเสียเวลาไล่หาว่าทำไมเทสต์ถึงพัง
  • render จะรับ React component แล้ว render มันในสุญญากาศ จากนั้นคุณ poke และ prod มันได้ตามต้องการเพื่อ test
  • ส่วนสำคัญมากของสิ่งที่ Playwright และ vitest-browser-react อยากให้คุณทำคืออย่า test implementation details แต่ให้ test user experiences จริง อย่า test internal state ของ React component แต่ test สิ่งที่ผู้ใช้จะเห็นและสัมผัส ด้วยเหตุนี้ สิ่งที่เราจะ test จำนวนมากจึงอยู่รอบ roles, attributes เป็นต้น
  • @testing-library มี document ดี ๆ ว่าทำไมพวกเขาเลือกทดสอบแบบนี้
  • โดยทั่วไป vitest-browser-react มุ่งเป็น drop in replacement สำหรับ @testing-library/react
  • สังเกตว่าเทสต์เวอร์ชันเบราว์เซอร์ไม่ต้องใช้ as HTMLImageElement เหมือนเวอร์ชัน happy-dom ในบทที่ 24 เพราะเราไม่ได้ไปแตะ .src หรือ .alt บน element ตรง ๆ แต่ใช้ toHaveAttribute() ซึ่งรับ element อะไรก็ได้ นี่เป็นตัวอย่างที่ดีว่าการเขียนเทสต์แบบที่ Testing Library แนะนำ (ยึด role และ attribute แทน property ของ DOM) มักจะทำให้ TypeScript พอใจไปด้วยโดยไม่ต้องพยายาม — เวลาเจอตัวเองต้องเขียน as ในเทสต์บ่อย ๆ นั่นมักเป็นสัญญาณว่ากำลังเทสต์ลึกเกินไปในรายละเอียดการทำงาน

ดูคล้ายมากใช่ไหม? โอเค มารันมัน npm run test คุณควรเห็น Vitest UI เดิม แต่ตอนนี้บาง tests กำลัง run ใน browser จริง

มันน่าจะ prompt ให้คุณรัน command อย่าง npx playwright install คุณจะติดตั้ง local copies ของ browsers เพื่อให้รันได้เร็วมาก

เจ๋งใช่ไหม และเร็วจริง ๆ! มาทำอีกอัน สร้าง Header.tsx test เราจะ test ว่า cart number ถูกต้อง จำได้ไหมที่ Facebook notification numbers ผิดตลอด? เราจะทำให้แน่ใจว่าสิ่งนั้นไม่เกิดกับ cart indicator ของเรา ใน Header.tsx file ของคุณ:

data-testid="cart-number" // add to .nav-cart-number

ตอนนี้สร้าง Header.browser.test.tsx

import { render } from "vitest-browser-react";
import { expect, test } from "vitest";
import Header from "../Header";
import {
  RouterProvider,
  createRouter,
  createRootRoute,
} from "@tanstack/react-router";
import { CartContext } from "../contexts";
import type { CartItem } from "../types";

function makeCart(count: number): CartItem[] {
  return Array.from({ length: count }, (_, i) => ({
    pizza: {
      id: `pizza-${i}`,
      name: `Test Pizza ${i}`,
      category: "Classic",
      description: "a pizza for testing",
      image: "/public/pizzas/pepperoni.webp",
      sizes: { S: 9.75, M: 12.5, L: 15.25 },
    },
    size: "M",
    price: "$12.50",
  }));
}

function renderHeaderWithCart(cart: CartItem[]) {
  const rootRoute = createRootRoute({
    component: () => (
      <CartContext.Provider value={[cart, () => {}]}>
        <Header />
      </CartContext.Provider>
    ),
  });

  const router = createRouter({ routeTree: rootRoute });
  return render(<RouterProvider router={router} />);
}

test("correctly renders a header with a zero cart count", async () => {
  const screen = await renderHeaderWithCart([]);

  const itemsInCart = screen.getByTestId("cart-number");

  await expect.element(itemsInCart).toBeInTheDocument();
  await expect.element(itemsInCart).toHaveTextContent("0");
});

test("correctly renders a header with a three cart count", async () => {
  const screen = await renderHeaderWithCart(makeCart(3));

  const itemsInCart = screen.getByTestId("cart-number");

  await expect.element(itemsInCart).toBeInTheDocument();
  await expect.element(itemsInCart).toHaveTextContent("3");
});

💡 renderHeaderWithCart ไม่ได้เขียนว่า async แต่เรา await ตอนเรียกใช้ นั่นเพราะมัน return render(...) ซึ่งเป็น Promise อยู่แล้ว TypeScript จึงสรุป return type ให้เป็น Promise<RenderResult> เอง — ไม่ต้องเขียน async/await ซ้อนอีกชั้นให้เปลืองโดยใช่เหตุ

เราต้องโค้งตัวไปข้างหลังสักหน่อยเพื่อให้ TanStack Router มีความสุข จึงมีการสร้าง root routes ทั้งหมดนั้น จำไว้ด้วยว่า cart ของเราได้ cart จาก context จึงต้องส่งมันเข้าแบบนั้น นอกเหนือจากนั้น มันทำงานคล้ายกันมาก!

context ที่มี type บังคับให้ mock ของเราซื่อสัตย์

เทสต์ชุดนี้ต่างจากเวอร์ชัน JavaScript พอสมควร และเหตุผลน่าสนใจ ต้นฉบับเขียนสองแบบนี้

value={[[]]}
value={[[{ pizza: 1 }, { pizza: 2 }, { pizza: 3 }]]}

ทั้งสองบรรทัดจะไม่ผ่าน TypeScript และทั้งสองบรรทัดมีปัญหาจริง ๆ ซ่อนอยู่

  • [[]] ขาดของไปครึ่งหนึ่ง — CartHook ที่เราประกาศไว้ในบทที่ 17 คือ tuple สองช่อง คือ [cart, setCart] แต่ตรงนี้ส่งมาช่องเดียว ในเวอร์ชัน JavaScript มันรอดมาได้เพราะบังเอิญ Header ใช้แค่ cart ไม่เคยเรียก setCart — แต่วันที่มีคนเพิ่มปุ่ม "ล้างตะกร้า" เข้าไปใน Header เทสต์นี้จะพังด้วย error ที่งงมาก เราจึงส่ง () => {} เป็นช่องที่สองให้ครบ
  • { pizza: 1 } ไม่ใช่ของในตะกร้า — มันไม่มี size ไม่มี price และ pizza ก็เป็นเลข 1 ไม่ใช่ object พิซซ่า มันผ่านได้เพราะเทสต์นี้สนใจแค่ cart.length — แต่นั่นแปลว่าถ้าวันหนึ่ง Header เปลี่ยนไปแสดงราคารวมด้วย เทสต์นี้จะพังทันทีทั้งที่ Header ทำงานถูกต้อง เราจึงเขียน makeCart() ที่สร้างข้อมูลจริงตาม type ให้แทน

บทเรียนที่ควรเก็บกลับไปคือ mock data ที่ "แค่พอให้ผ่าน" คือหนี้ที่รอวันทวง ทุกครั้งที่เราตัดมุมในข้อมูลทดสอบ เรากำลังผูกเทสต์ไว้กับรายละเอียดว่า component วันนี้บังเอิญใช้ field ไหนบ้าง TypeScript ไม่ยอมให้เราทำแบบนั้น และผลคือเทสต์ที่ทนต่อการเปลี่ยนแปลงได้ดีกว่า

ส่วน helper renderHeaderWithCart() นั้นเราแยกออกมาเพราะสองเทสต์ใช้โครงเดียวกันทั้งหมด ต่างแค่ข้อมูลตะกร้า — เป็นการจัดระเบียบธรรมดา ๆ ที่ไม่เกี่ยวกับ TypeScript แต่ทำให้เห็นชัดขึ้นว่าแต่ละเทสต์กำลังทดสอบอะไร

อีกครั้ง นี่เป็นช่วงแรก ๆ ของ browser-based testing ด้วย Vite ดังนั้นใน professional settings ของคุณให้ทำด้วยความระมัดระวัง อย่างไรก็ตามอนาคตสดใสด้วย Playwright!

coverage เมื่อแบ่งเป็นหลาย project

coverage ที่เราตั้งไว้ในบทที่ 28 ยังใช้ได้อยู่ แต่ตอนนี้ config ของเราย้ายเข้าไปอยู่ใน projects แล้ว จึงต้องย้าย coverage ขึ้นมาไว้ที่ระดับ test ตัวนอกแทน เพื่อให้รายงานผลรวมของทั้งสอง project เข้าด้วยกัน

export default defineConfig({
  // …
  test: {
    coverage: {
      reporter: ["text", "json", "html"],
    },
    projects: [
      // … เหมือนเดิม
    ],
  },
});

หมายเหตุผู้แปล: ต้นฉบับของหลักสูตร (ซึ่งอิง Vitest 2) แนะนำให้ถอน @vitest/coverage-v8 ออกแล้วเปลี่ยนไปใช้ Istanbul เพราะตอนนั้น coverage ของ V8 ยังใช้กับ browser mode บน React 19 ไม่ได้ ข้อจำกัดนั้นหมดไปแล้วใน Vitest 4 เราจึงใช้ @vitest/coverage-v8 ตัวเดิมจากบทที่ 28 ต่อได้เลย ไม่ต้องติดตั้งอะไรเพิ่ม · ถ้าคุณยังอยากลอง Istanbul ชื่อ package ที่ถูกต้องคือ @vitest/coverage-istanbul (ไม่ใช่ @vitest/istanbul อย่างในต้นฉบับ) แล้วเพิ่ม provider: "istanbul" เข้าไปใน object coverage
