บทเรียน 04 · เครื่องมือ (Tools)

npm: การจัดการแพ็กเกจ

npm

สองบทที่ผ่านมาเราโหลด React ด้วย <script> จาก CDN ซึ่งใช้ได้ดีตอนเรียน แต่พอโปรเจกต์จริงเริ่มโต วิธีนี้จะพังทันที ลองนึกภาพว่าคุณต้องใช้ไลบรารีสิบตัว แต่ละตัวมีเวอร์ชันของตัวเอง บางตัวต้องพึ่งไลบรารีอื่นอีกที และเพื่อนร่วมทีมของคุณต้องได้เวอร์ชันเดียวกันเป๊ะ ๆ กับคุณ ไม่อย่างนั้นโค้ดจะทำงานคนละแบบ

ถ้าใช้ CDN โปรเจกต์ที่มีไลบรารีเพียงสี่ตัวก็ต้องดูแล URL เวอร์ชัน และลำดับการโหลดเองทั้งหมด

<script src="https://unpkg.com/react@18.3.1/umd/react.development.js"></script>
<script src="https://unpkg.com/react-dom@18.3.1/umd/react-dom.development.js"></script>
<script src="https://unpkg.com/dayjs@1.11.13/dayjs.min.js"></script>
<script src="https://unpkg.com/lodash@4.17.21/lodash.min.js"></script>
<script src="./src/App.js"></script>

เมื่อใช้ npm รายชื่อและเวอร์ชันของไลบรารีเดียวกันจะถูกรวมไว้ใน package.json จุดเดียว

{
  "dependencies": {
    "dayjs": "1.11.13",
    "lodash": "4.17.21",
    "react": "18.3.1",
    "react-dom": "18.3.1"
  }
}

npm จะดาวน์โหลดแพ็กเกจเหล่านี้ รวมถึงแพ็กเกจที่มันพึ่งพาต่อให้อัตโนมัติ และใช้ package-lock.json ช่วยให้ทุกคนในทีมติดตั้งได้เวอร์ชันตรงกัน

นี่คือปัญหาที่ npm เกิดมาแก้ และบทนี้จะเป็นบทแรกของกลุ่ม “เครื่องมือ” ที่เราจะค่อย ๆ ประกอบขึ้นมาเองทีละชิ้น

npm คืออะไร

คนมักพูดถึง npm รวม ๆ เป็นคำเดียว แต่จริง ๆ แล้วมันหมายถึงสามสิ่งที่ทำงานร่วมกัน

  • Registry — คลังกลางบนอินเทอร์เน็ตที่เก็บแพ็กเกจ open source หลายล้านตัวที่นักพัฒนาทั่วโลกเผยแพร่ไว้ให้ใช้ฟรี
  • คำสั่ง npm — เครื่องมือ command line ที่ติดมากับ Node.js อยู่แล้ว ใช้ดาวน์โหลดแพ็กเกจจาก registry มาลงในโปรเจกต์ของเรา
  • package.json — ไฟล์บันทึกว่าโปรเจกต์นี้ต้องใช้แพ็กเกจอะไรบ้าง เวอร์ชันไหน เปรียบเหมือน “ใบสั่งยา” ของโปรเจกต์ ใครได้ไฟล์นี้ไปก็สร้างสภาพแวดล้อมเดียวกับคุณได้

💡 เกร็ดเล็กน้อย: npm ไม่ได้ ย่อมาจาก “Node Package Manager” — ทีมผู้สร้างไม่เคยประกาศว่ามันย่อมาจากอะไร ถึงมันจะทำหน้าที่นั้นจริง ๆ ก็ตาม

ตรวจสอบก่อนเริ่ม

npm ติดตั้งมาพร้อม Node.js อยู่แล้ว ไม่ต้องติดตั้งแยก เปิด terminal แล้วลองรัน

node -v
npm -v

ถ้าทั้งสองคำสั่งขึ้นเป็นเลขเวอร์ชัน (เช่น v20.16.0 และ 10.8.1) แปลว่าคุณพร้อมแล้ว หลักสูตรนี้ต้องการ Node.js เวอร์ชัน 20 ขึ้นไป ถ้าคำสั่งขึ้นว่า command not found ให้ไปดาวน์โหลดตัวติดตั้งจากเว็บไซต์ทางการของ Node.js (ค้นหาคำว่า “Node.js download” แล้วเลือกเวอร์ชัน LTS) จากนั้นปิดแล้วเปิด terminal ใหม่

ขั้นที่ 1: เปลี่ยนโฟลเดอร์ให้เป็นโปรเจกต์ npm

เข้าไปที่โฟลเดอร์ pizza-app ของเรา แล้วรัน

npm init -y

คุณจะได้ไฟล์ package.json โผล่ขึ้นมา หน้าตาประมาณนี้

{
  "name": "pizza-app",
  "version": "1.0.0",
  "description": "",
  "main": "index.js",
  "scripts": {
    "test": "echo \"Error: no test specified\" && exit 1"
  },
  "keywords": [],
  "author": "",
  "license": "ISC"
}

ธง -y แปลว่า “ตอบ yes ให้หมด” ใช้ค่าเริ่มต้นทั้งชุดโดยไม่ต้องตอบคำถามทีละข้อ ถ้ารัน npm init เฉย ๆ มันจะถามคุณทีละข้อ ซึ่งกด Enter รัว ๆ ก็ได้ผลเหมือนกัน ทุกค่าในไฟล์นี้แก้ทีหลังได้เสมอ เพราะมันเป็นแค่ไฟล์ข้อความธรรมดา

ความหมายของแต่ละช่อง

  • name และ version — ชื่อและเวอร์ชันของโปรเจกต์คุณเอง สำคัญมากถ้าคุณจะเผยแพร่แพ็กเกจขึ้น registry แต่ถ้าทำแอปใช้เองก็แค่ตั้งให้พอสื่อความหมาย
  • description, keywords, author, license — ข้อมูลประกอบ ไม่มีผลต่อการทำงานของโค้ด
  • main — ไฟล์เริ่มต้นเมื่อมีคน import แพ็กเกจนี้ เราไม่ได้ใช้ในหลักสูตรนี้
  • scripts — คำสั่งลัดของโปรเจกต์ เดี๋ยวเราจะพูดถึงมันด้านล่าง และคุณจะได้ใช้มันแทบทุกวัน

ขั้นที่ 2: ลองติดตั้งแพ็กเกจดูสักตัว

เพื่อไม่ให้กระทบโปรเจกต์หลัก ให้สร้างโฟลเดอร์ทดลองแยกต่างหาก (จะวางไว้ไหนก็ได้ที่ไม่ใช่ข้างใน pizza-app) แล้วทำตามนี้

mkdir npm-practice
cd npm-practice
npm init -y
npm install dayjs

สังเกตว่ามีสามอย่างเปลี่ยนไปในโฟลเดอร์นี้

  • node_modules/ — โฟลเดอร์ที่เก็บโค้ดจริงของแพ็กเกจที่ดาวน์โหลดมา ลองเปิดดูได้ คุณอาจเห็นโฟลเดอร์ย่อยมากกว่าที่ติดตั้งไว้ เพราะแพ็กเกจหนึ่งตัวมักพึ่งพาแพ็กเกจอื่นต่อไปอีกเป็นทอด ๆ (เรียกว่า transitive dependencies) โฟลเดอร์นี้ ห้าม เอาขึ้น Git เด็ดขาด
  • package.json — มีส่วน dependencies เพิ่มเข้ามา บันทึกว่าเราขอใช้ dayjs เวอร์ชันไหน
  • package-lock.json — ไฟล์ที่บันทึกเวอร์ชัน เป๊ะ ๆ ของทุกแพ็กเกจที่ถูกติดตั้งจริง รวมถึงของที่ติดมาเป็นทอด ไฟล์นี้ ต้อง เอาขึ้น Git

ลองสร้างไฟล์ test.js ในโฟลเดอร์ทดลอง แล้วเรียกใช้แพ็กเกจที่เพิ่งติดตั้งดู

const dayjs = require("dayjs");

console.log(dayjs().format("YYYY-MM-DD HH:mm"));

รันด้วย node test.js ถ้าเห็นวันเวลาปัจจุบันพิมพ์ออกมา แปลว่าคุณเพิ่งใช้โค้ดของคนอื่นในโปรเจกต์ของคุณสำเร็จแล้ว — และนี่คือทั้งหมดที่ npm ทำให้เรา

dependencies กับ devDependencies ต่างกันอย่างไร

แพ็กเกจแบ่งได้เป็นสองกลุ่มตามว่า “ผู้ใช้ปลายทางต้องการมันด้วยหรือไม่”

npm install react           # → dependencies
npm install -D vite         # → devDependencies (ใช้ --save-dev ก็ได้)
  • dependencies — โค้ดที่ต้องมีตอนแอปทำงานจริง เช่น React เพราะถ้าไม่มีมันแอปก็รันไม่ได้
  • devDependencies — เครื่องมือที่ใช้เฉพาะตอนพัฒนา เช่น Vite, Prettier, ESLint, Vitest ผู้ใช้ที่เปิดเว็บของคุณไม่ต้องโหลดสิ่งเหล่านี้เลย เพราะมันทำงานจบไปตั้งแต่ตอน build บนเครื่องเราแล้ว

💡 แยกให้ถูกตั้งแต่แรกจะดีกว่ามาแก้ทีหลัง เพราะถ้าใส่เครื่องมือพัฒนาไว้ใน dependencies เซิร์ฟเวอร์ที่ deploy จะเสียเวลาติดตั้งของที่ไม่จำเป็นทุกครั้ง ในบทถัด ๆ ไปเราจะติดตั้ง Prettier, ESLint และ Vite ด้วย -D เสมอ ส่วน React จะไม่ใส่ -D

เข้าใจเลขเวอร์ชัน (semver)

เปิด package.json ในโฟลเดอร์ทดลอง คุณจะเห็นเลขเวอร์ชันหน้าตาแบบ "dayjs": "^1.11.13" ตัวเลขสามชุดนี้เรียกว่า semantic versioning หรือ semver อ่านว่า

1  .  11  .  13
│      │      └── PATCH — แก้บั๊ก ไม่กระทบการใช้งานเดิม
│      └───────── MINOR — เพิ่มความสามารถใหม่ ของเดิมยังใช้ได้
└──────────────── MAJOR — มีการเปลี่ยนแปลงที่ทำให้โค้ดเดิมพัง

ส่วนสัญลักษณ์ข้างหน้าบอกว่าเรายอมให้อัปเดตไปได้ไกลแค่ไหน

ที่เขียนไว้ ความหมาย เวอร์ชันที่ยอมรับ
^1.11.13 อัปเดต minor และ patch ได้ (ค่าเริ่มต้นของ npm) 1.11.13 ถึงต่ำกว่า 2.0.0
~1.11.13 อัปเดตเฉพาะ patch 1.11.13 ถึงต่ำกว่า 1.12.0
1.11.13 ล็อกเวอร์ชันนี้เท่านั้น 1.11.13 เท่านั้น

ถ้าอยากติดตั้งเวอร์ชันเจาะจง ให้ใส่ @ ตามด้วยเวอร์ชัน เช่น npm install react@18.3.1 ซึ่งเป็นวิธีที่เราจะใช้ในบทเรื่อง Vite เพื่อให้ทุกคนได้ผลลัพธ์ตรงกัน

package-lock.json สำคัญอย่างไร

สังเกตว่า ^1.11.13 ไม่ได้ระบุเวอร์ชันตายตัว ถ้าเพื่อนร่วมทีมของคุณติดตั้งโปรเจกต์เดียวกันในอีกสองเดือน เขาอาจได้ 1.12.0 ซึ่งไม่ใช่ตัวเดียวกับที่คุณทดสอบไว้ นี่คือต้นตอของประโยคอมตะที่ว่า “แต่บนเครื่องผมมันรันได้นะ”

package-lock.json แก้ปัญหานี้ด้วยการจดเวอร์ชันที่ถูกติดตั้ง จริง เอาไว้ทุกตัว เมื่อไฟล์นี้อยู่ใน Git ทุกคนที่ npm install จะได้ต้นไม้แพ็กเกจชุดเดียวกันเป๊ะ

npm install   # อ่าน package.json ติดตั้ง และอัปเดต lockfile ได้
npm ci        # อ่าน package-lock.json อย่างเดียว ติดตั้งแบบเป๊ะ ๆ

npm ci (ย่อจาก clean install) จะลบ node_modules แล้วติดตั้งใหม่ตาม lockfile เป๊ะ ๆ โดยไม่แก้ไขอะไรเลย จึงเป็นคำสั่งที่ระบบ CI/CD และเซิร์ฟเวอร์ deploy ใช้กัน ส่วนบนเครื่องเราตอนพัฒนาให้ใช้ npm install ตามปกติ

🚨 อย่าแก้ package-lock.json ด้วยมือ และอย่าลบทิ้งเพื่อแก้ปัญหา ให้ปล่อยให้ npm จัดการ ถ้าติดตั้งแล้วมีปัญหาแปลก ๆ วิธีล้างที่ปลอดภัยคือลบ node_modules ทิ้งแล้วรัน npm install ใหม่

อย่าเอา node_modules ขึ้น Git

โฟลเดอร์ node_modules มีขนาดใหญ่มาก (หลักร้อย MB ได้ง่าย ๆ) มีไฟล์เป็นหมื่น และสร้างใหม่ได้เสมอจาก package.json กับ package-lock.json จึงไม่มีเหตุผลที่จะเก็บมันไว้ในระบบควบคุมเวอร์ชัน

สร้างไฟล์ชื่อ .gitignore ที่ root ของ pizza-app แล้วใส่

node_modules/

เราจะพูดถึง .gitignore อย่างละเอียดอีกครั้งในบทเรื่อง Git แต่ใส่บรรทัดนี้ไว้ก่อนได้เลย เพราะเราจะเริ่มติดตั้งแพ็กเกจกันในบทถัดไป

npm scripts: คำสั่งลัดของโปรเจกต์

ช่อง scripts ใน package.json ให้เราตั้งชื่อย่อให้คำสั่งยาว ๆ ได้ ลองแก้ package.json ของโฟลเดอร์ทดลองเป็นแบบนี้

"scripts": {
  "start": "node test.js",
  "greet": "echo สวัสดีจาก npm script"
}

แล้วเรียกใช้ด้วย

npm run greet
npm run start   # หรือเขียนสั้น ๆ ว่า npm start ก็ได้

ข้อดีที่ทำให้ทุกโปรเจกต์ใช้ scripts กัน

  • คนที่เพิ่งเข้าโปรเจกต์ไม่ต้องมานั่งจำคำสั่งยาว ๆ พร้อม option เต็มไปหมด แค่เปิดดู scripts ก็รู้ว่าโปรเจกต์นี้ทำอะไรได้บ้าง
  • ภายใน script คุณเรียกคำสั่งของแพ็กเกจใน node_modules ได้ตรง ๆ โดยไม่ต้องติดตั้งแบบ global
  • ชื่อ start, test, build, dev เป็นชื่อที่ใช้กันเป็นมาตรฐาน ควรใช้ตามธรรมเนียม

ในบทถัด ๆ ไปเราจะเพิ่ม scripts สำหรับ format โค้ด ตรวจ lint รัน dev server และรันเทสต์ จนสุดท้ายโปรเจกต์ทั้งหมดสั่งงานได้จาก npm run เพียงคำสั่งเดียว

npx คืออะไร

คุณเห็นคำสั่ง npx serve ไปแล้วในบทที่ 2 npx คือเครื่องมือที่ติดมากับ npm ไว้สำหรับ รัน แพ็กเกจโดยไม่ต้องติดตั้งถาวร มันจะหาแพ็กเกจใน node_modules ของโปรเจกต์ก่อน ถ้าไม่เจอก็จะดาวน์โหลดมาใช้ชั่วคราวแล้วลบทิ้ง

npx prettier --write src/App.js   # รันครั้งเดียว ไม่ต้องติดตั้งค้างไว้
npm install -g prettier           # ติดตั้งถาวรทั้งเครื่อง

โดยทั่วไป ควรหลีกเลี่ยงการติดตั้งแบบ global (-g) เพราะแต่ละโปรเจกต์อาจต้องใช้เครื่องมือคนละเวอร์ชันกัน การติดตั้งเป็น devDependency ของโปรเจกต์แล้วเรียกผ่าน npm script หรือ npx จะทำให้ทุกคนในทีมได้เวอร์ชันเดียวกันเสมอ

คำสั่งที่ใช้บ่อย

คำสั่ง ทำอะไร
npm init -y สร้าง package.json ด้วยค่าเริ่มต้น
npm install ติดตั้งทุกอย่างที่ระบุไว้ใน package.json
npm install <ชื่อ> เพิ่มแพ็กเกจเข้า dependencies
npm install -D <ชื่อ> เพิ่มแพ็กเกจเข้า devDependencies
npm uninstall <ชื่อ> ถอนแพ็กเกจออกจากโปรเจกต์
npm outdated ดูว่าแพ็กเกจไหนมีเวอร์ชันใหม่กว่าที่ใช้อยู่
npm update อัปเดตแพ็กเกจภายในขอบเขตที่ semver อนุญาต
npm ls แสดงต้นไม้ของแพ็กเกจที่ติดตั้งอยู่
npm run <ชื่อ script> รัน script ที่ตั้งไว้ใน package.json
npx <ชื่อ> รันแพ็กเกจโดยไม่ติดตั้งถาวร

ทางเลือกอื่นนอกจาก npm

ยังมี package manager ตัวอื่นที่ใช้ registry เดียวกันและอ่าน package.json รูปแบบเดียวกัน ที่พบบ่อยคือ pnpm ซึ่งประหยัดพื้นที่ดิสก์และติดตั้งเร็วกว่าด้วยการใช้ symlink ชี้ไปยังคลังกลางแทนการคัดลอกไฟล์ซ้ำทุกโปรเจกต์ และ Yarn ซึ่งเคยเป็นตัวเลือกหลักในยุคที่ npm ยังช้า

ทั้งหมดใช้งานได้ดี และแนวคิดที่คุณเรียนในบทนี้ใช้ได้กับทุกตัว หลักสูตรนี้จะใช้ npm ตลอด เพราะมันติดมากับ Node.js อยู่แล้วไม่ต้องติดตั้งเพิ่ม

🚨 ข้อควรระวัง: เลือกใช้ตัวเดียวต่อหนึ่งโปรเจกต์ อย่าสลับไปมา เพราะแต่ละตัวสร้าง lockfile คนละไฟล์ (package-lock.json, pnpm-lock.yaml, yarn.lock) การมีหลาย lockfile ในโปรเจกต์เดียวเป็นบ่อเกิดของปัญหาที่หาสาเหตุยากมาก

ลองทำเอง

  1. ในโฟลเดอร์ทดลอง ลองรัน npm ls แล้วเทียบกับจำนวนโฟลเดอร์ใน node_modules ว่าทำไมถึงไม่เท่ากัน
  2. ติดตั้งเวอร์ชันเจาะจงด้วย npm install dayjs@1.11.0 แล้วเปิดดูว่า package.json กับ package-lock.json เปลี่ยนไปอย่างไร
  3. ลบ node_modules ทิ้งทั้งโฟลเดอร์ แล้วรัน npm install ใหม่ สังเกตว่าทุกอย่างกลับมาเหมือนเดิมได้จาก package.json — นี่คือเหตุผลที่เราไม่ต้องเก็บโฟลเดอร์นี้ไว้ใน Git
  4. เพิ่ม script ชื่อ hello ที่รัน node test.js แล้วเรียกด้วย npm run hello
  5. ถอนแพ็กเกจออกด้วย npm uninstall dayjs แล้วดูว่าส่วน dependencies หายไปหรือไม่ จากนั้นลองรัน node test.js อีกครั้งเพื่อดูว่า error หน้าตาเป็นอย่างไร

เสร็จแล้วลบโฟลเดอร์ npm-practice ทิ้งได้เลย ส่วน pizza-app ของเราตอนนี้ควรมี package.json และ .gitignore เตรียมไว้สำหรับบทถัดไป

สรุป

  • npm คือ registry, คำสั่ง command line และรูปแบบไฟล์ package.json ที่ทำงานร่วมกัน
  • package.json บอกว่าเราต้องการอะไร ส่วน package-lock.json บอกว่าเราได้อะไรมาจริง ๆ — ทั้งสองไฟล์ต้องอยู่ใน Git ส่วน node_modules ต้องไม่อยู่
  • แยก dependencies (สิ่งที่แอปต้องใช้ตอนรันจริง) ออกจาก devDependencies (เครื่องมือตอนพัฒนา) ให้ชัดเจน
  • เข้าใจ semver แล้วคุณจะรู้ว่า ^ กับ ~ เปิดช่องให้อะไรเปลี่ยนได้บ้าง
  • ใช้ npm scripts เป็นหน้าต่างสั่งงานของโปรเจกต์ และใช้ npx แทนการติดตั้งเครื่องมือแบบ global
