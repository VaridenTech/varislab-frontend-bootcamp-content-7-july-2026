React 19: สิ่งที่กำลังมาถึง

React 19

เราติดตั้ง React 19 กันไปตั้งแต่บทที่ 8 แล้ว และทุกอย่างที่เขียนมาตลอดคอร์สนี้ก็รันอยู่บนมัน แต่จนถึงตอนนี้เรายังไม่ได้แตะฟีเจอร์ที่ ใหม่ ใน React 19 เลยสักตัว บทนี้เป็นต้นไปเราจะไปดูของใหม่เหล่านั้นกัน

และนั่นแหละคือประเด็นที่ควรสังเกตก่อนอื่น: คุณเขียน React 19 มาทั้งคอร์สโดยไม่รู้ตัว เพราะแทบทุกอย่างที่เรียนมา — components, JSX, hooks, context, effects — ทำงานเหมือนเดิมทุกประการ ข้อดีของ React คือ แม้จะมี breaking changes แต่โดยทั่วไปทีมจะตั้งใจทำและทำอย่างประหยัด สิ่งที่คุณเรียนวันนี้จึงยังมีประโยชน์อีกห้าปีนับจากนี้ คุณหยิบคอร์ส React ที่สอนกันเมื่อห้าปีก่อนมาเรียน ก็ยังตามวิธีเขียน React ได้เกือบทั้งหมด ของใหม่ทั้งหมดใน React 19 เพียงเสริมสิ่งที่คุณเรียนมา ไม่ได้เปลี่ยนมัน

ฟีเจอร์ของ React 19 หลายตัวเป็นเรื่องระดับถัดไป บทนี้จะพาดูภาพรวมว่ามีอะไรใหม่บ้าง เพื่อให้คุณรู้จักชื่อของมันไว้ก่อน แล้วสามบทถัดไปเราจะลงมือเขียนโค้ดจริงกับสามตัวที่ใช้ได้ทันทีในแอปฝั่ง client ของเรา คือ form actions, use กับ Suspense และ React Compiler

💡 อีกเรื่องที่มาพร้อม React 19 และคุณได้ประโยชน์ไปแล้วโดยไม่รู้ตัวคือ type ของ React ถูกปรับปรุงครั้งใหญ่ ใน @types/react รุ่น 19 เช่น useRef บังคับให้ระบุค่าเริ่มต้นเสมอ, ReactElement ใช้ unknown แทน any เป็นค่าเริ่มต้นของ props, และ ref กลายเป็น prop ปกติที่ส่งผ่าน component ได้โดยไม่ต้องใช้ forwardRef อีกแล้ว ถ้าคุณไปเจอโค้ด React เก่าที่เขียนด้วย TypeScript แล้วเห็น forwardRef เต็มไปหมด นั่นคือรูปแบบก่อน React 19

อย่างแรก มาคุยถึงฟีเจอร์เจ๋ง ๆ บางตัวที่ไม่คุ้มกับการใช้เวลาเขียนโค้ดมากนักก่อน แล้วค่อยดูตัวที่เราจะเพิ่มโค้ดลงในแอปจริง

'use client' และ 'use server'

เริ่มด้วยหนึ่งในการเปลี่ยนแปลงใหญ่ของ React เรื่องนี้ลงลึกได้อีกมากและเป็นหัวข้อระดับถัดไป ในบทนี้เราจะดูแค่แนวคิดคร่าว ๆ ก่อน โดยพื้นฐานเราสามารถบอก React ได้ว่า “เฮ้ รัน component นี้บน server เท่านั้น” หรือกลับกัน “เฮ้ render เฉพาะฝั่ง client” ทำไปทำไม?

สำหรับ server components เราทำสิ่งต่าง ๆ เช่นอ้างอิง secrets ฝั่ง server, query database, เรียก private APIs หรือสิ่งอื่นที่แอปฝั่ง client ต้องการข้อมูล แต่ไม่สามารถ query จาก client ได้โดยไม่เสี่ยงทำ secrets รั่วหรือโดน DDOS logic ทั้งหมดจะทำงานบน server แล้วส่ง component ที่เสร็จแล้วมายัง client เจ๋งใช่ไหม?

พวกเขาไปไกลกว่านั้นด้วย taintUniqueValue และ taintObjectReference ซึ่งให้ developer บอกว่า “นี่เป็นข้อมูลที่ละเอียดอ่อนมาก ให้แน่ใจว่าไม่ส่งไปยัง client เด็ดขาด” คุณจะใช้กับ API key, database connection string หรือ secret อื่นที่ไม่อยากรั่วโดยไม่ตั้งใจ แนวคิดนี้เข้าท่ามาก เพราะถ้า developer เปลี่ยน directive 'use server' เป็น 'use client' ล่ะ? เขาอาจไม่สังเกตแล้วส่งขึ้น production จนเกิด data breach ได้ แนวคิด taint ทำให้แน่ใจได้ว่าจะไม่เกิดเช่นนั้น

'use client' คือด้านตรงข้าม — สิ่งที่ไม่มีเหตุผลจะ render บน server ลองนึกถึง component ที่ interactive มาก เช่น text editor หรือ maps widget — มันควรเป็นประสบการณ์ฝั่ง client ดังนั้นส่งทุกอย่างไปยัง client ทันทีแล้วปล่อยให้เขา render จะดีกว่า จำไว้ว่าไม่จำเป็นต้องใช้ directive นี้ เว้นแต่ว่าคุณทำ server-side rendering โดยค่าเริ่มต้น React ยังคงทำ client-side rendering อยู่

วางสิ่งต่าง ๆ ใน head

ลองจินตนาการว่าคุณอยากให้ React component เพิ่ม <link>, <meta>, <title> หรือ HTML อื่นใน document ปัจจุบันคุณต้องใช้ portal หรือบางอย่างอย่าง react-helmet เพื่อทำสิ่งนี้ แต่ใน React 19 คุณแค่ render tag แล้วมันจะเข้าไปอยู่ใน header โดยอัตโนมัติ

const MyPizza = () => (
  <div>
    <h1>I love pizza</h1>
    <title>🍕 Brian Loves Pizza 🍕</title>
  </div>
);

ตอนที่ MyPizza ถูก render มันจะเปลี่ยน title ของ document (ซึ่งแสดงบน browser tab)

preload และ preconnect

เป็นสอง functions ที่มีประโยชน์มากสำหรับ hint ให้ browser รู้ว่าอาจต้องเริ่มโหลดอะไรบางอย่างเบื้องหลัง หากไม่คุ้นกับแนวคิดนี้ สรุปสั้น ๆ คือใช้กับ images, fonts, scripts, stylesheets และอื่น ๆ คุณบอก browser ได้ว่า “เฮ้ เราน่าจะต้องโหลดสิ่งนี้เร็ว ๆ นี้ ช่วย preconnect URL นี้เพื่อเตรียม download หรือ preload ไปเลยได้ไหม?” ผู้ใช้จึงได้ประสบการณ์ที่แทบจะทันที เพราะไม่ต้องรอโหลดเมื่อต้องใช้ จำไว้ว่านี่เป็นเพียง hints browser สามารถไม่สนใจได้ ตัวอย่างที่ดีคือโทรศัพท์อยู่ใน low-power mode อาจไม่สนใจ hint เพราะอยากประหยัดแบตเตอรี่

const EnterConfirmation = () => {
  preload("https://example.com/text-editor.js", { as: "script" });
  return (
    <div>
      <a href="/text-editor">Click here to open the text editor</a>
    </div>
  );
};

Custom components (หรือ web components)

ตามทฤษฎีแล้ว เราใช้ web components กับ React ได้เสมอ แต่เคยยุ่งยากมาก ต้องใช้ refs และวางแผนอย่างระมัดระวังเพื่อไม่ให้เผลอ un-render แล้ว re-render มัน สรุปคือทำได้ แต่ไม่สะดวกใช้งาน

React 19 จะจัดการการดูแล custom elements ทั้งหมดให้คุณ เพียงปฏิบัติกับมันเหมือน tag ปกติ แล้ว React จะคอยดูแลให้ เป็นก้าวใหญ่ในการทำให้ custom elements ใช้ได้ข้าม Angular, React, Svelte ฯลฯ แต่ก็ไม่รู้สิ วงการพูดถึง custom elements กันมาสิบกว่าปีแล้ว ตั้งแต่ยุค Polymer แต่มันก็ยังไม่แพร่หลายสักที
