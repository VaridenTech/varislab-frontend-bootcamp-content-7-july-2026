การทดสอบแบบ Snapshot

Snapshot Testing

ฉันไม่ใช่แฟนของการไล่หา 100% test coverage ฉันคิดว่ามันเป็นการไล่ตามสิ่งที่ไร้ประโยชน์และเสียเวลา ฉันอยากให้คุณเขียนห้า tests ที่ครอบคลุมห้าบรรทัดสำคัญที่สุดของ code มากกว่าเห็นคุณเขียนหนึ่ง test สำหรับ UI code ห้าชิ้นที่สำคัญน้อยกว่า

แต่เรามาดูวิธีโกงง่าย ๆ เพื่อไปถึงจุดนั้นกัน! มาคุยเรื่อง snapshot testing

Snapshot tests เป็นวิธีเขียน tests ที่ความมั่นใจต่ำ ต้นทุนต่ำ ด้วย code บรรทัดเดียวโดยประมาณ คุณ assert ได้ว่า: code นี้ไม่พัง และมันไม่ได้เปลี่ยนไปตามเวลา

มาทดสอบ Cart.jsx มันเป็น component ที่ค่อนข้างเสถียร ทำไม่มาก และเราไม่คาดว่ามันจะเปลี่ยนมากนักหรือเปลี่ยนเลย test ต้นทุนต่ำ ความมั่นใจต่ำจึงเหมาะตรงนี้ สร้าง file ชื่อ Cart.test.jsx

import { expect, test } from "vitest";
import { render } from "@testing-library/react";
import Cart from "../Cart";

test("snapshot with nothing in cart", () => {
  const { asFragment } = render(<Cart cart={[]} />);
  expect(asFragment()).toMatchSnapshot();
});

รันสิ่งนี้เพื่อดู Vitest บอกว่ามันสร้าง snapshot แล้ว ไปดู Cart.test.jsx.snap ใน src/__tests__/__snapshots__ เพื่อดูสิ่งที่มันสร้าง คุณจะเห็นว่ามันแค่ render หน้าตาที่ออกมา ตอนนี้ถ้าคุณแก้ Cart.jsx มันจะ fail test อย่างที่เห็น นี่คือ gut check เร็ว ๆ เพื่อให้แน่ใจว่าการเปลี่ยนแปลงของคุณไม่มีปัญหาลูกโซ่ ถ้าฉันแก้ App.jsx แล้วทำให้สิ่งนี้ fail ก็หมายความว่าฉันจับและตรวจสอบได้เร็ว บางคนไม่เห็นว่ามีประโยชน์ พูดตรง ๆ ฉันเองก็ยังไม่เชื่อทั้งหมด; อย่างมากที่สุดควรใช้อย่างจำกัดมาก สิ่งนี้อาจมีประโยชน์หากคุณมี component ที่คาดว่าจะ ไม่เคย เปลี่ยน และจะเป็นปัญหาหากมันเปลี่ยน อาจเป็น footer? ไม่รู้สิ ฉันไม่เคยเขียนพวกนี้

สิ่งนี้ทำงาน และตอนนี้คุณจะใช้ต่อแบบนี้ก็ได้ แต่มีปัญหา หากดู snapshot ของคุณ มัน render Pizza components ด้วย ตอนนี้ถ้าคุณแก้ Pizza.jsx (ที่มี tests ของตัวเองอยู่แล้ว) test Cart.jsx ของคุณจะ fail นี่ทำให้เข้าใจผิด ไม่มีอะไรผิดหรือเปลี่ยนกับ Cart.jsx ใน class เวอร์ชันก่อน ฉันแสดงวิธีทำสิ่งนี้ด้วย react-test-renderer อย่างไรก็ตามทีม @testing-lib คิดว่า shallow rendering ให้โทษมากกว่าประโยชน์ (ฉันเห็นด้วยราว 75%) เราจึงจะไม่ใส่มัน คลิกที่นี่ เพื่อดูฉันสอนเรื่องนี้ก่อนหน้านี้ มันเหมือนกัน 95% แค่ใช้ Jest แทน Vitest

อัปเดต snapshots ได้ด้วยการรัน npm run test -- -u หรือใช้ watcher ด้วย u เพื่ออัปเดตทั้งหมดทีเดียว หรือทำทีละอันด้วย i

คุณควร commit snapshot files เข้า git

ฉันจะปล่อยให้คุณตัดสินว่าคุณให้คุณค่ากับ tests เหล่านี้มากแค่ไหน ฉันคิดว่ามันมีที่เล็กมากในการทดสอบ UI แต่ช่วยได้น้อยมาก บ่อยครั้งมันกลายเป็น noise มากกว่าความช่วยเหลือ ไม่ว่าอย่างไร เก็บมันไว้ใน toolbox ของคุณ บางครั้งมันก็ช่วยได้

เกร็ดเพิ่มเติม: ที่หนึ่งที่ฉันเห็น snapshot tests มีประโยชน์บ้าง (เพราะมันติดตาม object shape ใดก็ได้ตามเวลา ไม่ใช่แค่ React components) คือ backend ใน API response shapes เราจะเขียน snapshot test ว่า API response นี้จะหน้าตาแบบนี้เสมอ และควร fail test หากมันพัง สิ่งนี้ทำให้ทุกครั้งที่คุณแก้ API response เป็นไปอย่างตั้งใจมาก (เพราะ API clients ของคุณน่าจะพึ่งพาให้มันมี shape แบบหนึ่ง) ยิ่งกว่านั้น มันหมายความว่า frontend devs ใช้ snapshot files เหล่านี้เพื่อดูว่า API response จะมีหน้าตาแบบใดได้ เฉพาะทาง แต่มีประโยชน์ใน project เดียวที่ฉันเคยทำซึ่งมีมัน
