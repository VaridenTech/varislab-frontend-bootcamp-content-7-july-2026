การทดสอบแบบ Snapshot

Snapshot Testing

การไล่ล่า 100% test coverage มักไม่คุ้มค่า เพราะเป็นการไล่ตามตัวเลขมากกว่าคุณภาพจริง ๆ เขียนห้า tests ที่ครอบคลุมห้าบรรทัดสำคัญที่สุดของโค้ด ยังมีค่ากว่าเขียนหนึ่ง test ให้ UI ห้าชิ้นที่สำคัญน้อยกว่า

แต่เรามาดูวิธีโกงง่าย ๆ เพื่อไปถึงจุดนั้นกัน! มาคุยเรื่อง snapshot testing

Snapshot tests เป็นวิธีเขียน tests ที่ความมั่นใจต่ำ ต้นทุนต่ำ ด้วย code บรรทัดเดียวโดยประมาณ คุณ assert ได้ว่า: code นี้ไม่พัง และมันไม่ได้เปลี่ยนไปตามเวลา

มาทดสอบ Cart.tsx มันเป็น component ที่ค่อนข้างเสถียร ทำไม่มาก และเราไม่คาดว่ามันจะเปลี่ยนมากนักหรือเปลี่ยนเลย test ต้นทุนต่ำ ความมั่นใจต่ำจึงเหมาะตรงนี้ สร้าง file ชื่อ Cart.test.tsx

import { expect, test } from "vitest";
import { render } from "@testing-library/react";
import Cart from "../Cart";

test("snapshot with nothing in cart", () => {
  const { asFragment } = render(<Cart cart={[]} />);
  expect(asFragment()).toMatchSnapshot();
});

รันสิ่งนี้เพื่อดู Vitest บอกว่ามันสร้าง snapshot แล้ว ไปดู Cart.test.tsx.snap ใน src/__tests__/__snapshots__ เพื่อดูสิ่งที่มันสร้าง คุณจะเห็นว่ามันแค่ render หน้าตาที่ออกมา ตอนนี้ถ้าคุณแก้ Cart.tsx มันจะ fail test อย่างที่เห็น นี่คือ gut check เร็ว ๆ เพื่อให้แน่ใจว่าการเปลี่ยนแปลงของคุณไม่มีปัญหาลูกโซ่ ถ้าคุณแก้ App.tsx แล้วทำให้สิ่งนี้ fail ก็แปลว่าคุณจับความเปลี่ยนแปลงได้เร็ว หลายคนไม่เห็นว่ามันมีประโยชน์ และควรใช้อย่างจำกัดมาก มันจะเข้าท่าก็ต่อเมื่อคุณมี component ที่คาดว่าจะ ไม่เคย เปลี่ยน และจะเป็นปัญหาถ้ามันเปลี่ยน เช่น footer เป็นต้น

มาเพิ่ม pizzas แล้วดูว่ามันเป็นอย่างไร คราวนี้เราจะแยกข้อมูลทดสอบออกมาเป็นตัวแปรที่มี type ก่อน ด้วยเหตุผลเดียวกับที่คุยกันในบทที่ 26 — ข้อมูลทดสอบที่ผูกกับ type จริงจะไม่มีวันเก่าโดยที่เราไม่รู้ตัว

ลองสังเกตว่า size: "M" ผ่านได้ทั้งที่ CartItem.size เป็น PizzaSize ไม่ใช่ string — นั่นเพราะเราประกาศ const cartItems: CartItem[] ไว้ TypeScript จึงรู้ว่าควรตีความ "M" เป็นค่าหนึ่งใน union ไม่ใช่ string ทั่วไป ลองเปลี่ยนเป็น size: "XL" ดู จะเห็นว่ามันจับได้ทันที

สิ่งนี้ทำงาน และตอนนี้คุณจะใช้ต่อแบบนี้ก็ได้ แต่มีปัญหา หากดู snapshot ของคุณ มัน render Pizza components ด้วย ตอนนี้ถ้าคุณแก้ Pizza.tsx (ที่มี tests ของตัวเองอยู่แล้ว) test Cart.tsx ของคุณจะ fail นี่ทำให้เข้าใจผิด ไม่มีอะไรผิดหรือเปลี่ยนกับ Cart.tsx ทางออกหนึ่งที่เคยนิยมคือ shallow rendering ซึ่ง render เฉพาะ component ชั้นบนสุดโดยไม่ลงไปถึง component ลูก อย่างไรก็ตามทีม @testing-library มองว่า shallow rendering ให้โทษมากกว่าประโยชน์ เพราะมันทดสอบสิ่งที่ผู้ใช้ไม่เคยเห็นจริง เราจึงจะไม่ใช้มัน

อัปเดต snapshots ได้ด้วยการรัน npm run test -- -u หรือใช้ watcher ด้วย u เพื่ออัปเดตทั้งหมดทีเดียว หรือทำทีละอันด้วย i

คุณควร commit snapshot files เข้า git

คุณตัดสินเองได้ว่าให้คุณค่ากับ tests เหล่านี้มากแค่ไหน โดยรวมแล้วมันพอมีที่ทางอยู่บ้างในการทดสอบ UI แต่ช่วยได้ไม่มาก บ่อยครั้งมันกลายเป็น noise มากกว่าความช่วยเหลือ ไม่ว่าอย่างไร เก็บมันไว้ใน toolbox ของคุณ บางครั้งมันก็ช่วยได้

เกร็ดเพิ่มเติม: จุดหนึ่งที่ snapshot tests มีประโยชน์ชัดเจน (เพราะมันติดตาม object shape ใดก็ได้ตามเวลา ไม่ใช่แค่ React components) คือ backend ใน API response shapes เราจะเขียน snapshot test ว่า API response นี้จะหน้าตาแบบนี้เสมอ และควร fail test หากมันพัง สิ่งนี้ทำให้ทุกครั้งที่คุณแก้ API response เป็นไปอย่างตั้งใจมาก (เพราะ API clients ของคุณน่าจะพึ่งพาให้มันมี shape แบบหนึ่ง) ยิ่งกว่านั้น มันหมายความว่า frontend devs ใช้ snapshot files เหล่านี้เพื่อดูว่า API response จะมีหน้าตาแบบใดได้ เฉพาะทางมาก แต่ในโปรเจกต์ที่ใช้แบบนี้ก็ช่วยได้จริง
