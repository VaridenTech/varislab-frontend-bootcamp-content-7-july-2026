Effects

ตอนนี้เรามีแอปมากพอที่จะเริ่มทำ API requests ได้แล้ว เราต้องการให้แอปขอ pizzaTypes ชุดแรกเมื่อหน้าโหลดครั้งแรก ดังนั้นมาทำสิ่งนั้นด้วย hook พิเศษชื่อ useEffect useEffect ให้คุณบอกว่า render component นี้ก่อนเพื่อให้ผู้ใช้เห็นบางอย่าง แล้วทันทีที่ render เสร็จ จึงทำบางอย่าง (สิ่งนั้นในที่นี้คือ effect) กรณีของเรา เราต้องการให้ผู้ใช้เห็น UI ก่อน แล้วจึง request ไปยัง API เพื่อเริ่มต้นรายการ pizzas

คุณรู้จัก async/await, Promise และ fetch มาแล้วจากบทที่ 11 และ 12 ดังนั้นโค้ดที่ยิง request ในบทนี้จะคุ้นตาทั้งหมด ของใหม่จริง ๆ ในบทนี้มีอย่างเดียวคือ useEffect — วิธีบอก React ว่า "หลัง render เสร็จแล้วค่อยไปทำสิ่งนี้"
ต้องแน่ใจว่าคุณให้ทั้ง Vite dev server และ API server ทำงานอยู่ ทั้งคู่

ตอนนี้ข้อมูลจะเริ่มมาจาก API แล้ว ก่อนอื่นเราต้องบอก TypeScript ว่าพิซซ่าหนึ่งลูกที่ API ส่งมาหน้าตาเป็นอย่างไร เปิด src/types.ts แล้วเพิ่ม type ใหม่ต่อจาก PizzaSize

export type PizzaSize = "S" | "M" | "L";

export type Pizza = {
  id: string;
  name: string;
  category: string;
  description: string;
  image: string;
  sizes: Record<PizzaSize, number>;
};
  • Record<PizzaSize, number> อ่านว่า "object ที่มี key เป็น PizzaSize ทุกตัว และ value เป็น number" ซึ่งก็คือ { S: number; M: number; L: number } นั่นเอง เขียนแบบยาวก็ได้ แต่แบบนี้ผูกกับ PizzaSize ไว้ ถ้าวันหนึ่งเราเพิ่มขนาด XL เข้าไปใน union มันจะบังคับให้แก้ทุกที่ที่เกี่ยวข้องให้ครบเอง
  • ประโยชน์ที่ได้ทันทีคือ selectedPizza.sizes[pizzaSize] จะทำงานได้โดยไม่ต้อง cast อะไรเลย เพราะ pizzaSize ของเราเป็น PizzaSize อยู่แล้ว — type สองตัวนี้เข้ากันได้พอดี
⚠️ ข้อควรรู้ที่สำคัญ: type ที่เราเขียนนี้เป็นเพียงความเชื่อของเราว่า API จะส่งอะไรกลับมา TypeScript ตรวจสอบให้ได้แค่ตอน compile มันไม่ได้ไปตรวจ response จริงตอนรัน ถ้า API เปลี่ยนรูปแบบข้อมูล โค้ดจะพังตอนรันเหมือนเดิม (ในระบบจริงที่ต้องการความมั่นใจระดับนั้น คนนิยมใช้ library อย่าง Zod มาตรวจ response จริง ๆ ซึ่งอยู่นอกขอบเขตคอร์สนี้)

// change import at top
import { useEffect, useState } from "react";
import Pizza from "./Pizza";
import type { Pizza as PizzaType, PizzaSize } from "./types";

// outside of the render function
// feel free to change en-US / USD to your locale
const intl = new Intl.NumberFormat("en-US", {
  style: "currency",
  currency: "USD",
});

// add to the other useStates inside component at top
const [pizzaTypes, setPizzaTypes] = useState<PizzaType[]>([]);
const [loading, setLoading] = useState<boolean>(true);

const selectedPizza = pizzaTypes.find((pizza) => pizzaType === pizza.id);
const price = selectedPizza
  ? intl.format(selectedPizza.sizes[pizzaSize])
  : "";

useEffect(() => {
  fetchPizzaTypes();
}, []);

async function fetchPizzaTypes() {
  await new Promise((resolve) => setTimeout(resolve, 3000)); // remove this later, just to show you the loading state

  const pizzasRes = await fetch("/api/pizzas");
  const pizzasJson: PizzaType[] = await pizzasRes.json();
  setPizzaTypes(pizzasJson);
  setLoading(false);
}

// replace the options
{
  pizzaTypes.map((pizza) => (
    <option key={pizza.id} value={pizza.id}>
      {pizza.name}
    </option>
  ));
}

// replace <Pizza /> and button at the end

🌐 Intl คือ built-in API ของ JavaScript เอง (ไม่ต้องติดตั้ง library เพิ่ม) ใช้จัดรูปแบบข้อมูลให้เข้ากับภาษา/ภูมิภาคต่าง ๆ (internationalization) เช่น ตัวเลข วันที่ เวลา และสกุลเงิน ที่นี่เราใช้ Intl.NumberFormat พร้อม style: "currency" เพื่อแปลงตัวเลขธรรมดาอย่าง 13.37 ให้กลายเป็นข้อความราคาที่อ่านง่ายอย่าง "$13.37" โดยอัตโนมัติ — เปลี่ยน locale ("en-US") และ currency ให้ตรงกับภูมิภาคของคุณได้ตามสบาย เราสร้าง intl ไว้นอก component (ไม่ใช่ข้างในระหว่าง render) เพราะการสร้าง formatter แบบนี้มีต้นทุนเล็กน้อย จึงอยากสร้างมันแค่ครั้งเดียวตอนโหลดไฟล์ ไม่ใช่สร้างใหม่ทุกครั้งที่ component render

⏱️ บรรทัด await new Promise((resolve) => setTimeout(resolve, 3000)) คือ wait helper ตัวเดียวกับที่เราสร้างเองในบทที่ 11 นั่นแหละ มันคือการหน่วงเวลาปลอม ๆ 3 วินาที เพื่อให้เห็นสถานะ Loading ชัด ๆ ไม่ได้มีประโยชน์อะไรกับแอปจริง อย่าลืมลบทิ้งเมื่อดูเสร็จแล้ว (อีกวิธีที่ไม่ต้องแก้โค้ดคือใช้ Network throttling แบบ Slow 3G จากบทที่ 12)

📌 สังเกตว่า fetchPizzaTypes ด้านบนไม่มีทั้งการเช็ค res.ok และ try / catch ที่บทที่ 12 ยืนกรานว่าต้องทำทุกครั้งไม่มีข้อยกเว้น — ตัดออกโดยตั้งใจ เพื่อให้บทนี้โฟกัสอยู่ที่ useEffect เพียงอย่างเดียว นี่ไม่ใช่การกลับคำ กฎของบทที่ 12 ยังใช้ได้เต็มร้อยกับแอปจริงเสมอ เพียงแต่ในบทที่ 19 เราจะเปลี่ยนไปใช้ TanStack Query ซึ่งจัดการ loading และ error state ให้อย่างถูกต้องอยู่แล้ว คอร์สนี้จึงไม่ลงมือสร้างกลไกพวกนั้นเองด้วยมือตรงนี้

ทำไมโค้ดชุดนี้ถึงต่างจากต้นฉบับ JavaScript

ถ้าคุณเคยเห็นเวอร์ชัน JavaScript ของบทนี้มาก่อน จะสังเกตว่าตรง selectedPizza เราเขียนไม่เหมือนกัน ต้นฉบับเขียนแบบนี้

let price, selectedPizza;
if (!loading) {
  selectedPizza = pizzaTypes.find((pizza) => pizzaType === pizza.id);
  price = intl.format(selectedPizza.sizes[pizzaSize]);
}

โค้ดนี้จะไม่ผ่าน TypeScript และเหตุผลที่มันไม่ผ่านคือเรื่องที่ควรรู้จริง ๆ: Array.find() คืน undefined ได้ ถ้าหาไม่เจอ type ของ selectedPizza จึงเป็น PizzaType | undefined ไม่ใช่ PizzaType การเขียน selectedPizza.sizes ต่อไปเลยจึงโดนฟ้องว่า 'selectedPizza' is possibly 'undefined'

และมันไม่ได้จู้จี้เกินเหตุ ลองนึกถึงจังหวะที่ข้อมูลเพิ่งโหลดเสร็จแต่ pizzaType ยังเป็น "pepperoni" ที่เราตั้งไว้ ถ้า API ไม่มีพิซซ่า id นั้น find จะคืน undefined แล้วแอปจะพังทั้งหน้าด้วย Cannot read properties of undefined ทันที การที่ loading เป็น false ไม่ได้แปลว่าหาพิซซ่าเจอ — TypeScript แค่ชี้ให้เห็นว่าเราสับสนสองเรื่องนี้เข้าด้วยกัน

เราจึงใช้เงื่อนไขที่เช็คสิ่งที่เราสนใจจริง ๆ แทน คือ "มี selectedPizza หรือเปล่า" กลไกนี้เรียกว่า type narrowing — เมื่อ TypeScript เห็นว่าคุณเช็ค selectedPizza แล้ว มันจะรู้เองว่าในกิ่ง true ค่านั้นเป็น PizzaType แน่นอน และปล่อยให้คุณเขียน .sizes ได้โดยไม่บ่น

💡 เราเปลี่ยนจาก let + if มาเป็น const + ternary ด้วย ไม่ใช่แค่เรื่องความสวยงาม — const ช่วยให้ TypeScript ทำ narrowing ได้แม่นยำกว่ามาก เพราะมันมั่นใจได้ว่าค่าจะไม่ถูกเปลี่ยนทีหลัง เป็นนิสัยที่ติดไว้แล้วดีตลอด

อีกจุดคือ const pizzasJson: PizzaType[] = await pizzasRes.json() เมธอด .json() คืน Promise<any> เสมอ เพราะไม่มีทางรู้ล่วงหน้าว่า server จะส่งอะไรมา การใส่ type annotation ตรงนี้คือจุดที่เรา "ประกาศความเชื่อ" ว่าข้อมูลหน้าตาแบบไหน และตั้งแต่บรรทัดนั้นเป็นต้นไปทุกอย่างก็จะมี type ครบ

🔍 import type { Pizza as PizzaType } — เราเปลี่ยนชื่อตอน import เพราะในไฟล์นี้ชื่อ Pizza ถูกใช้ไปแล้วโดย component ที่เรา import มาจาก ./Pizza การชนกันแบบนี้เกิดขึ้นบ่อยมากในโปรเจกต์จริง คำว่า as ในบริบทของ import ไม่เกี่ยวกับ type assertion ที่เราคุยกันในบทที่ 10 เลย มันคือการตั้งชื่อเล่นให้สิ่งที่ import มาเฉย ๆ

  • เราใส่ logic ทั้งหมดสำหรับการดึง pizza types ไว้ใน async function เพื่อให้อ่านง่ายขึ้น คุณทำให้ function ที่ส่งให้ useEffect เป็น async ไม่ได้
  • [] ท้าย useEffect คือที่ประกาศ data dependencies React ต้องการรู้ว่าเมื่อไรต้องรัน effect นั้นอีก หากไม่ให้ data dependencies มันจะสมมติว่าทุกครั้งที่ hook ใด ๆ เปลี่ยนควรรัน effect อีก นี่ไม่ดี เพราะหมายความว่าทุกครั้งที่เรียก setPizzaTypes มันจะรัน render และ hooks ทั้งหมดอีก เห็นปัญหาไหม? มันจะรันไม่สิ้นสุด เพราะ fetchPizzaTypes เรียก setPizzaTypes
  • แทนที่คุณจะบอกว่าต้องเฝ้าดู hooks ใดเพื่อหาการเปลี่ยนแปลงได้ กรณีของเรา เราต้องการให้มันรันเพียงครั้งเดียว ตอนสร้าง component แล้วไม่ต้องรัน effect นั้นอีก (เราจะทำ searching ภายหลังผ่านการคลิก submit button) คุณทำให้รันเพียงครั้งเดียวเมื่อสร้างได้ด้วยการให้ empty array
  • เราใช้ loading flag เพื่อแสดง data เมื่อพร้อมเท่านั้น อีกสักครู่เราจะใช้ TanStack Query เพื่อให้โค้ดนี้ดูสะอาดขึ้น แต่นี่คือวิธีแสดง/ซ่อน components แบบมีเงื่อนไขใน React
  • ส่วน key น่าสนใจ เมื่อ React render arrays ของสิ่งต่าง ๆ มันไม่รู้ว่าสิ่งใดเป็นของใหม่และสิ่งใดเพียงถูกจัดลำดับใหม่ใน array (ลองนึกถึงการเปลี่ยน sorting ของ results list เช่น ราคาเรียงสูงไปต่ำแล้วต่ำไปสูง) ด้วยเหตุนี้ หากคุณไม่บอก React ว่าจะจัดการสถานการณ์เหล่านั้นอย่างไร มันจะรื้อทั้งหมดและ re-render ทุกอย่างใหม่ ทำให้ devices ช้าลงโดยไม่จำเป็น นี่คือสิ่งที่ key มีไว้ให้ Key บอก React ว่า “นี่คือ identifier ง่าย ๆ ว่า component นี้คืออะไร” หาก React เห็นว่าคุณเพียงย้าย key ไปอยู่ลำดับอื่น มันจะเก็บ component tree ไว้ ดังนั้น key ที่นี่คือการผูก key เข้ากับสิ่งที่เป็นเอกลักษณ์ของ component นั้น 99/100 นี่คือ database ID บางชนิด อย่าใช้ index ของ array เพราะไม่ถูกต้อง เว้นแต่ array จะไม่เปลี่ยนลำดับเลยจริง ๆ

อัปเดต Pizza และ Price ที่เลือก

เมื่อ application โหลด เรายังไม่มี data ดังนั้นเราต้องการ render pizza และ price ที่เลือกเมื่อโหลดเสร็จแล้วเท่านั้น เพิ่ม condition ใน JSX เพื่อแสดง “Loading...” ตอนแรก จากนั้นแสดง pizza ที่เลือกเมื่อโหลดเสร็จ เพิ่ม condition ก่อน closing tag </form>:

...
  {
    loading || !selectedPizza ? (
      <h3>Loading...</h3>
    ) : (
      <div className="order-pizza">
        <Pizza
          name={selectedPizza.name}
          description={selectedPizza.description}
          image={selectedPizza.image}
        />
        <p>{price}</p>
      </div>
    )
  }
</form>

สังเกตเงื่อนไข loading || !selectedPizza — ถ้าเขียนแค่ loading ? เฉย ๆ อย่างในเวอร์ชัน JavaScript TypeScript จะฟ้องทันทีที่บรรทัด selectedPizza.name ว่า 'selectedPizza' is possibly 'undefined' เพราะมันมองไม่ออกว่า loading === false เกี่ยวอะไรกับการที่ find() จะหาเจอ

พอเราเติม || !selectedPizza เข้าไป narrowing ก็ทำงาน: ในกิ่ง else TypeScript รู้แน่นอนว่า selectedPizza ไม่ใช่ undefined และปล่อยให้เราเขียน .name, .description, .image ได้สบาย ๆ พร้อม auto-complete ครบทุกตัว

ผลพลอยได้คือแอปเราแข็งแรงขึ้นจริง ๆ ด้วย: ถ้า API ส่งรายการพิซซ่าที่ไม่มี pepperoni กลับมา ผู้ใช้จะเห็นข้อความ Loading ค้างไว้ แทนที่จะเห็นหน้าขาวเพราะแอปพัง เป็นตัวอย่างที่ดีมากว่าการทำให้ type ผ่านมักจะบังคับให้เราเขียนโค้ดที่ครอบคลุมกรณีจริงมากขึ้นไปด้วย
