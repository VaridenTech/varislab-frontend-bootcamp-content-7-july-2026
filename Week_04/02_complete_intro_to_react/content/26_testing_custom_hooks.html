การทดสอบ Custom Hooks

Testing Custom Hooks

สมมติว่าเราต้องการ tests สำหรับ custom hook ของเรา usePizzaOfTheDay การทดสอบ custom hooks มีเคล็ดเล็กน้อย เพราะมันผูกกับการทำงานภายในของ React โดยเนื้อแท้: เรียกมันนอก component ไม่ได้ แล้วเราจะเลี่ยงเรื่องนี้อย่างไร? เราปลอม component! สร้าง file ชื่อ usePizzaOfTheDay.test.tsx ใน __tests__ directory ของเรา

import { expect, test, vi } from "vitest";
import { render } from "@testing-library/react";
import createFetchMock from "vitest-fetch-mock";
import { usePizzaOfTheDay } from "../usePizzaOfTheDay";
import type { Pizza } from "../types";

const fetchMocker = createFetchMock(vi);
fetchMocker.enableMocks();

const testPizza: Pizza = {
  id: "calabrese",
  name: "The Calabrese Pizza",
  category: "Supreme",
  description:
    "Salami, Pancetta, Tomatoes, Red Onions, Friggitello Peppers, Garlic",
  image: "/public/pizzas/calabrese.webp",
  sizes: { S: 12.25, M: 16.25, L: 20.25 },
};

function getPizzaOfTheDay() {
  let pizza: Pizza | null = null;

  function TestComponent() {
    pizza = usePizzaOfTheDay();
    return null;
  }

  render(<TestComponent />);

  return pizza;
}

test("gives null when first called", async () => {
  fetchMocker.mockResponseOnce(JSON.stringify(testPizza));
  const pizza = getPizzaOfTheDay();
  expect(pizza).toBeNull();
});

ข้อมูลทดสอบที่มี type คือข้อมูลทดสอบที่เชื่อถือได้

สิ่งที่ควรสังเกตที่สุดในไฟล์นี้คือ const testPizza: Pizza = { … } การใส่ type ให้ข้อมูลทดสอบเป็นนิสัยที่ให้ผลตอบแทนสูงมาก และเป็นสิ่งที่คนมักลืมทำ

ปัญหาของ mock data ที่ไม่มี type คือมันเก่าเงียบ ๆ สมมติวันหนึ่งเราเพิ่ม field vegetarian: boolean เข้าไปใน Pizza โค้ดแอปทุกที่จะถูก TypeScript ไล่บอกให้แก้ แต่ mock data ในเทสต์จะไม่มีใครแตะเลย ผลคือเทสต์ยังเขียวอยู่ ทั้งที่กำลังทดสอบด้วยข้อมูลที่ไม่มีอยู่จริงในระบบแล้ว — ซึ่งแย่กว่าไม่มีเทสต์ เพราะมันให้ความมั่นใจปลอม ๆ

พอใส่ : Pizza เข้าไป mock data ของเราก็ถูกผูกกับ type จริงของแอป เพิ่ม field ใหม่เมื่อไร เทสต์จะฟ้องทันทีว่าข้อมูลไม่ครบ ลองพิมพ์ sizes: { S: 12.25 } โดยลบ M กับ L ออกดู แล้วจะเห็นว่ามันจับได้

💡 อีกจุดคือ let pizza: Pizza | null = null; ต้นฉบับเขียน let pizza; เฉย ๆ ซึ่งทำให้ type เป็น any โดยปริยาย และเราจะเสีย type safety ทั้งหมดตั้งแต่บรรทัดนั้นไป การประกาศ type ให้ชัดเจนทำให้ expect(pizza) ข้างล่างยังรู้ว่ากำลังตรวจอะไรอยู่ · เราเปลี่ยน fetch.mockResponseOnce เป็น fetchMocker.mockResponseOnce ด้วย เพราะ TypeScript ไม่รู้จัก method ที่ mock library แปะเพิ่มลงบน fetch ตัว global แต่ตัวแปร fetchMocker ที่เรารับกลับมาเองนั้นมี type ครบ

การทำ fake component เพื่อ test อะไรบางอย่างดูแปลกนิดหน่อย (เราใกล้เส้นการ test implementation details แบบอันตราย) แต่สิ่งนี้คือ library code โดยแก่น และเราอยากยืนยันว่า code นี้ทำงานหากเราใช้มันบ่อยใน code base ของเรา

เราทำให้ดีกว่านี้ได้ ลองเขียน test ใหม่ให้เป็นแบบนี้:

import { renderHook } from "@testing-library/react"; // change import

test("to be null on initial load", async () => {
  fetchMocker.mockResponseOnce(JSON.stringify(testPizza));
  const { result } = renderHook(() => usePizzaOfTheDay());
  expect(result.current).toBeNull();
});

ที่นี่ helper renderHook นามธรรมความแปลกที่เราต้องทำเพื่อทดสอบ hook นั้นออกไป แต่มั่นใจได้ว่ามันทำสิ่งเดียวกันเป็นหลัก: สร้าง component ภายในที่กำลังรัน hook lifecycle methods อย่างเหมาะสมให้คุณ

หมายเหตุผู้แปล: ต้นฉบับที่เป็น JavaScript เขียน usePizzaOfTheDay("") ทั้งที่ hook ตัวนี้ไม่รับ argument เลย — เป็น argument ที่หลงเหลือมาแล้วไม่มีผลอะไร JavaScript ปล่อยผ่านให้เงียบ ๆ แต่ TypeScript จะฟ้องว่า Expected 0 arguments, but got 1. เราจึงลบมันออก บั๊กประเภทนี้ไม่ทำให้อะไรพัง แต่มันทำให้คนอ่านเข้าใจผิดว่า hook รับค่าอะไรบางอย่าง ซึ่งเป็นหนี้ที่สะสมได้เรื่อย ๆ ใน codebase

มาเพิ่ม test ให้แน่ใจว่ามันทำสิ่งถูกต้องกับ API response และเรียก API ที่ถูกต้อง

import { renderHook, waitFor } from "@testing-library/react"; // add waitFor

test("to call the API and give back the pizza of the day", async () => {
  fetchMocker.mockResponseOnce(JSON.stringify(testPizza));
  const { result } = renderHook(() => usePizzaOfTheDay());
  await waitFor(() => {
    expect(result.current).toEqual(testPizza);
  });
  expect(fetchMocker).toBeCalledWith("/api/pizza-of-the-day");
});

ข้อดีที่ได้ฟรีอีกอย่างคือ result.current มี type เป็น Pizza | null โดยที่เราไม่ต้องบอก เพราะ renderHook เป็น generic ที่อ่าน type มาจาก callback ที่เราส่งให้ ดังนั้นถ้าวันหนึ่งมีคนแก้ usePizzaOfTheDay ให้คืนค่ารูปแบบอื่น เทสต์นี้จะรู้ทันทีตั้งแต่ตอน compile

  • waitFor เป็นทริกสะดวกเมื่อคุณต้องรอให้ React settle คุณให้ body ที่ throw errors จนกว่าจะเป็น true expect เมื่อใช้ไม่ได้จะ throw error จึงทำงานแบบนี้
  • เมื่อมัน resolve เป็น true ก็ผ่าน test และไปต่อ หากมัน fail ราว 20 ครั้ง (ตั้งค่าได้) ก็จะ fail test
  • บางคนคิดว่านี่เข้าไปใน implementation details มากเกินไป ซึ่งก็มีส่วนถูก อย่างไรก็ตามมันมีประโยชน์จากมุมที่ hook นี้ต้องทำงานบางแบบ และคาดหวัง API ที่จะเรียก ซึ่งส่งผลต่อ user behavior จึงอาจมีประโยชน์ ถ้าเป็น codebase จริง การ test PizzaOfTheDay component อย่างเดียวก็อาจพอแล้ว แต่ถ้า hook นี้ถูกใช้หลายที่ การเขียน test ให้มันโดยตรงก็คุ้ม
