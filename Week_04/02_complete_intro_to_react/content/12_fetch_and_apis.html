Fetch & APIs

Fetch & APIs

ในบทที่ 11 เราฝึกรอ "ผลลัพธ์ที่ยังมาไม่ถึง" กันจนคล่อง แต่สิ่งที่เรารออยู่ตลอดบทนั้นเป็นของปลอมทั้งหมด — setTimeout ที่แกล้งช้า และเหรียญที่เราโยนเองเพื่อแกล้งพัง บทนี้เราจะเปลี่ยนของปลอมนั้นเป็นของจริง คือส่งคำขอออกไปนอกเครื่อง ไปหาเซิร์ฟเวอร์ที่ไม่ได้อยู่ใต้บังคับของเรา แล้วรอคำตอบกลับมา

เครื่องมือที่เราจะใช้มีตัวเดียวชื่อ fetch มันเป็นฟังก์ชันที่เบราว์เซอร์มีมาให้อยู่แล้ว ไม่ต้องติดตั้งอะไรเพิ่ม และสิ่งที่มันคืนกลับมาก็คือ Promise ตัวเดียวกับที่คุณเพิ่งเรียนไป กล่าวอีกอย่างคือคุณรู้วิธีใช้มันครึ่งหนึ่งแล้วตั้งแต่ยังไม่เริ่มบทนี้ ส่วนอีกครึ่งที่เหลือ — และเป็นครึ่งที่คนพลาดกันมากที่สุด — คือการอ่านสิ่งที่เซิร์ฟเวอร์ตอบกลับมาให้ถูกต้อง

บทนี้ต้องมีเซิร์ฟเวอร์สองตัวทำงานอยู่พร้อมกัน หนึ่งคือ Vite dev server ของแอปเรา (npm run dev ในโฟลเดอร์ pizza-app) และสองคือ API server ซึ่งก็คือโปรเจกต์ pizza-shop-api-demo ที่เรา clone มาตั้งแต่บทที่ 9 เปิด terminal อีกหน้าต่างหนึ่ง cd เข้าไปแล้วสั่ง npm run dev มันจะฟังอยู่ที่ port 3000 · ตัวอย่างทั้งหมดในบทนี้ให้พิมพ์ลงใน console ของเบราว์เซอร์ เหมือนบทที่แล้ว แต่คราวนี้ต้องเป็นแท็บที่เปิด http://localhost:5173 อยู่เท่านั้น เดี๋ยวเราจะอธิบายว่าทำไม

API กับ HTTP คืออะไร

คำว่า API ฟังดูยิ่งใหญ่ แต่ในบริบทที่เรากำลังพูดถึงมันหมายถึงสิ่งเดียว: โปรแกรมอีกตัวหนึ่งที่รอรับคำถามและตอบกลับมาเป็นข้อมูล แอปของเราไม่ได้เก็บรายการพิซซ่าไว้เอง มันต้องไปถามเซิร์ฟเวอร์ว่า "ขอรายการพิซซ่าหน่อย" แล้วเซิร์ฟเวอร์ก็ส่งกลับมา ภาษาที่ทั้งสองฝ่ายใช้คุยกันคือ HTTP

HTTP ไม่ได้ลึกลับอะไรเลย มันคือการสลับกันพูดสองรอบ

  • request — ฝั่งเบราว์เซอร์ส่งออกไป ประกอบด้วย method (เช่น GET คือ "ขอดูข้อมูล", POST คือ "ส่งข้อมูลไปให้") กับ URL ว่าขออะไร และอาจมี header แนบไปด้วย
  • response — ฝั่งเซิร์ฟเวอร์ส่งกลับมา ประกอบด้วย status code (ตัวเลขสามหลักที่บอกว่าผลเป็นอย่างไร), headers (ข้อมูลกำกับ เช่น ข้างในเป็นข้อมูลชนิดไหน) และ body (เนื้อข้อมูลจริง ๆ ที่เราอยากได้)

เท่านี้จริง ๆ ทุกครั้งที่คุณเปิดเว็บ กดปุ่ม โหลดรูป เบื้องหลังคือ request/response คู่แล้วคู่เล่าวิ่งกันไปมาแบบนี้ทั้งนั้น

ทีนี้มีเรื่องหนึ่งที่ต้องเคลียร์ก่อน ไม่งั้นคุณจะงงว่าทำไมโค้ดในบทนี้ถึงหน้าตาแปลก ๆ แอป React ของเราเสิร์ฟจาก localhost:5173 ส่วน API server อยู่ที่ localhost:3000 คนละที่กัน แต่เรากลับเขียน fetch("/api/pizzas") เฉย ๆ ไม่มีชื่อโฮสต์ ไม่มีเลข port อะไรทั้งนั้น เหตุผลอยู่ในบล็อกที่เราใส่ไว้ใน vite.config.ts ตั้งแต่บทที่ 9

server: {
  proxy: {
    "/api": {
      target: "http://localhost:3000",
    },
  },
}

บล็อกนี้บอก Vite ว่า "ถ้ามี request วิ่งเข้ามาที่เส้นทางขึ้นต้นด้วย /api อย่าพยายามหาไฟล์ให้ ส่งต่อไปที่ localhost:3000 แทน" สิ่งนี้เรียกว่า proxy — คนกลางที่รับของแล้วเดินไปส่งต่อให้อีกที ผลคือในสายตาของเบราว์เซอร์ ทุกอย่างอยู่ที่ localhost:5173 ที่เดียว ทั้งหน้าเว็บและข้อมูล ส่วนความจริงที่ว่าข้อมูลมาจากอีก port หนึ่งกลายเป็นเรื่องของ Vite ที่จัดการให้เบื้องหลัง

💡 นี่คือเหตุผลที่ตัวอย่างในบทนี้ต้องพิมพ์ในแท็บ localhost:5173 เท่านั้น เส้นทาง /api/pizzas เป็น relative URL เบราว์เซอร์จะเติมที่อยู่ของหน้าปัจจุบันเข้าไปข้างหน้าให้เอง ถ้าคุณเผลอไปพิมพ์ใน console ของแท็บอื่น — สมมติหน้า Google — มันจะกลายเป็นการขอ google.com/api/pizzas ซึ่งไม่มีอยู่จริง และคุณจะได้ 404 มาแบบงง ๆ

fetch: ขอข้อมูลจาก server

เอาล่ะ ลองของจริงกัน เปิดแอปที่ http://localhost:5173 เปิด DevTools ไปที่แท็บ Console แล้วพิมพ์สองบรรทัดนี้

const res = await fetch("/api/pizza-of-the-day");
console.log(res);

fetch() คืน Promise<Response> ออกมา — ก็คือ Promise ที่เมื่อสำเร็จแล้วจะให้ object ชนิด Response กับเรา นี่คือของหน้าตาเดียวกับที่เรา await กันทั้งบทที่แล้วเป๊ะ ๆ ไม่มีอะไรใหม่ในบรรทัดแรกเลยนอกจากชื่อฟังก์ชัน

สิ่งที่ใหม่คือของที่ได้กลับมา กดลูกศรหน้า Response ใน console เพื่อกางออกดู แล้วสังเกตสามอย่างนี้

  • status — ตัวเลข status code ที่เซิร์ฟเวอร์ตอบมา ถ้าทุกอย่างเรียบร้อยควรเป็น 200
  • ok — ค่า boolean ที่เป็น true เมื่อ status อยู่ในช่วง 200–299 เป็นทางลัดให้เราไม่ต้องจำเลขเอง
  • headers — object ที่เก็บ header ของ response ไว้ ลอง res.headers.get("content-type") ดู คุณจะได้ application/json กลับมา นั่นคือเซิร์ฟเวอร์กำลังบอกเราว่า "ข้างในเป็น JSON นะ"

ทีนี้ลองหาข้อมูลพิซซ่าใน object นั้นดูสิ — หาไม่เจอ เพราะมันไม่ได้อยู่ในนั้น Response คือ "ซองจดหมาย" ที่บอกว่าคำตอบมาถึงแล้วและมาถึงในสภาพไหน แต่ยังไม่ได้แกะซองอ่าน การแกะซองคือบรรทัดถัดไป

const pizza = await res.json();
console.log(pizza);

คราวนี้ได้ object พิซซ่าจริง ๆ ออกมาแล้ว มี id, name, description และรายละเอียดอื่น ๆ ครบ

คำถามที่ทุกคนถามตรงนี้คือ ทำไมต้อง await ถึงสองครั้ง ในเมื่อเราขอข้อมูลแค่ครั้งเดียว ดูเหมือนพิธีกรรมเกินจำเป็น แต่มันไม่ใช่ และเหตุผลก็ตรงไปตรงมามาก: ทั้งสองครั้งรอคนละเหตุการณ์กัน

ข้อมูลไม่ได้เดินทางมาถึงพร้อมกันทั้งก้อน มันไหลมาเป็นสาย และสิ่งที่มาถึงก่อนเสมอคือ status code กับ headers ส่วน body ทยอยตามมาทีหลัง

  • await fetch(...) เสร็จเมื่อ header มาถึง — ณ วินาทีนั้นเรารู้แล้วว่าสำเร็จหรือไม่ และข้างในเป็นข้อมูลชนิดไหน ทั้งที่ body ยังอาจโหลดไม่เสร็จเลยสักไบต์
  • await res.json() เสร็จเมื่อ body โหลดครบและถูกแปลงจากข้อความเป็น object เรียบร้อย

กับ endpoint เล็ก ๆ บนเครื่องตัวเอง สองจังหวะนี้ห่างกันไม่ถึงมิลลิวินาที คุณจึงไม่รู้สึกถึงความต่าง แต่ลองนึกถึงการดาวน์โหลดไฟล์ JSON ขนาด 50 เมกะไบต์ผ่านเน็ตมือถือ header มาถึงในหนึ่งวินาทีแรก ส่วน body ใช้เวลาอีกครึ่งนาที การแยกสองจังหวะออกจากกันจึงมีประโยชน์จริง — มันเปิดโอกาสให้เราตัดสินใจก่อนที่จะเสียเวลาโหลด body เช่น เห็นว่า status ไม่ผ่านก็เลิกสนใจ body ไปเลย ไม่ต้องรอโหลดให้เสียเน็ตเปล่า ๆ ซึ่งเดี๋ยวเราจะได้ใช้ท่านี้จริงในหัวข้อถัดไป

ทีนี้ลองเขียนรวบทั้งชุดในครั้งเดียว และเปลี่ยนไปที่ endpoint ที่ข้อมูลเยอะกว่าเดิม

const res = await fetch("/api/pizzas");
const pizzas = await res.json();
console.table(pizzas);

console.table เป็นเพื่อนที่ดีมากเวลาทำงานกับข้อมูลที่เป็น array of objects แทนที่จะให้คุณนั่งกางลูกศรทีละตัว มันวาดออกมาเป็นตาราง มีคอลัมน์ตามชื่อ property ให้เลย กวาดตาดูรอบเดียวก็เห็นทั้งชุด

และให้สังเกตให้ดีว่าตารางนั้นคืออะไร — มันคือรายการพิซซ่าชุดเดียวกับที่แอปของเราจะเอาไปใส่ในช่อง dropdown ในบทที่ 13 ตอนนี้คุณกำลังมองข้อมูลชุดนั้นแบบดิบ ๆ ก่อนที่มันจะกลายเป็นหน้าจอ

กับดักที่ทุกคนเจอ: fetch ไม่ throw เมื่อ 404

ถ้าคุณจำอะไรจากบทนี้ได้อย่างเดียว ขอให้เป็นหัวข้อนี้ เพราะมันคือจุดที่โค้ดพังเงียบ ๆ ได้บ่อยที่สุด และเป็นพฤติกรรมที่ขัดกับสัญชาตญาณของเกือบทุกคน

ลองยิงไปที่เส้นทางที่ไม่มีอยู่จริงดู

const res = await fetch("/api/nope");
console.log(res.ok); // false
console.log(res.status); // 404
// ไม่มี error ถูก throw ออกมาเลย — await ผ่านฉลุย

อ่านผลลัพธ์ให้ดี ๆ เซิร์ฟเวอร์บอกเราชัดเจนว่า 404 แปลว่าไม่มีของที่ขอ แต่ await บรรทัดนั้นไม่ได้ throw อะไรออกมาเลย โค้ดวิ่งต่อไปบรรทัดถัดไปอย่างสงบเสงี่ยม ถ้าคุณห่อมันไว้ใน try / catch ตามที่เรียนมาในบทที่ 11 บล็อก catch จะไม่ทำงานแม้แต่นิดเดียว

เหตุผลอยู่ที่นิยามของคำว่า "ล้มเหลว" ในมุมของ fetch มันสนใจแค่คำถามเดียวคือ "ส่งคำขอออกไปแล้วได้คำตอบกลับมาไหม" ถ้าได้ ก็ถือว่าสำเร็จ จบ ส่วนเนื้อหาของคำตอบจะเป็นข่าวดีหรือข่าวร้ายไม่ใช่ธุระของมัน

ดังนั้น fetch จะ reject ก็ต่อเมื่อตัว request เองไปไม่ถึงหรือกลับมาไม่ได้ เท่านั้น เช่น

  • เน็ตหลุด หรือ Wi-Fi ตัด
  • หา DNS ของโดเมนไม่เจอ
  • เซิร์ฟเวอร์ไม่ได้เปิดอยู่ ต่อไม่ติดเลย (ถ้าคุณลืมรัน API server คุณจะเจอกรณีนี้)
  • โดน CORS บล็อก คือเบราว์เซอร์ไม่ยอมให้ JavaScript อ่าน response นั้น

ส่วน 404 หรือ 500 นั้น ในสายตาของ fetch คือการเดินทางไป-กลับที่สำเร็จสมบูรณ์แบบ เพียงแต่พกข่าวร้ายกลับมาด้วย จดหมายส่งถึงมือแล้ว เนื้อความข้างในจะเป็นใบปฏิเสธก็เรื่องของคุณที่ต้องอ่านเอง

ทีนี้ลองคิดต่อว่าถ้าเราไม่เช็คอะไรเลยแล้วเรียก await res.json() ต่อไปเลยจะเกิดอะไรขึ้น มีสองทางและแย่ทั้งคู่ ทางแรก ถ้าเซิร์ฟเวอร์ตอบหน้า error กลับมาเป็น HTML การแปลงเป็น JSON จะพังพร้อมข้อความประมาณ Unexpected token '<' ซึ่งอ่านแล้วไม่มีทางเดาถูกเลยว่าปัญหาจริงคือ 404 ทางที่สอง ซึ่งร้ายกว่า คือเซิร์ฟเวอร์ตอบ error กลับมาเป็น JSON อย่างสวยงาม (API หลายตัวรวมถึงตัวที่เราใช้อยู่ก็ทำแบบนี้) .json() จึงทำงานสำเร็จ แล้วโค้ดของเราก็รับ object ที่หน้าตาเป็น { error: "Not Found" } มาถือไว้ในมือเหมือนว่ามันคือข้อมูลปกติ แล้วเดินหน้าต่อ กว่าจะรู้ตัวก็ตอนที่หน้าจอว่างเปล่าโดยไม่มีใครบอกว่าเพราะอะไร

วิธีแก้คือเราต้องเช็คเอง ทุกครั้ง ไม่มีข้อยกเว้น และเนื่องจากมันต้องทำทุกครั้ง วิธีที่ดีที่สุดคือเขียนเป็นฟังก์ชันตัวเดียวแล้วใช้ตลอด

async function getJson(url) {
  const res = await fetch(url);
  if (!res.ok) {
    throw new Error(`เรียก ${url} ไม่สำเร็จ: ${res.status}`);
  }
  return res.json();
}

try {
  const pizzas = await getJson("/api/pizzas");
  console.log(pizzas.length);
} catch (error) {
  console.log("ผิดพลาด:", error.message);
}

สิ่งที่ฟังก์ชันนี้ทำคือเปลี่ยนข่าวร้ายที่เงียบ ให้กลายเป็น error ที่ส่งเสียง พอเราโยน Error ออกมาเอง try / catch ที่เราคุ้นเคยจากบทที่ 11 ก็กลับมาทำงานได้ตามปกติทันที และการจัดการ error ทั้งหมดก็รวมอยู่ที่เดียว ไม่ต้องเขียน if (!res.ok) กระจายเต็มโปรเจกต์

ลองรันชุดนี้สองรอบเพื่อดูทั้งสองทาง รอบแรกตามโค้ดข้างบนจะได้จำนวนพิซซ่าออกมา รอบสองเปลี่ยน URL เป็น "/api/nope" คราวนี้คุณจะเห็น ผิดพลาด: เรียก /api/nope ไม่สำเร็จ: 404 — ข้อความที่บอกทั้งว่าพังที่ไหนและพังเพราะอะไร ต่างจากตอนแรกลิบลับ

🔍 สังเกตว่าใน getJson เราเขียน return res.json() เฉย ๆ ไม่ได้ใส่ await — ทำแบบนี้ได้เพราะฟังก์ชัน async คืน Promise เสมออยู่แล้ว การ return Promise ออกจากฟังก์ชัน async จึงไม่ได้ทำให้เกิด Promise ซ้อน Promise แต่มันจะถูกคลี่ให้เองอัตโนมัติ คนเรียกฝั่งนอกจึงได้ข้อมูลจริงจากการ await ครั้งเดียว จะเขียน return await res.json() ก็ไม่ผิด และในบางกรณีก็ช่วยให้ stack trace อ่านง่ายขึ้น

ทีนี้ในเมื่อเราต้องอ่าน status code เป็นแล้ว มารู้จักตัวเลขพวกนี้กันสักหน่อย ตัวแรกของสามหลักบอกประเภทเสมอ จำแค่นี้พอ

  • 2xx — สำเร็จ 200 OK คือตัวที่คุณจะเห็นบ่อยที่สุด 201 Created ใช้ตอบตอนสร้างของใหม่สำเร็จ ซึ่งเราจะเจอตอนส่งออร์เดอร์ในบทหลัง ๆ
  • 3xx — ย้ายที่แล้ว เซิร์ฟเวอร์บอกว่า "ของที่ขออยู่ที่อื่น ไปตรงนั้น" ปกติเบราว์เซอร์ตามให้เองเงียบ ๆ เราแทบไม่ต้องยุ่ง
  • 4xx — คำขอมีปัญหา 404 Not Found ขอของที่ไม่มี, 400 Bad Request ส่งข้อมูลมาผิดรูปแบบ, 401 Unauthorized ยังไม่ได้ล็อกอิน, 403 Forbidden ล็อกอินแล้วแต่ไม่มีสิทธิ์
  • 5xx — เซิร์ฟเวอร์พังเอง 500 Internal Server Error คือ "มีอะไรบางอย่างระเบิดข้างในนี้" คำขอของคุณอาจถูกต้องทุกประการ แต่ฝั่งโน้นจัดการไม่ได้

กฎง่าย ๆ ที่ช่วยได้เยอะเวลาไล่ปัญหา: 4xx คือความผิดของคุณ 5xx คือความผิดของเขา ไม่ได้แม่นร้อยเปอร์เซ็นต์ แต่มันบอกว่าควรเริ่มหาจากฝั่งไหนก่อน ถ้าเจอ 4xx ให้กลับไปดู URL และข้อมูลที่ส่งไป ถ้าเจอ 5xx ให้ไปดู log ของเซิร์ฟเวอร์ในหน้าต่าง terminal ที่รัน API server อยู่

ดูของจริงในแท็บ Network

ทั้งหมดที่ผ่านมาเราดูผ่าน console.log ซึ่งเห็นแค่สิ่งที่เราสั่งให้พิมพ์ แต่ DevTools มีแท็บที่แสดงทุก request ที่วิ่งออกจากหน้านี้แบบไม่ต้องเขียนโค้ดอะไรเลย ชื่อแท็บ Network และมันจะเป็นเพื่อนคุณไปตลอดชีวิตการทำ frontend

ลองทำตามนี้

  • เปิด DevTools แล้วสลับไปที่แท็บ Network
  • บนแถบตัวกรอง เลือก Fetch/XHR เพื่อตัดพวกไฟล์รูป ไฟล์ CSS และ script ออกไป เหลือเฉพาะ request ที่โค้ดเป็นคนยิงเอง
  • กด reload หน้าเว็บ (หรือจะพิมพ์ fetch("/api/pizzas") ลง console อีกทีก็ได้ แท็บ Network จับได้เหมือนกัน)
  • คลิกที่ชื่อ request ที่โผล่ขึ้นมาในรายการ

พอคลิกแล้วคุณจะเห็นแผงรายละเอียดแยกเป็นหลายหัวข้อ สามอันที่ควรรู้จักคือ

  • Headers — ครึ่งบนบอกข้อมูลของ request (method, URL เต็ม, status code) ครึ่งล่างแยกเป็น response headers กับ request headers นี่คือของชุดเดียวกับที่เราอ่านผ่าน res.status และ res.headers เมื่อกี้ เพียงแต่คราวนี้แสดงให้ครบทุกตัวโดยไม่ต้องพิมพ์อะไร
  • Response — body ดิบ ๆ ตามที่เซิร์ฟเวอร์ส่งมาจริง ๆ ซึ่งก็คือข้อความ JSON ยาวเหยียดบรรทัดเดียว
  • Preview — ของอันเดียวกับ Response แต่ DevTools แปลงให้เป็นโครงสร้างที่กางดูได้ทีละชั้น อ่านง่ายกว่ามาก เวลาอยากรู้ว่า API ส่งอะไรมาบ้างให้ดูที่นี่

ประโยชน์ที่ได้ทันทีคือเวลาแอปไม่แสดงข้อมูล คุณจะตอบได้ในสิบวินาทีว่าปัญหาอยู่ตรงไหน — ถ้าใน Network ไม่มี request โผล่มาเลย แปลว่าโค้ดยังไม่ได้ยิงด้วยซ้ำ ถ้ามี request แต่ status เป็น 404 แปลว่า URL ผิด ถ้า status เป็น 200 และ Preview มีข้อมูลครบ แปลว่าปัญหาอยู่ที่โค้ด React ของเราที่เอาไปแสดงผล ไม่ใช่ที่การเรียก API เลย การแยกแยะสามกรณีนี้ได้ประหยัดเวลาคุณไปได้มหาศาล

อีกอย่างที่ต้องลองคือ การจำลองเน็ตช้า ในแท็บ Network จะมี dropdown สำหรับ throttling อยู่ (บางเบราว์เซอร์เขียนว่า No throttling บางตัวซ่อนไว้ใต้ไอคอนรูปสัญญาณ Wi-Fi) เปลี่ยนค่าเป็น Slow 3G แล้วยิง fetch เดิมซ้ำอีกครั้ง

คราวนี้คุณจะได้เห็นแถบเวลาของ request ยืดออกมาให้เห็นกับตา และรู้สึกได้จริง ๆ ว่ามันช้า นี่ไม่ใช่ลูกเล่น มันคือประสบการณ์ของผู้ใช้จำนวนไม่น้อยที่ใช้แอปของคุณบนมือถือกลางที่ที่สัญญาณไม่ดี อย่าลืมเปลี่ยนกลับเป็น No throttling เมื่อทดสอบเสร็จ ไม่งั้นเดี๋ยวคุณจะสงสัยว่าทำไมทุกอย่างช้าไปหมด

💡 ช่วงเวลาที่คุณเพิ่งยืดออกมาดูนั้นแหละคือเหตุผลที่แอปต้องมี สถานะ loading ในบทที่ 13 เราจะสร้าง state ชื่อ loading ขึ้นมาคุมข้อความ "Loading..." บนหน้าจอ และนั่นคือของที่มีไว้อุดช่องว่างนี้พอดี บนเครื่องตัวเองข้อมูลมาเร็วจนคุณแทบไม่ทันเห็นข้อความนั้นกะพริบด้วยซ้ำ — Slow 3G คือวิธีที่ทำให้คุณเห็นมันได้จริง (บทที่ 13 ยังมีอีกวิธีคือใส่ await new Promise((resolve) => setTimeout(resolve, 3000)) ไว้ถ่วงเวลา ซึ่งเป็น wait ตัวเดียวกับที่คุณเขียนเองในบทที่ 11 นั่นเอง)

JSON กับการใส่ type ให้ response

เราใช้ .json() กันมาทั้งบทโดยยังไม่ได้ถามว่ามันทำอะไรกันแน่ ถึงเวลาแล้ว

ข้อเท็จจริงที่คนมองข้ามบ่อยที่สุดคือ JSON ไม่ใช่ object มันคือข้อความ เป็นสตริงธรรมดา ๆ ที่เขียนตามรูปแบบมาตรฐานที่ตกลงกันไว้ทั้งโลก เซิร์ฟเวอร์ส่งข้อความมาให้เราตามสายเน็ตเวิร์ก เพราะสิ่งที่ส่งข้ามเครือข่ายได้มีแค่ข้อความกับไบต์เท่านั้น มันส่ง object ของ JavaScript ข้ามเครื่องมาตรง ๆ ไม่ได้ หน้าที่ของ .json() คืออ่านข้อความนั้นแล้วประกอบกลับขึ้นมาเป็น object จริงในหน่วยความจำของเรา

ลองดูความต่างให้เห็นกับตา

const res = await fetch("/api/pizza-of-the-day");
const text = await res.clone().text();
console.log(typeof text); // "string" — JSON ดิบ
const data = await res.json();
console.log(typeof data); // "object" — แปลงแล้ว

console.log(text) ดูด้วยก็ได้ คุณจะเห็นข้อความยาวบรรทัดเดียวที่มีปีกกาและเครื่องหมายคำพูดครบ หน้าตาเหมือน object เป๊ะ แต่มันเป็นสตริง คุณเขียน text.name แล้วได้ undefined ส่วน data.name ใช้ได้ปกติ

🔍 ทำไมต้อง res.clone() ก่อนแล้วค่อย .text() — เพราะ body ของ Response เป็น stream ที่อ่านได้ครั้งเดียว เหมือนเทน้ำออกจากขวด เทแล้วเทอีกไม่ได้ ถ้าคุณเรียก .text() ตรง ๆ แล้วตามด้วย .json() บนตัวเดิม อันหลังจะพังพร้อมข้อความ body stream already read เมธอด .clone() จึงมีไว้ก๊อป response ไว้อีกชุดเพื่ออ่านสองแบบ ในโค้ดจริงคุณแทบไม่ต้องใช้ท่านี้ ที่ยกมาก็เพื่อให้เห็นว่าข้อมูลก้อนเดียวกันมีสองหน้าตาเท่านั้น

ทีนี้มาถึงฝั่ง TypeScript ในไฟล์ .ts เมธอด .json() มี return type เป็น Promise<any> เสมอ ไม่ใช่เพราะคนเขียน TypeScript ขี้เกียจ แต่เพราะมันเป็นไปไม่ได้ที่จะรู้ล่วงหน้าว่าเซิร์ฟเวอร์ตัวไหนจะส่งอะไรกลับมา ณ เวลา compile ตัวเซิร์ฟเวอร์อาจยังไม่ได้เขียนด้วยซ้ำ TypeScript จึงยกธงขาวแล้วบอกว่า "อันนี้เป็นอะไรก็ได้ คุณบอกผมเองแล้วกัน"

วิธีบอกก็คือใส่ type annotation ตรงตัวแปรที่รับค่า

type Pizza = {
  id: string;
  name: string;
  description: string;
};

const res = await fetch("/api/pizzas");
const pizzas: Pizza[] = await res.json();

ตั้งแต่บรรทัดนั้นเป็นต้นไป ทุกอย่างก็มี type ครบ พิมพ์ pizzas[0]. แล้ว editor จะขึ้น autocomplete ให้ พิมพ์ชื่อ property ผิดก็โดนขีดแดงทันที pizzas.map(...) ก็รู้ว่าแต่ละตัวคืออะไร ประโยชน์ไหลต่อไปทั้งไฟล์จากการเขียนแค่บรรทัดเดียว

⚠️ แต่ต้องเข้าใจให้ตรงกันว่า type annotation ตรงนี้คือความเชื่อของเราเกี่ยวกับ response ไม่ใช่การตรวจสอบ response TypeScript ไม่ได้ไปเปิดดูข้อมูลจริงตอนรันแม้แต่นิดเดียว มันหายไปหมดตอน compile ถ้าวันหนึ่ง API เปลี่ยนชื่อ name เป็น title โค้ดชุดนี้จะพังตอนรันเหมือนกับที่มันจะพังใน JavaScript ล้วน ๆ ทุกประการ ไม่มีอะไรมาช่วยเลย · สิ่งที่ annotation ซื้อให้เราคือ autocomplete และการจับพิมพ์ผิดในโค้ดของเรา ทั้งไฟล์ ซึ่งก็คุ้มมากอยู่แล้ว แต่อย่าเข้าใจผิดว่ามันคือเกราะกันข้อมูลผิดรูปแบบ (ถ้าอยากได้เกราะแบบนั้นจริง ๆ ต้องใช้ library อย่าง Zod มาตรวจ response ตอนรัน ซึ่งอยู่นอกขอบเขตคอร์สนี้)

📌 Pizza ข้างบนเราเขียนแค่สาม property เพื่อให้ตัวอย่างสั้น ทั้งที่ API ส่งมามากกว่านั้น การประกาศ type ที่มีไม่ครบทุก field ไม่ผิดอะไร TypeScript ไม่บังคับให้คุณเขียนให้ครบ — คุณแค่จะใช้ field ที่ไม่ได้ประกาศไว้ไม่ได้เท่านั้น ในบทที่ 13 เราจะประกาศ type Pizza ตัวเต็มไว้ในไฟล์ src/types.ts เพราะเราต้องใช้ทั้ง image และ sizes ด้วย

ตอนนี้คุณยิง request เป็น อ่าน status code เป็น ดักกรณีที่เซิร์ฟเวอร์ตอบข่าวร้ายเป็น และแปลง JSON พร้อมใส่ type เป็นแล้ว ทั้งหมดนี้ยังทำอยู่ใน console ซึ่งแปลว่ามีคนพิมพ์คำสั่งเองทุกครั้ง ในบทที่ 13 เราจะย้าย fetch ชุดเดิมนี้เข้าไปอยู่ในคอมโพเนนต์ React ด้วย useEffect เพื่อให้มันยิงเองอัตโนมัติตอนหน้าโหลด แล้วเอาข้อมูลที่ได้ใส่ลงใน state — ผู้ใช้จะได้เห็นพิซซ่าจริง ๆ โดยไม่ต้องเปิด DevTools พิมพ์อะไรเลย
