POST /carts/add

เมื่อจบบทนี้ คุณจะสามารถ

  • เปิด route POST /carts/add ให้ตรงกับ path ที่ React app เรียกโดยไม่แก้ฝั่ง frontend
  • อธิบายได้ว่าทำไมไฟล์ controller ชื่อ carts แต่ module และ service ใช้คำว่า orders
  • พิสูจน์ทั้งสี่พฤติกรรมด้วย curl: 201, 400 ขาด userId, 404 สินค้าไม่มีจริงพร้อม rollback, 400 email ผิดรูป
  • เขียน test/orders.e2e-spec.ts ด้วยมือ ให้ npm run test:e2e ครอบคลุม POST /carts/add ด้วย

path มาจาก client ไม่ใช่จากเรา

ถ้าออกแบบ API ใหม่ตั้งแต่ต้น การสั่งซื้อควรเป็น POST /orders แต่คอร์สนี้มีข้อจำกัดที่ชัดเจน: React app เรียก POST /carts/add และเราสัญญาว่าจะไม่แก้โค้ด frontend นอกจาก base URL ดังนั้น path ต้องเป็น /carts/add เป๊ะ ๆ — พลาดตัวเดียวก็ได้ 404 ทุกครั้งที่กดสั่งซื้อ

ทางออกคือแยกสองเรื่องนี้ออกจากกัน: path เป็นเรื่องของสัญญากับ client จึงตั้งชื่อไฟล์ controller ตาม path (carts.controller.ts + @Controller('carts')) ส่วน module และ service เป็นเรื่องของ domain คือการสั่งซื้อ จึงใช้คำว่า orders (orders.module.ts, orders.service.ts) โครงสร้างนี้บอกคนอ่านโค้ดคนต่อไปได้ทันทีว่า "ชื่อ carts มาจากข้อจำกัดภายนอก ไม่ใช่จากวิธีที่เราคิดเรื่องธุรกิจ"

ทั้งสองไฟล์อยู่ในโฟลเดอร์ src/orders/ เดียวกัน ตามหลักการรวม domain ไว้ใน module เดียวจากคอร์ส NestJS Fundamentals — คนหาโค้ดเรื่องคำสั่งซื้อจะเจอทุกอย่างในที่เดียว แม้ route จะชื่อ /carts

ทวนของเดิม: @Body และ status 201

คอร์ส NestJS Fundamentals วางพื้นไว้แล้วสองข้อที่ใช้ตรง ๆ ในบทนี้ ข้อแรก @Body() dto: AddCartDto — การประกาศชนิดของ parameter ให้เป็น class ของ DTO คือสิ่งที่ทำให้ ValidationPipe รู้ว่าต้องเอา rule ชุดไหนมาตรวจ ถ้าเขียนเป็น @Body() dto: any หรือลืมใส่ชนิด DTO ทั้งชุดที่เขียน validation ไว้จะไม่ทำงานเลยแม้แต่ข้อเดียว และไม่มี error ใด ๆ เตือน

ข้อสอง handler ที่เป็น @Post() ของ Nest ตอบ 201 Created เป็นค่าเริ่มต้นอยู่แล้ว ตรงกับสัญญาที่เราออกแบบไว้ใน docs/api-spec.md พอดี จึงไม่ต้องใส่ @HttpCode() — ใส่ @HttpCode(200) ไปจะกลายเป็นการทำสัญญาเสียเอง

สุดท้าย OrdersModule ต้องถูก import เข้า AppModule ไม่ทำขั้นนี้ Nest จะไม่รู้จัก controller ตัวใหม่ และจะไม่มีบรรทัด Mapped {/carts/add, POST} ใน log ตอน start — ซึ่งเป็นวิธีตรวจที่เร็วที่สุดว่าลืมหรือไม่ลืม

ชื่อไฟล์และหน้าที่ด้านล่างมาจากโค้ดอ้างอิงของคอร์ส — Cursor อาจตั้งชื่อหรือแบ่งไฟล์ต่างออกไปได้ ขอแค่ไม่แตะไฟล์ที่ไม่เกี่ยวกับเป้าหมายและผ่านผลลัพธ์ที่ต้องได้ใน prompt

  • src/orders/carts.controller.ts — สัญญา: ต้องเป็น @Controller('carts') กับ @Post('add') และรับ body ด้วย @Body() dto: AddCartDto · ต้องไม่ใส่ @HttpCode(), ไม่คิดเลขหรือแตะ Prisma ใน controller
  • src/orders/orders.module.ts — สัญญา: ต้องประกาศ controllers: [CartsController] และ providers: [OrdersService] · ต้องไม่ import PrismaModule ซ้ำ (ตอนตั้งค่า Prisma ทำให้มันเป็น global module แล้ว)
  • src/app.module.ts — สัญญา: ต้องเพิ่ม OrdersModule ต่อจาก ProductsModule ใน imports · ต้องไม่แตะ ConfigModule, controllers หรือ providers เดิม
  • test/orders.e2e-spec.ts — สัญญา: ไฟล์ใหม่ที่ import orderResponseSchema จาก ./contract-schemas.js (ตัว schema มีอยู่แล้วตั้งแต่ตอนเขียน schema ด้วย zod) แล้วมี it() เดียวสำหรับ POST /carts/add · test/products.e2e-spec.ts ไม่ถูกแตะเลย · เขียนไฟล์นี้ด้วยมือ ไม่ใช่ผ่าน Cursor prompt ข้างล่าง เพราะการเขียน test ด้วยตัวเองคือการยืนยันว่าคุณอ่านสัญญาออกเอง ไม่ใช่ให้ AI ตรวจงานตัวเอง

สั่ง Cursor เปิด route แล้วยิงทดสอบสี่กรณี

commit งานก่อน แล้วเปิดแชทใหม่ใน Cursor โหมด Agent (git add -A && git commit -m "chore: before carts controller") — prompt ยก @src/products/products.controller.ts และ @src/products/products.module.ts ให้เป็นแบบอย่าง และย้ำเรื่อง path กับ status ไว้ในผลลัพธ์ที่ต้องได้ชัด ๆ เพราะนี่คือจุดที่ AI ชอบ "แก้ให้ดีขึ้น" โดยไม่ได้ขอ

ก่อนส่ง อ่านกติกาของคอร์สอีกครั้ง: AI พิมพ์แทนคุณได้ แต่คุณต้องอธิบายทุกบรรทัดได้ — ถ้าอธิบายไม่ได้ แปลว่ายังไม่ผ่านบทนี้

สร้าง CartsController ที่เปิด POST /carts/add และลงทะเบียน OrdersModule @src/app.module.ts @<ไฟล์ service ของ orders ที่คุณสร้างไว้ก่อนหน้านี้ — โค้ดอ้างอิงคือ src/orders/orders.service.ts> ผลลัพธ์ที่ต้องได้: - log ตอน npm run start:dev มีบรรทัด Mapped {/carts/add, POST} route (path ต้องเป็น /carts/add ตรงตัว เพราะ React app เรียก path นี้โดยไม่แก้ฝั่ง frontend — ไม่ใช่ /orders) - POST /carts/add body {"userId":1,"products":[{"id":1,"quantity":2}],"address":{"address":"1 Sukhumvit Rd","email":"a@b.com","phone":"0812345678"}} → 201 พร้อม receipt ตาม docs/api-spec.md (total 19.98, discountedPrice 17.89, discountedTotal 17.89, totalProducts 1, totalQuantity 2) - ไม่มี userId → 400 และ message เป็น array ["userId must not be less than 1","userId must be an integer number"] (validation ของ AddCartDto ต้องทำงานจริง) - สินค้า id 99999 → 404 {"message":"Product 99999 not found","error":"Not Found","statusCode":404} และจำนวนแถวใน Order ไม่เพิ่ม - email ผิดรูป → 400 message ["address.email must be an email"] - npm run build และ npm run lint ผ่าน ขอบเขต: - ห้ามติดตั้ง dependency ใหม่ - ห้ามแก้ service หรือการคำนวณที่ทำไว้ก่อนหน้านี้ - ห้ามแตะไฟล์ใน test/ — e2e test ของสัญญาผมเขียนเอง - ยังไม่ต้องเปิด CORS

ตรวจโค้ดที่ AI สร้าง

  • log ตอน start มี Mapped {/carts/add, POST} route — path รวมกันได้ POST /carts/add ไม่มี /orders โผล่ที่ไหน
  • ยิงทั้งสี่กรณีในส่วน "ผลลัพธ์ที่ต้องได้" แล้วได้ 201, 400, 404, 400 พร้อม body ตรงตัวอักษร — ถ้ากรณี 400 ได้ 201 แทน แปลว่า body ไม่ได้ถูกประกาศชนิดเป็น DTO class ทำให้ validation ไม่ทำงาน
  • POST ตอบ 201 ไม่ใช่ 200
  • controller ไม่คิดเลข ไม่เรียก Prisma ตรง และไม่กลืน error ด้วย try/catch — ส่งงานต่อให้ service ที่ทำไว้ในขั้นคิดเงิน
  • git status ไม่มีไฟล์ที่ไม่เกี่ยวกับเป้าหมายถูกแก้ — ฝั่ง root module มีแค่การลงทะเบียน module ใหม่ และ service/การคำนวณที่ทำไว้ก่อนหน้านี้ไม่ถูกแตะ
  • ไม่มี any, as, ! และ import ทุกตัวลงท้ายด้วย .js ตามกติกา ESM ของโปรเจกต์

AI มักพลาดตรงนี้: ตั้ง route เป็น /orders เพราะมันดูสอดคล้องกับชื่อ service และ module มากกว่า ผลคือโค้ดดูสวยแต่ React app ได้ 404 ทุกครั้งที่กดสั่งซื้อ อีกกรณีคือแถม @HttpCode(200) (ทำสัญญา 201 พัง) หรือเผลอ import PrismaModule ซ้ำ ทั้งที่มันเป็น global module อยู่แล้ว

โค้ดอ้างอิงของบทนี้ — เป็นหนึ่งในวิธีที่ถูก ของคุณไม่จำเป็นต้องเหมือนทุกบรรทัด ขอแค่ผ่านผลลัพธ์ที่ต้องได้:

// src/orders/carts.controller.ts
import { Body, Controller, Post } from '@nestjs/common';
import { AddCartDto } from './dto/add-cart.dto.js';
import { OrdersService } from './orders.service.js';

@Controller('carts')
export class CartsController {
  constructor(private readonly ordersService: OrdersService) {}

  @Post('add')
  create(@Body() dto: AddCartDto) {
    return this.ordersService.create(dto);
  }
}
// src/orders/orders.module.ts
import { Module } from '@nestjs/common';
import { CartsController } from './carts.controller.js';
import { OrdersService } from './orders.service.js';

@Module({
  controllers: [CartsController],
  providers: [OrdersService],
})
export class OrdersModule {}
// src/app.module.ts
import { Module } from '@nestjs/common';
import { ConfigModule } from '@nestjs/config';
import { AppController } from './app.controller.js';
import { AppService } from './app.service.js';
import { OrdersModule } from './orders/orders.module.js';
import { PrismaModule } from './prisma/prisma.module.js';
import { ProductsModule } from './products/products.module.js';

@Module({
  imports: [
    ConfigModule.forRoot({ isGlobal: true }),
    PrismaModule,
    ProductsModule,
    OrdersModule,
  ],
  controllers: [AppController],
  providers: [AppService],
})
export class AppModule {}

ถ้าอธิบายบรรทัดไหนไม่ได้ ยังไม่ผ่านบทนี้ — กลับไปอ่านส่วนแนวคิดก่อน

เขียน e2e test ของคำสั่งซื้อด้วยมือ

ตอนเขียน schema ด้วย zod เราตั้งใจปล่อยให้สัญญามีแค่เก้า test ของ products ไว้ก่อน เพราะตอนนั้น POST /carts/add ยังไม่มีอยู่จริง ตอนนี้มันมีแล้ว จึงถึงเวลาเขียน test ที่สิบ — เขียน ด้วยมือ ไม่ใช่ผ่าน Cursor prompt ข้างบน เพราะเป้าหมายของ prompt นั้นคือเปิด endpoint เท่านั้น และกติกาใน rules ห้ามแตะไฟล์ที่ไม่เกี่ยวกับเป้าหมาย การเขียน test นี้เป็นงานแยกที่ควรทำเอง จะได้อธิบายทุกบรรทัดได้เหมือนเดิม

test ที่สิบไปอยู่ในไฟล์ใหม่ test/orders.e2e-spec.ts ไม่ได้ต่อท้าย test/products.e2e-spec.ts ที่มีอยู่ — ธรรมเนียมของ Nest คือแบ่ง e2e spec ตาม resource ไฟล์ของ products จึงไม่ถูกแตะเลยในบทนี้ และนี่คือจังหวะที่การแยก schema ไว้คนละไฟล์ตั้งแต่ตอนเขียน zod ได้ผลจริง: spec สองไฟล์ import สัญญาชุดเดียวกันจาก ./contract-schemas.js ไม่มีสำเนาที่ค่อย ๆ เพี้ยนจากกัน

import { Test, TestingModule } from '@nestjs/testing';
import { INestApplication, ValidationPipe } from '@nestjs/common';
import request from 'supertest';
import { AppModule } from './../src/app.module.js';
import { orderResponseSchema } from './contract-schemas.js';

describe('Orders contract (e2e)', () => {
  let app: INestApplication;

  beforeAll(async () => {
    const moduleFixture: TestingModule = await Test.createTestingModule({
      imports: [AppModule],
    }).compile();

    app = moduleFixture.createNestApplication();
    app.useGlobalPipes(
      new ValidationPipe({
        whitelist: true,
        transform: true,
        transformOptions: { enableImplicitConversion: true },
      }),
    );
    await app.init();
  });

  afterAll(async () => {
    await app.close();
  });

  it('POST /carts/add → 201, discountedPrice rounds to 2dp', async () => {
    const response = await request(app.getHttpServer())
      .post('/carts/add')
      .send({
        userId: 1,
        products: [{ id: 1, quantity: 2 }],
        address: { address: '1 Sukhumvit Rd', email: 'a@b.com', phone: '0812345678' },
      })
      .expect(201);

    const receipt = orderResponseSchema.parse(response.body);
    expect(receipt.products[0].discountedPrice).toBe(17.89);
  });
});

บรรทัด app.useGlobalPipes(...) ต้องอยู่ที่นี่ด้วยเหตุผลเดียวกับใน spec ของ products: createNestApplication() สร้างแอปจาก AppModule เท่านั้น ไม่ได้รัน src/main.ts ให้ ค่าทั้งสามจึงต้องตรงกับใน main.ts ทุกตัว — ไม่อย่างนั้น spec นี้จะทดสอบแอปคนละตัวกับที่ผู้ใช้จริงเจอ และวันที่มีคนเพิ่ม test ของเคส 400 เข้ามา มันจะผ่านทั้งที่ไม่ควรผ่าน เพราะไม่มี pipe ตัวไหนตรวจ body เลย

ส่วน .send({...}) ของ supertest แปลง object เป็น JSON แล้วใส่ header Content-Type: application/json ให้เอง จึงไม่ต้องเขียน JSON.stringify หรือ header เองเหมือนตอนยิงด้วย curl

test นี้ยิง POST /carts/add จริง แปลว่ารันหนึ่งครั้งเท่ากับสร้างคำสั่งซื้อเพิ่มอีกหนึ่งใบในฐานข้อมูล — ถ้ารัน npm run test:e2e หลังจากยิง curl ทั้งสี่กรณีไปแล้ว แล้วย้อนไปนับแถวใน Order อีกครั้ง จำนวนจะเพิ่มจาก 1 เป็น 2 นั่นไม่ใช่ transaction รั่ว แต่เป็นเพราะ test นี้เองที่สั่งซื้อเพิ่ม และเพราะรันซ้ำได้เรื่อย ๆ แบบนี้ test จึงตรวจรูปทรงของ receipt กับตัวเลขที่คำนวณได้ ไม่ตรวจ id ของคำสั่งซื้อ ซึ่งเปลี่ยนทุกรอบ

รันเฉพาะไฟล์นี้ได้ด้วย npm run test:e2e -- orders เมื่อไม่อยากรอ spec ของ products ทั้งเก้าข้อ

ผลลัพธ์ที่คาดหวัง

รัน npm run start:dev แล้ว log ต้องมีสองบรรทัดนี้ ถ้าไม่มี แปลว่าลืม import OrdersModule เข้า AppModule

LOG [RoutesResolver] CartsController {/carts}: +0ms
LOG [RouterExplorer] Mapped {/carts/add, POST} route +0ms

ยิง body เดียวกับที่ React app ส่ง จะได้ 201 Created พร้อมตัวเลขตรงกับที่ orders.service.ts คำนวณจริงทุกตัว

curl -s -i -X POST http://localhost:3000/carts/add -H 'Content-Type: application/json' \
  -d '{"userId":1,"products":[{"id":1,"quantity":2}],"address":{"address":"1 Sukhumvit Rd","email":"a@b.com","phone":"0812345678"}}'
HTTP/1.1 201 Created

{"id":1,"userId":1,"products":[{"id":1,"title":"Velvet Matte Lipstick","price":9.99,"quantity":2,"total":19.98,"discountPercentage":10.48,"discountedPrice":17.89,"thumbnail":"https://picsum.photos/seed/product-1-thumb/300/300"}],"total":19.98,"discountedTotal":17.89,"totalProducts":1,"totalQuantity":2}

id เริ่มนับจาก 1 เพราะเราเก็บคำสั่งซื้อในฐานข้อมูลของเราเอง — ตัวเลขจะขึ้นอยู่กับว่าฐานข้อมูลของคุณเคยมีคำสั่งซื้อมาก่อนกี่ใบ field อื่นทั้งหมด (total, discountedTotal, discountedPrice, totalProducts, totalQuantity) ต้องตรงเป๊ะ

สามกรณีที่เหลือคือกรณีที่พลาดแล้วรู้ยาก จึงต้องยิงดูให้เห็นด้วยตาทั้งหมด ไม่มี userId → 400 จาก ValidationPipe โดยที่ message เป็น array และมีสองข้อ เพราะทั้ง @IsInt() และ @Min(1) ไม่ผ่านพร้อมกัน

curl -s -i -X POST http://localhost:3000/carts/add -H 'Content-Type: application/json' \
  -d '{"products":[{"id":1,"quantity":1}],"address":{"address":"x","email":"a@b.com","phone":"1"}}'
HTTP/1.1 400 Bad Request

{"message":["userId must not be less than 1","userId must be an integer number"],"error":"Bad Request","statusCode":400}

สินค้า id ที่ไม่มีจริง → 404 จาก NotFoundException ที่ throw อยู่ข้างใน transaction ข้อความตรงกับที่ GET /products/:id ตอบไว้ก่อนหน้านี้

HTTP/1.1 404 Not Found

{"message":"Product 99999 not found","error":"Not Found","statusCode":404}

email ผิดรูป → 400 โดยชื่อ field ใน message มีคำนำหน้า address. ซึ่งเป็นหลักฐานว่า @ValidateNested() ใน DTO ไล่ตรวจเข้าไปข้างใน object จริง

curl -s -i -X POST http://localhost:3000/carts/add -H 'Content-Type: application/json' \
  -d '{"userId":1,"products":[{"id":1,"quantity":1}],"address":{"address":"x","email":"not-an-email","phone":"1"}}'
HTTP/1.1 400 Bad Request

{"message":["address.email must be an email"],"error":"Bad Request","statusCode":400}

ตรวจว่าใช้งานได้จริง

  • log ตอน start มีบรรทัด Mapped {/carts/add, POST} route
  • ยิงทั้งสี่ curl ข้างบนแล้วได้ status 201, 400, 404, 400 ตามลำดับ พร้อม body ตรงกับตัวอย่าง
  • แถวที่บันทึกลงฐานข้อมูลมีจริง และยอดตรงกับ response
