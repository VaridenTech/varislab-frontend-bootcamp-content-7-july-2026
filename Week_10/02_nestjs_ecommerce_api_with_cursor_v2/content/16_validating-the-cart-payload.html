Validate Payload ของ POST /carts/add

เมื่อจบบทนี้ คุณจะสามารถ

  • เขียน DTO ที่มี object และ array ซ้อนอยู่ข้างใน ให้ ValidationPipe ตรวจได้จริงทุกชั้น
  • อธิบายได้ว่าทำไม nested object ต้องมีทั้ง @ValidateNested() และ @Type(() => Class)
  • เทียบ zod schema ฝั่ง React กับ DTO ฝั่ง API และบอกได้ว่าทำไมต้องตรวจซ้ำทั้งสองฝั่ง

ทวนของเดิม: DTO + whitelist

คอร์ส NestJS Fundamentals วางกติกาไว้แล้วว่า body ที่เข้ามาต้องผ่าน DTO ที่เป็น class ไม่ใช่ interface เพราะ decorator ของ class-validator ต้องเกาะอยู่กับ metadata ของ class จริงตอน runtime ส่วน interface หายไปหมดตอน compile และตั้งแต่ตอนทำ pagination src/main.ts ก็เปิด ValidationPipe แบบ global ไว้แล้ว

app.useGlobalPipes(
  new ValidationPipe({
    whitelist: true,
    transform: true,
    transformOptions: { enableImplicitConversion: true },
  }),
);

สามตัวเลือกนี้มีผลกับบทนี้ตรง ๆ: whitelist: true ตัด field ที่ไม่มี decorator ออกจาก body ทิ้งเงียบ ๆ (client แนบ isAdmin: true มาก็ไม่มีทางไหลเข้า service), transform: true สั่งให้ pipe แปลง body ดิบเป็น instance ของ DTO และ enableImplicitConversion แปลง string เป็น number ตามชนิดที่ประกาศไว้ให้ — สะดวกกับ query string ของ pagination แต่ body ของบทนี้เป็น JSON ที่มีชนิดข้อมูลมาถูกต้องแล้ว

nested object ไม่ถูกตรวจเอง

กับดักใหญ่ที่สุดของ DTO ซ้อนชั้นคือ: class-validator ตรวจได้เฉพาะ instance ของ class เท่านั้น แต่ JSON.parse คืน plain object ธรรมดาที่ไม่มี constructor ผูกอยู่ ดังนั้นถึงเราประกาศชนิดว่า address: AddressDto ตัว pipe ก็ยังไม่รู้ว่าจะต้องเอา rule ของ class ไหนไปตรวจ object ก้อนนั้น เพราะ type annotation ของ TypeScript หายไปตอน compile

จึงต้องใช้สอง decorator คู่กัน

Decoratorมาจากทำอะไร
@Type(() => AddressDto)class-transformerบอกว่าจะ สร้าง ก้อน JSON นี้เป็น instance ของ class ไหน ถ้าไม่มีบรรทัดนี้ object จะยังเป็น plain object
@ValidateNested()class-validatorบอกว่าให้ไล่ตรวจ rule ข้างใน instance นั้นต่อ ไม่ใช่ตรวจแค่ว่ามี field นี้
@ValidateNested({ each: true })class-validatorรูปแบบสำหรับ array — ไล่ตรวจทุกสมาชิก ไม่ใช่ตรวจตัว array เป็นก้อนเดียว
@ArrayMinSize(1)class-validatorตะกร้าว่างต้องไม่กลายเป็นคำสั่งซื้อ — products: [] ต้องได้ 400 ไม่ใช่ order ยอด 0 บาท

ถ้าลืม @Type(() => AddressDto) จะไม่มี error อะไรเลย แต่ validation ของ address จะผ่านทุกอย่าง — ส่ง {"address": {}} ก็ผ่าน นี่คือความพลาดที่อันตรายที่สุดในบทนี้ เพราะเงียบสนิทจนกว่าจะมีข้อมูลเสียลงฐานข้อมูล

เราเรียง class เล็กไปใหญ่เพื่ออ่านง่าย: CartProductDto → AddressDto → AddCartDto — arrow function ใน @Type(() => CartProductDto) ถูกเรียกตอน class-transformer แปลง payload จริง (คือตอนมี request เข้ามา) ไม่ใช่ตอนประกาศ class จึงไม่ผูกกับลำดับการประกาศ นั่นคือเหตุผลที่ @Type รับ function ไม่ใช่รับ class ตรง ๆ

ตรวจสองฝั่งไม่ใช่ความซ้ำซ้อน

ฝั่ง React app ตรวจ address ด้วย zod อยู่แล้ว (src/features/checkout/schema.ts)

export const checkoutAddressSchema = z.object({
  address: z.string().min(1, "Address is required"),
  email: z
    .string()
    .min(1, "Email is required")
    .pipe(z.email("Enter a valid email address")),
  phone: z.string().min(1, "Phone number is required"),
});

DTO ของเราจะสะท้อนกฎเดียวกันทีละข้อ: address ไม่ว่าง → @IsString() @IsNotEmpty(), email ต้องเป็นอีเมล → @IsEmail(), phone ไม่ว่าง → @IsString() @IsNotEmpty() ที่ต้องตรวจซ้ำเพราะ validation ฝั่ง client เป็นเรื่องของ ประสบการณ์ผู้ใช้ ไม่ใช่ความปลอดภัย — ใครก็ยิง curl ตรงเข้า API ข้าม React ไปได้ กฎง่าย ๆ คือข้อมูลจากภายนอกไม่เชื่อถือได้เลย จนกว่า API จะตรวจเอง

รูปแบบ error ที่ตอบออกไปเป็นมาตรฐานของ Nest: message เป็น array ของทุกข้อที่ผิดพร้อมกัน ไม่ใช่ string เดี่ยว — ApiError ของ React app อ่านค่าจาก data.message ได้อยู่แล้วไม่ว่าจะเป็น string หรือ array และการบอกครบทุกข้อในรอบเดียวมีประโยชน์กับคนใช้ API มากกว่าการต้องยิงซ้ำทีละข้อ

เป้าหมายของบทนี้

รายการด้านล่างคือไฟล์ที่เปลี่ยนในโค้ดอ้างอิงของคอร์ส — ใช้เป็นแผนที่ตอนเทียบงาน ไม่ใช่ข้อบังคับ Cursor ของคุณอาจวางไฟล์หรือตั้งชื่อต่างไปได้ ขอแค่ผ่านผลลัพธ์ที่ต้องได้ใน prompt

ecommerce-api/
└── src/
    └── orders/
        └── dto/
            └── add-cart.dto.ts   (สร้างใหม่)
  • src/orders/dto/add-cart.dto.ts — ในโค้ดอ้างอิง: export class สามตัวในไฟล์เดียว เรียง CartProductDto → AddressDto → AddCartDto, ทุก field มี decorator, products มีทั้ง @IsArray(), @ArrayMinSize(1), @ValidateNested({ each: true }) และ @Type() · ไม่มี field ที่เป็น optional, ไม่มีค่า default, ไม่ติดตั้ง package ใหม่ (class-validator และ class-transformer ติดตั้งไว้แล้วตั้งแต่ตอนเปิด ValidationPipe)
  • ยังไม่มี controller ในบทนี้ — DTO ตัวนี้จะถูกใช้ครั้งแรกในขั้นคิดเงิน (service) แล้วจึงผูกเข้า route POST /carts/add

สั่ง Cursor เขียน DTO ของ POST /carts/add

commit งานก่อน แล้วเปิดแชทใหม่ใน Cursor โหมด Agent (git add -A && git commit -m "chore: before add-cart dto") — ไม่ต้อง @-mention ไฟล์ตัวอย่าง Cursor Agent อ่านสไตล์ DTO ที่มีอยู่แล้วในโปรเจกต์และการตั้งค่า ValidationPipe ใน main.ts ได้เอง

ก่อนส่ง อ่านกติกาของคอร์สอีกครั้ง: AI พิมพ์แทนคุณได้ แต่คุณต้องอธิบายทุกบรรทัดได้ — ถ้าอธิบายไม่ได้ แปลว่ายังไม่ผ่านบทนี้

สร้าง DTO สำหรับ validate body ของ POST /carts/add ตามที่ React app ส่งมา ผลลัพธ์ที่ต้องได้ (ยังยิง curl ไม่ได้จนกว่าจะผูก route ในขั้นถัดไป — ตอนนี้ตรวจด้วย build และอ่านโค้ด): - body รูปนี้ผ่าน validation ครบทุกชั้น: { "userId": 1, "products": [{ "id": 1, "quantity": 2 }], "address": { "address": "...", "email": "...", "phone": "..." } } - ทุก field required: ขาด userId, products หรือ address ตัวใดตัวหนึ่ง → 400 - userId, products[].id, products[].quantity ต้องเป็นจำนวนเต็มตั้งแต่ 1 ขึ้นไป — 0, ติดลบ หรือทศนิยม → 400 - products: [] (ตะกร้าว่าง) → 400 - ทุกสมาชิกใน products ถูกตรวจ: { "products": [{ "id": 1 }] } ที่ขาด quantity → 400 - address ถูกตรวจข้างในตามกฎเดียวกับฟอร์มฝั่ง React (address ไม่ว่าง, email เป็นอีเมล, phone ไม่ว่าง): "address": {} → 400 และ email ผิดรูป → 400 ด้วย message ที่มีคำนำหน้า address. เช่น "address.email must be an email" - error 400 ใช้รูปแบบมาตรฐานของ ValidationPipe ใน Nest (message เป็น array ของทุกข้อที่ผิด) ไม่ต้องเขียนรูปแบบเอง - field ที่ไม่ได้ประกาศ (เช่น isAdmin) ถูกตัดทิ้ง ไม่ไหลเข้า service - DTO ของ body ถูก export ไว้ให้ service ที่คิดเงินและ route POST /carts/add import ไปใช้ในขั้นถัดไป - npm run build และ npm run lint ผ่าน ขอบเขต: - ห้ามติดตั้ง dependency ใหม่ - ยังไม่ต้องสร้าง service, controller หรือ module ของ orders

ตรวจโค้ดที่ AI สร้าง

  • body ของ request เป็น class ไม่ใช่ interface — ไม่งั้น ValidationPipe ไม่มี rule ให้ตรวจเลย
  • address และสมาชิกทุกตัวของ products ถูกแปลงเป็น instance และถูกไล่ตรวจข้างในจริง — อ่านโค้ดแล้วชี้ได้ว่าบรรทัดไหนทำให้ "address": {} ได้ 400 (ถ้าชี้ไม่ได้ มักแปลว่าขาดตัวแปลงชนิดของ nested object)
  • ตะกร้าว่าง (products: []) ไม่ผ่าน
  • email ถูกตรวจว่าเป็นอีเมลจริง ไม่ใช่แค่เป็น string และไม่มี regex เขียนเองมาแทนตัวตรวจของ library
  • ไม่มี field ไหนเป็น optional หรือมีค่า default
  • userId, id, quantity ปฏิเสธ 0, ค่าติดลบ และทศนิยม
  • git status ไม่มีไฟล์ที่ไม่เกี่ยวกับ DTO ตัวนี้ถูกแก้, package.json ไม่เปลี่ยน และไม่มี any, as หรือ !

AI มักพลาดตรงนี้: ลืม @Type(() => AddressDto) ที่ field address เพราะมันดู "ไม่ใช่ array" จึงรู้สึกว่าไม่ต้องมี ผลคือ address กลายเป็น plain object ที่ validation ผ่านทุกค่า รวมถึง object ว่าง ตรวจง่าย ๆ ด้วยการนับจำนวน @Type ในไฟล์ว่าได้ 2 จริง อีกกรณีคือใส่ @IsObject() แทน @ValidateNested() ซึ่งตรวจแค่ว่า "เป็น object" แล้วจบ

โค้ดอ้างอิงของบทนี้ — เป็นหนึ่งในวิธีที่ถูก ของคุณไม่จำเป็นต้องเหมือนทุกบรรทัด ขอแค่ผ่านผลลัพธ์ที่ต้องได้ (ขั้นถัดไปอ้างชื่อ AddCartDto และ path src/orders/dto/add-cart.dto.ts ถ้าของคุณต่างไปก็ไม่เป็นไร Cursor ในขั้นนั้นจะอ่านจากโค้ดของคุณเอง):

// src/orders/dto/add-cart.dto.ts
import { Type } from 'class-transformer';
import {
  ArrayMinSize,
  IsArray,
  IsEmail,
  IsInt,
  IsNotEmpty,
  IsString,
  Min,
  ValidateNested,
} from 'class-validator';

export class CartProductDto {
  @IsInt()
  @Min(1)
  id: number;

  @IsInt()
  @Min(1)
  quantity: number;
}

export class AddressDto {
  @IsString()
  @IsNotEmpty()
  address: string;

  @IsEmail()
  email: string;

  @IsString()
  @IsNotEmpty()
  phone: string;
}

export class AddCartDto {
  @IsInt()
  @Min(1)
  userId: number;

  @IsArray()
  @ArrayMinSize(1)
  @ValidateNested({ each: true })
  @Type(() => CartProductDto)
  products: CartProductDto[];

  @ValidateNested()
  @Type(() => AddressDto)
  address: AddressDto;
}

ถ้าอธิบายบรรทัดไหนไม่ได้ ยังไม่ผ่านบทนี้ — กลับไปอ่านส่วนแนวคิดก่อน

ผลลัพธ์ที่คาดหวัง

ได้ไฟล์ใหม่ไฟล์เดียวคือ src/orders/dto/add-cart.dto.ts และ npm run build ผ่านโดยไม่มี error — โฟลเดอร์ src/orders/ ยังไม่มี module ลงทะเบียนใน AppModule ดังนั้นการ build จะแค่ compile ไฟล์นี้ผ่าน type check ไม่มี route ใหม่โผล่ใน log ของ npm run start:dev และยังไม่มีอะไรให้ curl ทดสอบในบทนี้

ข้อความ error ที่ DTO ชุดนี้จะผลิตออกมา จะได้เห็นของจริงตอนเปิด route POST /carts/add — เช่น userId ที่ไม่ได้ส่งมาให้ {"message":["userId must not be less than 1","userId must be an integer number"],"error":"Bad Request","statusCode":400} และ email ผิดรูปให้ {"message":["address.email must be an email"],"error":"Bad Request","statusCode":400} สังเกตคำนำหน้า address. — นั่นคือหลักฐานว่า @ValidateNested() ไล่ตรวจเข้าไปข้างในจริง

ตรวจว่าใช้งานได้จริง

  • npm run build ผ่าน ไม่มี error
  • npm run lint ผ่าน (oxlint ดู src/ จึงครอบไฟล์นี้แล้ว)
  • ถ้าใช้ class-transformer เหมือนโค้ดอ้างอิง grep -rc "@Type" src/orders/dto/ รวมกันต้องได้ 2 (หนึ่งที่ products หนึ่งที่ address)
  • grep -rn "IsOptional\|?:" src/orders/dto/ ไม่เจออะไรเลย — ยืนยันว่าไม่มี field optional หลุดมา
  • git diff --stat HEAD เห็นแค่ไฟล์ DTO ที่สร้างใหม่ (ในโค้ดอ้างอิงคือ src/orders/dto/) และ package.json กับ package-lock.json ไม่อยู่ในรายการ
  • commit ผลงานของบทนี้: git add -A && git commit -m "feat: add-cart dto"
