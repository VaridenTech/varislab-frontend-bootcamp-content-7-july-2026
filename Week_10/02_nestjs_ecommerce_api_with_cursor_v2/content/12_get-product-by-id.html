GET /products/:id

เมื่อจบบทนี้ คุณจะสามารถ

  • รับ route parameter ด้วย @Param('id', ParseIntPipe) แล้วส่งต่อเป็น number ให้ service
  • อธิบายว่าทำไม @Get('categories') ต้องประกาศไว้ก่อน @Get(':id') เสมอ
  • พิสูจน์ว่า response ของสินค้าชิ้นที่ 1 ตรงกับ docs/api-spec.md ทุกคีย์ และข้อความใน NotFoundException ตรงตัวอักษรต่ออักษรกับที่เราออกแบบไว้
  • ย้าย checklist ของบทนี้ลงไปอยู่ใน npm run contract:check — คำสั่งเดียวที่ตัดสินถูก/ผิดได้เองและคืน exit code ให้ทั้งคุณและ AI ใช้ตรวจซ้ำได้

บทนี้คือบทที่ mapper ได้ทำงานจริง

บทที่ 11 เขียน toProductResponse ไว้แต่ยังไม่มีใครเรียก บทนี้เราต่อสายให้ครบ: controller รับ id → service query สินค้าพร้อม relation → ส่งแถวเข้า mapper → คืน JSON ที่ตรงกับ section Product ใน docs/api-spec.md

รูปแบบการรับ parameter เป็นแบบเดียวกับ NestJS Fundamentals บทที่ 7 (route parameters) และการโยน error เป็นแบบเดียวกับบทที่ 13 (ข้อความ error ที่อ่านรู้เรื่อง) ต่างกันที่คราวนี้ข้อความไม่ใช่เรื่องรสนิยม — มันคือส่วนหนึ่งของสัญญา

ข้อความ 404 คือสัญญา ไม่ใช่ข้อความประกอบ

เปิด docs/api-spec.md ดู section Errors — เราออกแบบให้ product ที่ไม่มีอยู่ตอบ status 404 พร้อม body

{ "message": "Product 9999 not found" }

React app ที่เราจะต่อในบทที่ 23 อ่าน data.message มาโชว์ให้ผู้ใช้เห็นตรง ๆ ผ่าน ApiError ของมัน ข้อความจึงต้องตรงตามที่เราออกแบบไว้ทุกตัวอักษร ถ้าเขียนเป็น Product #9999 not found แบบที่เคยทำในคอร์ส NestJS Fundamentals หน้าเว็บก็ยังไม่พัง (เพราะ client อ่านแค่ field message ไม่สนใจเนื้อหา) แต่ผิดสัญญาที่เราเขียนไว้ใน docs/api-spec.md และ script ตรวจสัญญาที่เราจะเขียนท้ายบทนี้จะจับได้ทันที

throw new NotFoundException(`Product ${id} not found`);

include และเหตุผลที่ต้องสั่ง orderBy ให้ reviews

แถว Product เปล่า ๆ ไม่มี category และไม่มี reviews ติดมา เราจึงต้องสั่ง include (ทบทวน NestJS Fundamentals บทที่ 26 เรื่องดึง model พร้อม relation)

include: { category: true, reviews: { orderBy: { id: 'asc' } } }

ทำไมต้องมี orderBy ให้ reviews ด้วย? เพราะ array ที่ลำดับไม่ตรงกันจะทำให้การตรวจสัญญาในบทถัด ๆ ไปไม่ผ่าน และ Postgres ไม่รับประกันลำดับของแถวที่คืนมาถ้าไม่มี ORDER BY — มันจะเรียงตามที่สะดวกที่สุดในแผนการ query นั้น ๆ ซึ่งอาจเปลี่ยนเมื่อข้อมูลโตขึ้นหรือมี index ใหม่ seed ในบทที่ 9 ใส่ review ของสินค้าแต่ละชิ้นตามลำดับที่เขียนไว้ในสคริปต์ ดังนั้น id น้อยไปมากคือลำดับเดียวกับที่ seed ใส่ไว้

ลำดับการประกาศ route คือลำดับที่ Nest ลองจับ

Nest ลงทะเบียน handler ตามลำดับที่ประกาศไว้ใน class และ router จะจับ pattern แรกที่ตรง ถ้าเราเผลอวาง @Get(':id') ไว้ก่อน

GET /products/categories
  → ตรงกับ pattern /products/:id  (id = "categories")
  → ParseIntPipe แปลง "categories" ไม่ได้
  → 400 Bad Request

endpoint ที่เคยทำงานในบทที่ 10 จะตายเงียบ ๆ ทั้งที่เราไม่ได้แตะโค้ดของมันเลย กฎง่าย ๆ คือ route ที่เป็นคำตายตัวต้องมาก่อน route ที่มี parameter เสมอ ดังนั้นใน ProductsController เราวาง findOne เป็น handler สุดท้ายของ class ตั้งแต่วันนี้ แล้วบทที่ 13 และ 14 จะแทรก handler ใหม่ไว้ก่อนมันทุกครั้ง

ทำไม id ที่ไม่ใช่ตัวเลขได้ 400 ไม่ใช่ 404

ถ้ายิง GET /products/abc เราตอบ 400 พร้อมข้อความ Validation failed (numeric string is expected) เพราะ ParseIntPipe ดักไว้ก่อนที่ handler จะทำงาน — เป็นพฤติกรรมมาตรฐานของ Nest ไม่ต้องเขียนโค้ดเพิ่ม

เราเลือกที่จะปล่อยให้เป็น 400 เพราะ React app ไม่เคยยิง id ที่ไม่ใช่ตัวเลข (มันได้ id มาจาก list ที่ API ตอบไป) และ 400 เป็นคำตอบที่ตรงความจริงกว่า: request นั้นผิดรูป ไม่ใช่ resource ไม่มีอยู่ พฤติกรรมนี้จะถูกตรวจซ้ำทุกครั้งด้วย contract:check ที่เราเขียนท้ายบทนี้

เป้าหมายของบทนี้

ในโค้ดอ้างอิงคือการเพิ่ม handler ใน controller กับ method ใน service เดิมของ src/products/ — Cursor เลือกวิธีเองได้ โดยต้องได้ผลลัพธ์นี้

  • GET /products/:id ตอบสินค้าหนึ่งชิ้นครบ 22 คีย์ผ่าน mapper จากบทที่ 11
  • id ที่ไม่มีอยู่ → 404 Product 9999 not found ตรงตัวอักษร / id ที่ไม่ใช่ตัวเลข → 400
  • GET /products/categories ยังทำงานเหมือนบทที่ 10

บทนี้ไม่แตะ mapper และ DTO จากบทที่ 11 เลย

สั่ง Cursor ต่อ endpoint สินค้าหนึ่งชิ้น

commit งานก่อน แล้วเปิดแชทใหม่ใน Cursor โหมด Agent (git add -A && git commit -m "chore: before product by id") จากนั้นส่ง prompt นี้

เพิ่ม endpoint GET /products/:id ที่ตอบสินค้าหนึ่งชิ้นตามรูปทรงใน docs/api-spec.md และ 404 ด้วยข้อความที่เราออกแบบไว้ @<controller และ service ของ products ที่คุณสร้างไว้ในบทที่ 10> — โค้ดอ้างอิงคือ src/products/products.controller.ts กับ src/products/products.service.ts ผลลัพธ์ที่ต้องได้: - GET /products/1 ตอบ 200 เป็นสินค้าครบ 22 คีย์ตาม section Product ใน docs/api-spec.md ผ่าน mapper เดิมจากบทที่ 11 (title "Velvet Matte Lipstick", price 9.99, discountPercentage 10.48, brand "Lumina") - reviews ของสินค้าเรียงตาม id ของ review (ลำดับที่ seed ใส่ไว้) และคงที่ทุกครั้งที่ยิง - GET /products/3 (ไม่มีส่วนลด) ไม่มีคีย์ discountPercentage เลย - GET /products/9999 ตอบ 404 และ message เป็น "Product 9999 not found" ตรงตัวอักษรต่ออักษร - GET /products/abc ตอบ 400 พร้อมข้อความ "Validation failed (numeric string is expected)" - GET /products/categories ยังตอบรายการหมวด 24 รายการเหมือนเดิม ไม่ถูกจับเป็น id ขอบเขต: - ห้ามติดตั้ง dependency ใหม่ - ห้ามแก้ mapper/DTO - ยังไม่ต้องทำ GET /products (list) หรือ pagination

ตรวจโค้ดที่ AI สร้าง

  • GET /products/abc ได้ 400 — ไม่ใช่ 404 หรือ 500 (ถ้าได้ 500 แปลว่า id ที่ไม่ใช่ตัวเลขหลุดเข้าไปถึง query)
  • GET /products/9999 ได้ 404 และข้อความตรงตัวอักษรต่ออักษร: Product 9999 not found
  • GET /products/categories ยังตอบรายการหมวด ไม่ถูกจับเป็น id (log ตอน start ต้องเห็น route categories ก่อน :id)
  • สินค้ามี category เป็น slug และมี reviews ครบ — ถ้าได้ category เป็น undefined หรือ reviews ว่าง แปลว่า query ไม่ได้ดึง relation มาด้วย
  • response ผ่าน mapper ตัวเดิมจากบทที่ 11 ไม่ได้ประกอบรูปทรงใหม่ขึ้นมาเองใน service
  • ไม่มีไฟล์ที่ไม่เกี่ยวกับเป้าหมายถูกแก้, mapper/DTO ไม่ถูกแก้, และไม่มี any / as / !

AI มักพลาดตรงนี้: เขียนข้อความเป็น Product #9999 not found ตามสไตล์ที่เคยเห็นในคอร์ส NestJS Fundamentals (ซึ่งเป็นข้อความที่ถูกต้องในคอร์สนั้น แต่ผิดสัญญาในคอร์สนี้) อีกแบบคือใช้ findFirst({ where: { id } }) โดยลืม include ทั้งก้อน — TypeScript จะฟ้องเมื่อส่งเข้า toProductResponse เพราะ type ProductWithRelations ไม่ยอม แต่บางครั้ง Cursor จะแก้ปัญหาด้วยการเติม as เข้าไปกลบ ให้ค้นคำว่า as ในไฟล์แล้วลบออก แก้ที่ include แทน

โค้ดอ้างอิงของบทนี้ — เป็นหนึ่งในวิธีที่ถูก ของคุณไม่จำเป็นต้องเหมือนทุกบรรทัด ขอแค่ผ่านผลลัพธ์ที่ต้องได้:

src/products/products.service.ts

import { Injectable, NotFoundException } from '@nestjs/common';
import { ConfigService } from '@nestjs/config';
import { PrismaService } from '../prisma/prisma.service.js';
import { toProductResponse } from './product.mapper.js';
import { ProductResponseDto } from './dto/product-response.dto.js';

@Injectable()
export class ProductsService {
  constructor(
    private readonly prisma: PrismaService,
    private readonly config: ConfigService,
  ) {}

  async findCategories() {
    const appUrl = this.config.getOrThrow<string>('APP_URL');
    const categories = await this.prisma.category.findMany({ orderBy: { id: 'asc' } });
    return categories.map(({ slug, name }) => ({
      slug,
      name,
      url: `${appUrl}/products/category/${slug}`,
    }));
  }

  async findOne(id: number): Promise<ProductResponseDto> {
    const product = await this.prisma.product.findUnique({
      where: { id },
      include: { category: true, reviews: { orderBy: { id: 'asc' } } },
    });
    if (!product) {
      throw new NotFoundException(`Product ${id} not found`);
    }
    return toProductResponse(product);
  }
}

src/products/products.controller.ts

import { Controller, Get, Param, ParseIntPipe } from '@nestjs/common';
import { ProductsService } from './products.service.js';

@Controller('products')
export class ProductsController {
  constructor(private readonly productsService: ProductsService) {}

  @Get('categories')
  findCategories() {
    return this.productsService.findCategories();
  }

  @Get(':id')
  findOne(@Param('id', ParseIntPipe) id: number) {
    return this.productsService.findOne(id);
  }
}

เปลี่ยน checklist ให้เป็นคำสั่งเดียวที่รันได้

ทุกข้อในส่วน "ตรวจว่าใช้งานได้จริง" ด้านบนคือสัญญาที่ต้องเป็นจริงตลอดไป ไม่ใช่แค่วันนี้ — บทที่ 13 และ 14 จะกลับมาแก้ controller ตัวเดิมนี้อีก และจะไม่มีใครไล่ยิง curl ห้าคำสั่งแล้วอ่านผลด้วยตาทุกครั้งที่ AI แก้โค้ดให้ วิธีที่ใช้ได้จริงคือย้าย checklist ทั้งอันลงไปอยู่ในไฟล์ที่รันได้ แล้วตัดสินด้วยคำสั่งเดียวว่า npm run contract:check ผ่านหรือไม่ผ่าน

เหตุผลที่ลึกกว่านั้นคือ check ที่รันได้คือสิ่งที่ AI เอาไปใช้เองได้ คู่มือของเครื่องมือ agent ทุกตัวพูดตรงกันข้อหนึ่ง: ให้คำสั่งที่ตัดสินถูก/ผิดได้เองกับมัน แล้วมันจะรัน อ่านผล และแก้ซ้ำจนผ่านได้โดยไม่ต้องรอคุณอ่าน output ให้ทีละบรรทัด ส่วน checklist ที่เป็นข้อความเฉย ๆ มีแต่คุณเท่านั้นที่ตรวจได้ และเป็นงานที่คนเลิกทำเป็นคนแรกเมื่อรีบ

เขียนไฟล์นี้ด้วยมือ ไม่ต้องสั่ง Cursor ด้วยเหตุผลเดียวกับ docs/api-spec.md ในบทที่ 3: เครื่องมือที่ใช้ตรวจงานของ AI ไม่ควรถูกเขียนโดย AI ตัวที่มันตรวจ และการพิมพ์เองคือการพิสูจน์ว่าคุณอ่านสัญญาออกจริง

mkdir -p scripts # เขียนไฟล์ scripts/contract-check.ts ด้วยมือตามด้านล่าง # แล้วเพิ่มบรรทัดนี้ในส่วน "scripts" ของ package.json ต่อจาก db:seed # "contract:check": "node scripts/contract-check.ts",

ไฟล์นี้ยังไม่ต้องติดตั้งอะไรเพิ่มเลย — fetch และ top-level await มีอยู่ใน Node อยู่แล้ว ส่วนไฟล์ .ts ที่ไม่มี import ข้ามไฟล์ แบบนี้ Node 24 รันได้เองด้วยการลบ type ทิ้ง (type stripping) จึงสั่ง node ตรง ๆ ได้ ไม่ต้องมี build step (ข้อจำกัดข้อนี้จะกลับมาสำคัญในบทที่ 15 ตอนที่ไฟล์เริ่ม import ข้ามไฟล์)

const BASE = process.env.LOCAL_URL ?? 'http://localhost:3000';

interface Check {
  name: string;
  run: () => Promise<void>;
}

async function getJson(path: string) {
  const response = await fetch(`${BASE}${path}`);
  const body = await response.json();
  return { status: response.status, body };
}

function assert(ok: boolean, message: string) {
  if (!ok) throw new Error(message);
}

const checks: Check[] = [
  {
    name: 'GET /products/categories → 200, 24 categories',
    run: async () => {
      const { status, body } = await getJson('/products/categories');
      assert(status === 200, `expected 200, got ${status}`);
      assert(body.length === 24, `expected 24 categories, got ${body.length}`);
      const keys = Object.keys(body[0]).sort().join(',');
      assert(keys === 'name,slug,url', `expected name,slug,url — got ${keys}`);
    },
  },
  {
    name: 'GET /products/1 → 200, product with 22 keys',
    run: async () => {
      const { status, body } = await getJson('/products/1');
      assert(status === 200, `expected 200, got ${status}`);
      const count = Object.keys(body).length;
      assert(count === 22, `expected 22 keys, got ${count}`);
      assert(body.title === 'Velvet Matte Lipstick', `unexpected title: ${body.title}`);
      assert(typeof body.category === 'string', 'category must be a slug string');
      assert(Array.isArray(body.reviews), 'reviews must be an array');
    },
  },
  {
    name: 'GET /products/9999 → 404 with the exact message',
    run: async () => {
      const { status, body } = await getJson('/products/9999');
      assert(status === 404, `expected 404, got ${status}`);
      assert(
        body.message === 'Product 9999 not found',
        `wrong message: ${JSON.stringify(body.message)}`,
      );
    },
  },
  {
    name: 'GET /products/abc → 400 with message',
    run: async () => {
      const { status, body } = await getJson('/products/abc');
      assert(status === 400, `expected 400, got ${status}`);
      assert(body.message !== undefined, 'error body must carry a message');
    },
  },
];

let failures = 0;
for (const check of checks) {
  try {
    await check.run();
    console.log(`✅ ${check.name}`);
  } catch (error) {
    failures += 1;
    console.log(`❌ ${check.name}`);
    console.log(`   ${error instanceof Error ? error.message : String(error)}`);
  }
}
process.exit(failures === 0 ? 0 : 1);

เปิด API ค้างไว้ที่พอร์ต 3000 แล้วรัน npm run contract:check ในอีก terminal ต้องได้สี่บรรทัดนี้

✅ GET /products/categories → 200, 24 categories
✅ GET /products/1 → 200, product with 22 keys
✅ GET /products/9999 → 404 with the exact message
✅ GET /products/abc → 400 with message
  • ลองทำให้พังก่อนจะเชื่อมัน: แก้ข้อความใน NotFoundException เป็น Product #9999 not found ชั่วคราว รอ watch mode compile แล้วรันซ้ำ — บรรทัดที่สามต้องเป็น ❌ พร้อมพิมพ์ข้อความที่ได้จริงออกมา และ echo $? ต้องไม่ใช่ 0 จากนั้นย้อนกลับด้วย git checkout -- .
  • ปิด API (Ctrl+C ที่ terminal ของ npm run start:dev) แล้วรันซ้ำ — ต้องได้ ❌ ทั้งสี่บรรทัดพร้อมข้อความ fetch failed ไม่ใช่ผ่านเงียบ ๆ
  • commit ด้วย git add -A && git commit -m "test: contract check for the products endpoints"

สี่ check นี้จะโตขึ้นทีละบท: บทที่ 13 เพิ่มสามข้อของ GET /products บทที่ 14 เพิ่มอีกสองข้อของหมวดสินค้า รวมเป็นเก้าข้อ แล้วบทที่ 15 จะเขียนทั้งไฟล์ใหม่ด้วย zod ให้ตรวจ ทุก field ใน response แทนที่จะตรวจเฉพาะข้อที่เราอุตส่าห์นึกออกและเขียนถึงเอง
