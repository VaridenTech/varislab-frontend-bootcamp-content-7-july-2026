ทำสัญญาให้รันได้จริงด้วย zod

เมื่อจบบทนี้ คุณจะสามารถ

  • ยกระดับ e2e test ของสัญญาที่เขียนเองไว้ด้วยมือก่อนหน้านี้ ให้ตรวจ โครงสร้างทั้งก้อน ของ response ด้วย zod ไม่ใช่แค่ field ที่เราอุตส่าห์นึกออกและเขียนเช็คไว้เอง
  • อธิบายว่า .strict() ให้อะไรเพิ่มจาก z.object({...}) เฉย ๆ — มันปฏิเสธ field ที่เกินมาหรือถูกเปลี่ยนชื่อ ไม่ใช่แค่ field ที่หายไป
  • อ่าน error ที่ zod โยนออกมาตอน .parse() ล้มเหลว (ZodError) เพื่อหาว่า field ไหนพังและพังเพราะอะไร โดยไม่ต้องเขียนตัวหา diff เอง

test ที่เขียนเอง จับได้แค่สิ่งที่เรานึกถึง

npm run test:e2e มีอยู่แล้วตั้งแต่ตอนที่คุณเขียน test/products.e2e-spec.ts ด้วยมือ และโตมาเป็นเก้า test ตอนเพิ่ม pagination กับ endpoint ตามหมวด — มันแก้ปัญหา "ไล่ยิง curl ใหม่ทุกครั้ง" ไปแล้วเรียบร้อย แต่มันมีช่องโหว่ที่ใหญ่กว่าเดิมซ่อนอยู่: มันตรวจเฉพาะสิ่งที่เราเขียนสั่งให้มันตรวจ ตอนนี้มันดู status, จำนวน category, จำนวนคีย์ของสินค้าชิ้นที่ 1, และข้อความ 404 — เท่านั้น

แปลว่าถ้า mapper เปลี่ยน thumbnail เป็น thumbnailUrl เงียบ ๆ จำนวนคีย์ยังเป็น 22 เท่าเดิม ทุก test ยังเขียว และสัญญาพังไปแล้วโดยไม่มีใครรู้ การไล่เขียน expect ให้ครบทั้ง 22 คีย์ของทุก endpoint ด้วยมือเป็นงานที่ไม่มีใครเขียนจบและไม่มีใครอยากดูแล

สิ่งที่เราต้องการคือ regression test ของสัญญา ที่ตรวจ body ทั้งก้อน: test ชุดเดิมที่ยิง request ชุดเดิมไปที่ API ของเรา แต่คราวนี้เทียบ response ทั้งอันกับ schema ที่เขียนจาก docs/api-spec.md ไม่ใช่เทียบทีละ field ที่เรานึกออก — และยังคืน exit code ที่ไม่ใช่ศูนย์เมื่อพังเหมือนเดิม เพื่อให้เอาไปแขวนใน CI ได้ในอนาคต

จุดที่ทำให้ e2e test ต่างจาก unit test คือมันยิงแอปจริงทั้งใบที่ต่อฐานข้อมูลจริง ไม่ได้ mock อะไรเลย มันจึงตรวจสิ่งที่ TypeScript ตรวจให้ไม่ได้: TypeScript เช็คว่า ProductResponseDto ที่คุณ ประกาศไว้ ถูกต้องตอน compile แต่ไม่รู้ว่า JSON ที่ออกไปจริงทาง HTTP ตรงกับที่ประกาศไว้หรือเปล่า ถ้า mapper คืนค่าผิดชนิด หรือมีใคร (หรือ AI) เปลี่ยนชื่อ field ไปเงียบ ๆ แต่ยังพอ compile ผ่านได้ด้วยเหตุผลบางอย่าง TypeScript จะไม่รู้เรื่องเลยจนกว่าจะมีคนอ่าน response จริง — นี่คือช่องว่างที่ zod ปิดให้ที่ขอบเขต JSON

ทำไม schema ต้องอยู่คนละไฟล์กับ test

schema ทั้งหมดแยกไว้ในไฟล์ test/contract-schemas.ts ต่างหาก ไม่ได้เขียนปนอยู่ใน products.e2e-spec.ts ด้วยเหตุผลสองข้อ ข้อแรก test ของ POST /carts/add ที่จะมาภายหลังอยู่คนละไฟล์กัน (orders.e2e-spec.ts) แต่ต้อง import schema ชุดเดียวกันนี้ไปใช้ซ้ำ — สัญญาต้องมีฉบับเดียว ไม่ใช่สำเนาที่ค่อย ๆ เพี้ยนจากกัน ข้อสอง ไฟล์ schema ล้วน ๆ อ่านและรีวิวแยกจาก test ที่รันจริงได้ง่ายกว่า: มันคือ docs/api-spec.md ที่เขียนใหม่ในรูปแบบที่เครื่องอ่านออก

ไฟล์ .ts ที่ import ข้ามกันแบบนี้ไม่ต้องตั้งค่าอะไรเพิ่มเลย เพราะ Vitest compile TypeScript ให้อยู่แล้ว — ขอแค่เขียน path ลงท้าย .js ตามธรรมเนียม ESM+TypeScript ที่ใช้ทั่วโปรเจกต์นี้ (ไฟล์จริงบนดิสก์คือ .ts ไม่ใช่พิมพ์ผิด)

ไฟล์ทั้งสองอยู่ใน test/ จึงถูก npm run lint ครอบให้อยู่แล้ว (oxlint src/ test/) และถูก vitest.config.e2e.ts มองเห็น ซึ่ง include ไว้เฉพาะ **/*.e2e-spec.ts — ไฟล์ schema จึงไม่ถูกนับเป็น test suite เปล่า ๆ เพราะชื่อไม่ได้ลงท้ายแบบนั้น

เป้าหมายของบทนี้

รายการด้านล่างคือไฟล์ที่เปลี่ยนในโค้ดอ้างอิงของคอร์ส — ใช้เป็นแผนที่ตอนเทียบงาน ไม่ใช่ข้อบังคับ Cursor ของคุณอาจวางไฟล์หรือตั้งชื่อต่างไปได้ ขอแค่ผ่านผลลัพธ์ที่ต้องได้ใน prompt

  • test/products.e2e-spec.ts — ในโค้ดอ้างอิง: import schema จาก ./contract-schemas.js, มี เก้า it() เรียงตามลำดับ (ชุดเดียวกับที่คุณสะสมไว้ตั้งแต่ฉบับเขียนมือ แต่เรียงใหม่และตรวจ body ทั้งก้อน ดูรายชื่อในส่วนผลลัพธ์ที่คาดหวังด้านล่าง) แต่ละ test เรียก schema.parse(response.body) ตรง ๆ (ไม่ใช่ .safeParse()) เพื่อให้ ZodError ที่โยนออกมาทำให้ test ล้มพร้อมรายละเอียดครบ ไม่ต้องเขียน if เช็ค success เอง / โครง beforeAll/afterAll ที่ boot แอปยังเป็นตัวเดิม / ต้องไม่มี test ของ POST /carts/add เพราะ endpoint นั้นยังไม่มีอยู่จริง ณ จุดนี้ (จะมาถึงภายหลัง)
  • package.json — ในโค้ดอ้างอิง: มี zod เพิ่มเข้ามาตัวเดียว / ไม่แก้ script ใด ๆ เพราะ test:e2e ที่ scaffold ให้มาครอบไฟล์ *.e2e-spec.ts ทุกไฟล์อยู่แล้ว

ไม่มีไฟล์ใน src/ ถูกแตะในบทนี้เลย — สิ่งที่เราเขียนคือ test ไม่ใช่ฟีเจอร์ และ schema พวกนี้ไม่ได้มาแทนที่ ProductResponseDto ที่มีอยู่แล้ว: ProductResponseDto ยังเป็น type ตอน compile ที่ Swagger CLI plugin จะอ่านตอนทำเอกสาร API อยู่เหมือนเดิม ส่วน zod schema ในบทนี้เป็นการตรวจแยกอีกชั้นหนึ่งตอนruntime ว่า response จริงที่ออกไปทาง HTTP ยังตรงกับสัญญาอยู่หรือเปล่า — ไม่ใช่รูปทรงที่สามอันดับที่มาแข่งกัน แต่เป็นเครื่องมือคนละงาน: DTO บอก compiler, zod บอกตอนรันจริง

สั่ง Cursor เขียน schema และ test ตรวจสัญญา

commit งานก่อน แล้วเปิดแชทใหม่ใน Cursor โหมด Agent (git add -A && git commit -m "chore: before contract check") ตรวจว่าฐานข้อมูลรันอยู่ เพราะเราจะรัน test ทันทีหลังได้โค้ด

เขียน zod schema แล้วเขียน e2e test ของสัญญาที่มีอยู่ใหม่ทั้งไฟล์ ให้ตรวจ body ทั้งก้อนตาม docs/api-spec.md @package.json @<ไฟล์ e2e test ของ products ที่คุณเขียนไว้ก่อนหน้านี้> — โค้ดอ้างอิงคือ test/products.e2e-spec.ts ผลลัพธ์ที่ต้องได้: - npm run test:e2e ตอนฐานข้อมูลรันอยู่และ API ตรงสัญญา ผ่านครบเก้า test ตามลำดับนี้ แล้ว exit 0 1. ตรวจโค้ดที่ AI สร้าง

  • ทุก object schema เต็มรูป (product, category, envelope, error) ปฏิเสธ field ที่ไม่รู้จัก — ทดสอบได้จริงด้วยการเปลี่ยนชื่อ field ในส่วนตรวจว่าใช้งานได้จริงด้านล่าง ถ้าตรวจแล้ว test ยังเขียว แปลว่า schema ปล่อยผ่านเงียบ ๆ
  • รัน npm run test:e2e ได้เก้า test ตามลำดับในผลลัพธ์ที่ต้องได้ และไม่มี test ของ POST /carts/add ปนมา เพราะ endpoint นั้นยังไม่มีอยู่จริงในบทนี้
  • รายงานของ test ที่ล้มบอกได้ว่า field ไหนพังและพังเพราะอะไร (มี path) — ไม่ใช่ข้อความคงที่อย่าง "invalid response"
  • import ข้ามไฟล์ในโปรเจกต์ลงท้าย .js ตามกติกาใน .cursor/rules (แม้ไฟล์จริงคือ .ts — ไม่ใช่พิมพ์ผิด)
  • ไม่มี URL ของ server ตัวไหนฮาร์ดโค้ดอยู่ในไฟล์ test เลย — ทุก request ยิงผ่าน request(app.getHttpServer()) เข้าแอปที่ suite boot เอง
  • มี test ล้มแล้ว echo $? ไม่ใช่ 0
  • git status ไม่มีไฟล์ใน src/ และไม่มีไฟล์ที่ไม่เกี่ยวกับ test ตรวจสัญญาถูกแก้, dependency ที่เพิ่มมีแค่ zod และไม่มี any, as หรือ !

AI มักพลาดตรงนี้: เขียน schema เป็น z.object({...}) เฉย ๆ โดยไม่ปิดท้ายด้วย .strict() — โค้ดยัง compile ผ่านและดูทำงานถูกในตอนแรก แต่ zod โหมดปกติ (ที่เรียกว่า "strip") จะเงียบ ๆ ตัดทุก field ที่ไม่รู้จักทิ้งไปโดยไม่ error เลย ถ้าวันหนึ่งมีใคร (หรือ AI ตัวอื่น) เปลี่ยนชื่อ field ใน mapper หรือเผลอเพิ่ม field แปลกปลอมเข้ามา test จะยังเขียวเหมือนไม่มีอะไรเกิดขึ้น ทั้งที่ response จริงเปลี่ยนไปแล้ว อีกจุดที่พลาดได้คือใช้ .safeParse() แล้ว expect(result.success).toBe(true) เฉย ๆ — test ยังล้มถูกต้องอยู่ แต่รายงานจะบอกได้แค่ expected false to be true ไม่บอกว่า field ไหนพังเพราะอะไร ทำให้ debug ช้าลงกลับไปเหมือนสมัยที่ยังไม่มี schema เลย ส่วน .parse() ที่โยน ZodError ออกมาจะพา issues ทั้งชุดขึ้นไปอยู่ในรายงานของ Vitest ให้เอง

โค้ดอ้างอิงของบทนี้ — เป็นหนึ่งในวิธีที่ถูก ของคุณไม่จำเป็นต้องเหมือนทุกบรรทัด ขอแค่ผ่านผลลัพธ์ที่ต้องได้ (ขั้นเปิด route POST /carts/add จะอ้างชื่อ cartProductSchema/orderResponseSchema ถ้าของคุณตั้งชื่อต่างไปก็ไม่เป็นไร Cursor ในขั้นนั้นจะอ่านจากโค้ดของคุณเอง):

test/contract-schemas.ts

import { z } from 'zod';

export const dimensionsSchema = z.object({
  width: z.number(),
  height: z.number(),
  depth: z.number(),
});

export const reviewSchema = z.object({
  rating: z.number().int().min(1).max(5),
  comment: z.string(),
  date: z.iso.datetime(),
  reviewerName: z.string(),
  reviewerEmail: z.email(),
});

export const metaSchema = z.object({
  createdAt: z.iso.datetime(),
  updatedAt: z.iso.datetime(),
  barcode: z.string(),
  qrCode: z.url(),
});

export const productSchema = z
  .object({
    id: z.number().int(),
    title: z.string(),
    description: z.string(),
    category: z.string(),
    price: z.number(),
    discountPercentage: z.number().optional(),
    rating: z.number(),
    stock: z.number().int(),
    tags: z.array(z.string()),
    brand: z.string(),
    sku: z.string(),
    weight: z.number(),
    dimensions: dimensionsSchema,
    warrantyInformation: z.string(),
    shippingInformation: z.string(),
    availabilityStatus: z.string(),
    reviews: z.array(reviewSchema),
    returnPolicy: z.string(),
    minimumOrderQuantity: z.number().int(),
    meta: metaSchema,
    images: z.array(z.url()),
    thumbnail: z.url(),
  })
  .strict();

export const categorySchema = z
  .object({ slug: z.string(), name: z.string(), url: z.url() })
  .strict();

export const listEnvelopeSchema = z
  .object({
    products: z.array(productSchema),
    total: z.number().int(),
    skip: z.number().int(),
    limit: z.number().int(),
  })
  .strict();

export const errorSchema = z
  .object({
    message: z.union([z.string(), z.array(z.string())]),
    error: z.string(),
    statusCode: z.number(),
  })
  .strict();

export const cartProductSchema = z
  .object({
    id: z.number().int(),
    title: z.string(),
    price: z.number(),
    quantity: z.number().int(),
    total: z.number(),
    discountPercentage: z.number().optional(),
    discountedPrice: z.number(),
    thumbnail: z.url(),
  })
  .strict();

export const orderResponseSchema = z
  .object({
    id: z.number().int(),
    userId: z.number().int(),
    products: z.array(cartProductSchema),
    total: z.number(),
    discountedTotal: z.number(),
    totalProducts: z.number().int(),
    totalQuantity: z.number().int(),
  })
  .strict();

  beforeAll(async () => {
    const moduleFixture: TestingModule = await Test.createTestingModule({
      imports: [AppModule],
    }).compile();

    app = moduleFixture.createNestApplication();
    app.useGlobalPipes(
      new ValidationPipe({
        whitelist: true,
        transform: true,
        transformOptions: { enableImplicitConversion: true },
      }),
    );
    await app.init();
  });

  afterAll(async () => {
    await app.close();
  });

  it('GET /products/categories → 200, 24 categories', async () => {
    const response = await request(app.getHttpServer())
      .get('/products/categories')
      .expect(200);

    const categories = categorySchema.array().parse(response.body);
    expect(categories).toHaveLength(24);
  });

  it('GET /products?limit=5&skip=0 → limit and skip echo the request', async () => {
    const response = await request(app.getHttpServer())
      .get('/products?limit=5&skip=0')
      .expect(200);

    const envelope = listEnvelopeSchema.parse(response.body);
    expect(envelope.limit).toBe(5);
    expect(envelope.products).toHaveLength(5);
  });

  it('GET /products?limit=0 → 400 (out of range)', async () => {
    const response = await request(app.getHttpServer())
      .get('/products?limit=0')
      .expect(400);

    errorSchema.parse(response.body);
  });

  it('GET /products?limit=101 → 400 (out of range)', async () => {
    const response = await request(app.getHttpServer())
      .get('/products?limit=101')
      .expect(400);

    errorSchema.parse(response.body);
  });

  it('GET /products/1 → validated product', async () => {
    const response = await request(app.getHttpServer())
      .get('/products/1')
      .expect(200);

    productSchema.parse(response.body);
  });

  it('GET /products/9999 → 404 with message', async () => {
    const response = await request(app.getHttpServer())
      .get('/products/9999')
      .expect(404);

    errorSchema.parse(response.body);
  });

  it('GET /products/abc → 400 with message', async () => {
    const response = await request(app.getHttpServer())
      .get('/products/abc')
      .expect(400);

    errorSchema.parse(response.body);
  });

  it('GET /products/category/groceries → total 27', async () => {
    const response = await request(app.getHttpServer())
      .get('/products/category/groceries?limit=20&skip=0')
      .expect(200);

    const envelope = listEnvelopeSchema.parse(response.body);
    expect(envelope.total).toBe(27);
  });

  it('GET /products/category/nope → 200, empty envelope', async () => {
    const response = await request(app.getHttpServer())
      .get('/products/category/nope?limit=5&skip=0')
      .expect(200);

    const envelope = listEnvelopeSchema.parse(response.body);
    expect(envelope.products).toHaveLength(0);
    expect(envelope.total).toBe(0);
  });
});

app.useGlobalPipes(...) ใน beforeAll คือบรรทัดเดิมที่คุณใส่ไว้ตั้งแต่ขั้น pagination ทบทวนเหตุผลอีกครั้ง: createNestApplication() สร้างแอปจาก AppModule เท่านั้น มันไม่ได้รัน src/main.ts ให้ ดังนั้นอะไรที่ตั้งค่าไว้ใน bootstrap() จะไม่ติดมาเอง ถ้าบรรทัดนี้หายไป สอง test ของ limit=0 และ limit=101 จะได้ status ที่ไม่ใช่ 400 เพราะไม่มี pipe ตัวไหนตรวจ query เลย ค่าใน ValidationPipe ตรงนี้จึงต้องตรงกับใน main.ts ทุกตัว

package.json ไม่ต้องแก้เลยในบทนี้ — test:e2e ที่ scaffold ให้มาเก็บไฟล์ *.e2e-spec.ts ทุกไฟล์อยู่แล้ว สิ่งเดียวที่เปลี่ยนคือมี zod เพิ่มเข้ามาในรายการ dependency

ถ้าอธิบายบรรทัดไหนไม่ได้ ยังไม่ผ่านบทนี้ — กลับไปอ่านส่วนแนวคิดก่อน

ตรวจว่าใช้งานได้จริง

  • npm run test:e2e ผ่านเก้า test ของสัญญาและ echo $? ได้ 0
  • npm run lint ไม่พิมพ์อะไรออกมา — ไฟล์ทั้งสองอยู่ใน test/ จึงถูก oxlint src/ test/ ครอบอยู่แล้ว ไม่ต้อง lint ทีละไฟล์เองเหมือนไฟล์ seed
  • ทำให้พังเพื่อดูว่า .strict() จับได้จริง: เปลี่ยนชื่อ field เดียวกันสองที่พร้อมกัน เพื่อให้ยัง compile ผ่าน — ใน src/products/product.mapper.ts แก้บรรทัดสุดท้ายของ object ที่ return จาก thumbnail: product.thumbnail, เป็น thumbnailUrl: product.thumbnail, และใน src/products/dto/product-response.dto.ts แก้ thumbnail: string; เป็น thumbnailUrl: string; ใน ProductResponseDto (แก้สองที่เพื่อให้ npm run build ยังผ่าน ไม่ติด TS2561 — แต่ถึงแก้แค่ mapper ไฟล์เดียว test ก็ยังจับได้อยู่ดี เพราะ Vitest ไม่ได้ type-check ให้ มันลบ type ทิ้งแล้วรันเลย นี่คือตัวอย่างตรง ๆ ของสิ่งที่ย่อหน้าข้างบนพูดไว้: TypeScript กับ zod ตรวจคนละเวลาและคนละเรื่อง) แล้วรัน npm run test:e2e ซ้ำ — สาม test ที่ response มีสินค้าติดมาด้วยจะล้ม โดย .strict() จับได้สองอย่างพร้อมกันในการพังครั้งเดียว: field ที่หายไป (thumbnail) กับ field แปลกปลอมที่โผล่มา (thumbnailUrl) รายงานของ Vitest จะพา ZodError ของแต่ละ test ขึ้นมาแสดงพร้อม issues ชุดนี้
