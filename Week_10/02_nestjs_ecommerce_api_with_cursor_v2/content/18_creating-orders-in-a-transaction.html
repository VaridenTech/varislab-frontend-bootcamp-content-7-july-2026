สร้างคำสั่งซื้อใน Transaction

เมื่อจบบทนี้ คุณจะสามารถ

  • คำนวณ total, discountedPrice และ discountedTotal ด้วยกติกาเดียวกันทุก field (ปัดทศนิยม 2 ตำแหน่งเสมอ ไม่มีข้อยกเว้น)
  • ใช้ interactive transaction อ่านสินค้าและเขียนคำสั่งซื้อในก้อนเดียว และอธิบายได้ว่า rollback เกิดตอนไหน
  • เขียน mapper แปลง Order + OrderItem เป็น response ตามสัญญา โดยไม่ปล่อยข้อมูลส่วนตัวหลุดออกไป

เลขทุกตัวใน response มาจากไหน

ก่อนเขียนโค้ด ต้องถอดสูตรจาก docs/api-spec.md ให้ครบก่อน ตัวอย่างที่ใช้อ้างอิงตลอดบทนี้คือสินค้า id 1 (Velvet Matte Lipstick) ราคา 9.99 ส่วนลด 10.48 เปอร์เซ็นต์ จำนวน 2 ชิ้น

Fieldสูตรตัวอย่าง
products[].totalprice × quantity ปัด 2 ตำแหน่ง9.99 × 2 = 19.98
products[].discountedPriceround2(total × (1 − discountPercentage / 100))19.98 × 0.8952 = 17.886096 → 17.89
totalผลรวม total ของทุกรายการ ปัด 2 ตำแหน่ง19.98
discountedTotalผลรวม discountedPrice ของทุกรายการ17.89
totalProductsจำนวนรายการ ใน products[]1
totalQuantityผลรวม quantity ของทุกรายการ2

จุดที่ต้องระวังที่สุดคือบรรทัดที่สอง: discountedPrice ปัดด้วย round2 เหมือน field ตัวเงินอื่น ๆ ทุกตัว ไม่มี field ไหนปัดเป็นจำนวนเต็มเป็นกรณีพิเศษ ค่าที่ถูกคือ 17.89 ไม่ใช่ 18 — เราออกแบบระบบเงินของเราเองให้สม่ำเสมอในทุก field ไม่ได้ลอกพฤติกรรมจากที่อื่นมา ถ้าใครเคยเห็นตัวอย่างที่ปัดเป็นจำนวนเต็มมาก่อน (จาก API อื่นที่เคยใช้) ต้องเปลี่ยนความเคยชินตรงนี้

ส่วน total ใช้การปัดสองตำแหน่งผ่าน helper round2 เพราะเลขทศนิยมแบบ floating point ทำให้การบวกราคาสะสมเพี้ยนได้ (เช่น 0.1 + 0.2 ได้ 0.30000000000000004) และ totalProducts นับจำนวนบรรทัด ไม่ใช่จำนวนชิ้น — สั่งสินค้าตัวเดียว 2 ชิ้นจะได้ totalProducts: 1 กับ totalQuantity: 2 — และ discountedPrice ก็เรียก round2 ตัวเดียวกันนี้ ไม่มี helper แยกสำหรับมันเอง

อ่านและเขียนในก้อนเดียวด้วย interactive transaction

การสร้างคำสั่งซื้อต้องทำสองอย่าง: อ่านราคาสินค้าจากตาราง Product แล้วเขียน Order พร้อมรายการลงไป ถ้าปล่อยสองอย่างนี้อยู่นอก transaction จะเกิดปัญหาสองแบบ — ราคาถูกแก้ระหว่างที่เราอ่านเสร็จแต่ยังไม่เขียน (ใบเสร็จได้ราคาผีที่ไม่มีอยู่จริงในช่วงเวลาใดเลย) และถ้าการเขียนพังกลางทางก็จะเหลือข้อมูลค้างครึ่ง ๆ

คำตอบคือ interactive transaction แบบเดียวกับบทที่ 29 ของคอร์ส NestJS Fundamentals: this.prisma.$transaction(async (tx) => { … }) ทุก query ข้างในต้องเรียกผ่าน tx ไม่ใช่ this.prisma ไม่งั้น query นั้นจะหลุดออกไปอยู่นอก transaction เงียบ ๆ

สิ่งที่ทำให้ pattern นี้สวยคือการจัดการ error: ถ้ามี id สินค้าที่ไม่มีจริง เรา throw new NotFoundException(...) ข้างใน callback ได้เลย Prisma จะ rollback ทุกอย่างให้อัตโนมัติเพราะ callback reject และ Nest จะแปลง exception ตัวนั้นเป็น response 404 ให้เอง เราจึงไม่ต้องเขียนโค้ดลบข้อมูลที่เพิ่งสร้างเลยแม้แต่บรรทัดเดียว

การเขียน Order กับ OrderItem ใช้ nested write (บทที่ 27 ของคอร์ส NestJS Fundamentals) คือ items: { create: items } ข้างใน tx.order.create() — Prisma ออก INSERT ให้ทั้งใบและทุกบรรทัดในคำสั่งเดียว โดยเติม orderId ให้เองหลังได้ id ของ Order ส่วน include: { items: { orderBy: { id: 'asc' } } } ทำให้ได้รายการกลับมาพร้อมกันในลำดับที่เขียนลงไป — ไม่ต้อง query ซ้ำ และ products[] ใน response เรียงตรงกับที่ client ส่งมา

เราอ่านสินค้าทั้งหมดด้วย findMany({ where: { id: { in: ids } } }) ครั้งเดียวแล้วทำ Map จาก id ไปหา product ไม่ใช่ loop findUnique ทีละตัว — ตะกร้า 10 รายการจึงเป็น 1 query ไม่ใช่ 10 query ส่วนการวน dto.products.map(...) ต่อจากนั้นทำให้ลำดับของ response ตรงกับลำดับที่ client ส่งมาเสมอ ไม่ใช่ลำดับที่ฐานข้อมูลคืนแถวมา

อีกเรื่องที่ตั้งใจไม่ทำ: เราไม่ลด stock ของสินค้า เพราะ React app อ่าน stock จาก GET /products/:id ใหม่ทุกครั้งที่เปิดหน้าสินค้า ถ้าเราลด stock ขึ้นมาเอง พฤติกรรมของแอปจะเปลี่ยนไปจากเดิมทันทีทั้งที่เราไม่ได้แก้ frontend — ขัดกับเป้าหมายของคอร์สนี้

mapper กันข้อมูลส่วนตัวหลุด

แถวที่ Prisma คืนมามีมากกว่าที่สัญญาอนุญาตให้ส่งออก: Order มี address, email, phone, createdAt ที่สัญญาของเรา (docs/api-spec.md) ไม่ได้กำหนดให้ส่งออกไป และ OrderItem มี id ของตัวเองซึ่งไม่ใช่ products[].id ที่ client ต้องการ — client ต้องการ productId เพราะมันใช้ค่านั้นลิงก์ไปหน้าสินค้า

เราจึงใช้ mapper แบบเดียวกับบทที่ 11 คือฟังก์ชันบริสุทธิ์ที่แปลงแถวเป็น response DTO ทีละ field อย่างชัดเจน ข้อดีคือ field ที่เพิ่มใน schema วันหลังจะไม่รั่วออก API เอง เพราะถ้าไม่เขียนไว้ใน mapper มันก็ไม่ถูกส่ง

ชื่อไฟล์และหน้าที่ด้านล่างมาจากโค้ดอ้างอิงของคอร์ส — Cursor อาจตั้งชื่อหรือแบ่งไฟล์ต่างออกไปได้ ขอแค่ไม่แตะไฟล์ที่ไม่เกี่ยวกับเป้าหมายและผ่านผลลัพธ์ที่ต้องได้ใน prompt

  • src/orders/dto/cart-response.dto.ts — สัญญา: ต้องมีแค่ชนิดข้อมูลของ response ตามสัญญา (CartProductResponseDto, CartResponseDto) · ต้องไม่มี decorator และไม่มี method
  • src/orders/cart.mapper.ts — สัญญา: ต้อง export toCartResponse() ที่ map products[].id จาก item.productId · ต้องไม่ส่ง address, email, phone, createdAt ออกไป และไม่แตะฐานข้อมูล
  • src/orders/orders.service.ts — สัญญา: ต้องทำทั้งการอ่านสินค้าและการเขียนคำสั่งซื้อใน $transaction เดียว, ต้อง throw NotFoundException ด้วยข้อความเดียวกับ ProductsService · ต้องไม่แก้ stock, ไม่ใช้ any, ไม่ใช้ as
  • ยังไม่มี controller และ module ในบทนี้ — service ตัวนี้จึงยังไม่ถูกเรียกจากที่ไหน จนถึงบทที่ 19

สั่ง Cursor เขียน OrdersService

commit งานก่อน แล้วเปิดแชทใหม่ใน Cursor โหมด Agent (git add -A && git commit -m "chore: before orders service") — prompt นี้ยาวที่สุดในคอร์ส เพราะมันต้องบอกทั้งสูตรคำนวณ ทั้งผลลัพธ์ที่ต้องได้เมื่อ transaction ล้ม และยกไฟล์ @src/products/products.service.ts กับ @src/products/product.mapper.ts เป็นแบบอย่างของสไตล์โปรเจกต์ ให้ AI ไม่ต้องเดา

ก่อนส่ง อ่านกติกาของคอร์สอีกครั้ง: AI พิมพ์แทนคุณได้ แต่คุณต้องอธิบายทุกบรรทัดได้ — ถ้าอธิบายไม่ได้ แปลว่ายังไม่ผ่านบทนี้

สร้าง OrdersService ที่บันทึกคำสั่งซื้อใน transaction และคืน cart ตามรูปทรงใน docs/api-spec.md ผลลัพธ์ที่ต้องได้: - มี service ที่รับ AddCartDto แล้วคืน receipt ตามรูปทรง "Order receipt" ใน docs/api-spec.md — สินค้า id 1 จำนวน 2 ชิ้นต้องได้ total 19.98, discountedPrice 17.89 (ไม่ใช่ 18), discountedTotal 17.89, totalProducts 1, totalQuantity 2 - total ของรายการ = price × quantity และ discountedPrice = total × (1 − discountPercentage / 100) สินค้าที่ไม่มีส่วนลดให้ถือว่าส่วนลดเป็น 0 (discountedPrice เท่ากับ total) - total ของ cart = ผลรวม total ทุกรายการ, discountedTotal = ผลรวม discountedPrice, totalProducts = จำนวนรายการ, totalQuantity = ผลรวม quantity - ตัวเลขเงินทุก field ปัดทศนิยม 2 ตำแหน่งเหมือนกันหมด ไม่มี field ไหนปัดเป็นจำนวนเต็ม - products[].id ใน receipt คือ id ของสินค้า (ไม่ใช่ id ของแถว OrderItem) และเรียงตามลำดับที่ client ส่งมา - สินค้าที่ไม่มีส่วนลด → ไม่มี key discountPercentage ในรายการนั้นเลย (ไม่ใช่ null) - receipt ไม่มี address, email, phone หรือ createdAt - ถ้ามี id สินค้าที่ไม่มีจริงแม้แต่ตัวเดียว → NotFoundException ข้อความ Product ${id} not found (ตรงตัวอักษรเหมือน GET /products/:id) และไม่มีแถว Order หรือ OrderItem ถูกบันทึกเลย (การอ่านสินค้าและการเขียนคำสั่งซื้อต้องอยู่ใน transaction เดียวกัน) - stock ของสินค้าไม่เปลี่ยน - npm run build และ npm run lint ผ่าน ขอบเขต: - ห้ามติดตั้ง dependency ใหม่ - ยังไม่ต้องสร้าง controller หรือ module

ตรวจโค้ดที่ AI สร้าง

  • การอ่านสินค้าและการเขียนคำสั่งซื้ออยู่ใน transaction เดียวกัน และทุก query ข้างในวิ่งผ่าน client ของ transaction นั้น — ไม่มี query ไหนหลุดออกไปใช้ this.prisma ตรง ๆ
  • ตัวอย่าง 9.99 × 2 ที่ 10.48% ให้ discountedPrice เป็น 17.89 ไม่ใช่ 18 และ field เงินทุกตัวปัด 2 ตำแหน่งด้วยกติกาเดียวกัน
  • ลำดับของ products[] ใน receipt ตรงกับลำดับที่ client ส่งมา ไม่ใช่ลำดับที่ฐานข้อมูลคืนแถว
  • ข้อความ 404 ตรงกับ ProductsService ทุกตัวอักษร: Product ${id} not found
  • address, email, phone ถูกบันทึกลงคอลัมน์ของ Order แยกกัน (ไม่ใช่เก็บ object ทั้งก้อนเป็น JSON)
  • products[].id ใน receipt คือ id ของสินค้า ไม่ใช่ id ของ OrderItem และ receipt ไม่มี address, email, phone, createdAt
  • สินค้าที่ไม่มีส่วนลดไม่มี key discountPercentage เลย (ไม่ใช่ null)
  • ไฟล์ที่เปลี่ยนอยู่ใน src/orders/ ทั้งหมด ไม่มีโค้ดแก้ stock ไม่มี any, as หรือ ! และ import ทุกตัวลงท้ายด้วย .js

AI มักพลาดตรงนี้: คำนวณ discountedPrice เป็นจำนวนเต็มด้วย Math.round(...) เฉย ๆ (ได้ 18 ทั้งที่สัญญาของเราต้องการ 17.89) เพราะเคยเห็นสไตล์การปัดแบบนี้จาก API ตัวอย่างอื่นมาก่อน ให้ตรวจว่าปัด 2 ตำแหน่งเหมือน field เงินตัวอื่นทุกตัว ไม่มีข้อยกเว้น อีกกรณีคือดึงสินค้าด้วย this.prisma.product.findMany ไว้ก่อน เปิด transaction แล้วค่อยเปิด transaction เพื่อ create — แบบนั้นการอ่านไม่ได้อยู่ใน snapshot เดียวกับการเขียน และถ้า throw 404 ก็ไม่มีอะไรต้อง rollback จริง (ดูเหมือนทำงานถูก แต่ผิดเจตนา) กรณีที่สามคือ mapper ส่ง item.id ออกไปเป็น products[].id ซึ่งจะทำให้ลิงก์ไปหน้าสินค้าของ React พาไปสินค้าผิดตัว

โค้ดอ้างอิงของบทนี้ — เป็นหนึ่งในวิธีที่ถูก ของคุณไม่จำเป็นต้องเหมือนทุกบรรทัด ขอแค่ผ่านผลลัพธ์ที่ต้องได้:

// src/orders/dto/cart-response.dto.ts
export class CartProductResponseDto {
  id: number;
  title: string;
  price: number;
  quantity: number;
  total: number;
  discountPercentage?: number;
  discountedPrice: number;
  thumbnail: string;
}

export class CartResponseDto {
  id: number;
  userId: number;
  products: CartProductResponseDto[];
  total: number;
  discountedTotal: number;
  totalProducts: number;
  totalQuantity: number;
}
// src/orders/cart.mapper.ts
import type { Order, OrderItem } from '../generated/prisma/client.js';
import { CartResponseDto } from './dto/cart-response.dto.js';

export type OrderWithItems = Order & { items: OrderItem[] };

export function toCartResponse(order: OrderWithItems): CartResponseDto {
  return {
    id: order.id,
    userId: order.userId,
    products: order.items.map((item) => ({
      id: item.productId,
      title: item.title,
      price: item.price,
      quantity: item.quantity,
      total: item.total,
      ...(item.discountPercentage !== null ? { discountPercentage: item.discountPercentage } : {}),
      discountedPrice: item.discountedPrice,
      thumbnail: item.thumbnail,
    })),
    total: order.total,
    discountedTotal: order.discountedTotal,
    totalProducts: order.totalProducts,
    totalQuantity: order.totalQuantity,
  };
}
// src/orders/orders.service.ts
import { Injectable, NotFoundException } from '@nestjs/common';
import { PrismaService } from '../prisma/prisma.service.js';
import { toCartResponse } from './cart.mapper.js';
import { AddCartDto } from './dto/add-cart.dto.js';
import { CartResponseDto } from './dto/cart-response.dto.js';

function round2(value: number): number {
  return Math.round(value * 100) / 100;
}

@Injectable()
export class OrdersService {
  constructor(private readonly prisma: PrismaService) {}

  async create(dto: AddCartDto): Promise<CartResponseDto> {
    const order = await this.prisma.$transaction(async (tx) => {
      const ids = dto.products.map((product) => product.id);
      const products = await tx.product.findMany({ where: { id: { in: ids } } });
      const productById = new Map(products.map((product) => [product.id, product]));

      const items = dto.products.map(({ id, quantity }) => {
        const product = productById.get(id);
        if (!product) {
          throw new NotFoundException(`Product ${id} not found`);
        }
        const total = round2(product.price * quantity);
        const discountedPrice = round2(total * (1 - (product.discountPercentage ?? 0) / 100));
        return {
          productId: product.id,
          title: product.title,
          thumbnail: product.thumbnail,
          price: product.price,
          discountPercentage: product.discountPercentage,
          quantity,
          total,
          discountedPrice,
        };
      });

      return tx.order.create({
        data: {
          userId: dto.userId,
          address: dto.address.address,
          email: dto.address.email,
          phone: dto.address.phone,
          total: round2(items.reduce((sum, item) => sum + item.total, 0)),
          discountedTotal: round2(items.reduce((sum, item) => sum + item.discountedPrice, 0)),
          totalProducts: items.length,
          totalQuantity: items.reduce((sum, item) => sum + item.quantity, 0),
          items: { create: items },
        },
        include: { items: { orderBy: { id: 'asc' } } },
      });
    });

    return toCartResponse(order);
  }
}

ผลลัพธ์ที่คาดหวัง

ได้ไฟล์ใหม่ใน src/orders/ (โค้ดอ้างอิงแบ่งเป็นสามไฟล์ ของคุณอาจต่างออกไปได้) และ npm run build กับ npm run lint ผ่านทั้งคู่โดยไม่มี error หรือ warning ยังไม่มี route ใหม่ใน log ของ dev server และยังไม่มีอะไรให้ curl เพราะ OrdersService ยังไม่ถูกลงทะเบียนใน module ไหน — ถ้า build ผ่านแต่ลืมสิ่งนี้ Nest จะไม่บ่นอะไรเลย มันแค่ไม่มีใครเรียก service ตัวนี้

type ที่ tx.order.create คืนมาต้องเข้ากับ OrderWithItems ได้เองโดยไม่ต้อง cast — ถ้า TypeScript บ่นตรงบรรทัดที่เรียก toCartResponse(order) ให้กลับไปดูว่า include: { items: … } หายไปหรือเปล่า นั่นคือกลไกที่ทำให้ include ที่หายไปกลายเป็น compile error ไม่ใช่บั๊กตอน runtime

ตรวจว่าใช้งานได้จริง

  • npm run build && npm run lint ผ่านทั้งสองคำสั่ง
  • grep -rn "this.prisma" src/orders/ — ทุกบรรทัดที่เจอต้องเป็นการเปิด transaction เท่านั้น ไม่มี query ใดเรียก this.prisma ตรง ๆ — ยืนยันว่าไม่มี query หลุดออกนอก transaction
  • grep -rn "stock\|: any\| as " src/orders/ ไม่เจออะไรเลย
  • คิดเลขตามด้วยมือใน node -e "console.log(Math.round(19.98 * (1 - 10.48 / 100) * 100) / 100)" ได้ 17.89 — เลขนี้คือ discountedPrice ที่ service ของคุณต้องคืน (จะยิงยืนยันจริงด้วย curl ในบทที่ 19)
  • git status ไม่มีไฟล์ที่ไม่เกี่ยวกับเป้าหมายถูกแก้ — ยังไม่มีการลงทะเบียน module ใน app.module.ts และโค้ดฝั่ง products ไม่ถูกแตะ
  • commit ผลงานของบทนี้: git add -A && git commit -m "feat: orders service"
