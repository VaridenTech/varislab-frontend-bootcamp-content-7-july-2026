Reviewing Accessibility

เลนส์แรกจบไปแล้ว — Header ตอนนี้ไม่มี scrollbar แนวนอนบนมือถืออีกต่อไป และมีทางเข้าเมนูผ่านปุ่ม hamburger แล้ว แต่เมนูข้างในยังเป็น <div> เปล่า ๆ อยู่ และทั้งไฟล์ยังไม่มี focus style ที่ไหนเลย บทนี้ใช้เลนส์ที่สองของ The Loop: accessibility เพื่อไล่จับ TODO ที่เหลืออีกสองข้อจากบทที่ 10 ให้จบ

ทำไม accessibility คือจุดที่โค้ด AI พังแบบเงียบที่สุด

สองเลนส์ก่อนหน้านี้ (responsive) ตรวจง่ายมาก — แค่ลากขนาดจอแล้วก็เห็นด้วยตาเลยว่าอะไรพัง แต่ accessibility ต่างออกไปโดยสิ้นเชิง โค้ดที่หน้าตาถูกทุกพิกเซล เปิดด้วยเมาส์แล้วใช้งานได้ปกติทุกอย่าง อาจใช้คีย์บอร์ดไม่ได้เลย หรือscreen reader อ่านแล้วไม่รู้เรื่อง โดยที่ไม่มีสัญญาณอะไรเตือนบนหน้าจอสักนิดเดียว — ต้องลองกดจริง ๆ ถึงจะรู้ นี่คือเหตุผลที่ Agent ที่ optimize เพื่อให้ "หน้าตาตรงกับ screenshot" มักพลาดเรื่องนี้แบบเงียบ ๆ เพราะ screenshot ไม่มีทางบอกได้เลยว่า element ไหนควรรับ keyboard focus ได้หรือไม่ได้

จับผิดข้อสอง-สาม: div ปลอมตัวเป็นลิงก์ กับไม่มี focus style ที่ไหนเลย

ทวนโค้ด nav จากบทที่แล้วอีกครั้ง

<div className="cursor-pointer text-gray-700 hover:text-primary">Home</div>
<div className="cursor-pointer text-gray-700 hover:text-primary">Products</div>

class cursor-pointer กับ hover:text-primary ทำให้ element นี้ดูเหมือนลิงก์ทุกอย่าง — เคอร์เซอร์เปลี่ยนเป็นรูปมือ สีเปลี่ยนตอน hover แต่มันคือ <div> เปล่า ๆ ไม่มี onClick ไม่มี href คลิกแล้วไม่มีอะไรเกิดขึ้นเลยตามที่บทที่ 10 เคยจดไว้ และที่แย่กว่านั้นคือ <div> ธรรมดาไม่อยู่ใน tab order ของเบราว์เซอร์เลย — กด Tab ไล่ทั้งหน้า โฟกัสจะข้าม Home กับ Products ไปเฉย ๆ เหมือนสอง element นี้ไม่มีอยู่จริง ผู้ใช้คีย์บอร์ดล้วนจึงไปหน้า Products ไม่ได้เลยไม่ว่าจะกดปุ่มไหน ทางแก้คือเปลี่ยนเป็น <Link> จริงจาก react-router ซึ่งเป็น element ที่รับ focus ได้เองตามธรรมชาติ ไม่ต้องเติมอะไรพิเศษ

ส่วนปัญหาที่สามคือทั้งไฟล์ไม่มี focus-visible ประกาศไว้เลยสักจุด — ทบทวนจากบทที่ 6: focus-visible: แสดงกรอบ focus เฉพาะตอนที่คาดว่าผู้ใช้กำลังนำทางด้วยคีย์บอร์ด รูปแบบมาตรฐานที่จะใช้ตลอดทั้งแอปคือ

focus-visible:outline-none focus-visible:ring-2 focus-visible:ring-primary/50

focus-visible:outline-none ปิด outline เริ่มต้นของเบราว์เซอร์ก่อน แล้ว focus-visible:ring-2 focus-visible:ring-primary/50 วาดกรอบวงแหวนสีของแบรนด์ขึ้นมาแทน — ต้องเติมไว้ที่ทุก element ที่รับ focus ได้ ไม่ใช่แค่บางจุด นี่คือ Header.tsx เวอร์ชันที่แก้ครบทั้งสอง TODO ที่เหลือแล้ว

// src/shared/components/Header/Header.tsx
import { useState } from "react";
import { Link } from "react-router";

export default function Header() {
  const [isMenuOpen, setIsMenuOpen] = useState(false);

  return (
    <header className="border-b border-gray-200 bg-white">
      <div className="mx-auto flex h-16 max-w-7xl items-center justify-between px-4 sm:px-6 lg:px-8">
        <Link
          to="/"
          className="rounded text-xl font-bold text-gray-900 focus-visible:outline-none focus-visible:ring-2 focus-visible:ring-primary/50"
        >
          My Store
        </Link>

        <nav className="hidden items-center gap-6 md:flex">
          <Link
            to="/"
            className="rounded text-gray-700 hover:text-primary focus-visible:outline-none focus-visible:ring-2 focus-visible:ring-primary/50"
          >
            Home
          </Link>
          <Link
            to="/categories"
            className="rounded text-gray-700 hover:text-primary focus-visible:outline-none focus-visible:ring-2 focus-visible:ring-primary/50"
          >
            Products
          </Link>
        </nav>

        <div className="flex items-center gap-4">
          <Link
            to="/cart"
            aria-label="ตะกร้าสินค้า มี 0 ชิ้น"
            className="relative rounded focus-visible:outline-none focus-visible:ring-2 focus-visible:ring-primary/50"
          >
            <svg className="h-6 w-6" viewBox="0 0 24 24" fill="none" stroke="currentColor" aria-hidden="true">
              <path d="M3 3h18l-2 12H5L3 3z" strokeWidth="2" />
            </svg>
            <span className="absolute -right-2 -top-2 flex h-4 w-4 items-center justify-center rounded-full bg-primary text-[10px] text-white">
              0
            </span>
          </Link>

          <button
            type="button"
            aria-expanded={isMenuOpen}
            aria-controls="mobile-nav"
            aria-label="เปิดเมนู"
            className="rounded focus-visible:outline-none focus-visible:ring-2 focus-visible:ring-primary/50 md:hidden"
            onClick={() => setIsMenuOpen((open) => !open)}
          >
            <svg className="h-6 w-6" viewBox="0 0 24 24" fill="none" stroke="currentColor" aria-hidden="true">
              <path d="M4 6h16M4 12h16M4 18h16" strokeWidth="2" />
            </svg>
          </button>
        </div>
      </div>

      {isMenuOpen && (
        <nav id="mobile-nav" className="flex flex-col gap-1 border-t border-gray-200 px-4 pb-4 md:hidden">
          <Link
            to="/"
            className="rounded py-2 text-gray-700 focus-visible:outline-none focus-visible:ring-2 focus-visible:ring-primary/50"
          >
            Home
          </Link>
          <Link
            to="/categories"
            className="rounded py-2 text-gray-700 focus-visible:outline-none focus-visible:ring-2 focus-visible:ring-primary/50"
          >
            Products
          </Link>
        </nav>
      )}
    </header>
  );
}

สามจุดที่เปลี่ยนไปจากเดิม: (1) <div> ทั้งสองใน nav กลายเป็น <Link> จริง ทั้งในเมนู desktop และแผงเมนูมือถือ (2) ทุก element ที่รับ focus ได้ — โลโก้, ลิงก์ nav ทั้งสอง, ไอคอนตะกร้า, ปุ่ม hamburger — มี focus-visible ครบ (3) ไอคอนตะกร้าที่แต่เดิมเป็นแค่ <div> ตกแต่งเฉย ๆ กลายเป็น <Link to="/cart"> พร้อม aria-label เพราะมันมีแค่ไอคอน SVG ไม่มีข้อความให้ screen reader อ่าน — เป็นปัญหารูปแบบเดียวกับ nav div ทุกประการ: หน้าตาสื่อว่ากดได้ แต่ไม่มี element ที่แท้จริงรองรับ จึงแก้ไปพร้อมกันในรอบนี้ ส่วน aria-hidden="true" บน SVG ไอคอนบอก screen reader ให้ข้ามรูปไอคอนไปเลย เพราะ aria-label บน element แม่พูดแทนความหมายไปหมดแล้ว ไม่ต้องอ่านซ้ำสอง

💡 route /categories และ /cart ยังไม่ถูกสร้างจริงในตอนนี้ — router.tsx ปัจจุบันมีแค่ path "/" ตามที่ทิ้งไว้ในบทที่ 10 คลิกลิงก์เหล่านี้ตอนนี้จะเจอ RouteErrorFallback ไปก่อน แต่นั่นไม่ใช่เหตุผลที่จะปล่อยให้ href ผิดหรือไม่มี href เลย ใส่ path ที่ถูกต้องไว้ตั้งแต่ตอนนี้ พอ route จริงถูกเพิ่มเข้ามาในบทที่ 16 และ 18 ลิงก์พวกนี้จะทำงานได้ทันทีโดยไม่ต้องแก้อะไรเพิ่มอีกเลย

Checklist: ตรวจ Accessibility (บทเรียน 12)

  • heading ไล่ระดับถูกต้อง — h1 เดียวต่อหน้า ไม่กระโดดข้ามระดับ (เช่น h2 ตามด้วย h4 ทันที)
  • landmark ครบ — header, nav, main, footer อยู่ในตำแหน่งที่ควรอยู่
  • alt ครบทุกรูป — รูปตกแต่งล้วน ๆ ที่ไม่มีความหมายให้ใช้ alt=""
  • ปุ่มที่มีแค่ไอคอนล้วนต้องมี aria-label อธิบายว่าปุ่มนี้ทำอะไร
  • ช่อง input ทุกช่องมี <label htmlFor> คู่กัน ไม่ใช่แค่ placeholder
  • interactive element เป็น <button> หรือ <a>/<Link> เท่านั้น ห้ามใช้ <div>/<span> ที่มี onClick
  • contrast (สัดส่วนความต่างสี) ผ่านเกณฑ์ — กับดักคลาสสิกคือ text-gray-400 บนพื้นขาว อ่านยากกว่าที่คิด
  • ทดลองกด Tab ไล่ให้ครบทุกหน้า ไม่ใช่แค่แตะเมาส์ดูเฉย ๆ
  • modal ต้อง trap focus ไว้ข้างในและปิดได้ด้วย Esc (ไลบรารี react-modal จัดการเรื่องนี้ให้อัตโนมัติ — จะได้ใช้จริงในบทที่ 17)

เครื่องมือ: Lighthouse และ axe DevTools

Checklist ด้านบนตรวจด้วยมือได้ทั้งหมด แต่มีเครื่องมือที่ช่วยหาจุดที่พลาดได้เร็วกว่า สองตัวที่ใช้บ่อยที่สุดคือ Lighthouse ที่มากับ Chrome DevTools อยู่แล้ว (แท็บ Lighthouse เลือกหมวด Accessibility แล้วกด Analyze page load) กับส่วนขยาย axe DevTools ที่ติดตั้งเพิ่มได้ฟรี ทั้งสองตัวสแกน DOM ที่ render จริงแล้วเทียบกับกฎ WCAG อัตโนมัติ

ลองรันที่หน้า Home ตอนนี้ (path "/" ที่ยังเป็นแค่ <div>Home (ว่างไว้ก่อน)</div> จากบทที่ 10) จะเจอ finding จริงทันที: หน้านี้ไม่มี heading ระดับ h1 อยู่เลยสักตัว — Header ไม่มี h1 (โลโก้เป็น Link ไม่ใช่ heading) และเนื้อหากลางหน้าก็เป็นแค่ข้อความเปล่า ๆ axe DevTools จะขึ้นเตือนในหมวด best practice ว่าหน้าควรมี heading ระดับ 1 finding นี้ไม่ใช่เรื่องน่าแปลกใจ เพราะหน้า Home ตัวจริงยังไม่ถูกสร้าง (รอบทที่ 14) แต่มันสาธิตให้เห็นว่าเครื่องมือพวกนี้ตรวจตาม DOM ที่ render จริงเท่านั้น ไม่สนใจว่าคุณ "ตั้งใจจะใส่ทีหลัง" — เก็บ finding นี้ไว้เป็นข้อเตือนใจของบทที่ 14 ด้วยว่าเมื่อสร้างหน้า Home จริง ต้องมี h1 อยู่ในนั้น

ให้ Agent self-audit: เพิ่มกติกาเข้า rules ไฟล์

Checklist ด้านบนมีประโยชน์มากขึ้นไปอีกถ้า Agent อ่านมันได้เองทุกครั้งที่สร้างหรือแก้โค้ด เปิด .cursor/rules/project.mdc ที่เขียนไว้ตั้งแต่บทที่ 9 แล้วเพิ่มกฎ accessibility เข้าไป

- ทุกรูปต้องมี alt (รูปตกแต่งล้วนใช้ alt="")
- ปุ่มที่มีแค่ไอคอนต้องมี aria-label
- interactive element เป็น <button> หรือ <a>/<Link> เท่านั้น ห้ามใช้ <div>/<span> ที่มี onClick
- ทุก element ที่รับ focus ได้ต้องมี focus-visible:outline-none focus-visible:ring-2 focus-visible:ring-primary/50
- แต่ละหน้ามี h1 เดียว และ heading ไล่ระดับไม่กระโดด

บรรทัดพวกนี้ทำให้กฎ accessibility ที่เพิ่งเรียนกลายเป็นสิ่งที่ Agent รู้ทุกแชทอัตโนมัติ เหมือนกับ mobile-first และ Tailwind-only ที่ตั้งไว้ตั้งแต่บทที่ 9 นอกจากนั้นยังสั่งให้ Agent ตรวจสอบงานตัวเองได้ด้วย prompt สั้น ๆ แบบนี้ หลังจากมันสร้างหรือแก้ component ใด ๆ เสร็จ

ตรวจ accessibility ของไฟล์นี้ตาม checklist ใน rules ให้ครบทุกข้อ ถ้าเจอจุดที่ไม่ผ่าน ให้แก้ให้เลย แล้วสรุปว่าแก้อะไรไปบ้าง

วางแนบไฟล์ที่ต้องการตรวจ Agent จะไล่เช็คทีละข้อในกฎแล้วรายงานกลับมา แต่อย่าเชื่อรายงานนั้นแบบไม่ตรวจซ้ำ — เครื่องมืออย่าง Lighthouse, axe และตัว Agent เองล้วนช่วยหาจุดที่พลาดได้เร็วกว่าคนไล่ดูเองทีละบรรทัด แต่ตัดสินว่าอะไรคือ "พอ" สำหรับผู้ใช้จริงยังคงเป็นหน้าที่ของคน ลองกด Tab ไล่ทั้งหน้าด้วยตัวเองอีกครั้งเสมอ ก่อนเชื่อว่าจบแล้วจริง ๆ

Header.tsx ตอนนี้ผ่านทั้งสองเลนส์แรกแล้ว — responsive จากบทที่ 11 และ accessibility จากบทนี้ แต่ลองเพ่งดู class string ในโค้ดด้านบนอีกรอบ: focus-visible:outline-none focus-visible:ring-2 focus-visible:ring-primary/50 ถูกพิมพ์ซ้ำอยู่ 7 รอบในไฟล์เดียว (โลโก้, ลิงก์ Home/Products บน desktop, ลิงก์ตะกร้า, ปุ่ม hamburger, ลิงก์ Home/Products บนแผงมือถือ) นี่คือกลิ่นที่เลนส์ที่สามจะจับ — บทหน้าไปตรวจ maintainability กัน
