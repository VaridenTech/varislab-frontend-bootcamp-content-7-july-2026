Maintainability & Refactoring

สองเลนส์แรกจบแล้ว — Header ใช้งานได้ดีทั้งบนมือถือและด้วยคีย์บอร์ด แต่บทที่แล้วปิดท้ายด้วยข้อสังเกตหนึ่งที่ยังไม่ได้แตะ: focus-visible:outline-none focus-visible:ring-2 focus-visible:ring-primary/50 ถูกพิมพ์ซ้ำอยู่ถึง 6 รอบในไฟล์เดียว นี่ไม่ใช่บั๊กที่ทำให้อะไรพัง หน้าตาและพฤติกรรมยังถูกต้องทุกอย่าง แต่มันคือกลิ่นของปัญหาคนละแบบ — เลนส์สุดท้ายของสัปดาห์นี้: maintainability ว่าด้วยโค้ดที่ "ใช้งานได้" วันนี้ จะยังแก้ง่ายอยู่ไหมในอีกสามเดือนข้างหน้า

กลิ่นของโค้ดที่ Agent สร้างสะสมไว้

Agent ทำงานเป็นครั้ง ๆ ไม่มีความจำข้ามแชท ทุกครั้งที่สั่งสร้างหน้าใหม่ มันเริ่มจากศูนย์ ไม่รู้ว่าเคยเขียนปุ่มหน้าตาแบบนี้ไว้ที่ไฟล์อื่นแล้ว ผลคือ pattern เดียวกันถูกพิมพ์ซ้ำหลายรอบ ทีละนิดทีละหน่อย จนกลายเป็นโค้ดที่ดูแลยากโดยไม่มีใครตั้งใจ ลองดูตัวอย่างจริงจากหน้าต่าง ๆ ที่เราจะสร้างในบทถัดไป — สมมุติว่า Agent สร้างปุ่ม "Add to Cart" แยกกันคนละไฟล์สามรอบ และปุ่ม "Place Order" อีกหนึ่งรอบ

// src/pages/Home.tsx — ปุ่ม Add to Cart ในการ์ดสินค้า
<button className="rounded-lg bg-primary px-4 py-2 font-medium text-white transition-colors hover:bg-primary-dark focus-visible:outline-none focus-visible:ring-2 focus-visible:ring-primary/50">
  Add to Cart
</button>

// src/pages/Category.tsx — ปุ่มเดียวกัน คัดลอกมาอีกไฟล์ เรียง class คนละลำดับ
<button className="rounded-lg bg-primary px-4 py-2 font-medium text-white hover:bg-primary-dark focus-visible:ring-2 focus-visible:ring-primary/50 focus-visible:outline-none">
  Add to Cart
</button>

// src/pages/Product.tsx — ปุ่มเดียวกันอีกรอบ คนละไฟล์ padding ขยับนิดหน่อย
<button className="rounded-lg bg-primary px-6 py-2 font-medium text-white hover:bg-primary-dark focus-visible:outline-none focus-visible:ring-2 focus-visible:ring-primary/50">
  Add to Cart
</button>

// src/features/checkout/components/CheckoutForm.tsx — ปุ่ม Place Order ที่ผูก state
<button
  className={`rounded-lg px-4 py-2 font-medium text-white transition-colors ${
    isSubmitting ? "cursor-not-allowed bg-gray-300" : "bg-primary hover:bg-primary-dark"
  }`}
>
  {isSubmitting ? "กำลังส่ง..." : "Place Order"}
</button>

// src/pages/Category.tsx — ปุ่ม Previous ของ pagination
<button className="w-[100px] rounded-lg border border-primary px-4 py-2 font-medium text-primary hover:bg-primary/10">
  Previous
</button>

สี่ปุ่มแรกหน้าตาเหมือนกันแทบทุกประการ — สีพื้น สีตัวหนังสือ ขนาดตัวอักษร มุมโค้ง แต่ class string ไม่ตรงกันเป๊ะสักคู่ (ลำดับ class สลับกัน padding ขยับนิดหน่อย) เพราะแต่ละไฟล์ถูกเขียนแยกกันคนละรอบ แก้สีแบรนด์ทีหนึ่งต้องไล่หาให้ครบ 4 ที่ ลืมที่ไหนที่หนึ่งก็เผลอทำให้ปุ่มหน้าตาไม่ตรงกันทั้งแอป ปุ่ม Place Order ยังมีปัญหาเพิ่มอีกชั้น — ตรรกะ disabled ถูกเขียนเป็น ternary ซ้อนอยู่ใน className โดยตรง ยิ่งเงื่อนไขเยอะขึ้น string นี้จะยิ่งอ่านยากขึ้นเรื่อย ๆ ส่วนปุ่ม Previous มี w-[100px] เป็นตัวเลข arbitrary ที่ไม่มีใครรู้ว่าทำไมต้อง 100 พิกเซลเป๊ะ — ตัวเลขแบบนี้มักโผล่มาโดย Agent เดาเอาจาก screenshot ไม่ได้มาจาก design system ที่ตั้งใจไว้

กติกา: เห็น class string ซ้ำ ≥ 2 ที่ = แยก component

บทที่ 6 เคยตั้งคำถามไว้ว่าทำไมไม่ใช้ @apply รวม class ยาว ๆ แล้วสรุปว่าคำตอบของ Tailwind ต่อการนำสไตล์กลับมาใช้ซ้ำไม่ใช่ CSS class ใหม่ แต่คือ React component นี่คือจุดที่เอาหลักการนั้นมาใช้จริง กติกาที่จำง่ายที่สุดคือ: เจอ class string หน้าตาเดียวกัน (หรือใกล้เคียงกันมาก) ตั้งแต่ 2 จุดขึ้นไป ให้แยกเป็น component ทันที ไม่ต้องรอให้ซ้ำถึง 5-6 จุดก่อน ยิ่งรอนาน ยิ่งมีจุดให้ไล่แก้ทีหลังมากขึ้น

สร้าง shared/components/Button/Button.tsx

ปุ่มทั้งสี่แบบด้านบนต่างกันแค่ "สไตล์กลุ่ม" — บางปุ่มพื้นทึบสีแบรนด์ (primary) บางปุ่มกรอบเปล่า (outline) และปุ่มบางแบบที่ยังไม่เจอในตัวอย่างนี้แต่จะเจอในบทหน้าคือปุ่มจาง ๆ ไม่มีพื้นหลัง (ghost) เขียน component เดียวที่รับ variant เป็น prop แล้วครอบคลุมทั้งสามแบบไปเลย

// src/shared/components/Button/Button.tsx
import { ButtonHTMLAttributes } from "react";

type Variant = "primary" | "outline" | "ghost";

const variantClasses: Record<Variant, string> = {
  primary: "bg-primary text-white hover:bg-primary-dark",
  outline: "border border-primary text-primary hover:bg-primary/10",
  ghost: "text-gray-600 hover:bg-gray-100",
};

interface ButtonProps extends ButtonHTMLAttributes<HTMLButtonElement> {
  variant?: Variant;
}

export default function Button({
  variant = "primary",
  className = "",
  ...rest
}: ButtonProps) {
  return (
    <button
      className={`inline-flex items-center justify-center rounded-lg px-4 py-2 font-medium transition-colors focus-visible:ring-2 focus-visible:ring-primary/50 focus-visible:outline-none disabled:pointer-events-none disabled:opacity-50 ${variantClasses[variant]} ${className}`}
      {...rest}
    />
  );
}

ไล่ทีละจุดที่น่าสังเกต: variantClasses เป็น object ธรรมดาที่ map ชื่อ variant ไปหา class ของมัน — วิธีนี้อ่านง่ายกว่า ternary ซ้อนกันหลายชั้นมาก เพราะเพิ่ม variant ใหม่แค่เพิ่ม key ใหม่เข้าไปในตาราง ไม่ต้องไล่แก้เงื่อนไข if/else ที่ไหนเลย ...rest รับ prop ที่เหลือทั้งหมดที่ <button> ปกติรับได้ (onClick, disabled, type ฯลฯ) แล้วกระจายลง element จริง ทำให้ Button ใช้แทน <button> ธรรมดาได้ทุกที่โดยไม่เสียความสามารถอะไรไป className = "" เป็น "ทางออกฉุกเฉิน" (escape hatch) เผื่อบางจุดต้องการเพิ่ม class พิเศษที่ variant ไม่ได้ครอบคลุมไว้ และสุดท้าย focus-visible:... กับ disabled:pointer-events-none disabled:opacity-50 ถูกเขียนไว้ครั้งเดียวในไฟล์นี้ ทุกปุ่มที่เรียกใช้ Button จะได้ focus ring และสไตล์ disabled ที่ถูกต้องโดยอัตโนมัติ ไม่ต้องมานั่งจำว่าต้องแปะ class ไหนอีกแล้ว

ใช้งานจริง: แทนที่ปุ่มที่ซ้ำให้เหลือจุดเดียว

เมื่อมี Button แล้ว โค้ดในตัวอย่างก่อนหน้าย่อลงเหลือแค่นี้

// src/pages/Home.tsx, src/pages/Category.tsx, src/pages/Product.tsx
<Button>Add to Cart</Button>

// src/features/checkout/components/CheckoutForm.tsx
<Button disabled={isSubmitting}>
  {isSubmitting ? "กำลังส่ง..." : "Place Order"}
</Button>

// src/pages/Category.tsx — pagination
<Button variant="outline">Previous</Button>

ternary ที่เคยซ้อนอยู่ใน className ของปุ่ม Place Order หายไปเลย เหลือแค่ disabled={isSubmitting} ตรง ๆ เพราะสไตล์ตอน disabled ถูกเขียนไว้ใน Button แล้วครั้งเดียว และปุ่ม Previous ไม่มี w-[100px] ติดมาด้วยอีกต่อไป เพราะความกว้างของปุ่มควรปล่อยให้ยืดตามเนื้อหาข้างในแทนการล็อกตัวเลขตายตัว

🔍 สังเกตว่าปุ่ม disabled หน้าตาเปลี่ยนไปเล็กน้อยจากเดิม — เดิมใช้ bg-gray-300 กับ cursor-not-allowed ตอนนี้ Button ใช้ disabled:opacity-50 แทน สีพื้นจึงจางลงแทนที่จะเปลี่ยนเป็นเทาไปเลย นี่คือตัวอย่างจริงของสิ่งที่ต้องเช็คด้วยตาหลัง refactor ทุกครั้ง — โครงสร้างโค้ดสะอาดขึ้นไม่ได้แปลว่า UI จะหน้าตาเหมือนเดิม 100% เสมอไป

Checklist: ตรวจ Maintainability (บทเรียน 13)

  • class string หน้าตาเดียวกันซ้ำตั้งแต่ 2 จุดขึ้นไป → แยกเป็น component
  • ตัวเลข arbitrary ([...]) ที่ไม่มีที่มาชัดเจน → เปลี่ยนเป็น design token หรือ scale ปกติของ Tailwind
  • ternary ซ้อนกันอยู่ใน className → เปลี่ยนเป็น variant map (object lookup แบบ Button ด้านบน)
  • component ไฟล์ไหนยาวเกินประมาณ 150 บรรทัด → พิจารณาแตกเป็นไฟล์ย่อย
  • ชื่อ component ที่ไม่สื่อความหมาย (Card2, NewSection) → ตั้งชื่อตาม domain จริงที่มันแทน
  • ทุกอย่างที่ต้อง import ข้าม feature (ใช้ร่วมกันมากกว่าหนึ่งฟีเจอร์) ต้องย้ายไปอยู่ใน shared/

สั่ง refactor ด้วย Agent

การไล่แทนที่ปุ่มซ้ำ ๆ หลายไฟล์เป็นงานที่ทำซ้ำ ๆ ตรงไปตรงมา เหมาะกับ Agent มาก แต่ต้องบอกให้ชัดว่า "แยก" หมายถึงอะไร ไม่ใช่แค่ "ทำให้สวยขึ้น" เฉย ๆ

แยกปุ่มที่ซ้ำใน Header, Footer, Home, Category, Product และ CheckoutForm ออกเป็น shared component เดียวที่ src/shared/components/Button/Button.tsx ตาม variant pattern (primary / outline / ghost) — ปุ่มพื้นสีแบรนด์ทึบใช้ primary, ปุ่มกรอบใช้ outline

หลังสร้าง Button แล้ว แทนที่ <button> เดิมทุกจุดที่ซ้ำด้วย <Button> ตัวใหม่ ส่ง prop ที่จำเป็น (onClick, disabled, type) ผ่านไปตามปกติ

ขอบเขต: ห้ามเปลี่ยนข้อความหรือ layout รอบ ๆ ปุ่ม แก้แค่ตัวปุ่มเท่านั้น

เหมือนทุกครั้งที่ผ่านมา อ่าน diff ก่อน accept เสมอ แต่รอบนี้มีอีกขั้นตอนที่สำคัญไม่แพ้กัน: เปิด dev server แล้วเทียบหน้าตาก่อน-หลัง refactor ด้วยตาจริง ๆ ที่ทุก breakpoint (390 / 768 / 1024 / 1440 จาก checklist บทที่ 11) เพราะเป้าหมายของการ refactor คือให้ โครงสร้างโค้ดดีขึ้นโดยที่ผู้ใช้ไม่เห็นความต่างเลย ถ้า UI เปลี่ยนไปแม้แต่นิดเดียวโดยไม่ได้ตั้งใจ (แบบปุ่ม disabled ในตัวอย่างด้านบน) ต้องจับให้ได้ก่อน commit เสมอ

ปิดท้ายบทที่ 5: สามเลนส์ครบแล้ว

ตอนนี้เรามี checklist ครบสามเลนส์แล้ว — responsive (บทที่ 11), accessibility (บทที่ 12), maintainability (บทนี้) — และมี Button component ตัวแรกที่จะใช้ซ้ำไปตลอดทั้งแอป ทุกหน้าที่เหลือของสัปดาห์นี้ ตั้งแต่บทที่ 14 เป็นต้นไป จะวน The Loop เต็มรูปแบบซ้ำ ๆ: 🎯 ตั้งเป้าหมาย → 📝 เขียน prompt → 🤖 ดู Agent สร้าง → 🔍 ตรวจทานผ่านสามเลนส์นี้ → 🔧 refactor จนสะอาด แล้ววนใหม่กับชิ้นถัดไป การตรวจทานสามเลนส์นี้จะไม่ใช่ขั้นตอนพิเศษที่ต้องนึกถึงอีกต่อไป แต่จะกลายเป็นนิสัยที่ทำโดยอัตโนมัติทุกครั้งที่ Agent ส่งโค้ดกลับมา — เริ่มจากหน้า Home ในบทถัดไป
