Responsive แบบ Mobile-first

Responsive Design

การ์ดสินค้าที่สร้างในบทที่แล้วหน้าตาดีบนจอกว้าง แต่ยังไม่รู้เรื่องขนาดจอเล็กเลย บทนี้จะสอนวิธีที่ Tailwind จัดการ responsive ซึ่งต่างจากที่หลายคนคุ้นเคยจาก media query ธรรมดาอยู่พอสมควร

หลักการ mobile-first

กฎข้อเดียวที่ต้องจำให้ขึ้นใจ: class ที่ไม่มี prefix จะมีผลกับทุกขนาดจอ ส่วน class ที่มี prefix เช่น md: จะมีผล ตั้งแต่ breakpoint นั้นขึ้นไป เท่านั้น ไม่ใช่แค่ตอนจอมีขนาดพอดีกับชื่อ breakpoint

🚨 กับดักที่พลาดกันบ่อยที่สุด: sm:flex ไม่ได้ แปลว่า “ใช้ flex เฉพาะตอนจอเล็ก” มันแปลว่า “ใช้ flex ตั้งแต่จอกว้าง 640px ขึ้นไปทั้งหมด” (รวมถึงจอ desktop ด้วย) ถ้าอยากให้มีผล เฉพาะ จอเล็กเท่านั้น ต้องเขียน class ฐาน (ไม่มี prefix) ไว้ก่อน แล้วใช้ prefix ที่ใหญ่กว่ามา “ยกเลิก” ทีหลัง เช่น flex md:hidden คือ “แสดงแบบ flex บนมือถือ แล้วซ่อนตั้งแต่ md ขึ้นไป”

ตาราง breakpoint ของ Tailwind

Prefix ความกว้างจอขั้นต่ำ
(ไม่มี prefix) 0px — ทุกขนาดจอ
sm: 640px ขึ้นไป
md: 768px ขึ้นไป
lg: 1024px ขึ้นไป
xl: 1280px ขึ้นไป
2xl: 1536px ขึ้นไป

ตัวอย่างจริงจากแอปต้นแบบ: บทเรียนที่ได้จากบั๊ก

ก่อนดูวิธีทำ responsive ที่ถูกต้อง ลองดูตัวอย่างที่ผิดพลาดจริงก่อน — จากแอปต้นแบบ My Store เอง

บนจอเดสก์ท็อปทุกอย่างดูปกติดี แต่พอย่อลงมาเป็นขนาดมือถือ แอปต้นแบบเองยังพลาดจุดนี้บนมือถือ — sidebar หมวดหมู่กับ grid สินค้าไม่ยอมเรียงต่อกันในแนวตั้ง (stack) แต่ยังพยายามอยู่เคียงข้างกันเหมือนบนจอกว้าง จนตัวหนังสือทับกันอ่านไม่ออก หน้า Category ก็มีปัญหาแบบเดียวกัน สาเหตุคือมีการล็อกเลย์เอาต์แบบ “เคียงข้างกัน” ไว้ตายตัว โดยไม่มี breakpoint คอยสลับกลับเป็นแนวตั้งเมื่อจอแคบลง

🚨 นี่ไม่ใช่ตัวอย่างที่ควรเลียนแบบ แต่เป็นเหตุผลว่าทำไมบทนี้ถึงสำคัญ — เวอร์ชัน Tailwind ที่คุณจะสร้างเองในสัปดาห์นี้ ต้องแก้ปัญหานี้ให้ถูกต้อง ด้วย mobile-first breakpoints ตั้งแต่แรก ไม่ใช่แก้ทีหลัง

รูปแบบที่ใช้บ่อย 3 แบบ

ต่อไปนี้คือรูปแบบ responsive ที่จะใช้ซ้ำแทบทุกหน้าของ My Store

1. Grid สินค้าที่ปรับจำนวนคอลัมน์ตามจอ

<div className="grid grid-cols-2 gap-4 md:grid-cols-3 lg:grid-cols-4">
  {/* การ์ดสินค้า */}
</div>

อ่านจากซ้ายไปขวา: มือถือ (ฐาน ไม่มี prefix) ได้ 2 คอลัมน์ พอจอกว้างขึ้นถึง md (แท็บเล็ต) ขยับเป็น 3 คอลัมน์ แล้วตั้งแต่ lg (เดสก์ท็อป) ขึ้นไปเป็น 4 คอลัมน์ — ไม่มีจุดไหนที่ grid หายไปเลยหรือคอลัมน์แคบจนอ่านไม่ออก

2. ซ่อนเมนูบนมือถือ

<nav className="hidden md:flex md:items-center md:gap-6">
  <a href="/categories">หมวดหมู่</a>
  <a href="/cart">ตะกร้า</a>
</nav>

hidden (ไม่มี prefix) ซ่อนเมนูนี้ไว้ก่อนบนทุกขนาดจอ แล้ว md:flex เปิดให้แสดงแบบแถวแนวนอนตั้งแต่จอ md ขึ้นไป ผลคือมือถือไม่เห็นเมนูนี้เลย ส่วนจอกว้างเห็นเป็นแถบเมนูปกติ — บนมือถือตอนนี้เราแค่ซ่อนไว้ก่อน ยังไม่ได้ทำปุ่ม hamburger เพื่อเปิดเมนูสำรอง เดี๋ยวบทที่ 11 ตอนตรวจทาน responsive ของโค้ดจาก AI เราจะกลับมาทำส่วนนี้ให้ครบ

3. คอนเทนเนอร์หน้าเว็บที่มี padding ขยับตามจอ

<div className="mx-auto max-w-7xl px-4 sm:px-6 lg:px-8">
  {/* เนื้อหาทั้งหน้า */}
</div>

รูปแบบนี้เจอแทบทุกหน้าของ My Store บนมือถือขอบซ้ายขวาแคบ (px-4) เพื่อไม่ให้เนื้อหาดูอึดอัด พอจอกว้างขึ้นถึง sm ขยับ padding เป็น px-6 และกว้างขึ้นอีกที่ lg เป็น px-8 — เนื้อหาจึงไม่ชิดขอบจอจนเกินไปไม่ว่าจอจะกว้างแค่ไหน ในขณะที่ max-w-7xl mx-auto ยังคงจำกัดความกว้างสูงสุดและจัดกึ่งกลางเหมือนที่เรียนไปในบทที่แล้ว

ทดสอบด้วย DevTools

เปิด DevTools ของเบราว์เซอร์แล้วสลับไปที่โหมด device toolbar (ไอคอนรูปมือถือ/แท็บเล็ต มุมซ้ายบนของแผง DevTools หรือกด Cmd+Shift+M บน Mac) จากนั้นลาก ลากช้า ๆ ปรับความกว้างหน้าจอจากแคบไปกว้าง แล้วสังเกตทีละ breakpoint ว่า layout สลับตอนไหน — นี่คือวิธีจับบั๊กแบบที่เห็นในภาพ home_mobile.png ก่อนที่จะ ship ออกไปจริง

กฎง่าย ๆ ที่ใช้ได้เสมอ

ออกแบบมือถือก่อน แล้วค่อยเติม prefix ขยับขึ้นไปหาจอที่ใหญ่กว่า อย่าออกแบบเดสก์ท็อปก่อนแล้วค่อยพยายามหา prefix มาบีบให้พอดีกับมือถือทีหลัง เพราะนั่นคือสาเหตุของบั๊กแบบที่เห็นในภาพ home_mobile.png พอดี — เลย์เอาต์เดสก์ท็อปถูกออกแบบไว้ก่อน แล้วไม่มีใครย้อนกลับมาคิดว่ามันควรจะพังยังไงตอนจอแคบ
