Real Data with TanStack Query

หน้า Home เสร็จแล้วด้วย mock data บทนี้ไม่มี screenshot ใหม่ให้ดู เพราะดีไซน์จะไม่เปลี่ยนแม้แต่พิกเซลเดียว — สิ่งที่เปลี่ยนคือข้อมูลข้างใต้เท่านั้น จาก MOCK_PRODUCTS ที่นอนอยู่เฉย ๆ ในไฟล์ ไปเป็นข้อมูลจริงที่ดึงจาก dummyjson แบบ real-time และบทนี้ก็ต่างจากบททั่วไปอีกอย่างหนึ่ง — งานส่วนใหญ่จะเขียนเอง ไม่ใช้ Agent ด้วยเหตุผลเดียวกับที่ตั้งโครงโปรเจกต์เองในบทที่ 9: การออกแบบ shape ของ API layer เป็นงาน deterministic ที่รู้คำตอบอยู่แล้ว ไม่ใช่งานสร้างสรรค์ที่ควรปล่อยให้ Agent เดา

dummyjson: API ปลอมที่ทำตัวเหมือนของจริง

dummyjson.com เป็น REST API สาธารณะที่สร้างไว้ให้ทดลองเชื่อมต่อโดยเฉพาะ ไม่ต้องสมัคร ไม่ต้องมี API key ส่งข้อมูลสินค้าจริง (ชื่อ, ราคา, รูป, รีวิว) กลับมาเป็น JSON เอนด์พอยต์ที่แอปนี้ใช้มีอยู่ห้าตัว

Endpoint คืนค่า
GET /products?limit&skip { products: Product[], total, skip, limit }
GET /products/categories Category[] — { slug, name, url }
GET /products/category/:slug?limit&skip โครงเดียวกับ /products
GET /products/:id Product
POST /carts/add จำลองการสั่งซื้อ คืน { id } (ใช้จริงบทที่ 19)

base URL ไม่ hardcode ไว้ในโค้ด แต่เก็บใน environment variable เพิ่มไฟล์ .env ที่ root ของโปรเจกต์

# .env
VITE_API_BASE_URL=https://dummyjson.com

💡 Vite เปิดเผยเฉพาะตัวแปรที่ขึ้นต้นด้วย VITE_ ให้โค้ดฝั่ง client อ่านได้ผ่าน import.meta.env — ตัวแปรอื่นที่ไม่มี prefix นี้จะถูกซ่อนไว้ ไม่ถูก bundle ไปกับโค้ดที่ส่งให้เบราว์เซอร์ ป้องกันความลับหลุดโดยไม่ตั้งใจ

Shared API Client: จุดเดียวที่คุยกับเซิร์ฟเวอร์

ก่อนเขียนฟังก์ชันเรียก endpoint ทีละตัว ต้องมี "ประตูทางเดียว" ที่ทุก request ผ่านก่อนเสมอ — เหตุผลคือ error จากเซิร์ฟเวอร์มาได้หลายรูปแบบ (timeout, 404, 500, network ล่ม) ถ้าปล่อยให้แต่ละ component ดัก error เองตามใจชอบ แต่ละที่จะจัดการไม่เหมือนกัน สร้าง apiClient ตัวเดียวที่ทุกฟังก์ชันเรียกผ่าน แล้วแปลง error ทุกแบบให้เป็นรูปทรงเดียวกันตั้งแต่จุดนี้

// src/shared/api/client.ts
import axios, { AxiosError } from "axios";

export class ApiError extends Error {
  readonly status?: number;

  constructor(message: string, status?: number) {
    super(message);
    this.name = "ApiError";
    this.status = status;
  }
}

export const apiClient = axios.create({
  baseURL: import.meta.env.VITE_API_BASE_URL,
});

apiClient.interceptors.response.use(
  (response) => response,
  (error: AxiosError<{ message?: string }>) =>
    Promise.reject(
      new ApiError(
        error.response?.data?.message ?? "Something went wrong. Please try again.",
        error.response?.status,
      ),
    ),
);

ApiError เป็น error class ของเราเอง — สืบทอดจาก Error มาตรฐานแต่เพิ่ม status (HTTP status code) เข้าไป ส่วน response interceptor คือฟังก์ชันที่ axios เรียกทุกครั้งหลังได้ response กลับมา ไม่ว่าจะจาก request ไหนก็ตาม ถ้าสำเร็จก็ปล่อยผ่าน ((response) => response) แต่ถ้า error เกิดขึ้น ไม่ว่าจะเป็น error รูปแบบไหนจากฝั่งเซิร์ฟเวอร์ ก็จะถูกจับแล้วห่อใหม่เป็น ApiError เสมอ ผลคือทุกจุดในแอปที่เรียก apiClient ไม่ว่าจะเป็น query ไหน รับประกันได้ว่า error ที่เจอจะมีรูปทรงเดียวกันเป๊ะ ไม่ต้องเขียน error handling ซ้ำที่ทุกจุดเรียก — นี่คือหลักการเดียวกับ Button ในบทที่ 13 แค่ย้ายจาก UI มาเป็น data layer

features/products/api.ts: ฟังก์ชันเรียก endpoint

ชั้นถัดไปคือฟังก์ชันธรรมดาที่ห่อ apiClient ไว้ ฟังก์ชันละหนึ่ง endpoint คืนค่าเป็น Promise ที่ type ตรงกับ interface ด้านบนเป๊ะ

// src/features/products/api.ts
import { apiClient } from "@/shared/api/client";
import { Category, FetchProductsResponse, Product } from "@/features/products/types";

export interface ProductListParams {
  page?: number;
  limit?: number;
}

export interface CategoryProductsParams extends ProductListParams {
  category: string;
}

export async function getProducts({
  page = 1,
  limit = 20,
}: ProductListParams = {}): Promise<FetchProductsResponse> {
  const { data } = await apiClient.get<FetchProductsResponse>("/products", {
    params: { skip: (page - 1) * limit, limit },
  });
  return data;
}

export async function getProductsByCategory({
  category,
  page = 1,
  limit = 20,
}: CategoryProductsParams): Promise<FetchProductsResponse> {
  const { data } = await apiClient.get<FetchProductsResponse>(
    `/products/category/${category}`,
    { params: { skip: (page - 1) * limit, limit } },
  );
  return data;
}

export async function getCategories(): Promise<Category[]> {
  const { data } = await apiClient.get<Category[]>("/products/categories");
  return data;
}

export async function getProduct(id: string | number): Promise<Product> {
  const { data } = await apiClient.get<Product>(`/products/${id}`);
  return data;
}

dummyjson ใช้ skip/limit แบบ offset ไม่ใช่เลขหน้าโดยตรง — หน้า UI ของเราคิดเป็น "หน้าที่เท่าไหร่" (page) แต่ API ต้องการ "ข้ามกี่ชิ้น" (skip) สูตรแปลงคือ skip = (page - 1) * limit: หน้า 1 ข้าม 0 ชิ้น, หน้า 2 ข้าม limit ชิ้นแรกไป ฯลฯ ตอนนี้เขียนสูตรนี้ตรง ๆ ไว้ในทั้งสองฟังก์ชันไปก่อน — บทที่ 16 จะกลับมาที่จุดนี้อีกครั้งตอนตรวจ maintainability

Query Factory: features/products/queries.ts

TanStack Query ต้องการ queryKey (ตัวระบุ cache) คู่กับ queryFn (ฟังก์ชันที่ไปดึงข้อมูล) ทุกครั้งที่เรียก useQuery ถ้าเขียนคู่นี้กระจายอยู่ทุก component ที่ต้องการข้อมูลสินค้า จะเจอปัญหาเดียวกับปุ่มซ้ำในบทที่ 13 — พิมพ์ผิดหนึ่งตัวใน queryKey แล้ว cache จะไม่ sync กันเงียบ ๆ โดยไม่มี error ใด ๆ เตือน ทางแก้คือรวมทุก query ของ feature นี้ไว้ในไฟล์เดียว เรียกว่า query factory

// src/features/products/queries.ts
import { keepPreviousData, queryOptions } from "@tanstack/react-query";
import {
  CategoryProductsParams,
  ProductListParams,
  getCategories,
  getProduct,
  getProducts,
  getProductsByCategory,
} from "./api";

export const productKeys = {
  all: ["products"] as const,
  lists: () => [...productKeys.all, "list"] as const,
  list: (params: ProductListParams) => [...productKeys.lists(), params] as const,
  byCategory: (params: CategoryProductsParams) =>
    [...productKeys.lists(), "category", params] as const,
  categories: () => [...productKeys.all, "categories"] as const,
  details: () => [...productKeys.all, "detail"] as const,
  detail: (id: string | number) => [...productKeys.details(), String(id)] as const,
};

export const productQueries = {
  list: (params: ProductListParams = {}) =>
    queryOptions({
      queryKey: productKeys.list(params),
      queryFn: () => getProducts(params),
    }),

  byCategory: (params: CategoryProductsParams) =>
    queryOptions({
      queryKey: productKeys.byCategory(params),
      queryFn: () => getProductsByCategory(params),
      placeholderData: keepPreviousData,
    }),

  categories: () =>
    queryOptions({
      queryKey: productKeys.categories(),
      queryFn: getCategories,
      staleTime: 5 * 60 * 1000,
    }),

  detail: (id: string | number) =>
    queryOptions({
      queryKey: productKeys.detail(id),
      queryFn: () => getProduct(id),
    }),
};

productKeys สร้าง key เป็น array ซ้อนกันเป็นลำดับชั้น (["products"] → ["products", "list"] → ["products", "list", { limit: 5 }]) ลำดับชั้นแบบนี้ทำให้ invalidate cache แบบกว้าง ๆ ได้ง่าย เช่นสั่ง invalidate ทุกอย่างที่ขึ้นต้นด้วย productKeys.all ก็เคลียร์ cache สินค้าทั้งหมดในทีเดียว productQueries ห่อ queryOptions ไว้ให้แต่ละ query พร้อมใช้ทันทีผ่าน useQuery(productQueries.list(...)) โดยไม่ต้องพิมพ์ queryKey/queryFn เองที่ component เลย สองตัวเลือกที่แปะเพิ่มเข้ามาคุ้มค่าที่จะสังเกต: staleTime: 5 * 60 * 1000 บน categories บอกว่าข้อมูลนี้ "ยังสดอยู่" ได้นานถึง 5 นาที ไม่ต้อง fetch ซ้ำทุกครั้งที่ component mount ใหม่ เพราะรายชื่อหมวดหมู่แทบไม่เปลี่ยนระหว่าง session ส่วน placeholderData: keepPreviousData บน byCategory บอกว่าเวลาเปลี่ยนพารามิเตอร์ (เปลี่ยนหมวดหรือเปลี่ยนหน้า) ให้โชว์ข้อมูลชุดเก่าค้างไว้ก่อนระหว่างรอข้อมูลใหม่ แทนที่จะเคลียร์จอเป็นค่าว่างแล้วโชว์ spinner กระพริบ — จะเห็นผลจริงตอนสร้าง pagination ในบทที่ 16

ต่อ Provider: QueryClientProvider

useQuery ทำงานได้ก็ต่อเมื่อทั้งแอปถูกห่อด้วย QueryClientProvider ก่อน สร้าง QueryClient ตัวเดียวที่ใช้ทั้งแอป

// src/app/queryClient.ts
import { QueryClient } from "@tanstack/react-query";

export const queryClient = new QueryClient({
  defaultOptions: {
    queries: {
      staleTime: 60 * 1000,
      retry: 1,
    },
  },
});

// src/app/providers.tsx
import { ReactNode } from "react";
import { QueryClientProvider } from "@tanstack/react-query";
import { queryClient } from "./queryClient";

export function AppProviders({ children }: { children: ReactNode }) {
  return <QueryClientProvider client={queryClient}>{children}</QueryClientProvider>;
}

💡 AppProviders ตั้งใจแยกไว้เป็นจุดเดียวที่รวม provider ทั้งหมดของแอป ตอนนี้มีแค่ TanStack Query แต่บทที่ 18 จะกลับมาเพิ่ม CartProvider เป็นอีกชั้นในไฟล์เดียวกันนี้ ไม่ต้องไปแก้ main.tsx ซ้ำอีกรอบ

แล้วห่อ RouterProvider ที่มีอยู่แล้วจากบทที่ 10 ด้วย AppProviders อีกชั้นใน main.tsx

รูปแบบการเช็คสามสถานะ (loading / error / success) ซ้ำเหมือนกันทั้งสาม section ของ Home — เขียนเป็น ternary ซ้อนสั้น ๆ ในแต่ละจุด isLoading ? <Skeleton /> : isError ? <ErrorMessage /> : <ProductGrid /> ก็เพียงพอสำหรับตอนนี้ เพราะทั้งสามจุดมี layout กริดที่ต่างกัน (จำนวนคอลัมน์ไม่เท่ากัน) การรวมเป็น component เดียวตอนนี้จะยิ่งซับซ้อนกว่าเดิม — จำกฎจากบทที่ 13 ไว้: รอให้เห็น pattern ซ้ำจริง ๆ ก่อนค่อยแยก ไม่ใช่แยกล่วงหน้าเผื่อไว้

ให้ Agent ช่วยตรงไหนในบทนี้

โครงของ api.ts และ queries.ts ทั้งหมดด้านบนควรออกแบบเองตาม pattern ที่ทีมตกลงกันไว้ ไม่ใช่ปล่อยให้ Agent เดาโครงสร้างเอง เพราะถ้าแชทสองแชทออกแบบ query factory ไม่เหมือนกัน โค้ดทั้งแอปจะไม่สอดคล้องกันทันที แต่มีงานหนึ่งในบทนี้ที่เหมาะกับ Agent มาก — งานแปล JSON response ให้เป็น TypeScript interface เป็นงาน mechanical ล้วน ๆ ไม่ต้องตัดสินใจเชิงสถาปัตยกรรมอะไรเลย เปิด https://dummyjson.com/products/1 ในเบราว์เซอร์ คัดลอก JSON ที่ได้ วางในแชทของ Agent แล้วสั่ง

เขียน TypeScript interface จาก JSON นี้

Agent จะไล่ทุก field ในตัวอย่างแล้วสร้าง interface ให้ครบทันที เร็วกว่าพิมพ์เองทีละบรรทัดมาก แต่ขั้นตอนที่ยังต้องเป็นคนตัดสินใจอยู่ดีคือเลือกว่า field ไหนแอปเราใช้จริง — interface เต็มที่ Agent สร้างจาก JSON จะมี field ที่เราไม่เคยใช้อีกสิบกว่าตัว หน้าที่ของคนคือตัดให้เหลือแค่ที่จำเป็น แบบที่ Product ด้านบนทำไว้ ไม่ใช่ copy ทุกอย่างที่ Agent เสนอมา

ข้อมูลจริงต่อครบทุกจุดของหน้า Home แล้ว หน้าตาเหมือนเดิมทุกประการ แต่ตอนนี้เชื่อมกับ dummyjson จริง ๆ บทหน้าเราจะใช้ productQueries กับ ProductCard ชุดเดียวกันนี้ซ้ำ สร้างหน้า Category ที่มีทั้งเมนูหมวดหมู่แบบเต็มและ pagination
