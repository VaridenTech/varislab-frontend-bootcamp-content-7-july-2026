แนวคิด Utility-First

Utility-First CSS

ก่อนเข้าโค้ดบรรทัดแรกของ Tailwind มาทวนก่อนว่าใน Week_04 คุณจัดสไตล์ component อย่างไร เพื่อให้เห็นชัดว่า Tailwind ต่างออกไปตรงไหน และทำไมความต่างนั้นถึงสำคัญ

ที่ผ่านมาเราจัดสไตล์กันแบบไหน

โปรเจกต์ Coffee Master ใน Week_04 ใช้ ไฟล์ CSS ไฟล์เดียว (style.css) import เข้ามาครั้งเดียวที่ main.tsx แล้วทุก component เรียกใช้ class ที่ตั้งชื่อไว้ในไฟล์นั้นผ่าน className เช่นปุ่ม +/- ปรับจำนวนสินค้าใน MenuCard.tsx

/* style.css */
.quantity-control button {
  width: 44px;
  height: 44px;
  border: none;
  border-radius: 999px;
  background: #fbbf24;
  color: #111827;
  font-size: 22px;
  font-weight: bold;
}

.quantity-control button:hover {
  background: #fcd34d;
}

// MenuCard.tsx
<div className="quantity-control">
  <button onClick={() => onDecrease(item.id)}>-</button>
  <span>{item.quantity}</span>
  <button onClick={() => onIncrease(item.id)}>+</button>
</div>

วิธีนี้ใช้งานได้ แต่มีต้นทุนที่มองข้ามง่าย สังเกตว่ากฎ CSS ข้างบนไม่ได้ผูกกับ <button> โดยตรง แต่ผูกกับ ตำแหน่งที่มันซ้อนอยู่ — เขียนว่า .quantity-control button ไม่ใช่ .quantity-btn ถ้าย้ายปุ่มนี้ไปวางไว้นอก .quantity-control สไตล์ทั้งหมดจะหายไปทันทีโดยไม่มี error เตือน และเพราะ style.css เป็นไฟล์เดียวที่ทุก component แชร์กัน ยิ่งโปรเจกต์โตขึ้น ไฟล์นี้ก็ยิ่งยาวขึ้นเรื่อย ๆ จนต้องเลื่อนหาว่ากฎไหนของ component ไหน และไม่มีอะไรป้องกันไม่ให้สอง component ตั้งชื่อ class ชนกันโดยไม่ได้ตั้งใจ

ปุ่มแบบเดียวกัน เขียนด้วย Tailwind

ลองดูอีกปุ่มหนึ่งที่เขียนด้วย Tailwind เพื่อเทียบแนวคิด

<button class="rounded-lg bg-blue-600 px-4 py-2 font-medium text-white hover:bg-blue-700">
  Add to Cart
</button>

ไม่มีไฟล์ style.css แยกต่างหาก ไม่มีการตั้งชื่อ class ใหม่ ไม่ต้องกังวลว่าปุ่มนี้จะไปชนกับ selector ของ component อื่น สไตล์ทั้งหมดอยู่ใน class ตรงนั้นเลย นี่คือแก่นของ utility-first

utility-first คืออะไรกันแน่

หลักการง่ายมาก: หนึ่ง class ทำหน้าที่แค่ CSS declaration เดียว — bg-blue-600 แปลว่า background-color: #2563eb เท่านั้น ไม่มีอย่างอื่นแอบซ่อนอยู่ ไม่เหมือน .quantity-control button ที่รวมทุกอย่างไว้ในกฎเดียว (width, height, สี, border-radius) เมื่อ class แต่ละตัวทำงานแค่อย่างเดียว คุณประกอบดีไซน์ขึ้นในตัว markup เอง โดยแปะ class เท่าที่ต้องการเรียงต่อกัน แทนที่จะไปนิยาม “สไตล์” เป็นชื่อไว้ล่วงหน้าในอีกไฟล์หนึ่ง

“แต่ HTML มันรกไม่ใช่เหรอ?”

นี่คือข้อโต้แย้งแรกที่ทุกคนที่เจอ Tailwind ครั้งแรกคิด และมันก็ไม่ผิด — class="rounded-lg bg-blue-600 px-4 py-2 font-medium text-white hover:bg-blue-700" ยาวกว่า className="quantity-control" จริง ๆ แต่ลองชั่งน้ำหนักข้อดีข้อเสียให้ครบ

  • Locality (สไตล์อยู่ที่เดียวกับ markup) — เห็นปุ่มก็เห็นสไตล์ของมันทันที ไม่ต้องเปิด style.css อีกไฟล์แล้วไล่หาว่ากฎไหนตรงกับ element นี้
  • ไม่มี naming fatigue — ไม่ต้องมานั่งคิดว่าจะตั้งชื่อ class ว่าอะไรดี .quantity-control, .qty-btn, .counter — Tailwind มีชื่อให้พร้อมอยู่แล้ว
  • ไม่มี dead CSS — ไฟล์ CSS ที่ทุก component แชร์กันสะสม class ที่ไม่มีใครใช้แล้วได้ง่าย เพราะลบ markup แล้วลืมลบกฎใน style.css ส่วน utility class ที่ไม่ได้ใช้ก็แค่ไม่ถูก generate ออกมา
  • Constraints ที่ช่วยคุณ — spacing และสีของ Tailwind มาเป็น scale ที่กำหนดไว้แล้ว (p-1, p-2, p-4…) ทำให้ทั้งแอปมีระยะห่างและสีที่สอดคล้องกันโดยอัตโนมัติ แทนที่จะมีคนเขียน padding: 13px มั่ว ๆ ที่ไหนสักแห่ง

ต้นทุนจริงของ utility-first คือ class string ที่ยาว เมื่อ component ซับซ้อนขึ้น แต่คำตอบของ Tailwind ต่อปัญหานี้ไม่ใช่การย้อนกลับไปตั้งชื่อ class เหมือนเดิม — คำตอบคือ extract เป็น React component เมื่อ <button class="..."> ถูกใช้ซ้ำหลายที่ ให้แยกมันเป็น <AddToCartButton /> ตัวเดียว แล้วเรียกใช้ซ้ำ — เราจะฝึกทำแบบนี้จริงในบทที่ 13

แล้วทำไมไม่ใช้ inline style ไปเลย

คำถามที่ตามมาคือ ถ้าจะเขียนสไตล์ติดกับ element เลย ทำไมไม่ใช้ style="..." ของ HTML ตรง ๆ ไปเลย เหตุผลคือ inline style ทำสามอย่างที่ Tailwind ทำได้ไม่ได้เลย

  • Responsive prefixes — md:flex บอกว่า “ใช้ flex ตั้งแต่จอขนาด md ขึ้นไป” style="" ไม่มีแนวคิดเรื่องขนาดจอ
  • States — hover:bg-blue-700 คือ CSS pseudo-class จริง ๆ ส่วน inline style ไม่รองรับ :hover, :focus, หรือ :disabled
  • Design tokens — bg-blue-600 ผูกกับค่าสีที่ประกาศไว้ที่เดียว เปลี่ยนทีเดียวเปลี่ยนทั้งแอป ส่วน inline style ต้องพิมพ์ #2563eb ซ้ำทุกจุดที่ใช้ — เดี๋ยวบทที่ 6 เราจะตั้ง token ของแบรนด์ My Store เอง

ทำไมเรื่องนี้สำคัญกับ workflow ที่ใช้ AI

ข้อดีอีกข้อของ utility-first ที่มักถูกมองข้ามคือมันเข้ากันได้ดีมากกับการทำงานร่วมกับ Agent เมื่อ Agent สร้าง component ให้หนึ่งไฟล์ สไตล์ทั้งหมดของมันอยู่ในไฟล์เดียวกัน ไม่กระจายไปอยู่ในไฟล์ CSS อีกไฟล์ที่คุณต้องเปิดดูคู่กัน ทำให้ diff ที่ Agent สร้างให้ในบทถัด ๆ ไป อ่านและตรวจทานได้ง่ายกว่ามาก — เห็นการเปลี่ยนแปลง markup และสไตล์พร้อมกันในหน้าจอเดียว
