Integration Testing

พื้นพร้อมแล้ว บทนี้เรามาเขียน Test ที่ยิงเข้า API ของเราจริง ๆ กัน แต่ก่อนอื่นขอคุยเรื่องประเภทของ Test สักหน่อย เพราะมันจะอธิบายว่าทำไมเราถึงเลือกเขียน Test แบบที่กำลังจะเขียน

Test มีกี่แบบ แล้วแต่ละแบบให้อะไรเรา

  • Unit Test — ทดสอบฟังก์ชันเดียวโดด ๆ เช่นเช็กว่า hashPassword คืนค่าที่ไม่ใช่รหัสผ่านดิบ เร็วมาก แต่ให้ความมั่นใจน้อย เพราะ Unit Test ไม่ได้ทดสอบ Business Logic มันทดสอบแค่ว่าชิ้นส่วนแต่ละชิ้นทำงานของตัวเองได้ ซึ่งชิ้นส่วนที่ผ่านหมดทุกตัวก็ยังประกอบกันแล้วพังได้อยู่ดี
  • Integration Test — ทดสอบหลายชิ้นส่วนที่ทำงานร่วมกัน สำหรับ API ก็คือยิง Request เข้าไปแล้วดูว่าได้ Status และ Body ตามที่คาดไว้ไหม ผ่านทั้ง Middleware, Validation, Auth, Controller และฐานข้อมูลจริง
  • End-to-End Test — ทดสอบทั้งระบบจากมุมผู้ใช้ ขับ Browser จริงให้คลิกและพิมพ์ ให้ความมั่นใจสูงสุดแต่ช้าที่สุด
  • Snapshot Test — เก็บภาพของ UI ไว้แล้วเทียบกับของเดิมว่าเปลี่ยนไปไหม เป็นเรื่องของฝั่งหน้าจอ ไม่เกี่ยวกับ API ของเรา

ประเด็นคือ โปรเจกต์ของเราไม่มี UI ไม่มีหน้าจอให้คลิก ดังนั้น Integration Test ก็คือ End-to-End Test ของเราไปในตัว เพราะมันเริ่มจากจุดเดียวกับที่ Client ตัวจริงจะเข้ามา คือ Request แล้วจบที่ Response

ถ้าคุณจะเขียน Test ได้แค่แบบเดียวในชีวิต สำหรับ API ให้เลือกแบบนี้ครับ มันให้ความมั่นใจต่อโค้ดหนึ่งบรรทัดที่เขียนสูงที่สุด แค่ไล่ทดสอบทุก Endpoint คุณก็ครอบคลุมทั้ง Route, Middleware และงานฐานข้อมูลไปพร้อมกันแล้ว

เขียน Test เพื่อความมั่นใจ ไม่ใช่เพื่อตัวเลข Coverage

หลายคนคิดถึงการเขียน Test เป็นเรื่องของ "ทำยังไงให้ครอบคลุมโค้ดครบ 100%" ซึ่งผมมองคนละมุม ผมเขียน Test เพื่อจะได้นอนหลับ เพื่อให้รู้ว่าของที่ปล่อยขึ้น Production ไปแล้วยังทำงานอย่างที่ตั้งใจไว้จริง ๆ

Coverage 100% ที่ยังตอบไม่ได้ว่าทำไมผู้ใช้ Login ไม่ได้นั้นไม่มีค่าอะไรเลย ในขณะที่ Test เพียงตัวเดียวที่ยืนยันว่า "สมัครสมาชิกแล้วรหัสผ่านไม่หลุดออกไปกับ Response" มีค่ามหาศาล ยิ่งถ้าโค้ดส่วนนั้นเกี่ยวกับเงิน ยิ่งต้องมี Test

SuperTest ยิง Request โดยไม่ต้องเปิด Server

เครื่องมือที่ทำให้เรื่องนี้เป็นจริงคือ SuperTest มันขับ Express App ของเราผ่านโค้ดได้เหมือนเป็น Client คนหนึ่ง โดยที่ไม่ต้องสั่ง listen เปิด Port จริง ๆ เลย ในสายตาของ Express มันคือ Request ที่วิ่งเข้ามาตามปกติ Middleware ทุกตัวทำงาน Controller ถูกเรียก และข้อมูลลงฐานข้อมูลจริง

นี่คือเหตุผลที่เราแยก src/server.ts ออกจาก src/index.ts ตั้งแต่บทที่ 3 — ไฟล์ที่ประกอบ App ไม่ได้สั่งเปิด Server เอง เราจึง Import app เข้ามาในไฟล์ Test ได้ตรง ๆ ตอนนั้นอาจดูเป็นการแยกไฟล์ที่ไม่จำเป็น วันนี้คือวันที่มันได้ใช้

ประโยชน์ที่ตามมาคือเราไม่ต้องยุ่งกับ Network เลย ซึ่งดีแล้ว เพราะเราไม่ได้ต้องการทดสอบว่าเน็ตเร็วแค่ไหน นั่นเป็นคำถามคนละข้อกัน

npm i -D supertest @types/supertest

โครงของไฟล์ tests/auth.test.ts

เริ่มจาก Endpoint ที่เรามีอยู่แล้วคือ Authentication สร้างไฟล์ tests/auth.test.ts

import request from 'supertest'
import app from '../src/server.ts'
import { createTestUser, cleanupDatabase } from './helpers/dbHelpers.ts'

describe('Authentication Endpoints', () => {
  afterEach(async () => {
    await cleanupDatabase()
  })

  describe('POST /api/auth/register', () => {
    // Test จะมาอยู่ตรงนี้
  })
})

describe คือกล่องจัดกลุ่ม ยังไม่ใช่ Test และซ้อนกันได้หลายชั้น ผมชอบให้ชั้นนอกเป็นชื่อกลุ่มของ Endpoint แล้วชั้นในเป็น Method บวก Path ที่กำลังทดสอบ พออ่าน Log ตอน Test พังจะได้รู้ทันทีว่าพังที่ไหน

afterEach ทำงานหลังจบ Test แต่ละตัว ไม่ใช่หลังแต่ละ expect นะครับ Test หนึ่งตัวมี expect ได้หลายบรรทัด เราเรียก cleanupDatabase ตรงนี้เพื่อให้ Test ตัวถัดไปเริ่มจากฐานข้อมูลว่างเปล่าเสมอ

ทดสอบการสมัครสมาชิก

ใส่ Test ตัวแรกลงไปในกล่อง POST /api/auth/register

it('should register a new user with valid data', async () => {
  const userData = {
    email: `test-${Date.now()}@example.com`,
    username: `testuser-${Date.now()}`,
    password: 'adminpassword1234',
    firstName: 'Test',
    lastName: 'User',
  }

  const response = await request(app)
    .post('/api/auth/register')
    .send(userData)
    .expect(201)

  expect(response.body).toHaveProperty('message')
  expect(response.body).toHaveProperty('user')
  expect(response.body).toHaveProperty('token')
  expect(response.body.user).not.toHaveProperty('password')
})

ชื่อ Test คือเอกสาร อ่านว่า "ควรสมัครสมาชิกใหม่ได้เมื่อส่งข้อมูลที่ถูกต้อง" แล้วโค้ดข้างในก็ทำตามนั้นเป๊ะ ๆ จะใช้ it หรือ test ก็ได้ทั้งคู่ ทำงานเหมือนกันทุกอย่าง ต่างกันแค่ว่า it ถูกออกแบบมาให้อ่านต่อกับคำว่า should ได้ลื่นกว่า ส่วน test อ่านเป็นประโยคบอกเล่า เลือกแบบที่คุณชอบแล้วใช้ให้เหมือนกันทั้งโปรเจกต์

ลูกโซ่ของ SuperTest — request(app) คือหยิบ App ของเรามา ตามด้วย .post(path) คือ Method และ Route ที่จะยิง .send(body) คือ Body ที่ส่งไป และ .expect(201) คือ Assertion ตัวแรกที่เช็ก Status Code ให้เลยในตัว ถ้าไม่ตรง Test พังทันที

Assertion ที่เหลือ เราตรวจว่ามี user และ token กลับมาครบตามที่ Controller ในบทที่ 21 สัญญาไว้ สังเกตว่าเราตรวจแค่ว่า มี Field message โดยไม่ตรวจข้อความข้างใน เพราะข้อความพวกนี้เปลี่ยนบ่อยและการไล่แก้ Test ทุกครั้งที่แก้คำไม่คุ้มค่าเลย

บรรทัดสุดท้ายคือบรรทัดที่ผมชอบที่สุด expect(response.body.user).not.toHaveProperty('password') — ตราบใดที่ Test ตัวนี้ยังเขียวอยู่ ไม่มีทางที่รหัสผ่านจะหลุดออกไปกับ Response ได้เลย นี่คือความมั่นใจที่จับต้องได้จริง

ทดสอบ Edge Case ด้วย

Happy Path อย่างเดียวไม่พอ ทุกจุดที่ Route มีเงื่อนไข มีการตัดจบ หรือมีโอกาสโยน Error ควรมี Test ของมันเอง

it('should return 400 when password is missing', async () => {
  const userData = {
    email: `test-${Date.now()}@example.com`,
    username: `testuser-${Date.now()}`,
  }

  const response = await request(app)
    .post('/api/auth/register')
    .send(userData)
    .expect(400)

  expect(response.body).toHaveProperty('error', 'Validation failed')
  expect(response.body.details[0].field).toBe('password')
})

Test ตัวนี้ไปไม่ถึง Controller ด้วยซ้ำ มันถูก validateBody จากบทที่ 12 สกัดไว้ก่อน ซึ่งนั่นแหละคือสิ่งที่เรากำลังยืนยัน ว่า Middleware ยังยืนอยู่ในลำดับที่ถูกต้องและตอบด้วยรูปแบบ { error, details } ที่ตกลงกันไว้

ที่น่าสนใจกว่านั้นคือ Edge Case ที่ Test แบบนี้จะไม่จับให้ ลองเปลี่ยนไปส่ง email: 'invalid-email' ที่ครบทุก Field ดูสิครับ คุณจะได้ 201 พร้อม User ที่ถูกสร้างจริง ไม่ใช่ 400 อย่างที่หลายคนเดา เพราะ insertUserSchema ที่เราเสียบไว้หน้า Route ในบทที่ 22 ถูกสร้างจากตาราง users มันจึงรู้แค่สิ่งที่ Database รู้ คือชนิดข้อมูล ความยาว และ Not Null ตามที่บทนั้นบอกไว้ตรง ๆ ว่ามันตรวจไม่ได้ว่า Email มี @ จริงหรือเปล่า

นี่คือคุณค่าอีกอย่างของ Integration Test — มันบอกคุณว่า Validation ของคุณกันอะไรได้จริง ไม่ใช่สิ่งที่คุณคิดว่ามันกันอยู่ ถ้าอยากให้ Email ถูกตรวจจริง ๆ ก็ .extend() Schema ตัวนั้นเพิ่มด้วย z.email() เสียก่อน แล้วค่อยกลับมาเขียน Test ยืนยันว่ามันได้ 400 ลำดับต้องเป็นแบบนี้เสมอ

ทดสอบการเข้าสู่ระบบ

คราวนี้ต่างออกไปนิดหนึ่ง เพราะก่อนจะ Login ได้ต้องมี User อยู่ในฐานข้อมูลก่อน ซึ่งคือจังหวะที่ Helper จากบทที่แล้วได้ใช้งาน

describe('POST /api/auth/login', () => {
  it('should log in with valid credentials', async () => {
    const testUser = await createTestUser()

    const credentials = {
      email: testUser.user.email,
      password: testUser.rawPassword,
    }

    const response = await request(app)
      .post('/api/auth/login')
      .send(credentials)
      .expect(200)

    expect(response.body).toHaveProperty('message')
    expect(response.body).toHaveProperty('user')
    expect(response.body).toHaveProperty('token')
    expect(response.body.user).not.toHaveProperty('password')
  })
})

rawPassword คือกุญแจของ Test นี้ ในฐานข้อมูลมีแต่รหัสผ่านที่ Hash แล้ว แต่ Client ตัวจริงย่อมส่งรหัสผ่านดิบขึ้นมา Helper ของเราจึงคืนค่าตัวนี้ออกมาให้ใช้พอดี

ระวังเรื่อง Status Code ให้ดีครับ Login ของเราตอบ 200 ไม่ใช่ 201 เพราะเราไม่ได้สร้างอะไรใหม่ในฐานข้อมูล ตอนสอนสด ๆ ผู้สอนเผลอเขียน .expect(201) แล้ว Test พังทันทีพร้อมข้อความว่า expected 201 got 200 ซึ่งก็คือ Test ทำงานถูกต้องแล้ว อีกเรื่องที่ควรจำคือถ้า Controller เรียก res.json() เฉย ๆ โดยไม่ได้ระบุ status Express จะตอบ 200 ให้เองเสมอ Test ต้องเขียนตามสิ่งที่ Route ตอบจริง

Route ที่ต้อง Login ก่อน

Endpoint ส่วนใหญ่ของเราถูกล็อกด้วย authenticateToken ไว้ตั้งแต่บทที่ 24 แต่การทดสอบมันแทบไม่ต่างจากเดิมเลย เพิ่มแค่ Header เดียว เหมือนกับที่เราเคยแปะ Token เองใน Postman

it('should create a new habit', async () => {
  const { token } = await createTestUser()

  const response = await request(app)
    .post('/api/habits')
    .set('Authorization', `Bearer ${token}`)
    .send({
      name: 'Exercise daily',
      description: 'Daily exercise routine',
      frequency: 'daily',
      targetCount: 1,
    })
    .expect(201)

  expect(response.body.habit).toBeDefined()
  expect(response.body.habit.name).toBe('Exercise daily')
})

เพราะ createTestUser คืน Token ที่เซ็นไว้เรียบร้อยมาให้ด้วย เราจึงไม่ต้องยิง Login ก่อนทุกครั้ง และอย่าลืมทดสอบด้านกลับด้วยว่า ยิงโดยไม่แนบ Token แล้วต้องได้ 401 เพราะนั่นคือหลักฐานว่าประตูล็อกอยู่จริง

แนวปฏิบัติที่ควรถือไว้

  • ทดสอบพฤติกรรม ไม่ใช่วิธีการ — อย่าไปสอดส่องว่า bcrypt.hash ถูกเรียกหรือยัง นั่นคือรายละเอียดการทำงานภายในที่เปลี่ยนเมื่อไรก็ได้ สิ่งที่ควรทดสอบคือ "Login ด้วยรหัสผ่านผิดแล้วต้องเข้าไม่ได้"
  • Test ต้องเป็นอิสระต่อกัน — ทุกตัวเริ่มจากสถานะสะอาดและเก็บกวาดของตัวเองเมื่อจบ ห้ามมี Test ที่ทำงานได้ก็ต่อเมื่อ Test ตัวก่อนหน้ารันไปแล้ว
  • ตั้งชื่อให้บอกทุกอย่าง — 'habits endpoint' ไม่ได้บอกอะไรเลย ส่วน 'GET /api/habits returns only habits for authenticated user' บอกครบทั้ง Method, Route และสิ่งที่คาดหวัง
  • Mock บริการภายนอกทิ้งไป — ถ้า Endpoint ไปคุยกับ API ของเจ้าอื่น เราไม่มีหน้าที่ทดสอบระบบของเขา เขามีทีมทดสอบของเขาอยู่แล้ว และการยิงจริงทุกครั้งที่รัน Test ทั้งช้าและอาจมีค่าใช้จ่าย
  • ทดสอบทุกทางแยกใน Route เดียว — เจอ if เจอการตัดจบ เจอจุดที่โยน Error ก็เขียน Test ให้มันสักตัว Route หนึ่งอันอาจต้องมี Test สี่ห้าตัว และนั่นคือเรื่องปกติ
  • Side Effect อยู่นอกขอบเขตของ Test แบบนี้ — งานที่ยิงทิ้งไว้แล้วไม่ได้รอผล เช่นส่งอีเมลแจ้งเตือน จะไม่ถูกครอบคลุมโดย Test ที่ดูแค่ Response เพราะถ้าเรารอผลของมัน มันก็ไม่ใช่ Side Effect ตั้งแต่แรก อย่างมากที่ทำได้คือตรวจว่ามันถูกเรียกจริงหรือไม่
  • ระวัง Race Condition — ถ้า Test สองตัวแตะข้อมูลชุดเดียวกันพร้อมกัน ผลจะไม่เหมือนเดิมทุกรอบ เราจึงสั่งให้ Vitest รันทีละตัวไว้ตั้งแต่บทที่แล้ว

Test ของ Endpoint อื่น ๆ ที่เหลือก็หน้าตาแบบนี้ทั้งหมด คำถามมีอยู่แค่สามข้อเสมอ — ยิง Route ไหน ส่งอะไรขึ้นไป และคาดว่าจะได้อะไรกลับมา ลองเขียนต่อให้ครบทั้ง GET, PATCH และ DELETE ของ Habit ดูครับ

ตอนนี้ API ของเราครบทุกอย่างแล้ว ทั้งโค้ดและ Test ที่คอยเฝ้าให้ เหลืออย่างเดียวคือเอามันออกไปให้คนอื่นใช้ได้จริง บทหน้าเรา Deploy กัน
