Error Handling ใน Express

ที่ผ่านมาเราจัดการ Error กันมาพอสมควรแล้ว ทุก Controller และทุก Middleware ที่เราเขียนมี try/catch ห่อไว้หมด ซึ่งถือว่ารับผิดชอบดี

แต่วันที่คุณอยากจัดรูปแบบ Error ให้เหมือนกันทั้งระบบ อยากส่ง Error ไปเก็บที่บริการภายนอก หรืออยากให้มีคนโดนแจ้งเตือนเมื่อ Server มีปัญหา คุณคงไม่อยากไปไล่แก้ทีละไฟล์ งานแบบนี้ควรอยู่ที่เดียว เหมือนกับที่เราจับการตรวจ Token มารวมไว้ที่ Middleware ตัวเดียวในบทที่ 24

ข่าวดีคือ Express มีของสิ่งนี้ให้อยู่แล้ว และมันก็คือ Middleware นั่นแหละ แค่พิเศษกว่านิดหน่อย

Error Handler คือ Middleware ที่มีสี่อาร์กิวเมนต์

ความต่างมีอยู่ข้อเดียวเท่านั้น

// Middleware ธรรมดา — สามอาร์กิวเมนต์
const regular = (req: Request, res: Response, next: NextFunction) => {
  next()
}

// Error Handler — สี่อาร์กิวเมนต์ และตัวแรกคือ Error เสมอ
const errorHandler = (
  err: Error,
  req: Request,
  res: Response,
  next: NextFunction
) => {
  // จัดการ Error
}

Express ดูจากจำนวนอาร์กิวเมนต์ล้วน ๆ เพื่อตัดสินว่าฟังก์ชันที่คุณลงทะเบียนไว้เป็น Error Handler หรือไม่ ศัพท์ของเรื่องนี้เรียกว่า Arity ของฟังก์ชัน ผลที่ตามมาคือคุณต้องใส่ครบทั้งสี่ตัวเสมอ ถึงจะไม่ได้ใช้ next เลยก็ตาม ถ้าใส่แค่สาม Express จะมองว่ามันเป็น Middleware ธรรมดาแล้วมันจะไม่มีวันถูกเรียก

พูดตามตรง ถ้าเป็นวันนี้ผมคงไม่ออกแบบแบบนี้ มันเป็นความมหัศจรรย์ประเภทที่ทำให้คนอ่านโค้ดงงว่าทำไม แทนที่จะให้ลงทะเบียน Error Handler ด้วยวิธีที่บอกเจตนาตรง ๆ ไปเลย แต่นี่คือมรดกจากยุคนั้นที่เรายังต้องอยู่กับมัน

อีกอย่างที่ควรรู้คือ Error Handler วางได้หลายระดับเหมือน Middleware ทั่วไป ทั้งระดับ Route ระดับ Router และระดับ App ส่วนระดับที่สี่คือระดับโค้ดซึ่ง try/catch ทำหน้าที่นั้นอยู่แล้ว

Error เดินทางไปหามันได้อย่างไร

วิธีที่ชัดเจนที่สุดคือ เรียก next() พร้อมส่ง Error เข้าไป ตามที่เราเจอกันมาตั้งแต่บทที่ 10

next(new Error('อะไรบางอย่างพัง'))

ทันทีที่ทำแบบนี้ ทุกอย่างที่เหลือจะถูกข้ามหมด ไม่มี Middleware ตัวไหนได้ทำงาน ไม่มี Route ไหนถูกเรียก มันจะกระโดดไปหา Error Handler ตัวที่ใกล้ที่สุดทันที และถ้าคุณมี Error Handler หลายตัวลงทะเบียนไว้คนละที่ ตัวที่รับไปก็ยังเรียก next(err) ส่งต่อให้ตัวถัดไปได้อีก

ใน Express 5 ยังมีอีกสองทางที่ Error จะไปถึงมันได้เองโดยเราไม่ต้องเรียก next() ตามที่เราเรียนไว้ในบทที่ 13

  • โยน Error แบบ Synchronous ใน Handler — Express เรียก Handler ของเราอยู่ใน try/catch ของมันเองอยู่แล้ว จึงรับไปส่งต่อให้ Error Handler ได้
  • Promise ที่ Reject จากฟังก์ชัน Async — Express 5 await ผลลัพธ์ของ Handler และ Middleware ให้ ถ้ามัน Reject ก็เท่ากับเราเรียก next(err) เอง

ข้อหลังนี่แหละคือสิ่งที่ Express 4 ทำไม่ได้ และเป็นที่มาของรูปแบบ asyncHandler ที่เราคุยกันในบทที่ 13 ถ้าคุณไปอ่านบทความเก่า ๆ ที่บอกว่า "โยน Error ใน Middleware แล้ว Server จะตาย" ให้รู้ไว้ว่านั่นคือกติกาของ Express 4 ซึ่งยังจริงอยู่สำหรับโค้ดเก่าที่ยังไม่อัปเกรด

แต่มีข้อยกเว้นที่ยังต้องระวังคือ Error ที่เกิดนอกช่วงที่ Express ควบคุมอยู่ เช่น Promise ที่คุณยิงทิ้งไว้เฉย ๆ โดยไม่ await หรือ Callback ใน setTimeout พวกนี้ Express ไม่มีทางเห็น

แล้วควรเรียก next() ใน Controller ไหม

ในทางเทคนิคทำได้ แต่ผมมีความเห็นเรื่องนี้ — การเรียก next(err) ใน Controller เท่ากับตั้งสมมติฐานว่า Controller ตัวนี้จะถูกลงทะเบียนไว้ในที่ที่มี Error Handler รออยู่ข้างใต้เสมอ เพราะ Controller คือปลายทาง ถ้ามันเรียก next แล้วไม่มี Error Handler อยู่ ก็ไม่มีอะไรมารับช่วงต่อ

มันเหมือนเวลาเราเขียน Component ใน React แล้วใส่สมมติฐานลงไปว่า Component แม่จะต้องหน้าตาแบบนั้นแบบนี้ เช่นพวก TableRow ที่ทำงานได้ก็ต่อเมื่ออยู่ใน Table เท่านั้น พอทำแบบนั้นแล้ว Component นั้นก็ยกไปวางที่อื่นไม่ได้อีก Controller ก็เหมือนกัน — ยืดหยุ่นน้อยลง แต่บางทีมันก็ไม่จำเป็นต้องยืดหยุ่นตั้งแต่แรกอยู่แล้ว คุณแค่ต้องรู้ตัวว่ากำลังแลกอะไรไป

ส่วนใน Middleware นั้นคนละเรื่อง คุณต้องเรียก next อยู่แล้ว ไม่งั้น Request จะค้าง

สร้าง errorHandler.ts

สร้างไฟล์ src/middleware/errorHandler.ts

import type { NextFunction, Request, Response } from 'express'
import { env } from '../../env.ts'

export class APIError extends Error {
  status: number
  name: string
  message: string

  constructor(message: string, name: string, status: number) {
    super()
    this.message = message
    this.name = name
    this.status = status
  }
}

export const errorHandler = (
  err: APIError,
  req: Request,
  res: Response,
  next: NextFunction
) => {
  console.log(err.stack)

  let status = err.status || 500
  let message = err.message || 'Internal Server Error'

  if (err.name === 'ValidationError') {
    status = 400
    message = 'Validation Error'
  }

  if (err.name === 'UnauthorizedError') {
    status = 401
    message = 'Unauthorized'
  }

  return res.status(status).json({
    error: message,
    ...(env.APP_STAGE === 'dev' && {
      stack: err.stack,
      details: err.message,
    }),
  })
}

ก่อนจะอธิบายทีละบรรทัด ขอบอกไว้ก่อนว่า เนื้อในของ Error Handler ไม่มีคำตอบที่ถูกหรือผิด มันคือความเห็นล้วน ๆ คุณจะส่ง Error ไป Sentry ตรงนี้ก็ได้ จะ Log ด้วย Pino ก็ได้ จะเขียนลงไฟล์ก็ได้ จะยิง Slack เรียกคนที่อยู่เวรก็ได้ สิ่งที่ผมเขียนให้ดูคือตัวอย่างของสิ่งที่เป็นไปได้ ไม่ใช่แบบแผนที่ต้องทำตาม

บทเรียนจริงของบทนี้คือการที่ Error ถูกจัดการ ส่วนจะจัดการอย่างไรขึ้นอยู่กับว่าคุณ Debug ระบบ Production ของคุณด้วยวิธีไหน

console.log(err.stack) คือ Stack Trace เต็ม ๆ ซึ่งมีประโยชน์มากตอนพัฒนา ในระบบจริงตรงนี้ควรเป็น Logger ที่ส่งไปเก็บที่ไหนสักแห่งมากกว่า

ค่าตั้งต้น — ถ้า Error มี status ติดมาก็ใช้ค่านั้น ถ้าไม่มีก็ถือว่าเป็นความผิดของเราคือ 500 ข้อความก็เช่นกัน ถ้าไม่มีก็ตอบกลาง ๆ ว่า Internal Server Error

แยกตามชนิดของ Error — ผมเลือกดูจาก err.name แล้วจับคู่กับ Status ที่เหมาะสม คุณจะเปลี่ยนไปดูจาก Error Code ของตัวเองแล้วเขียนเป็น switch ก็ได้ หรือจะดูจาก Error Code ของ PostgreSQL ตรง ๆ ก็ได้เหมือนกัน เช่นโค้ด 23505 ที่แปลว่าข้อมูลซ้ำ ก็แปลงเป็น 409

รายละเอียดเฉพาะตอน Dev — บรรทัดที่ Spread env.APP_STAGE === 'dev' เข้าไปคือทริกที่ใช้กันบ่อย เพราะ Spread ค่า false เข้า Object จะไม่เกิดอะไรขึ้นเลย ผลคือ stack และ details จะโผล่มาเฉพาะตอนพัฒนา ส่วน Production จะเห็นแค่ error ก้อนเดียว ซึ่งสำคัญมาก เพราะ Stack Trace บอกโครงสร้างภายในของระบบคุณให้คนนอกรู้

คลาส APIError คือทางที่เราเลือกเพื่อให้โค้ดที่โยน Error กำหนดได้เองว่าอยากได้ Status เท่าไรและ Name อะไร มันคือ Error ธรรมดาที่ extends ออกมาแล้วแปะ Field เพิ่มสองตัว

ประเด็นที่ต้องคิดต่อคือ Error Handler จะแยกแยะอะไรได้ก็ต่อเมื่อโค้ดฝั่งที่โยน Error ร่วมมือกับมัน ถ้าไม่มีใครโยน APIError ที่มี name ว่า ValidationError เลย เงื่อนไข if ก้อนนั้นก็ไม่มีวันทำงาน นี่คือเหตุผลที่คุณต้องตัดสินใจให้ชัดว่าระบบ Error ของคุณคืออะไร แล้วใช้มันให้เหมือนกันทั้งโปรเจกต์

ลงทะเบียนไว้ล่างสุดเสมอ

เปิด src/server.ts แล้วเติมบรรทัดเดียวไว้ใต้ Route ทั้งหมด

import { errorHandler } from './middleware/errorHandler.ts'

app.use('/api/auth', authRoutes)
app.use('/api/users', userRoutes)
app.use('/api/habits', habitRoutes)

// Global error handler — ต้องอยู่ล่างสุด
app.use(errorHandler)

กฎมีข้อเดียวคือ มันต้องอยู่ล่างสุด ด้วยเหตุผลเดียวกับ Middleware ทุกตัว คือมันเห็นเฉพาะสิ่งที่อยู่เหนือมันขึ้นไป ถ้าเผลอเอาไปวางก่อน Route มันจะไม่มีวันถูกเรียกเลยแม้แต่ครั้งเดียว

// ผิด — Route ยังไม่ได้ลงทะเบียนเลย
app.use(errorHandler)
app.use('/api/habits', habitRoutes)

// ถูก
app.use('/api/habits', habitRoutes)
app.use(errorHandler)

ทดสอบว่ามันทำงานจริง

วิธีพิสูจน์ที่เร็วที่สุดคือแกล้งโยน Error ทิ้งไว้กลางทาง ใส่ Middleware ชั่วคราวไว้บนสุดของแอป

app.use((req, res, next) => {
  next(new APIError('validation error', 'ValidationError', 400))
})

ทีนี้ไม่ว่าคุณจะยิง Path ไหนก็จะได้ก้อนนี้กลับมา

{
  "error": "Validation Error",
  "stack": "Error\n    at ...",
  "details": "validation error"
}

สังเกตสองอย่าง อย่างแรกคือได้ 400 ตามที่ name กำหนด อย่างที่สองคือ Route ทั้งหมดถูกข้ามไปเฉย ๆ ไม่มีอะไรได้ทำงานเลย มันวิ่งตรงไปหา Error Handler ที่ใกล้ที่สุด ซึ่งก็คือตัวที่เราเพิ่งลงทะเบียนไว้ ทดสอบเสร็จแล้วอย่าลืมลบ Middleware ตัวนี้ทิ้ง

จับ Route ที่ไม่มีอยู่จริง

เมื่อมี Error Handler แล้ว การจัดการ 404 ก็ง่ายขึ้น เพิ่ม Middleware ตัวเล็ก ๆ ไว้หลัง Route ทั้งหมดแต่ก่อน Error Handler

export const notFound = (req: Request, res: Response, next: NextFunction) => {
  next(new APIError(`Not found - ${req.originalUrl}`, 'NotFoundError', 404))
}

หลักการคือถ้า Request วิ่งผ่าน Route ทุกตัวมาถึงตรงนี้ได้ แปลว่าไม่มี Route ไหนรับมันไว้เลย ก็คือ 404 นั่นเอง แล้วเราส่งต่อให้ Error Handler จัดรูปแบบ Response ให้เหมือนกับ Error อื่น ๆ ทั้งหมด แทนที่ผู้ใช้จะได้หน้า HTML ที่ Express แถมมาให้

ลำดับใน src/server.ts จึงเป็น Global Middleware ก่อน แล้ว Route แล้ว notFound แล้ว errorHandler ปิดท้าย

แล้ว Middleware เดิมของเราล่ะ

พอมี Error Handler กลางแล้ว validateBody ในบทที่ 12 ก็ไม่จำเป็นต้องตอบ Response เองอีกต่อไป มันจะแค่สร้าง APIError ที่มี name ว่า ValidationError แล้วเรียก next(error) จบก็ได้ แล้วปล่อยให้ Error Handler เป็นคนแปลงเป็น 400

แต่เราจะไม่แก้มัน ด้วยเหตุผลเดียวกับที่คุยกันไว้ในบทที่ 25 — validateBody และ authenticateToken รู้ดีอยู่แล้วว่า Error ของมันคืออะไรและควรตอบอะไร การจบเรื่องตรงนั้นทำให้เราคุม Status Code และรูปแบบ Body ได้แม่นยำ เช่นให้ Client เห็น details รายฟิลด์จาก Zod ซึ่งเป็นข้อมูลที่ Error Handler กลางไม่มีทางรู้

บทบาทของทั้งสองอย่างจึงต่างกัน — Error ที่เราคาดไว้แล้วจบที่จุดเกิดเหตุ ส่วน Error ที่เราไม่ได้คาดไว้ตกลงมาที่ตาข่ายกลาง สังเกตว่า validateBody ของเราลงท้ายด้วย next(e) อยู่แล้วสำหรับ Error ที่ไม่ใช่ ZodError นั่นแหละคือรอยต่อระหว่างสองระบบนี้

Error Handler เองก็พังได้

เรื่องนี้เกิดบ่อยกว่าที่คิด ถ้าข้างใน Error Handler คุณทำงาน Async เช่นยิง Error ไปหา Sentry แล้วการยิงนั้นพังเสียเอง ให้ห่อด้วย try/catch ส่วนงาน Synchronous ธรรมดานั้นถ้าพังคุณจะเจอมันเองตั้งแต่ตอนพัฒนาอยู่แล้ว

ตาข่ายชั้นสุดท้ายที่ระดับ Node.js

ยังมีอีกชั้นที่อยู่นอกเหนือ Express ไปเลย คือดักที่ตัว Process

process.on('unhandledRejection', (reason) => {
  console.error('Unhandled rejection:', reason)
})

process.on('uncaughtException', (error) => {
  console.error('Uncaught exception:', error)
})

สองตัวนี้จับ Error ที่ไม่มีใครรับเลยทั้งโปรแกรม แต่ต้องเข้าใจข้อจำกัดสองข้อ ข้อแรกคือ Error ที่เกิดใน Express มักไม่ขึ้นมาถึงตรงนี้ เพราะ Express ดักไว้เองแล้วส่งให้ Error Handler ของเราตามที่คุยกันไปข้างบน ข้อที่สองคือ Callback ตรงนี้เป็น Async ไม่ได้ เพราะตอนนั้นโปรเซสกำลังจะปิดตัวลงแล้ว จึงเหมาะกับการ Log ทิ้งท้ายหรือสั่งปิดอย่างเรียบร้อยเท่านั้น

สรุปตรง ๆ ว่า ไม่มีวิธีไหนกัน Server ไม่ให้ตายได้ร้อยเปอร์เซ็นต์นอกจากเขียนโค้ดให้ดี สิ่งที่ต้องทำเพิ่มคือตอน Deploy ต้องมีอะไรสักอย่างคอยรีสตาร์ท Server ให้เมื่อมันตาย ซึ่งเราจะได้เห็นในบทที่ 31 และคำถามที่ต้องถามคือ Error นั้นกู้คืนได้ไหม ถ้าเป็นบั๊กในโค้ด รีสตาร์ทกี่รอบมันก็ตายอยู่ดี

สรุปแนวปฏิบัติ

  • Log ไว้ที่ฝั่ง Server เสมอ — ถึงจะไม่ได้ส่งอะไรให้ Client เห็นก็ตาม
  • ใช้ Status Code ให้ตรงความหมาย — 4xx คือฝั่งเขาผิด 5xx คือฝั่งเราผิด
  • ซ่อนรายละเอียดใน Production — ไม่ส่ง Stack Trace ออกไปเด็ดขาด
  • รูปแบบต้องเหมือนกันทุก Endpoint — ของเราคือ { error } เสมอ คนใช้ API จะเขียนโค้ดรับได้ที่เดียวจบ
  • ลงทะเบียนไว้ล่างสุด — และใส่ครบสี่อาร์กิวเมนต์
  • มีระบบของ Error ให้ชัด — จะใช้ Custom Error Class หรือ Error Code ก็ได้ ขอให้ทั้งโปรเจกต์ใช้แบบเดียวกัน
  • เขียนไว้ในเอกสาร API — บอกให้ชัดว่าแต่ละ Endpoint คืน Error อะไรได้บ้าง

ตอนนี้ API ของเราครบทุกชิ้นส่วนแล้ว ทั้ง Routing, Middleware, Database, Authentication, CRUD และ Error Handling เหลือคำถามสุดท้ายที่ยังตอบไม่ได้คือ เรารู้ได้อย่างไรว่าทุกอย่างยังทำงานอยู่จริง หลังจากที่เราแก้โค้ดครั้งต่อไป บทหน้าเราจะเริ่มเขียน Test กัน
