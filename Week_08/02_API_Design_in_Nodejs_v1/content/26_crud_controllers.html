เขียน CRUD Controllers สำหรับ Habit

ทุกชิ้นส่วนที่เราสร้างมาตลอดคอร์สกำลังจะมาบรรจบกันในบทนี้ ลองไล่เส้นทางของ Request หนึ่งใบดู — Request วิ่งเข้ามา ถูก Route ไปยังที่ที่ถูกต้อง ระหว่างทางเจอ Middleware คอยตรวจว่าล็อกอินหรือยัง เจออีกตัวคอยตรวจว่าข้อมูลที่ส่งมาถูกรูปแบบไหม แล้วสุดท้ายถึงจะไปถึงปลายทางคือ Controller ที่ทำงานจริงแล้วตอบกลับ

บทนี้เราจะเขียนปลายทางนั้นให้ครบทั้ง Create, Read และ Update ของ Habit

ทบทวน RESTful สั้น ๆ

หัวใจของ REST ที่เราคุยกันไว้ในบทที่ 7 สรุปได้ประโยคเดียวคือ Route + Verb = ฟังก์ชันหนึ่งตัว ตัว Router แปลความหมายนี้ออกมาตรง ๆ เลย

router.get('/', getUserHabits)        // GET    /api/habits
router.get('/:id', getHabitById)      // GET    /api/habits/123
router.post('/', createHabit)         // POST   /api/habits
router.patch('/:id', updateHabit)     // PATCH  /api/habits/123
router.delete('/:id', deleteHabit)    // DELETE /api/habits/123

Path เดียวกันเป๊ะ แต่ Verb ต่างกันก็ไปคนละฟังก์ชัน นี่คือเหตุผลที่ API แบบ RESTful เดาง่าย — คุณเห็น /api/habits คุณก็เดาได้ทันทีว่าถ้าอยากสร้างต้องยิง POST มาที่นี่

Status Code ที่ใช้จริง

เรื่องนี้เราพูดกันเป็นระยะมาตลอด บทนี้ขอรวบไว้ที่เดียว หลักคือดูตัวเลขหลักแรก

  • 2xx สำเร็จ — 200 สำเร็จทั่วไป 201 สร้างของใหม่สำเร็จ 204 สำเร็จแต่ไม่มีอะไรจะส่งกลับ ซึ่งพูดตรง ๆ ว่าแทบไม่ค่อยเห็นใครใช้
  • 4xx ฝั่ง Client ผิด — 400 ข้อมูลที่ส่งมาไม่ถูกต้อง 401 คุณไม่ได้ส่งอะไรมาให้พิสูจน์ตัวตนเลย ไม่มี Bearer Token ไม่มี API Key ไม่มีอะไรทั้งนั้น 403 ส่งมาแล้วแต่ไม่มีสิทธิ์ 404 สิ่งที่ขอไม่มีอยู่จริง 409 ชนกัน เช่นสมัครด้วยอีเมลที่มีคนใช้แล้ว
  • 5xx ฝั่งเราผิด — 500 Server เราพังเอง 502 ตัวกลางอย่าง CDN บอกว่า "ผมทำงานปกตินะ แต่เครื่องต้นทางที่ผมต้องคุยด้วยมันตาย" ส่วน 503 คือเรารู้ตัวว่าปิดอยู่ เช่นกำลังแก้ Migration ที่พลาดไป

มีมากกว่านี้อีกเยอะถ้าไปไล่ดู แต่ในชีวิตจริงคุณจะเจอวนอยู่แค่กลุ่มนี้ ผมกล้าพูดว่า 409 เองก็ยังถือว่าหายากแล้ว

สร้าง habitController.ts

สร้างไฟล์ src/controllers/habitController.ts แล้วเริ่มจาก Import ที่จะใช้ทั้งไฟล์

import type { Response } from 'express'
import type { AuthenticatedRequest } from '../middleware/auth.ts'
import { db } from '../db/connection.ts'
import { habits, entries, habitTags, tags } from '../db/schema.ts'
import { eq, and, desc, inArray } from 'drizzle-orm'

จุดที่สำคัญที่สุดคือบรรทัดที่สอง — เราใช้ AuthenticatedRequest แทน Request ของ Express เพราะทุก Route ใน habitRoutes.ts ถูกล็อกด้วย authenticateToken ไปแล้วตั้งแต่บทที่ 24 นั่นแปลว่าเมื่อโค้ดวิ่งมาถึง Controller เรารู้แน่นอนว่า req.user มีค่าอยู่

ส่วน habitTags คือตารางกลางแบบ Many-to-Many ที่เราสร้างไว้ในบทที่ 16 เพราะ Habit หนึ่งอันมีได้หลาย Tag และ Tag หนึ่งอันก็ผูกกับได้หลาย Habit เราจึงเปิดช่องให้ผู้ใช้ผูก Tag ผ่านฝั่ง Habit ได้ (จะทำจากฝั่ง Tag ก็ได้เหมือนกัน มันสมมาตร) ส่วน tags กับ inArray เอาไว้ใช้กับ Controller ตัวอื่นในไฟล์เดียวกันนี้

C คือ Create

export const createHabit = async (req: AuthenticatedRequest, res: Response) => {
  try {
    const { name, description, frequency, targetCount, tagIds } = req.body
    const userId = req.user!.id

    const result = await db.transaction(async (tx) => {
      const [newHabit] = await tx
        .insert(habits)
        .values({ userId, name, description, frequency, targetCount })
        .returning()

      // ถ้าส่ง tagIds มาด้วย ให้สร้างความสัมพันธ์ในตารางกลาง
      if (tagIds && tagIds.length > 0) {
        const habitTagValues = tagIds.map((tagId: string) => ({
          habitId: newHabit.id,
          tagId,
        }))
        await tx.insert(habitTags).values(habitTagValues)
      }

      return newHabit
    })

    res.status(201).json({
      message: 'Habit created successfully',
      habit: result,
    })
  } catch (error) {
    console.error('Create habit error:', error)
    res.status(500).json({ error: 'Failed to create habit' })
  }
}

req.user!.id — เครื่องหมายอัศเจรีย์คือการบอก TypeScript ว่า "ตรงนี้มีค่าแน่นอน" เพราะเรานิยาม user ไว้เป็น Optional ในบทที่ 24 แต่เรารู้จากลำดับ Middleware ว่ามันผ่าน authenticateToken มาแล้ว

และนี่คือประเด็นด้าน Security ที่ห้ามลืม — userId มาจาก Token ที่ผ่านการตรวจลายเซ็นแล้ว ไม่ใช่จาก req.body ถ้าเราเชื่อ userId ที่ Client ส่งมา ใครก็สร้าง Habit ในชื่อคนอื่นได้ทันที

ทำไมต้องตอบ 201 เพราะ POST ที่สร้างของใหม่สำเร็จมี Status ของตัวเองอยู่แล้ว ไม่ใช่ 200 เฉย ๆ

ทำไม catch ตอบ 500 เพราะถ้าโค้ดวิ่งมาถึงตรงนี้ได้ แปลว่า Input ผ่าน Validation แล้ว และผู้ใช้ผ่าน Authentication แล้ว สิ่งที่พังได้จึงเหลือแต่ฝั่งเรา — Database ล่ม Query ผิด อะไรทำนองนั้น มันเป็นความผิดของเราล้วน ๆ

Transaction คืออะไร

ถ้าคุณไม่เคยทำงานกับ Database มาก่อน db.transaction() คือของใหม่ในบทนี้

ลองคิดตาม ถ้าฟังก์ชันหนึ่งต้องเขียนลง Database มากกว่าหนึ่งครั้ง แล้วครั้งแรกสำเร็จ แต่ครั้งที่สองพัง ข้อมูลของคุณจะค้างอยู่ในสภาพที่ไม่สมบูรณ์ ตัวอย่างคลาสสิกคือการโอนเงิน — ขั้นตอนตัดเงินจากบัญชีต้นทางสำเร็จ แต่ขั้นตอนเพิ่มเงินให้บัญชีปลายทางพัง แล้วเงินก้อนนั้นอยู่ไหน ไม่อยู่ทั้งสองบัญชี

Transaction เกิดมาเพื่อเรื่องนี้ มันมัดคำสั่งเขียนหลายคำสั่งเข้าเป็นก้อนเดียว ถ้ามีตัวใดตัวหนึ่งพัง ทุกตัวจะถูกย้อนกลับหมด คำอธิบายที่ผมชอบที่สุดคือมันเหมือน Git Commit — คุณรวบการเปลี่ยนแปลงทั้งหมดแล้วสั่งให้มีผลพร้อมกันทีเดียว Database ที่รองรับ ACID ทุกตัวมีของสิ่งนี้

วิธีใช้ง่ายมาก เรียก db.transaction() แล้วจะได้ Object ที่ผมตั้งชื่อว่า tx ออกมา ซึ่งใช้เหมือน db ทุกประการ ข้างในนั้นต้องเรียก tx เท่านั้น ถ้าเผลอเรียก db คำสั่งนั้นจะหลุดออกไปนอก Transaction ทันที และสิ่งที่ return ออกมา คือสิ่งที่ result ข้างนอกจะได้รับ

ต้องสั่ง Commit หรือ Rollback เองไหม — ไม่ต้อง Drizzle จัดการให้ วิ่งจนจบก็ Commit มี Error โยนออกมาก็ Rollback ที่ต้องสั่งเองมีกรณีเดียวคือคุณไปทำงาน Async อย่างอื่นข้างในที่ไม่เกี่ยวกับ Database เช่นยิงไปอัปเดต Stripe แล้วอยากให้ Stripe พังเมื่อไรก็ Rollback ด้วย ซึ่ง Drizzle ไม่มีทางรู้ วิธีที่ง่ายที่สุดคือ โยน Error ออกมาเอง แล้วมันจะ Rollback ให้

เสียบเข้ากับ Route

กลับไปที่ src/routes/habitRoutes.ts เอา Handler ปลอมที่เราเขียนไว้ตั้งแต่บทที่ 8 ออก แล้วใส่ Controller ตัวจริงลงไป

import {
  createHabit,
  getUserHabits,
  updateHabit,
} from '../controllers/habitController.ts'

const createHabitSchema = z.object({
  name: z.string(),
  description: z.string().optional(),
  frequency: z.string(),
  targetCount: z.number(),
  tagIds: z.array(z.string()).optional(),
})

router.post('/', validateBody(createHabitSchema), createHabit)

createHabitSchema ที่เราใส่ไว้เป็นตัวอย่างในบทที่ 12 มีแค่ name ตอนนี้ถึงเวลาเขียนของจริง วิธีที่ผมทำคือเปิด Controller ดูว่ามัน Destructure อะไรออกมาจาก req.body บ้าง แล้วเปิด Schema ของ Database ดูว่า Field ไหนบังคับ — ได้ความว่า name กับ frequency บังคับ ที่เหลือ Optional หรือมี Default อยู่แล้ว

คำถามที่ควรถามคือ ทำไมไม่ Import Schema จาก Drizzle มาใช้เลย ในเมื่อบทที่ 17 เราก็ทำแบบนั้นได้ คำตอบคือเพราะสิ่งที่เรารับจากผู้ใช้กับสิ่งที่ Database เก็บ ไม่เหมือนกัน ตรงนี้ — ตาราง habits ไม่มีคอลัมน์ชื่อ tagIds เพราะความสัมพันธ์กับ Tag อยู่คนละตาราง แต่เราอยากเปิดให้ผู้ใช้ส่ง tagIds มาพร้อมกันในครั้งเดียว เมื่อสองฝั่งไม่ตรงกัน เราก็ต้องเขียน Schema ของตัวเอง

อีกจุดที่ต้องระวังคือ targetCount เป็น z.number() เพราะในตาราง Database มันคือ integer ส่งมาเป็น String จะไม่ผ่านทันที (เดี๋ยวเราจะเจอกับดักนี้ของจริงในบทหน้า) ส่วน frequency ยังเป็น z.string() ตามคอลัมน์ที่เป็น varchar ซึ่งจุดอ่อนข้อนี้เราคุยกันไว้แล้วในบทที่ 17

R คือ Read — ดึงทั้งหมด

ต่อไปคือ "ขอ Habit ทั้งหมดของฉัน" ซึ่งผมจะแถม Tag ที่ผูกอยู่ไปให้ด้วยเลยโดยไม่ต้องขอ

export const getUserHabits = async (
  req: AuthenticatedRequest,
  res: Response
) => {
  try {
    const userId = req.user!.id

    const userHabitsWithTags = await db.query.habits.findMany({
      where: eq(habits.userId, userId),
      with: {
        habitTags: {
          with: {
            tag: true,
          },
        },
      },
      orderBy: [desc(habits.createdAt)],
    })

    // แผ่ Tag ออกมาให้อยู่ระดับเดียวกับ Habit
    const habitsWithTags = userHabitsWithTags.map((habit) => ({
      ...habit,
      tags: habit.habitTags.map((ht) => ht.tag),
      habitTags: undefined,
    }))

    res.json({ habits: habitsWithTags })
  } catch (error) {
    console.error('Get habits error:', error)
    res.status(500).json({ error: 'Failed to fetch habits' })
  }
}

where: eq(habits.userId, userId) คือหัวใจของ Controller ตัวนี้ ทุก Query ที่แตะข้อมูลของผู้ใช้ต้องกรองด้วย Id ที่ได้จาก Token เสมอ ถ้าลืมบรรทัดนี้ คุณกำลังส่ง Habit ของทุกคนในระบบให้คนที่ยิงเข้ามา

with คือการ Join เราเริ่มจากตาราง habits ซึ่งมีความสัมพันธ์ไปยัง habitTags และตารางนั้นก็มีความสัมพันธ์ต่อไปยัง tags อีกที ทางเดียวที่จะรู้ว่า Habit หนึ่งอันมี Tag อะไรบ้างคือต้องเดินผ่านตารางกลางนั้น with ซ้อน with จึงเป็นการบอกว่า "หา Habit มา แล้วหา habitTags ของแต่ละอัน แล้วหา Tag ของแต่ละ habitTag อีกที" ส่วน tag: true แปลว่า "เอา Field นี้มาด้วย" เฉย ๆ ไม่ได้ใส่ true ให้ habit ด้วยเพราะมันจะวนกลับมาที่ Habit ตัวเดิมที่อยู่ชั้นบนสุด

orderBy: [desc(habits.createdAt)] เรียงจากใหม่ไปเก่า อันที่เพิ่งสร้างจะอยู่บนสุด

แปลงหน้าตาข้อมูลก่อนส่ง

ผลลัพธ์ดิบที่ได้จะมี habitTags โผล่คั่นกลางอยู่ ซึ่งเป็นรายละเอียดภายในของ Database ที่คนใช้ API ไม่ควรต้องรับรู้ เราจึงแผ่มันออกให้แบนลง เอา Tag ขึ้นมาไว้ที่ tags ตรง ๆ

ทริกที่น่าสนใจคือบรรทัด habitTags: undefined — เมื่อ JSON.stringify() เจอค่า undefined มันจะตัด Field นั้นทิ้งไปเลย เราจึงลบ Field ออกจาก Response ได้ด้วยวิธีนี้

ขอสารภาพตรง ๆ ว่าวิธีนี้ไม่ใช่วิธีที่ถูกที่สุด งานแปลงข้อมูลแบบนี้ควรทำที่ระดับ Database ด้วย Query ที่เขียนดีกว่านี้หรือด้วย Materialized View ผมทำใน JavaScript เพราะเร็วกว่าและผมไม่ใช่พ่อมด SQL ถ้าคุณทำที่ฝั่ง Database ได้ ทำเถอะครับ

สังเกตว่า Route นี้ไม่มี Validation Middleware เพราะ GET ไม่มี Body ให้ตรวจ Input Validation มีไว้สำหรับ POST, PUT และ PATCH ที่จริงเรายังตรวจ Query Parameter ได้ด้วย validateQuery จากบทที่ 12 ถ้าเราจะทำระบบแบบ "ส่ง ?tags=true มาแล้วค่อยแถม Tag ให้" แต่พอถึงจุดนั้นคุณก็กำลังประดิษฐ์ภาษา Query ของตัวเองขึ้นมาแล้ว

R คือ Read — ดึงตัวเดียว

ตัวนี้แทบเหมือนเดิมเป๊ะ ส่วนที่ต่างมีแค่ตรงกลาง ที่เหลือ ทั้งการแผ่ Tag การตอบ และ catch เหมือน getUserHabits ทุกประการ

const { id } = req.params
const userId = req.user!.id

const habit = await db.query.habits.findFirst({
  where: and(eq(habits.id, id), eq(habits.userId, userId)),
  with: {
    habitTags: { with: { tag: true } },
    entries: {
      orderBy: [desc(entries.completion_date)],
      limit: 10, // เอาแค่ 10 ครั้งล่าสุดพอ
    },
  },
})

if (!habit) {
  return res.status(404).json({ error: 'Habit not found' })
}

findFirst แทน findMany และเงื่อนไขต้องตรงสองอย่างคือ Id ของ Habit และ Id ของเจ้าของ ถ้าไม่เจอตอบ 404

เพิ่มมาอีกอย่างคือเราแถม entries ซึ่งคือประวัติการทำ Habit นั้นไปด้วย แต่จำกัดไว้ที่ 10 รายการล่าสุด เพราะการดึงประวัติทั้งหมดของ Habit ที่ทำมาสามปีไม่มีใครได้ประโยชน์ limit แบบนี้คือกำแพงกันไม่ให้ Response บวมโดยไม่มีเพดาน

U คือ Update

ตัวนี้สนุกที่สุดในบท เพราะมีทั้ง Transaction และประเด็นเรื่องสิทธิ์

export const updateHabit = async (req: AuthenticatedRequest, res: Response) => {
  try {
    const { id } = req.params
    const userId = req.user!.id
    const { tagIds, ...updates } = req.body

    const result = await db.transaction(async (tx) => {
      const [updatedHabit] = await tx
        .update(habits)
        .set({ ...updates, updatedAt: new Date() })
        .where(and(eq(habits.id, id), eq(habits.userId, userId)))
        .returning()

      if (!updatedHabit) {
        throw new Error('Habit not found')
      }

      if (tagIds !== undefined) {
        // ลบความสัมพันธ์เดิมทิ้งก่อน แล้วค่อยใส่ชุดใหม่เข้าไป
        await tx.delete(habitTags).where(eq(habitTags.habitId, id))

        if (tagIds.length > 0) {
          const habitTagValues = tagIds.map((tagId: string) => ({
            habitId: id,
            tagId,
          }))
          await tx.insert(habitTags).values(habitTagValues)
        }
      }

      return updatedHabit
    })

    res.json({
      message: 'Habit updated successfully',
      habit: result,
    })
  } catch (error: any) {
    if (error.message === 'Habit not found') {
      return res.status(404).json({ error: 'Habit not found' })
    }
    console.error('Update habit error:', error)
    res.status(500).json({ error: 'Failed to update habit' })
  }
}

แยก tagIds ออกมาก่อน ด้วย Rest Operator เพราะสองอย่างนี้จะไปลงคนละตาราง tagIds ไปที่ habitTags ส่วน updates ที่เหลือทั้งหมดคือสิ่งที่จะเอาไปอัปเดตตาราง habits

.set() คือการอัปเดตแบบบางส่วน Field ไหนที่ไม่ได้ส่งมาก็ไม่ถูกแตะต้อง เราแอบใส่ updatedAt: new Date() เพิ่มเข้าไปเองทุกครั้งด้วย

บรรทัดที่ห้ามลืมเด็ดขาด

ดูที่ where ให้ดี มันเช็คสองเงื่อนไขพร้อมกันด้วย and()

.where(and(eq(habits.id, id), eq(habits.userId, userId)))

เงื่อนไขแรกคือ "Habit ที่มี Id ตรงกับที่ส่งมาใน Route Param" ซึ่งตรงไปตรงมา แต่เงื่อนไขที่สองคือเรื่องเป็นเรื่องตาย — Habit นั้นต้องเป็นของผู้ใช้ที่กำลังยิงเข้ามาด้วย นี่คือ Authorization ตัวเป็น ๆ คนละเรื่องกับ Authentication ที่แปลว่า "คุณคือใคร" อันนี้แปลว่า "คุณมีสิทธิ์แก้ของชิ้นนี้ไหม"

ถ้าไม่มีเงื่อนไขที่สอง ใครก็ตามที่รู้ Id ของ Habit คนอื่นจะแก้ Habit นั้นได้ทันที ลองนึกภาพว่าถ้า Twitter ไม่เช็คข้อนี้ คุณจะโพสต์ในนามใครก็ได้แค่รู้ Id ของเขา นี่คือช่องโหว่ที่เจอบ่อยมากในระบบจริงและร้ายแรงเสมอ

ทำไมต้อง .returning() แล้วเช็ค เพราะถ้า where ไม่แมตช์อะไรเลย Drizzle จะไม่โยน Error มันจะคืนค่าว่างเปล่ากลับมาเฉย ๆ (ORM บางตัวโยน Error ให้ ของ Drizzle ไม่ทำ) เราจึงต้องตรวจเอง แล้ว throw new Error('Habit not found') ซึ่งได้ผลสองอย่างในทีเดียว — Transaction ถูก Rollback และ catch ข้างนอกจับได้แล้วแปลงเป็น 404

ตอนสอนสด ผมเลือกตอบ 401 แล้วปิด Response ด้วย res.status(401).end() เฉย ๆ ตรงจุดนี้ (.end() คือ "จบ Request เลย ไม่มี Body จะส่ง" ซึ่งบางครั้งก็เพียงพอแล้ว) เหตุผลที่ลังเลระหว่างสอง Status คือเราแยกไม่ออกจริง ๆ ว่ามันไม่เจอเพราะ Id ไม่มีอยู่จริง หรือเพราะ Id มีอยู่แต่ไม่ใช่ของคุณ แต่โค้ดที่ลงเอยใน Repo ใช้ 404 ซึ่งผมว่าดีกว่า เพราะการตอบ 404 เหมือนกันทั้งสองกรณีไม่เผยให้คนนอกรู้ว่า Id นั้นมีอยู่จริงหรือไม่

เรื่อง Tag เป็นการแทนที่ ไม่ใช่การเพิ่ม ถ้าคุณส่ง tagIds มา เราลบความสัมพันธ์เดิมทั้งหมดทิ้งก่อนแล้วค่อยใส่ชุดใหม่ นี่ไม่ใช่วิธีที่ถูกหรือผิด มันคือการตัดสินใจของคนออกแบบ Server ว่าจะตีความคำว่า "อัปเดต Tag" อย่างไร และต้องเขียนไว้ในเอกสาร API ให้ชัด

ต่อ Route ให้ครบ

router.get('/', getUserHabits)
router.get('/:id', getHabitById)
router.post('/', validateBody(createHabitSchema), createHabit)
router.patch('/:id', updateHabit)

ผมเลือก PATCH ไม่ใช่ PUT เพราะเราอัปเดตแค่บางส่วน ตามที่คุยกันไว้ในบทที่ 7

สังเกตว่า PATCH ไม่มี Validation ทั้งที่ควรมี เหตุผลตรง ๆ คือ Schema ของมันต้องเป็นแบบ Partial คือทุก Field เป็น Optional หมด (Zod มี .partial() ให้อยู่แล้ว) แต่ผมขี้เกียจเขียน และถ้าส่งข้อมูลผิดมาแล้วมันพัง ผมก็ยอมรับได้เพราะยังไงมันก็พังอยู่ดี แต่พูดให้เป็นธรรม เหตุผลจริง ๆ ที่ควรใส่ Validation ไม่ใช่เพื่อกัน Server พัง แต่เพื่อบอกผู้ใช้ให้ชัดว่าเขาพลาดที่ Field ไหน เวอร์ชันเต็มใน Repo จึงใส่ทั้ง updateHabitSchema และตรวจ Route Param ด้วย

const uuidSchema = z.object({
  id: z.uuid('Invalid habit ID format'),
})

router.get('/:id', validateParams(uuidSchema), getHabitById)

ประโยชน์ของการตรวจ Param คือถ้ามีคนยิง Id มั่ว ๆ ที่ไม่ใช่รูปแบบ UUID เขาจะได้ 400 พร้อมคำอธิบายตั้งแต่ก่อนถึง Controller แทนที่จะปล่อยให้ Database เป็นคนพังแล้วตอบ 500 กลับไป (และเขียน z.uuid() ไม่ใช่ z.string().uuid() ด้วยเหตุผลเดียวกับ z.email() ในบทที่ 23)

ทุก Controller หน้าตาเหมือนกันหมด

เราไม่ได้เขียนครบทุก Resource ในคอร์สนี้ และไม่จำเป็นด้วย เพราะถ้าคุณเลื่อนดู Controller ของ Tag หรือ User ใน Repo คุณจะพบว่ามันคือรูปแบบเดียวกันซ้ำ ๆ บนคนละตาราง เหมือนกันจนเขียนฟังก์ชันที่รับชื่อ Resource เข้าไปแล้วผลิต Controller ออกมาให้ได้เลย ที่ผมให้เขียนมือก็เพื่อให้คุณได้ซ้อมจริง ๆ เท่านั้น

รูปแบบที่ซ้ำกันทุกตัวมีดังนี้

  • ห่อด้วย try/catch เสมอ — เพื่อคุม Status Code และรูปแบบ Response ของกรณีที่เราคาดไว้แล้ว
  • ตัวตนมาจาก req.user เท่านั้น — ไม่เอาจาก Body ไม่เอาจาก Query
  • กรองด้วย Id ของเจ้าของทุก Query — ทั้งตอนอ่าน ตอนแก้ และตอนลบ
  • Validate ก่อนถึง Controller — ข้างใน Controller จึงไม่ต้องมี if เช็ค Input อีก
  • รูปแบบ Response สม่ำเสมอ — สำเร็จได้ { message, habit } ผิดพลาดได้ { error }
  • ใช้ Transaction เมื่อเขียนหลายตาราง — เพื่อไม่ให้ข้อมูลค้างครึ่ง ๆ กลาง ๆ

โค้ดครบแล้ว บทหน้าเราจะเปิด Postman ยิงทดสอบทุกเส้นทางที่เพิ่งเขียนกัน แล้วคุณจะได้เห็นด้วยว่าเวลามันพังจริง หน้าตาของ Error เป็นอย่างไร
