Validation Middleware ด้วย Zod

สิ่งแรก ๆ ที่ผมทำเสมอเวลาสร้าง API คือตรวจสอบข้อมูลขาเข้า เพราะผมไม่อยากนั่งเขียน if เช็คว่าค่านี้มีไหม ค่านั้นเป็น String หรือเปล่า ซ้ำแล้วซ้ำอีกในทุก Handler ผมอยากให้ Handler ของผมสมมติได้เลยว่าทุกอย่างที่ต้องใช้มาครบและถูกต้องแล้ว

วิธีที่ดีที่สุดที่จะได้แบบนั้นคือเขียน Middleware มาคั่นไว้ก่อนถึง Handler ซึ่งเราจะทำกันในบทนี้ ถ้าให้พูดตรง ๆ คือ ผมไม่มีวันสร้าง API โดยไม่มีตัวตรวจ Input มันเหมือนการทำ Database โดยไม่มี Schema ซึ่งไม่มีใครทำกัน

ทำไมต้อง Validate

นอกจากความสบายในการเขียนโค้ดแล้ว การไม่ตรวจ Input เปิดช่องให้ปัญหาตามมาเป็นพรวน

  • SQL / NoSQL Injection — ข้อมูลที่แต่งมาเพื่อหลอกให้ Query ทำสิ่งที่เราไม่ได้ตั้งใจ
  • XSS — Script ที่แอบฝังเข้ามาแล้วไปโผล่ใน Response
  • Input ขนาดมหึมา ที่ส่งมาเพื่อทำให้ Server ล่ม
  • Type Confusion — ได้ String ตอนที่โค้ดคาดว่าจะได้ Number แล้วพังกลางทาง
  • ข้อมูลสกปรกลง Database ซึ่งเป็นปัญหาที่แก้ทีหลังยากที่สุด

ของแถมคือ Schema ที่เราเขียนกลายเป็นเอกสารของ API ไปในตัว และ Error ที่ตอบกลับไปช่วยให้คนเรียกใช้ API ของเรา Debug ได้เร็วขึ้นมาก

สร้าง src/middleware/validation.ts

สร้างโฟลเดอร์ src/middleware แล้วสร้างไฟล์ validation.ts ในนั้น เริ่มจาก Import

import type { Request, Response, NextFunction } from 'express'
import { type ZodSchema, ZodError } from 'zod'

สังเกตคำว่า import type — ของจาก Express ทั้งสามตัวเป็นแค่ Type ที่ TypeScript ใช้ตอน Compile ไม่มีตัวตนตอน Runtime การเขียนแบบนี้บอก TypeScript ให้ถอดบรรทัดนี้ทิ้งตอนแปลงเป็น JavaScript ส่วนฝั่ง Zod เราเอา ZodSchema มาเป็น Type แต่เอา ZodError มาเป็นค่าจริง เพราะเราต้องใช้มันกับ instanceof

validateBody

ตัวแรกไว้ตรวจ Payload ที่ถูกส่งขึ้นมาพร้อม POST หรือ PUT ซึ่งก็คือ req.body

export const validateBody = (schema: ZodSchema) => {
  return (req: Request, res: Response, next: NextFunction) => {
    try {
      const validatedData = schema.parse(req.body)
      req.body = validatedData
      next()
    } catch (e) {
      if (e instanceof ZodError) {
        return res.status(400).json({
          error: 'Validation failed',
          details: e.issues.map((err) => ({
            field: err.path.join('.'),
            message: err.message,
          })),
        })
      }
      next(e)
    }
  }
}

ไล่ดูทีละจุด

มันคือ Higher-Order Function เหมือน helmet() และ cors() ในบทที่แล้ว คือฟังก์ชันชั้นนอกรับ Zod Schema เข้าไป แล้ว Return Middleware ตัวจริงที่มีครบสามอาร์กิวเมนต์ (req, res, next) ออกมา เราจึงใช้ Middleware ตัวเดียวกับ Schema กี่แบบก็ได้

ทำไมต้อง try/catch เพราะ schema.parse() จะโยน Error ทันทีเมื่อข้อมูลไม่ตรง Schema กฎเหล็กของงานฝั่ง Server คือ ต้องจัดการ Error ทุกตัว ไม่งั้นโปรเซสตาย — try/catch ไม่ได้ช่วยเราจากทุกอย่าง แต่เป็นจุดเริ่มต้นที่ดี

ทำไมต้องยัดค่าที่ผ่านการตรวจกลับเข้า req.body เพราะ Schema อาจมี .default() หรือมีการ Coerce ชนิดข้อมูล ซึ่งผลลัพธ์จาก parse() รวมการเปลี่ยนแปลงพวกนั้นไว้แล้ว ถ้าไม่ยัดกลับ req.body เดิมก็ยัง "ผ่าน" อยู่ก็จริง แต่จะไม่มีค่า Default และชนิดข้อมูลที่แปลงแล้ว สุดท้ายสิ่งที่ Handler คาดหวังกับของจริงจะไม่ตรงกัน

ทำไมเป็น 400 และทำไมยังมี next(e) — 4xx แปลว่า "ฝั่งคุณส่งมาผิด" ไม่ใช่ 5xx ที่แปลว่า "ฝั่งเราพัง" ส่วน next(e) ท้ายสุดมีไว้เผื่อกรณีที่ Error ไม่ใช่ ZodError ซึ่งแปลว่าเป็นเรื่องที่เราไม่ได้คาดไว้ ก็โยนต่อให้ Error Handler กลางจัดการ (บทที่ 28) อีกทางเลือกคือตัด if ทิ้งแล้วเรียก next(e) อย่างเดียว ไปแยกแยะที่ Error Handler กลางแทน ก็ทำได้ แต่ผมเลือกจบตรงนี้เพราะรูปแบบ Error ของการ Validate เฉพาะเจาะจงพอที่จะอยู่ใกล้ ๆ กันดีกว่า

และย้ำตามบทที่ 10 — ตรงที่ตอบ Response เราใส่ return นำหน้า เพื่อไม่ให้โค้ดหลุดไปเรียก next() ต่อหลังตอบไปแล้ว

เอาไปใช้ที่ Route

เปิด src/routes/habitRoutes.ts แล้วนิยาม Schema กับเสียบ Middleware เข้าไปคั่นระหว่าง Path กับ Handler

import { Router } from 'express'
import { z } from 'zod'
import { validateBody } from '../middleware/validation.ts'

const createHabitSchema = z.object({
  name: z.string(),
})

const router = Router()

router.post('/', validateBody(createHabitSchema), (req, res) => {
  res.status(201).json({ message: 'created habit' })
})

ตรงนี้แหละที่เราเรียกว่า Local Middleware คือ Middleware ที่นั่งติดกับ Route ที่มันใช้จริง ๆ ต่างจาก Global Middleware ที่นั่งอยู่บนสุดของแอป ข้อกำหนดมีแค่ข้อเดียวคือมันต้องมาก่อน Handler (เรายังไม่ได้ต่อ Database จึงยังไม่รู้ว่า Habit ตัวจริงต้องมี Field อะไรบ้าง ตอนนี้สมมติไว้แค่ name ก่อน)

ที่ได้กลับมาคือ Handler ข้างในไม่ต้องมี if เช็คอะไรอีกเลย เพราะถ้าโค้ดในนั้นได้รัน แปลว่า Payload ผ่านการตรวจมาแล้วแน่นอน ถ้าไม่ผ่าน Middleware จะไม่เรียก next() และ Handler จะไม่มีวันได้ทำงาน

ลองยิงดู

เปิด Postman แล้วยิง POST /api/habits โดยไม่ส่ง Body อะไรเลย

{
  "error": "Validation failed",
  "details": [
    { "field": "", "message": "Invalid input: expected object, received undefined" }
  ]
}

ค่า field ว่างเพราะยังไม่มี Object เลย ไม่ใช่ว่า Field ไหนผิด ทีนี้ลองส่ง Object เปล่า {} ดูบ้าง

{
  "error": "Validation failed",
  "details": [
    { "field": "name", "message": "Invalid input: expected string, received undefined" }
  ]
}

ชัดมาก และเราได้มันมาฟรี ๆ แค่เขียน Schema กับส่งเข้า Middleware (เกร็ดที่มักพลาดกัน — Path คือ /api/habits มี s ต่อท้าย ถ้าลืมจะได้ Cannot POST /api/habit ซึ่งไม่เกี่ยวกับ Validation เลย)

validateParams — Route Parameter

ตัวถัดไปเหมือนกันแทบทุกตัวอักษร ต่างแค่ตรวจ req.params แทน

export const validateParams = (schema: ZodSchema) => {
  return (req: Request, res: Response, next: NextFunction) => {
    try {
      schema.parse(req.params)
      next()
    } catch (e) {
      if (e instanceof ZodError) {
        return res.status(400).json({
          error: 'Invalid params',
          details: e.issues.map((err) => ({
            field: err.path.join('.'),
            message: err.message,
          })),
        })
      }
      next(e)
    }
  }
}

ข้อแตกต่างสำคัญคือ เราไม่ยัดค่ากลับเข้า req.params เพราะอะไรก็ตามที่อยู่ใน URL เป็น String เสมอ ไม่มีทางหนีความจริงข้อนี้ได้ ไม่เหมือน Body ที่เป็น Object และแปลงชนิดข้อมูลได้ จึงไม่มีอะไรให้แก้ เรื่องนี้เป็นเหตุผลที่ผมไม่ชอบ ID แบบนับเลขเพิ่มขึ้นเรื่อย ๆ ใน Database เพราะสุดท้ายต้องมานั่ง Parse String เป็น Number ที่ไหนสักแห่งเสมอ ผมเลยเลือกใช้ UUID ซึ่งก็มีปัญหาของมันเองเรื่องความเร็วในการทำ Index แต่เป็นปัญหาที่ผมยอมรับได้

validateQuery — Query String

ตัวสุดท้ายตรวจ req.query ซึ่งก็คือ Object ที่มี Key เป็นชื่อตัวแปรใน Query String ตรงตามที่คุณคิดเลย

export const validateQuery = (schema: ZodSchema) => {
  return (req: Request, res: Response, next: NextFunction) => {
    try {
      schema.parse(req.query)
      next()
    } catch (e) {
      if (e instanceof ZodError) {
        return res.status(400).json({
          error: 'Invalid Query Params',
          details: e.issues.map((err) => ({
            field: err.path.join('.'),
            message: err.message,
          })),
        })
      }
      next(e)
    }
  }
}

ที่จริงเราเขียนทั้งสามตัวรวมเป็นฟังก์ชันเดียวแล้วส่งเข้าไปว่าจะตรวจ body, params หรือ query ก็ได้ ต่างกันแค่บรรทัดเดียวเอง แต่ผมอยากให้คุณเห็นมันสามรอบเต็ม ๆ จะได้จำโครงสร้างได้

ซ้อน Middleware หลายตัว

เราใส่ Middleware กี่ตัวก็ได้ในบรรทัดเดียวกัน มันจะเรียก next() ส่งไม้ต่อกันเองตามลำดับซ้ายไปขวา อย่าง Route POST /:id/complete ของเรามีทั้ง Parameter และ Body ก็ตรวจทั้งคู่ได้เลย

const completeParamsSchema = z.object({
  id: z.string().max(3),
})

router.post(
  '/:id/complete',
  validateParams(completeParamsSchema),
  validateBody(createHabitSchema),
  (req, res) => {
    res.status(201).json({ message: 'completed habit' })
  }
)

ลองยิง POST /api/habits/1/complete ดู ตัว Params จะผ่านสบาย ๆ เพราะ Express การันตีอยู่แล้วว่า id ต้องมีและเป็น String แต่พอยิง POST /api/habits/1234/complete จะติด .max(3) ทันที

มีคนแย้งว่าการตรวจ Params ดูซ้ำซ้อน ในเมื่อ Express การันตีให้อยู่แล้ว ซึ่งก็จริงในตัวอย่างง่าย ๆ แบบนี้ แต่Express ไม่ได้การันตีความยาว รูปแบบ หรือว่ามันเป็น UUID ที่ถูกต้องหรือเปล่า พอ Validation ของคุณซับซ้อนขึ้นมันจะคุ้มมาก

อีกลูกเล่นคือส่ง Middleware เป็น Array ก็ได้ เช่น router.post('/:id/complete', habitGuards, handler) เมื่อ habitGuards คือ Array ของ Middleware ประโยชน์คือเราแยกชุด Middleware ไปนิยามไว้อีกไฟล์แล้วเอามาใช้ซ้ำได้หลาย Route โดยไม่ต้องพิมพ์ใหม่ เหมือนทำให้ Middleware ของเราพกพาได้

สรุประดับของ Middleware

ตอนนี้เราเห็นครบทุกระดับแล้ว

  • Global — app.use(helmet()) อยู่บนสุดของแอปทั้งในเชิงตำแหน่งและเชิงความหมาย
  • Router-level — router.use(authenticate) ครอบทุก Route ในไฟล์ Router นั้น เราจะใช้จริงตอนล็อก Route ในบทที่ 24
  • Local / Route-level — เสียบไว้บนบรรทัดของ Route ตัวนั้นตัวเดียว อย่างที่เราเพิ่งทำ
  • ที่จริง Route เองก็คือ Middleware แค่มันไปจบที่ Route อื่นเท่านั้น

และถ้าจะพูดให้สุด Handler กับ Controller ก็คือ Middleware เพราะมันรับ next เป็นอาร์กิวเมนต์ที่สามได้เหมือนกัน เราแค่ไม่ใช้ — และผมแนะนำอย่างยิ่งว่าอย่าเรียก next() ใน Handler เพราะมันจะสับสนมาก ถ้าคุณรู้สึกว่าจำเป็นต้องทำ แปลว่าคุณเขียน Route ผิดที่แล้ว มีวิธีที่ดีกว่านั้นเสมอ

บทหน้าเราจะปิดท้ายเรื่อง Middleware ด้วยกับดักที่เจอบ่อยที่สุดเวลาโค้ดของเราเริ่มเป็น Async
