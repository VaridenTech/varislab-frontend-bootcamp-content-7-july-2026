Router และ Subrouter

ถึงเวลาสร้าง Routing ของแอปจริง ๆ แล้ว สิ่งแรกที่เราจะทำคือสร้าง Subrouter ซึ่งก็คือ Router ย่อยที่เราจะเอาไปแปะ (Mount) ไว้บน Router ตัวบนสุดอีกที

บทนี้เราจะเขียนแต่ตัว Router และ Route ก่อน ส่วนการเอาไปแปะกับ App เก็บไว้บทหน้า

ทำไมต้องมี Router

ถ้าเราเขียน Route ทุกตัวของทุก Resource ลงใน src/server.ts ไฟล์เดียว พอโปรเจกต์โตขึ้นไฟล์นั้นจะยาวเป็นพันบรรทัดและไม่มีใครกล้าแตะ Express จึงมี Router มาให้ ซึ่งให้ประโยชน์หลายอย่าง

  • จัดกลุ่ม — Route ที่เกี่ยวข้องกันอยู่ด้วยกัน หาง่าย แก้ง่าย
  • ใช้ซ้ำได้ — Router ตัวเดียวเอาไปแปะที่ Path ไหนก็ได้ หรือแปะหลายที่พร้อมกันก็ยังได้
  • กำหนดขอบเขต Middleware ได้ — เช่น สั่งให้ทุก Route ในไฟล์นี้ต้อง Login ก่อน โดยเขียนแค่บรรทัดเดียว (เราจะทำจริงในบทที่ 24)
  • แบ่งงานกันในทีมได้ — คนละคนดูแลคนละไฟล์ ลดโอกาส Conflict
  • ทดสอบง่ายขึ้น — แยกทดสอบทีละกลุ่มได้

สร้างโฟลเดอร์ src/routes

สร้างโฟลเดอร์ src/routes ขึ้นมา แล้วสร้างไฟล์หนึ่งไฟล์ต่อหนึ่ง Resource

src/routes/
├── authRoutes.ts
├── habitRoutes.ts
├── tagRoutes.ts
└── userRoutes.ts

เรื่องชื่อไฟล์ ขอให้เลือกแบบใดแบบหนึ่งแล้วใช้ให้เหมือนกันทั้งโปรเจกต์ ในคอร์สนี้เราใช้ userRoutes.ts ไม่ใช่ userRouter.ts ปนกันไปมา

ทุกไฟล์จะมีโครงเหมือนกันหมด คือ Import Router แบบ Named Import จาก Express แล้วเรียกใช้เพื่อสร้าง Router ของตัวเองขึ้นมาหนึ่งตัว

import { Router } from 'express'

const router = Router()

จากตรงนี้ เราใช้ router ได้เหมือนกับที่ใช้ app เลย มันมี .get(), .post(), .put(), .patch(), .delete() ครบเหมือนกันทุกตัว

authRoutes.ts

Route ชุดนี้ไม่ใช่ CRUD เต็มรูปแบบ เพราะ Auth ไม่ได้เป็น Resource แบบที่ User เป็น มันเป็นแค่กลไก สิ่งที่เราต้องการมีแค่สมัครสมาชิกกับเข้าสู่ระบบ

import { Router } from 'express'

const router = Router()

router.post('/register', (req, res) => {
  res.status(201).json({ message: 'user signed up' })
})

router.post('/login', (req, res) => {
  res.status(201).json({ message: 'user logged in' })
})

export default router

ตอนนี้เรายังไม่เขียนของจริง เราแค่ทำ Placeholder ไว้ก่อนเพื่อให้ยิงทดสอบได้ว่า Routing ทำงานถูกต้องหรือไม่ ส่วนตรรกะจริงจะมาเติมตอนทำ Controller ในบทที่ 21 เป็นต้นไป

เรื่อง Status Code คือถ้าไม่ระบุอะไร Express จะใช้ 200 ให้อัตโนมัติเมื่อเราส่ง Response ที่ไม่ใช่ Error ส่วน 201 แปลว่า "สร้างสำเร็จ" ซึ่งเป็นคู่หูของ POST ในทางปฏิบัติสองตัวนี้แทบไม่ต่างกัน แต่การใส่ให้ชัดทำให้ API ของเราสื่อสารได้ดีขึ้น ในโลกจริงคุณจะเห็นแค่ 200 กับ 201 เป็นหลัก ส่วนที่คนให้ความสำคัญจริง ๆ คือกลุ่ม 4xx เพราะมันคือสิ่งที่ผู้ใช้เห็นเวลาส่งข้อมูลผิด ตอนนี้ผมใส่ 201 ให้ Login ไปก่อนเพราะมันเป็นแค่ Placeholder เดี๋ยวตอนทำ Login จริงในบทที่ 23 เราจะเปลี่ยนมาใช้ 200 เพราะการเข้าสู่ระบบไม่ได้สร้างอะไรใหม่ขึ้นมา

สังเกตบรรทัดสุดท้าย export default router ถ้าลืมบรรทัดนี้ไฟล์อื่นจะ Import ไม่ได้เลย ให้นึกภาพว่า Module ก็คือ Closure และ Closure ก็คือ Function — Function ข้างนอกเอื้อมเข้าไปหยิบของข้างใน Function อื่นไม่ได้ นอกจากว่า Function นั้นจะ Return อะไรออกมาให้ การ Export ก็คือการ Return ของออกจากไฟล์นั่นเอง

habitRoutes.ts

อันนี้เป็น CRUD เต็มรูปแบบ

import { Router } from 'express'

const router = Router()

router.get('/', (req, res) => {
  res.json({ message: 'habits' })
})

router.get('/:id', (req, res) => {
  res.json({ message: 'got one habit' })
})

router.post('/', (req, res) => {
  res.status(201).json({ message: 'created habit' })
})

router.delete('/:id', (req, res) => {
  res.json({ message: 'deleted habit' })
})

router.post('/:id/complete', (req, res) => {
  res.status(201).json({ message: 'completed habit' })
})

export default router

จุดที่สำคัญที่สุดของไฟล์นี้คือ เราไม่ได้เขียน /habits ไว้ข้างหน้าเลยสักที่ เราเขียนแค่ / กับ /:id เท่านั้น นั่นเพราะ Path ใน Router เป็น Path สัมพัทธ์ ที่นับต่อจากจุดที่ Router ถูกเอาไปแปะ ซึ่งเราจะกำหนดกันในบทหน้า

ประโยชน์คือไฟล์นี้ไม่จำเป็นต้องรู้เลยว่าตัวมันเองจะไปอยู่ที่ URL ไหน มันจึงถูก Decouple ออกมาอย่างสมบูรณ์

Route ตัวสุดท้าย POST /:id/complete คือจุดที่เราแหกกฎ REST อย่างจงใจ เพราะการ "ทำ Habit สำเร็จ" ไม่ใช่การ Create หรือ Update ตรง ๆ มันเป็นคำสั่งให้ทำอะไรบางอย่างกับ Habit ตัวนั้น จำที่เราคุยกันไว้ได้ไหมว่า REST เป็นแค่ข้อตกลง ไม่มีใครบังคับ ถ้าการออกแบบแบบนี้อ่านเข้าใจง่ายกว่าก็ทำได้เลย

userRoutes.ts

ไฟล์นี้หน้าตาคล้ายไฟล์ก่อนหน้ามาก แต่แนะนำให้พิมพ์เองอีกรอบ การเขียนซ้ำคือวิธีที่ดีที่สุดวิธีหนึ่งในการจำโครงสร้าง

import { Router } from 'express'

const router = Router()

router.get('/', (req, res) => {
  res.json({ message: 'users' })
})

router.get('/:id', (req, res) => {
  res.json({ message: 'got user' })
})

router.put('/:id', (req, res) => {
  res.json({ message: 'user updated' })
})

router.delete('/:id', (req, res) => {
  res.json({ message: 'user deleted' })
})

export default router

สังเกตว่าเราไม่มี POST / สำหรับสร้าง User ทั้งที่ตำรา CRUD บอกว่าควรมี ลองคิดดูว่าจะมีใครสร้าง User โดยไม่ผ่านการสมัครสมาชิกในกรณีไหนบ้าง คำตอบคือกรณีที่มี Admin Dashboard ใช้ API ตัวเดียวกันแล้วอยากสร้าง User ให้เลย ซึ่งถ้ามีจริงก็ต้องใส่ระบบสิทธิ์กำกับให้แน่นหนา ในระบบปกติเราไม่ควรเปิด Route ที่ใครก็ได้สร้าง User ขึ้นมาโดยข้าม Business Logic ของ Authentication ทั้งหมด เพราะฉะนั้นเราจะไม่ใส่มัน

tagRoutes.ts

ในโค้ดตัวอย่างจะมีไฟล์ tagRoutes.ts ติดมาด้วย แต่เนื้อหาข้างในซ้ำกับที่เราเพิ่งทำไปเกือบทั้งหมด เราจึงยกให้เป็นการบ้านเสริม ใครอยากลองเขียน CRUD Routes ของ Tag เองก็ทำได้ และมันจะไม่กระทบกับบทเรียนที่เหลือ

ข้อควรระวังที่เจอบ่อยที่สุด

  • ลืม export default router — เขียน Route ครบสวยงามแล้วแต่ Import ไปใช้ไม่ได้ ข้อนี้เกิดขึ้นกับทุกคน
  • ลืมใส่ Handler — เขียน router.get('/users') เฉย ๆ หรือส่ง undefined เข้าไป Express จะโยน Error ออกมาบอกทันทีตอนสตาร์ท ซึ่งถือว่าดีเพราะเรารู้ตัวเร็ว
  • ลำดับ Route ผิด — เรื่องนี้สำคัญมากจนต้องคุยกันยาวในบทหน้า

ตอนนี้เรามี Router สามตัวที่พร้อมใช้งานแล้ว แต่ถ้าลองรัน npm run dev แล้วยิงไปที่ /api/habits จะยังได้ 404 อยู่ เพราะ App ของเรายังไม่รู้จัก Router พวกนี้เลย บทหน้าเราจะเอามันไปแปะเข้ากับ App กัน
