Database Migrations

เรารู้จัก Git กันทุกคนใช่ไหม Database เองก็มี Version Control ของตัวเองเหมือนกัน มันเรียกว่า Migration และผมจะบอกตรง ๆ ตั้งแต่ตอนนี้เลยว่ามันน่าปวดหัว

ผมเขียนโค้ดมาสิบห้าปี และเพิ่งจะเข้าใจ Migration แบบทะลุปรุโปร่งเมื่อสองปีที่แล้วนี่เอง เพราะฉะนั้นถ้าคุณอ่านบทนี้แล้วยังงง ๆ ไม่ต้องคิดว่าตัวเองโง่ ผมจะย่อยมันลงมาให้เหลือเท่าที่ต้องรู้จริง ๆ

Database คือสัญญา

ทำไมเราต้องทำ Version ให้ Database ด้วย ลองนึกว่า Database คือสัญญา ที่เราไปประกาศกับทุกคนว่า "ข้อมูลของผมจะหน้าตาแบบนี้ตลอดไป รับรอง เอาไปสร้างแอปได้เลย"

คนก็เชื่อ แล้วก็ไปสร้างแอปกันใหญ่ วันดีคืนดีเรากลับมาบอกว่า "ผมขอเปลี่ยนหน้าตาข้อมูลนิดหน่อยนะ" ทุกคนก็จะร้องว่าแล้วโค้ดที่เขียนไปทั้งหมดจะทำยังไง จะให้ไปใส่ if เช็คทีละเวอร์ชันเหรอ ซึ่งฟังดูแล้วไม่ไหวเลย นั่นแหละคือช่องว่างที่ Migration เข้ามาเติม

หน้าที่ของ Migration คือย้ายสถานะเดิมของ Database ไปสู่สถานะใหม่ที่เราต้องการ และคำว่าย้ายมีสองชั้นเสมอ

  • Schema Migration — ย้ายตัวสัญญา คือโครงสร้างตาราง คอลัมน์ Index และ Constraint
  • Data Migration — ย้ายข้อมูลเก่าที่อยู่ใต้สัญญาฉบับเดิม ให้มาอยู่ใต้สัญญาฉบับใหม่ได้

ชั้นที่สองนี่แหละคือส่วนที่น่ากลัว เพราะเรากำลังยุ่งกับข้อมูลจริงของคนจริง ถ้าทำพังแล้วไม่มี Backup ก็คือจบ กู้ไม่ได้

ถ้าไม่มี Migration จะเกิดอะไรขึ้น

สิ่งที่จะเกิดคือ Database ไปอยู่เวอร์ชันใหม่ แต่โค้ดของเรายังอยู่เวอร์ชันเก่า มันจะพังแน่นอน อาจพังที่ Server ตอน Query อาจพังที่ Client ตอนอ่านผลลัพธ์ แต่ยังไงก็ต้องพังสักที่

อาการนี้เหมือนตอนที่ Package ใน node_modules ขยับเวอร์ชันแล้วโค้ดเราใช้ไม่ได้ ต่างกันแค่ว่าคราวนี้เราแก้ด้วยการ Rollback เวอร์ชันไม่ได้ เพราะข้อมูลจริงถูกแก้ไปแล้ว

และถ้าจะบอกว่า "โค้ดผมเขียนแบบยืดหยุ่นไว้แล้ว ไม่พังหรอก" ผมขอถามกลับว่าถ้ายืดหยุ่นขนาดนั้น แสดงว่าโค้ดคุณเต็มไปด้วย if กับค่า Default เต็มไปหมดใช่ไหม ซึ่งนั่นก็ไม่ใช่ทางที่เราอยากไปอยู่ดี

เวิร์กโฟลว์มาตรฐาน

สมมติว่าเรามี Database บน Production ที่มีคนใช้อยู่จริงแล้ว ขั้นตอนปกติจะเป็นแบบนี้

  1. Develop — แก้ Schema ในโค้ดก่อน
  2. Generate — สร้างไฟล์ Migration ขึ้นมา จะเขียนมือเองหรือให้เครื่องมือสร้างให้ก็ได้
  3. Review — อ่าน SQL ที่ถูกสร้างขึ้นให้ละเอียดก่อน เหมือนเรารีวิว PR ก่อนกด Merge เข้า Main
  4. Apply — รัน Migration ใส่ Database
  5. Deploy — ทำแบบเดียวกันบน Production แต่ควรทดสอบบน Staging ให้ผ่านก่อนเสมอ

คนส่วนใหญ่ทำแบบนี้ แต่ผมไม่ทำแบบนี้ทุกครั้ง ผมไม่ชอบ วิธีเลี่ยงมีอยู่ ไม่ใช่การเลี่ยงทั้งหมดหรอก แต่ทำให้เหลือน้อยที่สุดได้ ซึ่งเราจะได้เห็นกันจริง ๆ ตอนใช้ Drizzle

หัวใจที่สุดของบทนี้: Destructive กับ Non-destructive

ไม่ใช่ทุกการเปลี่ยนแปลงที่เจ็บเท่ากัน ถ้าจับจุดนี้ได้ ชีวิตคุณจะง่ายขึ้นทันที

Non-destructive Change คือการเพิ่มของใหม่ที่ไม่บังคับ เช่นเพิ่มคอลัมน์ใหม่ที่เป็น Optional มันปลอดภัยเพราะยังไม่มีใครเขียนโค้ดใช้มัน และเพราะไม่บังคับ เราจึงไม่ต้องไปใส่ค่า Default ให้ข้อมูลเก่าเลยสักแถว แปลว่าไม่ต้องทำ Data Migration

Destructive Change คือการลบหรือแก้ของเดิม และตัวที่คนพลาดบ่อยที่สุดคือการเปลี่ยนชื่อคอลัมน์ เพราะถ้าคิดให้ดี การเปลี่ยนชื่อคือสองงานซ้อนกัน คือลบของเก่าแล้วสร้างของใหม่ที่ชื่อไม่เหมือนเดิม คนที่พึ่งพาคอลัมน์เดิมอยู่ก็พังทันที

ทางออกคือแตกงานเดียวออกเป็นสองรอบ

  1. เพิ่มคอลัมน์ใหม่ที่ชื่อและชนิดที่เราต้องการ ตั้งให้เป็น Optional แล้ว Deploy ขึ้นไปเลย รอบนี้ปลอดภัยร้อยเปอร์เซ็นต์
  2. ส่ง PR อีกใบที่ย้ายโค้ดทั้งหมดมาใช้คอลัมน์ใหม่ พร้อม Data Migration ที่ก๊อปข้อมูลจากคอลัมน์เก่ามาใส่คอลัมน์ใหม่ ซึ่งเป็น Data Migration ที่ง่ายที่สุดเท่าที่จะเป็นไปได้ เพราะชนิดข้อมูลเหมือนกันเป๊ะ

ผลคือไม่มี Downtime เลย ใช่ มันคือ PR สองใบแทนที่จะเป็นใบเดียว และต้องไล่ผ่าน Development ไป Staging ไป Production สองรอบ แต่ผมยอมทำสองรอบมากกว่าจะเสี่ยงพัง Production หนึ่งรอบ

เพื่อให้เห็นภาพว่า Data Migration แบบดิบ ๆ หน้าตาเป็นอย่างไร นี่คือตัวอย่างการเปลี่ยนโครงสร้างที่มีทั้งสองชั้นปนกัน

-- ขั้นที่ 1 (Schema) เพิ่มคอลัมน์ใหม่แบบไม่บังคับ
ALTER TABLE habits ADD COLUMN frequency VARCHAR(20);

-- ขั้นที่ 2 (Data) เติมค่าให้ข้อมูลเก่าจากคอลัมน์เดิม
UPDATE habits SET frequency =
  CASE
    WHEN target_days_per_week = 7 THEN 'daily'
    WHEN target_days_per_week BETWEEN 3 AND 6 THEN 'weekly'
    ELSE 'monthly'
  END;

-- ขั้นที่ 3 (Schema) ค่อยบังคับให้ต้องมีค่า
ALTER TABLE habits ALTER COLUMN frequency SET NOT NULL;

-- ขั้นที่ 4 (Schema) ทิ้งคอลัมน์เก่า
ALTER TABLE habits DROP COLUMN target_days_per_week;

ผมยกมาให้ดูเพื่อให้กลัวไว้ก่อน เราจะไม่เขียน SQL แบบนี้เองในคอร์สนี้ Drizzle จะสร้างให้เรา แต่คุณควรอ่านมันออกเวลาที่ต้องรีวิว

เหตุผลจริง ๆ ที่ผมย้ายจาก Prisma มา Drizzle

บทที่แล้วผมค้างเรื่องนี้ไว้ ตอนนี้อธิบายได้แล้ว

Prisma ต้อง Generate Client ขึ้นมาเพื่อให้ได้ Type ที่ถูกต้อง แต่พอเป็นเรื่อง Migration มันมีปัญหา เพราะ Migration ทำงานโดยไล่รันทุกไฟล์ตามลำดับที่มันถูกสร้าง ตั้งแต่ไฟล์แรกจนถึงไฟล์ล่าสุด

ทีนี้ถ้าเรามีแต่ Prisma Schema ฉบับล่าสุดฉบับเดียว แล้วเราจะเอา Schema ของ Migration ตัวก่อน ๆ มาจากไหน คำตอบคือไม่มี สุดท้ายเลยต้องมานั่งเขียน Migration เป็น SQL ดิบเอง ซึ่งผมไม่เอาด้วย ผมเลยย้ายมา Drizzle ที่เป็น TypeScript ล้วน ไม่มี DSL ไม่มีขั้นตอน Code Generation และ Query ที่ออกมาเดาได้

drizzle-kit ตามรอยการเปลี่ยนแปลงอย่างไร

Drizzle ไม่ได้เป็นแค่ ORM มันมาพร้อม CLI ชื่อ drizzle-kit ที่ดูแลงานฝั่ง Migration ให้ วิธีที่มันตามรอยคือเก็บ Snapshot ของ Schema ไว้ทุกครั้งที่เรา Generate

เวลาเราสั่ง Generate มันจะเทียบ Schema ปัจจุบันในโค้ดกับ Snapshot ล่าสุดที่มันเก็บไว้ แล้วสรุปว่ามีอะไรต่างกันบ้าง จากนั้นเขียนไฟล์ SQL ออกมาหนึ่งไฟล์พร้อม Snapshot ใหม่ ทั้งคู่ถูกเก็บลงโฟลเดอร์ migrations ซึ่งเรา Commit ขึ้น Git นั่นแปลว่าประวัติของ Database อยู่ในที่เดียวกับประวัติของโค้ด และทีมทุกคนได้ไฟล์ชุดเดียวกัน

เวลาเราสั่ง Migrate มันจะไปดูว่า Database ตัวนั้นรันไฟล์ไหนไปแล้วบ้าง แล้วรันเฉพาะไฟล์ที่ยังค้างอยู่ตามลำดับ

แต่ Drizzle ยังมีอีกทางเลือกหนึ่งที่ชื่อว่า Push ซึ่งเป็นทางที่เราจะใช้บ่อยที่สุดตอนพัฒนา วิธีจำความต่างที่ง่ายที่สุดคือเทียบกับ Git

  • Generate แล้ว Migrate เหมือนการเปิด PR แล้วรีวิวก่อนค่อย Merge เข้า Main มีร่องรอยเก็บไว้ทุกขั้น เหมาะกับ Production
  • Push เหมือนการ Push ตรงเข้า Main ไม่สนว่าในนั้นมีอะไร เอา Schema ปัจจุบันยัดเข้า Database ให้ตรงกันเดี๋ยวนี้ ไม่มีไฟล์ Migration เกิดขึ้น

Push บน Production คือหายนะ แต่บนเครื่องเราเองมันคือสวรรค์ เพราะ Database ตัวนั้นเป็นของเราคนเดียว ข้อมูลข้างในเป็นข้อมูลปลอมที่ Seed ขึ้นมาเอง จะพังก็ Seed ใหม่

เวิร์กโฟลว์ที่เราจะใช้จริงในคอร์สนี้จึงเป็นแบบนี้ ตอนพัฒนาให้แก้ Schema แล้ว Push รัว ๆ กี่รอบก็ได้ พอฟีเจอร์เสร็จพร้อมเปิด PR แล้วค่อย Generate ครั้งเดียว ให้ได้ไฟล์ Migration ไฟล์เดียวที่รวมทุกการเปลี่ยนแปลง ไม่ใช่หกไฟล์จากหกครั้งที่เราเปลี่ยนใจ เพราะ PR ที่มี Migration หกไฟล์ไม่มีใครกล้า Merge ให้หรอก

แผนที่ข้อมูลของ Habit Tracker

ก่อนจบบท มาดูหน้าตาข้อมูลที่เราจะสร้างกันในบทหน้า เรามีห้าตาราง

  • users — ผู้ใช้
  • habits — Habit ที่ผู้ใช้ตั้งไว้ มี Foreign Key ชี้ไปหา users
  • entries — บันทึกว่าทำ Habit นั้นสำเร็จเมื่อไร มี Foreign Key ชี้ไปหา habits
  • tags — ป้ายกำกับ เช่น Health หรือ Learning
  • habit_tags — ตารางเชื่อมระหว่าง habits กับ tags

สองความสัมพันธ์แรกเป็น One-to-Many ทั้งคู่ User หนึ่งคนมีได้หลาย Habit และ Habit หนึ่งอันมีได้หลาย Entry ตามกฎที่เราคุยกันไปแล้ว Foreign Key จึงไปอยู่ฝั่ง Many เสมอ

ส่วน habits กับ tags เป็น Many-to-Many คือ Habit หนึ่งอันติดได้หลาย Tag และ Tag หนึ่งอันก็ไปเกาะได้หลาย Habit กรณีแบบนี้เราไม่แปะ Foreign Key ใส่กันตรง ๆ แต่สร้างตารางกลางขึ้นมาอีกหนึ่งตาราง ซึ่งก็คือ habit_tags หน้าที่ของมันคือเก็บ Foreign Key ของทั้งสองฝั่งไว้คู่กันเท่านั้น อยากรู้ว่า Tag นี้มี Habit อะไรบ้าง ก็ Query ตารางนี้ด้วย tag_id แล้วเอา habit_id ที่ได้ไปดึงตัวจริงต่อ

บทหน้าเราจะลงมือเขียน Schema ทั้งห้าตารางนี้ด้วย Drizzle กันจริง ๆ
