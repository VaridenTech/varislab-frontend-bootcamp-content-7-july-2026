สรุปทบทวนเนื้อหาทั้งหมด

มาถึงบทสุดท้ายแล้วครับ ตอนนี้ Habit Tracker API ของเราขึ้น Production ไปเรียบร้อย มีคนอื่นยิงเข้ามาใช้ได้จริง ก่อนจะปิดคอร์ส มาไล่ดูกันอีกรอบว่าเราผ่านอะไรมาบ้าง

สิ่งที่อยากให้สังเกตคือทุกบทมันต่อกันเป็นเส้นเดียว เราไม่ได้เรียนหัวข้อกระจัดกระจาย แต่เราเริ่มจาก Server เปล่า ๆ แล้วค่อย ๆ ประกอบชิ้นส่วนขึ้นมาจนกลายเป็น API ที่ใช้งานได้จริงหนึ่งตัว

Server และเครื่องมือพื้นฐาน

  • Node.js ทำให้ JavaScript รันนอก Browser ได้ พอเปลี่ยนมาอยู่ฝั่ง Server มุมมองก็เปลี่ยนจาก "คนเรียก" เป็น "คนรับ" — เราคือคนที่ต้องคอยฟัง Request แล้วตัดสินใจว่าจะตอบอะไรกลับไป
  • เราสร้าง Server ด้วย http Module ล้วน ๆ ได้ แต่พอต้องแยก Path แยก Method เอง โค้ดจะบวมเร็วมาก นั่นคือช่องว่างที่ Express เข้ามาเติม
  • เราตั้งโปรเจกต์ TypeScript แล้วแยกไฟล์เป็นสองส่วนตั้งแต่วันแรก คือ src/server.ts ที่ประกอบ App กับ src/index.ts ที่สั่ง listen การแยกนี้ดูเกินจำเป็นในตอนนั้น แต่มันคือเหตุผลที่บทที่ 30 เราเขียน Test ได้โดยไม่ต้องเปิด Server จริง
  • เราใช้ Postman เป็นเครื่องมือคุยกับ API ทั้งการยิง Request ทุก Method อ่าน Status Code กับ Body ที่ได้กลับมา และเก็บ Request ไว้ใช้ซ้ำใน Collection

Environment Variables

  • ค่าที่เปลี่ยนไปตามสภาพแวดล้อมและค่าที่เป็นความลับต้องอยู่นอกโค้ดเสมอ เราอ่านมันผ่าน process.env โดยมีไฟล์ .env เป็นแหล่งค่าบนเครื่องเรา ซึ่ง ห้ามขึ้น Git เด็ดขาด และใช้ .env.example เป็นคู่มือบอกทีมว่าต้องมีตัวแปรอะไรบ้าง
  • process.env แบบดิบ ๆ เป็น string | undefined เสมอ เราจึงห่อมันด้วย Zod ในไฟล์ env.ts แล้วสร้าง Type ออกมาด้วย z.infer ได้ทั้งการตรวจค่าและ Type Safety ในคราวเดียว
  • หลักคิดสำคัญคือ Fail Fast — ถ้าตัวแปรขาดหรือผิดรูปแบบ ให้แอปตายตั้งแต่ตอนเริ่มทำงานพร้อมบอกว่าตัวไหนผิด ดีกว่าปล่อยให้ไปพังกลางทางตอนมีผู้ใช้จริง (ซึ่งเราได้เห็นของจริงตอน Deploy ในบทที่ 31)

REST และ Routing

  • HTTP Verb ห้าตัวที่ใช้บ่อยคือ GET, POST, PUT, PATCH และ DELETE ซึ่งจับคู่กับงาน CRUD ได้ตรง ๆ ส่วน REST คือข้อตกลงที่ทำให้ทุกคนเดา Route ของกันและกันได้ถูก
  • Express ให้ข้อมูลจาก Client มาสามทาง คือ Route Parameter (req.params), Query String (req.query) และ Body (req.body)
  • เราแยก Route ออกเป็นไฟล์ในโฟลเดอร์ src/routes/ ด้วย express.Router() ได้แก่ authRoutes.ts, habitRoutes.ts, userRoutes.ts และ tagRoutes.ts แล้ว Mount เข้า App ด้วย app.use('/api/habits', habitRoutes)
  • Path จริงเกิดจาก Mount Path + Route Path และ ลำดับการลงทะเบียนสำคัญเสมอ Express จะไล่จากบนลงล่างแล้วหยุดที่ตัวแรกที่ตรง ดังนั้น Route ที่เฉพาะเจาะจงต้องมาก่อน Route ที่มี Parameter

Middleware และ Validation

  • Middleware คือฟังก์ชันที่รับ (req, res, next) แล้วยืนขวางอยู่ระหว่าง Request กับ Handler มันจะอ่าน แก้ไข ตอบกลับเลย หรือส่งต่อด้วย next() ก็ได้ กฎเหล็กคือ ถ้ายังไม่ตอบ ต้องเรียก next() ไม่งั้น Request จะค้าง
  • Global Middleware ที่เราติดตั้งไว้ใน src/server.ts ได้แก่ helmet() สำหรับ Security Header, cors() สำหรับอนุญาต Origin, express.json() ที่ทำให้ req.body ใช้งานได้, express.urlencoded() และ morgan สำหรับ Log
  • เราเขียน Validation Middleware ของตัวเองใน src/middleware/validation.ts เป็น Higher-Order Function คือ validateBody, validateParams และ validateQuery ที่รับ Zod Schema เข้าไปแล้วคืน Middleware ออกมา เสียบใช้กับ Route ไหนก็ได้
  • กับดักของ Async Middleware ที่ต้องระวังคือลืม next(), เรียงลำดับผิด, ไม่จัดการ Error ของ Promise และการแตะ Response หลังส่ง Header ไปแล้ว

Database

  • เราออกแบบ Schema โดย เริ่มจาก Feature ไม่ใช่เริ่มจากตาราง แล้วจึงได้ตารางห้าตัวคือ users, habits, entries, tags และ habit_tags ที่เป็นตัวเชื่อมความสัมพันธ์แบบ Many-to-Many
  • เราเลือก PostgreSQL กับ Prisma ORM ที่เขียน Schema ด้วย DSL อ่านง่ายในไฟล์ schema.prisma แล้ว Generate Client ที่มี Type ครบทุกตาราง พร้อมประกาศความสัมพันธ์ด้วย @relation
  • Migration คือประวัติการเปลี่ยนแปลงของ Database เราใช้ db:push ได้เฉพาะกับเครื่องเราเท่านั้น ส่วนที่อื่นต้อง db:migrate เพื่อสร้างไฟล์ Migration แล้ว db:deploy เสมอ และต้องแยกให้ออกว่าการเปลี่ยนแปลงไหน Destructive ไหน Non-destructive
  • เราได้ Type ของทุกตารางฟรีจาก Generated Client (รวบไว้ใน src/db/types.ts) และเขียน Zod Schema ใน src/db/validation.ts ให้ล้อกฎของตารางเป๊ะ ๆ เพื่อให้กฎของ Database กับกฎของ Validation เดินไปด้วยกันเสมอ
  • เราใช้ Neon เป็น PostgreSQL บนคลาวด์ เชื่อมต่อผ่าน Connection Pool ของ @prisma/adapter-pg ใน src/db/connection.ts ส่องข้อมูลด้วย Prisma Studio และเติมข้อมูลตัวอย่างด้วย src/db/seed.ts

Authentication และ Authorization

  • สามคำที่ต้องแยกให้ออกคือ Identity (คุณคือใคร), Authentication (พิสูจน์ว่าคุณคือคนนั้นจริง) และ Authorization (คุณทำสิ่งนี้ได้ไหม) ซึ่งสะท้อนออกมาเป็น Status Code 401 กับ 403 คนละความหมาย
  • เราเลือกใช้ JWT เพราะมันเป็น Stateless เราเขียน generateToken กับ verifyToken ไว้ใน src/utils/jwt.ts ใส่เฉพาะข้อมูลที่ไม่เป็นความลับลงใน Payload และตั้งวันหมดอายุเสมอ
  • รหัสผ่านต้องผ่าน bcrypt เท่านั้น เพราะ Hash เป็นทางเดียว มี Salt อยู่ในตัว Hash เอง และ bcrypt.compare เทียบแบบ Constant Time เพื่อกัน Timing Attack — ทั้งหมดอยู่ใน src/utils/password.ts
  • เราสร้าง src/controllers/authController.ts ให้ครบทั้งสมัครสมาชิกและเข้าสู่ระบบ โดยตอบ 401 ด้วยข้อความเดียวกันไม่ว่าอีเมลผิดหรือรหัสผ่านผิด และไม่ส่ง Object ของ User ทั้งก้อนกลับไป
  • src/middleware/auth.ts อ่าน Token จาก Header ตาม Bearer Token Pattern ตรวจสอบแล้วแปะข้อมูล User ไว้บน req ให้ Handler ถัดไปใช้ต่อ เราเสียบมันที่ระดับ Router เพื่อล็อกทั้งกลุ่ม Route ในบรรทัดเดียว
  • เรื่อง Security ที่ต้องติดหัวไว้คือห้าม Log Token, อย่าใช้ Secret ร่วมกันระหว่าง Development กับ Production, ใช้ HTTPS เสมอ, ตั้งอายุ Token ให้สมเหตุสมผล และห้ามเชื่อข้อมูลจากฝั่ง Client

CRUD และ Error Handling

  • เราเขียน src/controllers/habitController.ts ครบทั้งสี่ตัว โดยแต่ละตัวหน้าตาเหมือนกันหมด คือรับข้อมูลที่ผ่าน Validation มาแล้ว คุยกับ Database แล้วตอบด้วย Status Code ที่ถูกต้อง (201 ตอนสร้าง, 200 ตอนอ่านและแก้ไข, 404 เมื่อไม่เจอ)
  • Error Handler ของ Express คือ Middleware ที่มี สี่อาร์กิวเมนต์ คือ (err, req, res, next) ต้องลงทะเบียนไว้ล่างสุดเสมอ และ Error จะเดินทางไปหามันได้ก็ต่อเมื่อเราส่งผ่าน next(err)
  • เรามีตาข่ายรับ Error หลายชั้น ตั้งแต่ errorHandler.ts, ตัวจับ Route ที่ไม่มีอยู่จริงที่ตอบ 404 ไปจนถึงตัวจับระดับ Node.js อย่าง uncaughtException

การทดสอบ

  • เราใช้ Vitest คู่กับ SuperTest ซึ่งยิง Request เข้า App ของเราได้โดยไม่ต้องเปิด Port จริง Middleware ทุกตัวทำงานครบเหมือน Request จริงทุกประการ
  • สิ่งแรกที่ต้องทำก่อนเขียน Test คือ แยก Database สำหรับ Test ออกมาต่างหาก ผ่าน .env.test แล้วล้างข้อมูลด้วย Helper ใน afterEach เพื่อให้ Test แต่ละตัวเป็นอิสระต่อกัน
  • สำหรับ API แล้ว Integration Test คุ้มที่สุด เพราะยิงทีเดียวได้ทดสอบทั้ง Route, Middleware, Controller และ Database ไปพร้อมกัน และเราเขียน Test เพื่อความมั่นใจ ไม่ใช่เพื่อไล่ตามตัวเลข Coverage

การ Deploy

  • ก่อน Deploy ต้องเตรียม Production Database แยกอีกตัว รัน Migration เข้าไป ทำให้ Port เป็น Dynamic เตรียม Environment Variables ชุดใหม่ ไล่เก็บ URL ที่ Hardcode ไว้ และระบุเวอร์ชัน Node ผ่าน Field engines
  • บน Render เราสร้าง Web Service ที่ผูกกับ Repository บน GitHub ใส่ Environment Variables ในหน้า Dashboard ตั้ง Health Check Path เป็น /health แล้วเปิด Auto-Deploy ไว้
  • จากนั้นทุกครั้งที่โค้ดเข้า Branch ที่ผูกไว้ Render จะ Deploy ให้เอง ส่วนการรัน Test ก่อน Deploy เป็นงานของ CI ซึ่งต้องเสริมด้วยเครื่องมืออย่าง GitHub Actions

ตอนนี้คุณสร้างอะไรได้แล้วบ้าง

ถ้ามองภาพรวม คุณสร้าง Backend ที่ครบวงจรของแอปหนึ่งตัว ได้แล้วครับ คือมีระบบสมาชิกที่ปลอดภัย มีข้อมูลของแต่ละคนที่คนอื่นแตะไม่ได้ มีการตรวจข้อมูลก่อนบันทึก มีการจัดการ Error ที่เป็นระบบ มี Test คอยเฝ้า และมีที่อยู่บนอินเทอร์เน็ตจริง

เปลี่ยนจาก Habit เป็น Task, Post, Order หรือ Booking โครงสร้างก็ยังเป็นชุดเดิมทั้งหมด นี่คือสิ่งที่ทำให้ความรู้ชุดนี้ใช้ต่อได้กับแทบทุกโปรเจกต์ และมันคือฝั่งที่รอ Frontend มาเชื่อมต่อพอดี

ก้าวต่อไป

เมื่อเข้าใจ REST API ดีแล้ว โลกฝั่ง Backend ยังมีอีกหลายเส้นทางให้เดินต่อ

  • GraphQL — Query Language สำหรับ API ที่ให้ Client ขอข้อมูลเท่าที่ต้องการผ่าน Endpoint เดียว เกิดมาเพื่อแก้ปัญหา Over-fetching และ Under-fetching ของ REST เหมาะกับงานที่มี Client หลายแบบและข้อมูลซ้อนกันหลายชั้น
  • gRPC และ Protocol Buffers — โปรโตคอลแบบ Binary ที่เร็วและเล็กกว่า JSON มาก มี Contract ที่มี Type ชัดเจนระหว่างบริการ นิยมใช้คุยกันระหว่าง Microservice
  • Serverless — เขียนเป็นฟังก์ชันแล้วให้ผู้ให้บริการจัดการ Server ให้ทั้งหมด เช่น AWS Lambda หรือ Vercel Functions ได้ Auto-scaling และจ่ายตามการใช้งานจริง แลกกับ Cold Start และการผูกกับผู้ให้บริการ
  • Edge Functions — รันโค้ดที่จุดกระจายสัญญาณใกล้ผู้ใช้ที่สุด เช่น Cloudflare Workers หรือ Deno Deploy เหมาะกับงานอย่างการตรวจสิทธิ์ การ Redirect หรือ Rate Limiting
  • WebSockets — เปิดการเชื่อมต่อค้างไว้ให้คุยกันได้สองทาง ต่างจาก HTTP ที่เป็น Request/Response เหมาะกับ Chat, การทำงานร่วมกันแบบ Real-time, เกม และข้อมูลที่อัปเดตตลอดเวลา
  • Docker และ Kubernetes — แพ็กแอปพร้อม Dependency ทั้งหมดไว้ใน Container ให้รันที่ไหนก็เหมือนกัน แล้วให้ Kubernetes ดูแลเรื่อง Scaling, การกู้คืนอัตโนมัติ และการอัปเดตแบบไม่มี Downtime
  • CI/CD ด้วย GitHub Actions — ก้าวต่อไปที่ใกล้ตัวที่สุดจากบทที่แล้ว ตั้งให้รัน Test และ Linter ทุกครั้งที่มี Push หรือ Pull Request แล้วค่อยปล่อย Deploy เมื่อทุกอย่างผ่าน

ขอบคุณที่เรียนมาจนจบครับ ของที่ดีที่สุดที่จะทำต่อจากนี้คือหยิบไอเดียแอปสักตัวที่คุณอยากใช้เองจริง ๆ แล้วสร้าง API ของมันขึ้นมาตามเส้นทางเดียวกับที่เราเพิ่งเดินผ่านมาด้วยกัน
