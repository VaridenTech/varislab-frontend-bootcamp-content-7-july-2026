การ Seed ข้อมูลลงฐานข้อมูล

เรามีตารางครบแล้วแต่ยังว่างเปล่า บทนี้เราจะเขียน Seed Script ซึ่งก็คือไฟล์ที่รันแล้วใส่ข้อมูลลง Database ให้เรา

ทำไมต้อง Seed

Seed ไม่ได้แปลว่าข้อมูลปลอมเสมอไป มันคือการเติมข้อมูลลงฐานข้อมูลเพื่อให้เราทำงานต่อได้ ซึ่งมีหลายสถานการณ์

  • ทำฟีเจอร์ที่ต้องพึ่งความสัมพันธ์ — บางฟีเจอร์เขียนไม่ได้เลยถ้าไม่มีข้อมูลที่เชื่อมโยงกันอยู่จริง
  • งานฝั่ง Frontend — ถ้าคุณทำ Full-stack แล้วอยากเริ่มจากหน้าจอก่อน คุณจะ Mock ข้อมูลบนหน้าบ้านก็ได้ แต่เดี๋ยวต้องกลับมารื้อใส่ Logic การยิง Network ทีหลังอยู่ดี สู้ต่อหลังบ้านให้ครบแล้ว Seed ข้อมูลปลอมลงไปเลยดีกว่า จากมุมของหน้าบ้านมันไม่มีทางรู้เลยว่าข้อมูลนั้นปลอม เพราะรูปร่างเหมือนกันทุกอย่าง
  • ทุกคนในทีมได้ข้อมูลชุดเดียวกัน — คนเข้าใหม่โคลนโปรเจกต์ รัน Seed แล้วทำงานได้เลย
  • ไล่ปัญหา — บางทีเราอยากดึงข้อมูลรูปแบบเดียวกับที่ Production มีลงมาไว้บนเครื่อง เพื่อทำซ้ำอาการที่ผู้ใช้เจอ

วิธีสร้างข้อมูลก็มีหลายทาง จะใช้ Library อย่าง Faker สร้างข้อมูลปลอมเป็นร้อยแถวก็ได้ จะเลือกเขียนข้อมูลเองทีละตัวให้ตรงกับสถานการณ์ที่อยากทดสอบก็ได้ หรือจะ Export ข้อมูลจาก Database อีกตัวมา Import ก็ได้ ซึ่งฐานข้อมูลส่วนใหญ่มีความสามารถนี้ติดมาให้อยู่แล้ว ของเราจะเขียนเองแบบง่าย ๆ

ก่อนไปต่อ ขอเตือนหนึ่งข้อ ห้ามรัน Seed Script ใส่ Database ของ Production เด็ดขาด เพราะสิ่งแรกที่มันจะทำคือล้างข้อมูลทิ้ง

จริง ๆ แล้วคุณไม่ควรมี Credential ของ Production อยู่บนเครื่องตัวเองตั้งแต่แรกด้วยซ้ำ ถ้าบังเอิญมี ให้ถามตัวเองว่าใครให้มาและทำไมถึงให้ได้ บริษัทส่วนใหญ่จะไม่ให้ใครเข้าถึง Production Database ง่าย ๆ อยู่แล้ว มีทีมดูแลเรื่องนี้โดยเฉพาะทั้งด้วยเหตุผลทางกฎหมายและทางเทคนิค ผมเองก็เคยเผลอลบ Database ของ Production เพราะนึกว่าเป็นของตัวเองมาแล้ว โชคดีที่ Neon สำรองข้อมูลถี่มากจนกดกู้กลับมาได้ แต่ก็ไม่อยากให้ใครต้องเจอ

เขียน src/db/seed.ts

สร้างไฟล์ src/db/seed.ts เริ่มจาก Import และโครงของ Function

import { prisma } from './connection.ts'

const seed = async () => {
  console.log('🌱 Starting database seed...')

  try {
    // โค้ดทั้งหมดของเราจะอยู่ในนี้
  } catch (e) {
    console.error('❌ seed failed', e)
    process.exit(1)
  }
}

ผมชอบ Log เยอะ ๆ ใน Seed Script เพราะเวลารันแล้วพัง เราจะรู้ทันทีว่าพังตรงขั้นไหน และการครอบด้วย try/catch ทำให้เราคุมได้ว่าจะจบยังไงตอนมีปัญหา

ล้างข้อมูลเดิมก่อน และลำดับสำคัญมาก

console.log('Clearing existing data...')
await prisma.entry.deleteMany()
await prisma.habitTag.deleteMany()
await prisma.habit.deleteMany()
await prisma.tag.deleteMany()
await prisma.user.deleteMany()

สังเกตหน้าตาของ Prisma Client ก่อน — ทุกตารางกลายเป็น Property บน prisma ในชื่อเดียวกับ Model (ตัวเล็ก) แล้วมี Method ให้เลือกใช้ deleteMany() ที่ไม่ใส่เงื่อนไขอะไรเลยแปลว่า "ลบทุกแถวในตารางนี้"

เราล้างก่อนเพื่อให้ Seed Script รันกี่ครั้งก็ได้ผลเหมือนเดิม ไม่ใช่ว่ารันสามรอบแล้วได้ข้อมูลซ้อนกันสามชุด

สังเกตลำดับให้ดี เราลบจากลูกไปหาแม่เสมอ คือลบ entry กับ habitTag ที่ถือ Foreign Key ก่อน แล้วค่อยลบ habit และ tag ปิดท้ายด้วย user ถ้าสลับลำดับ ฐานข้อมูลจะไม่ยอมให้ลบเพราะยังมีคนอ้างถึงอยู่

สร้าง User และดูว่า create คืนอะไรให้เรา

console.log('Creating demo users...')

const demoUser = await prisma.user.create({
  data: {
    email: 'demo@habittracker.com',
    username: 'demouser',
    password: 'demo123',
    firstName: 'Demo',
    lastName: 'User',
  },
})

รูปแบบคือ prisma.ชื่อโมเดล.create({ data }) ส่วนที่สนุกคือ data ถูก Type Check ตาม Model ที่เรากำลังใส่ ลองพิมพ์ในเอดิเตอร์ดูจะเห็นรายชื่อ Field ทั้งหมดของ User โผล่มา และตัวที่มีเครื่องหมายคำถามคือตัวที่ไม่ต้องใส่ก็ได้ เหลือที่บังคับจริง ๆ แค่ email, username และ password ตรงกับ Type NewUser ที่เรา Export ไว้ในบทที่ 17 พอดี

อีกเรื่องที่ดีงามคือ create คืนแถวที่เพิ่งถูกสร้างกลับมาให้เลย ครบทุก Field รวมทั้ง id ที่เพิ่งถูกสุ่มและ createdAt ที่เพิ่งถูกประทับ ซึ่งเราต้องการ id นั้นมาก เพราะเดี๋ยวต้องเอาไปผูกกับตารางอื่น (ถ้าอยากใส่ทีละหลายแถวก็มี createMany ที่รับ Array ของ Object)

เรื่อง password ตอนนี้เรายังใส่เป็นข้อความธรรมดาไปก่อน เพราะเรายังไม่ได้เรียนเรื่องการ Hash รหัสผ่าน ซึ่งจะอยู่ในบทที่ 21 หลังจากบทนั้นเราจะกลับมาแก้ตรงนี้ให้เป็นแบบนี้แทน

import { hashPassword } from '../utils/password.ts'

const hashedPassword = await hashPassword('demo123')
// แล้วส่ง hashedPassword เข้าไปใน data แทนข้อความดิบ

บนเครื่องเราเองตอนนี้ไม่มีปัญหาอะไร แต่บน Production ห้ามเก็บรหัสผ่านเป็นข้อความธรรมดาเด็ดขาด

สร้าง Tag และ Habit

console.log('Creating tags...')

const healthTag = await prisma.tag.create({
  data: { name: 'Health', color: '#10B981' },
})

console.log('Creating demo habits...')

const exerciseHabit = await prisma.habit.create({
  data: {
    userId: demoUser.id,
    name: 'Exercise',
    description: 'Daily workout routine',
    frequency: 'daily',
    targetCount: 1,
  },
})

ตรงนี้คือจุดที่ความสัมพันธ์เริ่มทำงานจริง userId: demoUser.id คือการผูก Habit เข้ากับ User ที่เราเพิ่งสร้าง และถ้าเราลืมบรรทัดนี้ ฐานข้อมูลจะปฏิเสธทันที เพราะ userId เป็น Field บังคับตั้งแต่บทที่ 16

สังเกตด้วยว่า frequency เราใส่ 'daily' ได้ตามใจเพราะยังเป็น String ธรรมดาอยู่ ซึ่งเป็นข้อจำกัดที่เราคุยกันไปแล้วในบทที่ 17

ผูก Habit เข้ากับ Tag ผ่านตารางกลาง

await prisma.habitTag.create({
  data: {
    habitId: exerciseHabit.id,
    tagId: healthTag.id,
  },
})

นี่คือการใช้ตารางกลางจริง ๆ ครั้งแรก เราแค่จับ id ของทั้งสองฝั่งมาวางคู่กัน แค่นั้น Habit ชื่อ Exercise ก็ถูกติดป้าย Health เรียบร้อย และตรงนี้เราไม่ต้องเก็บผลลัพธ์ใส่ตัวแปร เพราะไม่ต้องเอาไปทำอะไรต่อ แค่ต้องการให้แถวนั้นมีอยู่

ใส่ Entry ย้อนหลังเจ็ดวัน

console.log('Adding completion entries...')

const today = new Date()
today.setHours(12, 0, 0, 0)

for (let i = 0; i < 7; i++) {
  const date = new Date(today)
  date.setDate(date.getDate() - i)

  await prisma.entry.create({
    data: {
      habitId: exerciseHabit.id,
      completion_date: date,
      note: i === 0 ? 'Great workout today!' : null,
    },
  })
}

เราปักเวลาไว้ที่เที่ยงวันด้วย setHours(12, 0, 0, 0) เพื่อไม่ให้ผลลัพธ์เปลี่ยนไปตามเวลาที่เรารัน Script แล้ววนถอยหลังเจ็ดวันเพื่อสร้างประวัติการทำ Habit

อยากให้สังเกตจุดสำคัญตรงนี้ Insert ชุดนี้ไม่ได้สร้าง Habit ใหม่ มันสร้าง Entry ให้กับ Habit ที่มีอยู่แล้ว โดยชี้ผ่าน habitId ทุกแถวจะมี habitId เป็นตัวเดียวกันหมด นั่นแหละคือหน้าตาของ One-to-Many ในข้อมูลจริง

และย้ำอีกครั้งว่าชื่อ Field คือ completion_date ไม่ใช่ completionDate ตามที่เราประกาศไว้ใน Schema

ปิดท้ายด้วยการบอกรหัสเข้าระบบ

console.log('✅ Database seeded successfully!')
console.log('\n🔑 Login Credentials:')
console.log(`Email: ${demoUser.email}`)
console.log(`Username: ${demoUser.username}`)
console.log('Password: demo123')

ทริกเล็ก ๆ ที่มีประโยชน์มาก เพราะเดี๋ยวเราจะต้องเอา User ตัวนี้ไปทดสอบใน Postman การพิมพ์ออกมาให้เห็นเลยช่วยประหยัดเวลาไม่ต้องเปิดไปหาในฐานข้อมูล

ทริก import.meta.url ให้ไฟล์รันได้สองแบบ

ท้ายไฟล์ให้ใส่โค้ดนี้

if (import.meta.url === `file://${process.argv[1]}`) {
  seed()
    .then(() => process.exit(0))
    .catch(() => process.exit(1))
}

export default seed

สิ่งที่เราต้องการคือถ้ารันไฟล์นี้จากเทอร์มินัลตรง ๆ ให้ Seed ทันที แต่ถ้ามีใคร Import ไปอย่าเพิ่งรันเอง เพราะบางทีเราอยากเรียก seed() จากโค้ดอื่น เช่นในไฟล์ Test

ถ้าไม่มีเงื่อนไขนี้ วินาทีที่ใครก็ตาม Import ไฟล์นี้ มันจะล้าง Database แล้ว Seed ใหม่ทันทีโดยไม่ได้ตั้งใจ

ไล่ดูทีละส่วน import.meta.url คือ Path ของไฟล์ที่โค้ดบรรทัดนั้นอยู่ (ใน ES Module เราใช้ __dirname แบบสมัยก่อนไม่ได้แล้ว จึงต้องใช้ตัวนี้แทน)

ส่วน process.argv คือ Array ของทุกคำที่คั่นด้วยช่องว่างตอนเราสั่งรันจากเทอร์มินัล เรียงจากซ้ายไปขวา ถ้าเราสั่ง node src/db/seed.ts ก็จะได้ว่า argv[0] คือ node และ argv[1] คือไฟล์ที่เราสั่งให้ Node.js รัน

เพราะฉะนั้นเงื่อนไขทั้งบรรทัดอ่านว่า "ไฟล์ที่ถูกสั่งให้รัน คือไฟล์เดียวกับไฟล์นี้ใช่ไหม" ถ้าใช่ก็คือมีคนรันมันจากเทอร์มินัล ให้ Seed เลย ถ้าไม่ใช่ก็แปลว่ามีคน Import เข้าไป ก็แค่ Export Function ออกไปเฉย ๆ ให้เขาเรียกเอง ได้ทั้งสองทางในโค้ดสี่บรรทัด

ปิดท้ายด้วย process.exit() พร้อม Exit Code เหมือนที่เราทำใน env.ts คือ 0 แปลว่าจบดี 1 แปลว่าจบเพราะพัง

รันแล้วตรวจผล

npm run db:seed

คุณควรเห็น Log ไล่ตามลำดับที่เราเขียนไว้จนถึงบรรทัดสุดท้ายที่บอกว่าสำเร็จ ถ้ามี Error ก็ย้อนกลับไปดูว่าพังที่ Log บรรทัดไหน

วิธียืนยันว่าข้อมูลลงจริงคือเปิด Prisma Studio

npm run db:studio

กด Refresh แล้วไล่ดูทีละตาราง คุณจะเห็น Entry ทั้งเจ็ดแถวที่ผูกกับ Habit ตัวเดียวกัน เห็น Habit ที่ผูกกับ User ของเรา เห็น habit_tags หนึ่งแถวที่มี habit_id กับ tag_id ชี้ไปหาของจริงทั้งคู่ ถ้าครบทั้งหมดนี้ก็แปลว่าความสัมพันธ์ที่เราออกแบบไว้ทำงานได้จริง

อีกอย่างที่ควรรู้ Prisma Studio ไม่ใช่เครื่องมือแยกส่วน มันมากับ CLI ทีมเดียวกันกับ ORM และมันอ่าน Schema ของเราตรง ๆ เพราะฉะนั้นตารางและความสัมพันธ์ที่เห็นในนั้นคือสิ่งที่เราเขียนเป๊ะ ๆ ลองกดที่แถว Habit แล้วเดินตามความสัมพันธ์ไปหา Entry ทั้งเจ็ดแถวดู จะเห็นภาพ One-to-Many ชัดขึ้นอีก

เกร็ดเสริม — Prisma มีคำสั่ง npx prisma db seed ของมันเองด้วย ซึ่งจะไปเรียก Script ที่เราประกาศไว้ใน prisma.config.ts ได้ (เพิ่ม seed: 'node src/db/seed.ts' เข้าไปใน migrations) ทำงานเหมือน npm run db:seed ของเราทุกประการ ผมขอใช้ Script ตรง ๆ ของเราต่อเพื่อให้เห็นชัดว่ามันคือไฟล์ Node.js ธรรมดา ๆ ไฟล์หนึ่ง

เมื่อข้อมูล Seed เริ่มเยอะ

มีคนถามว่าถ้าข้อมูลที่ต้อง Seed เยอะมาก ควรยัดไว้ใน seed.ts ไฟล์เดียวไหม คำตอบคือแล้วแต่ว่าคุณ Seed ไปเพื่ออะไร

ที่เราทำวันนี้เรียกว่า Generic Seed คือแค่อยากให้มีข้อมูลอยู่ ไม่ได้เจาะจงว่าจะทดสอบอะไร กรณีแบบนี้ไฟล์เดียวก็พอ ถ้าอยากได้เยอะ ๆ ก็สร้างโฟลเดอร์เก็บ JSON ไว้ หรือให้ Faker สร้างให้

แต่วิธีที่ผมใช้จริงคือแบ่งตาม Scenario ผมจะมีโฟลเดอร์ seed ที่ข้างในมีไฟล์ละสถานการณ์ เช่นตอนผมทำ Pagination บนหน้าจอที่แสดงทีละ 10 แถว ผมอยากทดสอบว่าเลื่อนได้สามหน้า ผมก็เขียน Scenario ที่ Seed User หนึ่งคนที่มี 30 Habit พอดี ไม่มีอะไรมากกว่านั้น

อีกทางที่ง่ายมากคือถ้าคุณใช้บริการที่มี Database Branching อย่าง Neon แค่แตก Branch ออกมาก็ได้ข้อมูลจริงมาทั้งชุดโดยไม่ต้อง Seed อะไรเลย แต่ต้องดูนโยบายของบริษัทว่าเอาข้อมูล Production ลงเครื่องได้หรือไม่

สรุปคือเรื่องนี้ไม่มี Best Practice ตายตัว วิธีที่เราเขียนกันวันนี้ไม่มีอะไรผิด ถ้าวันหนึ่งมันเริ่มรกค่อยหาทางแตกออกไป

อ้อ อีกเรื่องที่อยากฝากไว้ การให้ AI ช่วยสร้างข้อมูลปลอมเป็นงานที่มันเหมาะมาก เพราะสิ่งที่เราอยากได้คือข้อมูลมั่ว ๆ ที่ดูสมจริงพอดี

เวิร์กโฟลว์จากนี้ไป

คุณอาจสังเกตว่าเราไม่เคยรัน db:migrate กับ db:deploy เลยสักครั้ง ถูกแล้ว เพราะเรายังไม่จำเป็นต้องใช้ เราจะได้ใช้จริงตอน Deploy ขึ้น Production ในบทที่ 31

จังหวะการทำงานที่ถูกต้องคือแบบนี้ ระหว่างที่ทำฟีเจอร์อยู่และยังเปลี่ยน Schema ไปมา ให้ db:push รัว ๆ ได้เลย ตราบใดที่ไม่ใช่ Destructive Change มันจะไม่มีปัญหาอะไร

ถ้าเป็น Destructive Change เช่นเปลี่ยนชื่อคอลัมน์ที่มีข้อมูลอยู่แล้ว Prisma จะเตือนว่าข้อมูลจะหายและถามยืนยันก่อน (หรือถึงขั้นให้ล้าง Database ทิ้งแล้วสร้างใหม่ด้วย Flag --force-reset) บนเครื่องเราเองก็ยอมได้เพราะเดี๋ยว Seed ใหม่ก็จบ แต่ถ้าใครไปทำแบบนั้นกับ Production คือการลบข้อมูลของคนอื่นทิ้ง ซึ่งถึงขั้นติดคุกได้จริง ๆ อย่าทำ

พอฟีเจอร์เสร็จและพร้อมเปิด PR ค่อยรัน db:migrate ครั้งเดียว เพื่อให้ได้ไฟล์ Migration ไฟล์เดียวที่สรุปทุกการเปลี่ยนแปลง แล้วให้ Production รัน db:deploy ตอน Deploy ถ้าคุณสร้าง Migration ทุกครั้งที่เปลี่ยนใจ PR ของคุณจะมี Migration หกไฟล์และไม่มีใครกล้า Merge ให้

เรื่อง Database จบครบแล้ว เรามี Schema มี Database จริง มี Connection และมีข้อมูลให้เล่น บทหน้าเราจะเริ่มเรื่องใหญ่เรื่องถัดไป คือ Authentication ว่าจะรู้ได้อย่างไรว่าคนที่ยิง Request เข้ามาเป็นใคร และเขามีสิทธิ์แตะข้อมูลชุดไหนบ้าง
