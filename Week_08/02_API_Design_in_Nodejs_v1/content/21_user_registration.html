ระบบสมัครสมาชิก (Registration)

บทนี้เราจะลงมือเขียนโค้ดจริงแล้ว สิ่งที่เราจะได้คือ POST /api/auth/register ที่ทำงานได้จริง ครอบคลุมทั้ง Identification และ Authentication ตามที่คุยกันไว้บทที่แล้ว

Flow ของการสมัครสมาชิก

  1. Validate Input — ตรวจว่าข้อมูลที่ส่งมาครบและถูกรูปแบบ
  2. เช็คความซ้ำ — Email หรือ Username ต้องไม่ถูกใช้ไปแล้ว
  3. Hash รหัสผ่าน — ห้ามเก็บข้อความดิบลง Database เด็ดขาด
  4. สร้าง User — Insert ลงตาราง
  5. ออก Token — ล็อกอินให้เขาทันทีโดยไม่ต้องกรอกซ้ำ
  6. ส่งอีเมลยืนยัน — ไม่บังคับ และเราจะไม่ทำในคอร์สนี้

ข้อ 1 เราทำเสร็จไปแล้วตั้งแต่บทที่ 12 ด้วย validateBody และ Schema ที่ Drizzle สร้างให้เรา

ข้อ 2 อย่าเขียน Query เช็คความซ้ำเอง

ถ้าคุณกำลังจะเขียน Query ไปไล่ดูว่ามี Email นี้ใน Database แล้วหรือยัง หยุดก่อน ลองคิดดูว่าถ้าคุณมีผู้ใช้ร้อยล้านคน แล้วทุกครั้งที่มีคนสมัคร คุณต้องไปไล่หาทีละแถว มันคือหายนะด้านประสิทธิภาพ และผมรับประกันว่าไม่มีใคร Merge PR แบบนั้นให้คุณ

ของแบบนี้เป็นหน้าที่ของ Database เราใส่ .unique() ให้ email และ username ไว้แล้วตั้งแต่บทที่ 16 ซึ่ง Postgres จะสร้าง Unique Index ให้ ถ้ามีคนสมัครซ้ำ Database จะโยน Error ออกมาเองฟรี ๆ และเร็วกว่ามาก เราแค่รับ Error นั้นมาจัดการต่อ

ทำไมต้อง Hash รหัสผ่าน

ถ้า Database รั่ว สิ่งที่คนร้ายเห็นจะเป็นแบบนี้

id | email             | password
1  | user@example.com  | MyPassword123!
2  | admin@site.com    | admin2024

ผลที่ตามมาไม่ได้จบแค่แอปเรา เพราะคนส่วนใหญ่ใช้รหัสผ่านซ้ำกันหลายเว็บ รหัสที่หลุดจากเราจะกลายเป็นกุญแจเปิดอีเมลและบัญชีธนาคารของเขาต่อ นี่ยังไม่นับความรับผิดทางกฎหมายและความเชื่อมั่นที่หายไปทั้งหมด

แต่ถ้า Hash ไว้ สิ่งที่รั่วออกไปจะเป็นแบบนี้แทน

id | email             | password
1  | user@example.com  | $2b$12$N9qo8uL...
2  | admin@site.com    | $2b$12$K7xI9pQ...

เหตุการณ์แบบนี้เกิดขึ้นจริงและเกิดบ่อย LinkedIn ปี 2012 หลุดรหัสผ่านที่ Hash แบบไม่ใส่ Salt ไป 6.5 ล้านรายการ Adobe ปี 2013 หลุด 150 ล้านรายการที่เข้ารหัสแบบถอดกลับได้ ส่วน RockYou ปี 2009 หลุด 32 ล้านรายการที่เป็นข้อความดิบล้วน ๆ อย่าไปเป็นข่าวหน้าถัดไป

Hash ไม่ใช่การสุ่ม

จุดที่คนเข้าใจผิดบ่อยคือ ถ้ามันดูมั่วขนาดนั้นแล้วเราจะเทียบตอนล็อกอินได้อย่างไร คำตอบคือ Hashing เป็น Deterministic คือใส่วัตถุดิบชุดเดิมเข้าไปจะได้ผลลัพธ์เดิมเสมอ

ถ้าคุณเคยเขียน Hash Table คุณจะคุ้นความรู้สึกนี้ Key เดิมผ่าน Algorithm เดิมย่อมได้ Index เดิมทุกครั้ง ไม่งั้น Hash Table ก็ใช้งานไม่ได้ ถ้า Hashing ไม่ Deterministic เราก็จะล็อกอินใครไม่ได้เลยตลอดกาล

bcrypt ทำงานอย่างไร

bcrypt คือมาตรฐานที่ใช้กันมานานสำหรับงานนี้โดยเฉพาะ ขั้นตอนคร่าว ๆ เป็นแบบนี้

// รหัสผ่านที่ผู้ใช้กรอก
"MyPassword123!"

// สิ่งที่ bcrypt ทำ
1. สุ่ม Salt ขึ้นมาหนึ่งชุด: "$2b$12$N9qo8uLOickgx2ZMRZoMye"
2. เอา Salt มาต่อกับรหัสผ่าน
3. ผ่าน Blowfish Algorithm 2^12 ครั้ง (4,096 รอบ)
4. ได้ผลลัพธ์: "$2b$12$N9qo8uLOickgx2ZMRZoMye.IjQ0JwF2cJX8nnYA5VYA.KQIeqHLWa"

Salt คือค่าสุ่มที่ถูกสร้างใหม่ทุกครั้งที่ Hash และถูกเก็บติดไปในผลลัพธ์เลย ส่วน Rounds คือเลขที่บอกว่าจะวนกี่รอบ ยิ่งเยอะยิ่งทนต่อการเดาสุ่ม แต่ก็ยิ่งกินเวลา CPU ตัวเลขที่ใช้กันคือ 10 ถึง 12 ซึ่งตรงกับที่เราตั้ง BCRYPT_ROUNDS ไว้ใน env.ts ตั้งแต่บทที่ 6 (เราจะเจาะรายละเอียดของ String ผลลัพธ์ทีละส่วนในบทที่ 23 ตอนทำ Sign In)

สร้าง src/utils/password.ts

ก่อนจะเขียน Controller เรามาทำเครื่องมือให้พร้อมก่อน สร้างโฟลเดอร์ src/utils ขึ้นมา ผมมักมีโฟลเดอร์ชื่อนี้ในทุกโปรเจกต์ (บางคนเรียก helpers หรือ modules) ไว้เก็บฟังก์ชันที่มีประโยชน์แต่ไม่รู้จะไปอยู่ตรงไหนดี แล้วสร้างไฟล์ password.ts

ถ้ายังไม่ได้ติดตั้ง bcrypt ให้ติดตั้งก่อน

npm install bcrypt
npm install -D @types/bcrypt
import bcrypt from 'bcrypt'
import { env } from '../../env.ts'

export const hashPassword = async (password: string): Promise<string> => {
  return bcrypt.hash(password, env.BCRYPT_ROUNDS)
}

สังเกตว่ามันเป็น async ซึ่งสำคัญมาก bcrypt มีเวอร์ชัน hashSync ให้ใช้ด้วย แต่อย่าใช้ เพราะการวน 4,096 รอบแบบ Synchronous จะบล็อก Event Loop ของ Node.js ทั้งเส้น แปลว่าตอนใครสักคนสมัครสมาชิก Request ของคนอื่นทั้งหมดจะหยุดรอ

อีกเหตุผลที่ต้องแยกออกมาเป็นไฟล์ต่างหากแทนที่จะเรียก bcrypt.hash() ตรง ๆ ใน Controller คือ เราต้องการเทสต์มันแยกได้ ถ้า Logic นี้ฝังอยู่กลาง Controller เราจะเขียน Test ให้เฉพาะส่วนนี้ไม่ได้เลย และถ้าวันหนึ่งต้องเปลี่ยนวิธี Hash เราก็แก้ที่เดียวจบ

ตอนนี้กลับไปแก้ src/db/seed.ts ได้แล้วตามที่สัญญาไว้ในบทที่ 19 เปลี่ยนจากรหัสผ่านข้อความดิบเป็น await hashPassword('demo123') แล้วรัน Seed ใหม่

สร้าง src/controllers/authController.ts

สร้างโฟลเดอร์ src/controllers แล้วสร้างไฟล์ authController.ts คำว่า Controller กับ Handler หมายถึงสิ่งเดียวกัน คือฟังก์ชันที่เราเสียบเข้าไปใน Route เพื่อบอกว่า "ถ้า Request วิ่งมาที่นี่ ให้รันตัวนี้" ผมสลับไปมาระหว่างสองคำนี้ตลอด รอบนี้ขอใช้คำว่า Controller

เริ่มจากโครงเปล่า ๆ พร้อม try/catch

import type { Request, Response } from 'express'
import { db } from '../db/connection.ts'
import { users, type NewUser } from '../db/schema.ts'
import { hashPassword } from '../utils/password.ts'

export const register = async (
  req: Request<any, any, NewUser>,
  res: Response
) => {
  try {
    // เดี๋ยวมาเติม
  } catch (e) {
    console.error('Registration error', e)
    res.status(500).json({ error: 'Failed to create user' })
  }
}

ทำไม 500 เพราะถ้าโค้ดหลุดมาถึงตรงนี้ได้ แปลว่าไม่น่าใช่ความผิดของฝั่งผู้ใช้แล้ว Input ผ่านการตรวจไปตั้งแต่ Middleware ที่หน้า Route ดังนั้นสิ่งที่พังได้คือ Database ล่ม หรือโค้ดเราเอง — ซึ่งทั้งคู่เป็นความผิดของเรา

มีข้อยกเว้นอยู่หนึ่งกรณีคือคนสมัครด้วย Email ที่ถูกใช้ไปแล้ว Postgres จะโยน Error Code เฉพาะสำหรับ Duplicate ออกมา ซึ่งเราดักแล้วตอบ 400 แทนได้ ตอนนี้ผมขอตอบ 500 ไปทุกกรณีก่อน แล้วดูจาก console.error ว่า Error หน้าตาเป็นอย่างไรจริง ๆ

ส่วน Request<any, any, NewUser> คือการบอก TypeScript ว่า req.body หน้าตาเป็นอย่างไร Generic ตัวแรกคือ Params ซึ่ง Route นี้ไม่มี เลยใส่ any ตัวที่สามคือ Body — เราใช้ NewUser ที่ Export ไว้ตั้งแต่บทที่ 17 ไม่ใช่ User เพราะ User มาจาก $inferSelect ซึ่งจะมี id, createdAt, updatedAt ครบเสมอ แต่คนที่กำลังจะสมัครยังไม่มีของพวกนั้น ส่วน NewUser มาจาก $inferInsert จึงเหลือแค่ที่จำเป็นจริง ๆ ตรงกับสิ่งที่ Client ส่งมาพอดี

ย้ำว่าสิ่งนี้ไม่ได้เปลี่ยนพฤติกรรมของโค้ดเลย มันคือ TypeScript ล้วน ๆ แต่ผลที่ได้คือพอพิมพ์ req.body. ในเอดิเตอร์ ทุก Field ของ User จะเด้งขึ้นมาให้เลือก

เติมเนื้อใน Controller

const hashedPassword = await hashPassword(req.body.password)

const [user] = await db
  .insert(users)
  .values({
    ...req.body,
    password: hashedPassword,
  })
  .returning({
    id: users.id,
    email: users.email,
    username: users.username,
    firstName: users.firstName,
    lastName: users.lastName,
    createdAt: users.createdAt,
  })

const token = await generateToken({
  id: user.id,
  email: user.email,
  username: user.username,
})

return res.status(201).json({
  message: 'User created',
  user,
  token,
})

ลำดับสำคัญมาก เรา Hash ก่อน Insert เสมอ

ลูกเล่นที่ผมชอบคือ ...req.body แล้วเขียน password ทับไว้ทีหลัง ถ้าสลับลำดับกันคือเอา password ขึ้นก่อนแล้ว Spread ทีหลัง รหัสผ่านข้อความดิบจะทับค่าที่ Hash แล้วทันที ซึ่งเป็นบั๊กที่มองไม่เห็นด้วยตาเปล่า ที่กล้าทำแบบนี้ได้เพราะเรา Validate Body มาแล้วอย่างเข้มงวด จึงมั่นใจว่าไม่มีของแปลกปลอมหลุดเข้ามา

.returning() คือจุดสำคัญที่สุดของบทนี้ ถ้าเราเรียก .returning() เปล่า ๆ Drizzle จะคืน User ทั้งแถวมาให้ ซึ่งรวมคอลัมน์ password ด้วย ถ้าเราเผลอส่งกลับไปให้ Client ก็เท่ากับยิงรหัสผ่านที่ Hash ไว้ออกไปในสายลม เราจึงระบุเองว่าอยากได้ Field ไหนบ้าง และไม่มี password อยู่ในนั้น

ผมขอตั้งเป็นกฎเลย — เหตุผลเดียวที่คุณควร Query คอลัมน์ password คือตอนล็อกอินกับตอนเปลี่ยนรหัสผ่าน นอกจากสองเรื่องนี้ไม่มีเหตุผลอื่นเลย

และเพราะ .returning() คืน Array เสมอ เราจึง Destructure ด้วย [user] เหมือนที่ทำใน Seed Script

ทำไมต้องออก Token ทันทีที่สมัครเสร็จ

เพราะการออก Token ณ จุดนี้เท่ากับล็อกอินให้เขาอัตโนมัติ ลองเทียบสองแบบ

ถ้าไม่ออก Token ผู้ใช้ต้องกรอกฟอร์มสมัคร กดส่ง เห็นข้อความว่าสร้างบัญชีแล้ว ถูกพาไปหน้าล็อกอิน กรอกข้อมูลเดิมซ้ำอีกรอบ แล้วถึงจะเข้าใช้งานได้ — หกขั้นตอน ผมเกลียดแอปที่ทำแบบนี้มาก คุณเพิ่งรู้ทุกอย่างของผมเมื่อสามวินาทีที่แล้ว ทำไมต้องให้กรอกใหม่

ถ้าออก Token เลย เหลือแค่กรอกฟอร์ม กดส่ง เข้าใช้งานได้ทันที — สี่ขั้นตอนและไม่มีความหงุดหงิด

ฟังก์ชัน generateToken ที่เราเรียกไว้ยังไม่มีตัวตนนะครับ ตอนนี้เอดิเตอร์จะขึ้นเส้นแดง เราจะไปสร้างมันกันในบทหน้า พร้อมกับเสียบ Route และทดสอบทั้งหมดใน Postman
