กลยุทธ์การทำ Authentication

เรื่อง Database จบไปแล้ว เรามีตาราง users และมีข้อมูลอยู่ในนั้นจริง ๆ บทนี้เราจะเริ่มเรื่องใหญ่เรื่องถัดไป คือทำอย่างไรให้ API รู้ว่าคนที่ยิง Request เข้ามาเป็นใคร และเขาแตะข้อมูลชุดไหนได้บ้าง

บทนี้ไม่มีโค้ดให้พิมพ์ตาม เป็นบทปูพื้นล้วน ๆ เพราะถ้าคุณไม่เข้าใจว่ากลยุทธ์แต่ละแบบต่างกันอย่างไร คุณจะเลือกผิดตั้งแต่วันแรก แล้วรื้อทีหลังแพงมาก บทที่ 21 เป็นต้นไปเราจะลงโค้ดกันยาว ๆ

สามคำที่คนสับสนกันมากที่สุด

คำสามคำนี้ถูกใช้ปนกันจนหลายคนคิดว่ามันคือเรื่องเดียวกัน ทั้งที่มันตอบคำถามคนละคำถาม

  • Identification — "คุณอ้างว่าคุณเป็นใคร"
  • Authentication — "พิสูจน์สิว่าคุณเป็นคนนั้นจริง"
  • Authorization — "แล้วคุณมีสิทธิ์ทำสิ่งนั้นหรือเปล่า"

ลองนึกภาพเดินเข้าโรงแรม คุณเดินไปที่เคาน์เตอร์แล้วบอกว่า "ผมชื่อสมชาย" — นั่นคือ Identification คุณแค่อ้างตัวตน ยังไม่ได้พิสูจน์อะไรเลย ในโลกของ API ตัวอ้างตัวตนก็คือ Email, Username หรือ ID ที่ส่งขึ้นมา

พนักงานขอดูบัตรประชาชนแล้วคุณยื่นให้ — นั่นคือ Authentication คุณพิสูจน์แล้วว่าคำอ้างเมื่อกี้เป็นความจริง ในโลกของ API ก็คือรหัสผ่านที่ตรงกัน หรือ Token ที่ผ่านการตรวจสอบ

พนักงานเช็คต่อว่าคุณจองห้องไหนไว้ เป็นสมาชิก VIP หรือเปล่า ใช้ห้องยิมได้ไหม — นั่นคือ Authorization ต่อให้ระบบรู้แน่ชัดว่าคุณคือใคร ก็ไม่ได้แปลว่าคุณจะเข้าไปแก้ข้อมูลของ User ID 123 ได้ ถ้านั่นไม่ใช่ข้อมูลของคุณ

สังเกตว่าทั้งสามอย่างต่อกันเป็นลูกโซ่ ไม่มี Authorization ถ้าไม่ผ่าน Authentication และไม่มี Authentication ถ้าไม่มี Identification กับดักที่เจอบ่อยมากคือโค้ดที่เช็ค Role จาก Header ที่ Client ส่งมาเอง โดยไม่เคยตรวจ Token เลยสักครั้ง นั่นคือการทำ Authorization โดยไม่มี Authentication ซึ่งเท่ากับไม่มีอะไรเลย

ในคอร์สนี้เราจะทำ Identification กับ Authentication เต็มรูปแบบ ส่วน Authorization เราจะทำแบบอ่อน ๆ ผ่าน Controller คือผูกทุก Query กับ User ที่ล็อกอินอยู่ ไม่ได้ทำถึงขั้น Role แบบเต็มรูปแบบ

Authorization แบบที่โลกจริงเขาใช้กัน

ถ้าจะทำ Authorization จริงจัง รูปแบบที่พบบ่อยที่สุดคือ RBAC หรือ Role-Based Access Control คือนิยาม Role ขึ้นมาชุดหนึ่งแล้วแจกให้แต่ละคน คุณเคยใช้แอปที่เชิญเพื่อนเข้าทีมแล้วเลือกได้ว่าจะให้เป็น Member, Admin หรือ Owner ใช่ไหม นั่นแหละคือ RBAC

อีกแบบคือ Resource-Based คือไม่ได้ดูที่ Role แต่ดูว่า "ของชิ้นนี้เป็นของคุณหรือเปล่า" ซึ่งเป็นแบบที่ Habit Tracker ของเราใช้ เพราะ Habit ทุกอันมี userId ผูกอยู่

Status Code ที่สื่อความหมายถูกต้อง

เรื่องนี้พลาดกันบ่อยจนต้องพูดไว้ก่อนเลย

  • 401 Unauthorized — ยังไม่ผ่าน Authentication ไม่ได้ส่ง Token มา ส่ง Token ผิด หรือ Token หมดอายุ (ชื่อมันชวนเข้าใจผิดมาก แต่ 401 คือเรื่องของ Authentication)
  • 403 Forbidden — ผ่าน Authentication แล้ว แต่ไม่มีสิทธิ์ เช่น User ทั่วไปพยายามลบข้อมูลของ Admin
  • 404 Not Found — บางครั้งเราจงใจตอบ 404 แทน 403 เพื่อไม่บอกใบ้ว่าของชิ้นนั้นมีอยู่จริง เช่นเมื่อ User พยายามเปิด Habit ของคนอื่น ตอบ "ไม่พบ" ปลอดภัยกว่าตอบ "มีอยู่แต่คุณห้ามดู"

สี่กลยุทธ์ของ Authentication

1. Session-Based

แบบดั้งเดิมที่สุด และยังเป็นแบบที่เจอเยอะที่สุดในฝั่ง Web App เต็มรูปแบบ หลักการคือServer เก็บ State ของการล็อกอินไว้เอง พอคุณล็อกอินสำเร็จ Server สร้าง Session ขึ้นมาหนึ่งอัน แล้วส่งกุญแจของ Session นั้นกลับไปให้ Client เก็บไว้ใน Cookie ซึ่ง Browser จะแนบขึ้นมาให้ทุก Request โดยอัตโนมัติ

ตัว Session เก็บไว้ที่ไหน ห้ามเก็บใน Memory เด็ดขาดเพราะ Server ตายเมื่อไรทุกคนหลุดหมด ส่วนใหญ่จึงเก็บใน Redis หรือ Database ที่ทำ Index ไว้ดี

ข้อดีที่ JWT ให้ไม่ได้เลยคือServer ควบคุมได้เต็มที่ จึงทำฟีเจอร์อย่าง "ดูว่าคุณล็อกอินค้างไว้ที่เครื่องไหนบ้าง" หรือ "ออกจากระบบทุกอุปกรณ์" ได้ เพราะแค่ลบ Session ทิ้งก็จบ ถ้าตรวจพบพฤติกรรมน่าสงสัยก็เตะออกได้ทันที ลองนึกถึง YouTube หรือ Google ที่มีทั้งแอปมือถือ แอปทีวี และเว็บ — Session เหมาะกับเคสแบบนั้นที่สุด

2. JWT (JSON Web Token)

ตรงข้ามกับ Session แบบสุดขั้ว มันคือ Stateless — Server ไม่เก็บอะไรไว้เลย

หลักการคือเราเอา Object ที่บอกว่าคนนี้เป็นใครมาแปลงเป็น String ตัวยาว ๆ ด้วย Algorithm และ Secret ที่มีแค่ Server รู้ String นั้นคือ JWT แล้วโยนให้ Client เก็บเอง จะเก็บใน Local Storage หรือ Cookie ก็เรื่องของ Client ทีนี้ทุก Request ที่ยิงเข้ามา Client ต้องแนบ String นี้ขึ้นมาด้วยตัวเอง

วิธีจำที่ง่ายที่สุดคือ Server ของเราขี้ระแวงสุดขีดและความจำสั้นมาก ต่อให้คุณเพิ่งยิง Request ไปเมื่อวินาทีที่แล้ว รอบถัดไปมันก็ยังไม่จำคุณอยู่ดี ต้องส่ง Token ขึ้นมาใหม่ทุกครั้ง

ข้อเสียที่ต้องรู้ตั้งแต่วันนี้คือ JWT ยกเลิกไม่ได้ เพราะ Server ไม่เคยเก็บมันไว้ที่ไหนเลย ถ้าใครเผลอ Push Token ขึ้น GitHub คุณจะเข้าไปกดยกเลิก Token นั้นไม่ได้ ทำได้อย่างเดียวคือรอให้มันหมดอายุ นี่คือเหตุผลที่การตั้งวันหมดอายุสำคัญมาก

3. API Key

ถ้าคุณเคยไปสมัครใช้ API ของเจ้าอื่น คุณจะได้ Key ยาว ๆ มาอันหนึ่ง หน้าตาการใช้งานคล้าย JWT มาก แต่ต่างกันที่ฝั่ง Server เพราะ Server เป็นคนสร้าง Key นั้นและเก็บอ้างอิงไว้ใน Database ด้วย

ผลคือ API Key ยกเลิกได้ ถ้า Key หลุด ก็แค่ลบแถวนั้นทิ้ง คราวหน้าที่มีคนเอา Key นั้นมาใช้ Server หาไม่เจอก็จบ และเพราะมีแถวใน Database เราจึงทำ Rate Limiting รายลูกค้าได้ด้วย ถ้าสินค้าของคุณคือตัว API เอง ไม่ได้มี Client เป็นของตัวเอง API Key คือคำตอบที่ถูกต้อง ไม่ใช่ Session

4. OAuth และบริการ Auth สำเร็จรูป

OAuth คือ Flow มาตรฐานสำหรับ "ล็อกอินด้วย Google" หรือ "ล็อกอินด้วย GitHub" ซึ่งปลายทางมักจบลงด้วยการที่คุณได้ Token หรือ API Key มาอยู่ดี

และมีบริการอย่าง Clerk หรือ Auth0 ที่รับทำ Auth ให้ทั้งก้อน เหตุผลที่คนยอมจ่ายไม่ใช่แค่เรื่องยาก แต่เป็นเรื่องความรับผิดชอบ ถ้าระบบโดนเจาะแล้วคุณเขียนเองทั้งหมด คุณจะโทษใคร แต่ถ้าจ่ายเงินซื้อบริการพร้อม SLA มันเหมือนซื้อประกันไว้ พูดตรง ๆ ว่านี่คือเหตุผลจริงในองค์กรใหญ่

แล้วเราจะใช้อะไร

คอร์สนี้เลือก JWT ด้วยเหตุผลตรงไปตรงมา คือ Habit Tracker ของเราเป็น API ล้วน ๆ ไม่มี Client เป็นของตัวเอง ไม่ต้องพึ่ง Cookie ของ Browser ไม่ต้องตั้ง Redis เพิ่ม และมันคือแบบที่พบบ่อยที่สุดในยุคของ Single Page Application

ไม่ใช่ว่ามันดีที่สุดนะครับ ในโลกที่สมบูรณ์แบบ Session อาจจะดีกว่าด้วยซ้ำ แต่มันจัดการยากกว่ามาก เลือกให้เหมาะกับสิ่งที่เรากำลังสร้างคือคำตอบที่ถูก

แล้ว bcrypt มาตรงไหน

มีจุดที่คนสับสนบ่อย — bcrypt ไม่ใช่ ทางเลือกที่สี่ มันคนละชั้นกันเลย

bcrypt คือเครื่องมือสำหรับ Hash รหัสผ่านก่อนเก็บลง Database และสำหรับเทียบรหัสผ่านตอนล็อกอิน มันทำงานแค่สองจังหวะเดียวในชีวิตของ Request คือตอนสมัครสมาชิกกับตอนเข้าสู่ระบบ พอผ่านสองจังหวะนั้นไปแล้ว bcrypt ก็หมดหน้าที่ และ JWT รับช่วงต่อไปตลอดอายุการใช้งาน

พูดอีกแบบคือ bcrypt ปกป้องรหัสผ่าน ส่วน JWT ปกป้องRoute ทั้งคู่จำเป็นและแทนกันไม่ได้

ภาพรวมของสิ่งที่เราจะสร้าง

  1. บทที่ 21 — Hash รหัสผ่านด้วย bcrypt แล้วเขียน Controller สมัครสมาชิก
  2. บทที่ 22 — สร้าง JWT แล้วส่งกลับไปให้ผู้ใช้ พร้อมทดสอบใน Postman
  3. บทที่ 23 — เขียน Controller เข้าสู่ระบบด้วย bcrypt compare
  4. บทที่ 24 — เขียน Middleware ตรวจ Token แล้วเอาไปล็อก Route
  5. บทที่ 25 — เก็บกวาดเรื่อง Security ที่เหลือ

อ่านหัวข้อพวกนี้แล้วอาจรู้สึกว่าเยอะ ซึ่งจริงครับ Auth เป็นเรื่องที่ลึกได้ไม่มีที่สิ้นสุด แต่พอทำครบรอบหนึ่งแล้วมันจะกลายเป็นของที่คุ้นมือไปเลย
