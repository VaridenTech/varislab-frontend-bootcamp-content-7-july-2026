สร้างตารางและความสัมพันธ์ด้วย Drizzle ORM

ทฤษฎีพอแล้ว บทนี้เราจะเขียน Schema ทั้งห้าตารางของ Habit Tracker กันจริง ๆ สร้างโฟลเดอร์ src/db ขึ้นมา แล้วสร้างไฟล์ src/db/schema.ts ข้างในนั้น

ถ้ายังไม่ได้ติดตั้ง Package ให้ติดตั้งก่อน

npm install drizzle-orm
npm install -D drizzle-kit

แล้วเริ่มไฟล์ด้วยการ Import ของที่จะใช้

import {
  pgTable,
  uuid,
  varchar,
  text,
  timestamp,
  boolean,
  integer,
} from 'drizzle-orm/pg-core'
import { relations } from 'drizzle-orm'

ทุกอย่างที่มาจาก drizzle-orm/pg-core คือของเฉพาะของ PostgreSQL pgTable คือตัวสร้างตาราง ส่วนที่เหลือคือชนิดของคอลัมน์ ส่วน relations ที่มาจาก drizzle-orm ตรง ๆ คือตัวประกาศความสัมพันธ์ ซึ่งเราจะใช้ตอนท้ายบท

ตาราง users

export const users = pgTable('users', {
  id: uuid('id').primaryKey().defaultRandom(),
  email: varchar('email', { length: 255 }).notNull().unique(),
  username: varchar('username', { length: 50 }).notNull().unique(),
  password: varchar('password', { length: 255 }).notNull(),
  firstName: varchar('first_name', { length: 50 }),
  lastName: varchar('last_name', { length: 50 }),
  createdAt: timestamp('created_at').defaultNow().notNull(),
  updatedAt: timestamp('updated_at').defaultNow().notNull(),
})

มีรายละเอียดหลายจุดที่ควรเข้าใจ ไม่ใช่แค่ก๊อปวาง

  • ต้อง export ทุกตารางเสมอ เพราะเราต้อง Import มันไปอ้างถึงตอนเขียน Query ในโค้ด ผมตั้งชื่อเป็นพหูพจน์เสมอเพื่อให้ตรงกับชื่อในฐานข้อมูล
  • Argument ตัวแรกของ pgTable คือชื่อจริงในฐานข้อมูล ส่วนชื่อ Const ทางซ้ายคือชื่อที่เราเรียกในโค้ด ผมให้ตรงกันเสมอเพื่อไม่ให้สับสน
  • เช่นเดียวกัน String ที่ใส่ใน Function ของแต่ละคอลัมน์คือชื่อคอลัมน์จริง สังเกตว่า firstName ในโค้ดแมปไปเป็น first_name ในฐานข้อมูล เพราะธรรมเนียมของ Relational Database คือ Snake Case ส่วนธรรมเนียมของ JavaScript คือ Camel Case Drizzle เลยให้เราเขียนสองชื่อคู่กันแบบนี้
  • uuid('id').primaryKey().defaultRandom() คือ Primary Key ที่เป็น UUID และให้ฐานข้อมูลสุ่มค่าให้เองตอนสร้างแถวใหม่ ข้อดีของ UUID คือไม่ซ้ำกันข้ามระบบ ใส่ใน URL ได้ และไม่หลุดข้อมูลว่าเรามีผู้ใช้กี่คนเหมือนเลขรันนิ่ง
  • ทุกคอลัมน์ที่ไม่ใช่ Primary Key เป็น Optional โดยปริยาย ถ้าอยากบังคับต้องเติม .notNull() เอง สังเกตว่า firstName กับ lastName เราไม่บังคับ เพราะบางคนไม่อยากบอกชื่อจริง
  • .defaultNow() บน createdAt และ updatedAt คือให้ฐานข้อมูลเติมเวลาปัจจุบันให้เอง เรื่อง Timestamp นี้เป็น Best Practice ที่ผมจะย้ำอีกครั้งในบทหน้า

varchar กับ text ต่างกันอย่างไร

varchar ก็คือ Text ธรรมดานี่แหละ แค่มันจำกัดความยาวได้ ถ้าไม่ใส่ length เลยมันก็เท่ากับ text เป๊ะ ๆ

ผมใส่ length ให้ email ไว้ 255 ไม่ใช่เพราะเชื่อว่าเป็นวิธีที่ดีที่สุด แต่เพื่อให้คุณเห็นว่ามันทำอะไรได้ จะจำกัดความยาวอีเมลจริง ๆ หรือไม่ก็แล้วแต่คุณ ส่วนคอลัมน์อย่าง description ที่เราไม่อยากจำกัดอะไรเลย ใช้ text ไปตรง ๆ ง่ายกว่า

.unique() คือทางลัดของการสร้าง Unique Index

คุณเจอ Index มาแล้วในคอร์ส Database ของ Week 8 ขอทวนสั้น ๆ ในภาษาที่ใช้กับงานนี้ Index คือที่เก็บแยกอีกที่หนึ่งในฐานข้อมูล ที่จับคู่ Key ไว้กับตำแหน่งของข้อมูล พูดแบบ JavaScript มันคือ Object ที่ทำหน้าที่เป็น Hash Table นั่นเอง

ถ้าไม่มี Index การหาอะไรสักอย่างแปลว่าต้องไล่สแกนทั้งตาราง แต่ถ้ามี Index ฐานข้อมูลจะสแกนแค่ตัว Index ที่เล็กกว่ามาก (บางระบบเก็บไว้ใน Memory เลย) เจอ Key แล้วกระโดดไปที่ตำแหน่งของข้อมูลได้ทันที

การเติม .unique() จึงหมายความสองอย่างพร้อมกัน คือห้ามมีอีเมลซ้ำในระบบ และสร้าง Index ให้คอลัมน์นี้ด้วย เพื่อให้ตอนมีคนสมัครใหม่ ฐานข้อมูลตอบได้ทันทีว่าอีเมลนี้มีคนใช้แล้วหรือยัง โดยไม่ต้องไล่สแกนผู้ใช้ทั้งตาราง

สังเกตว่า password เรา ไม่ ใส่ .unique() ซึ่งฟังดูตลกแต่มีคนพลาดจริง ลองคิดดูว่าถ้ารหัสผ่านห้ามซ้ำ พอสมัครไม่ผ่านปุ๊บก็แปลว่ามีคนใช้รหัสนี้อยู่ เหลือแค่หาอีเมลให้เจอก็เข้าระบบได้เลย

อีกเรื่องที่อยากให้เห็นคือ Validation เกิดได้หลายชั้น ทั้งที่ Form ฝั่งหน้าบ้าน ที่ Middleware ที่เราเขียนไปในบทที่ 12 และที่ระดับ Database ตรงนี้ ชั้นนอกข้ามได้ง่าย แต่ชั้นในสุดข้ามไม่ได้เลย ยิ่งกฎตรงกันทุกชั้นยิ่งดี

ตาราง habits และ Foreign Key ตัวแรกของเรา

export const habits = pgTable('habits', {
  id: uuid('id').primaryKey().defaultRandom(),
  userId: uuid('user_id')
    .references(() => users.id, { onDelete: 'cascade' })
    .notNull(),
  name: varchar('name', { length: 100 }).notNull(),
  description: text('description'),
  frequency: varchar('frequency', { length: 20 }).notNull(), // daily, weekly, monthly
  targetCount: integer('target_count').default(1), // ทำกี่ครั้งต่อรอบ
  isActive: boolean('is_active').default(true).notNull(),
  createdAt: timestamp('created_at').defaultNow().notNull(),
  updatedAt: timestamp('updated_at').defaultNow().notNull(),
})

userId คือ Foreign Key ตัวแรกของเรา กฎข้อแรกคือชนิดต้องตรงกับ Primary Key ที่มันชี้ไป ฝั่ง users.id เป็น uuid ฝั่งนี้ก็ต้องเป็น uuid

.references() รับ Function เข้าไป ไม่ได้รับตัวตารางตรง ๆ ซึ่งจำเป็น เพราะตอน JavaScript อ่านบรรทัดนี้ ตารางที่ถูกอ้างถึงอาจยังไม่ถูกสร้างขึ้น การห่อด้วย Function ทำให้ค่าถูกอ่านทีหลังตอนที่ทุกอย่างพร้อมแล้ว

{ onDelete: 'cascade' } คือคำสั่งว่าถ้า User ที่ถูกอ้างถึงถูกลบ ให้ลบ Habit นี้ตามไปด้วย ซึ่งสมเหตุสมผล เพราะ Habit ที่ไม่มีเจ้าของก็ไม่มีความหมาย

และเพราะเราเติม .notNull() ด้วย จึงสร้าง Habit โดยไม่ผูกกับ User ไม่ได้เลย ฐานข้อมูลจะปฏิเสธตั้งแต่ต้น ไม่ต้องรอให้โค้ดเราตรวจ

คอลัมน์ที่เหลือ frequency คือรอบการทำ เช่น daily, weekly, monthly ตรงนี้จริง ๆ ควรใช้ Enum จะดีกว่า แต่ผมยังไม่ใส่และจะกลับมาคุยเรื่องนี้ในบทหน้า targetCount คือเป้าหมายว่าต้องทำกี่ครั้งต่อรอบ เผื่อ Habit อย่าง "ดื่มน้ำแปดแก้วต่อวัน" และ isActive ให้ซ่อน Habit ที่เลิกทำแล้วโดยไม่ต้องลบประวัติทิ้ง

ข้อนี้เป็นอีกเหตุผลที่ผมชอบ Drizzle คือเราเขียน JavaScript ปนลงมาในนี้ได้เลย จะคำนวณค่า Default ด้วย Function ก็ทำได้ ซึ่งใน Prisma ทำไม่ได้เพราะมันไม่ใช่ JavaScript

ตาราง entries

export const entries = pgTable('entries', {
  id: uuid('id').primaryKey().defaultRandom(),
  habitId: uuid('habit_id')
    .references(() => habits.id, { onDelete: 'cascade' })
    .notNull(),
  completion_date: timestamp('completion_date').defaultNow().notNull(),
  note: text('note'),
  createdAt: timestamp('created_at').defaultNow().notNull(),
})

รูปแบบเดิมทุกอย่าง Entry หนึ่งแถวคือ "ทำ Habit นี้สำเร็จหนึ่งครั้ง" ความสัมพันธ์เป็น One-to-Many อีกครั้ง Foreign Key จึงอยู่ฝั่ง Many ตามเคย และ Cascade ก็สมเหตุสมผล เพราะถ้า Habit ถูกลบ ประวัติการทำ Habit นั้นก็ไม่ควรค้างอยู่

completion_date ใส่ .defaultNow() ไว้ เพราะปกติแถวนี้ถูกสร้างตอนที่คุณเพิ่งทำเสร็จพอดี ส่วน note เป็น Optional เผื่ออยากบันทึกอะไรไว้

สังเกตว่าคอลัมน์นี้ชื่อ completion_date ทั้งฝั่งโค้ดและฝั่งฐานข้อมูล ไม่ได้เป็น Camel Case เหมือนคอลัมน์อื่น อันนี้คือหน้าตาที่มันเป็นจริงในโปรเจกต์ ให้จำชื่อนี้ไว้ เพราะเราจะใช้มันตอนเขียน Seed และ Controller ในบทถัด ๆ ไป

ตาราง tags กับกับดักเรื่อง Unique

export const tags = pgTable('tags', {
  id: uuid('id').primaryKey().defaultRandom(),
  name: varchar('name', { length: 50 }).notNull().unique(),
  color: varchar('color', { length: 7 }).default('#6B7280'), // hex color
  createdAt: timestamp('created_at').defaultNow().notNull(),
  updatedAt: timestamp('updated_at').defaultNow().notNull(),
})

color ยาว 7 ตัวอักษรพอดีสำหรับ Hex Color อย่าง #6B7280 ตรงนี้ไม่มีอะไรซับซ้อน แต่บรรทัด name มีกับดักที่ผมอยากให้เห็น

การใส่ .unique() ตรงนี้แปลว่าชื่อ Tag ห้ามซ้ำกันทั้งระบบ ซึ่งหมายความว่าถ้าผมสร้าง Tag ชื่อ Fitness ไปแล้ว คุณจะสร้าง Tag ชื่อเดียวกันบนบัญชีของคุณไม่ได้เลย ทั้งที่มันควรเป็นของใครของมัน

สิ่งที่ถูกต้องกว่าคือทำ Unique บนคู่ของ userId กับ name ซึ่ง Drizzle รองรับผ่าน Compound Index แต่มันซับซ้อนขึ้นอีกระดับ ผมเลยขอคงไว้แบบนี้ก่อนในคอร์ส แล้วบอกให้คุณรู้ว่ามันเป็นข้อจำกัด

ที่ยกมาเล่าเพราะกับดักแบบนี้เกิดขึ้นได้จริง Server ตัวแรกในชีวิตผมเคยมีช่องโหว่ที่ใครก็เข้าไปดูข้อมูลของคนอื่นได้ ทั้งที่ตอนนั้นผมคิดว่าเขียนดีมากแล้ว และมันถูกใช้งานจริงด้วย ผิดแล้วก็จำไว้

ตาราง habit_tags ตัวเชื่อม Many-to-Many

export const habitTags = pgTable('habit_tags', {
  id: uuid('id').primaryKey().defaultRandom(),
  habitId: uuid('habit_id')
    .references(() => habits.id, { onDelete: 'cascade' })
    .notNull(),
  tagId: uuid('tag_id')
    .references(() => tags.id, { onDelete: 'cascade' })
    .notNull(),
  createdAt: timestamp('created_at').defaultNow().notNull(),
})

ตารางนี้ไม่มีข้อมูลของตัวเองเลย หน้าที่เดียวของมันคือจับคู่ Habit หนึ่งอันเข้ากับ Tag หนึ่งอัน แล้วมี id ของตัวเองไว้อ้างถึงคู่นั้น

ให้เห็นภาพชัด ๆ หนึ่งความสัมพันธ์เท่ากับหนึ่งแถวในตารางนี้ ถ้า Habit หนึ่งอันติดยี่สิบ Tag จะมียี่สิบแถวที่ habit_id เหมือนกันหมดแต่ tag_id ต่างกัน ถ้า Tag หนึ่งอันไปเกาะยี่สิบ Habit ก็จะมียี่สิบแถวที่ tag_id เหมือนกันแต่ habit_id ต่างกัน

ประกาศความสัมพันธ์ด้วย relations()

ตอนนี้ฐานข้อมูลรู้จักความสัมพันธ์แล้วผ่าน Foreign Key แต่ตัว ORM ยังไม่รู้ว่าเราอยากให้ Query ออกมาหน้าตาแบบไหน นั่นคืองานของ relations()

คิดง่าย ๆ ว่า .references() คือการบอกฐานข้อมูล ส่วน relations() คือการบอกDrizzle ว่าเราอยากได้ Field ใหม่อะไรงอกขึ้นมาตอน Query

export const usersRelations = relations(users, ({ many }) => ({
  habits: many(habits),
}))

export const habitsRelations = relations(habits, ({ one, many }) => ({
  user: one(users, {
    fields: [habits.userId],
    references: [users.id],
  }),
  entries: many(entries),
  habitTags: many(habitTags),
}))

export const entriesRelations = relations(entries, ({ one }) => ({
  habit: one(habits, {
    fields: [entries.habitId],
    references: [habits.id],
  }),
}))

export const tagsRelations = relations(tags, ({ many }) => ({
  habitTags: many(habitTags),
}))

export const habitTagsRelations = relations(habitTags, ({ one }) => ({
  habit: one(habits, {
    fields: [habitTags.habitId],
    references: [habits.id],
  }),
  tag: one(tags, {
    fields: [habitTags.tagId],
    references: [tags.id],
  }),
}))

วิธีอ่านมีแค่นี้ relations() รับตารางที่เราจะประกาศเป็น Argument แรก แล้วรับ Callback ที่เรา Destructure เอา one หรือ many ออกมาใช้ตามชนิดความสัมพันธ์ สิ่งที่ Callback คืนคือ Object ของField ใหม่ที่เราอยากให้มี

อย่าง usersRelations อ่านว่า "ถ้า Query User ให้มี Field ชื่อ habits ที่เป็น Habit ทั้งหมดของ User คนนั้น" ฝั่ง many ง่ายเพราะ Drizzle หาทางเชื่อมได้เองจาก Foreign Key ที่เราประกาศไว้แล้ว

ฝั่ง one ต้องบอกเพิ่ม อย่างใน habitsRelations เราบอกว่าอยากได้ Field ใหม่ชื่อ user โดยที่ fields คือคอลัมน์บนตารางนี้ที่ใช้เชื่อม และ references คือคอลัมน์ปลายทางที่มันต้องตรงกัน ย้ำว่าบนตาราง habits ไม่มี Field ชื่อ user อยู่จริง มีแค่ userId สิ่งที่เรากำลังทำคือขอให้ Drizzle เสกมันขึ้นมาให้เวลาเรา Query

ส่วน habitTagsRelations ประกาศเป็น one ทั้งสองฝั่ง เพราะเมื่อมองจากตารางกลาง หนึ่งแถวผูกกับ Habit หนึ่งอันและ Tag หนึ่งอันเท่านั้น ความเป็น Many-to-Many เกิดขึ้นเมื่อมองภาพรวมจากการที่มีหลายแถว

สามเรื่องที่ต้องระวัง

หนึ่ง Drizzle ไม่ช่วยจับผิดชื่อคอลัมน์ใน fields ถ้าคุณใส่คอลัมน์ที่มีอยู่จริงบนตารางนั้นแต่เป็นคอลัมน์ผิดตัว TypeScript จะไม่ฟ้องอะไรเลย เพราะมันเป็นคอลัมน์ที่ถูกต้องตาม Type ผมเองติดกับข้อนี้มานับครั้งไม่ถ้วน นั่งงงว่าทำไมข้อมูลไม่โผล่ ทั้งที่ตอนนั้นเปิด Note ที่ตัวเองเขียนไว้อยู่ตรงหน้า ให้อ่านสองรอบทุกครั้ง

สอง ทำไม relations() ต้องแยกจาก .references() คำถามนี้ดีมากและผมก็เคยสงสัย เหตุผลที่ผมเดาได้คือถ้าเราประกาศ Field แบบ user ไว้ในตัวนิยามตาราง มันจะกลายเป็นการอ้างถึงตารางอื่นภายในตัวนิยามของตัวเอง ซึ่งพันกันยุ่งมาก แยกออกมาแบบนี้ตรงไปตรงมากว่า ถึงจะดูเยิ่นเย้อไปหน่อยก็ตาม

สาม จะแยก Schema เป็นหลายไฟล์ก็ได้ เหมือนที่เราแยก Route ออกเป็นไฟล์ละ Resource บางโปรเจกต์ของผมที่มีเกิน 50 ตารางก็ต้องแยก เพราะเปิดไฟล์เดียวแล้วมึน แต่ของเรามีร้อยกว่าบรรทัด ผมเลยรวมไว้ไฟล์เดียว ถ้าคุณจะแยก ให้ระวังเรื่อง Circular Dependency เพราะไฟล์ตารางอาจ Import กันไปมา ซึ่งเป็นเรื่องที่ต้องมาแก้เพิ่ม แต่ในแง่ความสามารถแล้วไม่ต่างกันเลย

Schema ของเราครบแล้ว บทหน้าเราจะดึงประโยชน์จากมันต่อ ด้วยการ Export TypeScript Type และ Zod Schema ออกมาจากตารางพวกนี้โดยไม่ต้องเขียนซ้ำ
