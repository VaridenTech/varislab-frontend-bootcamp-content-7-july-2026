การใช้งาน Environment Variables

ตอนนี้ Server ของเรามีเลข 3000 Hardcode อยู่ใน src/index.ts ซึ่งใช้งานได้ดีบนเครื่องเรา แต่พอวันที่เราเอาโค้ดชุดเดียวกันนี้ไปรันที่อื่นเมื่อไหร่ เลขตัวนี้จะกลายเป็นปัญหาทันที

บทนี้เราจะมาทำความรู้จัก Environment Variables ซึ่งเป็นเรื่องที่นักพัฒนาฝั่ง Server ต้องทำเป็นตั้งแต่โปรเจกต์แรก และเป็นหนึ่งในสิ่งแรก ๆ ที่ควรตั้งค่าให้เรียบร้อยในทุกโปรเจกต์ Node.js ไม่ว่าจะเป็น API, Script หรือ AI Agent ก็ตาม

Environment Variable คืออะไร

Environment Variable คือตัวแปรที่ถูกฉีดเข้ามาใน Environment ที่โปรแกรมของเรารันอยู่ พูดง่าย ๆ คือค่าที่มาจากข้างนอกโค้ด ไม่ได้เขียนไว้ในไฟล์ .ts ของเรา แต่โปรแกรมอ่านมันได้ตอนรัน

ประโยชน์หลักคือมันทำให้เราเปลี่ยนการตั้งค่าของ Server ได้โดยไม่ต้องแก้โค้ดเลยแม้แต่บรรทัดเดียว (ส่วนใหญ่แค่ต้องรีสตาร์ท Server เท่านั้น) ถ้าคุณเคยทำ Feature Flag หรือ A/B Testing ฝั่ง Frontend หรือเคยกด Publish บทความใน Headless CMS แล้วเว็บอัปเดตทันทีโดยไม่ต้อง Deploy ใหม่ นั่นคือแนวคิดเดียวกัน และ Environment Variable ก็คือต้นกำเนิดของแนวคิดเหล่านั้น

ทำไมเราต้องใช้มัน

มีเหตุผลใหญ่ ๆ อยู่สองข้อ

  • ข้อมูลลับต้องไม่อยู่ในโค้ด — รหัสผ่านฐานข้อมูล, API Key, Secret ของ JWT ถ้าเราพิมพ์ค่าพวกนี้ลงในไฟล์แล้ว Push ขึ้น GitHub เท่ากับเราแจกกุญแจบ้านให้ทุกคนที่เห็น Repository นั้น
  • โค้ดชุดเดียวต้องรันได้หลาย Environment — โค้ดชุดนี้จะรันบนเครื่องคุณ บนเครื่องเพื่อนร่วมทีม บน Staging และบน Production โดยแต่ละที่มีฐานข้อมูลคนละตัวและ URL คนละอัน ถ้าเรา Hardcode DATABASE_URL ลงในไฟล์ TypeScript แล้วจะทำยังไงตอนขึ้น Staging เขียนเงื่อนไข if ไล่ทีละที่อย่างนั้นหรือ

ยังมีอีกเหตุผลที่คนมักลืม คือค่าหลายตัวไม่ได้ถูกตั้งไว้ล่วงหน้าตายตัว ผู้ให้บริการ Hosting ส่วนใหญ่จะสร้างค่าพวกนี้ให้แบบ Dynamic ตอน Deploy เช่น Port หรือ URL ที่มาจาก Load Balancer และบางค่าก็ถูกหมุนเปลี่ยน (Rotate) เป็นระยะเพื่อความปลอดภัย ค่าที่เปลี่ยนได้ตลอดเวลาแบบนี้จะเขียนตายตัวลงในโค้ดไม่ได้อยู่แล้ว

ระวัง Environment Variable ฝั่ง Frontend

ถ้าคุณเคยเขียน React มาก่อน คุณน่าจะเคยใช้ process.env.NEXT_PUBLIC_XXX หรือ import.meta.env.VITE_XXX มาแล้ว แต่ของพวกนั้นไม่ใช่ Environment Variable จริง ๆ มันแค่ถูกฉีดเข้ามาผ่าน Environment ตอน Build เท่านั้น

สิ่งที่เกิดขึ้นจริงคือ Build System อย่าง Vite หรือ Webpack จะแทนที่ข้อความ process.env.NEXT_PUBLIC_XXX ในโค้ดด้วยค่าจริงของตัวแปรนั้น แล้วส่งผลลัพธ์ไปให้ Browser ดังนั้นถ้าใครเปิด Source Code ของเว็บคุณดู เขาจะเห็นค่านั้นเต็ม ๆ พูดอีกอย่างคือคุณกันคนบน GitHub ไม่ให้เห็นได้ก็จริง แต่กันคนที่เปิดเว็บคุณไม่ได้ ฝั่ง Server ไม่เป็นแบบนั้น เพราะไม่มีใครมานั่งเปิดดูโค้ด Server ได้ นอกจากคนที่เข้าถึงตัวเครื่องได้จริง ๆ ค่าที่เก็บไว้ที่นี่จึงเป็นความลับได้อย่างแท้จริง

อ่านค่าด้วย process.env

ใน Node.js เราเข้าถึง Environment Variable ผ่าน Object ที่ชื่อ process.env ลองแทรกบรรทัดนี้ไว้บนสุดของ src/server.ts ดูก็ได้

console.log(process.env.NODE_ENV)

ถ้ายังไม่มีใครตั้งค่าไว้ คุณจะได้ undefined กลับมา ตรงนี้คือจุดที่ต้องจำให้ขึ้นใจ นั่นคือ process.env เป็นแค่ Object ธรรมดาที่มี Key เป็นชื่อตัวแปรและ Value เป็น String เท่านั้น

อย่าเผลอ console.log(process.env) ทั้งก้อนตอนแชร์หน้าจอหรือถ่ายวิดีโอ เพราะมันจะพ่นตัวแปรทุกตัวบนเครื่องคุณออกมา รวมถึง Secret Key ของงานอื่นด้วย

ไฟล์ .env สำหรับเครื่องเรา

บนเครื่องตัวเอง วิธีที่ใช้กันมากที่สุดคือเขียนค่าลงไฟล์ชื่อ .env ที่รากของโปรเจกต์ ตอน Clone โปรเจกต์มาคุณจะมีแค่ .env.example ให้สร้างอีกสองไฟล์เพิ่มเองตอนนี้เลย

habit-tracker-api/
├── .env          # ค่าสำหรับตอนพัฒนาบนเครื่องเรา
├── .env.test     # ค่าสำหรับตอนรัน Test
└── .env.example  # ไฟล์ตัวอย่าง อันนี้ Commit ขึ้น Git ได้

เนื้อหาของ .env เป็นแค่ไฟล์ Text ธรรมดา หน้าตาแบบนี้

PORT=3000
DATABASE_URL=postgresql://postgres:password@localhost:5432/habit_tracker_dev
JWT_SECRET=development-jwt-secret-key-32-characters-minimum

ส่วน .env.test ใช้รูปแบบเดียวกัน แต่มีไว้ให้ตอนรัน Test สลับไปใช้ค่าอีกชุดหนึ่ง เช่น PORT=3001 และชี้ DATABASE_URL ไปที่ฐานข้อมูลคนละตัว จะได้ไม่ไปลบข้อมูลที่เรานั่งกรอกไว้ตอนพัฒนา

.env ห้ามขึ้น Git เด็ดขาด

เหตุผลที่คุณไม่เห็นไฟล์ .env ตอน Clone โปรเจกต์มา ก็เพราะมันถูกกันไว้ตั้งแต่แรกด้วย .gitignore ซึ่งมีบรรทัดประมาณนี้

# Environment variables
.env
.env.*
!.env.example

สองบรรทัดแรกคือห้ามทุกไฟล์ที่ขึ้นต้นด้วย .env ส่วนบรรทัดที่มีเครื่องหมาย ! คือการยกเว้นให้ .env.example ขึ้น Git ได้ตัวเดียว

กฎข้อนี้ไม่มีข้อยกเว้น อย่า Commit ไฟล์ .env ขึ้น GitHub ไม่ว่าจะกรณีไหน แม้บาง Framework จะบอกว่าให้ Commit ได้ถ้าไม่มีความลับอยู่ข้างใน แต่การตั้งกฎเดียวไปเลยว่า "ไม่เอาขึ้น" ปลอดภัยกว่าการต้องมานั่งตัดสินทีละไฟล์ว่าอันนี้ลับพอไหม

.env.example คือคู่มือของทีม

พอ .env ขึ้น Git ไม่ได้ ก็เกิดปัญหาใหม่ทันที คือคนที่เพิ่งเข้าทีมจะไม่มีทางรู้เลยว่าโปรเจกต์นี้ต้องการตัวแปรอะไรบ้าง ธรรมเนียมที่ใช้แก้ปัญหานี้คือทำไฟล์ .env.example ที่ Commit ขึ้น Git แล้วใส่ชื่อตัวแปรทั้งหมดพร้อมค่าตัวอย่างที่ไม่ใช่ของจริง

# Database Configuration
DATABASE_URL=postgresql://username:password@localhost:5432/habit_tracker_db

# Server Configuration
PORT=3000
NODE_ENV=development

# JWT Configuration
JWT_SECRET=your_super_secret_jwt_key_here
JWT_EXPIRES_IN=7d

คนใหม่ที่เข้ามาก็แค่ก๊อปไฟล์นี้ไปเป็น .env ของตัวเอง แล้วเติมค่าจริงลงไป จบ ไม่ต้องเดินไปถามใครทีละตัว

.env.example ที่มากับโปรเจกต์นี้ใส่ตัวแปรมาให้เยอะกว่าที่คอร์สเราจะได้ใช้จริง ไม่ต้องตกใจ ให้ก๊อปเฉพาะตัวที่เราใช้ก็พอ

ไฟล์ .env กลายเป็น process.env ได้ยังไง

คำถามที่ควรสงสัยคือ ในเมื่อ .env เป็นแค่ไฟล์ Text แล้ว Node.js รู้จักมันได้ยังไง คำตอบคือไม่รู้จัก เราต้องมี Package มาช่วยอ่านไฟล์นั้นให้

Package ที่คนใช้กันมากที่สุดคือ dotenv ส่วนในโปรเจกต์นี้เราจะใช้ custom-env ซึ่งทำงานเหมือนกันแทบทุกอย่าง แต่สลับไฟล์ตามชื่อ Environment ได้ง่ายกว่า ซึ่งตรงกับที่เราต้องการ เพราะเรามีทั้ง .env และ .env.test

npm install custom-env

สิ่งที่ Package พวกนี้ทำ ไม่มีเวทมนตร์อะไรเลย มันแค่

  1. เปิดอ่านไฟล์ .env แบบ Synchronous
  2. ไล่อ่านทีละบรรทัด แยกชื่อกับค่าออกจากกันที่เครื่องหมาย =
  3. เซ็ตค่าให้เราด้วยการทำ process.env.DATABASE_URL = '...' ทีละตัว

คำว่า Synchronous ตรงนี้สำคัญมาก เพราะมันการันตีว่าพอโค้ดวิ่งมาถึงบรรทัดถัดไป ตัวแปรทุกตัวถูกเซ็ตครบแล้วแน่นอน ถ้ามันทำงานแบบ Asynchronous เราอาจเผลอรันโค้ดที่ต้องใช้ค่าเหล่านั้นก่อนที่มันจะพร้อม ซึ่งจะกลายเป็นบั๊กที่หาสาเหตุยากมาก

แยกค่าระหว่าง Development กับ Production

ทีนี้ Server ของเราจะรู้ได้ยังไงว่าตอนนี้มันรันอยู่ที่ไหน คำตอบคือเราบอกมันด้วย Environment Variable อีกตัวหนึ่งนั่นแหละ

หลายคนคุ้นกับ NODE_ENV แต่ในคอร์สนี้เราจะไม่ใช้มันเป็นตัวตัดสิน เพราะโดยเจตนาดั้งเดิม NODE_ENV มีไว้เปิด/ปิด Optimization ของ Library ต่าง ๆ ไม่ได้มีไว้บอกว่าแอปรันอยู่ที่ไหน ในโลกอุดมคติเราอยากตั้ง NODE_ENV=production ไว้เกือบตลอดเวลาด้วยซ้ำ เพื่อให้ได้ Optimization เหล่านั้น

เราจึงสร้างตัวแปรของเราเองชื่อ APP_STAGE ขึ้นมาทำหน้าที่นี้โดยเฉพาะ โดยมีค่าที่เป็นไปได้คือ dev, test และ production

โค้ดชุดนี้จะไปอยู่ในไฟล์ env.ts ที่รากของโปรเจกต์ ซึ่งเราจะสร้างกันเต็ม ๆ ในบทหน้า

import { env as loadEnv } from 'custom-env'

process.env.APP_STAGE = process.env.APP_STAGE || 'dev'

const isProduction = process.env.APP_STAGE === 'production'
const isDevelopment = process.env.APP_STAGE === 'dev'
const isTesting = process.env.APP_STAGE === 'test'

if (isDevelopment) {
  loadEnv()
} else if (isTesting) {
  loadEnv('test')
}

อ่านทีละบรรทัดจะเห็นว่ามันตรงไปตรงมามาก

  • ตอน Import เราเปลี่ยนชื่อ env ที่ custom-env ส่งออกมาเป็น loadEnv ด้วยคำว่า as เพราะเดี๋ยวเราจะใช้ชื่อ env กับ Object ของเราเองในไฟล์นี้
  • บรรทัดถัดมาแปลว่า "ถ้าใครตั้ง APP_STAGE มาให้แล้วก็ใช้ค่านั้น ถ้าไม่มีใครตั้งมาเลยให้ถือว่าเป็น dev" เพราะคนที่รันโดยไม่ตั้งค่าอะไรเลย ก็คือเราที่กำลังพัฒนาอยู่บนเครื่องตัวเองนั่นแหละ
  • ตัวแปร Boolean สามตัวมีไว้กันเขียนเงื่อนไขซ้ำ ๆ ทั่วทั้งไฟล์
  • ตอนพัฒนาโหลดจาก .env ตอน Test โหลดจาก .env.test
  • สังเกตว่าตอน Production เราไม่โหลดไฟล์อะไรเลย เพราะบน Production จะไม่มีไฟล์ .env อยู่แล้ว (เรากันไม่ให้มันขึ้น Git ไปตั้งแต่แรก) ค่าทั้งหมดจะถูกฉีดเข้ามาโดย Hosting Provider แทน

เวลา Deploy จริง เราจะไปกรอกชื่อและค่าของตัวแปรทั้งหมดในหน้า Settings ของผู้ให้บริการ แล้วเขาจะเซ็ตลง process.env ให้เราเอง เราจะได้ลงมือทำจริงกันในบทที่ 31 นอกจากนี้ Hosting Provider ส่วนใหญ่ยังฉีดตัวแปรของตัวเองเข้ามาให้ด้วย เช่น Render บอก URL ของแอปเรามา หรือ GitHub Actions ตั้ง GITHUB_ACTIONS=true ไว้ให้ เราจึงเดาได้ว่าโค้ดกำลังรันอยู่ที่ไหน

เอาเลข Port ออกจากโค้ดเสียที

กลับมาที่ src/index.ts ของเรา สิ่งที่ทำได้ทันทีคือเปลี่ยนเลข 3000 ที่ Hardcode ไว้ให้มาจาก Environment Variable แทน

import app from './server.ts'

const PORT = process.env.PORT || 3000

app.listen(PORT, () => {
  console.log(`Server running on port ${PORT}`)
})

เรื่องนี้ไม่ใช่เรื่องความสวยงาม แต่เป็นเรื่องจำเป็น เพราะตอน Deploy เราไม่ได้เป็นคนเลือก Port ผู้ให้บริการจะกำหนดมาให้แล้วส่งมาทาง PORT ถ้าเรายัง Hardcode ไว้ Server จะไปเปิดฟังผิดช่อง แล้วก็จะไม่มีใครเข้าถึงมันได้เลย นี่คือ Environment Variable ตัวแรกที่ทุกคนต้องเจอเมื่อ Deploy Server

แต่โค้ดข้างบนยังมีปัญหาที่ซ่อนอยู่สามข้อ

  • Type ของ PORT คือ string | number เพราะค่าจาก process.env เป็น String เสมอ
  • ไม่มีใครตรวจว่าค่าที่ได้มาสมเหตุสมผลไหม ถ้ามีคนพิมพ์ PORT=abc เราจะรู้ตัวก็ตอนที่มันพังไปแล้ว
  • Editor ไม่ช่วยเติมชื่อตัวแปรให้ พิมพ์ process.env.PROT ผิดไปตัวเดียวก็ได้ undefined เงียบ ๆ โดยไม่มีใครเตือน

บทถัดไปเราจะแก้ทั้งสามข้อนี้ให้จบในไฟล์เดียว ด้วยการทำ Environment Variable ให้เป็น Type-safe ด้วย Zod
