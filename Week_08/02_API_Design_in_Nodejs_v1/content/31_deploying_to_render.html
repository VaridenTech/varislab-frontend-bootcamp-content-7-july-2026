Deploy ขึ้น Production ด้วย Render

ถึงเวลาเอา API ของเราออกไปให้คนอื่นใช้ได้จริงเสียที ที่ผ่านมาทุกอย่างวิ่งอยู่บนเครื่องเราคนเดียว บทนี้เราจะย้ายมันขึ้นไปอยู่บนอินเทอร์เน็ต แล้วได้ URL จริงที่ยิงจาก Postman ที่ไหนก็ได้

ทำไมเลือก Render

เจ้าที่รับ Deploy แอปให้เรามีเยอะมาก Railway ก็คล้าย ๆ กัน ฝั่ง Serverless มี Vercel, Netlify และ Cloudflare ส่วน Fly.io ก็เป็นอีกทาง และถ้าอยากลงไปใกล้เครื่องมากขึ้นก็มี AWS, Google Cloud, Azure หรือ DigitalOcean

ทั้งหมดทำงานบนตรรกะเดียวกัน คือรับโค้ดจาก Git แล้วรันให้ ผมเลือก Render ไม่ใช่เพราะมันดีที่สุด แต่เพราะมันเริ่มต้นง่ายที่สุด (คนที่เคยใช้ Heroku จะรู้สึกคุ้นมาก) พอเข้าใจภาพรวมจากที่นี่แล้ว ย้ายไปเจ้าอื่นก็ไม่ยาก ก่อนกดปุ่ม Deploy มีของที่ต้องเตรียมอยู่เจ็ดข้อ ทำให้ครบก่อนแล้วขั้นตอนหลังจากนั้นจะราบรื่นมาก

1. สร้าง Production Database

Database บนเครื่องเราไม่มีใครเข้าถึงได้จากข้างนอก เราจึงต้องมีอีกตัวสำหรับ Production ตอนนี้เราจะมีสามตัวแล้ว คือตัวสำหรับ Development ตัวสำหรับ Test (จากบทที่ 29) และตัวสำหรับ Production วิธีสร้างเหมือนบทที่ 18 ทุกอย่าง กลับไปที่ Neon Launchpad กดสร้างอันใหม่แล้วเก็บ Connection String ไว้

อย่าลืมว่า Database ที่ได้จาก Launchpad จะหายไปใน 72 ชั่วโมง ถ้าไม่สมัครบัญชี Neon แล้ว Claim มันไว้ ถ้าอีกสามวันแอปที่ Deploy แล้วเริ่ม Error ขึ้นมาเฉย ๆ นี่แหละคือสาเหตุ

ในทีมจริง แต่ละสภาพแวดล้อมมักมี Database ของตัวเอง ทั้ง Staging และบางทีคนละตัวต่อคนในทีมด้วยซ้ำ ซึ่ง Neon ทำได้แบบอัตโนมัติผ่าน Database Branching

2. รัน Migration ครั้งแรกเข้า Production

Database ที่เพิ่งสร้างมันว่างเปล่า ไม่รู้จัก Schema ของเราเลย ถ้า Deploy ตอนนี้แอปพังแน่นอน เราต้องส่ง Schema เข้าไปก่อน ที่ผ่านมาเราใช้ npm run db:push ยัด Schema เข้า Database ของเครื่องเราแบบตรง ๆ ซึ่งทำได้เพราะข้อมูลในนั้นพังก็ไม่มีใครเดือดร้อน แต่กับ Production ห้ามใช้ db:push เด็ดขาด มันเทียบเท่ากับการ Force Push ทับ Branch หลัก มีสิทธิ์ล้างข้อมูลของผู้ใช้จริงทิ้งได้ ต้องไปทาง Migration เท่านั้น

เปิดไฟล์ .env แล้วคอมเมนต์ DATABASE_URL ตัวเดิมไว้ ใส่ของ Production ลงไปแทนชั่วคราว (ใส่ใน .env นะครับ ไม่ใช่ .env.test) จากนั้นสั่ง

npm run db:generate

คำสั่งนี้ ไม่ได้คุยกับ Database เลย มันแค่อ่าน src/db/schema.ts แล้วเขียนไฟล์ SQL ออกมาในโฟลเดอร์ migrations/ ตามที่เราตั้งค่า out ไว้ใน drizzle.config.ts ข้างในจะมีสองอย่าง

  • 0000_xxxx.sql — SQL จริงที่จะถูกรัน นี่คือสิ่งที่เราต้องนั่งเขียนเองถ้าไม่มี Drizzle
  • meta/ — มี _journal.json กับไฟล์ Snapshot ที่เป็นภาพแทน Schema ของเราในรูปแบบ JSON เอาไว้ให้ Drizzle เทียบ Diff ในครั้งถัดไป

สังเกตเลขนำหน้าชื่อไฟล์ Migration ต้องถูกรันตามลำดับเสมอ เลขจึงเป็นตัวบอกลำดับ (บางทีมใช้วันที่แทนเลขก็ได้เหมือนกัน) และ ไฟล์ Migration ต้องถูก Commit ขึ้น Git เพราะทุกคนในทีมและเครื่องที่ Deploy ต้องใช้มัน จากนั้นค่อยสั่งรัน Migration เข้า Database

npm run db:migrate

Drizzle จะไล่รันไฟล์ในโฟลเดอร์ migrations/ จากเก่าสุดไปใหม่สุด ถ้าไม่มี Error แปลว่าเรียบร้อย ตรวจซ้ำได้ด้วย npm run db:studio แล้วดูว่าตารางทั้งห้าตัวขึ้นครบใน Production Database

พอเสร็จแล้ว เอา Connection String ของ Production ออกจาก .env ทันที แล้วเอาของ Development กลับมา การรัน Migration จากเครื่องตัวเองใส่ Production แบบนี้เราทำเพราะเป็นการเรียนการสอน ในงานจริงจะไม่ทำกัน เขาจะรันผ่านสคริปต์บนเครื่องที่ Deploy แล้ว หรือผ่านเครื่องมือจัดการ Migration ที่บริษัทซื้อมาโดยเฉพาะ

3. ทำให้ Port เป็น Dynamic

เราทำข้อนี้ไปแล้วตั้งแต่บทที่ 5 แต่ขอย้ำอีกครั้งเพราะมันทำให้ Deploy ล้มเหลวได้ง่ายที่สุด ห้าม Hardcode เลข Port เพราะบน Production เราไม่ได้เป็นคนเลือก Port ผู้ให้บริการเป็นคนกำหนดมาให้ผ่าน Environment Variable ชื่อ PORT ซึ่งใน env.ts ของเรามี PORT: z.coerce.number().positive().default(3000) อยู่แล้ว แปลว่ามันอ่านจาก Environment ก่อน ถ้าไม่มีค่อยตกไปที่ 3000 และ src/index.ts ก็ใช้ env.PORT ตรง ๆ

app.listen(env.PORT, () => {
  console.log(`Server running on port ${env.PORT}`)
  console.log(`Environment: ${env.APP_STAGE}`)
})

4. เตรียม Environment Variables

รวบรวมให้ครบว่า Production ต้องใช้ตัวไหนบ้าง ของเราคือ DATABASE_URL, JWT_SECRET, APP_STAGE, NODE_ENV และ BCRYPT_ROUNDS โดยกฎเหล็กคือ สร้างค่าใหม่ที่ปลอดภัยสำหรับ Production เสมอ อย่าใช้ Secret ตัวเดียวกับ Development ถ้า Secret ของเครื่อง Dev หลุด (ซึ่งหลุดง่ายกว่ามาก) เท่ากับ Production หลุดตามไปด้วยทันที

อีกเรื่องที่ต้องเข้าใจคือบน Render ไม่มีไฟล์ .env ซึ่งไม่เป็นปัญหา เพราะ env.ts ของเราเรียก loadEnv() เฉพาะตอน APP_STAGE เป็น dev หรือ test เท่านั้น พอเป็น production มันจะอ่านจาก process.env ที่ Render ฉีดเข้ามาให้โดยตรง

5. แทนที่ URL ที่ Hardcode ไว้

ไล่หาในโค้ดว่ามี localhost โผล่อยู่ตรงไหนบ้าง เพราะ URL บน Production ไม่ใช่ Localhost แน่นอน จุดที่คนลืมบ่อยคือ CORS Configuration, Email Template, Webhook URL, เอกสาร API และโค้ดฝั่ง Frontend ที่เรียก API

โปรเจกต์เราไม่มีปัญหานี้เพราะ CORS อ่านจาก env.CORS_ORIGIN อยู่แล้ว ส่วนถ้าที่ไหนต้องรู้ URL ของตัวเอง Render มี Environment Variable ชื่อ RENDER_EXTERNAL_URL ให้ใช้

const apiUrl = process.env.RENDER_EXTERNAL_URL || 'http://localhost:3000'

ผู้ให้บริการทุกเจ้าจะฉีด Environment Variable ชุดหนึ่งเข้ามาบอกสถานะของระบบให้เรา แต่ชื่อตัวแปรต่างกันไป ต้องไปอ่านเอกสารของเจ้านั้น ๆ เอง

6. ระบุเวอร์ชันของ Node

ข้อนี้สำคัญมากสำหรับโปรเจกต์เรา เพราะ Render จะเลือกเวอร์ชัน Node เก่ากว่าที่เราต้องการถ้าเราไม่บอก แล้วโค้ด TypeScript ที่รันตรง ๆ ด้วย node src/index.ts จะทำงานไม่ได้เลย เพิ่ม Field engines ลงใน package.json

{
  "name": "habit-tracker-api",
  "type": "module",
  "engines": {
    "node": ">=24.3.0"
  },
  "scripts": {
    "dev": "node --watch src/index.ts",
    "start": "node src/index.ts"
  }
}

7. เตรียม Branch แล้ว Push ขึ้น GitHub

Render ดึงโค้ดจาก GitHub ดังนั้นโค้ดที่จะ Deploy ต้องอยู่บน GitHub ก่อน โดยทั่วไปจะเป็น Branch main แต่ไม่จำเป็นต้องเป็น เพราะเราบอก Render ได้ว่าให้ดู Branch ไหน บางทีมมี Branch production แยกต่างหากก็มี เลือก Branch ที่มีโค้ดครบตามที่ต้องการ (อย่าลืมว่าโฟลเดอร์ migrations/ ต้องอยู่ในนั้นด้วย) แล้ว Push ขึ้นไป

git add .
git commit -m "Prepare for deployment"
git push origin your-branch

สร้าง Web Service บน Render

สมัครบัญชีที่ Render ด้วยการ Sign In with GitHub ไม่ต้องใส่บัตรเครดิต จากนั้นกดสร้างของใหม่ เลือก Web Service (ไม่ใช่ Static Site ไม่ใช่ Background Worker) แล้วเลือก Repository ของเราที่มันดึงมาให้จาก GitHub อยู่แล้ว

  • Name — ชื่อนี้ ต้องไม่ซ้ำกับใครทั้งแพลตฟอร์ม ไม่ใช่แค่ในบัญชีเรา เพราะมันจะกลายเป็น URL ให้เรา ถ้าโดนคนอื่นจองไปแล้วต้องเปลี่ยนชื่อ
  • Language — เลือก Node
  • Branch — Branch ที่เพิ่ง Push ขึ้นไป
  • Root Directory — ปล่อยว่างไว้ถ้า package.json อยู่ที่รากของ Repository
  • Build Command — เปลี่ยนเป็น npm install (ค่าเริ่มต้นอาจเป็น Yarn ซึ่งเราไม่ได้ใช้มาตลอดทั้งคอร์ส)
  • Start Command — Render อ่าน package.json เจอ Script start แล้วเดาให้เองว่าเป็น npm start
  • Instance Type — เลือก Free ได้เลย

ใส่ Environment Variables ในหน้า Dashboard

เลื่อนลงมาที่ส่วน Environment Variables แล้วใส่ค่าที่เตรียมไว้ในข้อ 4 ทีละตัว หรือจะกดปุ่มอัปโหลดไฟล์ .env ทั้งไฟล์ให้มันแตกออกมาเป็นตัวแปรให้เองทีเดียวก็ได้

DATABASE_URL=postgresql://...   # ของ Production ที่สร้างในข้อ 1
JWT_SECRET=...                  # ค่าใหม่ ยาวอย่างน้อย 32 ตัวอักษร
APP_STAGE=production
NODE_ENV=production
BCRYPT_ROUNDS=12

ที่เหลืออีกสองช่องที่น่าสนใจคือ Health Check Path ใส่ /health ได้เลยเพราะเรามี Route นั้นอยู่ใน src/server.ts แล้ว Render จะยิงเข้าไปเป็นระยะเพื่อดูว่ายังมีชีวิตอยู่ไหม (มันดูแค่ว่าได้ Status 200 กลับมาหรือเปล่า ไม่สนใจ Body) และ Pre-Deploy Command ซึ่งเป็นที่ที่เหมาะที่สุดสำหรับสั่งรัน Migration ตอน Deploy แต่ต้องใช้แพ็กเกจแบบเสียเงิน

ส่วน Auto-Deploy ตั้งเป็น On Commit ไว้ก่อน หมายความว่าทุกครั้งที่มีโค้ดใหม่เข้า Branch นั้น (จะ Push ตรงหรือ Merge Pull Request ก็ตาม) Render จะ Deploy ให้อัตโนมัติ

Deploy จริงและอ่าน Log

กด Deploy แล้วนั่งดู Log ได้เลย สิ่งที่เห็นคือหน้าจอของเครื่องที่กำลัง Build ให้เรา มันทำแบบเดียวกับที่เราทำบนเครื่องตัวเองเป๊ะ ๆ คือดึงเวอร์ชัน Node ตาม engines ที่เราระบุไว้ รัน Build Command แล้วย้ายไฟล์ขึ้น Server จากนั้นสั่ง Start

ครั้งแรกของผมพังครับ Log บอกว่าค่าหนึ่งต้องมากกว่า 10 ซึ่งคือ BCRYPT_ROUNDS ที่ผมเผลอใส่ 8 ลงไป แล้ว Zod Schema ใน env.ts กำหนดไว้ว่า .min(10) นี่คือประโยชน์ของการ Validate Environment ตั้งแต่ตอนแอปเริ่มทำงานตามที่คุยกันในบทที่ 6 — มันพังทันทีพร้อมบอกเหตุผลชัดเจน ดีกว่าไปพังตอนผู้ใช้คนแรกกดสมัครสมาชิก แก้ง่ายมาก กลับไปที่แท็บ Environment แก้ค่าเป็น 12 กด Save แล้ว Render จะ Deploy รอบใหม่ให้เอง

รอบนี้ผ่าน สังเกตว่าจะเห็น 404 โผล่มาหนึ่งครั้งตอนแรก นั่นเป็นเรื่องปกติ ผู้ให้บริการส่วนใหญ่จะยิง GET ไปที่ / เพื่อดูว่าแอปตอบกลับมาไหม ได้ 404 ก็ถือว่าตอบแล้ว แปลว่า Server ทำงานอยู่

ยิงทดสอบ URL จริง

คัดลอก URL ที่ Render ให้มาแล้วเปิด Postman ขึ้นมา ลอง GET /health ก่อนเพื่อดูว่า Server ตอบไหม แล้วต่อด้วยตัวที่ต้องใช้ฐานข้อมูลจริง

POST https://habit-api.onrender.com/api/auth/register

{
  "email": "user@example.com",
  "username": "user",
  "password": "adminpassword1234"
}

ได้ 201 Created พร้อม Token กลับมาเมื่อไร แปลว่าครบวงจรแล้ว ทั้ง Server, Route, Middleware, Validation, Auth และ Production Database ทำงานร่วมกันได้จริงบนอินเทอร์เน็ต

Continuous Deployment กับเรื่องที่ Render ไม่ได้ทำให้

จากนี้ไปทุกครั้งที่โค้ดเข้า Branch ที่เราผูกไว้ Render จะ Deploy ใหม่ให้เอง นี่คือ Continuous Deployment แบบพื้นฐานที่สุด

แต่สิ่งที่ Render ไม่ได้ ทำให้คือรัน Test ให้ก่อน Deploy นั่นเป็นงานของ CI ซึ่งต้องหาเครื่องมืออื่นมาเสริม ตัวที่ง่ายที่สุดคือ GitHub Actions (สั่งให้รัน npm test ทุกครั้งที่มี Push หรือ Pull Request) ส่วนเจ้าอื่นก็มี Jenkins กับ CircleCI ที่อยู่มานาน พอ CI ผ่านแล้วให้ GitHub ไฟเขียว เราค่อยตั้ง Render ให้ Deploy ตามหลัง ซึ่งตั้งได้ที่ตัวเลือก Auto-Deploy นั่นเอง

Checklist หลัง Deploy

  • ยิงทดสอบ Endpoint ให้ครบทุกตัว
  • ยืนยันว่าเชื่อมต่อ Database ได้จริง
  • เช็คว่า Environment Variables ถูกโหลดครบ
  • ไล่อ่าน Log ว่ามี Error แปลก ๆ ไหม
  • ทดสอบ Flow ของ Authentication ตั้งแต่สมัครจนถึงเข้า Route ที่ล็อกไว้
  • ตรวจว่า CORS ตั้งค่าถูกต้องสำหรับ Domain ที่จะเรียกใช้จริง

การ Deploy มีรายละเอียดมากกว่านี้อีกเยอะ ทั้งการทำ Staging Environment แยก การให้ทุกคนในทีมมีสภาพแวดล้อมของตัวเอง หรือการทำ Rollback แต่จุดเริ่มต้นมันง่ายแค่นี้จริง ๆ ครับ API ของเราขึ้น Production เรียบร้อยแล้ว บทหน้าเป็นบทสุดท้าย เรามาทบทวนกันว่าตลอดคอร์สนี้เราผ่านอะไรมาบ้าง
