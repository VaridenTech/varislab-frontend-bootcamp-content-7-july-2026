Environment Variables แบบ Type-safe

บทที่แล้วเรารู้จัก Environment Variables และย้ายเลข Port ออกจากโค้ดไปแล้ว แต่เราทิ้งปัญหาไว้สามข้อ คือไม่มี Type, ไม่มีการตรวจสอบค่า และ Editor ไม่ช่วยเติมชื่อให้

บทนี้เราจะสร้างไฟล์ env.ts ที่รากของโปรเจกต์ขึ้นมาแก้ทั้งสามข้อในทีเดียว นี่เป็นไฟล์ที่หลายคนไม่ค่อยทำกัน แต่พอทำแล้วจะติดใจจนต้องทำทุกโปรเจกต์

ปัญหาของ process.env แบบดิบ ๆ

ลองดูโค้ดสามบรรทัดนี้ ทุกบรรทัดคือระเบิดเวลา

const port = process.env.PORT || 3000     // Type เป็น string | number
const dbUrl = process.env.DATABASE_URL    // อาจเป็น undefined
const jwtSecret = process.env.JWT_SECRET  // ไม่มีใครตรวจว่าสั้นเกินไปหรือเปล่า

ปัญหาที่แท้จริงไม่ใช่แค่เรื่อง Type แต่คือเราจะรู้ว่าตัวแปรหายไปก็ตอนที่โค้ดวิ่งไปถึงบรรทัดที่ใช้มันแล้ว ลองนึกภาพว่าคุณ Deploy แอปขึ้น Production ทุกอย่างดูปกติดี แล้วอีกสามวันต่อมามีคนกดปุ่มที่ไปเรียกโค้ดส่วนที่ต้องใช้ DATABASE_URL พอดี แล้วแอปพังทั้งระบบ ทั้งที่สาเหตุคือเราลืมกรอกค่าตั้งแต่วันแรก

สิ่งที่เราอยากได้คือ ถ้าตัวแปรที่จำเป็นไม่ครบ ให้ Server ตายตั้งแต่วินาทีที่มันพยายามจะสตาร์ท พร้อมบอกให้ชัดว่าขาดตัวไหน แนวคิดนี้เรียกว่า Fail Fast และมันจะช่วยชีวิตคุณตอน Deploy อีกหลายครั้งในอนาคต

ของแถมอีกข้อคือ Editor จะเติมชื่อตัวแปรให้เราอัตโนมัติ และเราไม่ต้องพิมพ์คำว่า process.env. นำหน้าทุกครั้งอีกต่อไป

Zod คือ TypeScript ที่ทำงานตอน Runtime

TypeScript ตรวจ Type ให้เราตอนที่เราพิมพ์โค้ดและตอน Build เท่านั้น แต่ตอนโปรแกรมรันจริง TypeScript ไม่มีตัวตนอยู่แล้ว เพราะ V8 ไม่รู้จักมัน Type ทั้งหมดถูกลบทิ้งไปก่อนหน้านั้น

แล้วถ้าเราอยากตรวจค่าจริงที่ไหลเข้ามาตอน Runtime ล่ะ นั่นคือหน้าที่ของ Zod พูดให้ชัดคือ TypeScript ตรวจโค้ด ส่วน Zod ตรวจค่า เราจะเขียน Schema ขึ้นมาหนึ่งชุด แล้วให้ Zod เอา Schema นั้นไปตรวจข้อมูลจริงให้เรา

npm install zod

ถ้าเจอ Error ว่าหา Package ไม่เจอเมื่อไหร่ ก็แค่ npm install ตัวนั้นเพิ่ม อาการนี้จะตามหลอกหลอนคุณไปตลอดชีวิตการเขียนโค้ด

เขียน Schema ของ Environment

ในไฟล์ env.ts ให้เพิ่ม Import ของ Zod ไว้บนสุดคู่กับ custom-env แล้วเขียน Schema ต่อจากส่วนโหลดไฟล์ .env ที่เราเขียนไว้ในบทที่แล้ว

import { z } from 'zod'

const envSchema = z.object({
  NODE_ENV: z
    .enum(['development', 'test', 'production'])
    .default('development'),

  APP_STAGE: z.enum(['dev', 'test', 'production']).default('dev'),

  PORT: z.coerce.number().positive().default(3000),
  DATABASE_URL: z.string().startsWith('postgresql://'),
  JWT_SECRET: z.string().min(32, 'Must be 32 chars long'),
  JWT_EXPIRES_IN: z.string().default('7d'),
  BCRYPT_ROUNDS: z.coerce.number().min(10).max(20).default(12),
})

วิธีอ่าน Schema นี้คือ Key ทางซ้ายคือชื่อ Environment Variable ที่เราคาดหวังว่าจะมี ส่วนทางขวาคือกฎที่ค่านั้นต้องผ่าน มาไล่ดูทีละตัว

  • z.enum([...]) แปลว่าค่าต้องเป็นหนึ่งในลิสต์นี้เท่านั้น (คำว่า Enum ย่อมาจาก Enumeration หมายถึงการไล่ตัวเลือกทั้งหมดออกมา) ส่วน .default(...) คือค่าที่จะใช้ถ้าไม่มีใครตั้งมา ทั้งสองตัวนี้จึงไม่บังคับว่าต้องมี
  • PORT ใช้ z.coerce.number() เพราะทุก Environment Variable เป็น String เสมอ ไม่มีข้อยกเว้น มันคือ Text ล้วน ๆ คำว่า Coerce คือสั่งให้ Zod แปลงค่าให้เป็นชนิดที่เราต้องการก่อนตรวจ แล้วเราค่อยเติม .positive() ว่าต้องเป็นเลขบวก และ .default(3000) ให้ตรงกับเลขที่เรา Hardcode ไว้เดิม
  • DATABASE_URL เป็น String ที่ต้องขึ้นต้นด้วย postgresql:// ตรงนี้คือ Protocol ของ URL ซึ่งไม่ได้มีแค่ http กับ file ใครจะสร้าง Protocol ของตัวเองก็ได้ (แอปบนมือถือทุกตัวก็มี Protocol ของตัวเองไว้ทำ Deep Link) ฐานข้อมูลก็เช่นกัน การเช็คแค่คำนำหน้าก็ช่วยดักคนที่วางค่าผิดชนิดมาได้เยอะแล้ว
  • JWT_SECRET ต้องยาวอย่างน้อย 32 ตัวอักษร สังเกตว่าเราใส่ข้อความเป็น Argument ตัวที่สองได้ นั่นคือ Error Message ที่เราจะเห็นตอนมันไม่ผ่าน ซึ่งช่วยให้เดี๋ยวเราไล่ปัญหาได้เร็วขึ้นมาก
  • BCRYPT_ROUNDS เกี่ยวกับการ Hash รหัสผ่าน เราจะพูดถึงมันจริงจังในบทที่ 21 ส่วนตัวเลข 10 ถึง 20 มาจากคำแนะนำทั่วไป ไม่ใช่เลขศักดิ์สิทธิ์อะไร

ตัวไหนที่ไม่มี .default() แปลว่าบังคับต้องมี ในที่นี้คือ DATABASE_URL กับ JWT_SECRET ถ้าขาดไปแอปจะไม่ยอมสตาร์ท

สร้าง Type จาก Schema ด้วย z.infer

จุดที่ Zod เจ๋งที่สุดคือเราสร้าง TypeScript Type ขึ้นมาจาก Schema ได้เลย โดยไม่ต้องนั่งเขียน Type ซ้ำอีกรอบ

export type Env = z.infer<typeof envSchema>
let env: Env

ของที่อยู่ในวงเล็บแหลมเรียกว่า Generic ให้นึกภาพว่ามันคือการส่ง Argument เข้าไปใน Type เหมือนที่เราส่ง Argument เข้า Function นั่นแหละ ในที่นี้เราส่ง Type ของ envSchema เข้าไปให้ z.infer แล้วมันจะคายหน้าตาของ Object ที่ผ่านการตรวจแล้วออกมาให้เรา

ผลลัพธ์คือเรามี Schema ชุดเดียวแต่ได้ประโยชน์สองต่อ คือได้ Type Checking ตอนพัฒนาจาก TypeScript และได้การตรวจค่าจริงตอน Runtime จาก Zod

ตรวจค่าและตายให้ไวถ้าไม่ผ่าน

ทีนี้ก็ถึงเวลาเอา Schema ไปใช้จริง

try {
  env = envSchema.parse(process.env)
} catch (e) {
  if (e instanceof z.ZodError) {
    console.log('Invalid env var')
    console.error(JSON.stringify(e.flatten().fieldErrors, null, 2))

    e.issues.forEach((err) => {
      const path = err.path.join('.')
      console.log(`${path}: ${err.message}`)
    })

    process.exit(1)
  }

  throw e
}

หัวใจอยู่ที่ envSchema.parse(process.env) บรรทัดเดียว เราโยน process.env ทั้งก้อนเข้าไปได้เลย เพราะมันก็เป็นแค่ Object ที่มี Key กับ Value ธรรมดา ๆ ตัวไหนตรงกับ Schema ก็ถูกดึงออกมาแปลงและตรวจให้ ตัวที่ไม่ได้อยู่ใน Schema ก็ถูกมองข้ามไป

ถ้ามีอะไรไม่ผ่าน Zod จะ Throw Error ออกมา เราจึงครอบด้วย try...catch ไว้ แล้วในนั้นมีรายละเอียดที่น่าสนใจหลายจุด

  • เราเช็ค e instanceof z.ZodError ก่อน เพื่อให้แน่ใจว่าเป็นปัญหาเรื่องการตรวจค่าจริง ๆ ไม่ใช่ Error อื่นที่บังเอิญเกิดขึ้น ถ้าไม่ใช่ก็ throw ต่อไปตามปกติ
  • e.flatten().fieldErrors ช่วยแบน Error ที่ Zod ซ้อนกันหลายชั้นให้เหลือรูปแบบที่อ่านง่าย
  • JSON.stringify(..., null, 2) คือทริกที่ควรจำไว้ใช้ตลอดชีวิต เพราะ console.log ของ Node.js จะย่อ Object ที่ลึกเกินสามชั้นให้เหลือแค่คำว่า [Object] การ Stringify ทำให้เห็นครบทุกชั้น ส่วนเลข 2 ตัวท้ายคือให้จัดย่อหน้าให้สวยงามด้วยการเว้น 2 ช่อง ไม่งั้นมันจะพ่นออกมาเป็นบรรทัดยาวเหยียดบรรทัดเดียว
  • e.issues คือรายการปัญหาทั้งหมดที่เจอ เราวนอ่านทีละตัวเพื่อ Log ว่า Field ไหนพังเพราะอะไร คำว่า path ตรงนี้ไม่ใช่ Path ของไฟล์ แต่เป็นตำแหน่งของ Field ใน Object ที่เราตรวจ (ถ้าเป็น Object ซ้อนกันก็จะเห็นเป็น a.b.c) ถ้าคุณไปเจอตัวอย่างเก่า ๆ ที่เขียนว่า e.errors นั่นคือชื่อเดิมของ Zod รุ่นก่อน ปัจจุบันเปลี่ยนมาเป็น issues แล้ว
  • process.exit(1) คือคำสั่งฆ่า Process ของตัวเองทิ้ง ตัวเลขที่ใส่คือ Exit Code โดย 0 แปลว่าจบแบบปกติ ส่วน 1 แปลว่าจบเพราะมีข้อผิดพลาด ซึ่งจำเป็นมากเพราะ CI/CD และ Hosting Provider จะดูตัวเลขนี้เพื่อตัดสินว่า Deploy สำเร็จหรือไม่

ปิดท้ายไฟล์ด้วย Helper และ Export

export const isProd = () => env.APP_STAGE === 'production'
export const isDev = () => env.APP_STAGE === 'dev'
export const isTest = () => env.APP_STAGE === 'test'

export { env }
export default env

Helper สามตัวนี้หน้าตาเหมือนตัวแปร Boolean ที่เราเขียนไว้บนหัวไฟล์ แต่ต่างกันตรงที่ชุดนี้อ้างอิงจาก env ที่ผ่านการตรวจแล้ว เราจะได้เรียกใช้จากที่ไหนก็ได้ในแอปโดยไม่ต้องไปเขียนเงื่อนไขเทียบ String ซ้ำ ๆ ซึ่งวันหนึ่งถ้าเราเปลี่ยนชื่อ Stage เราจะได้แก้ที่เดียว

ไฟล์ env.ts ฉบับสมบูรณ์

เราเขียนไฟล์นี้กันมาทีละท่อนตั้งแต่บทที่แล้ว ลองถอยออกมาดูภาพรวมกันหน่อยว่าเมื่อประกอบทุกส่วนเข้าด้วยกันแล้ว env.ts ทั้งไฟล์หน้าตาเป็นแบบนี้

import { env as loadEnv } from 'custom-env'
import { z } from 'zod'

process.env.APP_STAGE = process.env.APP_STAGE || 'dev'

const isProduction = process.env.APP_STAGE === 'production'
const isDevelopment = process.env.APP_STAGE === 'dev'
const isTesting = process.env.APP_STAGE === 'test'

if (isDevelopment) {
  loadEnv()
} else if (isTesting) {
  loadEnv('test')
}

const envSchema = z.object({
  NODE_ENV: z
    .enum(['development', 'test', 'production'])
    .default('development'),

  APP_STAGE: z.enum(['dev', 'test', 'production']).default('dev'),

  PORT: z.coerce.number().positive().default(3000),
  DATABASE_URL: z.string().startsWith('postgresql://'),
  JWT_SECRET: z.string().min(32, 'Must be 32 chars long'),
  JWT_EXPIRES_IN: z.string().default('7d'),
  BCRYPT_ROUNDS: z.coerce.number().min(10).max(20).default(12),
})

export type Env = z.infer<typeof envSchema>
let env: Env

try {
  env = envSchema.parse(process.env)
} catch (e) {
  if (e instanceof z.ZodError) {
    console.log('Invalid env var')
    console.error(JSON.stringify(e.flatten().fieldErrors, null, 2))

    e.issues.forEach((err) => {
      const path = err.path.join('.')
      console.log(`${path}: ${err.message}`)
    })

    process.exit(1)
  }

  throw e
}

export const isProd = () => env.APP_STAGE === 'production'
export const isDev = () => env.APP_STAGE === 'dev'
export const isTest = () => env.APP_STAGE === 'test'

export { env }
export default env

ไล่จากบนลงล่างจะเห็นว่าไฟล์นี้เล่าเรื่องเป็นลำดับชัดเจน คือรู้ก่อนว่าตัวเองรันอยู่ Stage ไหน แล้วโหลดไฟล์ .env ให้ถูกไฟล์ จากนั้นประกาศกฎของตัวแปรทั้งหมดไว้ใน Schema เอากฎไปตรวจค่าจริง ถ้าไม่ผ่านก็ตายทันทีพร้อมบอกเหตุผล และถ้าผ่านก็ Export ออกไปให้ทั้งแอปใช้

ใช้ env จริงใน src/index.ts

ตอนนี้ env.ts พร้อมแล้ว กลับไปแก้ Entry Point ของเราให้เป็นแบบนี้

import { env } from '../env.ts'
import app from './server.ts'

app.listen(env.PORT, () => {
  console.log(`Server running on port ${env.PORT}`)
  console.log(`Environment: ${env.APP_STAGE}`)
})

ลองพิมพ์ env. ใน Editor ดู คุณจะเห็นรายชื่อตัวแปรทั้งหมดโผล่มาให้เลือก และ env.PORT ก็เป็น number เรียบร้อยแล้วไม่ใช่ string | undefined อีกต่อไป นี่คือผลตอบแทนของงานที่เราเพิ่งทำไป

ทดลองของจริงด้วยการลบทุกบรรทัดใน .env ออกให้หมด แล้วรัน npm run dev ใหม่ คุณจะได้เห็นแบบนี้

Invalid env var
{
  "DATABASE_URL": [
    "Required"
  ],
  "JWT_SECRET": [
    "Required"
  ]
}

Server ไม่ยอมสตาร์ทเลยแม้แต่นิดเดียว ซึ่งเป็นสิ่งที่เราต้องการเป๊ะ ๆ ให้ใส่ค่ากลับเข้าไปใน .env จะเป็นค่าอะไรก็ได้ตอนนี้ ขอแค่ DATABASE_URL ขึ้นต้นด้วย postgresql:// และ JWT_SECRET ยาวเกิน 32 ตัวอักษร แล้วรันใหม่อีกครั้ง

มีอีกเรื่องที่ต้องรู้ไว้ คือถ้าคุณแก้ไฟล์ .env คุณต้องรีสตาร์ท Server เอง เพราะ Flag --watch เฝ้าดูแค่ไฟล์โค้ด ไม่ได้เฝ้าไฟล์ .env ให้

เทคนิคเพิ่มเติมที่ทำได้

พอ Environment เป็น Code แล้ว เราจะต่อยอดอะไรก็ได้ ตัวอย่างที่ใช้กันบ่อยคือตั้งกฎหรือค่า Default ต่างกันตาม Stage โดยใช้ตัวแปร Boolean ที่เราเขียนไว้บนหัวไฟล์มาช่วย

LOG_LEVEL: z
  .enum(['error', 'warn', 'info', 'debug', 'trace'])
  .default(isProduction ? 'info' : 'debug'),

ด้วยวิธีเดียวกันนี้ เราทำให้ตัวแปรบางตัวบังคับเฉพาะตอน Production แต่ไม่บังคับตอนพัฒนาก็ได้ หรือจะใช้เป็น Feature Flag เพื่อเปิดปิดฟีเจอร์โดยไม่ต้อง Deploy ใหม่ก็ได้เช่นกัน

ส่วนเรื่องความปลอดภัย มีสามข้อที่ควรจำติดตัวไว้

  • อย่า Commit .env ขึ้น GitHub เด็ดขาด ย้ำอีกครั้งเพราะเป็นข้อที่คนพลาดกันมากที่สุด
  • หมุนเปลี่ยน Secret เป็นระยะ (Rotate) คือการสร้างค่าใหม่แล้วยกเลิกค่าเก่าทุก ๆ ช่วงเวลาหนึ่ง เหมือนการเปลี่ยนรหัสผ่านตามรอบ เผื่อวันที่ค่าเก่าหลุดออกไปโดยที่เราไม่รู้ตัว
  • โปรเจกต์ใหญ่ให้ใช้ Secrets Manager เช่น HashiCorp Vault แนวคิดคือเก็บ Environment Variables ทั้งหมดไว้ที่เดียว แล้วแอปดึงไปใช้ผ่าน SDK หรือ URL เส้นเดียว คล้ายหน้า Settings ของ Hosting Provider แต่ไม่ผูกกับเจ้าใดเจ้าหนึ่ง และใช้บนเครื่องตัวเองได้ด้วย ข้อดีคือคนเข้าใหม่แค่ต่อเข้า Vault ก็ทำงานได้ทันทีโดยไม่ต้องรู้ค่าจริงสักตัว

โปรเจกต์ใหญ่ ๆ ในโลกจริงมีตัวแปรเกินร้อยตัวก็มี ถ้าไม่มีไฟล์อย่าง env.ts คงไม่มีใครในทีมจำได้ว่าตัวแปรไหนมีอยู่บ้างและตัวไหนบังคับ ลงทุนเขียนไฟล์นี้ครั้งเดียวตอนเริ่มโปรเจกต์ คุ้มกว่ามานั่งไล่บั๊กทีหลังเสมอ

รากฐานของ Server เราแน่นพอแล้ว บทถัดไปเราจะเริ่มเข้าเรื่อง HTTP Verbs และการออกแบบ Route ให้เป็น RESTful กัน
