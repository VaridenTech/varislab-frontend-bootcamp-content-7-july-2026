ใช้ PostgreSQL บนคลาวด์ด้วย Neon

Schema เราพร้อมแล้ว แต่ยังไม่มี Database จริงให้มันไปนอน บทนี้เราจะได้ฐานข้อมูลจริง ต่อโค้ดเข้าไป แล้วยิง Schema ขึ้นไปครั้งแรก

ขอ Database ฟรีจาก Neon

ถ้าคุณติดตั้ง PostgreSQL ไว้บนเครื่องอยู่แล้ว (เวอร์ชัน 16 ขึ้นไปกำลังดี) และถนัดใช้มันอยู่ ใช้ตัวนั้นได้เลย ประสบการณ์เหมือนกันทุกอย่าง เพราะปลายทางก็คือ PostgreSQL เหมือนกัน

สำหรับคนที่ไม่อยากติดตั้งอะไรเพิ่ม ผมเตรียมทางลัดไว้ให้ ไปที่ neon.new

Neon เป็นบริษัทที่ให้บริการ PostgreSQL แบบ Managed คือดูแลเครื่องให้เราทั้งหมด มีเจ้าอื่นแบบนี้อีกเยอะ แต่ Neon เป็นเจ้าโปรดของผม และมีของเล่นชื่อ Launchpad ที่สะดวกมาก

พอเข้าเว็บให้กดปุ่ม Try in the Browser ยืนยันว่าคุณเป็นมนุษย์ แล้วมันจะสร้าง Database ให้ทันที ไม่ต้องสมัครสมาชิก ไม่ต้องใส่บัตร

คุณจะเห็นข้อความว่านี่เป็น Database ที่ยังไม่มีเจ้าของ และจะหมดอายุใน 72 ชั่วโมงถ้าไม่สมัครบัญชี ซึ่งนานเกินพอสำหรับคอร์สนี้ ให้ก๊อป Connection String เก็บไว้ หรือเปิดหน้านั้นค้างไว้ก่อนก็ได้

ใส่ Connection String ลง .env

เปิดไฟล์ .env ที่รากโปรเจกต์ แล้วใส่ค่าที่ก๊อปมา

DATABASE_URL=postgresql://user:password@ep-xxxx.neon.tech/neondb?sslmode=require

ระวังให้ดีว่าใส่ลง .env ไม่ใช่ .env.example และไม่ใช่ .env.test ทั้งสองไฟล์นั้นทำหน้าที่คนละอย่างตามที่เราคุยกันไปในบทที่ 5

สังเกตว่าค่าที่ Neon ให้มาขึ้นต้นด้วย postgresql:// พอดี ซึ่งตรงกับกฎที่เราเขียนไว้ใน env.ts ตั้งแต่บทที่ 6 ว่า

DATABASE_URL: z.string().startsWith('postgresql://'),

ถ้าใครวางค่าผิดชนิดมา Server จะไม่ยอมสตาร์ทตั้งแต่วินาทีแรก ซึ่งคือสิ่งที่เราออกแบบไว้ตั้งแต่ต้น และอย่าลืมว่า Flag --watch ไม่ได้เฝ้าไฟล์ .env เพราะฉะนั้นแก้เสร็จต้องรีสตาร์ท Server เอง

Connection Pool คืออะไร และทำไมต้องมี

ก่อนจะเขียนโค้ดเชื่อมต่อ ขออธิบายเรื่องหนึ่งก่อน

Server ของเราเป็น Server ที่รันค้างไว้ยาว ๆ และรับ Request เข้ามาเรื่อย ๆ เราไม่อยากเปิดการเชื่อมต่อใหม่ทุกครั้งที่มี Request เข้ามา เพราะการสร้าง Connection แพงมากในเชิงการคำนวณ ทั้งการเปิด TCP และการยืนยันตัวตน แถม Database เองก็จำกัดจำนวน Connection ที่รับได้พร้อมกัน

ทางออกคือ Connection Pool แนวคิดง่ายมาก คือเปิด Connection ไว้กลุ่มหนึ่งแล้วใช้ซ้ำ ใครต้องการก็ยืมไปใช้แล้วคืนเข้ากอง คนต่อไปยืมต่อได้ทันทีโดยไม่ต้องเปิดใหม่

// แบบไม่มี Pool — เปิดใหม่ทุกครั้ง เปลืองมาก
const client = new Client({ connectionString })
await client.connect()
const result = await client.query('SELECT * FROM users')
await client.end()

// แบบมี Pool — ยืมและคืนให้เองอัตโนมัติ
const pool = new Pool({ connectionString })
const result = await pool.query('SELECT * FROM users')

แต่ Pool มีปัญหาของมันเอง และตัวที่จะกัดเราตอนพัฒนาคือเรื่อง Hot Reload เพราะเรารัน Server ด้วย node --watch ทุกครั้งที่เราเซฟไฟล์ Server จะรีสตาร์ทและสร้าง Pool ใหม่ แต่Pool เก่ายังเปิดค้างอยู่ เซฟสิบครั้งก็สิบ Pool สุดท้ายจะเจอ Error ว่า Connection เต็ม

วิธีแก้คือทำให้ Pool เป็น Singleton คือค่าที่ถูกสร้างครั้งเดียวแล้วใช้ซ้ำตลอด โดยเก็บมันไว้บน Global Object ซึ่งไม่ถูกล้างตอน Node.js โหลดไฟล์ใหม่ คิดง่าย ๆ ว่าเหมือนตอนที่เราแปะค่าไว้บน window ในเบราว์เซอร์เพื่อใช้ซ้ำ

เราจะใช้ Package เล็ก ๆ ชื่อ @epic-web/remember ทำงานนี้ให้ มันไม่ได้ทำอะไรมหัศจรรย์เลย โค้ดข้างในไม่กี่บรรทัด แค่แปะค่าไว้บน Global ให้เราเท่านั้น แต่ก็ไม่มีเหตุผลที่จะเขียนเอง

เขียน src/db/connection.ts

ติดตั้งของที่ยังขาด

npm install pg @epic-web/remember

แล้วสร้างไฟล์ src/db/connection.ts ข้าง ๆ schema.ts

import { drizzle } from 'drizzle-orm/node-postgres'
import { Pool } from 'pg'
import * as schema from './schema.ts'
import { env, isProd } from '../../env.ts'
import { remember } from '@epic-web/remember'

const createPool = () => {
  return new Pool({
    connectionString: env.DATABASE_URL,
  })
}

let client

if (isProd()) {
  client = createPool()
} else {
  client = remember('dbPool', () => createPool())
}

export const db = drizzle({ client, schema })
export default db

ไล่อ่านทีละส่วน

  • drizzle-orm/node-postgres คือ Driver ที่ Drizzle เตรียมไว้สำหรับ Package pg Drizzle รองรับ Driver ของ PostgreSQL หลายตัว เราเลือกตัวนี้เพราะเป็นตัวมาตรฐานที่สุด
  • import * as schema from './schema.ts' อ่านว่า "เอาทุกอย่างที่ Export จากไฟล์นั้น ยัดใส่ Object แล้วเรียกมันว่า schema" เราต้องส่งทั้งก้อนให้ Drizzle เพื่อให้มันรู้จักทั้งตารางและ Relation ที่เราประกาศไว้
  • เราใช้ env.DATABASE_URL ที่ผ่านการตรวจแล้วจาก env.ts ไม่ใช่ process.env ดิบ ๆ
  • ถ้าอยู่บน Production เราสร้าง Pool ตรง ๆ ไปเลย เพราะไม่มี Hot Reload ให้ต้องกังวล โค้ดบรรทัดนี้จะรันแค่ครั้งเดียวตอน Server สตาร์ท ถ้าไม่ใช่ Production ค่อยห่อด้วย remember
  • 'dbPool' คือชื่อที่ค่านี้จะไปนั่งอยู่บน Global Object จะตั้งชื่ออื่นก็ได้
  • drizzle({ client, schema }) คือตัว ORM จริง ๆ ที่เราจะ Import ไปใช้ทั่วแอป

ย้ำอีกครั้งว่าเรื่อง remember ทั้งหมดนี้มีอยู่เพราะ Hot Reload ตอนพัฒนาอย่างเดียว ไม่มีเหตุผลอื่นเลย และถ้าคุณใช้ Database ที่คุยผ่าน HTTP แทน (ซึ่ง Neon ก็รองรับ) ก็ไม่ต้องมีเรื่องพวกนี้เลยเพราะไม่มี Connection ให้ค้าง

ตั้งค่า drizzle.config.ts

Drizzle มี CLI ชื่อ drizzle-kit ที่รับงานฝั่ง Migration ให้เราตามที่คุยกันในบทที่ 15 แต่มันต้องรู้ก่อนว่า Schema อยู่ไหนและ Database อยู่ไหน นั่นคือหน้าที่ของไฟล์ drizzle.config.ts ที่รากโปรเจกต์

import { defineConfig } from 'drizzle-kit'
import env from './env.ts'

export default defineConfig({
  schema: './src/db/schema.ts',
  out: './migrations',
  dialect: 'postgresql',
  dbCredentials: {
    url: env.DATABASE_URL,
  },
  verbose: true,
  strict: true,
})

out คือโฟลเดอร์ที่ไฟล์ Migration จะไปอยู่ verbose คือให้แสดง SQL ที่มันกำลังจะรันให้เราดูก่อนเสมอ และ strict คือให้ถามยืนยันก่อนลงมือ สองตัวหลังนี้เปิดไว้เถอะ เพราะการเห็นสิ่งที่กำลังจะเกิดกับข้อมูลของเราก่อนคือเรื่องที่ดีเสมอ

เพิ่ม db Scripts ใน package.json

วิธีคุยกับ Database ในระดับการดูแลระบบที่สะดวกที่สุดคือทำเป็น Script ไว้ใน package.json ผมชอบตั้งชื่อโดยขึ้นต้นด้วยชื่อ Resource ในที่นี้คือ db: เพื่อให้เห็นเป็นกลุ่มเดียวกัน

"scripts": {
  "dev": "node --watch src/index.ts",
  "start": "node src/index.ts",
  "db:generate": "drizzle-kit generate",
  "db:push": "drizzle-kit push",
  "db:migrate": "drizzle-kit migrate",
  "db:studio": "drizzle-kit studio",
  "db:seed": "node src/db/seed.ts"
}

สี่ตัวแรกเรียก drizzle-kit ซึ่งอยู่ใน devDependencies อยู่แล้ว ส่วนตัวสุดท้ายไม่ใช่คำสั่งของ Drizzle มันแค่สั่ง Node.js ให้รันไฟล์ ซึ่งเราจะเขียนกันในบทหน้า

  • db:generate — สร้างไฟล์ SQL ของ Migration จากส่วนต่างของ Schema ใช้ตอนแก้ Schema เสร็จและพร้อมเปิด PR
  • db:push — ยัด Schema ปัจจุบันเข้า Database ตรง ๆ ไม่สร้างไฟล์ Migration ใช้ตอนพัฒนา ตัวนี้จะใช้บ่อยที่สุด
  • db:migrate — ไล่รันไฟล์ Migration ที่ค้างอยู่ ใช้ตอน Deploy ขึ้น Production
  • db:studio — เปิดเครื่องมือดูข้อมูลแบบภาพ ใช้ตอนไล่ปัญหาหรืออยากส่องข้อมูล
  • db:seed — ใส่ข้อมูลตัวอย่างลง Database

Push Schema ขึ้น Database ครั้งแรก

Database ที่เราเพิ่งได้มายังว่างเปล่า ไม่มีตารางสักตาราง และมันเป็น Database สำหรับพัฒนาของเราคนเดียว ไม่มีข้อมูลจริงของใคร เพราะฉะนั้นไม่ต้องทำ Migration ให้ยุ่งยาก Push ไปเลย

npm run db:push

เพราะเราเปิด verbose ไว้ มันจะพ่น SQL ทั้งชุดที่กำลังจะรันออกมาให้ดูก่อน ซึ่งก็คือ CREATE TABLE ของทั้งห้าตารางพร้อม Constraint และ Index ทั้งหมด

ลองอ่านมันสักรอบ นี่คือ SQL ที่เราจะต้องเขียนเองถ้าไม่มี Drizzle และมันก็คือหน้าตาของ Migration ตัวแรกของทุกโปรเจกต์พอดี เพราะ Migration แรกก็คือการสร้างตารางนั่นเอง กด Yes เพื่อยืนยัน แล้วมันจะบอกว่าเปลี่ยนแปลงเรียบร้อย

ถ้าลองสั่ง npm run db:push ซ้ำอีกรอบ คราวนี้มันจะบอกว่าไม่พบการเปลี่ยนแปลง เพราะสิ่งที่อยู่ใน Database กับสิ่งที่อยู่ใน Schema ตรงกันเป๊ะแล้ว

ส่อง Database ด้วย Drizzle Studio

npm run db:studio

Drizzle มี Web App สำหรับดูข้อมูลแบบภาพติดมาให้ด้วย คำสั่งนี้จะเปิดมันขึ้นมาแล้วให้ URL มาเส้นหนึ่ง กดเข้าไปในเบราว์เซอร์ได้เลย

หน้าตาของแต่ละคนอาจไม่เหมือนกันเพราะเปลี่ยน Theme ได้ แต่สิ่งที่เราอยากเห็นตอนนี้มีอย่างเดียว คือตารางทั้งห้าที่เราเขียนไว้ปรากฏอยู่ครบ ถ้าเห็นครบก็แปลว่า Schema ของเราขึ้นไปนั่งอยู่บน Database เรียบร้อยแล้ว

ใน Studio ยังทำได้อีกหลายอย่าง ทั้งเพิ่มแก้ข้อมูลด้วยมือ รัน SQL ดิบ เขียนโค้ด Drizzle ที่ผูกกับ Schema ของเราจริง ๆ และดูโครงสร้าง Schema ในรูปแบบ SQL

ตอนนี้ตารางมีแล้วแต่ยังไม่มีข้อมูลสักแถว บทหน้าเราจะเขียน Seed Script เพื่อใส่ข้อมูลตัวอย่างลงไปให้ครบทุกตาราง
