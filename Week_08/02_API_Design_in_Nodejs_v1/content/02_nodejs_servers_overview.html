ภาพรวมการสร้าง Server ด้วย Node.js

ก่อนจะลงมือเขียนโค้ด เรามาปรับมุมมองกันก่อน เพราะการย้ายจากงาน Frontend มาทำ Backend ไม่ได้เปลี่ยนภาษา แต่เปลี่ยนสภาพแวดล้อมที่ภาษานั้นทำงานอยู่

ภาษาเดียวกัน แต่คนละ Runtime

JavaScript ที่คุณเขียนใน Browser กับที่เขียนใน Node.js เป็นภาษาเดียวกันเป๊ะ ๆ ตัว Engine ที่รันมันก็ตัวเดียวกัน คือ V8 ของ Chrome เพียงแต่มีคนหยิบ V8 ออกมาวางไว้บนระดับ Operating System ให้เรารันในเทอร์มินัลได้

สิ่งที่ต่างกันคือ "ของแถม" รอบ ๆ Engine ต่างหาก

  • Global Object — บน Browser คือ window ส่วนบน Node.js คือ global หรือ globalThis
  • API ที่ใช้ได้ — Browser ให้ DOM API และ Web API มาเพื่อทำงานกับหน้าจอ ส่วน Node.js ให้ File System, Networking, Process Management และ Crypto มาเพื่อทำงานกับเครื่อง
  • สิ่งที่หายไป — บน Node.js ไม่มี document ไม่มี window และไม่มี DOM ให้เล่น
  • Security — ข้อนี้สำคัญที่สุด

เรื่อง Security คือจุดที่คนย้ายมาจาก Frontend มักไม่ทันคิด บน Browser เราได้ความปลอดภัยมาฟรี ๆ เพราะ Browser ทำ Sandbox ครอบไว้ให้ โค้ดในหน้าเว็บอ่านไฟล์ในเครื่องคุณไม่ได้ ยิง Request ข้ามโดเมนมั่ว ๆ ไม่ได้ แต่บน Node.js ไม่มีใครกั้นให้ โค้ดที่รันมีสิทธิ์เท่ากับผู้ใช้ที่รันมัน ความปลอดภัยจึงกลายเป็นความรับผิดชอบของเราเอง

เรื่อง Module ก็เหมือนกัน สมัยก่อน Node.js ใช้ CommonJS แต่เวอร์ชันใหม่ ๆ รองรับ ES Modules (ESM) แล้ว คอร์สนี้เราจะใช้ ESM ล้วน ๆ คือ import และ export แบบเดียวกับที่คุณคุ้นเคยบน Frontend

Client กับ Server ต่างกันตรงไหน

Client คือโปรแกรมที่รันอยู่บนเครื่องของผู้ใช้แต่ละคน จะเป็นเว็บ แอปมือถือ แอปบนสมาร์ตทีวี หรือโปรแกรมเดสก์ท็อปก็ได้ ทุกคนมีสำเนาของตัวเองและกินทรัพยากรของเครื่องตัวเอง

Server คือคอมพิวเตอร์กลางเครื่องเดียวที่ทุกคนใช้ร่วมกัน และตรงนี้คือความต่างที่สำคัญมาก

ถ้าเว็บฝั่ง Client พังขึ้นมา เช่นมี Animation ที่ทำให้หน้าจอค้าง คนที่เดือดร้อนคือคุณคนเดียว รีเฟรชหน้าเว็บก็จบ แต่ถ้า Server พัง ทุกคนใช้งานไม่ได้พร้อมกันทั้งหมด เพราะทุก Client แชร์ Server ตัวเดียวกันอยู่ นี่คือเหตุผลว่าทำไมเรื่อง Error Handling บน Backend ถึงซีเรียสกว่ามาก และเป็นเรื่องที่เราจะเรียนกันจริงจังในบทที่ 28

เปลี่ยนมุมจากคนเรียก เป็นคนรับ

สมัยทำ Frontend คุณเป็นฝ่าย "เรียก" ก็จะเขียนประมาณนี้

const data = await fetch('/api/users')
const users = await data.json()

คำถามคือแล้วปลายทาง /api/users มันมาจากไหน คำตอบคือมีใครสักคนไปเขียน Route ไว้ฝั่ง Server และตั้งแต่นี้ไปคนคนนั้นก็คือคุณ

app.get('/api/users', async (req, res) => {
  const users = await db.query('SELECT * FROM users')
  res.json(users)
})

พูดให้สั้นที่สุด Server ก็คือตัว Router ที่จับคู่ URL เข้ากับโค้ด ที่เหลือทั้งหมดในคอร์สนี้เป็นเพียงส่วนเสริมที่ทำให้การจับคู่นั้นปลอดภัย ตรวจสอบได้ และดูแลต่อได้

Backend มีกี่แบบ

คำว่า Backend ทุกวันนี้ไม่ได้หมายถึง Server แบบเดียวอีกแล้ว ลองดูภาพรวมกัน

  • Long-lived Server — โปรแกรมที่เปิดค้างไว้ตลอด คอยรับ Request ไปเรื่อย ๆ นึกภาพเป็น Loop ที่ไม่มีวันจบ มันจะไม่หยุดจนกว่าเราจะสั่งหยุดหรือมันพังไปเอง ข้อดีคือเก็บ State ระหว่าง Request ได้และรองรับ WebSocket ได้ นี่คือแบบที่เราจะสร้างในคอร์สนี้
  • Serverless Function — Function ที่หลับอยู่เฉย ๆ จะตื่นขึ้นมาทำงานก็ต่อเมื่อมีคนเรียก พอทำเสร็จก็ดับไป จ่ายเงินเฉพาะตอนที่รันจริง แต่แลกมาด้วยข้อจำกัดเรื่องความเร็วตอนเริ่มและใช้ของที่ต้องเชื่อมต่อยาว ๆ อย่าง WebSocket ไม่ได้
  • Edge Function — Serverless ที่ไปรันอยู่บน CDN ซึ่งเป็นเครือข่ายเครื่องที่กระจายสำเนาไฟล์ไว้ทั่วโลกเพื่อให้ผู้ใช้โหลดได้เร็ว จุดเด่นคือใกล้ผู้ใช้มาก แต่ Runtime มักไม่ครบเท่า Node.js เต็ม ๆ
  • Background Job — งานที่แยกออกไปทำนอกวงจร Request-Response เช่นส่งอีเมล ประมวลผลรูปภาพ หรืองานที่นานเกินกว่าจะให้ผู้ใช้นั่งรอ
  • Cron Job — Background Job ชนิดที่ทำงานตามตารางเวลา เช่นสรุปรายงานทุกเที่ยงคืน หรือล้างข้อมูลเก่าทุกสัปดาห์

จาก http module สู่ Framework

ถ้าคุณผ่านคอร์ส Node.js เบื้องต้นมา คุณเคยสร้าง Server ด้วย Module http ล้วน ๆ มาแล้ว หน้าตาประมาณนี้

import http from 'node:http'

const server = http.createServer((req, res) => {
  res.writeHead(200, { 'Content-Type': 'text/html; charset=utf-8' })
  res.end('<h1>สวัสดี</h1>')
})

server.listen(3000)

โค้ดชุดนี้ทำงานได้จริงและไม่ต้องติดตั้งอะไรเพิ่มเลย แต่สังเกตว่ามันตอบเหมือนกันหมดไม่ว่าจะขอ Path ไหน เพราะเรายังไม่ได้ดู req.url ถ้าจะทำ API จริงจัง เราต้องเขียนเองทั้งหมด ตั้งแต่แยก Path แยก HTTP Verb อ่าน Body ที่ส่งมาเป็น JSON ไปจนถึงจัดการ Error

Express คือ Framework ที่มาเติมงานน่าเบื่อพวกนั้นให้เรา สิ่งที่ Express ให้มาคือ

  • Routing — จับคู่ URL กับ HTTP Verb เข้ากับโค้ดของเราแบบอ่านง่าย
  • Middleware — ระบบต่อ Function เป็นทอด ๆ เพื่อประมวลผล Request ก่อนถึงปลายทาง เป็นหัวใจของ Express ที่เราจะเรียนกันตั้งแต่บทที่ 10
  • Helper ของ Request และ Response — เช่น res.json() ที่ตั้ง Header ให้เสร็จสรรพ
  • ระบบนิเวศ — มี Package ให้ใช้มหาศาล เพราะ Express อยู่มานานและถูกใช้งานจริงในระดับ Production ทั่วโลก

Express อาจไม่ใช่ Framework ที่ใหม่ที่สุด แต่มันคือตัวเลือกที่ผ่านสนามจริงมาแล้วนับไม่ถ้วน และแนวคิดที่คุณได้จากมันย้ายไปใช้กับ Framework อื่นได้แทบทั้งหมด

สองเรื่องที่ควรติดหัวไว้

Stateless — ต่างจากแอป Frontend ที่เก็บ State ไว้ในหน่วยความจำได้ยาว ๆ HTTP Server มองทุก Request เป็นเรื่องอิสระต่อกัน State ตัวจริงอยู่ใน Database ไม่ใช่ในตัวแปรบน Server

Concurrency — Node.js ใช้ Event Loop กับ I/O แบบ Non-blocking หมายความว่า Thread เดียวรับ Request ได้พร้อมกันจำนวนมาก โดยอาศัยการทำงานแบบ Asynchronous ต่างจาก Server แบบดั้งเดิมที่แจก Thread ให้ทีละ Request
