Middleware ใน Express

ถ้าให้เลือกแนวคิดเดียวที่ทรงพลังที่สุดของ Express ผมเลือกคำนี้ทันที — Middleware มันคือสิ่งที่ผมเรียกว่ากระดูกสันหลังของ Web App สมัยใหม่ และถ้าคุณเคยเขียนแอปมาบ้าง คุณใช้มันมาแล้วแน่นอน แค่อาจจะไม่รู้ตัว

Middleware คืออะไรกันแน่

คำนี้กำกวมพอ ๆ กับคำว่า Caching คือทุกคนใช้กันหมดแต่คนละความหมาย ("Cache ที่ไหน Database? Network? เครื่อง Client?") ความจริงแล้วมันมีความหมายเดียว แค่ถูกเอาไปใช้ในหลายบริบท

Middleware คือโค้ดที่นั่งอยู่ตรงกลางระหว่างโค้ดสองก้อน มันอยู่ "ตรงกลาง" จึงชื่อ Middleware แค่นั้นเลย

ในบริบทของ API สิ่งที่เราทำมาตลอดคือ Request เข้ามา → เข้า Handler ของเรา → ส่ง Response กลับ ส่วน Middleware คือของที่ไปแทรกอยู่ระหว่างสองจุดนั้น

Request → Middleware 1 → Middleware 2 → ... → Handler → Response

และเพราะ Middleware ได้รับ req กับ res ตัวเดียวกันกับที่ Handler ได้รับ มันจึงทำได้ทุกอย่างที่ Handler ทำได้ คือ

  • อ่าน Request เช่นดู Header ดู IP ดู Path
  • แก้ไข Request หรือ Response เช่นแปะข้อมูล User ที่ถอดจาก Token ไว้ที่ req
  • ตัดจบ (Short-circuit) คือตอบกลับไปเลยโดยไม่ให้ถึง Handler
  • ส่งต่อ ให้ Middleware ตัวถัดไปทำงาน

Middleware มีอยู่ทุกชั้นของ Stack

ก่อนจะลงลึกที่ Express ขอให้เห็นภาพก่อนว่ารูปแบบเดียวกันนี้อยู่รอบตัวเราหมด

ชั้น Network (Edge Function) — ถ้าใช้ Next.js คุณจะเจอไฟล์ middleware.ts ที่เขียนได้ประมาณว่า "ถ้า Path ตรงกับ /about ให้ Redirect ไปหน้าแรก" ของแบบนี้ไม่ได้รันบน Server ของเรา แต่รันอยู่บน CDN ก่อน จะถึง Server ต้นทาง (Origin) ด้วยซ้ำ Cloudflare Workers ก็เป็นหนึ่งใน Edge Function ที่โปรแกรมได้ตัวแรก ๆ ของโลก และทำอะไรได้บ้าระห่ำมาก เช่นดู IP ของ Request ที่เข้ามาแล้วเปลี่ยนหัวข้อบนหน้าเว็บให้ตรงกับบริษัทของคนที่กำลังดูอยู่

Load Balancer และ Reverse Proxy — Nginx ที่ตั้งค่าให้เติม Header อย่าง X-Real-IP แล้วส่งต่อไปยัง Backend ข้างหลัง ก็คือ Middleware แบบดั้งเดิม มันไม่ได้ตอบอะไร แค่เติมของแล้วส่งต่อ

ฝั่ง Frontend — HTTP Interceptor ของ Axios ที่เติม JWT ให้ทุก Request ขาออกโดยที่เราไม่ต้องเขียนซ้ำทุกฟังก์ชัน หรือ Interceptor ขารับที่เช็คว่าถ้าได้ 401 ให้เด้งไปหน้า Login ก็คือ Middleware (Library ดึงข้อมูลเจ้าอื่นก็มีของแบบนี้กันหมด ไม่ว่าจะเป็น Apollo ของ GraphQL หรือตัวห่อ Fetch ต่าง ๆ)

axios.interceptors.request.use((config) => {
  config.headers.Authorization = `Bearer ${getToken()}`
  return config
})

แม้แต่ Component ครอบ Route ใน React ก็ใช่

const ProtectedRoute = ({ children }) => {
  const { user } = useAuth()
  if (!user) return <Navigate to="/login" />
  return children
}

Logic ตัวนี้นั่งอยู่ตรงกลางระหว่าง "สิ่งที่ผู้ใช้ขอ" กับ "ทรัพยากรที่เขาจะได้" เป๊ะตามนิยาม

Signature ของ Middleware ใน Express

Middleware ของ Express หน้าตาเหมือน Handler ทุกประการ ต่างกันแค่ มี Argument ตัวที่สาม ชื่อ next — นั่นคือสิ่งเดียวที่ทำให้มันเป็น Middleware

const logger = (req, res, next) => {
  console.log(`${req.method} ${req.path}`)
  next() // ส่งต่อให้ตัวถัดไปใน Stack
}
  • req — Request Object ที่เก็บ Body, Header, Params ทั้งหมดไว้
  • res — Response Object ที่ใช้ตอบกลับไปหา Client
  • next — Function สำหรับส่งต่อการควบคุมให้ Middleware ตัวถัดไปใน Stack

เบื้องหลังของ next ไม่มีเวทมนตร์อะไรเลย Express เก็บ Middleware ทุกตัวที่เราลงทะเบียนไว้เป็น Array ของ Function แล้วห่อแต่ละตัวด้วย Function ที่รู้ว่าตัวถัดไปคือใคร พอเราเรียก next() มันก็แค่ไปเรียกตัวถัดไปใน Array คิดง่าย ๆ ว่ามันคือ Loop ที่เราคุมจังหวะเดินเอง

ลำดับสำคัญเสมอ

Middleware ทำงานตามลำดับที่ลงทะเบียน คือบนลงล่างสำหรับ app.use() และซ้ายไปขวาสำหรับ Middleware ที่ใส่ไว้ในบรรทัดเดียวกับ Route

app.use(middleware1)  // ลำดับ 1
app.use(middleware2)  // ลำดับ 2

app.get('/test',
  middleware3,        // ลำดับ 3
  middleware4,        // ลำดับ 4
  finalHandler        // ลำดับ 5
)

ทุกครั้งที่เรียก next() Express จะเดินไปตัวถัดไป และถ้าไม่เหลือ Middleware แล้ว มันจะเดินไปที่ Handler ของ Route นั้น

Return ไม่ใช่ Response

ตรงนี้คือหัวใจของบทนี้ และเป็นจุดที่คนพลาดกันเยอะที่สุด

เมื่อ Request ถูกตอบไปแล้วครั้งหนึ่ง Connection จะถูกปิด เราตอบซ้ำไม่ได้ และคำสั่ง return ในโค้ดของเราไม่ใช่สิ่งเดียวกับการตอบ Response

// ระดับโค้ด: JavaScript เลิกทำงานใน Function นี้
return

// ระดับ Network: HTTP ยังรออยู่ "Response ของฉันอยู่ไหน"

เรากำลังจัดการของสองอย่างพร้อมกันคือ โค้ด กับ Network ให้คิดว่า res.json() คือคำสั่ง Return ของ HTTP Request แต่ไม่ใช่ Return ของ Function เรา ถ้าตอบไปแล้วโค้ดยังวิ่งต่อ แล้วบังเอิญมีการตอบอีกรอบ นั่นคือปัญหาใหญ่ (จริง ๆ คือส่ง Header ซ้ำไม่ได้ ซึ่งความหมายเดียวกัน) Express จะกลืนมันไปเงียบ ๆ ซึ่งยิ่ง Debug ยาก

กฎที่จำง่ายที่สุด: ถ้าจะตอบ Response ใน Middleware ให้ใส่ return นำหน้าเสมอ ยกเว้นมันเป็นบรรทัดสุดท้ายจริง ๆ

const authenticate = (req, res, next) => {
  if (!req.headers.authorization) {
    return res.status(401).json({ error: 'No token' })  // ตอบแล้วจบ ห้ามเรียก next()
  }
  next()
}

เมื่อไรควรเรียก next()

จากประสบการณ์จริง Middleware ที่เราเขียนจะมีแค่สองแบบ

  • แมลงวันเกาะกำแพง — แค่มาส่องดู Request หรือแปะข้อมูลเพิ่ม หรือทำ Side Effect ที่ไม่เกี่ยวกับ Request เช่นยิง Analytics แบบนี้เรียก next() เสมอ ไม่มีเงื่อนไข
  • ด่านตรวจ (Go / No-Go) — เช็คค่าบางอย่างว่าจริงหรือเท็จ ถ้าผ่านก็ next() ถ้าไม่ผ่านก็ res.json() ตัดจบตรงนั้น แบบนี้คือ Authentication, Authorization, Access Control หรือกระทั่ง "บัตรเครดิตคุณหมดอายุและค้างชำระ"

และมีอีกกฎที่ห้ามลืม — ถ้าไม่ตอบ ไม่โยน Error และไม่เรียก next() Request จะค้างตลอดกาล เพราะ Express ไม่รู้ว่าจะทำอะไรต่อ มันก็นั่งรออยู่อย่างนั้น ซึ่งอาการเหมือนกับการลืมตอบใน Handler เป๊ะ ๆ

// แย่ — Request ค้าง
const badMiddleware = (req, res, next) => {
  console.log('Did something')
  // ไม่เรียกทั้ง next() และ res.send()
}

next() รับ Argument ได้หนึ่งตัว

next รับ Argument ได้แค่ตัวเดียว และไม่ว่าคุณจะส่งอะไรเข้าไป Express ถือว่านั่นคือ Error ต่อให้เป็น String คำว่า 'yes' ก็ตาม

const riskyMiddleware = async (req, res, next) => {
  try {
    await someDatabaseOperation()
    next()        // สำเร็จ ไปต่อ
  } catch (error) {
    next(error)   // พัง ส่งให้ Error Handler
  }
}

ความหมายของมันคือ "มีเรื่องไม่ดีเกิดขึ้น ช่วยข้ามทุกอย่างที่เหลือ แล้วกระโดดไปที่ Error Handler Middleware ทีเถอะ" ถ้าเราลงทะเบียน Error Handler ไว้เองมันจะไปที่ตัวนั้น ถ้าไม่มีก็ใช้ตัวที่ Express ติดมาให้ เราจะเขียนของเราเองในบทที่ 28 และเซอร์ไพรส์ครับ — Error Handler ก็คือ Middleware ทุกอย่างใน Express คือ Middleware

เกร็ด: res.json() ทำอะไรให้เราบ้าง

ระหว่างทางมีคำถามว่า res.json() กับ res.send() ต่างกันไหม คำตอบคือทุกอย่างคือ send ส่วน json เป็นแค่ตัวห่ออีกที ที่เรียก JSON.stringify() ให้ แล้วเซ็ต Header บอก Client ว่านี่คือ JSON

res.json({ ok: true })

// เทียบเท่ากับการทำเองแบบนี้
res.setHeader('Content-Type', 'application/json')
res.send(JSON.stringify({ ok: true }))

เหตุผลที่ต้อง Stringify คือเราส่ง Object ข้ามสายไม่ได้ สิ่งที่ส่งข้ามสายได้มีแค่ String, Number, Boolean เท่านั้น (จริง ๆ ก็คือ String ทั้งหมดนั่นแหละ) และถ้าไม่เซ็ต Header ให้ Client รู้ มันก็จะไม่ถูก Parse เป็น JSON

ทำไมรูปแบบนี้ถึงชนะ

ผมคิดว่ารูปแบบ (req, res, next) นี่แหละคือสิ่งที่ทำให้ Node.js ดังเปรี้ยงในยุคนั้น เพราะในเวลาเดียวกัน การเขียน Server ด้วย Java หรือ Python ยากกว่านี้มาก

จนถึงวันนี้ Framework ใหม่ ๆ อย่าง Fastify, NestJS หรือ Hono ต่างก็ได้แรงบันดาลใจจากตรงนี้ ส่วนหนึ่งเพื่อให้ยังเข้ากันได้กับ Middleware จำนวนมหาศาลที่มีคนเขียนไว้แล้ว (สมัยก่อนมี Package Middleware ของ Express เยอะพอ ๆ กับ Package React ทุกวันนี้) เหตุผลที่มันชนะคือ Mental Model เข้าใจง่าย ประกอบร่างกันได้ ใช้ซ้ำได้ และยืดหยุ่นพอจะทำได้ทุกเรื่องตั้งแต่ Auth ยัน Logging

บทหน้าเราจะเอาแนวคิดนี้ไปใช้จริง โดยติดตั้ง Middleware ระดับ Global ที่ทุกโปรเจกต์ควรมีเข้าไปใน src/server.ts ของเรา
