Security Best Practices

ระบบ Auth ของเราทำงานครบวงจรแล้ว บทนี้เป็นบทเก็บกวาด รวมทุกอย่างที่ควรรู้ก่อนเอาของแบบนี้ขึ้น Production จริง

ไม่ต้องท่องจำนะครับ อ่านให้เข้าใจเหตุผลของแต่ละข้อพอ แล้วเวลาไปเจอของจริงคุณจะนึกออกเอง

ห้าม Log Token เด็ดขาด

Token คือกุญแจ ใครถือก็เข้าได้ การ Log มันออกมาเท่ากับก๊อปกุญแจไปวางไว้ในไฟล์ Log ที่ทั้งทีมเข้าถึงได้ แถมมักถูกส่งต่อไปยังบริการ Log ภายนอกอีกทอดหนึ่ง

ครั้งเดียวที่ผมเคยต้อง Log Token คือตอนที่สงสัยว่ามีคนขโมย Token ไปจริง ๆ นอกจากเคสแบบนั้นก็ไม่มีเหตุผลอื่น และนี่คือเหตุผลที่ผมย้ำให้ลบ console.log(payload) ทิ้งหลังทดสอบเสร็จในบทที่แล้ว

ดูแล Secret ให้ดี

JWT_SECRET คือสิ่งเดียวที่กั้นระหว่างระบบของคุณกับคนที่ปลอมตัวเป็น Admin ได้

  • ยาวและสุ่มจริง — เราตั้งเงื่อนไขไว้ใน env.ts ตั้งแต่บทที่ 6 ว่าต้องยาวอย่างน้อย 32 ตัวอักษร ให้ใช้ค่าที่สุ่มมาจริง ๆ ไม่ใช่คำที่พิมพ์เอาเอง
  • อยู่ใน .env เท่านั้น — และ .env ต้องอยู่ใน .gitignore เสมอ ส่วน .env.example ที่ Commit ขึ้นไปให้ใส่แค่ชื่อตัวแปร ไม่ใส่ค่า
  • คนละค่าในแต่ละ Environment — Secret ของเครื่องคุณกับของ Production ต้องไม่ใช่ค่าเดียวกัน ไม่งั้น Token ที่ออกจากเครื่องคุณจะใช้กับ Production ได้จริง
  • เปลี่ยนได้เสมอถ้าสงสัยว่าหลุด — ผลข้างเคียงคือทุกคนจะถูกเตะออกพร้อมกัน ซึ่งบางครั้งก็เป็นสิ่งที่เราต้องการพอดี

ประโยชน์อีกข้อของการมี env.ts คือแอปจะไม่ยอมสตาร์ทเลยถ้า Secret หายไปหรือสั้นเกินไป ดีกว่าไปพังเงียบ ๆ ตอน Production มีคนใช้งานอยู่

จำนวนรอบของ bcrypt

ค่า BCRYPT_ROUNDS คือการชั่งน้ำหนักระหว่างความปลอดภัยกับความเร็ว

// น้อยไป เร็วแต่ไม่ปลอดภัย
await bcrypt.hash(password, 4)

// ค่าที่แนะนำกัน ปลอดภัยและยังเร็วพอ
await bcrypt.hash(password, 12)

ทุกครั้งที่เพิ่มขึ้นหนึ่ง งานจะหนักขึ้นเป็นสองเท่า ทั้งของเราและของคนที่พยายามเดารหัสผ่าน ค่าที่วงการใช้กันอยู่ตอนนี้คือ 10 ถึง 12 ซึ่งเป็น Default ของเราอยู่แล้ว และเพราะมันอยู่ใน Environment Variable เราจึงปรับขึ้นได้ในอนาคตโดยไม่ต้องแก้โค้ด

อีกข้อที่ย้ำไปแล้วแต่ขอย้ำอีก — ใช้เวอร์ชัน Async เสมอ hashSync และ compareSync จะบล็อก Event Loop ของ Node.js ทั้งเส้น ทำให้ Request ของคนอื่นทั้งหมดหยุดรอ

ตั้งอายุ Token ให้สมเหตุสมผล

เราคุยกันไปแล้วว่า JWT ยกเลิกไม่ได้ อายุของ Token จึงคือระยะเวลาที่เราต้องยอมรับความเสี่ยงถ้ามันหลุด

สั้นเกินไปผู้ใช้จะรำคาญเพราะต้องล็อกอินบ่อย ยาวเกินไปก็เสี่ยง '7d' ที่เราตั้งไว้เป็นค่าที่สมดุลดีสำหรับแอปทั่วไป ถ้าเป็นแอปธนาคารหรือแอปที่ถือข้อมูลอ่อนไหว ควรสั้นกว่านั้นมากแล้วใช้ Refresh Token ช่วย

Refresh Token คือคำตอบของปัญหา "อายุสั้นแล้วผู้ใช้รำคาญ" ตามที่เล่าไว้ในบทที่ 22 คือให้ Token ใช้งานมีอายุสั้น ส่วน Refresh Token อายุยาว แล้วให้ Client ต่ออายุเองเงียบ ๆ เบื้องหลัง

ใช้ HTTPS บน Production เสมอ

Token ถูกส่งไปใน Header เป็นข้อความธรรมดา ไม่ได้เข้ารหัสอะไรทั้งนั้น ถ้าวิ่งบน HTTP ล้วน ๆ ใครก็ตามที่ดักดูสายอยู่ระหว่างทาง — เช่นบน Wi-Fi สาธารณะ — อ่านมันได้และเอาไปใช้ต่อได้ทันที

HTTPS ทำให้เนื้อในของ Request ทั้งหมดรวมถึง Header ถูกเข้ารหัสระหว่างทาง ข่าวดีคือ Platform สมัยใหม่จัดการเรื่องนี้ให้ฟรีอยู่แล้ว ซึ่งเราจะเห็นตอน Deploy ในบทที่ 31

ตรวจทุก Request ห้าม Cache

ข้อนี้สำคัญและคนพลาดกันเพราะหวังดี เห็น verifyToken ถูกเรียกทุก Request แล้วรู้สึกว่าน่าจะ Cache ไว้สักหน่อย

อย่าทำ เพราะ Token ที่ใช้ได้วันนี้อาจใช้ไม่ได้พรุ่งนี้ ถ้ามันหมดอายุแล้วแต่ Cache ยังตอบว่าผ่านอยู่ คุณก็กำลังส่งข้อมูลให้คนที่ไม่ควรได้รับ ต่อให้เป็นข้อมูลชุดเดิมที่เขาเคยเห็นก็ตาม

ให้ Server ขี้ระแวงตลอดเวลา มันต้องความจำเสื่อมโดยสมบูรณ์ จำไม่ได้ว่าเคยเห็นใครมาก่อน เพราะทุกสมมติฐานที่คุณตั้งไว้จะกลายเป็นช่องให้คนอื่นใช้ประโยชน์เสมอ

ข้อแลกเปลี่ยนคือ JWT ทำให้การ Cache ที่ระดับ HTTP ยากขึ้นมาก ซึ่งเป็นราคาที่เราต้องจ่ายสำหรับความ Stateless

ห้ามเชื่อข้อมูลจากฝั่ง Client

ข้อนี้เป็นข้อที่ทำให้เกิดรูรั่วจริงมากที่สุด

// ผิด — เชื่อ userId ที่ Client ส่งมา
app.post('/habits', (req, res) => {
  const habit = { userId: req.body.userId, name: req.body.name }
})

// ถูก — ใช้ตัวตนที่ผ่านการตรวจ Token มาแล้ว
app.post('/habits', authenticateToken, (req, res) => {
  const habit = { userId: req.user.id, name: req.body.name }
})

อะไรก็ตามที่มาจาก Body, Query หรือ Header ที่ Client กำหนดเอง แก้ได้หมดในสามวินาที ส่วน req.user มาจาก Token ที่ผ่านการตรวจลายเซ็นด้วย Secret ของเรา ปลอมไม่ได้

รูปแบบเดียวกันนี้ใช้กับเรื่อง Role ด้วย อย่าเช็ค Role จาก Header ที่ Client ส่งมา ให้ตรวจ Token ก่อนเสมอแล้วค่อยดู Role จาก Payload ที่ถอดออกมา — Authentication มาก่อน Authorization เสมอ

Rate Limiting และการล็อกบัญชี

Route ล็อกอินคือเป้าหมายอันดับหนึ่งของ Brute Force Attack เพราะมันเปิดสาธารณะและตอบชัดเจนว่าเดาถูกหรือผิด

ทางแก้ที่ใช้กันมีสองระดับ ระดับแรกคือ Rate Limiting คือจำกัดจำนวน Request ต่อช่วงเวลา ซึ่งทำได้ในรูปแบบ Global Middleware เหมือน helmet() และ cors() ที่เราใส่ไว้ในบทที่ 11 ระดับที่สองคือ ล็อกบัญชีชั่วคราว เมื่อล็อกอินพลาดติดกันหลายครั้ง ซึ่งใส่ไว้ตรงจุดที่ comparePassword คืนค่า false ตามที่คุยกันในบทที่ 23

เราไม่ได้ทำทั้งสองอย่างในคอร์สนี้ แต่ในระบบจริงอย่างน้อยต้องมี Rate Limiting

กับดักที่เจอบ่อยที่สุด

ลืมคำว่า Bearer

// ผิด
headers: { Authorization: token }

// ถูก
headers: { Authorization: `Bearer ${token}` }

Middleware ของเรา .split(' ') แล้วหยิบ Index 1 ถ้าไม่มีคำว่า Bearer นำหน้า Index 1 จะเป็น undefined แล้วผู้ใช้จะได้ 401 ทั้งที่ Token ถูกต้องทุกประการ อาการนี้ไล่หาสาเหตุยากมากเพราะทุกอย่างดูปกติหมด

ตัวพิมพ์ใหญ่เล็กของชื่อ Header

// อาจไม่ทำงาน ขึ้นอยู่กับ Server
req.headers['Authorization']

// ปลอดภัยกว่า เพราะ Express ปรับเป็นตัวพิมพ์เล็กให้หมด
req.headers['authorization']

ไม่จัดการ Error ของ Async

ข้อแรกคืออย่าลืมใส่คำว่า async ถ้าข้างในมี await ฟังดูพื้นฐานมากแต่พลาดกันจริง

ข้อที่สองคือเรื่อง try/catch ซึ่งขอย้ำให้ชัดว่าเหตุผลไม่ใช่เรื่อง Server ตาย ตามที่เราเรียนในบทที่ 13 Express 5 รับ Promise ที่ Reject จาก Async Middleware ไปให้ Error Handler กลางเองอยู่แล้ว เหตุผลจริงคือในเรื่อง Auth เราต้องคุม Status Code และรูปแบบ Response เอง ถ้าปล่อยให้ Error ทะลุไปถึง Error Handler กลาง คนที่ส่ง Token หมดอายุมาจะได้ 500 กลับไปแทนที่จะเป็น 403 ซึ่งทำให้ Client ฝั่งนั้นแยกไม่ออกว่าควรพาผู้ใช้ไปล็อกอินใหม่หรือควรแจ้งว่าระบบมีปัญหา นี่คือเหตุผลที่ทั้ง Controller และ Middleware ของเราถูกห่อด้วย try/catch ทุกตัว

สับสนระหว่าง 401 กับ 403

// ผิด — ไม่มี Token คือยังพิสูจน์ตัวตนไม่ได้ ต้องเป็น 401
if (!token) {
  return res.status(403).json({ error: 'Forbidden' })
}

// ถูก
if (!token) {
  return res.status(401).json({ error: 'Access token required' })
}
if (!hasPermission) {
  return res.status(403).json({ error: 'Access denied' })
}

หลักคิดที่ใช้ได้กับทุกเรื่อง

  • ปฏิเสธไว้ก่อนเป็นค่าเริ่มต้น — ออกแบบให้ทุกอย่างปิดไว้ แล้วค่อยเปิดเป็นราย ๆ ไป ไม่ใช่เปิดหมดแล้วค่อยไล่ปิด เพราะถ้าคุณลืมปิดสักจุดคือรูรั่ว แต่ถ้าคุณลืมเปิดสักจุดคือแค่ผู้ใช้บ่นว่าใช้ไม่ได้
  • ให้สิทธิ์น้อยที่สุดเท่าที่จำเป็น — คนที่ต้องการแค่อ่าน ไม่ควรได้สิทธิ์เขียน
  • Log เหตุการณ์ด้าน Security — การล็อกอินที่ล้มเหลวและการเข้าถึงที่ถูกปฏิเสธควรถูกบันทึกไว้ (บันทึกว่าเกิดอะไรขึ้น ไม่ใช่บันทึกตัว Token)
  • ตอบ Error ให้เหมือนกันเมื่อเป็นเรื่อง Auth — ทุกข้อความที่ต่างกันคือข้อมูลที่คนร้ายเอาไปใช้ได้
  • กลับมาทบทวนเป็นระยะ — สิทธิ์ที่เคยถูกต้องเมื่อปีที่แล้วอาจกว้างเกินไปในวันนี้

สิ่งที่เราไม่ได้ทำ

เพื่อความตรงไปตรงมา ระบบที่เราสร้างยังขาดของพวกนี้ซึ่งระบบจริงควรมี

  • ยืนยันอีเมล และการรีเซ็ตรหัสผ่าน
  • Refresh Token
  • MFA หรือการยืนยันตัวตนสองชั้น
  • Rate Limiting และการล็อกบัญชี
  • RBAC เต็มรูปแบบ
  • ตรวจความแข็งแรงของรหัสผ่านตอนสมัคร

แต่ละหัวข้อลงลึกได้เป็นปี ๆ สิ่งที่คอร์สนี้ให้คุณคือความรู้ที่พอจะทำงานได้จริง และที่สำคัญกว่าคือรู้ว่าตัวเองยังไม่รู้อะไรบ้าง ซึ่งเป็นสิ่งที่มีค่ากว่ามากเวลาต้องตัดสินใจในโปรเจกต์จริง

เรื่อง Auth จบแล้วครับ ตอนนี้ทุก Controller ที่เราจะเขียนต่อจากนี้รู้แล้วว่าคนที่ยิงเข้ามาเป็นใคร บทหน้าเราจะเอาความรู้นั้นไปเขียน CRUD Controller ของ Habit ให้ครบทุกการกระทำ
