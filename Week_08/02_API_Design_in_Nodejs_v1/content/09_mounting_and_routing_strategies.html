การ Mount Route และกลยุทธ์ Routing ขั้นสูง

เรามี Router สามตัวแล้วแต่ยังไม่มีใครรู้จักมัน บทนี้เราจะเอามันไปแปะเข้ากับ App ด้วยคำสั่ง app.use() แล้วต่อด้วยเทคนิคการจัดระเบียบ Route ที่จะช่วยคุณตอนโปรเจกต์โตขึ้น

รู้จัก app.use()

use เป็น Method ที่ไม่เกี่ยวกับ HTTP Verb เลย ในขณะที่ app.get() หมายถึง "ถ้าเป็น Verb นี้ และ Path นี้ ให้ทำสิ่งนี้" คำว่า app.use() หมายถึง "ถ้าเป็น Path นี้ ไม่ว่า Verb ไหนก็ตาม ให้ทำสิ่งนี้"

เปิด src/server.ts แล้วเพิ่มเข้าไป

import express from 'express'
import authRoutes from './routes/authRoutes.ts'
import habitRoutes from './routes/habitRoutes.ts'
import userRoutes from './routes/userRoutes.ts'

const app = express()

// Health check endpoint
app.get('/health', (req, res) => {
  res.status(200).json({
    status: 'OK',
    timestamp: new Date().toISOString(),
    service: 'Habit Tracker API',
  })
})

// Routes
app.use('/api/auth', authRoutes)
app.use('/api/habits', habitRoutes)
app.use('/api/users', userRoutes)

export { app }

export default app

เรื่องที่คนเจอปัญหากันบ่อยคือ นามสกุล .ts ในบรรทัด Import ต้องใส่เสมอ ถ้าคุณเคยเขียน Node.js มาก่อนแล้วชินกับการไม่ใส่นามสกุล นั่นคือยุคของ CommonJS พอเปลี่ยนมาใช้ ES Modules แล้วนามสกุลกลายเป็นข้อบังคับ และการใช้ TypeScript ก็ไม่ได้ทำให้ข้อนี้เปลี่ยนไป ถ้าไม่ใส่มันจะ Import ไม่เจอ

Mount Path + Route Path = Path จริง

นี่คือสูตรที่ต้องจำ Path จริงที่ Client ยิงมาได้ เกิดจากการเอา Path ที่เรา Mount ไว้ มาต่อกับ Path ที่เขียนไว้ในไฟล์ Router

app.use('/api/users', userRoutes)   // Mount Path
router.get('/:id', handler)          // Route Path
// ผลลัพธ์: GET /api/users/:id

ไล่ดูตารางการจับคู่ทั้งหมดของแอปเรา

GET    /api/users             → userRoutes.get('/')
GET    /api/users/123         → userRoutes.get('/:id')
PUT    /api/users/123         → userRoutes.put('/:id')
DELETE /api/users/123         → userRoutes.delete('/:id')
GET    /api/habits            → habitRoutes.get('/')
POST   /api/habits            → habitRoutes.post('/')
POST   /api/habits/1/complete → habitRoutes.post('/:id/complete')
POST   /api/auth/register     → authRoutes.post('/register')
POST   /api/auth/login        → authRoutes.post('/login')

คำว่า / ที่เราเขียนใน Router หมายถึง "แค่ Path ที่มาก่อนหน้าเท่านั้น ไม่ต้องต่ออะไรอีก" ในกรณีของ habitRoutes มันจึงกลายเป็น /api/habits เฉย ๆ

ข้อดีที่ใหญ่ที่สุดคือ Router ไม่ต้องรู้ว่าตัวเองจะไปอยู่ตรงไหน ถ้าวันหนึ่งเราอยากเปลี่ยนจาก /api/users เป็น /api/v2/users เราแก้ที่ src/server.ts บรรทัดเดียวจบ ไม่ต้องแตะไฟล์ Router เลย นี่คือความหมายของคำว่า Decoupled

ลองรัน npm run dev แล้วยิงจาก Postman ดู GET /health ต้องยังทำงานเหมือนเดิม GET /api/habits ต้องได้ { "message": "habits" } และ POST /api/auth/register ต้องได้ { "message": "user signed up" } ถ้าได้ 404 ให้เช็คสองอย่างก่อนเสมอ คือ Verb ถูกหรือเปล่า และคำว่า habits เติม s แล้วหรือยัง (พลาดกันบ่อยมาก)

Express ไม่ได้สนใจว่าคุณทำอะไรใน Handler

มีคำถามที่ดีมากข้อหนึ่งคือ ในเมื่อ POST /api/auth/register ควรจะสร้าง User แต่เราแค่ตอบ JSON เปล่า ๆ กลับไป ทำไม Express ไม่ฟ้อง Error

คำตอบคือ Express รู้จักแค่ HTTP ไม่รู้จัก REST HTTP Spec เป็นสิ่งที่ถูกเขียนเป็นมาตรฐานจริง ๆ Express จึงเขียนโค้ดรองรับ Verb ต่าง ๆ ตามนั้น แต่ REST เป็นแค่ข้อตกลงระหว่างมนุษย์ที่ไม่มีอยู่ในโค้ดของใครเลย

สิ่งเดียวที่ Express สนใจคือ คุณต้องส่ง Response กลับ หรือไม่ก็โยน Error ออกมา เท่านั้นจริง ๆ นอกจากนั้นมันไม่รู้และไม่สนใจ การบังคับให้ POST Route ทำหน้าที่สร้างของจริง ๆ เป็นเรื่องของ Business Logic ที่ทีมคุณต้องช่วยกันดูตอน Review Code เอง

ซ้อน Router หลายชั้น

เพิ่ง Mount ไปนั้นคือชั้นเดียว แต่จริง ๆ เราเอา Router ไป Mount บน Router อีกทีก็ได้ และซ้อนลึกลงไปกี่ชั้นก็ได้ ไม่มีอะไรห้าม

const userRouter = Router()
const userHabitsRouter = Router()

userHabitsRouter.get('/', getUserHabits)
userHabitsRouter.post('/', createUserHabit)
userHabitsRouter.delete('/:habitId', deleteUserHabit)

// Mount Router ย่อยบน Router
userRouter.use('/:userId/habits', userHabitsRouter)

// Mount Router บน App
app.use('/api/users', userRouter)

// ผลลัพธ์:
// GET    /api/users/123/habits
// POST   /api/users/123/habits
// DELETE /api/users/123/habits/456

ข้อควรรู้คือโดยปกติ Router ลูกจะอ่าน Parameter ของ Router แม่ไม่เห็น ถ้าอยากให้เห็นต้องเปิด Option mergeParams ตอนสร้าง

const userHabitsRouter = Router({ mergeParams: true })

userHabitsRouter.get('/', (req, res) => {
  console.log(req.params.userId) // "123" อ่านค่าจาก Router แม่ได้แล้ว
})

เทคนิคนี้มีประโยชน์เวลาอยากแบ่ง API ตาม Version เช่น /api/v1 กับ /api/v2 หรือแบ่งตาม Microservice ที่แต่ละทีมดูแลคนละส่วน แต่ต้องระวังว่า ไม่ว่าจะซ้อนลึกแค่ไหน สุดท้าย Route ทุกตัวจะไปรวมกันอยู่ในทะเบียนเดียว ยิ่งลึกยิ่งมีโอกาสที่ Route ญาติห่าง ๆ สองตัวจะชนกันโดยที่เราไม่รู้ตัว แล้วตัวที่ลงทะเบียนก่อนก็จะชนะไปเงียบ ๆ ซึ่ง Debug ยากมาก ถ้าโครงสร้างเริ่มซับซ้อนขนาดนั้น แนะนำให้เลิกพิมพ์ String ตรง ๆ แล้วหันไปเก็บชื่อ Path ไว้ในตัวแปรกลางหรือ Enum เพื่อให้ใช้ซ้ำได้และค้นหาเจอ

ลำดับของ Route สำคัญมาก

นี่คือกับดักที่คนเขียน Express ทุกคนต้องเคยตกอย่างน้อยหนึ่งครั้ง ลองดูสอง Route นี้

// แบบผิด
router.get('/:id', getUser)         // ดักทุกอย่างรวมถึง /profile
router.get('/profile', getProfile)  // ไม่มีวันถูกเรียก

// แบบถูก
router.get('/profile', getProfile)  // ตัวที่เจาะจงไว้ก่อน
router.get('/:id', getUser)         // ตัวที่กว้างไว้ทีหลัง

เหตุผลคือ /:id แปลว่า "Slash แล้วตามด้วยอะไรก็ได้" ซึ่งคำว่าอะไรก็ได้ก็รวมคำว่า profile เข้าไปด้วย สอง Route นี้จึงเป็น Route เดียวกันในสายตาของ Express และตามกฎที่เราเรียนไปในบทที่ 7 คือตัวที่ลงทะเบียนก่อนชนะ ดังนั้นถ้า /:id อยู่ก่อน คำสั่ง getProfile จะไม่มีวันทำงาน

กฎง่าย ๆ คือ Route ที่เจาะจงกว่าต้องมาก่อน Route ที่กว้างกว่าเสมอ

Route แบบมีเงื่อนไข

อย่าลืมว่าไฟล์ Router ก็คือ JavaScript ธรรมดา เราจึงเขียน if ครอบการลงทะเบียน Route ได้เลย

import { isDev } from '../env.ts'

if (isDev()) {
  const devRouter = Router()
  devRouter.get('/debug', debugInfo)
  devRouter.post('/seed', seedDatabase)
  app.use('/dev', devRouter)
}

ตัวอย่างนี้จะเปิด Route สำหรับ Debug เฉพาะตอนพัฒนา พอขึ้น Production แล้ว Route พวกนี้จะไม่มีอยู่เลย ไม่ใช่แค่เข้าไม่ได้ วิธีเดียวกันนี้ใช้ทำ Feature Flag ได้ด้วย คือให้ Environment Variable เป็นตัวตัดสินว่าฟีเจอร์นี้จะเปิดหรือไม่ ซึ่งทำให้เราเปิดปิดฟีเจอร์ได้โดยไม่ต้อง Deploy ใหม่ และเหมาะกับการทำ A/B Test

กลยุทธ์การจัดระเบียบ Route

ไม่มีวิธีไหนถูกหรือผิด มีแต่วิธีที่เหมาะกับทีมและโปรเจกต์ของคุณ นี่คือแบบที่พบบ่อย

  • แบ่งตาม Resource (แบบที่เราใช้ในคอร์สนี้) — แยกไฟล์ตาม Resource คือ auth, user, habit, tag ข้อดีคือแบนและเรียบง่าย หาของเจอทันที และแบ่งความรับผิดชอบในทีมได้ตรงไปตรงมา
  • แบ่งตาม Feature — คิดจากมุมประสบการณ์ผู้ใช้ เช่นมีโฟลเดอร์ onboarding/ ที่มี registration.ts กับ verification.ts และโฟลเดอร์ dashboard/ ที่มี overview.ts กับ analytics.ts เหมาะกับทีมที่แบ่งงานกันตามฟีเจอร์
  • แบ่งตาม Version — ทำโฟลเดอร์ v1/ และ v2/ แล้ว Mount แยกกันด้วย app.use('/api/v1', v1Routes) เหมาะกับ API สาธารณะที่มีคนนอกใช้อยู่และเราเปลี่ยนของเดิมทิ้งไม่ได้
  • Co-location — แทนที่จะมีโฟลเดอร์ routes รวมทุกอย่าง ให้มีโฟลเดอร์ habit/ ที่เก็บทั้ง Route, Handler, Test และ Query ของ Habit ไว้ที่เดียวกันหมด แล้วค่อยรวบทุกโฟลเดอร์เข้าด้วยกันที่ไฟล์ Index ตัวเดียว

Endpoint ที่เจอบ่อยในโปรเจกต์จริง

Health Check — เรามีอยู่แล้วที่ /health Server เกือบทุกตัวในโลกมีเส้นนี้ เพราะมีบริการอย่าง Uptime Robot ที่คอยยิง Request เข้ามาซ้ำ ๆ ตลอดเวลา ถ้าได้ 200 แปลว่าปกติ ถ้าไม่ได้ก็บันทึกไว้แล้วส่งแจ้งเตือนหาคนที่อยู่เวร ประโยชน์อีกข้อคือดูแนวโน้มเวลาตอบสนอง ถ้ามันช้าลงเรื่อย ๆ แปลว่ามีบางอย่างผิดปกติ อาจเป็นเพราะ Traffic เยอะขึ้น (ซึ่งก็น่ายินดี) หรือเพราะโค้ดที่เพิ่งขึ้นไปทำแอปพัง

Catch-all 404 — เอาไว้แทนที่หน้า 404 แบบ HTML ของ Express ด้วย JSON ของเราเอง

// วางไว้ล่างสุด หลัง Route ทั้งหมด
app.use('/api/*splat', (req, res) => {
  res.status(404).json({
    error: 'Not Found',
    message: `Cannot ${req.method} ${req.originalUrl}`,
  })
})

ที่มันทำงานได้เพราะลำดับสำคัญ ถ้าเราวางไว้ล่างสุด Route ที่ลงทะเบียนไว้แล้วจะถูกจับคู่ไปก่อนหมด เหลือแต่ตัวที่ไม่ตรงกับอะไรเลยที่จะตกมาถึงตรงนี้

สังเกตคำว่า *splat ตัวอย่างเก่า ๆ ตามอินเทอร์เน็ตจะเขียนแค่ '/api/*' ซึ่งใช้ไม่ได้แล้ว เพราะ Express 5 บังคับว่า Wildcard ต้องมีชื่อ ชื่อที่ตั้งจะไปโผล่ใน req.params (จะตั้งว่าอะไรก็ได้ แต่คนนิยมใช้คำว่า splat) ด้วยเหตุผลเดียวกัน การใส่ Regex ในวงเล็บแบบ /users/:id(\d+) ก็ถูกถอดออกจาก Express 5 แล้ว ถ้าอยากบังคับรูปแบบให้ไปตรวจใน Handler หรือใช้ Validation Middleware แทน ซึ่งเราจะทำกันในบทที่ 12

Catch-all สำหรับ SPA — ถ้า Server ตัวเดียวกันต้องเสิร์ฟ Single Page Application ด้วย ต้องมี Route แบบ app.get('/*splat', ...) ที่ตอบไฟล์ index.html กลับไปเสมอไม่ว่าจะขอ Path ไหน เพราะชื่อ Single Page App หมายความตามตัวอักษรจริง ๆ คือมีหน้าเดียว เมื่อ Browser ได้ index.html ไปแล้ว JavaScript จะโหลดขึ้นมาและ Router ฝั่ง Client อย่าง React Router ก็รับช่วงจัดการ Routing ต่อเอง แต่ตอนที่ผู้ใช้กด Refresh บน Path ลึก ๆ Browser จะยิงไปหา Server จริง ถ้า Server ไม่มี Route นั้นก็จะได้ 404 ทุกวันนี้เราไม่ต้องเขียนเองแล้วเพราะ Dev Server อย่าง Vite และผู้ให้บริการ Hosting จัดการให้อัตโนมัติ แต่เบื้องหลังก็คือสิ่งนี้

Routing ของเราครบแล้ว แต่ตอนนี้ยังไม่มีอะไรมาคั่นกลางระหว่าง Request ที่เข้ามากับ Handler ของเราเลย ทั้งการอ่าน req.body การตรวจสิทธิ์ และการ Log บทถัดไปเราจะรู้จักกับ Middleware ซึ่งเป็นแนวคิดที่ทรงพลังที่สุดของ Express กัน
