การสร้างและตรวจสอบ JWT

บทที่แล้วเราค้างไว้ที่ generateToken ที่ยังไม่มีตัวตน บทนี้เราจะสร้างมันขึ้นมา แล้วยิงทดสอบให้เห็นกับตาว่าสมัครสมาชิกได้จริง

JWT คืออะไรกันแน่

วิธีคิดที่ง่ายที่สุดคือ JWT คือ Object ที่ถูกแปลงเป็น String ด้วย Algorithm และ Secret เท่านั้นเอง

ผมแปลง Object เป็น String แล้วส่งให้ Client เก็บไว้ พอ Client อยากใช้ API มันส่ง String นั้นกลับขึ้นมา แล้วผมแปลงกลับเป็น Object เดิมเพื่อดูว่าคนนี้เป็นใคร กระบวนการนี้ย้อนกลับได้ ต่างจากการ Hash รหัสผ่านที่ย้อนไม่ได้เลย

ตัว String ที่ได้จะหน้าตาแบบนี้ คือมีจุดคั่นสามส่วน

eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9.eyJpZCI6IjU1MGU4NDAwIn0.SflKxwRJSMeKKF2QT4
  • Header — Metadata ที่บอกระบบปลายทางว่าใช้ Algorithm อะไรในการเซ็น เช่น HS256
  • Payload — Object ที่เราใส่เข้าไปเอง บวกกับ Field มาตรฐานอย่างเวลาที่ออกและเวลาหมดอายุ
  • Signature — ลายเซ็นที่คำนวณจากสองส่วนแรกรวมกับ Secret ของเรา

จุดที่ต้องเน้นให้ชัด — Header กับ Payload ไม่ได้ถูกเข้ารหัส มันแค่ถูก Encode แบบ Base64 ใครก็ตามที่ได้ Token ไปสามารถอ่านเนื้อในได้ทันที ของที่ป้องกันคือ Signature ซึ่งทำให้ใครก็แก้ Payload แล้วส่งกลับมาโดยที่เราไม่รู้ตัวไม่ได้ เพราะลายเซ็นจะไม่ตรงทันที

ผลที่ตามมาคือกฎเหล็กข้อหนึ่ง — ห้ามใส่ของลับใน Payload ไม่ใส่รหัสผ่าน ไม่ใส่เลขบัตรเครดิต ไม่ใส่อะไรที่คุณไม่อยากให้คนอื่นอ่าน ใส่แค่ของที่ใช้ระบุตัวตนก็พอ

จะใส่อะไรลงใน Payload

คำถามที่ต้องตอบคือ "ตอน Request วิ่งกลับเข้ามา ผมอยากรู้อะไรเกี่ยวกับคนนี้บ้าง" คำตอบของเราคือสามอย่างที่ Unique บนตาราง users พอดี คือ id, email และ username

สร้าง src/utils/jwt.ts

เราจะใช้ Library ชื่อ jose ซึ่งเป็นตัวที่ทันสมัยและรองรับ Promise เต็มรูปแบบ สร้างไฟล์ src/utils/jwt.ts ข้าง ๆ password.ts

import { SignJWT } from 'jose'
import { createSecretKey } from 'crypto'
import { env } from '../../env.ts'

export interface JwtPayload {
  id: string
  email: string
  username: string
}

export const generateToken = (payload: JwtPayload): Promise<string> => {
  const secret = env.JWT_SECRET
  const secretKey = createSecretKey(secret, 'utf-8')

  return new SignJWT(payload)
    .setProtectedHeader({ alg: 'HS256' })
    .setIssuedAt()
    .setExpirationTime(env.JWT_EXPIRES_IN || '7d')
    .sign(secretKey)
}

crypto เป็น Module ที่มากับ Node.js อยู่แล้ว ไม่ต้องติดตั้งเพิ่ม เกร็ดเล็ก ๆ คือเราเขียน node:crypto ก็ได้และทำงานเหมือนกันเป๊ะ ข้อดีของ Prefix node: คือมันบอกชัดเจนว่าเราหมายถึงของที่มากับ Node.js เผื่อวันหนึ่งมีใครเผลอติดตั้ง Package ชื่อ crypto จาก npm เข้ามาจะได้ไม่หยิบผิดตัว

ไล่ทีละบรรทัด

  • createSecretKey() แปลง Secret ที่เป็น String ธรรมดาให้เป็น Key Object สำหรับการเข้ารหัสแบบ Symmetric (HMAC) เอกสารบอกไว้แค่นั้น ถ้าจะให้พูดตรง ๆ คือมันไม่ได้จำเป็นขนาดนั้น แต่ก็ไม่เสียหายอะไรที่จะทำ
  • setProtectedHeader({ alg: 'HS256' }) คือการบอกระบบที่จะมาถอด Token นี้ในอนาคตว่าเราเซ็นด้วย Algorithm อะไร ค่านี้เป็น Default อยู่แล้ว แต่เขียนไว้ให้ชัดดีกว่า
  • setIssuedAt() ใส่ Field iat ที่บอกเวลาที่ Token ถูกสร้าง มีประโยชน์มากตอนไล่ปัญหา
  • setExpirationTime() ใส่ Field exp ที่บอกวันหมดอายุ เราดึงมาจาก JWT_EXPIRES_IN ใน env.ts โดยมี '7d' เป็นค่าสำรอง
  • .sign(secretKey) ปิดท้ายด้วยการเซ็น แล้ว Return String ออกมา

วันหมดอายุไม่ใช่ของตกแต่ง

จำที่คุยกันบทที่ 20 ได้ไหมว่า JWT ยกเลิกไม่ได้ Server ไม่ได้เก็บมันไว้ที่ไหนเลย ถ้าเราไม่ใส่วันหมดอายุ แล้ววันหนึ่ง Token ของใครสักคนหลุดออกไป คนที่ได้มันไปจะเข้าถึงข้อมูลของเขาได้ตลอดไป และเราทำอะไรไม่ได้เลยนอกจากเปลี่ยน Secret ทั้งระบบซึ่งจะเตะทุกคนออกพร้อมกัน

ใส่วันหมดอายุเถอะครับ ต้นทุนเป็นศูนย์

ทำไม Secret ต้องอยู่ฝั่ง Server เท่านั้น

Secret คือสิ่งเดียวที่พิสูจน์ว่า Token ใบนี้ออกโดย Server ของเราจริง ๆ ใครก็ตามที่มี Secret สามารถปลอม Token เป็นใครก็ได้ รวมถึงปลอมเป็น Admin โดยที่ระบบตรวจไม่เจอเพราะลายเซ็นถูกต้องทุกประการ

ฉะนั้นห้ามส่ง JWT_SECRET กลับไปใน Response ห้าม Log ออกมาดู ห้ามฝังใน Bundle ของ Frontend และห้าม Commit ขึ้น Git เด็ดขาด นี่คือเหตุผลที่เราลงแรงทำ env.ts กันตั้งแต่บทที่ 6 พร้อมเงื่อนไขว่าต้องยาวอย่างน้อย 32 ตัวอักษร เพราะ Secret สั้น ๆ ถูกไล่เดาได้จริง

เสียบเข้ากับ Route

กลับไปที่ src/controllers/authController.ts เพิ่ม Import ที่ยังขาดอยู่

import { generateToken } from '../utils/jwt.ts'

เส้นแดงในเอดิเตอร์จะหายไป ทีนี้เปิด src/routes/authRoutes.ts แล้วเอา Handler ชั่วคราวที่เราเขียนไว้ตั้งแต่บทที่ 8 ออก แล้วแทนที่ด้วย Controller ตัวจริง

import { Router } from 'express'
import { register } from '../controllers/authController.ts'
import { validateBody } from '../middleware/validation.ts'
import { insertUserSchema } from '../db/schema.ts'

const router = Router()

router.post('/register', validateBody(insertUserSchema), register)

export default router

อย่าลืม validateBody เด็ดขาด เพราะ Controller ที่เราเขียนไปตั้งสมมติฐานไว้เต็มไปหมดว่า Body มี email, username และ password ครบแน่นอน สมมติฐานพวกนั้นจะเป็นจริงก็ต่อเมื่อมี Middleware ยืนเฝ้าอยู่ข้างหน้า

ส่วน insertUserSchema เราได้มาฟรีจาก drizzle-zod ตั้งแต่บทที่ 17 ซึ่งสร้าง Zod Schema จากตาราง users ให้เลย ไม่ต้องเขียนเอง

ข้อจำกัดที่ควรรู้คือ Schema ตัวนี้รู้แค่สิ่งที่ Database รู้ คือความยาวและ Not Null แต่ตรวจไม่ได้ว่า Email มี @ กับ Domain จริงหรือเปล่า หรือรหัสผ่านซับซ้อนพอไหม เพราะ Database ไม่ได้ละเอียดขนาดนั้น (และไม่ควรละเอียดขนาดนั้น เพราะจะช้ามากตอน Insert) แต่ Zod ทำได้สบายเพราะมันทำงานตอน Runtime ถ้าอยากได้เพิ่มก็ใช้ .extend() ต่อยอดจากตัวนี้ หรือเขียน Schema ใหม่เองทั้งอันก็ได้ ตอนนี้ผมขอใช้ตัวที่ได้มาฟรีไปก่อน

รอบแรกลองไม่ส่ง Body อะไรเลย เพื่อดูว่า Validation ทำงานไหม

แล้ว Refresh Token ล่ะ

คำถามที่ต้องมีคนถามแน่ ๆ คือ "พอ Token หมดอายุแล้วจะทำอย่างไร" ให้ผู้ใช้ล็อกอินใหม่คือประสบการณ์ที่แย่ ทางออกที่นิยมคือ Refresh Token

หลักการคือตอนล็อกอินเราออก Token ให้สองใบ ใบหลักอายุสั้นไว้ใช้งานจริง กับใบ Refresh ที่อายุยาวกว่ามาก พอใบหลักหมดอายุ Client ส่งใบ Refresh ขึ้นมาแทน Server ตรวจว่าใบ Refresh ยังใช้ได้ก็ออกใบหลักใบใหม่ให้ Client แค่เอาไปเขียนทับใน Local Storage แล้วใช้งานต่อได้เลยโดยผู้ใช้ไม่รู้สึกอะไร OAuth เองก็ทำงานคล้าย ๆ กันแบบนี้

เราจะไม่ทำ Refresh Token ในคอร์สนี้ แต่รู้ไว้ว่ามันมีอยู่ และมันคือคำตอบมาตรฐานของปัญหานี้

บทหน้าเราจะทำอีกครึ่งที่ขาดอยู่ คือให้คนที่มีบัญชีอยู่แล้วเข้าสู่ระบบได้
