ระบบเข้าสู่ระบบ (Sign In)

เราสมัครสมาชิกได้แล้วและได้ Token กลับมาเรียบร้อย ทีนี้คนที่มีบัญชีอยู่แล้วต้องเข้าระบบได้ด้วย ซึ่งคล้ายกับการสมัครมาก แค่ต่างกันนิดเดียว

Flow ของการเข้าสู่ระบบ

  1. ผู้ใช้ส่ง email กับ password ขึ้นมา
  2. หา User ในตารางจาก email นั้น
  3. เอา Hash ที่เก็บไว้มาเทียบกับรหัสผ่านที่เพิ่งส่งขึ้นมา
  4. ถ้าตรง ออก JWT ให้แล้วส่งกลับไป

มีจุดที่เส้นทางนี้จบก่อนกำหนดได้สองจุด จุดแรกคือหา Email ไม่เจอ แปลว่าคนนี้ไม่เคยสมัคร จุดที่สองคือเจอ Email แต่รหัสผ่านไม่ตรง ซึ่งอาจเป็นเจ้าตัวที่ลืมรหัสผ่าน หรืออาจเป็นคนอื่นที่กำลังนั่งเดารหัสผ่านของเขาอยู่ก็ได้ ไม่ว่าทางไหนเราก็ไม่ให้เข้า

bcrypt.compare ทำงานอย่างไร

ประเด็นที่น่าสนใจคือ bcrypt เทียบรหัสผ่านได้โดยไม่ต้องรู้ค่าเดิมของรหัสผ่านเลย

// ตอนสมัคร (บทที่ 21)
const hash = await bcrypt.hash('myPassword123', 12)
// เก็บลง Database: $2b$12$N9qo8uLOickgx2ZMRZoMye.IjQ0JwF2cJX8nnYA5VYA.KQIeqHLWa

// ตอนล็อกอิน (บทนี้)
const isValid = await bcrypt.compare('myPassword123', hash)
// ได้ true ถ้าตรง, false ถ้าไม่ตรง

มันทำแบบนั้นได้เพราะ Hash ที่เก็บอยู่มีวัตถุดิบครบทุกอย่างอยู่ในตัวเอง ทั้ง Algorithm ทั้งจำนวนรอบ และทั้ง Salt ตอน Compare มันแค่ดึงวัตถุดิบเหล่านั้นออกมา เอาไปทำซ้ำกับรหัสผ่านที่เพิ่งส่งขึ้นมา แล้วเทียบผลลัพธ์

ผ่า bcrypt Hash ออกเป็นชิ้น ๆ

ขอออกตัวก่อนว่าเรื่องนี้ไม่จำเป็นต่อการทำงาน ถ้าคุณไม่ได้ทำงานสาย Security คุณจะไม่มีวันต้องรู้เรื่องนี้ ผมเองเพิ่งรู้เมื่อไม่นานมานี้เอง แต่มันน่าสนใจดีเลยอยากเล่าให้ฟัง

$2b$10$N9qo8uLOickgx2ZMRZoMyeIjZAgcfl7p92ldGxad68LJZdL17lhWy

$2b$                             → เวอร์ชันของ Algorithm
10                               → Cost Factor (จำนวนรอบ)
N9qo8uLOickgx2ZMRZoMye           → Salt (22 ตัวอักษรถัดมา)
IjZAgcfl7p92ldGxad68LJZdL17lhWy  → ผลลัพธ์ของการ Hash (ที่เหลือทั้งหมด)

Cost Factor ยิ่งสูงยิ่งทนต่อ Brute Force แต่ก็ยิ่งช้า ต้องหาจุดสมดุลตามเครื่องที่รันจริง ส่วนผลลัพธ์ท่อนสุดท้ายคือการ Hash รหัสผ่านรวมกับ Salt ข้างบน

Salt มีไว้ทำไม

เราห้ามคนสองคนใช้รหัสผ่านเดียวกันไม่ได้ แต่เราไม่อยากให้ Hash ของทั้งสองคนเหมือนกัน เพราะคนร้ายที่ได้ Database ไปแล้วเห็นสิบแถวมีค่า Hash เท่ากันเป๊ะ ย่อมรู้ทันทีว่าสิบคนนี้ใช้รหัสผ่านเดียวกัน แกะได้อันเดียวก็เปิดได้ทั้งสิบบัญชี

Salt คือค่าสุ่มที่ถูกสร้างใหม่ทุกครั้งที่ Hash แล้วผสมเข้าไปในการคำนวณ ไม่ใช่แค่แปะไว้ข้างหน้าเฉย ๆ (ถ้าแค่แปะไว้ คนร้ายก็ข้าม 22 ตัวแรกไปเทียบส่วนที่เหลือซึ่งยังเหมือนกันอยู่ดี) มันจึงเป็นการเติมความสุ่มเข้าไปในกระบวนการที่ปกติแล้ว Deterministic ผลคือต่อให้คุณกับผมใช้รหัสผ่านเดียวกัน Hash ในฐานข้อมูลก็ต่างกันคนละเรื่อง

Timing Attack และการเทียบแบบ Constant Time

มีการโจมตีแบบหนึ่งชื่อ Timing Attack คือคนร้ายจับเวลาว่าฟังก์ชันเทียบรหัสผ่านใช้เวลานานแค่ไหน ถ้าฟังก์ชันเทียบทีละตัวอักษรแล้วหยุดทันทีที่เจอตัวผิด การเดาที่ถูกไป 5 ตัวจะช้ากว่าการเดาที่ผิดตั้งแต่ตัวแรก คนร้ายก็ไล่เดาทีละตัวจากเวลาที่ต่างกันได้ bcrypt แก้ด้วยการทำให้ compare เป็น Constant Time คือใช้เวลาเท่ากันเสมอไม่ว่าจะตรงกี่ตัวอักษร

// สองบรรทัดนี้ใช้เวลาเท่ากันเป๊ะ ๆ
await bcrypt.compare('a', hash)              // ผิดตั้งแต่ตัวแรก
await bcrypt.compare('myPassword12', hash)   // ผิดแค่ตัวสุดท้าย

ย้ำว่านี่ต่างจากตอน Hash นะครับ ตอน Hash ยิ่งรอบเยอะยิ่งช้าตามจำนวนรอบ แต่ตอน Compare เวลาคงที่เสมอ

เพิ่ม comparePassword

กลับไปที่ src/utils/password.ts แล้วเพิ่มฟังก์ชันที่สอง

export const comparePassword = async (
  password: string,
  hashedPassword: string
): Promise<boolean> => {
  return bcrypt.compare(password, hashedPassword)
}

ลำดับ Argument สำคัญมาก ตัวแรกคือรหัสผ่านข้อความดิบที่เพิ่งส่งขึ้นมา ตัวที่สองคือ Hash จาก Database สลับกันแล้วผลลัพธ์จะเป็น false ตลอดชีวิตโดยไม่มี Error อะไรฟ้องให้เห็นเลย

เขียน Controller login

เปิด src/controllers/authController.ts เพิ่ม Import สองตัว

import { comparePassword } from '../utils/password.ts'
import { eq } from 'drizzle-orm'

แล้วเขียนฟังก์ชันที่สองต่อจาก register

export const login = async (req: Request, res: Response) => {
  try {
    const { email, password } = req.body

    const user = await db.query.users.findFirst({
      where: eq(users.email, email),
    })

    if (!user) {
      return res.status(401).json({ error: 'Invalid credentials' })
    }

    const isValidPassword = await comparePassword(password, user.password)

    if (!isValidPassword) {
      return res.status(401).json({ error: 'Invalid credentials' })
    }

    const token = await generateToken({
      id: user.id,
      email: user.email,
      username: user.username,
    })

    return res.status(200).json({
      message: 'Login success',
      user: {
        id: user.id,
        email: user.email,
        username: user.username,
        firstName: user.firstName,
        lastName: user.lastName,
        createdAt: user.createdAt,
      },
      token,
    })
  } catch (e) {
    console.error('Login error', e)
    res.status(500).json({ error: 'Failed to login' })
  }
}

findFirst กับ select ต่างกันอย่างไร

Drizzle มีสองวิธีในการหาข้อมูล และคุณจะเจอทั้งคู่ในโค้ดจริง

// แบบที่ 1 — Query API คืน Object เดียวหรือ undefined
const user = await db.query.users.findFirst({
  where: eq(users.email, email),
})

// แบบที่ 2 — Select API คืน Array เสมอ จึงต้อง Destructure
const [user] = await db.select().from(users).where(eq(users.email, email))

eq ที่ Import มาจาก drizzle-orm ย่อมาจาก equals อ่านตรงตัวว่า "คอลัมน์ email ของตาราง users เท่ากับค่า email ที่ส่งขึ้นมา"

ที่กล้าใช้ findFirst ได้เพราะเราตั้ง .unique() ไว้ที่ email ตั้งแต่บทที่ 16 จึงเป็นไปไม่ได้ที่จะมีสองแถว

ทำไม 401 ทั้งสองกรณีและทำไมข้อความเหมือนกัน

นี่คือส่วนที่สำคัญที่สุดของบทนี้ สังเกตว่าทั้งกรณี "ไม่มี Email นี้" และกรณี "รหัสผ่านผิด" เราตอบ Invalid credentials เหมือนกันเป๊ะ

เพราะถ้าแยกข้อความ เราจะกลายเป็นเครื่องมือให้คนร้ายโดยไม่ตั้งใจ ลองนึกภาพว่าผมอยากรู้ว่าคุณเป็นลูกค้าธนาคารแห่งนี้ไหม ผมก็แค่เอา Email ของคุณไปกรอกที่หน้าล็อกอินพร้อมรหัสผ่านมั่ว ๆ ถ้าระบบตอบว่า "ไม่พบผู้ใช้นี้" แปลว่าคุณไม่ใช่ลูกค้า แต่ถ้าตอบว่า "รหัสผ่านไม่ถูกต้อง" ผมยืนยันได้ทันทีว่าคุณเป็นลูกค้าที่นี่ เหลือแค่หาทางเดารหัสผ่านต่อ

ช่องโหว่นี้เรียกว่า User Enumeration และไม่ได้จบแค่หน้าล็อกอิน หน้าสมัครสมาชิกที่ตอบว่า "อีเมลนี้ถูกใช้แล้ว" ก็รั่วข้อมูลแบบเดียวกัน (แอปดัง ๆ หลายเจ้าก็ยังทำแบบนี้อยู่) ข้อความที่นิยมใช้กันจึงเป็นทำนอง "ไม่พบผู้ใช้ที่ตรงกับอีเมลและรหัสผ่านนี้" ซึ่งเป็นความจริงทั้งสองกรณีและไม่บอกใบ้ว่าตัวไหนผิด

ส่วนที่เลือก 401 ไม่ใช่ 404 เพราะ 401 แปลว่า "ยังพิสูจน์ตัวตนไม่ผ่าน" ซึ่งตรงกับสถานการณ์พอดี ถ้าตอบ 404 จะกลายเป็นการยืนยันว่า Resource ไม่มีอยู่ ซึ่งย้อนกลับไปสู่ปัญหา User Enumeration อีกรอบ

เช็คด้านลบแล้ว Return ทันที

สังเกตรูปแบบของทั้งสอง if — เราเช็คกรณีที่ไม่ผ่านแล้ว return ออกไปเลย ไม่ใช่เขียน if (user) { ... } แล้วห่อโค้ดที่เหลือไว้ข้างใน เพราะถ้าเขียนแบบหลัง พอเงื่อนไขเพิ่มขึ้นโค้ดจะซ้อนกันลึกลงไปเรื่อย ๆ และ return ของกรณีที่ไม่ผ่านจะกระจายอยู่คนละระดับความลึกทั่วทั้งฟังก์ชัน อ่านแล้วเวียนหัว การเช็คด้านลบแล้วออกทันทีทำให้โค้ดแบนราบและไล่อ่านจากบนลงล่างได้ตรง ๆ

อย่าส่ง User ทั้งก้อนกลับไป

คุณอาจสงสัยว่าทำไมไม่เขียนสั้น ๆ ว่า res.json({ user }) ไปเลย คำตอบคือ findFirst คืน User ทั้งแถวมาให้ ซึ่งรวมคอลัมน์ password ด้วย ถ้าส่งกลับไปตรง ๆ เราจะยิง Hash ของรหัสผ่านออกไปให้ทุกคนที่ดักดูสายได้เห็น ตอนสมัครสมาชิกเราไม่เจอปัญหานี้เพราะ .returning() กรอง Field ให้ตั้งแต่ระดับ Query แต่ตอนล็อกอินเราต้องดึงคอลัมน์ password มาจริง ๆ เพื่อเอาไปเทียบ จึงต้องประกอบ Object ที่จะส่งกลับด้วยมือ

ยังมีอะไรทำได้อีกที่จุดนี้

ตรงจุดที่รหัสผ่านไม่ตรงเป็นตำแหน่งที่ระบบจริงมักใส่ของเพิ่ม เพราะถ้าคุณคิดถึงแค่สถานการณ์ "เจ้าตัวลืมรหัสผ่าน" คุณจะปล่อยให้ลองกี่ครั้งก็ได้ตลอดชีวิต แต่ถ้าคิดถึงสถานการณ์ที่สองด้วยคือ "คนอื่นกำลังไล่เดารหัสผ่านอยู่" คุณจะรีบหยุดเขาก่อนที่เขาจะเดาถูก ของที่นิยมใส่กันคือนับจำนวนครั้งที่ล็อกอินพลาดแล้วล็อกบัญชีชั่วคราว หรือทำ Rate Limiting ที่ระดับ Route เราไม่ทำในคอร์สนี้ แต่ให้ติดไว้ในหัวว่าจุดนี้คือจุดที่มันควรอยู่

Schema สำหรับล็อกอินและการทดสอบ

เปิด src/routes/authRoutes.ts เราใช้ insertUserSchema กับ Route นี้ไม่ได้ เพราะมันบังคับให้มี username ด้วย ทั้งที่เราล็อกอินด้วย Email กับรหัสผ่านเท่านั้น จึงต้องเขียน Schema ใหม่

import { z } from 'zod'
import { login } from '../controllers/authController.ts'

const loginSchema = z.object({
  email: z.email('Invalid email'),
  password: z.string().min(1, 'Password is required'),
})

router.post('/login', validateBody(loginSchema), login)

สังเกตว่าเราเขียน z.email() ไม่ใช่ z.string().email() เพราะใน Zod เวอร์ชันปัจจุบัน z.string().email() ถูกทำเครื่องหมายว่า Deprecated ไปแล้ว ตัวตรวจ Email กลายเป็น Type ของตัวเองที่สืบทอดมาจาก String อีกที

อีกจุดที่ตั้งใจคือ password เราขอแค่ .min(1) คือมีค่าอะไรก็ได้ เราไม่ตรวจความแข็งแรงของรหัสผ่านตอนล็อกอิน เพราะถ้าวันหนึ่งเราขึ้นเกณฑ์ความปลอดภัยให้เข้มขึ้น คนที่สมัครไว้ตั้งแต่สมัยเกณฑ์เก่าจะล็อกอินไม่ได้ทันทีทั้งที่รหัสผ่านของเขาถูกต้อง การตรวจความแข็งแรงเป็นเรื่องของตอนสมัครเท่านั้น

ทดสอบใน Postman ด้วยการยิง POST /api/auth/login ลองพิมพ์ Email ให้ผิดไปหนึ่งตัวจะได้ 401 Invalid credentials ซึ่งถูกต้อง เพราะผ่าน Validation มาแล้ว (รูปแบบ Email ยังถูก) แต่หาในฐานข้อมูลไม่เจอ ลองลบ Field email ออกทั้งอันจะได้ 400 จาก Validation แทน แล้วพอใส่ให้ถูกทั้งหมดจะได้ Login success พร้อม Token ใบใหม่

ตอนนี้เราออก Token เป็นแล้วทั้งตอนสมัครและตอนล็อกอิน แต่ยังไม่ได้เอามันไปใช้ทำอะไรเลย Token ที่ได้ไปเป็นหน้าที่ของ Client ที่จะเก็บไว้ใน Local Storage หรือ SQLite บนมือถือ แล้วแนบขึ้นมาทุก Request บทหน้าเราจะไปทำฝั่ง Server ให้มันเริ่มบังคับใช้ Token จริง ๆ
