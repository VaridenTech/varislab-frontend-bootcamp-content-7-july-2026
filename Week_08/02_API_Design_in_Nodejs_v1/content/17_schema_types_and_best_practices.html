Generated Types และ Schema Best Practices

Schema ที่เราเขียนไปในบทที่แล้วมีข้อมูลครบทุกอย่างอยู่ในตัวมันแล้ว ทั้งชื่อ Field ชนิดข้อมูล ตัวไหนบังคับ ตัวไหนมีค่า Default บทนี้เราจะดึงข้อมูลชุดนั้นออกมาใช้ต่อในฝั่ง TypeScript

Generate Client จาก Schema

จำได้ไหมว่าบล็อก generator ในไฟล์ schema.prisma บอกไว้ว่าให้สร้าง Client ออกมาที่ src/generated/prisma ตอนนี้ถึงเวลาสั่งให้มันสร้างจริง

npx prisma generate

คำสั่งนี้ไม่ได้แตะ Database เลย (เรายังไม่มี Database ด้วยซ้ำ ซึ่งไม่เป็นไร) มันแค่อ่าน schema.prisma แล้วเขียนโค้ด TypeScript ออกมาเป็นโฟลเดอร์หนึ่ง ข้างในคือ Client ที่รู้จักทั้งห้าตารางของเรา พร้อม Type ของทุก Model ครบทุกตัว ลองเปิดดูได้แต่อย่าไปแก้อะไรในนั้น เพราะมันจะถูกเขียนทับทุกครั้งที่ Generate ใหม่ และให้เติม src/generated ลงใน .gitignore ด้วย เพราะมันคือของที่สร้างขึ้นใหม่ได้เสมอ ไม่ใช่ Source Code ของเรา

ข้อควรจำมีข้อเดียว แก้ schema.prisma เมื่อไร ต้องรัน Generate ใหม่เมื่อนั้น ไม่งั้น Type ในเอดิเตอร์กับความจริงจะไม่ตรงกัน เดี๋ยวบทหน้าเราจะทำ Script ให้เรียกง่าย ๆ ด้วย

Type ที่ได้มาฟรีจากการ Generate

สร้างไฟล์ src/db/types.ts ขึ้นมา (สร้างโฟลเดอร์ src/db ก่อนถ้ายังไม่มี) เพื่อรวบ Type ที่เราจะใช้บ่อยไว้ที่เดียว

import type { Prisma } from '../generated/prisma/client.ts'

export type { User, Habit, Entry, Tag, HabitTag } from '../generated/prisma/client.ts'

export type NewUser = Prisma.UserUncheckedCreateInput
export type NewHabit = Prisma.HabitUncheckedCreateInput
export type NewEntry = Prisma.EntryUncheckedCreateInput
export type NewTag = Prisma.TagUncheckedCreateInput
export type NewHabitTag = Prisma.HabitTagUncheckedCreateInput

Prisma สร้าง Type มาให้เราสองตระกูล ซึ่งต่างกันชัดเจนและเป็นจุดที่ควรเข้าใจ

  • Type ที่ชื่อตรงกับ Model อย่าง User คือหน้าตาของข้อมูลตอนที่ดึงออกมาจากฐานข้อมูล มีครบทุก Field ทั้ง id, createdAt, updatedAt เพราะของพวกนั้นถูกสร้างขึ้นแล้ว
  • Type ตระกูล CreateInput คือหน้าตาของข้อมูลตอนที่จะยัดลงฐานข้อมูล Field ที่มีค่า Default หรือถูกสุ่มให้จะกลายเป็น Optional หมด เหลือแค่ที่เราต้องกรอกจริง ๆ ซึ่งของ User คือ email, username และ password

ส่วนคำว่า Unchecked ขออธิบายหน่อยเพราะชื่อมันชวนกลัว Prisma มี Input สองแบบ — UserCreateInput แบบปกติจะให้เราผูกความสัมพันธ์ผ่าน Object ซ้อน (เช่นสร้าง Habit พร้อมระบุ user: { connect: ... }) ส่วน UncheckedCreateInput คือแบบที่ยอมให้เรากรอก Foreign Key เป็นค่าธรรมดาตรง ๆ อย่าง userId ซึ่งตรงกับสไตล์ที่เราจะเขียนในคอร์สนี้ คำว่า Unchecked หมายถึงแค่ว่า TypeScript ไม่ช่วยเช็คว่า Id นั้นชี้ไปหาของที่มีจริง — แต่ฐานข้อมูลยังเช็ค Foreign Key ให้เหมือนเดิมทุกประการ

พอมี Type สองชุดนี้ Function ที่คุยกับฐานข้อมูลจะเขียนได้สวยมาก

const createUser = async (userData: NewUser): Promise<User> => {
  return prisma.user.create({ data: userData })
}

อ่านแล้วเข้าใจทันทีว่ารับของที่ยังไม่ถูกสร้าง แล้วคืนของที่ถูกสร้างแล้ว โดยที่เราไม่ต้องเขียน Interface ไหนขึ้นมาเองสักบรรทัด และถ้าวันหนึ่งเราเพิ่มคอลัมน์ใน Schema แล้วรัน Generate ใหม่ Type ทั้งหมดนี้จะอัปเดตตามให้เอง

สร้าง Zod Schema ให้ล้อกับตาราง

Type ช่วยเราได้แค่ตอนเขียนโค้ด แต่ตอน Runtime มันหายไปหมด ถ้าอยากตรวจค่าจริงเราต้องใช้ Zod เหมือนที่ทำใน env.ts และใน Validation Middleware

Prisma ไม่มีตัวแปลง Schema เป็น Zod ติดมาให้ (มี Generator ของชุมชนอย่าง zod-prisma-types ที่ทำให้ได้ แต่ผมอยากให้คุณเห็นของจริงก่อนค่อยไปใช้ตัวช่วย) เราจึงเขียนเองในไฟล์ src/db/validation.ts โดยมีกติกาข้อเดียวที่ผมยึดเวลาเขียนไฟล์นี้ คือสะท้อนเฉพาะกฎที่ฐานข้อมูลบังคับจริง — ความยาวของ varchar ตัวไหนบังคับ ตัวไหน Optional — เปิด schema.prisma คู่กันแล้วไล่ทีละ Field

import { z } from 'zod'

export const insertUserSchema = z.object({
  email: z.string().max(255),
  username: z.string().max(50),
  password: z.string().max(255),
  firstName: z.string().max(50).optional(),
  lastName: z.string().max(50).optional(),
})

export const insertTagSchema = z.object({
  name: z.string().max(50),
  color: z.string().max(7).optional(),
})

export const insertEntrySchema = z.object({
  habitId: z.uuid(),
  note: z.string().optional(),
})

สังเกตสองเรื่อง หนึ่ง — เราไม่ใส่ Field อย่าง id, createdAt, updatedAt เพราะพวกนั้นฐานข้อมูลเติมให้เอง ผู้ใช้ไม่มีหน้าที่ส่งมา สอง — ต้นทุนของการเขียนมือคือถ้าแก้ schema.prisma ต้องกลับมาแก้ไฟล์นี้ให้ตรงกันด้วย ซึ่งเป็นวินัยที่ต้องรักษาเอง นี่คือจุดที่ Generator ของชุมชนเข้ามาช่วยได้เมื่อโปรเจกต์โตขึ้น

เอาไปใช้กับ Validation Middleware

คำถามที่ตามมาทันทีคือ Schema พวกนี้ใช้แทน Zod Schema ตัวอย่างที่เราเขียนมือใน src/middleware/validation.ts ตอนบทที่ 12 ได้ไหม คำตอบคือได้ และควรใช้ด้วย

import { insertUserSchema } from '../db/validation.ts'

router.post('/register', validateBody(insertUserSchema), register)

ตอนบทที่ 12 เราเขียน Schema กันสด ๆ เพราะยังไม่มีฐานข้อมูล ตอนนี้มีแล้วก็รวมกฎมาไว้ที่ src/db/validation.ts ที่เดียว เพราะกฎของ Validation ควรเดินตามกฎของตารางเสมอ

แต่มีข้อยกเว้นสำคัญที่ต้องรู้ Schema ที่ล้อกับตารางใช้ตรวจ Input ของผู้ใช้ได้ก็ต่อเมื่อทุก Field ที่บังคับ ผู้ใช้เป็นคนส่งมาทั้งหมด

ลองนึกถึงตอนสร้าง Habit ฐานข้อมูลบังคับให้มี userId แต่ผู้ใช้ไม่ได้ส่งค่านั้นมาใน Body เราต่างหากที่เป็นคนเติมให้จาก Token ถ้า Schema สำหรับตรวจ Body บังคับ userId ด้วย Request ที่ถูกต้องทุกอันจะถูกปฏิเสธหมด เพราะฉะนั้น Schema ของ Habit ที่ใช้ตรวจ Body เราจึงจงใจไม่ใส่ userId ลงไป (เดี๋ยวได้เขียนกันจริงในบทที่ 26)

อีกทางคือใช้เครื่องมือตัดแต่งของ Zod — .omit(), .pick() และ .partial() ช่วยหยิบเฉพาะส่วนจาก Schema ที่มีอยู่ หรือ .extend() เพื่อเพิ่มกฎที่ฐานข้อมูลไม่รู้จัก เช่นบังคับความยาวขั้นต่ำของรหัสผ่าน ซึ่งเป็นกฎของแอปเรา ไม่ใช่กฎของฐานข้อมูล

export const createUserSchema = insertUserSchema.extend({
  password: z.string().min(8, 'Password must be at least 8 characters'),
})

เทคนิคนี้จะกลับมามีบทบาทตอนคุยเรื่อง Validation ของระบบสมัครสมาชิก (บทที่ 22 และ 30) — ในคอร์สเราเลือกใช้ insertUserSchema ฉบับล้อตารางไปก่อน

Best Practices ของการออกแบบ Schema

ก่อนจะไปต่อ ขอรวบเจ็ดข้อที่ผมยึดทุกครั้งที่ออกแบบ Schema

  • ใส่ Timestamp เสมอ — createdAt กับ updatedAt มีประโยชน์มากกว่าที่คุณคิด และวันที่คุณต้องการมันคือวันที่มันไม่มี
  • บังคับกฎที่ระดับ Database — ใช้ @unique, การไม่ใส่ ? และ @relation ให้เป็นประโยชน์ เป็นชั้นที่ไม่มีใครข้ามได้
  • ทำ Index ให้คอลัมน์ที่ Query บ่อย — โดยเฉพาะ Foreign Key ทุกตัว (Prisma มี @@index ให้ประกาศเพิ่มได้)
  • ตั้งชื่อให้สื่อความหมาย — ผมทนไม่ได้กับ Schema ที่ตั้งชื่อคอลัมน์ว่า tg แล้วไม่มีใครในทีมบอกได้ว่ามันคืออะไร
  • เผื่ออนาคตไว้ด้วย — ถ้ารู้ว่ามีฟีเจอร์อะไรอยู่ใน Roadmap ให้คิดตั้งแต่ตอนนี้ว่ามันจะกระทบ Schema อย่างไร เพราะ Migration กำลังมาแน่
  • Normalize แต่พอดี — Normalize คือการเลือกว่าจะวาง Key ไว้ฝั่งไหนแล้ว Query จากฝั่งนั้นตลอด ซึ่งเป็นเป้าหมายที่ดี แต่อย่ายึดจนถึงขั้นต้องรื้อ Logic หลังบ้านสามเดือนเพียงเพื่อความสวยงาม ถ้าเพิ่ม Key อีกตัวแล้วจบก็เพิ่มไปเถอะ
  • ใช้ Enum เมื่อค่าที่เป็นไปได้มีจำกัด — Enum ก็คือ "ต้องเป็นหนึ่งในลิสต์นี้" เหมือนที่เราใช้ใน env.ts และ Prisma มี Block enum ให้ประกาศใน Schema ได้เลย

ข้อสุดท้ายนี่แหละคือจุดที่ Schema ของเรายังทำได้ไม่ดี คอลัมน์ frequency ของเราเป็น String ที่ใส่อะไรลงไปก็ได้ ทั้งที่มันควรเลือกได้แค่ daily, weekly, monthly ถ้าเปลี่ยนเป็น Enum ข้อมูลจะสม่ำเสมอขึ้น และคนทำหน้าบ้านจะรู้ทันทีว่ามีตัวเลือกอะไรบ้าง เอาไปทำ Dropdown ได้เลย

สี่กับดักที่เจอบ่อย

ลืมใส่ Foreign Key จริง ๆ — การมีคอลัมน์ชื่อ userId ไม่ได้แปลว่ามีความสัมพันธ์ ถ้าไม่มี @relation ฐานข้อมูลจะยอมให้ใส่ ID มั่ว ๆ ที่ไม่มีอยู่จริงลงไปได้

// ผิด — มีแค่คอลัมน์ ไม่มีการตรวจสอบความถูกต้องของความสัมพันธ์
userId String @map("user_id") @db.Uuid

// ถูก — ฐานข้อมูลรับประกันให้ว่า User คนนั้นมีอยู่จริง
userId String @map("user_id") @db.Uuid
user   User   @relation(fields: [userId], references: [id], onDelete: Cascade)

ลืมทำ Index — Query อย่าง SELECT * FROM habits WHERE user_id = ? ถ้าไม่มี Index จะกลายเป็นการสแกนทั้งตาราง ตอนมีข้อมูลร้อยแถวไม่รู้สึกอะไร ตอนมีล้านแถวถึงจะรู้สึก

Normalize เกินจำเป็น — เคยเห็นคนแยกตาราง user_first_names ออกมาต่างหากมาแล้ว ผลคือทุก Query ต้อง JOIN เพิ่มโดยไม่ได้อะไรกลับมาเลย ชื่อจริงควรอยู่บนตาราง users ตรงนั้นแหละ

ไม่มี Timestamp — ข้อเดิมที่ต้องย้ำ เพราะพอไม่มีแล้วอยากได้ทีหลัง คุณจะเติมย้อนหลังให้ข้อมูลเก่าไม่ได้เลย

Migration แบบไหนที่ยากที่สุด

มีคนถามผมว่าจากประสบการณ์แล้ว Migration แบบไหนปวดหัวที่สุด งานแรกในชีวิตผมเคยใช้เวลาทำ Database Migration ตัวเดียวไปสองเดือน และคำตอบก็คือข้อเดิมที่เราคุยกันในบทที่ 15 คือDestructive Change

วิธีเลี่ยงคือทำให้ทุกอย่างเป็นการเพิ่ม ถ้าคุณแค่เพิ่มของใหม่โดยไม่แตะของเก่า จะไม่มีโค้ดไหนพัง เพราะยังไม่มีใครพึ่งพาของที่เพิ่งเกิด แล้วค่อยแบ่งเป็นสองรอบตามที่คุยกันไป

อีกทางที่ช่วยได้มากในยุคนี้คือ Database Branching ซึ่งบริการอย่าง Neon หรือ PlanetScale มีให้ แนวคิดคือแตก Branch ของฐานข้อมูลได้เหมือนแตก Branch ของ Git พร้อมข้อมูลข้างในทั้งก้อน ทำให้ทดลอง Migration บนสำเนาจริงได้โดยไม่แตะตัวจริง บางเจ้าตรวจให้ด้วยซ้ำว่าการเปลี่ยนแปลงนี้จะทำให้พังหรือเปล่าแล้วแนะนำทางออกให้

แน่นอนว่าการย้ายแพลตฟอร์มฐานข้อมูลของระบบที่วิ่งอยู่บน Production แล้วนั้นแทบเป็นไปไม่ได้ แต่ถ้าคุณเริ่มโปรเจกต์ใหม่วันนี้ ผมแนะนำให้เลือกเจ้าที่มี Branching ตั้งแต่แรก

พูดถึง Neon พอดี บทหน้าเราจะไปสร้าง Database จริงบนนั้นกัน แบบฟรีและไม่ต้องสมัครสมาชิกด้วยซ้ำ
