ทำไมเราต้องใช้ฐานข้อมูล

สมมติว่าเรากำลังสร้างร้านค้าออนไลน์ขนาดเล็ก ช่วงแรกอาจมีสินค้าเพียงสิบชิ้น เราเก็บรายการทั้งหมดไว้ใน Array หรือไฟล์ JSON ก็ยังใช้งานได้ดี แต่เมื่อมีลูกค้าเข้ามาพร้อมกัน มีคำสั่งซื้อเพิ่มขึ้น และข้อมูลต้องเชื่อมโยงกันหลายส่วน วิธีที่เคยเรียบง่ายจะเริ่มสร้างปัญหา

Database ช่วยจัดการปัญหาเหล่านี้ ไม่ใช่เพียงเพราะมันเก็บข้อมูลได้มากกว่าไฟล์ แต่เพราะมันช่วยให้หลายส่วนของระบบอ่านและเขียนข้อมูลร่วมกันได้อย่างเป็นระเบียบ

ข้อมูลต้องอยู่ต่อหลังโปรแกรมหยุดทำงาน

ข้อมูลใน Memory อ่านและเขียนได้เร็ว แต่จะหายไปเมื่อโปรแกรมหยุดทำงาน เราคงยอมรับไม่ได้ถ้ารายการสั่งซื้อหายทุกครั้งที่ Server Restart การเก็บข้อมูลลง Disk ช่วยให้ข้อมูลอยู่ต่อได้ แต่ถ้าเราจัดการไฟล์เองก็ต้องคิดเพิ่มว่าจะบันทึกเมื่อไร อ่านส่วนไหน และทำอย่างไรเมื่อเขียนไฟล์ไม่สำเร็จ

Database มีวิธีจัดเก็บข้อมูลแบบ Persistent และมีกลไกช่วยรับมือกับการเขียนที่ไม่สมบูรณ์ Database บางตัวเก็บข้อมูลหลักไว้ใน Memory เพื่อความเร็ว แต่ก็ยังมีทางบันทึกหรือสร้างข้อมูลกลับคืนตามรูปแบบการใช้งานของมัน

ผู้ใช้หลายคนแก้ข้อมูลพร้อมกัน

ไฟล์หนึ่งไฟล์อาจพอใช้เมื่อมีโปรแกรมเดียวเขียนข้อมูลทีละงาน แต่ Web App มักรับ Request หลายรายการพร้อมกัน ลองนึกถึงลูกค้าสองคนกดซื้อสินค้าชิ้นสุดท้ายในเวลาใกล้กัน ถ้าทั้งสอง Request อ่านว่าเหลือหนึ่งชิ้นแล้วเขียนผลลัพธ์กลับไปเอง เราอาจขายสินค้าเกินจำนวนโดยไม่รู้ตัว

Database ช่วยประสานการอ่านและเขียนที่เกิดพร้อมกัน มีทั้ง Constraint, Lock และ Transaction ให้เราเลือกใช้ตามความสำคัญของงาน เครื่องมือเหล่านี้ช่วยลดโอกาสที่ข้อมูลจะอยู่ในสถานะขัดแย้งกัน

ค้นหาข้อมูลได้โดยไม่ต้องอ่านทั้งหมด

ถ้าเก็บคำสั่งซื้อหนึ่งล้านรายการในไฟล์เดียว การหาคำสั่งซื้อของลูกค้าคนหนึ่งอาจต้องเปิดไฟล์และไล่ดูทุกบรรทัด Database เปิดให้เราส่ง Query เพื่อระบุข้อมูลที่ต้องการ เช่น “หาคำสั่งซื้อของลูกค้าคนนี้ใน 30 วันที่ผ่านมาและเรียงจากใหม่ไปเก่า”

Database ยังสร้าง Index เพื่อช่วยค้นหาข้อมูลบางรูปแบบได้เร็วขึ้น แนวคิดคล้ายดัชนีท้ายหนังสือ: เราไม่ต้องเปิดอ่านทุกหน้าเพื่อหาหัวข้อที่ต้องการ แต่ Index ก็ใช้พื้นที่และมีต้นทุนตอนเขียนข้อมูล เราจึงต้องเลือกสร้างให้เหมาะกับ Query ที่แอปใช้จริง

รักษากฎของข้อมูล

ข้อมูลของแอปมักมีกฎ เช่น Email ของผู้ใช้ห้ามซ้ำ จำนวนสินค้าในสต็อกต้องไม่ติดลบ หรือคำสั่งซื้อต้องอ้างถึงลูกค้าที่มีอยู่จริง เราตรวจสอบกฎเหล่านี้ใน Application Code ได้ แต่ Database หลายตัวก็ช่วยบังคับกฎในจุดที่เก็บข้อมูลโดยตรง

การบังคับใช้กฎใกล้กับจุดที่เก็บข้อมูลมีความสำคัญ เพราะอาจมีหลายระบบเชื่อมต่อ Database เดียวกัน หากแต่ละระบบตรวจสอบไม่เหมือนกัน ข้อมูลอาจผิดพลาดได้ การให้ Database ปฏิเสธข้อมูลที่ไม่ถูกต้องจึงเป็นแนวป้องกันเพิ่มอีกชั้นหนึ่ง

ดูแลสิทธิ์ การสำรอง และการกู้คืน

Database ส่วนใหญ่มีระบบ User และ Permission เพื่อกำหนดว่าใครอ่านหรือแก้ข้อมูลส่วนไหนได้ รวมถึงมีเครื่องมือสำหรับ Backup, Replication และ Recovery ความสามารถเหล่านี้สำคัญเมื่อข้อมูลมีมูลค่าและระบบต้องให้บริการต่อเนื่อง

อย่างไรก็ตาม Database ไม่ได้เปิดความปลอดภัยและการสำรองที่เหมาะสมให้เราโดยอัตโนมัติ ทีมยังต้องตั้งค่า ทดสอบการกู้คืน และติดตามการทำงานของระบบอยู่เสมอ การมี Backup ที่ไม่เคยลอง Restore อาจช่วยเราไม่ได้เมื่อเกิดเหตุจริง

แล้วไฟล์หรือ Spreadsheet ยังใช้ได้ไหม

ใช้ได้ และบางงานก็เหมาะกว่าด้วย ไฟล์ Configuration, ข้อมูลตัวอย่าง หรือรายงานที่ส่งต่อให้คนอ่านอาจไม่ต้องใช้ Database ส่วน Spreadsheet เหมาะกับงานที่คนต้องดูและแก้ข้อมูลขนาดไม่ใหญ่มากด้วยตัวเอง การเลือก Database ไม่ควรเกิดจากความเคยชิน แต่ควรเกิดจากปัญหาที่เราต้องแก้

เมื่อแอปต้องเก็บข้อมูลระยะยาว รองรับผู้ใช้หลายคน ค้นหาข้อมูลหลายรูปแบบ หรือรักษาความถูกต้องของข้อมูล Database มักเป็นทางเลือกที่เหมาะกว่า ในคอร์สนี้เราจะค่อย ๆ เรียนว่า Database แต่ละประเภทแก้ปัญหาเหล่านี้ด้วยแนวทางใด และต้องแลกกับอะไรบ้าง
