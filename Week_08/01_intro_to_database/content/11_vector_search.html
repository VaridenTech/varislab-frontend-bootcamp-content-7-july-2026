การค้นหาแบบเวกเตอร์

เรามาพูดถึงการค้นหาเวกเตอร์ซึ่งใช้บ่อยที่สุดกับเทคนิคที่เรียกว่า RAG (การสร้างแบบดึงข้อมูลเสริม) ที่ง่ายที่สุด RAG คือแนวคิดที่ว่าคุณมีฐานข้อมูลที่เต็มไปด้วยบริบทที่เป็นประโยชน์สำหรับ LLM

สมมติว่าคุณเปิดร้านขายอุปกรณ์กลางแจ้ง และผู้ใช้ถามว่าถุงมือนั้นเหมาะกับการเล่นสกีในฤดูใบไม้ผลิที่อุ่นกว่าหรือไม่ คุณมีฐานข้อมูลที่เต็มไปด้วยคำอธิบายของถุงมือ ก่อนที่คุณจะขอคำแนะนำจาก LLM คุณจะต้องสืบค้นฐานข้อมูลของคุณด้วยสตริงการค้นหาและฟีดนั้นเป็นบริบทใน LLM เพื่อให้มีรายการผลิตภัณฑ์ที่เกี่ยวข้องกับการสืบค้นอยู่แล้ว โดยให้บริบททั้งหมดที่จำเป็นในให้คำแนะนำโดยอาศัยข้อมูลตามผลิตภัณฑ์จริงที่คุณมี

สมมติว่าคุณกำลังสร้างบอทสนับสนุนลูกค้าและคุณมีฐานข้อมูลที่เต็มไปด้วยโซลูชั่นที่ได้รับการยอมรับ คุณสามารถใช้ RAG เพื่อดึงข้อมูลวิธีแก้ปัญหาที่ได้รับการยอมรับ ก่อนที่จะขอให้บอทแก้ไขปัญหา โดยให้เหตุผลเบื้องต้นโดยถือว่าปัญหาการสนับสนุนส่วนใหญ่ไม่ใช่ครั้งแรกที่คุณพบปัญหานั้น

สิ่งนี้เรียกว่า RAG และคุณใช้สิ่งที่เรียกว่าการค้นหาเวกเตอร์เพื่อให้บรรลุเป้าหมาย เวกเตอร์เป็นเพียงอาร์เรย์ของตัวเลข ข้อความของคุณจะกลายเป็นอาร์เรย์ของตัวเลขที่แสดงถึงความคล้ายคลึงและระยะห่างที่สัมพันธ์กับมิติอื่นๆ ในฐานข้อมูลของคุณ

เวกเตอร์เหล่านี้ไม่สามารถอ่านหรือเข้าใจได้โดยมนุษย์ คุณส่งข้อความของคุณไปยังโมเดลการฝัง (LLM เฉพาะทางที่ทำเช่นนี้เท่านั้น) และข้อความจะส่งกลับชุดของเวกเตอร์ที่คุณจัดเก็บไว้ในฐานข้อมูลการค้นหาเวกเตอร์ของคุณ

ผลลัพธ์ที่ได้ค่อนข้างดีเพราะรวมกลุ่มคำ หัวข้อ และแนวคิดไว้ด้วยกัน หมายความว่าสิ่งต่างๆ เช่น "การผลักดันให้ใช้งานจริงในวันศุกร์ถือเป็นฝันร้าย" และ "การหยุดทำงานของการปรับใช้ในช่วงสุดสัปดาห์ทำให้ฉันกังวลเช่นนั้น" น่าจะปรากฏขึ้นพร้อมกันในการค้นหาเนื่องจากสิ่งเหล่านั้นเกี่ยวข้องกัน แม้ว่าจะไม่แชร์คีย์เวิร์ดก็ตาม นั่นคือพลังของการค้นหาเวกเตอร์

การค้นหาเวกเตอร์อาจมีประโยชน์นอกเหนือจาก RAG แต่ส่วนใหญ่จะเป็นที่ที่คุณจะเห็น สำหรับสิ่งต่างๆ เช่น การค้นหาข้อความแบบเต็ม มีเครื่องมืออื่นๆ เช่น Elasticsearch ที่ได้รับการปรับให้เหมาะสมที่สุดสำหรับสิ่งนั้น

เราเคยต้องการฐานข้อมูลพิเศษ เช่น [pinecone] เพื่อให้สามารถทำเช่นนี้ได้ แต่แล้วสิ่งต่างๆ เช่น pgvector ก็เข้ามาทำสิ่งนั้น และทั้งหมดนี้ก็อยู่ใน Postgres ของคุณ และได้ขจัดความจำเป็นส่วนใหญ่ในการใช้เครื่องมือพิเศษ เช่น Pinecone

มาทำกัน

เราจะเพิ่มการดึงข้อมูล RAG ลงในตารางความคิดเห็นของเรา เพื่อให้เราสามารถค้นหาความคิดเห็นที่คล้ายกันโดยอิงจากเวกเตอร์ได้

คุณมีทางเลือกสองสามทางเกี่ยวกับวิธีการฝังเวกเตอร์ กระบวนการคือคุณใช้โมเดล LLM เฉพาะทางซึ่งมีประโยชน์สำหรับการเข้ารหัสการฝังเท่านั้น ฉันจะให้คุณทำสองวิธี: ผ่านการเรียก API ไปยัง OpenAI หรือผ่าน LLM ท้องถิ่นผ่าน Ollama โดยใช้ nomic-embed-text ขอย้ำอีกครั้งว่าไม่สำคัญว่าคุณจะใช้อันไหน คุณแค่ต้องใช้ the Same อันหนึ่งอย่างสม่ำเสมอ VoyageAI ก็เป็นตัวเลือกเช่นกัน และเป็นตัวเลือกที่ Anthropic แนะนำ

หากคุณมีแล็ปท็อปที่สามารถใช้งาน LLM และ Ollama ขนาดเล็กได้ ฉันขอแนะนำให้ทำตามข้อความ nomic-embed-text มิฉะนั้น การใช้การเรียก OpenAI, OpenRouter หรือ VoyagerAI API จะทำงานได้ดี

เมื่อคุณติดตั้ง Ollama แล้ว ให้เรียกใช้สิ่งนี้จาก CLI ของคุณ

ollama pull nomic-embed-text

curl http://localhost:11434/api/embed \
  -d '{
    "model": "nomic-embed-text",
    "input": "Never push to prod on a Friday"
  }'

และคุณจะได้ผลลัพธ์ที่ดูคล้ายกัน เพียงแค่ดูจากแบบจำลองแทนที่จะเป็นแบบโนมิกส์ คู่มือ OpenAI อยู่ที่นี่

ฉันชอบแยกรูปแบบข้อมูลเหล่านี้ออกและบอกคุณว่ารูปแบบเหล่านี้หมายถึงอะไร แต่จริงๆ แล้วรูปแบบเหล่านี้แทบจะเป็นไปไม่ได้เลยในฐานะผู้ที่ไม่ใช่ผู้เชี่ยวชาญที่จะแยกออกจากกัน พอจะพูดได้ว่ามันคืออาร์เรย์ของตัวเลขที่แสดงความหมายของสตริงข้อความเป็นจุดข้อมูลจำนวนคงที่ นั่นคือมากเท่าที่คุณสามารถพูดได้ จากนั้นระยะห่างระหว่างจุดข้อมูลเหล่านี้จะถูกใช้เพื่อจัดกลุ่มสตริงข้อความที่มีความหมายคล้ายกัน

เรามาเพิ่มความสามารถนี้ให้กับ Postgres กัน คุณต้องเพิ่มส่วนขยายที่เรียกว่า vector อย่างเหมาะสม

โดยปกติคุณจะรันคำสั่งดังนี้:

CREATE EXTENSION IF NOT EXISTS vector;
ALTER TABLE comments ADD COLUMN embedding vector(<length of your vector>);

โมเดลการฝังของคุณจะกำหนดความยาวของเวกเตอร์ของคุณ โมเดลโนมิกมีความยาว 768 และโมเดล OpenAI มีความยาวเวกเตอร์ 1536 นี่คือตัวเลขที่คุณจะใช้ที่นั่น หากคุณใช้เวกเตอร์อื่น คุณจะมีตัวเลขที่แตกต่างกันตรงนั้น

ฉันมีสิ่งนี้อยู่ในสคริปต์ฝังแล้ว ดังนั้นคุณไม่จำเป็นต้องทำเช่นนี้ แต่นี่คือวิธีที่คุณเพิ่มส่วนขยายให้กับ Postgres: คุณพบมัน เพิ่มลงใน Postgres (ซึ่งเราทำโดยใช้คอนเทนเนอร์ pgvector) ทำการเรียก CREATE EXTENSION แล้วใช้งาน vector() เป็นประเภทข้อมูลที่รวมอยู่ในส่วนขยายและเพิ่มความสามารถในการสืบค้นเวกเตอร์

ดังนั้นให้เพิ่มสคริปต์ฝังนี้ในโครงการของคุณ:

import pg from "pg";

const CONNECTION_STRING =
  "postgresql://postgres:mysecretpassword@localhost:5432"; // NOTE you may need to add your database name (e.g. /message_boards) if you aren't using the default postgres database

const PROVIDERS = {
  openai: {
    dimensions: 1536,
    model: "text-embedding-3-small",
    async embed(texts) {
      const res = await fetch("https://api.openai.com/v1/embeddings", {
        method: "POST",
        headers: {
          Authorization: `Bearer ${process.env.OPENAI_API_KEY}`,
          "Content-Type": "application/json",
        },
        body: JSON.stringify({
          input: texts,
          model: "text-embedding-3-small",
        }),
      });

      if (!res.ok) {
        const err = await res.text();
        throw new Error(`OpenAI API error: ${res.status} ${err}`);
      }

      const data = await res.json();
      return data.data.map((d) => d.embedding);
    },
  },

  ollama: {
    dimensions: 768,
    model: "nomic-embed-text",
    async embed(texts) {
      const res = await fetch("http://localhost:11434/api/embed", {
        method: "POST",
        headers: { "Content-Type": "application/json" },
        body: JSON.stringify({
          model: "nomic-embed-text",
          input: texts,
        }),
      });

      if (!res.ok) {
        const err = await res.text();
        throw new Error(`Ollama API error: ${res.status} ${err}`);
      }

      const data = await res.json();
      return data.embeddings;
    },
  },
};

const [mode, providerName, ...rest] = process.argv.slice(2);

if (!PROVIDERS[providerName] || !["generate", "get"].includes(mode)) {
  console.error("Usage:");
  console.error(
    "  node embeddings.js generate <openai|ollama>     Embed all comments",
  );
  console.error(
    '  node embeddings.js get <openai|ollama> "text"    Get a single embedding',
  );
  process.exit(1);
}

const provider = PROVIDERS[providerName];

if (mode === "get") {
  const text = rest.join(" ");
  if (!text) {
    console.error(
      'Provide text to embed: node embeddings.js get ollama "your text here"',
    );
    process.exit(1);
  }

  const [embedding] = await provider.embed([text]);
  console.log(`[${embedding.join(",")}]`);
} else {
  console.log(
    `Using ${providerName} (${provider.model}, ${provider.dimensions} dimensions)`,
  );

  const client = new pg.Client({ connectionString: CONNECTION_STRING });
  await client.connect();

  await client.query("CREATE EXTENSION IF NOT EXISTS vector");

  // Drop and recreate column to match provider dimensions
  await client.query(`
    DO $$
    BEGIN
      IF EXISTS (
        SELECT 1 FROM information_schema.columns
        WHERE table_name = 'comments' AND column_name = 'embedding'
      ) THEN
        ALTER TABLE comments DROP COLUMN embedding;
      END IF;
    END $$
  `);
  await client.query(
    `ALTER TABLE comments ADD COLUMN embedding vector(${provider.dimensions})`,
  );

  const { rows } = await client.query(
    "SELECT comment_id, comment FROM comments ORDER BY comment_id",
  );
  console.log(`Found ${rows.length} comments to embed`);

  const BATCH_SIZE = 50;
  for (let i = 0; i < rows.length; i += BATCH_SIZE) {
    const batch = rows.slice(i, i + BATCH_SIZE);
    const texts = batch.map((r) => r.comment);
    const embeddings = await provider.embed(texts);

    for (let j = 0; j < batch.length; j++) {
      const vectorStr = `[${embeddings[j].join(",")}]`;
      await client.query(
        "UPDATE comments SET embedding = $1 WHERE comment_id = $2",
        [vectorStr, batch[j].comment_id],
      );
    }

    console.log(
      `Embedded ${Math.min(i + BATCH_SIZE, rows.length)}/${rows.length}`,
    );
  }

  console.log("Done!");
  await client.end();
}

จากนั้นเพิ่มสิ่งเหล่านี้ลงในสคริปต์ของคุณใน package.json

"scripts": {
  "embed:openai": "node embed.js generate openai",
  "embed:ollama": "node embed.js generate ollama",
  "get:openai": "node embed.js get openai",
  "get:ollama": "node embed.js get ollama"
},

ตอนนี้หากคุณรัน npm run embed:<provider> มันจะสอบถามทุกความคิดเห็น รันผ่านโมเดลการฝัง และบันทึกลงในฐานข้อมูล ตรวจสอบให้แน่ใจว่าคุณได้ดึงโมเดลที่ถูกต้องสำหรับ ollama และโมเดลจะทำงานหากคุณใช้ Ollama และตรวจสอบให้แน่ใจว่าคุณมี OPENAI_API_KEY ในสภาพแวดล้อมของคุณหากคุณต้องการใช้ OpenAI เช่น OPENAI_API_KEY=<your OpenAI API key> npm run embed:openai. สิ่งนี้ควรแบทช์และบันทึกลงในฐานข้อมูลของคุณ อาจใช้เวลาประมาณ 10 วินาทีในการดำเนินการบน M3 MacBook Air บน Ollama (ตัวโมเดลเองมีขนาด 273MB ในขณะที่เขียน และควรทำงานบนแล็ปท็อปสมัยใหม่เกือบทุกรุ่น) และฉันคิดว่ามันน้อยกว่า 1¢ เมื่อฉันรันบน OpenAI (ฉันบอกไม่ได้ แต่มันก็เป็นจำนวนเล็กน้อย)

เมื่อคุณดำเนินการเสร็จแล้ว เรามาดำเนินการค้นหากันดีกว่า!

SELECT comment, embedding FROM comments LIMIT 1;

การจัดรูปแบบอาจดูแปลกเล็กน้อย แต่เมื่อเลื่อนลงไปจะเห็นความคิดเห็นพร้อมชุดตัวเลขที่แทนความหมายของข้อความนั้น ต่อไปเราจะนำข้อมูลนี้ไปใช้งานจริง แต่มีประเด็นหนึ่งคือ เราต้องแปลงข้อความค้นหาให้เป็นเวกเตอร์ก่อนจึงจะค้นหาได้ โดยปกติแอปจะเรียกโมเดลจากภายในโค้ด แต่เพื่อไม่ต้องสร้างแอปอีกชุด ตัวอย่างนี้จึงเตรียมเป็นสคริปต์ npm ให้เรียกใช้แทน

แบบสอบถามของคุณจะมีลักษณะเช่นนี้

SELECT
  comment,
  embedding <=> '[<your vectors>]' AS distance
FROM comments
ORDER BY distance
LIMIT 15;

ขั้นตอนมากมาย แต่สุดท้ายก็กลายเป็นโค้ดที่ค่อนข้างง่าย

  1. ทำการฝังทุกอย่างในฐานข้อมูลของคุณ
  2. ตรวจสอบให้แน่ใจว่าคุณเพิ่มการฝังสำหรับทุกความคิดเห็นใหม่ที่เพิ่มลงในฐานข้อมูล และอัปเดตการฝังหากความคิดเห็นมีการเปลี่ยนแปลง
  3. เมื่อคุณไปทำ RAG ด้วย LLM ให้รันคำค้นหาผ่านโมเดลการฝัง
  4. ใช้สิ่งนั้นเพื่อค้นหาฐานข้อมูลโดยใช้ตัวดำเนินการ <=>
  5. กำไร

ลองนึกภาพถ้าคุณต้องการค้นหาความคิดเห็นที่คล้ายกับความคิดเห็นที่มีอยู่ในฐานข้อมูลของคุณแล้ว ง่ายด้วยแบบสอบถามย่อย

-- Wrap it in a function they can call
-- (you'd create this ahead of time)
SELECT
  comment,
  embedding <=> (
    SELECT embedding FROM comments
    WHERE comment_id = 1
  ) AS distance
FROM comments
WHERE comment_id != 1
ORDER BY distance
LIMIT 15;

เนื่องจากการฝังมีอยู่แล้ว คุณจึงไม่จำเป็นต้องเรียกโมเดล นี่จะให้ความคิดเห็นที่คล้ายกันมากที่สุดกับความคิดเห็น ID 1

เปรียบเทียบสิ่งนี้กับการค้นหาการเปรียบเทียบข้อความ (เช่น LIKE, ILIKE) - คุณจะได้รับสิ่งที่มีคำหลักเหมือนกันทุกประการ แต่คุณจะพลาดสิ่งที่มีความหมายคล้ายกัน

คำเตือนเกี่ยวกับ RAG

RAG ไม่ใช่กระสุนเงิน มันไม่ได้ทำให้ผลลัพธ์ของคุณจาก LLM ดีขึ้นเสมอไป

มาใช้บอทสนับสนุนลูกค้าของเรากันเถอะ มันอาจจะทำงานได้ดีหากคุณมีแคตตาล็อกวิธีแก้ปัญหาที่มีประสิทธิภาพ และ ปัญหาส่วนใหญ่คือปัญหาที่คุณเคยเห็นมาก่อน แต่หากคุณมีแค็ตตาล็อกโซลูชันที่ไม่ดี และ/หรือปัญหาส่วนใหญ่เป็นปัญหาใหม่และไม่มีอยู่ในแค็ตตาล็อกโซลูชัน ถ้าอย่างนั้น คุณกำลังพูดถึงบริบทมากมายที่ไม่เพียงแต่ไร้ประโยชน์เท่านั้น แต่ยังกำลังขับเคลื่อน LLM ไปในทิศทางที่ผิดอีกด้วย มันเป็นอันตรายต่อผลิตภัณฑ์ของคุณจริงๆ

ดังนั้นคำเตือนบางประการ:

  • การเรียกค้นที่ไม่ถูกต้องนั้นแย่ยิ่งกว่าการไม่เรียกค้นเลย RAG ทำงานในสถานการณ์เฉพาะที่คุณมีบริบทที่เป็นประโยชน์ในพื้นที่ปัญหาที่มีขอบเขต - คำแนะนำผลิตภัณฑ์จากร้านค้าของคุณคือตัวอย่างที่ดีในเรื่องนี้ เป็น/อาจเป็นอันตรายได้เมื่อเป็นปัญหาที่มีขอบเขตน้อยกว่า เช่น ฝ่ายสนับสนุนลูกค้า ไม่ว่าในกรณีใด คุณต้องทดสอบอย่างละเอียดเพื่อให้แน่ใจว่า RAG ของคุณช่วยได้ไม่ทำให้เจ็บ
  • LLM เริ่มฉลาดขึ้นเรื่อยๆ และบ่อยครั้งไม่จำเป็นต้องใช้ RAG เพื่อให้ได้โซลูชันที่ดี ในบางกรณี ปล่อยให้ LLM ดำเนินการต่อไปและดูว่าจะได้อะไรกลับมาบ้าง คุณสามารถเพิ่มเช่นเซิร์ฟเวอร์ MCP หรือทักษะในการดึงข้อมูลของตัวเองได้หากเหมาะสมกับกรณีการใช้งานของคุณสำหรับโมเดล "LLM สามารถดึงบริบทเมื่อจำเป็น" แทน "พุชบริบทไปยัง LLM ทุกครั้ง"
  • ในบางกรณี คุณสามารถ fine-tune โมเดลแทนการใช้ RAG ได้ หากเป้าหมายคือการเปลี่ยน พฤติกรรม ของโมเดล ไม่ใช่เพิ่มบริบทใหม่ตอนค้นหา นั่นเป็นโจทย์ของการ fine-tune ไม่ใช่การดึงข้อมูล วิธีนี้เหมาะกับการปรับโทน รูปแบบการแก้ปัญหา หรือฝังแนวโน้มบางอย่างลงในคำตอบโดยตรง (บางกรณีอาจแก้ได้ด้วยการออกแบบ prompt อย่างง่าย ทั้งนี้ขึ้นอยู่กับปัญหา)

โปรดทราบว่าการทำ RAG มีต้นทุนทั้งเวลาแฝง ความซับซ้อนของโค้ดสำหรับการค้นหา จำนวนโทเค็นที่เพิ่มขึ้นในทุกคำขอ และโครงสร้างพื้นฐานเพิ่มเติมสำหรับจัดการเวกเตอร์ จึงควรตรวจสอบให้แน่ใจว่าระบบได้รับประโยชน์จากมันจริง ๆ คุณสามารถเพิ่ม RAG ในภายหลังได้เสมอ และโดยทั่วไปหากยังไม่จำเป็นก็ควรเริ่มต้นโดยไม่มี RAG ก่อน
