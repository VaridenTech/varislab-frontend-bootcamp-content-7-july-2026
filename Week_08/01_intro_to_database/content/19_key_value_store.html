รู้จักฐานข้อมูลแบบ Key-Value

ฐานข้อมูลแบบ Key-Value แตกต่างจากฐานข้อมูลที่เราเรียนมาก่อนหน้านี้อย่างชัดเจน สิ่งแรกที่ควรรู้คือ เราแทบไม่ใช้ Key-Value Store เป็นฐานข้อมูลหลัก แต่จะใช้เป็นเครื่องมือเสริมให้ฐานข้อมูลอื่น แม้จะมีระบบที่ใช้ Key-Value Store เพียงอย่างเดียว แต่เป็นกรณีขั้นสูงและพบไม่บ่อย

จุดเด่นของ Key-Value Store คือ API และความสามารถที่เรียบง่าย จึงเข้าใจง่าย ใช้งานง่าย และรองรับปริมาณงานสูงมากได้ เพราะไม่ต้องประมวลผล Query ซับซ้อนเหมือน PostgreSQL ที่ JOIN หลายตารางหรือ Aggregate ข้อมูลได้ โดยแก่นของ Key-Value Store คือ “บันทึกค่านี้ด้วย Key นี้” และ “อ่านค่าจาก Key นี้”

ลองนึกภาพ Key-Value Store เป็น JavaScript Object ขนาดใหญ่ เราบันทึกค่าได้ด้วย store['my-key'] = 5 แล้วกลับมาอ่านด้วย store['my-key'] เพื่อรับค่า 5 แนวคิดหลักมีเพียงการผูก Value ไว้กับ Key และเรียกคืนในภายหลัง

กรณีใช้งาน

กรณีที่พบบ่อยที่สุดคือการทำ Cache สมมติว่า PostgreSQL Query หนึ่งใช้เวลาห้าวินาที ถูกเรียกบ่อย และข้อมูลเปลี่ยนไม่บ่อย การรัน Query เดิมทุกครั้งจะทำให้ Server รับภาระหนัก เราจึงอาจรันวันละครั้งแล้วเก็บผลไว้ใน Redis เมื่อแอปต้องการข้อมูลก็ลองอ่าน Cache ก่อน ถ้าพบก็ใช้ได้ทันที วิธีนี้ช่วยเพิ่มประสิทธิภาพได้มาก

อีกกรณีคือข้อมูลที่ถูกใช้งานบ่อยแต่ไม่ใช่ข้อมูลวิกฤต เช่น Session ของผู้ใช้ หาก Cache หาย ผู้ใช้ทั้งหมดอาจต้อง Login ใหม่ ซึ่งไม่ดีแต่ระบบยังทำงานต่อได้ จึงไม่ควรเก็บข้อมูลสำคัญไว้ใน Key-Value Store เพียงแห่งเดียวในฐานะ Source of Truth

Key-Value Store ยังเหมาะกับ Analytics หรือ Telemetry เพราะเพิ่มหรือลดตัวเลขได้รวดเร็ว เช่น นับ Page View ของเว็บไซต์ที่มี Traffic สูง ยังมีกรณีอื่นอีกมาก จึงควรเปิดกว้างและเลือกใช้ตามลักษณะงาน

ตัวเลือกของ Key-Value Store

PostgreSQL hstore และ JSONB

PostgreSQL เลียนแบบ API แบบ SET/GET ของ Redis ได้ผ่าน hstore และ JSONB ปัจจุบัน JSONB แพร่หลายกว่า โดยทั่วไปเราใช้ Redis เพื่อลดภาระ PostgreSQL ดังนั้นการใช้ JSONB แบบ Key-Value เหมาะกับงานเบาหรือเมื่ออยากได้ API ที่เรียบง่ายเท่านั้น

Memcached

Memcached เป็น Key-Value Store รุ่นเก่าที่ยังนิยม จุดแข็งคือความเรียบง่าย ไม่มี Replication ในตัว ไม่มีฟีเจอร์จำนวนมาก และไม่เขียนข้อมูลลง Disk ทุกอย่างอยู่ใน Memory หากพื้นที่เต็มก็ขับข้อมูลเก่าออก เหมาะกับ Session และ Cache ที่สูญหายได้ ให้ประสิทธิภาพสูงแต่ Server ปิดแล้วข้อมูลทั้งหมดจะหาย

Memcached เก็บเฉพาะ String แต่ String นั้นใส่ข้อมูลใดก็ได้โดยไม่มี Validation จึงมักแปลง Object เป็น JSON String ก่อนจัดเก็บ

Redis

Redis ย่อจาก remote dictionary server เป็นเครื่องมือหลักของบทนี้ มีแนวคิดคล้าย Memcached แต่ฟีเจอร์มากกว่า เช่น Cluster ชนิดข้อมูลหลายแบบ และการบันทึก Cache ลง Disk เพื่อกู้สถานะหลัง Restart อย่างไรก็ตาม การรับประกันข้อมูลยังไม่เทียบเท่า MongoDB หรือ PostgreSQL

Valkey

ปี 2024 Redis เปลี่ยนจากสัญญาอนุญาต Open Source เป็น Dual License ที่เข้มงวดขึ้น Linux Foundation จึง Fork โครงการเป็น Valkey (Value Key) ภายใต้สัญญาอนุญาต Open Source เดิม Valkey ใช้ API คำสั่ง Protocol และ Client Library ร่วมกับ Redis ได้ หากเริ่มโครงการใหม่และให้ความสำคัญกับสัญญาอนุญาต Valkey เป็นตัวเลือกที่ควรศึกษา ทุกแนวคิดต่อจากนี้ใช้ได้กับทั้ง Redis และ Valkey
