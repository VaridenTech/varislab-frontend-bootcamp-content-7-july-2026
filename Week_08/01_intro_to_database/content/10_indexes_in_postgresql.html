Index ใน PostgreSQL

Database สมัยใหม่จัดการข้อมูลมหาศาลได้รวดเร็วมาก หลายระบบเริ่มใช้งานได้ดีโดยแทบไม่ต้องปรับแต่งอะไร แต่เมื่อข้อมูลและ Traffic โตขึ้น Query บางตัวอาจช้า ใช้ทรัพยากรสูง หรือทำให้ Server ไม่เสถียร จุดนี้ Index จะเข้ามาช่วย

Index เป็น Data Structure แยกที่ Database ดูแลไว้เพื่อค้นหา Row ได้เร็วขึ้น Trade-off คือการเพิ่ม แก้ไข และลบข้อมูลจะช้าลงเล็กน้อยเพราะต้องอัปเดต Index ตามไปด้วย และยังใช้พื้นที่บน Disk เพิ่มขึ้น แลกกับ Query ที่เร็วขึ้นและความสามารถอย่างการบังคับค่าไม่ซ้ำ

EXPLAIN

การ Optimize Database เป็นงานที่ลงลึกมากและมักเป็นหน้าที่ของ DBA บทนี้จะเน้นเครื่องมือพื้นฐานที่ช่วยให้เราเห็นว่า Query ทำงานอย่างไร เพื่อใช้วิเคราะห์ปัญหาและคุยกับผู้เชี่ยวชาญได้ตรงจุด

ลองดู Query ที่ใช้บ่อยในระบบกระดานข้อความ: ดึง Comment ล่าสุดของ Board หนึ่ง

SELECT comment_id, user_id, time, LEFT(comment, 20) FROM comments WHERE board_id = 39 ORDER BY time DESC LIMIT 40;

Query ดูเรียบง่าย แต่ Database อาจต้องตรวจทุก Record ใน Table ตอนมีข้อมูลน้อยยังไม่เห็นผล แต่บน Production ที่มีข้อมูลมากจะใช้ทรัพยากรสูง เราจึงควรดู Execution Plan ก่อน

มาดูกันว่า PostgreSQL ทำอะไรได้บ้างโดยเพิ่ม EXPLAIN ไว้ข้างหน้า:

EXPLAIN SELECT comment_id, user_id, time, LEFT(comment, 20) FROM comments WHERE board_id = 39 ORDER BY time DESC LIMIT 40;

Seq Scan on comments หมายถึง PostgreSQL ต้องไล่ดู Comment ทุก Row เป็นการค้นหาแบบ O(n) ต่อไปมาสร้าง Index ให้ board_id

สร้าง Index

CREATE INDEX ON comments (board_id);

ทีนี้มาเรียกใช้ EXPLAIN อีกครั้ง:

EXPLAIN SELECT comment_id, user_id, time, LEFT(comment, 20) FROM comments WHERE board_id = 39 ORDER BY time DESC LIMIT 40;

คราวนี้ Plan เปลี่ยนเป็น Bitmap Heap Scan PostgreSQL ใช้ Index ช่วยไปยัง Row ที่ต้องการ แทนการสแกนทั้ง Table

ดู Index ทั้งหมดของ Table ได้ด้วย Query นี้

SELECT indexname, indexdef FROM pg_indexes WHERE tablename = 'comments';

Composite Index

ถ้า Query ใช้หลาย Field ร่วมกันบ่อย เช่น board_id กับ time เราสร้าง Composite Index ที่รวมทั้งสอง Field ได้ สำหรับ Query รูปแบบนี้มักทำงานได้ดีกว่าการมี Index แยกสองตัว

CREATE INDEX ON comments (board_id, time);

Unique Index

Unique Index ใช้บังคับให้ค่าใน Field ไม่ซ้ำกัน เช่น Username ซึ่งผู้ใช้สองคนไม่ควรใช้ชื่อเดียวกันได้

CREATE UNIQUE INDEX username_idx ON users (username);

username_idx เป็นชื่อ Index จะตั้งเป็นชื่ออื่นก็ได้

ตอนนี้ลองใส่ชื่อผู้ใช้ที่ซ้ำกัน:

INSERT INTO users (username, email, full_name, created_on) VALUES ('aaizikovj', 'lol@example.com', 'Varis Dara', NOW());

คำสั่งนี้จะล้มเหลวเพราะ Username มีอยู่แล้ว และเมื่อ Field มี Index เราก็ค้นหาด้วย Username ได้เร็วขึ้นด้วย

Full-Text Search

Full-Text Search คือการค้นหาเนื้อหาแบบที่ Search Engine ทำ เช่น ตัดคำที่ไม่มีผลต่อความหมายอย่าง a หรือ the และจับคู่คำตามรูปคำ ไม่ได้เทียบ String ตรง ๆ เพียงอย่างเดียว

PostgreSQL มีความสามารถในการค้นหาข้อความแบบเต็มในตัว สมมติว่าเราต้องการค้นหาความคิดเห็นด้วยคำที่เจาะจง:

SELECT comment_id, LEFT(comment, 50)
FROM comments
WHERE to_tsvector('english', comment) @@ to_tsquery('english', 'love');
  • to_tsvector แปลงข้อความเป็นเวกเตอร์ที่ค้นหาได้ของคำศัพท์ (คำที่ทำให้เป็นมาตรฐาน)
  • to_tsquery แปลงข้อความค้นหาของคุณให้เป็นข้อความค้นหา
  • @@ เป็นตัวดำเนินการ "จับคู่"

ใช้งานได้ แต่ช้าเพราะ PostgreSQL ต้องคำนวณ tsvector สำหรับทุกแถว มาเพิ่มดัชนี:

CREATE INDEX comments_search_idx ON comments USING GIN (to_tsvector('english', comment));

GIN หรือ Generalized Inverted Index เป็น Index ที่เหมาะกับ Full-Text Search เมื่อเพิ่มแล้ว Query เดิมจะทำงานเร็วขึ้นมาก

คุณสามารถค้นหาที่ซับซ้อนมากขึ้นได้เช่นกัน:

-- Search for comments containing "love" AND "dog"
SELECT comment_id, LEFT(comment, 50)
FROM comments
WHERE to_tsvector('english', comment) @@ to_tsquery('english', 'love & dog');

-- Search for "love" OR "hate"
SELECT comment_id, LEFT(comment, 50)
FROM comments
WHERE to_tsvector('english', comment) @@ to_tsquery('english', 'love | hate');

ถ้าระบบค้นหาซับซ้อนมาก เช่น E-commerce ที่ต้องมี Faceted Filter, รองรับคำสะกดผิด และปรับ Relevance อย่างละเอียด อาจเหมาะกับ Search Engine โดยเฉพาะอย่าง Elasticsearch แต่สำหรับหลายแอป Full-Text Search ที่มากับ PostgreSQL ก็เพียงพอและทรงพลังมาก

PostgreSQL ยังมี Index อีกหลายประเภท ให้เลือกตามรูปแบบ Query และข้อมูลของระบบ

ถ้าต้องการศึกษา Query Performance ต่อ ดูรายละเอียดเพิ่มได้จาก บทเรียน Postgres นี้
