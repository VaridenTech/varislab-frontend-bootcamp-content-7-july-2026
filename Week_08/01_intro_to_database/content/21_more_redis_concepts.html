แนวคิด Redis เพิ่มเติม

Redis มีความสามารถอีกมากที่ควรรู้ไว้ หัวข้อต่อไปนี้เหมาะกับกรณีขั้นสูงมาก และไม่ใช่สิ่งที่ทุกระบบจำเป็นต้องใช้

EVAL และ Lua

Redis มี Interpreter สำหรับ Lua ซึ่งเป็นภาษา Script ที่ค่อนข้างเรียบง่าย หากต้องทำหลายคำสั่งพร้อมกันหรือต้องการ Logic มากกว่าคำสั่ง Redis ปกติ Lua เป็นอีกทางเลือกหนึ่ง

อย่างไรก็ตาม เมื่อเริ่มต้องให้ Redis ประมวลผล Lua ควรกลับมาทบทวนการออกแบบ เพราะโดยทั่วไป Business Logic ควรอยู่ในโค้ดของแอป ไม่ใช่ฐานข้อมูล มาลองตัวอย่างเพื่อทำความเข้าใจ

EVAL "for i = 0,9,1 do redis.call('SET', 'lua_key_' .. i, i * 5) end" 0

EVAL ส่ง Lua ให้ Redis ตัวอย่างนี้ Loop เพื่อสร้างสิบ Key ตั้งแต่ lua_key_0 ถึง lua_key_9 ไม่จำเป็นต้องเรียน Lua ทั้งหมดในตอนนี้ เพราะภาษานี้ออกแบบให้เรียนรู้เฉพาะเวลาต้องใช้ได้ง่าย

เลข 0 ตอนท้ายหมายถึงเราไม่ได้แจ้ง Key ที่ Script จะใช้ล่วงหน้า Redis ต้องการข้อมูลนี้ใน Cluster หรือ Sharded Mode เพื่อส่งคำสั่งไปยัง Server ที่ถูกต้อง หากไม่ระบุ Script นี้จะใช้กับ Cluster ไม่ได้ แต่ตัวอย่างของเราทำงานแบบ Server เดียวจึงไม่มีปัญหา

ตัวอย่างที่ซับซ้อนขึ้นใช้ KEYS และ ARGV รับ Key กับ Argument โดย Array ของ Lua เริ่มที่ 1 ไม่ใช่ 0

SET lua_key_name cool_stuff_
EVAL "for i = 0,9,1 do redis.call('SET', redis.call('get', KEYS[1]) .. i, i * ARGV[1]) end" 1 lua_key_name 100

Redis ยังโหลด Script ภายนอกทั้งไฟล์และตรวจด้วย SHA ได้ จึงแยกจัดการ Script เป็นสัดส่วนได้

Pub/Sub

Redis รองรับการส่งข้อความแบบ Publish/Subscribe Client สามารถ Subscribe กลุ่ม Key แล้วรับ Notification เมื่อข้อมูลเปลี่ยน เหมาะกับระบบ Real-time ที่ต้องตอบสนองต่อเหตุการณ์แทนการ Polling อ่านรายละเอียดจาก เอกสาร Pub/Sub

Transaction

บางครั้งเราต้องการให้หลายคำสั่งทำงานทั้งหมดหรือไม่ทำเลย เช่น SET หลาย Key ลบ Key อื่น และเพิ่ม Counter ในชุดเดียว โดยไม่มีคำสั่งจาก Client อื่นแทรกกลาง ลักษณะนี้เรียกว่า Transaction และมีคุณสมบัติ Atomic

Redis ใช้ MULTI, EXEC, DISCARD และ WATCH จัดการ Transaction อ่านต่อได้จาก เอกสาร Transaction

LRU

หากต้องการใช้ Redis เป็น Cache แบบเรียบง่ายที่ขับข้อมูลเก่าออกเมื่อ Memory เต็ม สามารถกำหนดนโยบาย LRU หรือ least recently used ซึ่งจะลบ Key ที่ไม่ได้ถูกใช้งานมานานที่สุดเพื่อให้มีพื้นที่สำหรับข้อมูลใหม่

ลองนึกถึงบริการรูป Profile ที่มีผู้ใช้ 100 ล้านคน รูปทั้งหมดอยู่ในฐานข้อมูลหลัก แต่ต้องการให้ Traffic ส่วนใหญ่ตอบจาก Redis เรากำหนดขนาด Redis เช่น 1 GB แล้วให้โค้ดตรวจ Cache ก่อน ถ้าพบก็ส่งรูปทันที ถ้าไม่พบจึงอ่านฐานข้อมูลหลัก บันทึกลง Redis และส่งให้ผู้ใช้ เมื่อเต็ม Redis จะขับ Key ที่ใช้น้อยที่สุดออก ทำให้รูปยอดนิยมยังอยู่และเพิ่ม Cache Hit Rate

นี่คือพฤติกรรมหลักของ Memcached หากต้องการเพียงเท่านี้และยอม Warm Cache ใหม่เมื่อระบบล่มได้ Memcached อาจเร็วและง่ายกว่า ส่วน Redis มีนโยบายขับ Key หลายรูปแบบให้เลือก อ่านได้จาก เอกสาร Eviction
