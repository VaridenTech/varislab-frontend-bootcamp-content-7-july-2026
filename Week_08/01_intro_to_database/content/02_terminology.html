คำศัพท์พื้นฐานเกี่ยวกับฐานข้อมูล

ก่อนลงมือใช้ฐานข้อมูลแต่ละแบบ เรามาทำความรู้จักคำศัพท์สำคัญกันก่อน จะได้เข้าใจตรงกันว่าแต่ละคำหมายถึงอะไรและเกี่ยวข้องกับงานของเราอย่างไร

Database และ Query

Database คือที่เก็บข้อมูลหรือสถานะของแอป เพื่อให้เราเรียกกลับมาใช้ภายหลังได้ เมื่อแยกข้อมูลไปไว้ใน Database ตัว Server เองก็ไม่จำเป็นต้องจำทุกอย่างไว้ตลอดเวลา ในความหมายกว้าง ๆ แม้แต่ Spreadsheet หรือไฟล์ข้อความก็ถือเป็น Database แบบหนึ่งได้

Query คือคำสั่งที่ส่งไปให้ Database ทำงาน เช่น อ่าน เพิ่ม แก้ไข หรือลบข้อมูล รวมถึงสรุปข้อมูลให้อยู่ในรูปที่เราต้องการ

Schema

Schema คือโครงสร้างหรือ “รูปร่าง” ของข้อมูล ลองนึกถึงตารางใน Excel: Schema จะกำหนดว่าตารางมีคอลัมน์อะไรบ้าง และแต่ละคอลัมน์เก็บข้อมูลแบบไหน

เช่น ออบเจ็กต์ผู้ใช้ { "name": "Brian", "city": "Seattle", "state": "WA" } มี Schema ประกอบด้วย name, city และ state ฐานข้อมูลอย่าง PostgreSQL ต้องกำหนดโครงสร้างไว้ล่วงหน้าค่อนข้างชัดเจน ส่วน MongoDB ยืดหยุ่นกว่าและให้เอกสารแต่ละรายการมีโครงสร้างต่างกันได้

ฐานข้อมูลมีกี่ประเภท

ฐานข้อมูลมีหลายประเภท คอร์สนี้จะเน้น Relational Database หรือ SQL Database, Document Database และ Key-Value Store แต่ยังมีระบบข้อมูลแบบอื่นที่ควรรู้จักไว้ด้วย

  • Graph Database เช่น Neo4j เหมาะกับข้อมูลที่เป็นเครือข่ายความสัมพันธ์ เช่น นักแสดงกับภาพยนตร์ หรือผู้ใช้กับผู้ใช้ในโซเชียล
  • Columnar Database เช่น DuckDB เหมาะกับงานวิเคราะห์ข้อมูลปริมาณมากมากกว่า Transaction ของแอปทั่วไป
  • Search Engine เช่น Solr หรือ Sphinx มักทำงานคู่กับ Database เพื่อรองรับ Full-Text Search โดยเฉพาะ เหมาะกับระบบที่ต้องค้นหาเนื้อหาทั้งเว็บไซต์แต่ Database หลักรองรับได้ไม่ดีพอ
  • Wide-Column Database ยังใช้แนวคิดตาราง แถว และคอลัมน์คล้าย Relational Database แต่แต่ละแถวมีคอลัมน์ต่างกันได้ จึงมองได้ว่าเป็น Key-Value Store สองมิติ ตัวอย่างที่รู้จักกันดีคือ Apache Cassandra และ Google Bigtable ซึ่งออกแบบมาให้ขยายระบบได้ใหญ่และยืดหยุ่นมาก
  • Message Broker ช่วยให้แอปหรือ Service ส่ง Event และ Message หากันแบบไม่ต้องเชื่อมกันโดยตรง เมื่อมีเหตุการณ์เกิดขึ้น Broker จะส่งต่อไปยัง Subscriber ที่สนใจ แนวทางนี้ช่วยให้ระบบยืดหยุ่นและ Scale ได้ง่ายขึ้น ตัวอย่างเช่น Apache Kafka, RabbitMQ และ Celery
  • Multi-Model Database รองรับรูปแบบข้อมูลมากกว่าหนึ่งแนวทางในระบบเดียว เช่น Azure Cosmos DB, SurrealDB และ ArangoDB ส่วน MongoDB กับ PostgreSQL ก็มีความสามารถบางอย่างที่ใช้งานข้ามรูปแบบได้เช่นกัน

ACID

ACID เป็นหลักสำคัญที่มักถูกพูดถึงเมื่อออกแบบ Database แต่ไม่ได้แปลว่าทุก Query ต้องเข้มงวดที่สุดเสมอไป เราต้องเลือกระดับความปลอดภัยให้เหมาะกับต้นทุนและความเร็วของระบบ

ACID ย่อมาจาก Atomicity, Consistency, Isolation และ Durability ซึ่งช่วยให้เราคิดถึงความถูกต้องของการอ่านและเขียนข้อมูลในสี่มุมนี้

  • Atomicity หมายถึงงานหลายขั้นตอนต้องสำเร็จทั้งหมดหรือไม่เกิดขึ้นเลย เช่น การโอนเงินต้องหักจากบัญชีหนึ่งและเพิ่มให้อีกบัญชีพร้อมกัน หากไฟดับระหว่างสองคำสั่ง เราไม่ควรปล่อยให้เงินหายไปกลางทาง
  • Consistency หมายถึงข้อมูลต้องยังถูกต้องตามกฎของระบบ แม้มีหลาย Server หรือเกิดความล้มเหลวระหว่างการทำงาน เช่น Query ที่เขียนเข้า Server หลักแล้วต้องไม่ทำให้ Server สำรองมีข้อมูลขัดแย้งกันจนผู้ใช้เสียเงิน
  • Isolation หมายถึง Query ที่รันพร้อมกันควรให้ผลลัพธ์เหมือนกับการรันทีละคำสั่ง แต่ละงานต้องไม่เห็นสถานะครึ่ง ๆ กลาง ๆ ของอีกงาน
  • Durability หมายถึงเมื่อ Database ยืนยันว่าเขียนข้อมูลสำเร็จแล้ว ข้อมูลนั้นต้องยังอยู่แม้ Server จะล่ม การเขียนลง Disk ช่วยเรื่องนี้ได้ แต่ก็ช้ากว่าการเก็บไว้ใน Memory อย่างเดียว

ไม่ใช่ทุกงานต้องใช้ ACID ระดับสูงสุด เพราะความปลอดภัยที่มากขึ้นมักแลกกับเวลาและทรัพยากร Database หลายตัวจึงเปิดให้กำหนดระดับความเข้มงวดตาม Query ได้ งานการเงินอาจต้องรอให้ข้อมูลถูกเขียนครบทุกสำเนา ส่วนข้อมูลที่สร้างใหม่ได้อาจยอมรับความเสี่ยงเล็กน้อยเพื่อให้ตอบเร็วขึ้น สิ่งสำคัญคือเลือกให้เหมาะกับผลกระทบของงานนั้น

Transaction

Transaction ใช้รวมหลาย Query ให้เป็นงานเดียว Database จะรับประกันว่าทุก Query ใน Transaction สำเร็จทั้งหมดหรือยกเลิกทั้งหมด และไม่ปล่อยให้ Query อื่นแทรกเข้ามาเห็นสถานะระหว่างทาง ตัวอย่างที่ชัดเจนคือการโอนเงิน ซึ่งการหักและเพิ่มยอดต้องเกิดครบทั้งคู่เสมอ
