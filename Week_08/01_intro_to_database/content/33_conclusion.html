สรุปการเลือกใช้ฐานข้อมูล

ยินดีด้วย คุณผ่านเนื้อหาปริมาณมากเกี่ยวกับการเก็บข้อมูลหลายรูปแบบแล้ว ตอนนี้มีบริบทเพียงพอสำหรับตัดสินใจเลือกฐานข้อมูลตามความต้องการ มาทบทวนปัจจัยสำคัญก่อนเลือกใช้งานจริง

รูปแบบของข้อมูล

คำถามแรกคือข้อมูลของเรามีรูปแบบใด

  • ข้อมูลสัมพันธ์กันสูงและต้อง JOIN หลาย Table เหมาะกับ SQL หรือ Relational Database
  • ข้อมูลไม่มีโครงสร้างตายตัว เป็นกลุ่ม Object ที่รูปร่างต่างกัน เหมาะกับ Document Database
  • ข้อมูลอธิบายเครือข่ายความสัมพันธ์ เหมาะกับ Graph Database
  • ต้องการอ่านค่าจาก Key อย่างเรียบง่าย เหมาะกับ Key-Value Store
  • ต้องวิเคราะห์ข้อมูลปริมาณมากเพื่อหา Insight เหมาะกับ OLAP เช่น Columnar Database
  • มี Pipeline ที่ต้องกรอง แยก รวม และเผยแพร่ข้อมูลใหม่ เครื่องมืออย่าง Apache Kafka อาจเหมาะกว่า

ระบบหนึ่งอาจตรงกับบางข้อ หลายข้อ หรือไม่มีข้อใดเลย ควรสำรวจความต้องการข้อมูลทั้งหมดก่อนเลือกเทคโนโลยี

งานอ่านหนักกับงานเขียนหนัก

ปัจจัยนี้มีผลทั้งต่อการเลือกฐานข้อมูลและการออกแบบ Schema ตัวอย่างเช่น หากข้อมูลเชิงสัมพันธ์ถูกอ่านไม่บ่อย แต่กรณีใช้งานส่วนใหญ่เหมาะกับ Document Database การใช้ MongoDB ก็สมเหตุสมผล แม้ JOIN จะไม่เร็วเท่า PostgreSQL

ค้นหา Hotspot ของการอ่านและเขียนแล้ว Optimize จุดนั้น ยอมให้ส่วนที่เรียกไม่บ่อยทำงานช้ากว่าได้ และต้องยืดหยุ่น เพราะก่อนเปิดใช้งานจริงเราแทบคาดเดา Hotspot ทั้งหมดไม่ได้

ความคุ้นเคยของทีม

นักพัฒนามักให้น้ำหนักกับความคุ้นเคยน้อยเกินไป การเรียนเทคโนโลยีใหม่มีต้นทุนทั้งเวลาและความเสี่ยงจากปัญหาที่ทีมยังไม่เคยพบ ครั้งหนึ่งทีมของผู้สอนเลือก MySQL แม้ PostgreSQL กำลังนิยม เพราะทุกคนมีประสบการณ์กับ MySQL และไม่มีใครรู้จัก PostgreSQL ความรู้บางอย่างได้มาจากประสบการณ์เท่านั้น จึงต้องนับเป็นปัจจัยสำคัญ

คุณภาพของ Driver

ตรวจ SDK หรือ Driver ของฐานข้อมูลในภาษาที่โครงการใช้ ต่อให้ฐานข้อมูลยอดเยี่ยม แต่ Driver ของภาษานั้นไม่มีหรือคุณภาพต่ำ ทีมก็ต้องต่อสู้กับเครื่องมือทุกวัน การตรวจล่วงหน้าช่วยลดปัญหาในระยะยาว

ต้นทุน Operations

ฐานข้อมูลมักเป็นส่วนแพงที่สุดของแอป ทั้งค่าใช้จ่าย เวลาเขียนโค้ด และความเสียหายเมื่อระบบล่ม ต้องคิดถึงต้นทุนการจ้างผู้ดูแลที่มีความรู้ในการรัน Server ชนิดนั้นบน Production

Managed Database บน Cloud มีค่าใช้จ่ายตรงสูงกว่า VM แต่ลดงาน Sharding, Cluster, Peering, Election, Network, Firewall, Software Update, OS Update, Capacity และ Scaling ได้มาก ผู้ให้บริการ Cloud รายใหญ่มีตัวเลือกที่ดี อย่างไรก็ตามควรประเมินตามทีม งบประมาณ และข้อกำหนดของระบบ

เลือกเทคโนโลยีที่น่าเบื่อ

Infrastructure หลักควรใช้เทคโนโลยีที่ผ่านการพิสูจน์แล้ว แทนการเลือกเพราะกำลังเป็นกระแส ทุกฐานข้อมูลในคอร์สเติบโตและมั่นคงพอสำหรับงานจริง แต่ทีมต้องทดลอง ใช้งาน พบปัญหา และเรียนรู้จนกลายเป็นเครื่องมือที่คุ้นเคย เทคโนโลยียอดนิยมและมั่นคงยังมีเอกสารจำนวนมาก ทำให้เครื่องมือ AI ช่วยแก้ปัญหาได้ง่ายกว่า

หากจะเลือกเทคโนโลยีใหม่ที่เสี่ยง ต้องมีเหตุผลชัดเจนว่าดีกว่าทางเลือกที่มั่นคงอย่างไร เพราะบน Bleeding Edge คนที่เสียเลือดคือทีมของเราเอง

Cache

Cache เป็นปัญหาที่ยาก อย่าใส่เพียงเพราะคิดว่าน่าจะต้องใช้ ต้องพิสูจน์ก่อนว่าระบบต้องการจริง ๆ เพราะต้องตัดสินใจว่าจะ Cache อะไร นานเท่าใด ล้างเมื่อใด และป้องกันข้อมูลเก่าอย่างไร

Cache มักเป็นเพียงผ้าพันแผลปิดปัญหาประสิทธิภาพ หากปรับ Query หรือ Configuration แล้วเร็วพอ ก็ไม่ควรเพิ่ม Cache ฐานข้อมูลสมัยใหม่รองรับภาระได้สูงเมื่อใช้อย่างถูกต้อง

Cache ยังเพิ่มชั้นทางอ้อม เมื่อ API คืนข้อมูลผิด เราต้องถามว่า “Cache เก่าหรือไม่” หากมีหลายชั้น เช่น Cache ฐานข้อมูล Cache External API และ Cache Response การ Debug ยิ่งยาก รวมถึงต้องรับมือ Thundering Herd แม้บางระบบจำเป็นต้องใช้ Cache แต่ควรทำให้เรียบง่ายที่สุด

โปรเจกต์ฝึกฝน

  • ขยายแอปตัวอย่างทั้งสี่ให้ใหญ่ขึ้นและใช้ฐานข้อมูลมากกว่าหนึ่งชนิดร่วมกัน
  • เลือก Dataset ฟรีจาก Kaggle หรือ Hugging Face แล้วทดลองออกแบบ Schema และ Query
  • แม้ปกติไม่สร้างแอป Transaction บน DuckDB แต่สามารถสร้าง Dashboard สำหรับข้อมูล OLAP ได้
