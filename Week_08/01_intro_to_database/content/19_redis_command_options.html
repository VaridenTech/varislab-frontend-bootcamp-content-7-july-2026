ตัวเลือกคำสั่ง Redis

NX และ XX

ตัวเลือกสองตัวนี้ใช้สั่ง Redis ว่า “ให้ล้มเหลวถ้า Key นี้มีอยู่แล้ว” หรือ “ให้ล้มเหลวถ้า Key นี้ยังไม่มี” ซึ่งมีประโยชน์เมื่อต้องเขียนข้อมูลแบบมีเงื่อนไข

Comment ที่ขึ้นต้นด้วย # ในตัวอย่างไม่ใช่ Syntax ที่ Redis รองรับ จึงไม่ควร Copy ไปพร้อมคำสั่ง

SET color blue XX # fails because it doesn't exist yet
SET color blue NX # succeeds because it didn't exist
SET color blue XX # succeeds because it does exist
SET color blue NX # fails because it does exist

จำง่าย ๆ ว่า NX สำเร็จเมื่อ Key not exists ส่วน XX ทำงานในกรณีตรงกันข้าม เราจึงเขียนตัวสำรวจพิกัดจากบทก่อนหน้าใหม่ได้ดังนี้

SET plane:0:0 visited NX # succeeds
SET plane:1:0 visited NX # succeeds
SET plane:0:0 visited NX # fails
SET plane:1:1 visited NX # succeeds

เพียงตรวจว่าการเขียนสำเร็จหรือล้มเหลวก็ทราบได้ว่าเคยผ่านตำแหน่งนั้นหรือยัง

TTL

TTL ย่อจาก time to live หมายถึงอายุของ Key เมื่อครบเวลา Redis จะลบ Record ให้อัตโนมัติ MongoDB และ PostgreSQL ก็ทำได้เช่นกัน แต่ความสามารถนี้สำคัญมากกับ Cache

สมมติแอป Fitness ต้องคำนวณสถิติการออกกำลังกายที่ใช้ทรัพยากรสูง เราไม่อยากคำนวณซ้ำทุกครั้งที่ผู้ใช้ Refresh แต่ข้อมูลที่เก่ากว่าหนึ่งชั่วโมงก็ไม่ควรนำมาใช้ จึงเขียน Cache แบบนี้

SET fitness:total:btholt 750kj EX 3600

Key fitness:total:btholt จะหมดอายุหลัง 3,600 วินาที โดย EX กำหนดเวลาเป็นวินาที ในโค้ดให้ลองอ่าน Cache ก่อน ถ้าพบแปลว่ายังใช้ได้ ถ้าไม่พบจึงคำนวณใหม่ นอกจากนี้ยังมี PX สำหรับหน่วย Millisecond

ทดลองดูการหมดอายุภายในห้าวินาทีได้ดังนี้

SET test_expire hi EX 5
EXISTS test_expire

หลังห้าวินาที EXISTS จะคืนค่าเท็จ เทคนิคนี้นำไปใช้กับกลยุทธ์ Cache ได้หลายรูปแบบ

ปัญหา Thundering Herd

ต้องระวังปัญหา Thundering Herd สมมติ Cache หมดอายุพอดีกับที่ผู้ใช้ 1,000 คนเปิดหน้าเดียวกัน Server จะ Cache Miss 1,000 ครั้งและเริ่มคำนวณคำตอบซ้ำพร้อมกัน 1,000 งาน การทำ Cache จึงมีความซับซ้อนกว่าที่เห็น

ตัวอย่างนี้ผูก Cache กับผู้ใช้รายเดียวจึงมีโอกาสน้อย แต่หากหลายคนอาจ Miss Key เดียวกัน ต้องออกแบบการป้องกัน วิธีหนึ่งคือให้ Server อ่านจาก Cache อย่างเดียว และใช้ Background Job แยกต่างหากคอยอัปเดต Cache ล่วงหน้า ซึ่งกรณีนี้อาจไม่ต้องใช้ TTL
