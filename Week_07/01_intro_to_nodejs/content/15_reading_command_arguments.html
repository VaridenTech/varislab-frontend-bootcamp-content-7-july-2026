การรับคำสั่งจาก process.argv

บทที่ 9 เราอ่านค่าหนึ่งตัวจาก process.argv[2] ได้แล้ว แต่แอปของเราต้องรองรับมากกว่าการเพิ่มรายการ รูปแบบที่อยากได้คือ:

todo add "ซื้อนม"
todo list
todo done 3
todo remove 3
todo web

สังเกตว่าคำแรกหลัง todo คือคำสั่ง (add, list, done, remove, web) และคำที่สองคือข้อมูลเพิ่มเติมของคำสั่งนั้น ซึ่งบางคำสั่งก็ไม่ต้องมี

process.argv มีอะไรอยู่ข้างในบ้าง

ก่อนจะเขียนอะไร มาดูกันก่อนว่า process.argv หน้าตาเป็นยังไง ลอง console.log(process.argv) แล้วรัน todo add "ซื้อนม" ดู:

[
  '/usr/local/bin/node',
  '/Users/you/todo/index.js',
  'add',
  'ซื้อนม'
]

สองตัวแรกคือ Path ของ Node.js และ Path ของไฟล์เรา ซึ่งเราไม่ได้ใช้ ตัวที่เราสนใจคือตั้งแต่ตัวที่สามเป็นต้นไป เราจึงใช้ slice(2) เพื่อตัดสองตัวแรกทิ้ง:

const [command, arg] = process.argv.slice(2)

บรรทัดเดียวก็พอ เราใช้ Array Destructuring ดึงค่าออกมาใส่สองตัวแปร ถ้ารัน todo add "ซื้อนม" ค่า command จะเป็น 'add' และ arg จะเป็น 'ซื้อนม' แต่ถ้ารันเพียง todo list ค่า arg จะเป็น undefined

แยกการทำงานด้วย switch

เมื่อรู้แล้วว่าผู้ใช้พิมพ์คำสั่งอะไรมา เราก็แค่ต้องเลือกว่าจะทำอะไรต่อ ซึ่งงานแบบนี้ switch เหมาะที่สุด ในไฟล์ index.js:

#!/usr/bin/env node

const [command, arg] = process.argv.slice(2)

switch (command) {
  case 'add': {
    console.log('จะเพิ่ม:', arg)
    break
  }
  case 'list': {
    console.log('จะแสดงรายการทั้งหมด')
    break
  }
  case 'done': {
    console.log('จะทำเครื่องหมายว่าเสร็จ:', arg)
    break
  }
  case 'remove': {
    console.log('จะลบ:', arg)
    break
  }
  case 'web': {
    console.log('จะเปิดเว็บ')
    break
  }
  default: {
    console.log('คำสั่งที่ใช้ได้: add, list, done, remove, web')
  }
}

ลองรันดูได้เลย ทุกคำสั่งควรจะตอบกลับมาถูกตัว และถ้าพิมพ์คำสั่งมั่ว ๆ หรือไม่พิมพ์อะไรเลย default จะทำงานแล้วบอกผู้ใช้ว่ามีคำสั่งอะไรให้ใช้บ้าง

ทำไมต้องมี break และวงเล็บปีกกา

  • break จำเป็นมาก ถ้าลืมใส่ โปรแกรมจะไหลลงไปทำ case ถัดไปต่อด้วย (เรียกว่า Fall-through) ซึ่งไม่ใช่สิ่งที่เราต้องการ
  • วงเล็บปีกกา { } รอบเนื้อหาของแต่ละ case ไม่ได้บังคับ แต่ใส่ไว้ดีกว่า เพราะมันทำให้เราประกาศตัวแปรด้วย const ข้างในแต่ละ case ได้โดยไม่ชนกัน

ก้าวต่อไป

ตอนนี้โครง CLI ครบแล้ว แม้แต่ละคำสั่งจะยังแค่ console.log เพราะเรายังไม่มีที่เก็บข้อมูล บทต่อไปเราจะเรียนเรื่อง Asynchronous และการอ่านเขียนไฟล์ ก่อนกลับมาเติมให้ทุกคำสั่งทำงานจริง
