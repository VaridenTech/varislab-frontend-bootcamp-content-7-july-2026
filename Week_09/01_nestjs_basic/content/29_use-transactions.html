ใช้ Transactions

เมื่อจบบทนี้ คุณจะสามารถ

  • อธิบายได้ว่า transaction แก้ปัญหาอะไร และเมื่อไหร่ที่การ save สองครั้งติดกันไม่พอ
  • สร้าง Event entity สำหรับเก็บเหตุการณ์ในระบบด้วย Nest CLI
  • ใช้ QueryRunner คุมวงจร startTransaction → commit/rollback → release ได้ครบถ้วน

งานที่ต้องสำเร็จด้วยกันหรือล้มด้วยกัน

Transaction คือหน่วยของงานฐานข้อมูลที่ต้องเกิดผลแบบ all-or-nothing สมมติเราเพิ่มฟีเจอร์ "แนะนำกาแฟ" ที่ต้องทำสองอย่าง: เพิ่มตัวนับ recommendations ของกาแฟ และบันทึกแถว event ลงอีกตารางเพื่อ analytics ถ้า save แรกสำเร็จแต่ตัวที่สองล้ม ข้อมูลจะค้างอยู่ในสภาพครึ่ง ๆ กลาง ๆ ที่เชื่อถือไม่ได้ — transaction ทำให้ทั้งคู่ commit พร้อมกัน หรือ rollback กลับทั้งหมด

เริ่มจากสร้าง entity สำหรับเก็บ event (และเพิ่มคอลัมน์ recommendations: number เข้า Coffee entity ด้วย @Column({ default: 0 }))

nest g class events/entities/event.entity --no-spec
import { Column, Entity, PrimaryGeneratedColumn } from 'typeorm';

@Entity()
export class Event {
  @PrimaryGeneratedColumn()
  id: number;

  @Column()
  type: string;

  @Column()
  name: string;

  @Column('json')
  payload: Record<string, any>;
}

QueryRunner: คุม transaction ด้วยมือ

ฉีด Connection (ใน TypeORM รุ่นใหม่คือ DataSource) เข้า service แล้วสร้าง QueryRunner ของตัวเองเมื่อจะเริ่ม transaction — ทุก operation ภายในต้องเรียกผ่าน queryRunner.manager เท่านั้น จึงจะอยู่ใน transaction เดียวกัน

import { Connection } from 'typeorm';
import { Event } from '../events/entities/event.entity';

@Injectable()
export class CoffeesService {
  constructor(private readonly connection: Connection) {}

  async recommendCoffee(coffee: Coffee) {
    const queryRunner = this.connection.createQueryRunner();

    await queryRunner.connect();
    await queryRunner.startTransaction();
    try {
      coffee.recommendations++;

      const recommendEvent = new Event();
      recommendEvent.name = 'recommend_coffee';
      recommendEvent.type = 'coffee';
      recommendEvent.payload = { coffeeId: coffee.id };

      await queryRunner.manager.save(coffee);
      await queryRunner.manager.save(recommendEvent);

      await queryRunner.commitTransaction();
    } catch (err) {
      await queryRunner.rollbackTransaction();
    } finally {
      await queryRunner.release();
    }
  }
}

โครง try/catch/finally นี้คือหัวใจของบท:

  • try — ทำงานทั้งหมดผ่าน queryRunner.manager แล้ว commitTransaction() เมื่อครบ
  • catch — อะไรพังกลางทาง rollbackTransaction() ยกเลิกทุกอย่างที่ทำไปแล้ว
  • finally — release() คืน connection กลับ pool เสมอ ไม่ว่าสำเร็จหรือล้ม

ลืม release() คือ bug แบบเงียบที่อันตรายที่สุดของ QueryRunner: connection จะรั่วออกจาก pool ทีละอันจนแอปค้างทั้งระบบเมื่อ pool หมด ใส่ไว้ใน finally ทุกครั้งโดยไม่มีข้อยกเว้น

อย่าลืมลงทะเบียน Event ผ่าน forFeature ใน module ที่เกี่ยวข้อง เพื่อให้ synchronize สร้างตาราง event ให้ และเพิ่ม endpoint ทดลอง เช่น POST /coffees/:id/recommend ที่เรียก recommendCoffee เพื่อใช้ทดสอบ

ทำให้การแนะนำกาแฟเป็น atomic

เพิ่มคอลัมน์ recommendations, สร้าง Event entity, เขียน recommendCoffee ตามโค้ดด้านบน แล้วต่อ endpoint ทดลองใน controller

# สร้าง entity nest g class events/entities/event.entity --no-spec # ทดสอบ POST http://localhost:3000/coffees/1/recommend GET http://localhost:3000/coffees/1 # ดูในฐานข้อมูล SELECT * FROM event;

ผลลัพธ์ที่คาดหวัง

ทุกครั้งที่ยิง recommend ค่า recommendations ของกาแฟเพิ่มขึ้น 1 และ ตาราง event ได้แถวใหม่ที่ payload ระบุ coffeeId เสมอ — สองตารางขยับพร้อมกันทุกครั้ง ถ้าจงใจทำให้ save ตัวที่สองพัง (เช่น ตั้ง recommendEvent.name = null ชั่วคราว) ตัวนับต้องไม่เพิ่ม เพราะโดน rollback ทั้งก้อน

ตรวจว่าใช้งานได้จริง

  • ยิง recommend 3 ครั้ง — recommendations เป็น 3 และตาราง event มี 3 แถว เท่ากันเป๊ะ
  • ทดลอง sabotage ให้ save ที่สองล้ม — ตัวนับไม่ขยับและไม่มีแถว event ใหม่ (แล้วแก้กลับ)
  • แอปยังรับคำขออื่นได้ปกติหลังทดลองหลายรอบ แสดงว่า connection ถูก release ครบ ไม่มีรั่ว
  • ทุก operation ใน transaction เรียกผ่าน queryRunner.manager ไม่ใช่ repository ปกติ
