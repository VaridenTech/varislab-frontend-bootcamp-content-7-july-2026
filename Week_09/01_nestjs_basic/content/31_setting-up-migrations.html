ตั้งค่า Migrations

เมื่อจบบทนี้ คุณจะสามารถ

  • อธิบายได้ว่าทำไม production ต้องใช้ migrations แทน synchronize: true
  • สร้างไฟล์ migration ด้วย TypeORM CLI และเขียนเมธอด up/down ให้ย้อนกลับได้
  • รัน, revert และ generate migrations จากโค้ดที่ build แล้วใน dist/

ทำไมต้องมี Migrations

ตลอดบทที่ผ่านมาเราเปิด synchronize: true ให้ TypeORM ปรับ schema ของฐานข้อมูลตาม entity โดยอัตโนมัติ ซึ่งสะดวกมากตอนพัฒนา แต่บน production ถือว่าอันตราย: การเปลี่ยนชื่อ property เพียงตัวเดียวอาจทำให้ TypeORM ตัดสินใจ drop column แล้วสร้างใหม่ ข้อมูลจริงของผู้ใช้จะหายทันที Migration คือไฟล์ที่บันทึกการเปลี่ยนแปลง schema เป็นขั้น ๆ อย่างชัดเจน ทำให้เราควบคุมได้ว่าจะเปลี่ยนอะไร เมื่อไหร่ และย้อนกลับอย่างไร

ก่อนใช้ migrations จริง ให้ปิด synchronize ในสภาพแวดล้อมที่ไม่ใช่ development เสมอ มิฉะนั้น TypeORM จะแก้ schema แข่งกับ migration ของเรา

สร้าง DataSource สำหรับ TypeORM CLI

TypeORM CLI ทำงานนอก NestJS application จึงต้องมีไฟล์ config ของตัวเองที่ประกาศ DataSource ชี้ไปฐานข้อมูลเดียวกับแอปของเรา สร้างไฟล์ typeorm-cli.config.ts ที่ root ของโปรเจกต์

/* typeorm-cli.config.ts */
export default new DataSource({
  type: 'postgres',
  host: 'localhost',
  port: 5432,
  username: 'postgres',
  password: 'pass123',
  database: 'postgres',
  entities: [],
  migrations: [],
});

เมื่อมี entity หรือ migration ที่เกี่ยวข้องกับการ generate ให้เพิ่มเข้า array entities และ migrations ตามลำดับ เพื่อให้ CLI มองเห็น schema ปัจจุบัน

สร้างและเขียน Migration แรก

ใช้คำสั่ง migration:create เพื่อสร้างไฟล์เปล่าใน src/migrations โดยชื่อท้ายคำสั่งคือชื่อที่เราตั้งให้ migration นั้น

npx typeorm migration:create src/migrations/CoffeeRefactor

ในไฟล์ที่ได้ เขียนสิ่งที่ต้องเปลี่ยนใน up และวิธีย้อนกลับใน down — ทั้งสองฝั่งต้องสมมาตรกันเสมอ ตัวอย่างนี้เปลี่ยนชื่อ column name เป็น title ของตาราง coffee

public async up(queryRunner: QueryRunner): Promise<any> {
  await queryRunner.query(
    `ALTER TABLE "coffee" RENAME COLUMN "name" TO "title"`,
  );
}

public async down(queryRunner: QueryRunner): Promise<any> {
  await queryRunner.query(
    `ALTER TABLE "coffee" RENAME COLUMN "title" TO "name"`,
  );
}

รัน, Revert และให้ TypeORM Generate ให้

CLI รัน migration จากไฟล์ JavaScript ที่ compile แล้ว ไม่ใช่ TypeScript โดยตรง จึงต้อง npm run build ให้ทุกอย่างออกไปอยู่ใน dist/ ก่อนเสมอ

# compile โปรเจกต์ก่อน
npm run build

# รัน migration ทั้งหมดที่ยังไม่ถูก apply
npx typeorm migration:run -d dist/typeorm-cli.config

# ย้อนกลับ migration ล่าสุด
npx typeorm migration:revert -d dist/typeorm-cli.config

# ให้ TypeORM เทียบ entity กับ schema แล้ว generate migration ให้อัตโนมัติ
npx typeorm migration:generate src/migrations/SchemaSync -d dist/typeorm-cli.config

migration:generate ช่วยเขียน SQL ให้เองโดยเทียบ entity ปัจจุบันกับ schema ในฐานข้อมูล เหมาะกับการเปลี่ยนแปลงทั่วไป แต่ควรเปิดไฟล์ที่ได้มาตรวจทุกครั้งก่อนรันจริง โดยเฉพาะคำสั่งที่ drop ข้อมูล

เปลี่ยนชื่อ column แบบไม่ทำข้อมูลหาย

ในโปรเจกต์ iluvcoffee สร้างไฟล์ typeorm-cli.config.ts แล้วเขียน migration CoffeeRefactor เปลี่ยน column name เป็น title จากนั้น build, รัน migration และทดลอง revert กลับหนึ่งครั้ง

npx typeorm migration:create src/migrations/CoffeeRefactor npm run build npx typeorm migration:run -d dist/typeorm-cli.config npx typeorm migration:revert -d dist/typeorm-cli.config

ผลลัพธ์ที่คาดหวัง

ตอน migration:run terminal แสดง SQL ที่ถูก execute และชื่อ migration ที่สำเร็จ ตาราง coffee มี column title แทน name โดยข้อมูลเดิมยังอยู่ครบ และเมื่อ revert คอลัมน์กลับเป็น name เหมือนเดิม TypeORM ยังสร้างตาราง migrations ไว้บันทึกว่า migration ใดถูก apply ไปแล้ว

ตรวจว่าใช้งานได้จริง

  • เปิด GUI จากบทที่ 21 แล้วดูตาราง coffee ว่า column เปลี่ยนตาม migration และแถวข้อมูลเดิมไม่หาย
  • ตรวจตาราง migrations ว่ามีแถวบันทึกชื่อ CoffeeRefactor หลังรัน และหายไปหลัง revert
  • ลองรัน migration:run ซ้ำ — ต้องไม่มีอะไรถูกรันซ้ำ เพราะ TypeORM รู้ว่า apply ไปแล้ว
  • ลอง migration:generate หลังแก้ entity เล็กน้อย แล้วเปิดไฟล์ที่ได้มาอ่าน SQL ก่อนตัดสินใจรัน
