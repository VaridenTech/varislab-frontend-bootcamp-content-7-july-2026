เพิ่ม Indexes ให้ Entities

เมื่อจบบทนี้ คุณจะสามารถ

  • อธิบายได้ว่า index ช่วยให้ query เร็วขึ้นอย่างไร และต้องแลกกับอะไร
  • ติด @Index() บนคอลัมน์เดียวที่ถูกใช้ค้นหาบ่อย
  • สร้าง composite index หลายคอลัมน์ที่ระดับ class เมื่อ query ค้นด้วยหลายเงื่อนไขพร้อมกัน

Index คือสารบัญของตาราง

เวลา query ค้นหาจากคอลัมน์ที่ไม่มี index ฐานข้อมูลต้องไล่สแกนทุกแถว (full table scan) ซึ่งช้าลงเรื่อย ๆ ตามขนาดตาราง Index คือโครงสร้างข้อมูลเสริมที่ทำหน้าที่เหมือนสารบัญหนังสือ: แทนที่จะพลิกทุกหน้า ฐานข้อมูลกระโดดไปยังแถวที่ต้องการได้ทันที primary key อย่าง id ได้ index อัตโนมัติอยู่แล้ว แต่คอลัมน์อื่นที่เราค้นบ่อย — เช่น name ของ Event ที่ระบบ analytics ต้อง filter ตลอดเวลา — ต้องประกาศเอง

import { Column, Entity, Index, PrimaryGeneratedColumn } from 'typeorm';

@Entity()
export class Event {
  @PrimaryGeneratedColumn()
  id: number;

  @Column()
  type: string;

  @Index() // สร้าง index ให้คอลัมน์ name
  @Column()
  name: string;

  @Column('json')
  payload: Record<string, any>;
}

Composite index เมื่อค้นหลายคอลัมน์พร้อมกัน

ถ้า query ของเรามักค้นด้วยสองเงื่อนไขคู่กัน เช่น WHERE name = ... AND type = ... การมี index แยกสองอันยังไม่ optimal เท่า composite index ที่ครอบทั้งสองคอลัมน์ในโครงสร้างเดียว ซึ่งประกาศที่ระดับ class โดยส่ง array ของชื่อคอลัมน์

@Index(['name', 'type']) // composite index ครอบสองคอลัมน์
@Entity()
export class Event {
  // ...
}
รูปแบบประกาศที่เหมาะกับ
@Index() บน propertyเหนือ @Column() ของคอลัมน์นั้นquery ที่ filter จากคอลัมน์นั้นเดี่ยว ๆ บ่อย
@Index(['a', 'b']) บน classเหนือ @Entity()query ที่ filter สองคอลัมน์นั้นร่วมกันเป็นประจำ

Index ไม่ใช่ของฟรี: ทุก insert/update ต้องอัปเดต index ด้วย และแต่ละ index กินพื้นที่จัดเก็บเพิ่ม จึงควรเพิ่มเฉพาะคอลัมน์ที่มี query pattern รองรับจริง ไม่ใช่ติดทุกคอลัมน์กันเหนียว

บนเครื่อง dev ที่เปิด synchronize: true อยู่ index จะถูกสร้างในฐานข้อมูลทันทีที่ save ไฟล์ ใน production การเพิ่ม index เป็นการเปลี่ยน schema ที่ต้องทำผ่าน migration — บทถัดไปพอดี

ทำให้การค้น event เร็วขึ้น

เพิ่ม @Index() ให้คอลัมน์ name ของ Event entity แล้วทดลอง composite index ['name', 'type'] ที่ระดับ class จากนั้นไปดู index ที่เกิดขึ้นจริงในฐานข้อมูล

# หลัง save ไฟล์และแอป restart แล้ว - ดู index ใน pgAdmin Query Tool SELECT indexname, indexdef FROM pg_indexes WHERE tablename = 'event';

ผลลัพธ์ที่คาดหวัง

ผลของ query แสดง index ของตาราง event อย่างน้อย 3 รายการ: primary key ของ id, index ของ name และ composite index ที่ครอบ name กับ type — ทั้งหมดถูกสร้างจาก decorator ใน entity โดยตรง

ตรวจว่าใช้งานได้จริง

  • pg_indexes ของตาราง event มี index ใหม่ปรากฏหลังแอป restart
  • indexdef ของ composite index ระบุทั้งสองคอลัมน์ (name, type)
  • ลองรัน EXPLAIN SELECT * FROM event WHERE name = 'recommend_coffee'; — plan ควรอ้างถึง index scan เมื่อตารางมีข้อมูลมากพอ
  • แอปยัง start และ CRUD ได้ตามปกติ ไม่มี error จากการประกาศ index
