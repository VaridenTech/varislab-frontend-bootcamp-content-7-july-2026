ใช้ Nested Writes สร้างและอัปเดตพร้อม Relation

เมื่อจบบทนี้ คุณจะสามารถ

  • อธิบายได้ว่า nested write คืออะไร และแยกความต่างของ create, connect และ connectOrCreate
  • ใช้ connectOrCreate reuse flavor เดิมหรือสร้างใหม่เมื่อยังไม่มี โดยอาศัยฟิลด์ @unique
  • ปรับ create และ update ให้บันทึกกาแฟพร้อม flavors ได้ในคำขอเดียว และใช้ set: [] แทนที่ชุด relation เดิม

ให้การบันทึกกาแฟพา flavor ไปด้วย

ตอนนี้ POST /coffees พร้อม flavors ยังไม่บันทึกความสัมพันธ์ลงตารางเชื่อม (และ type-check ยังไม่ผ่านตั้งแต่บทที่ 25) เพราะ Prisma ไม่รับ array ของ string ใส่ relation field ตรง ๆ สิ่งที่ Prisma ต้องการคือ nested write: ใน data ของ create/update เดียวกัน เราบอกได้เลยว่าจะทำอะไรกับ model ปลายทาง — Prisma รวมทั้งหมดเป็นการเขียนก้อนเดียวที่สำเร็จหรือล้มไปพร้อมกัน โดยไม่ต้องเปิด option cascade อะไรเพิ่ม

คำสั่งทำอะไรเหมาะกับ
createสร้างแถวใหม่ใน model ปลายทางแล้วผูกให้ทันทีของที่ไม่มีทางซ้ำ เช่น comment ใหม่ของโพสต์
connectผูกกับแถวที่มีอยู่แล้ว โดยอ้างด้วยฟิลด์ unique (id หรือ @unique อื่น)เมื่อรู้แน่ว่าปลายทางมีอยู่ ไม่มีก็ให้ error
connectOrCreateค้นด้วยฟิลด์ unique ก่อน เจอก็ผูกตัวเดิม ไม่เจอจึงสร้างใหม่แล้วผูกข้อมูลอ้างอิงที่ใช้ซ้ำ เช่น tag หรือ flavor ของเรา

ทั้ง connect และ connectOrCreate ต้องค้นด้วยฟิลด์ที่ unique เท่านั้น — นี่คือเหตุผลที่บทที่ 25 เราใส่ @unique ให้ Flavor.name ไว้ล่วงหน้า ทำให้ไม่ต้องเขียน helper "หา flavor จากชื่อ ถ้าไม่มีค่อยสร้าง" เองอีกเลย

reuse flavor เดิม อย่าสร้างซ้ำ

ก่อนส่ง data ให้ Prisma ต้อง destructure flavors ออกจาก DTO ก่อน เพราะ field นี้ใน data ไม่ใช่ array ของ string อีกแล้ว แต่เป็น object ที่บอกคำสั่ง nested write จากนั้น map ชื่อแต่ละตัวเป็นคู่ where/create ให้ connectOrCreate

import { Injectable, NotFoundException } from '@nestjs/common';
import { PrismaService } from '../prisma/prisma.service.js';
import { CreateCoffeeDto } from './dto/create-coffee.dto.js';
import { UpdateCoffeeDto } from './dto/update-coffee.dto.js';

@Injectable()
export class CoffeesService {
  constructor(private readonly prisma: PrismaService) {}

  create(createCoffeeDto: CreateCoffeeDto) {
    const { flavors, ...data } = createCoffeeDto;
    return this.prisma.coffee.create({
      data: {
        ...data,
        flavors: {
          connectOrCreate: flavors.map((name) => ({
            where: { name },
            create: { name },
          })),
        },
      },
      include: { flavors: true },
    });
  }

  async update(id: string, updateCoffeeDto: UpdateCoffeeDto) {
    await this.findOne(id);
    const { flavors, ...data } = updateCoffeeDto;
    return this.prisma.coffee.update({
      where: { id: +id },
      data: {
        ...data,
        ...(flavors && {
          flavors: {
            set: [], // ตัดความสัมพันธ์เดิมทั้งหมดก่อน
            connectOrCreate: flavors.map((name) => ({
              where: { name },
              create: { name },
            })),
          },
        }),
      },
      include: { flavors: true },
    });
  }

  // findAll / findOne / remove คงเดิมจากบทที่ 26
}

ใน update มีสองจุดที่ต้องอ่านให้ขาด: set: [] สั่งให้ตัด join row ทั้งหมดของกาแฟตัวนี้ทิ้งก่อน แล้ว connectOrCreate ค่อยผูกชุดใหม่เข้าไป — ผลคือ "แทนที่ทั้งชุด" ไม่ใช่ "เพิ่มต่อท้าย" ส่วนเงื่อนไข flavors && {...} สำคัญมาก: PATCH ที่ไม่ได้ส่ง flavors มาจะได้ undefined และ spread ของ undefined คือไม่ใส่อะไรเลย relation เดิมจึงไม่ถูกแตะ — ส่งมาเมื่อไหร่จึงค่อยแทนที่

set: [] ตัดแค่แถวในตารางเชื่อม _CoffeeToFlavor เท่านั้น ไม่เคยลบแถวในตาราง flavor — flavor ที่ไม่มีกาแฟตัวไหนใช้แล้วจะยังอยู่ ไม่มีเรื่อง orphan ถูกลบโดยไม่ตั้งใจให้ต้องกังวล และการใส่ include: { flavors: true } ท้าย create/update ทำให้ response คืน flavors ที่ผูกแล้วกลับมาทันทีโดยไม่ต้อง query ซ้ำ

connectOrCreate ทำงานเป็นสองขั้น (ค้นแล้วค่อยสร้าง) ดังนั้นถ้ามีคำขอจำนวนมากสร้าง flavor ชื่อเดียวกันพร้อมกันเป๊ะ อาจมีตัวหนึ่งชน unique constraint ได้ (Prisma docs ระบุไว้) สำหรับแอปนี้ไม่ใช่ปัญหา แต่ในระบบที่ concurrent สูงต้องเผื่อ retry หรือจัดการ error ตรงนั้น

สร้างกาแฟพร้อม flavors ในคำขอเดียว

แทนที่ create/update ใน CoffeesService ด้วยโค้ดด้านบน (ลบโค้ดที่คอมเมนต์ไว้ตั้งแต่บทที่ 25 ออก) ตรวจว่า TypeScript compile ผ่านแล้ว จากนั้นทดสอบ

POST http://localhost:3000/coffees { "name": "Shipwreck Roast", "brand": "Buddy Brew", "flavors": ["chocolate", "vanilla"] } # ยิงซ้ำอีกครั้งด้วย flavor เดิมบางตัว POST http://localhost:3000/coffees { "name": "Salemander Roast", "brand": "Buddy Brew", "flavors": ["chocolate", "caramel"] }

ผลลัพธ์ที่คาดหวัง

คำขอแรกสร้างกาแฟพร้อม flavor chocolate และ vanilla ในตาราง flavor คำขอที่สอง reuse แถว chocolate เดิม (id เดิม) และสร้างเฉพาะ caramel เพิ่ม — ตาราง flavor มี 3 แถว ไม่ใช่ 4 และ _CoffeeToFlavor ผูกความสัมพันธ์ครบทุกคู่ response ของทั้งสองคำขอมี flavors เป็น object พร้อม id กลับมาทันที

ตรวจว่าใช้งานได้จริง

  • POST พร้อม flavors แล้ว GET /coffees เห็น flavors กลับมาเป็น object ที่มี id จริง
  • ตาราง flavor ไม่มีชื่อซ้ำ แม้จะ POST ด้วย flavor เดิมหลายครั้ง
  • PATCH โดยไม่ส่ง flavors — relation เดิมต้องไม่หาย; PATCH พร้อม flavors ชุดใหม่ — ต้องแทนที่ชุดเดิม และแถวใน flavor ที่ถูกถอดออกยังอยู่
  • npm run start:dev compile ผ่านไม่มี type error — ข้อผิดพลาดชั่วคราวจากบทที่ 25 หายไปแล้ว
